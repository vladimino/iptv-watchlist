# Agent delivery workflow

This document is the durable collaboration policy for the IPTV Watchlist project. It does **not** track today's active Trello card, latest PR, deployment version, or production feature flags. Those must be checked live. For code-agent Git preflight and repository safety, also follow [AGENTS.md](../../AGENTS.md); for Trello formatting follow [trello-card-conventions.md](trello-card-conventions.md).

## ADR pre-merge decision gate

An ADR must not be merged with `Status: Proposed`. Before the ADR PR is merged, the owner explicitly decides `Accepted` or `Declined`; the ADR file and register must reflect that decision in the same PR, with an identifiable approval source. Independent technical review or the merge of a design proposal does **not** constitute owner acceptance. A `Declined` ADR is recorded as a rejected decision and does not authorize implementation. Accepting an ADR approves its documented architecture only; it does not authorize production flags, data writes, migration, task edits, or cutover. This gate applies even when the code/documentation changes are otherwise green. An administrative correction to a previously merged Proposed ADR is separate from ongoing authorized implementation and must not block unrelated or owner-authorized successor work.

## Roles and sources of truth

- **Owner:** approves goals, non-routine scope and production-risk actions; may have several ChatGPT conversations working on independent streams.
- **Cursor / coding agent:** implements a bounded card, writes tests/docs, creates a PR and reports evidence. Do not assume the coding agent's summary replaces review.
- **ChatGPT delivery coordinator / reviewer:** checks Trello and GitHub firsthand, maintains the board, reviews changes, provides ready-to-send Cursor instructions, merges approved work, watches deployment, verifies acceptance, documents completion and advances the approved queue.
- **Trello:** current card status, approved ordering, native prerequisites, scoped acceptance criteria and operational discussion. Inspect the *actual* linked cards, not IDs inferred from memory; IDs can collide across independent streams.
- **GitHub:** the latest source, code diff, review threads, CI/CD runs and technical documentation. GitHub main is canonical code, but a successful commit is not proof of an enabled production feature.
- **Production evidence:** safe, authorized status and diagnostic reads; source-of-truth, flag and schedule state must be verified for the relevant decision. Historical snapshots are not live evidence.

At the start of work, read the relevant current card and latest comments, its native checklist and linked upstream/downstream cards, the current PR/commits and CI, plus affected runbooks. Do not reuse a previous-session handoff as a current board snapshot. Separate parallel delivery streams, and do not take over another stream's cards unless authorized.

## Language and public-repository boundary

- **Trello:** Russian for cards, comments, dependencies, delivery reports, and instructions intended for Cursor.
- **GitHub:** English for PR descriptions, review summaries, inline review comments, code discussions, and repository documentation.
- **Technical names:** preserve function/class names, API paths, field names, error/reason codes, commit SHAs, and other identifiers exactly.
- **ChatGPT conversation:** Russian by default, unless the owner asks otherwise.
- This repository is public. Never post secrets, authorization tokens, private production payloads, raw model responses/prompts, personally identifying data or confidential operational records to GitHub. Use sanitized aggregate evidence where appropriate.

## Work item scope, acceptance and dependencies

- Each Trello card must deliver one independently reviewable and closeable outcome. Avoid numbered implementation epics hidden in one card. Split separate shadow/cutover/stabilization or live-migration outcomes into independent cards before work starts.
- Follow the detailed [Trello card conventions](trello-card-conventions.md) for Russian descriptions, '[AIR-N]' names, a current plan-context introduction, relevant functional labels, scope, objectively verifiable Done, tests/evidence and rollback.
- Real prerequisites belong in a **native Trello checklist**. **Read existing checklists first; reuse an existing prerequisites checklist instead of creating a duplicate**, and deduplicate prerequisite items across legacy checklists. Each item must be **only the bare Trello card URL**, never a Markdown link or an AIR/title-prefixed label; this is required for Trello to display the actual linked card title and status. Do not create false blockers or empty checklists. Reconcile checkmarks with *actual* Done status after closing upstream cards.
- Give direct Trello links to relevant prerequisites and successor work in PR descriptions and final delivery reports. Do not assign the next AIR number without checking whether it is already used.
- **Ambiguous Trello write results are not permission to retry.** After a timeout, tool error or missing/unclear write response, read or search live Trello to determine whether the mutation actually succeeded before repeating it. Especially never retry `create` blindly: check the intended card's name, AIR number, board/list, and existing matches first. If a duplicate is found, preserve the canonical card and its activity, then archive only the confirmed duplicate. Apply the same verify-before-retry rule to moves, comments, checklist edits and other non-idempotent mutations.
- Code ready, PR merged, successful deployment, read-only production smoke test, shadow verification and cutover are different claims. Record precisely which of them is proven.

## Newly discovered risks: explicit owner triage, not automatic scope expansion

**A task must not become a gate for risks outside its explicitly approved acceptance boundary.** Newly discovered risks are tracked separately unless they demonstrably invalidate that boundary. Define the smallest safe, independently useful outcome and its acceptance boundary before work begins; do not silently grow Done criteria into a migration-wide or cutover-wide gate. A prerequisite must block only the capability that truly depends on it, not unrelated successors.

**The coordinator's responsibility is two-sided:** actively surface meaningful risks **and** prevent unrelated work from being blocked by them. Do not treat every discovered risk as an instruction to stop and broaden the current card. For each material new risk, tell the owner what was found, the evidence and uncertainty, what concrete operation or acceptance criterion it threatens, the consequences of proceeding, and the recommended disposition. Ask the owner to select one of three explicit outcomes:

1. **Accept (принять).** Record the identified risk, consequences, owner decision and date in the current Trello card's comments for traceability; continue the originally approved work and retain the original Done criteria. Acceptance is informed risk ownership, not a claim that the risk was fixed.
2. **Address now (адресовать).** Pause only the affected delivery or production action, define the corrective work and verification, and obtain any needed scope/approval change. Expand the current card only if the risk demonstrably invalidates its accepted result; otherwise use a separate atomic blocking card for the affected capability.
3. **Defer (отложить).** Create or reuse a separate atomic, **non-blocking** Trello card describing the risk, evidence, impact, follow-up trigger and owner; link it from the current card and continue. Do not add it to native prerequisites unless a later, explicitly justified dependency requires it.

**Never silently choose “address now” as the default.** If the owner has not decided, present the options, pause only the operation actually exposed to the unresolved risk, and continue unrelated already-approved safe work; do not silently expand the acceptance boundary. An existing hard safety requirement, an actual invalidation of the agreed acceptance, an explicit legal/security obligation or a production owner gate cannot be waived by merely calling it accepted or deferred: stop the unsafe operation and request an authorized resolution. Record any revised scope and dependencies explicitly before implementation; do not retroactively declare an unmet criterion satisfied or remove an agreed gate without owner approval. Historical comments explain decisions, while live Trello scope and native prerequisites remain the operative contract.

## Delivery pipeline for already approved work

1. **Card-first implementation handoff.** Before moving an approved, unblocked card to `В процессе` or handing it to Cursor, make its live Trello description and/or a clearly named handoff comment **self-sufficient**: exact scope, inputs/contract, dependencies, tests, safety limits, documentation impact, visual QA and PR/report expectations. The owner's entire executable instruction must be simply **«Приступай к AIR-N»**. Cursor reads the card, latest comments, native checklist, current `main` and repository workflow; no separate instruction text in ChatGPT is needed or expected. Correct missing or stale Trello detail **before** task handoff. For rework, write actionable review findings in GitHub and put a linked, consolidated fix handoff in the same Trello card before asking Cursor to continue. Chat may briefly report status and the card link, but must not be the only place that contains execution requirements.
2. **Independent review.** Open the actual PR diff and relevant changed files, confirm the base/head and current card scope, inspect CI/test evidence and documentation changes, check risk/security/read-only claims, consider missing negative tests and rollback, and resolve review threads. Do not accept a summary alone.
3. **Review feedback.** Leave specific technical comments in English on GitHub. Report practical findings and Cursor instructions in Russian to the owner. If reviewing one's own PR via the owner's GitHub identity, GitHub may reject formal APPROVE; use an explicit positive COMMENT review, not a false claim of approval.
4. **Merge without a redundant owner prompt.** Owner approval of a card's scope and its ordinary PR delivery path **pre-authorizes merge** after a positive independent code/documentation review, resolved blocking threads, successful PR CI on the exact reviewed head, and confirmation that prerequisites and the agreed scope still hold. ChatGPT then checks the latest main/head for conflicts and merges without force or destructive operations, **without asking the owner to say “merge” again**. This is not permission to self-approve an authored PR: independent review remains mandatory. Do not merge if the card or changed artifact has an **explicit pre-merge owner gate** (notably actual rendered Mermaid visual approval), a new architectural/security decision or material scope change, failed/pending CI, unresolved blocking review findings, or meaningful new risk; first obtain the particular missing approval or fix. Normal UI visual acceptance on real production data is **post-deploy** and does not by itself block an otherwise eligible merge, but it does block premature Trello Done. A standard code deploy triggered by merging approved work does **not** authorize any distinct production writer, migration/cutover, flag, Access or Scheduled Task operation; those require separate action-specific owner authorization.
5. **Post-merge tracking is mandatory.** Read the new main merge commit and corresponding GitHub Actions workflow. Stay with the workflow through terminal results for **both Test and build and Deploy to Cloudflare**. A running/queued deployment is not a finished report. On failure, do not claim success or close the card; report the blocker and concrete corrective steps.
6. **Production acceptance.** After successful deploy, use only the safe, authorized checks required by the card. If acceptance calls for a new MCP tool, actually invoke that tool; a successful probe/CI alone is not enough. A cached connector tool list is a real blocker, not proof of a successful smoke test.
7. **Close with evidence.** Add a Russian Trello report linking the PR, review, merge SHA, terminal CI/CD run, smoke test or other evidence, unresolved known limitations and exact outcome. Move the card to 'Готово' and mark it complete only when all defined acceptance criteria are met. Update any successor prerequisite checklists.
8. **Continue the conveyor.** If the next card is unambiguous, already approved and unblocked, first ensure its Trello card is self-sufficient for «Приступай к AIR-N», then move it to 'В процессе' without writing a separate Cursor prompt in the chat. Do not ask for re-approval of an agreed sequence. Stop and ask the owner only at a genuine ambiguity, new scope/approval gate, safety decision or unavailable external action.

The reviewer must not return an unfinished routine handoff just because a merge happened while post-merge deployment is still running. If tooling fails or access prevents verification, explicitly distinguish blocked from Done rather than guessing.

## Feature flag lifecycle: plan, test, switch, remove

Every temporary feature flag must have an explicit end-to-end lifecycle **at the time it is first planned**:

1. **Create and plan.** Specify its owner, exact permitted values and defaults, consumers, data effects, rollback boundaries and the reason the flag is temporary. Create a separate, atomic Trello **flag-removal card immediately**, before implementation, link it from the introduction/rollout card, and include the specific cutover, stabilization and acceptance criteria that will unblock deletion. Do not defer creation of the removal card until after rollout.
2. **Implement and test.** Ship the gated change with tests for old/new modes, compatibility and failure paths; register the flag in [the maintained feature-flag contract](../reference/feature-flags.md). No assumption that a deployed flag is enabled.
3. **Switch and stabilize.** Execute shadow/rollout/cutover only under explicit, action-specific owner authorization. Verify the actual production binding from authoritative Cloudflare settings or an MCP diagnostic that **explicitly exposes that exact effective setting**, then verify the relevant production behavior and complete the defined stabilization period. A code default, previous Trello comment, generic MCP probe, or successful deployment alone does not establish a live binding.
4. **Remove.** When the new mode is permanently accepted and rollback no longer requires the old mode, take up the pre-created cleanup card: delete the environment selector, legacy branch and obsolete tests, update references/runbooks and production configuration as separately authorized, and verify both CI/CD jobs and necessary safe runtime checks. Preserve valid data, security gates, and retained operational capabilities. Record evidence and mark the cleanup card Done only after acceptance.

Distinguish a **transitional switch** from a **permanent owner-only safety gate**: an endpoint permitting sensitive one-off writes may need a durable gate rather than automatic removal. In that case the initial card must state the rationale and the removal/disposition ticket must explicitly decide whether to retire the endpoint, retain its gate, or replace it with a supported operational control. Never remove protections merely to satisfy a cleanup metric.

Before creating any cleanup card, search live Trello for an existing removal/disposition card using the flag's literal identifier and relevant migration terms; avoid duplicate tickets and duplicate prerequisite checklists. If the required rollback or migration remains incomplete, do not prematurely remove the flag. Review the register after each rollout and verify the cleanup card's existence and prerequisites.

## Documentation acceptance

Before implementation, record the documentation impact in the Trello card and implementation handoff using the [documentation governance matrix](documentation-governance.md). At independent review, compare the actual diff with that matrix; require the matching source, contract, evidence, ADR and diagram changes in the same delivery. A claimed `Documentation impact: none` needs a reason that survives review. Missing required documentation is a blocking finding even when tests are green. Do not defer it to a future cleanup card.

Every material architectural change requires a new ADR that records alternatives, rationale, trade-offs, and supersession where applicable, plus corresponding Mermaid diagrams and technical contracts. Pure refactoring that preserves architectural decisions does not require a new ADR. Mermaid modifications retain the existing owner visual review gate.

## Visual QA

A substantial UI change requires visual QA in a local browser at a desktop width around 1280 px and a mobile width around 390 px. Check representative full and partial states, visual hierarchy, spacing, overflow, whether the controls can be reached, and the main interactions. The PR needs a short written report of what was checked and which problems were found or fixed. Creating, saving, downloading, or attaching screenshots is not required. The owner does the final visual acceptance on real production data after a successful merge and CI/CD. Until that acceptance, the UI card stays open. Green tests or CI are not visual QA. Do not commit screenshots anywhere in the repository.

## Safety and production boundaries

- Never run production sync, discovery/TMDB, model predictions, retry resets, lease overrides, destructive cleanup, R2/D1 migration/backfill, authoritative read/write cutovers, or enable/disable scheduled jobs/feature flags without **separate explicit authorization** for that action.
- Deploying main code is not permission to exercise writable endpoints. A route named GET or 'status' may still have recovery side effects: follow [deployment.md](../runbooks/deployment.md), [mcp.md](../reference/api/mcp.md), README and side-effect tests for safe verification.
- Check the live authoritative storage and configuration; do not assume that a historical Site, R2 snapshot or D1 dry-run has become current production. Treat snapshot integrity/parity and source/target identity reconciliation as evidence gates, not as permission for migration.
- Keep production and historical data private. Do not reproduce raw record dumps in public issues, PR comments, docs, CI logs or chat summaries if those contain sensitive information.
- Verify current Scheduled Task and Access state from authorized live sources before operational claims. Neither an older runbook nor a successful Worker deployment proves tasks are enabled, disabled, connected or executed.

## Conversation handoffs and shared state

- Cross-session handoffs should describe the present blocked acceptance, exact links and the next safe action, **with a date**. New sessions immediately recheck GitHub, Trello and connected tool availability.
- Stable operating rules belong here and in the Trello conventions; live status belongs in Trello, GitHub and current operational evidence. Avoid baking temporary AIR statuses, counts or next-ticket numbers into evergreen instructions.
- The ChatGPT Movies project may include both film-taste modeling and the IPTV website. These workflow rules apply only to IPTV/code/operations tasks, not to general film recommendations or Letterboxd analysis.
- If the owner's requested project change is only documentation, direct-to-main is allowed **only when explicitly approved**; even then, verify the resulting commit and the automatic post-merge/deploy pipeline, because every main push can publish the Worker.
