# ADR 0085: D1 owns the discovery ledger only after its own marker is switched

**Status:** Accepted  
**Original decision date:** 2026-11-04  
**Recorded at:** 2026-11-03

## Context

Live and archived candidate observations, the current-generation evidence, score and attempt state, retry and terminal decisions, their history, and verified catalog admission are R2 objects. The published EPG generation is already D1 ([ADR 0079](0079-d1-authoritative-published-epg.md), Accepted, marker `d1` / `open`). Discovery still fences on that generation and still stores the ledger in R2. Owner reconsideration and identity correction ([ADR 0061](0061-discovery-observation-index-and-reconsider.md), [ADR 0080](0080-discovery-identity-correction.md)) write that R2 map. When the published-EPG marker is `d1` and discovery is not, both actions report `supported: false` and write nothing.

Production D1 is schema v9. Migration `0009` (owner reviews, [ADR 0081](0081-d1-authoritative-owner-reviews.md)) is applied, and owner reviews are `d1` at generation 1. Schema versions are linear. Ratings owns version 10 (`migrations/0010_ratings_authority.sql`, AIR-318). This discovery migration is version 11 and refuses a database that is not already a complete version 10, including the ratings tables and marker row plus the prediction, published-EPG and owner-review tables and authority rows. Neither `0010` nor `0011` is applied. The external executor remains the only executor ([ADR 0083](0083-inert-discovery-workflow.md)). `DISCOVERY_EXECUTOR` is unchanged. There is no transaction that covers D1 and R2 together.

## Decision

1. **New tables, no Film foreign key.** Migration `migrations/0011_discovery_authority.sql` adds the discovery marker, fence, transfer, lease, continuation, status, checkpoint, workflow record, observations, shows, decisions, decision history, catalog admission, archive segments, scores and owner intents. `film_id` and `observation_key` are not foreign keys to `film`. The migration inserts no film, person, credit or owner-review row. `tmdb` and `tmdb_tv` stay distinct admission rows. A duplicate `(media_kind, tmdb_id)` or a canonical identity other than `tmdb:<id>` or `tmdb_tv:<id>` is `discovery_conflict` and writes nothing. Catalog admission is not a Film row.
2. **Version 11 follows a complete version 10.** The file refuses to create a table unless `schema_contract.version` is at least 10 and below 11, the 26 named prediction, published-EPG, owner-review and ratings tables are present, and the four authority rows exist. The natural order is `0009`, already applied, then `0010` ratings, then this file. Applying ratings and applying this file are separate GOs. A version 10 that has ratings and is missing owner reviews is refused before any discovery table exists. A trigger rejects a later downgrade. A deploy does not apply `0011`. Ratings does not need to be `d1` for this file to apply later: the inserted ratings marker stays `r2` until its own GO.
3. **One marker, default `r2`.** The inserted row is `mode` `r2`, `cutover` `open`, generation 0, null programme. Readers and writers use D1 only when `mode` is `d1` and `cutover` is `open`. `cutover` `held` is not that authority: readers stay on R2 and writers throw `discovery_fence`. A missing binding, a missing `schema_contract`, or a version below 11 stays on R2, so a schema v10 ratings database with no discovery tables keeps the R2 path. Production is version 11 with the marker still `r2` / `open`, so it also stays on R2 until a separate activation ([discovery apply](../evidence/d1-migration/air-320-discovery-apply-2026-11-04.md)). Version 11 without these tables, a marker other than `r2` or `d1`, or a read that throws is `discovery_unavailable`. That path does not serve the R2 ledger. `discovery_transfer.state` `loading` is `discovery_incomplete` for readers. A failed multi-batch replace leaves `loading`, so a torn ledger or catalog is not served.
4. **What moves when the marker is `d1` and open.** `loadJSON` / `saveJSON` route the live ledger, the generation ledger, the catalog, the decision map, status, the score preview, the continuation, the workflow record and the lease key. The lease key is not written as an R2 object. A generation key is that generation only: a read of another run returns nothing, and a write of another run does not replace the current ledger. The publish handoff is the explicit exception. It streams the new ledger into D1 under the lease already held for the current run, one observation at a time, and moves `programme_run_id` before the published pointer moves. A seal that dies stays `loading` and is not served. The same live lease may retry it. After that lease expires or is released, the next handoff takes a new lease and replays the seal from the beginning when the in-progress programme differs from the published programme, or retiring observations are present. Partial rows stay unserved until that replay commits, and the interrupted lease cannot commit after the takeover. A catalog, decision or segment load stays closed. A later acquire returns no lease when that programme and the requested run differ. A decision write requires the lease programme to equal the marker programme and the observation's evidence key, when both sides have one. Departed active rows move to residence `archive` with `source_key` `archive:<programme>:<generation>:<key>`. They are not deleted. Each committed decision is appended to `discovery_decision_history` when its hash changes. Statement batches stay at or below 40. One observation's shows may span batches while the transfer is `loading`. A ledger above 20,000 active observations is not returned as one array. Continuation reads it one page at a time. The continuation etag is `d1:<revision>`. The workflow etag is `d1:workflow:<revision>`.
5. **Owner actions are real D1 writes when discovery is ready.** `discovery_reconsider` and `discovery_identity_correct` (assign and reject) store the issued confirmation, the command (effect, movie id and the owner's basis), the expected decision hash and the issued expiry with the intent (`approved`, then `running`, then `receipt`). Execute binds the submitted confirmation to that issuance, rechecks the stored command, and writes the decision in one fenced batch. A different scope, hash, expiry, basis or identity target does not write. A replay returns the stored receipt and does not write again. The receipt GET reads that row and does not read the R2 action object. A `running` intent with no receipt answers `unknown` and does not write again. While discovery is not ready and the published EPG marker is `d1`, both actions stay `supported: false` and do not write R2. While discovery is held, the confirm is refused. The UI disable contract is unchanged: an action that cannot run is not offered as a write.
6. **What does not move.** Canonical Film and Person, credits, owner-reviewed titles and names, ratings, prediction state, and raw EPG XML. R2 keeps immutable observation segments, snapshots, raw TMDB bodies, and the owner-action receipts of the `r2` path. `importSegment` copies an archive segment into D1 only when the marker is already authoritative, the source key starts with `archive:`, the SHA-256 matches, and no lease is live. The operator script does not expose it. No automatic merge. No AIR-131 group apply and no AIR-132 versioned revoke. `ensureDiscoveryWorkflow` and `reconcileDiscoveryWorkflow` are not rewritten and are not started by this marker. The external executor remains the executor until [AIR-324](https://trello.com/c/kNtaEbm8). No new feature flag.

Not decided here, and not authorized by accepting this record: applying `0010` or `0011`, importing a ledger or an archive segment, holding or sealing the marker, setting `mode` to `d1`, any discovery or TMDB run, and any production R2 or D1 write. `0009` is already applied; that fact is not a GO for this file. Applying `0010` is a separate ratings GO and is not a discovery cutover.

## Alternatives considered

- **Reuse the v1 `candidate` tables and their Film foreign key.** Rejected on the card. A publish or a decision would insert a Film, and `tmdb` / `tmdb_tv` would collapse.
- **Fall back to the R2 ledger when D1 fails after the marker says `d1`.** Rejected on the card. The object can be the stale copy the failure just left behind.
- **Apply discovery as version 10, beside ratings.** Rejected. AIR-318 already holds migration `0010` and ADR 0084 for ratings. Discovery is `0011` and this record.
- **Start the Cloudflare Workflow from this marker.** Rejected. [ADR 0083](0083-inert-discovery-workflow.md) leaves that switch to AIR-324. This record only stores the workflow row when discovery is already authoritative.

## Consequences

Two chunks cannot hold the lease. A decision whose evidence key does not match the active observation fails the fence and leaves the stored decision. A catalog identity collision fails before the transfer goes `loading`. A killed multi-batch leaves `loading`, and every discovery read then fails closed. The same live lease may retry a ledger seal. After that lease expires or is released, the next handoff replays that seal; the interrupted lease cannot commit after the takeover. A catalog, decision or segment load is not replayed by that handoff. The owner page's index, when the marker is `d1` and open, is the D1 rows rather than the R2 shards. `saveObservationIndex` does not write those shards in that mode. While the marker is absent, `r2`, or the schema is below 11, the R2 shards remain the index.

The discovery, EPG and persistence Mermaid diagrams were visually approved by the owner on 2026-11-04. That approval is not a production GO.

## Recovery and migration boundary

A code rollback while the marker is `r2` leaves readers on R2, whether or not `0011` has been applied. Applying `0011` leaves `mode` at `r2` and copies nothing. Schema apply, archive import, a hold, a seal, and the marker change are separate owner GOs. This delivery's script, `scripts/discovery-authority.mjs`, prints the marker and `writes: false`. It refuses `--apply`, `--activate`, `--import` and `--load`. It refuses a database path that contains the production database id `3fba0e0a-44e9-4a3a-a7ba-edaee6bcafcb` or a path segment `iptv` before sqlite is opened. It does not call the network. There is no production entry. Returning a future `d1` marker to `r2` is not implemented here. A Time Travel restore of the whole database would be its own approval. Neither is authorized by this record.
