# MCP endpoint — transport, tools and security contract

Worker `iptv` serves a remote MCP server at `https://iptv.vladimino.workers.dev/mcp`. Cloudflare Access application `IPTV MCP` authenticates every request with Managed OAuth, and the Worker verifies the signed Access JWT. The same endpoint exposes two connection probes and a narrow set of EPG and prediction tools. Those tools call the existing Worker functions. They do not accept a URL, an R2 key, or an API path, and they do not generate fingerprints or predictions: ChatGPT does that and submits the result.

Publishing this Worker does not start sync or prediction and does not enable Scheduled Tasks. A tool writes to R2 only when an authorized caller invokes it. [AIR-62](https://trello.com/c/CU71gW4c) separately restored the two external ChatGPT Scheduled Tasks on 21 October 2026. A deploy does not control their enablement, and additional writer runs or task changes require separate approval. See [deployment.md](../../runbooks/deployment.md) and check live task state. Any isolated production write/read/cleanup test would require separate explicit approval; `probe_echo` does not replace it.

The endpoint lives in the existing Worker. There is no second Worker, no new binding, no Durable Object, and no KV namespace.

## Architecture

```text
ChatGPT (custom MCP server, OAuth) or Claude (claude.ai custom connector, OAuth)
  -> Cloudflare Access application "IPTV MCP" (path /mcp, Managed OAuth, owner-only policy)
       answers unauthenticated requests itself: 401 challenge, OAuth discovery, DCR, /authorize, /token
  -> Worker "iptv": src/mcp.js
       1. verifies the signed Cf-Access-Jwt-Assertion (signature, issuer, audience, time, identity)
       2. validates the Streamable HTTP request
       3. answers JSON-RPC: initialize, notifications/initialized, ping, tools/list, tools/call
```

`src/worker.js` routes only the exact path `/mcp` to `mcpRoute`. Every other path, including `/mcp/`, keeps its existing behaviour, and `/api/*` is unchanged. Access application `All Workers` still protects all other paths.

### Transport

- Streamable HTTP, single endpoint, `POST` only. Every response is one JSON object (`Content-Type: application/json`). The server never opens an SSE stream.
- Stateless: no `Mcp-Session-Id`. `GET` and `DELETE` return `405` with `Allow: POST`. That is the documented response when a server offers no standalone SSE stream and no sessions.
- Protocol versions `2025-11-25` and `2025-06-18` (the `initialize`-based era). `initialize` echoes a supported requested version and otherwise answers `2025-11-25`. Every later message, including `notifications/initialized` and `ping`, must carry a supported `MCP-Protocol-Version` header. Without sessions, the header is the server's only record of the negotiated version. Under the 2025-11-25 transport rules a missing header means `2025-03-26`, which this server does not support, so it gets `400`. `probe_read` reports the version from that header.
- A `2026-07-28` request (stateless era) gets `400` with JSON-RPC code `-32600`, not the modern `-32022`. Under the MCP backward-compatibility rules, a dual-era client treats that as a legacy server and falls back to `initialize`. A client that supports only `2026-07-28` cannot connect.
- Batches, client-sent JSON-RPC responses, malformed JSON, invalid UTF-8, non-JSON `Content-Type` (`415`), an `Accept` header that excludes JSON (`406`), and bodies over 64 KiB (`413`) are rejected. Notifications get `202` with no body.
- A browser `Origin` header must be the Worker's own origin or `https://chatgpt.com`. Any other origin gets `403`. Server-to-server requests without `Origin` are accepted once the Access JWT is valid.

The protocol is implemented directly in `src/mcp.js` instead of through the MCP TypeScript SDK. The build in `build.mjs` concatenates source files without a bundler or runtime npm dependencies. The SDK would add a bundler, dependencies, and Node compatibility flags to the deploy artifact, all for four JSON-RPC methods. `tests/mcp.mjs` exercises the protocol over real HTTP requests through `worker.fetch`.

### Tools

`probe_read`, `probe_echo`, `feature_flags` and `prediction_validate` do not read or write R2; `feature_flags` reads the registered feature flag bindings by name and answers even without a bucket binding; `prediction_validate` runs the submit validators on the caller's own candidate objects and answers even without a bucket binding. `prediction_queue_overview`, `prediction_film_diagnostics`, and `prediction_pending` read a fixed set of stored objects and return that diagnostic with `httpStatus: 200`. They do not call an HTTP route, list storage, or write. Every other tool returns `structuredContent.httpStatus` plus the JSON body of the existing HTTP contract. `400`, `404`, `409`, `503`, and `5xx` set `isError`, and the body stays in `structuredContent` so the caller can still read `Run id mismatch`, `lease_lost`, `busy`, or `Queue not empty`. `already_running` is HTTP 200: stop and do not adopt that `runId`.

All MCP tools require the [Cloudflare Access and Worker JWT validation](#authorization) described below. `epg_sync_step` follows the [discovery continuation contract](#discovery-contract-for-scheduled-tasks). External Scheduled Tasks orchestrate EPG and predictions independently of deployment; D1 is not the authoritative data source for these tools.

Write tools are annotated `readOnlyHint: false`. `enrichment_status` is too, because the HTTP status route can persist a recovered stop event. `epg_sync_start` and `epg_sync_step` are `openWorldHint: true` because they fetch Letterboxd, the configured EPG source, or TMDB. A wrong argument returns a tool result with `isError: true` and does not call the domain function. An unknown tool returns JSON-RPC error `-32602`. The response never contains the caller's identity.

The caller repeats `epg_sync_step` until `stage` is `complete`. It then reads `discovery.nextAction`: `continue` means call `epg_sync_step` again now with the same `runId`; `wait` means do not call before `discovery.nextCatchUpAt`; `stop` means discovery is finished until the next EPG commit. `ratingsPending` does not mean retry Letterboxd: no step repeats the films list. A ratings attempt killed before it recorded an outcome is closed as `unknown` by a later step on the completed run ([ratings attempt](../integrations/letterboxd-ratings.md#ratings-attempt)). One call is one metadata batch, the EPG commit, or one discovery chunk. A separate request does not guarantee a new isolate. The caller repeats `prediction_next` / `prediction_submit` until the runner returns `mustComplete` or the queue is empty. ChatGPT generates the fingerprint and prediction, calls `prediction_validate` with the complete objects (or applies the `enrichment_schema` `contract` itself), submits only on `success: true` (equivalently `valid: true`), otherwise fixes every reported issue and validates again; the Worker validates again and stores them. A submit rejection names the field and the violation code in `results[].validation.issues`; the caller fixes that field for the following films, and the rejected film stays deferred under the ordinary retry rules. The Worker is the enforcement point: the preflight tool is available to the client, but whether the external Scheduled Task calls it is decided by that task's prompt, outside this repository.

### Discovery contract for Scheduled Tasks

`epg_sync_step` returns this object once the programme commit has happened. The external EPG caller should branch on `nextAction` and not infer it from `ratingsPending` or from `stage` alone.

| `discovery.nextAction` | When | What the caller does |
| --- | --- | --- |
| `continue` | EPG commit (`state: paused`, `reason: epg_committed`, `remainingChunks: 12`), a chunk finished with candidates and budget left, or an orphaned `running` record (`reason: orphaned`: its writer's lease expired without a checkpoint) | Call `epg_sync_step` again now with the same `runId`; on an orphan that one call settles and resumes the same generation; on a checkpoint left behind by an earlier generation that one call supersedes it with a new series for the published generation |
| `wait` | `chunk_budget`, `backoff`, `busy`, or `error` before `nextCatchUpAt`; a live `running` record (`reason: busy`, `nextCatchUpAt` = the writer's lease expiry); a newer generation published but not yet in place (`generation_pending`) | Do not call before `discovery.nextCatchUpAt`; `discovery.nextScheduledRunAt` is the hourly task trigger expected to catch up after that gate ([timing](../scheduled-tasks.md#timing-nominal-trigger-versus-server-gate)) |
| `stop` | Backlog finished for the published generation, a programme change seen by the chunk, nothing to resolve, or a series that failed closed after repeated interruptions (`reason: interrupted`, below) | Do not call until the next EPG commit. A checkpoint left behind by an earlier generation (an orphan, a finished series or a programme-changed stop pinned to it) is not a `stop` once a newer generation is published and in place: the next call supersedes it (`continue` above). While the pointer already names the new generation but the shared programme has not followed yet, the call writes nothing and answers `wait` with a catch-up time (`diagnostic.branch: generation_pending`) |

**Hourly catch-up after an exhausted chunk budget (AIR-299).** The published `discovery.nextAction=wait` is a snapshot of the stored checkpoint, not a dynamically recomputed permission to restart a series. The Worker permits the next ordinary `epg_sync_step({runId})` after `nextCatchUpAt` when `continuation.stage=paused`, `reason=chunk_budget`, `remainingChunks=0`, and the checkpoint belongs to the current published generation. `continuationDecision` then replenishes the per-series budget to `DISCOVERY_CHUNK_BUDGET` (currently 12), without an EPG refresh or a forced resolve. The external hourly task's authorization is narrower: it requires fresh `epg_status.stage=complete`, exact current-generation agreement in both read-only statuses and the checkpoint, `continuationHealth.status=settled`, no future retry or extra hard wait, no conflicting writer indication, and revalidation immediately before a **single** ordinary step. A `settled` status does not prove an absent live lease; the Worker enforces lease and checkpoint CAS independently. Any `busy`, wait, generation mismatch, error, or unknown result stops this attempt without retry. This is separate from orphaned-`running` recovery and old-generation handoff. See [Scheduled Task contract](../scheduled-tasks.md#hourly-discovery-catch-up-and-predictions).

**Interrupted steps.** When the platform ends a step invocation without a response (for example the Workers memory limit, outcome `exceededMemory`, HTTP 503 from the platform), the MCP client shows a generic error such as `Internal error`. The step's result is then unknown to the caller and the call must not be repeated: the next scheduled step reconciles it. Whether the step committed is read from `epg_pipeline_status` (the step's diagnostics entry and the continuation, see below). A series in which two hops in a row end before their checkpoint fails closed: the next step writes `paused` with `reason: interrupted` and answers `stop` without running a chunk, so a chunk that kills its invocation every time is not run again by the schedule. A new EPG generation opens a new series; an owner-approved `POST /api/enrichment/discovery/resolve` (forced) runs the chunk again.

`discovery.state` is `paused`, `running`, `complete`, `error`, or `busy`. A finished response is not left `running`; a `running` record in `epg_pipeline_status` is read together with `continuationHealth` (`live`, `orphaned`, `settled`, `idle`), which is what distinguishes an active writer from an interrupted one. `remainingChunks` counts chunks still allowed in the current series. The field list, the lease rules and the orphan recovery are in [ENRICHMENT_API.md](enrichment.md#live-and-orphaned-running-records).

### Continuation diagnostics

Every `epg_sync_step` that reaches `POST /api/sync/epg`, and every discovery resolve request, is one **step entry** with two channels. The Worker log gets one structured line per phase (`{"event":"epg_continuation", …}`): `entered` before any storage access, `checkpointed` as soon as the step's discovery hop has stored its continuation checkpoint (before the hop's trailing writes and the response), then `completed` or `failed`, all with the same `id`. The ring `epg/resolver-continuation-diagnostics.json` (newest first, at most 20) gets the same entry written best effort with `phase: entered` before the step, replaced by `checkpointed` and then by the outcome. An entry that is still `entered` or `checkpointed` 15 minutes after its `at` belongs to an invocation that ended without its terminal phase; the next ring write closes it as `phase: interrupted` and logs one `interrupted` line with the same `id`. `epg_pipeline_status` returns the stored ring as `continuationDiagnostics`; reading it writes nothing. The log line is the arrival evidence; the ring is a convenience view that can miss an entry (write failure, eviction after 20 later steps), so an absent ring entry means *no persisted evidence*, not *no call*.

| Field | Meaning |
| --- | --- |
| `id`, `at`, `durationMs` | Entry identity, time the step was entered, wall time |
| `phase` | `entered`, `checkpointed` (the hop's checkpoint is stored, no outcome yet), `completed` (a response was formed, including 4xx), `failed` (the handler threw) or `interrupted` (closed by a later step: the invocation ended without a terminal phase) |
| `checkpoint` | Set from `checkpointed` on: `hopId`, `owned` (the checkpoint write stored this hop's record), `write` (`saved`, `other_hop`, `write_conflict`), `stage` and `remainingChunks` of the record left in place; `null` otherwise |
| `interruption` | Only on `interrupted`: `lastPhase` (`entered` or `checkpointed`), `committed` (`true`/`false` from a `checkpointed` entry, `null` (unknown) from an `entered` one), `cause: unknown`, `closedAt`. It is not a proven error: the Worker cannot see why the invocation ended. The platform outcome of the same invocation (`exceededMemory`, `canceled`, `exception`) is in Workers Logs, joined through the `id` of the entry's `epg_continuation` lines |
| `caller` | `mcp` (this endpoint), `http` (`/api/sync/*`, `/api/enrichment/discovery/resolve`) or `internal` (`DiscoveryContinuation`) |
| `route`, `runStage` | Route taken (`other` outside the known three) and the server's `sync.json` stage at entry (`metadata`, `epg`, `complete`, `other`) |
| `runId`, `runIdShape` | The caller's `runId` only when it has the server-generated UUID shape, else `null`; `runIdShape` is `uuid`, `invalid` or `null` (not sent) |
| `branch` | `run_mismatch`, `stage_mismatch`, `metadata`, `epg_commit`, `continuation`, `resolve`, `invalid_limit`, `no_programme`, `not_found` |
| `httpStatus`, `error` | HTTP status of the formed response; on a failed step `error.code` (`storage`, `upstream`, `timeout`, `publish_conflict`, `resolver_busy`, `invalid_input`, `unknown`) and `error.name` (built-in error class, else `Error`). The thrown message is classified, never copied |
| `recorded` | Result of the best-effort ring writes: `entered`, `checkpoint` (only on a step that reached its checkpoint) and `outcome` are `true`, `false`, or `null` when the route is not persisted. The stored entry carries only the writes before its own; the final log line carries all of them |
| `discovery` | The `discovery` contract the response carried: `state`, `nextAction`, `reason`, `remainingChunks`, `programmeRunId`, `nextCatchUpAt`, `retryAt` |
| `diagnostic` | The `advanceDiscovery` trace, also returned in the step response: `branch` (`report_only`, `lease_live`, `generation_pending`, `generation_handoff`, `orphan_settled`, `interrupted`, `record_changed`, `contract`, `missing_secret`, `lease_lost`, `chunk`), `entry` (continuation record before), `lease` (`none`, `expired`, `live`), `health` (the continuation health: `status` `idle` / `settled` / `live` / `orphaned`, `hopId`, `lease`, `leaseHop` `same` / `other`, `leaseExpiresAt`, `chunkCompleted`, `resumeBudget`, `generationConflict`, `interruptions`), `recovery` (only when an orphan or a generation handoff was handled: `orphanHopId` (the hop of the orphan or of the superseded record), `action` `settled` / `resumed` / `interrupted` / `generation_recovered` / `generation_pending`, `chunkCompleted`, `budget`, `settled`, for `resumed` and `interrupted` the `interruptions` count, and for a handoff `superseded`, the earlier generation), `decision` (`run`, `budget`, `force`, `hardWait`, `nextAction`), `hopId`, `budget`, `chunk` (`stage`, `checked`, `remaining`, `added`, `variantPending`, `retryAt`, `programmeRunId`, `error` as an error code), `saved` (continuation record after, with `owned: false` and `write` `other_hop` when another hop had taken the continuation or the record moved before this call's write, `write_conflict` when both conditional checkpoint writes were rejected, `saved` otherwise), `leaseReleased` (whether the hop's lease was released after its checkpoint; `false` means the next call waits until the lease expires, nothing else is affected), `trailingError` (the classified code of a write that failed after the checkpoint, for example the score preview; the step is still committed; `null` otherwise). A checkpoint is written before the lease release, the diagnostics ring and the response, so an MCP error or a lost response after a step is not a rollback ([order of the hop's final writes](enrichment.md#live-and-orphaned-running-records)) |

Every string field is drawn from a closed vocabulary: stages and states (`idle`, `paused`, `running`, `complete`, `error`, `busy`, `partial`, `programme_changed`, `awaiting_epg_discovery`, `backoff`, `missing_secret`), `nextAction` (`continue`, `wait`, `stop`), `reason` (`epg_committed`, `scan_committed`, `busy`, `chunk_budget`, `backoff`, `programme_changed`, `idle`, `missing_secret`, `error`, `discovery_failed`, `orphaned`, `interrupted`); a value outside its list is recorded as `other`, and a `reason` outside the list (an error continuation keeps the thrown message as its reason) is classified into the error codes above. Ids (`runId`, `programmeRunId`, `hopId`) are kept only in UUID shape, times only when they parse, counts only as finite numbers. No tokens, cookies, identities, raw payloads, titles or messages can enter an entry or a log line. The metadata route is logged but not persisted. Recording an outcome does not retry, dispatch or change the resolver; the interpretation table is in [the connectivity runbook](../../runbooks/mcp-connectivity.md#diagnosing-a-stalled-epg-continuation).

### Ratings tools

The separate Letterboxd ratings pipeline ([ADR 0060](../../adr/0060-independent-letterboxd-ratings-pipeline.md), [contract](../integrations/letterboxd-ratings.md#separate-ratings-pipeline)) has four tools under the same [authorization](#authorization). They act only when `RATINGS_PIPELINE` is `separate` and `ratings_storage_migrate` has completed: otherwise start and step answer `disabled` (switch `inline`) or `not_migrated` and write nothing, and ratings run inside the EPG commit as described above. The HTTP routes are owner-only behind the Worker's Cloudflare Access like the other `/api/` routes; a body is a JSON object with only the listed fields, and anything else is `400` before any read. No tool accepts a URL, R2 key, page or limit.

| Tool | Writes | What it calls |
| --- | --- | --- |
| `ratings_sync_status` | no, not even recovery | `GET /api/letterboxd/ratings/status`: `switch` (`inline`, `separate`), `pipeline` (`inline`, `separate_pending_migration`, `idle`, `running`, `isolated`), `migration` (`none`, `partial`, `complete`, `regressed`, with `regressedObjects`), the run record `letterboxd/ratings/run.json` (with `lease {live, expiresAt}` and `stale` (`interrupted`, `abandoned` or `null`) instead of the step id), `diary` (cursor coverage, `historicalCoverage` `incomplete` when `coverage.window` is `recent` and `unknown` otherwise, `overflowSuspected`, resume page, last outcome, `lastSuccessAt`), `removal` (queue version, `lookupEnabled`, entries, pending, unresolved references, `refIssues` by issue, legacy, expired, `droppedRefs`, `pausedUntil`), `freshness`, `contractVersion`, `readAt`, `sideEffects: none`. | `ratings_sync_start` | yes | `POST /api/letterboxd/ratings/start` with `{trigger, clearIsolation?}`; `trigger` is `scheduled` or `manual`. Answers `{runId, created, nextAction, reason}` with `reason` `started` (`nextAction: continue`), `busy` (a run is active; its `runId` is not returned), `isolated` (with `isolation`), `disabled` or `not_migrated` (with `migration`). A scheduled start has no minimum interval after the previous one ([ADR 0069](../../adr/0069-no-scheduled-ratings-start-gap.md)). A stale `running` record is closed as `unknown` before deciding. `clearIsolation: true` only with `trigger: manual`, and only after the owner approved clearing an isolation. No Letterboxd request |
| `ratings_sync_step` | yes, open world | `POST /api/letterboxd/ratings/step` with `{runId}`: one step under a three-minute lease. The removal phase, only while a rated legacy entry still needs its event scan, lists one page of existing removal events and links an exact film id ([ADR 0071](../../adr/0071-legacy-removal-event-link.md)); a step with nothing left to link does not list. The caller starts once, steps sequentially while `nextAction` is `continue`, honors `wait`, and never retries a `stop` or an invocation that ended without a response; a later start closes such a run `unknown`. The states, lease and races are in [the record](../../adr/0060-independent-letterboxd-ratings-pipeline.md#5-state-machine). No Scheduled Task calls these tools; enabling one is a separate owner decision ([Scheduled Tasks](../scheduled-tasks.md)).

## Authorization

Cloudflare Access is the OAuth authorization server and the gate. The Worker issues no OAuth tokens, publishes no protected-resource or authorization-server metadata, and sends no `WWW-Authenticate` header. Cloudflare documents that Managed OAuth replaces the application's `401` behaviour, so a competing challenge from the origin would only confuse clients.

With Managed OAuth, ChatGPT sends an opaque bearer token (`oauth:…`) to Access. Access resolves it to the owner's identity, re-checks the Access policy, and forwards the request with a signed RS256 JWT in `Cf-Access-Jwt-Assertion`. The Worker trusts only that header, after verifying:

- `alg` is `RS256`, and `kid` names a key from `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`. Keys are cached for up to an hour. An unknown `kid` triggers at most one refresh per 30 seconds.
- The RSASSA-PKCS1-v1_5 SHA-256 signature is valid.
- `iss` equals `MCP_ACCESS_TEAM_DOMAIN` exactly.
- `aud` contains `MCP_ACCESS_AUD`, the AUD tag of `IPTV MCP`. A token minted for `All Workers` has a different AUD and is rejected.
- `exp` is present and not past; `nbf` and `iat`, when present, are not in the future. The allowed clock skew is 60 seconds.
- `sub` is a non-empty user identity. Service-token assertions, whose `sub` is empty, are rejected.

The Worker ignores the `CF_Authorization` cookie, `Cf-Access-Authenticated-User-Email` and other identity headers, and the client's own `Authorization` header.

Failures are closed and generic:

| Condition | Response |
| --- | --- |
| `MCP_ACCESS_TEAM_DOMAIN` or `MCP_ACCESS_AUD` missing or malformed | `503`, JSON-RPC `-32603` "MCP authorization is not configured" |
| Signing keys unreachable or unusable | `503`, JSON-RPC `-32603` "Access signing keys are unavailable" |
| Any missing or invalid assertion | `403`, JSON-RPC `-32001` "Forbidden" |

Authorization runs before method, header, and body checks. A caller without a valid assertion learns nothing else about the endpoint. The Worker answers `403` instead of `401`: an assertion mismatch is a server-side configuration problem, and re-running OAuth cannot fix it.

If `IPTV MCP` is disabled or deleted, `/mcp` falls under `All Workers`. That application's JWT carries a different AUD, so the Worker keeps returning `403`.

## Configuration

| Variable | Value | Secret |
| --- | --- | --- |
| `MCP_ACCESS_TEAM_DOMAIN` | `https://<team>.cloudflareaccess.com`, the Zero Trust team domain | No |
| `MCP_ACCESS_AUD` | Application Audience (AUD) tag of Access application `IPTV MCP` (Zero Trust → Access controls → Applications → `IPTV MCP`) | No |

Set both as plain-text variables on Worker `iptv` (Workers & Pages → `iptv` → Settings → Variables and Secrets). They are not committed, following the repository rule that runtime values live in Cloudflare. `wrangler.jsonc` has `keep_vars: true`, so a GitHub deploy keeps dashboard variables. Until both are set, `/mcp` returns `503` behind Access.

Saving a variable publishes a new Worker version. That is a production environment change and needs the owner's explicit approval. No other configuration is involved: the R2 binding `BUCKET` is unchanged, and no secret is added. The probe tools ignore `BUCKET`. The EPG and prediction tools use it only when called.

## Cloudflare Access requirements

This repository change does not modify Cloudflare Access. Each item below must be confirmed by the owner, and any change needs separate approval. Do not add Bypass or Everyone policies, service-token shortcuts, or exceptions to `All Workers` to make discovery work.

1. **`IPTV MCP` application.** Destination `iptv.vladimino.workers.dev/mcp`, owner-only Allow policy, Managed OAuth on. Cloudflare recommends a short access-token lifetime (5–15 minutes) with a longer grant session (1–2 weeks) for agents.
2. **Redirect URI for dynamic client registration.** ChatGPT and Claude register themselves through DCR. Access accepts only redirect URIs on the Managed OAuth allow-list (Advanced settings → Allowed redirect URIs). The working `IPTV MCP` allow-list permits the connected ChatGPT server through the path wildcard `https://chatgpt.com/connector/oauth/*` and, since 25 October 2026, the claude.ai custom connector through `https://claude.ai/api/mcp/auth_callback`. No exact ChatGPT callback was recorded in the UI. An exact callback, `https://chatgpt.com/connector/oauth/<callback_id>` or `https://chatgpt.com/connector_platform_oauth_redirect` when the authorization server advertises RFC 9207 issuer identification (`authorization_response_iss_parameter_supported: true`), is preferable once ChatGPT shows one. Tightening the allow-list is a separate Access change and is not part of this repository change.
3. **RFC 8707 resource indicator.** Access Managed OAuth rejects `/authorize` without `resource` (`invalid_target`). ChatGPT sends the `resource` value from the protected-resource metadata on both the authorization and token requests. That value must be exactly `https://iptv.vladimino.workers.dev/mcp`, with no trailing slash, and the ChatGPT server URL must be the same string.
4. **Discovery reachability on a path-scoped application.** `IPTV MCP` covers only `/mcp`, while `All Workers` covers the rest of the hostname, including `/.well-known/*`. Cloudflare documents that Access serves the challenge and `/.well-known/oauth-authorization-server` for a Managed OAuth application. It does not document which application answers well-known URLs outside the protected path. The 401 challenge must point to metadata that Access serves without an `All Workers` login redirect. Verify this with step 1 of the procedure below. If any discovery URL returns an HTML login page or a `302`, discovery is blocked. Stop and choose a fix with the owner. Possible options, each needing approval and a check against current Cloudflare documentation: an additional `IPTV MCP` destination for the metadata path, or a dedicated hostname for the same Worker that `IPTV MCP` covers entirely.
5. **Authorization-server metadata.** It must include `registration_endpoint`, `code_challenge_methods_supported` with `S256`, and `token_endpoint_auth_methods_supported` with `none`. If it does not advertise `client_id_metadata_document_supported`, choose DCR in ChatGPT, not CIMD.


## Limitations


- Probe tools, `feature_flags` and `prediction_validate` do not touch R2. `feature_flags` shows the bindings of the Worker version that answered; a changed variable publishes a new version, and a client sees it on its next call. The EPG and prediction tools can, and only when an authorized caller invokes them. A connected ChatGPT or Claude client may cache the tool list; a tool added by a deploy appears only after that client refreshes or reconnects the server. Exercising those tools on production, including an isolated write/read/cleanup, needs its own approval. The external Scheduled Tasks were enabled under their own owner approval; new invocations or modifications need separate approval.
- No SSE, sessions, server-to-client requests, `list_changed` notifications, resources, prompts, or batches. Clients that support only `2026-07-28` are not supported.
- The origin allow-list is fixed in code: the Worker's own origin and `https://chatgpt.com`.
- Initial October 19–20 interactive MCP probes did not establish unattended access. [AIR-62](https://trello.com/c/CU71gW4c) subsequently accepted scheduled EPG/prediction runs on October 21; on October 24 both external recurring tasks remained enabled with recent executions. These dated checks do not prove current OAuth health or unspecified security/revocation test results.
- The first request after a cold start fetches Access signing keys from the team domain. If they are unreachable, the endpoint returns `503`.
