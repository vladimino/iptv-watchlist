# Orchestration reliability contract for Cloudflare-executed pipelines

This is the field-level contract that every Cloudflare executor for EPG publication, Discovery and Ratings must implement. The decision and its rationale are [ADR 0089](../adr/0089-shared-orchestration-reliability-contract.md) (Accepted; not activated). The target topology and lifecycle are drawn in [scheduling and orchestration](../architecture/scheduling-and-orchestration.md#proposed-cloudflare-executors-and-shared-recovery).

**Implementation status (2026-11-08).** This page is the field-level target contract; each domain implements the part its own ADR sets out, and no domain is claimed to implement every field. **Ratings** runs inside the Letterboxd Sync Workflow ([ADR 0186](../adr/0186-letterboxd-sync-and-independent-watchlist-authority.md)); the Cloudflare executor of [ADR 0090](../adr/0090-ratings-cloudflare-workflow-executor.md) is retired and kept only as documented history, and the external Task is disabled. **Discovery** runs on the Cloudflare Discovery Workflow ([ADR 0083](../adr/0083-inert-discovery-workflow.md), [ADR 0093](../adr/0093-discovery-workflow-cron-reconcile.md), permanent since AIR-325), which implements an earlier subset (capped recovery, quarantine, rollover, owner record, cron reconcile, intent reconstruction) and recovers a recognised transient step failure inside the instance (arm once, durable sleep until `dueAt`, successor through `ensureDiscoveryWorkflow`, [ADR 0098](../adr/0098-discovery-workflow-step-failure-recovery.md), Accepted); the hourly reconcile stays the fallback for a platform kill and a failing arm, and a scheduled `projector_window` on that fallback is retried in the same tick after the window expiry (AIR-428). **EPG** runs on the Cloudflare executor of [ADR 0100](../adr/0100-epg-cloudflare-workflow-executor.md) (Accepted, AIR-348): mode `cloudflare`, epoch 1, Daily ChatGPT Task disabled after the first natural run was accepted on 8 November 2026. **Predictions** stay on ChatGPT and are outside this contract. This page authorizes no operation.

## Shared vocabulary

### Failure classes

| Class | Typical codes | Executor action | Budget effect |
| --- | --- | --- | --- |
| `transient` | `network_error`, `timeout`, `rate_limited` (HTTP 429), `upstream_blocked` (Letterboxd 403 `cf-mitigated`; no in-run retry), `upstream_5xx`, `exceeded_memory`, `exceeded_cpu`, `worker_1102`, `wakeup_lost`, `instance_terminated`, `instance_errored`, `create_uncertain`, `owner_unknown`, `d1_unavailable` (D1 read or write failed or the authority is unreadable), `step_failed` (a Workflow action threw before classification) | Read back, then retry after cooldown | `consecutive` and `total` +1 |
| `permanent` | `credentials_missing`, `credentials_rejected`, `contract_unsupported`, `config_invalid` | Stop; re-check the precondition cheaply on each due wakeup; resume when it holds | Not counted; health `failed_permanent` |
| `unsafe` | `evidence_unreadable`, `evidence_contradictory`, `checkpoint_malformed`, `lease_malformed`, `stale_generation_write`, `owner_conflict`, `epoch_mismatch` (a commit from a stale epoch or mode is refused), `step_lease_expired` (an EPG step ran past its 5-minute lease; stopped like `epoch_mismatch`, AIR-444), `authority_held`, `authority_loading` | Quarantine the domain immediately; no retry | Quarantine reason is the code |

**The EPG step guard (AIR-348).** The guard that every EPG mutation boundary calls (`assertStep`) refuses the mutation in two different ways. A mode revision that moved, a lease that was taken over or released is `epg_step_fenced` and is the stale-epoch stop (`epoch_mismatch`). A lease that merely ran out is the same fence with `detail: lease_expired` and is named `step_lease_expired` (AIR-444): it stops the instance in exactly the same way (unsafe, no retry, no quarantine written), but it no longer claims an epoch change. On 2026-11-11 a `seal_stage` of 348 s outlived the 300 s lease, its last write was refused and the instance was reported as `epoch_mismatch` while the stored epoch was still 1 and its mode revision unchanged since 8 November ([evidence](../evidence/discovery/air-444-bounded-seal-stage-rca-2026-11-11.md)). Every archive fence of the ledger staging is now a mutation boundary of the step, so a step that keeps writing renews its lease. A D1 read of the mode revision and the lease that fails is `epg_step_unreadable`: the mutation is still refused (fail closed), but it is the transient `d1_unavailable`, so the executor cools down and retries inside the instance instead of stopping it. On 2026-11-08 the first natural run was stopped after 61 steps by a D1 read failure that the guard had reported as a fence, with no epoch change ([evidence](../evidence/orchestration/epg-first-natural-run-air-348-2026-11-08.md)).

Not failures: `stale_generation` (a newer published generation took over), `rollover` (a healthy successor instance), `backlog_empty`, `complete`, a domain pause that the upstream asked for, and a lost CAS against a live owner (`busy`).

A domain maps its own outcomes onto these codes. A code not in this table must be added here before it is used. Thrown messages are classified, never copied into a record.

### Control record

One record per domain, in that domain's authoritative store (D1 for an activated domain). Field names are logical; the storage shape is the delivery's choice.

| Field | Meaning |
| --- | --- |
| `domain` | `epg`, `discovery` or `ratings` |
| `mode` | `external` (ChatGPT Task path, executor inert), `cloudflare`, or `switching` (admission closed, draining) |
| `target`, `drain` | While `switching`: the mode being entered, and the drain state (`lease_live`, `instance_live`, `verified`) |
| `epoch` | Integer, increased by every mode change. Every executor write compares it |
| `runKey` | EPG / Ratings: Madrid date `YYYY-MM-DD`. Discovery: `programmeRunId` + series |
| `phase`, `checkpoint` | Domain phase and the last read-back checkpoint |
| `owner` | `{kind, instanceId, leaseUntil}`; one active step per domain |
| `budget` | `{consecutive, total, fingerprint, lastFailureAt}` |
| `cooldownUntil` | Earliest next attempt after a transient failure |
| `quarantine` | `{scope: run \| domain, reason, at}` or null |
| `lastDurableProgressAt` | Time of the last checkpoint that advanced (below) |
| `nextWakeAt` | The executor's own next planned wakeup, when one is set |

The `fingerprint` is the tuple class, code, phase and checkpoint. It shows whether the same fault repeats at the same point.

### Default policy

Defaults apply unless a domain row below sets a stricter value. Loosening a default needs a new ADR.

| Policy | Default |
| --- | --- |
| Cooldown after the n-th consecutive transient failure | 1 min, 5 min, 15 min, 1 h (the fifth failure quarantines instead) |
| Jitter | Multiply by a uniform factor in [0.8, 1.2]; tests inject the random source |
| Upstream `Retry-After` or domain pause | The later of that time and the cooldown |
| `consecutive` cap | 5: the fifth consecutive transient failure without durable progress quarantines the run key with `budget_exhausted` |
| `total` cap per run key | 12 transient failures |
| `budget_exhausted` scope | The run key; the next run key starts with a fresh budget |
| `unsafe` scope | The domain, until an explicit owner-approved clear |
| Reset of `consecutive` | Only on durable progress for the same run key and epoch |
| Reset of `total` | Only with a new run key |
| `ensure` cost | At most a few reads per domain per firing; at most one `create`. The EPG `ensure` also reconciles R2 compatibility mirrors of the published D1 generation (idempotent; no write when aligned, held, switching, or a step lease is live) |

With the defaults, a fault that never clears quarantines after cooldowns of about 1 h 21 min plus four attempts.

A fenced call answers `external_writer_fenced` and writes nothing. While the mode is `switching`, both paths answer `switch_in_progress` and write nothing. Read-only status tools stay available in every mode.

## Domain rules

### EPG

- Steps: metadata, watchlist, programme download and parse, scan, publication, tail. The XML is streamed in bounded steps and never held whole.
- Publication is the atomic D1 switch of `programmeRunId`. A failure before it leaves the earlier generation published. After it, reading the pointer decides: if it names this run, the run is published and only the tail remains.
- Mirror repair writes R2 compatibility mirrors only from the currently published D1 generation. A failed mirror is retried as a tail step and never unpublishes.
- At most one successful publication per Madrid date. Publication queues the Discovery intent and does not run Discovery. Accepted [ADR 0135](../adr/0135-epg-priority-discovery-pause.md) lets the publication soft-busy-wait for a live Discovery lease without spending the failure budget; the schema gate was activated on 14 November 2026 and its normal natural-run priority refusal, release and resume were verified on 15 November ([AIR-467 evidence](../evidence/orchestration/air-467-epg-priority-natural-run-2026-11-15.md)).
- **Implementation (AIR-348, [ADR 0100](../adr/0100-epg-cloudflare-workflow-executor.md), inert).** `EpgOrchestration` (`src/epg-orchestration.js`): the logical due time is `EPG_SCHEDULE` 17:00 Europe/Madrid; the run key is the Madrid date; the Workflow instance id is `epg_<YYYYMMDD>_<series>`; one action is one existing `/api/sync/start` or `/api/sync/metadata|epg` step called in-process; durable progress is a sync-run checkpoint that moved forward in the same run (stage, metadata cursor, seal phase) or a completed run; a seal `busy` answer sleeps until its own `nextCatchUpAt`; a run of the same date that already completed is the success whoever drove it. The mode and control documents are the `mode` and `control` rows of `epg_orchestration_document`; every published-EPG pointer or replacement batch asserts the `mode` revision it was admitted with (`epgFence`). The external path answers HTTP 409 `switch_in_progress` or `external_writer_fenced`. Read model: the `orchestration` object of `GET /api/status` (MCP `epg_status`). **Adopted foreign-day seal (AIR-464).** `drive` takes the day of a sync run from its own frozen `sync.json.runKey` (else its frozen `startedAt`, Madrid day), never from the adopting Workflow's payload. When a seal of another day completes inside `act`, the outcome is `continue` (`note: foreign_run_sealed`): no `doneAt` or `publishedRunId` is written to the adopting control, and the next action starts the run of the control's own day. `sync.json.runKey` (when present) and `startedAt` must both be well formed and agree; a missing legacy key falls back to `startedAt`, a malformed or contradicting key fails closed as `evidence_contradictory`, and the `epg_status` read model uses the same day. The sequence diagram is unchanged: only the completion condition inside an existing step changed. Failure mapping: a `409` run-id conflict is `owner_conflict`, a generation changed under the run is `stale_generation_write`, an unfinished D1 seal that `sync.json` does not name is `evidence_contradictory` (all unsafe, a domain quarantine until the owner clears it); a source, timeout or 5xx failure is transient and resumes the same run after the cooldown.

- **Completion proof for a complete run; a prior attempt's error (AIR-525).** `sync.json.error` is written by `syncStep` when a step of a run throws, and nothing clears it when a later step of the **same** `runId` completes the run, so a durable `stage: complete` record can still carry the error of an earlier attempt (for example a `seal/finalize` unit that threw, then a retry that reached `queue` and wrote `completedAt`), or of a tail that threw after the complete record was saved. That field is history of an attempt, not the current state of the run; the writers are unchanged and keep it as evidence. The EPG executor credits a complete run of the control's own Madrid day only on a **completion proof**, never on its stage alone and never refused because of a prior error: a completion receipt (the AIR-518 rule: `completedAt` when the record has the field, which must parse; for a legacy record without the field, `updatedAt` only when there is no `error`) **and** the D1 published pointer (`PublishedEpg.readAuthority`: `ready`, `programmeRunId` equal to the run's `runId`). The same proof applies when a step of the action itself reaches `complete` (or drains a complete run): only then are control `doneAt` and `publishedRunId` written. Proven, `drive` finishes on the same `runId` (`lastStep.note: recovered_complete` when the run carries an error), or first takes **one** `/api/sync/epg` step on that `runId` when an `epg` / watchlist event is owed (as before) or a Ratings hand-over is owed (`removalRefs`, `removalLookups`, or `ratingPending` with an attempt that is absent or still `started`); after such a step completion is judged by the journal events alone, so a Ratings gate that keeps the hand-over cannot hold the day open. A proven same-day run never reaches `/api/sync/start`. Not proven (no or malformed receipt, a pointer at another run or at none, no `runId`) is `evidence_contradictory` (unsafe: a domain quarantine for the owner, never a second run); an authority read that throws is the transient `d1_unavailable` (cooldown, then the same check). A `seal` or `complete` run whose frozen day is malformed or contradicting (AIR-464) is `evidence_contradictory` before any other decision, also when the pointer names it. A complete run of another Madrid day keeps the previous rule (never this control's success; with an error it is not usable and today's run starts). A run still in `seal` with an error is a current failure and is continued under its `runId`, as before. The read model's done check uses the same proof; it reports the history as `syncRun.priorAttemptError` (`true` only for a complete run carrying an error), and `GET /api/status` / MCP `epg_status` as `priorAttemptError` beside the unchanged `error`. No state, stage or persistence authority changes: only the completion condition inside existing steps and the read model's done check.

### Discovery

- One chunk per durable step; 20 chunks per instance, then a successor instance. A due `chunk_budget` renews by CAS when the saved status shows remaining work.
- The instance is pinned to the published generation. A newer generation stops it as `stale_generation`.
- TMDB 429 and the stored series `retryAt` or backoff become `cooldownUntil`. A TMDB-touched candidate that cannot be stored is a per-key `retry_at` fence (`deferReason: wall_budget`), not a series backoff: `checked` does not increase, the hop continues, and other eligible keys are selected. Selection-only `wall_budget` (no TMDB started) still sets the five-minute series `retryAt`. Cheap-pass and verified-slot replay stop while unresolved candidates remain if the next write would consume the TMDB start window; the checkpoint reserve is the 8 s commit floor or three observed write durations capped at 15 s, not six times a cheap group plus the pre-TMDB fence. A stored hop `error` of `wall_budget` is reported as that allowlisted code, not `unknown`.
- Decisions, including `cheap_pass`, budget defers and partial ones, are idempotent per key.
- A thrown Discovery application error keeps its allowlisted `error.code` (`discovery_conflict`, `discovery_fence`, `discovery_lease`, `discovery_unavailable`, `discovery_bounded`, `discovery_not_authoritative`, `discovery_incomplete`) on the continuation checkpoint (`reason` plus `failedAt` / `failureKind` / `failureConstraint`), the operational `lastCheckpoint`, the chunk summary and Workflow `lastProgress`. It does not rewrite `epg/discovery-status.json`, so `lastChunk` may still be the earlier `cheap_pass`. It is not classified as `unknown` from the `Error(code)` message. Bounded `failedAt`: `cheap_decision`, `cheap_admission`, `replay_assignment`, `candidate_admission`, `candidate_decision`, `candidate_assignment`, `revalidation`, `revalidation_assignment`, `final_checkpoint`. `failureKind`: `unique_constraint`, `input_invariant`, `fence`, `other`. A D1 UNIQUE also carries `failureConstraint` as `unique.<table>` with no SQL, parameters, titles or ids. `discovery_fence` stays `fence` and is never mapped to `discovery_conflict`. The Workflow step still succeeds: `advanceDiscovery` stores the checkpoint and does not throw, so `discovery_workflow_step_failed` is not this class. `discovery_conflict` remains a hard application code (hourly wait), not a transient step retry.
- A `discovery_fence` thrown outside the guarded D1 writes (a status, checkpoint or assignment write, a read-side generation compare, a direct refusal, a partial or missing diagnostic; [AIR-687](https://trello.com/c/jrP0z56f), second delivery) separates two decisions and never decides either from how complete the error's own classification is (the first delivery retried only a proven batch `CHECK` collision, and an unclassified refusal still cost an hour on 27 Nov 2026 at 20:00 Madrid). **Write safety** is unchanged: the refused hop writes nothing more, and every read and write of the next chunk is fenced again with a fresh lease; decisions and slot assignments are idempotent per key, so work that was already durable is neither lost nor repeated. **Wake** is decided by `assessFenceRefusal`, a read-only assessment (it reads the published pointer, the authority gate and the stored lease and compares the lease id and expiry; it never renews or writes): the series needs another chunk whenever the refusal can still clear, that is for every state except a positively superseded run. A lost or expired hop lease, a pointer that is missing, not `published` or unreadable, a not-ready, held or loading authority and unreadable state are all re-evaluated (`fenceBasis`: `lease_lost`, `pointer_unconfirmed`, `authority_not_ready`, `authority_held`, `authority_loading`, `state_unreadable`, `state_confirmed`), because the next chunk takes its own lease and applies its own busy times. Only the pointer naming another run as `published`, or the authority bound to another run (`run_superseded`, `other_programme`), keeps the fail-closed `error` checkpoint, and the Workflow plan stops that series as `stale_generation`. A held authority refuses the checkpoint write itself and is not retried behind it. The checkpoint is `paused`/`backoff` with a `retryAt`, so the Workflow wakes there independent of the hourly Cron. The cause (`fenceCause`: `generation_moved`, `batch_fence`, `batch_check`, `read_or_direct`) is diagnostic only. When the final status write is the refused one, the chunk's real counts (checked, touched, assignments) travel into that checkpoint, so the report counts them exactly once and the monitor sees the progress.
- The wait is an engineering interval, not a product limit: it starts at 30 s (a competing writer holds the counter for seconds), doubles with each consecutive re-evaluation and is capped at five minutes, the existing backoff of a chunk that made no progress (`PAGED_BUDGET_BACKOFF_MS`). There is no count-based hour tier: whatever blocks is re-read every re-evaluation, so work resumes within the cap after the obstruction ends, and a persistent refusal costs at most twelve light chunks an hour (a lease attempt and a few reads). It stays visible: `fenceCollisions` counts the consecutive re-evaluations (cleared by the first chunk that is not refused or that did real work) and the monitor treats a counted loop as a zero-work loop (below).
- Step output `progress` only means the checkpoint was saved by this hop and keeps driving the stall counter, so a legitimate wait or backoff is never counted as a stall. `usefulProgress` is separate and is read from the real chunk summary: a checked candidate (the count includes the cheap pass), a touched or added Film, an assigned or replayed slot (`assignment.assigned` / `assignment.replayed`) or a revalidated decision; an error chunk, a collision retry and a checkpoint-only chunk are not useful progress. It is persisted in `lastProgress` and as `lastUsefulProgressAt` (with `usefulProgressTrackedSince`, the first chunk the series judged) on the Workflow state, carried across a same-generation rollover, recovery or successor and dropped for another programme run, and shown by the Discovery status view. The Monitor (`evaluateDiscovery`) judges a tracked series by this clock: a fresh saved error, collision or backoff checkpoint and a fresh chunk time neither refresh it nor end an open `discovery_stalled` incident, a zero-work loop (error record or counted collision retry) is not hidden by its own future gate while a legitimate deferred wait is, the start of tracking is a detection baseline and never recovery evidence (an open incident recovers only on useful work newer than its baseline, as the Predictions stream does), and the existing three-hour Discovery threshold applies (no new threshold or alert); a legacy record without the fields keeps the checkpoint and chunk clocks. Contract: [monitor API](api/monitor.md#discovery-queue). See the [monitoring runbook](../runbooks/monitoring.md).
- A busy that has no deadline of its own (a lost lease race, a record moved by another hop), asked for by the Workflow executor (`caller: internal`), waits for the blocking fact: the live lease's expiry, else one short recheck; it no longer defaults to the next hour boundary. Other callers keep the hourly contract of `busyOutcome`. An EPG-priority pause and a projector window keep their own poll time and expiry. A lost compare-and-swap of the Workflow state by the same owner (a progress, final stop or recovery arming checkpoint) is contention, not lost ownership: after three immediate retries the step sleeps a short durable interval (the fallback a refused window write uses) and re-reads the record, its ownership and its revision before trying again, without repeating the chunk (its report contribution is keyed by the chunk, so it counts once); only the existing step cap still ends the instance as deferred for the reconcile, and a record owned by another instance still ends it quietly. Reachable fence and busy paths and what each does are in the [AIR-687 evidence](../evidence/discovery/air-687-fence-evening-2026-11-27.md).
- A publication that is only unconfirmed at the Workflow plan ([AIR-687](https://trello.com/c/jrP0z56f)) is not a different published run. When the pointer is missing, or not `published` yet and still names this run, `workflowPlan` waits (`generation_unpublished`, at least 30 s and never before the record's own retry time) and rechecks without any candidate write; the instance step cap bounds it. A pointer that names another run (an EPG commit in flight or a newer publication) keeps the terminal `stale_generation`, and a readback that fails at the plan is a recognised step failure with the existing autonomous recovery. The recovery arming after a step failure takes the same owner-gated backoff on a same-owner lost compare-and-swap (`armedFor` keeps the failure counted once, one successor is created); only the step cap ends it as `recovery_write_conflict`.
- An interrupted hop is recovered by the executor only when its proof holds: same published generation, the hop's own unfinished status, no diagnostic claiming its checkpoint, authority open. Otherwise the outcome is `evidence_contradictory` or `evidence_unreadable` (`unsafe`).
- The manual interrupted confirm of [ADR 0088](../adr/0088-guarded-interrupted-discovery-recovery.md) is refused since AIR-325 (`cause: executor_workflow`); the Workflow applies the interruption rules itself.

### Ratings

- Diary page 1 only, and at most 5 removal lookups per step.
- Letterboxd HTTP 403 with `cf-mitigated` is never bypassed and not retried inside the run; the run ends with its existing outcome and the next Madrid date is the retry. HTTP 429 sets the six-hour pause as `cooldownUntil`.
- A removal event is written by CAS before its queue reference is resolved; a repeat writes the same event and does not add a viewing or a second removal.
- The existing `unknown` close is a counted `owner_unknown` transient failure. The existing `isolated` state is an `unsafe` domain quarantine, cleared only by an explicit owner-approved action that does not itself run a step.

### Predictions

Outside this contract. The hourly ChatGPT Tasks keep the leased queue, `prediction_batch_validate` and `prediction_batch_submit`. A model quota of zero leaves items pending; no Cloudflare executor generates predictions.

## Mode switch and write fencing

The switch is three steps, each an owner-approved action ([ADR 0089 decision 2a](../adr/0089-shared-orchestration-reliability-contract.md#2a-mode-switch-protocol-and-what-the-fence-can-and-cannot-guarantee)):

1. **Close admission:** one CAS sets `mode: switching`, `target` and `epoch+1`. No new step of either writer is admitted (`switch_in_progress`).
2. **Verified drain:** the old owner's lease is absent or expired with margin greater than the longest step wall time, the previous Workflow instance is finished or absent, and the domain lease or run-record lease is released or expired. An unverifiable drain stays open and is `unsafe` evidence.
3. **Complete:** a second CAS sets `mode` to the target; only then does the target writer start and the other path answer `external_writer_fenced`.

Every authoritative D1 commit carries the epoch and mode it was admitted under and is applied only if the control record still equals them, in the same batch as the data. Fencing by write kind:

| Write | Fence | Domain examples |
| --- | --- | --- |
| D1 authoritative commit | Transactional: epoch and mode compared in the same batch | EPG pointer and generation; Ratings documents and run record; Discovery ledger and control record; every checkpoint |
| R2 write with etag CAS | Conditional, plus admission recheck immediately before | Objects the domain already writes by CAS |
| R2 write without a transactional fence | Admission recheck, lease TTL bound, idempotent by construction; never the evidence of progress | Ratings removal events (event key); EPG raw XML (content digest) and R2 mirrors (derived only from the currently published D1 generation); Discovery archive or side objects |

An unknown outcome of an R2 write is read back by key and compared (byte length and SHA-256, or event key) before anything is repeated; unreadable is `evidence_unreadable`. The contract does not claim immediate exclusivity at the epoch increment: exclusivity holds once the drain is verified.

The lease admission predicate decides the owed day on the **database clock** inside the lease `UPDATE` (the Worker binds today's arming instant and the two candidate dates) and fences the requested programme id against the pointer in the same statement, so a read-to-write boundary crossing or a pointer move after the pre-read cannot admit a chunk. A request that loses the lease because the pointer moved is the hard `stale_generation` fence (`generation_mismatch` busy, no retry loop), never a soft `lost_race`, and unreadable evidence fails closed. Table presence in the Worker has three answers: present, verified absent (today's behaviour) and unknown; `beginSync` and the pointer stamp fail closed on unknown (no new run without its frozen `runKey`, no NULL day stamped), and the structured EPG busy is only for a table known to be there. Not delivered here, by design: the arm of the row by the hourly cron (there is none), an owner override tool, and the cross-day seal control fence ([AIR-464](https://trello.com/c/asr6KVU8), `src/epg-orchestration.js`). A writer that arms the row from a lease-free generation writer is not delivered either: those batches abort on their own fence, so only the lease acquire arms the row.

Discovery admission of a new lease closes five minutes before the EPG due instant (16:55 Europe/Madrid while the due time is 17:00) and stays closed until `published_epg_authority.madrid_run_key` is that owed `YYYY-MM-DD` and `published_programme_run_id` already equals the pointer's `programme_run_id`. The column is written only in the pointer `UPDATE` inside `commitPublish`, from `sync.json.runKey` frozen at `beginSync`, not from the adopting Workflow's `runKey`, not from `published_at` and not from the live orchestration control. A Workflow that resumes a seal after midnight is specified to publish it under the frozen sync day (`adopted_seal`) and not to mark its own control done. The control-completion fence for an adopted foreign-day seal is implemented separately by AIR-464 in `src/epg-orchestration.js` (see the AIR-464 paragraph of the EPG implementation notes); it is not part of AIR-459 and does not need the pause table. A null or different key is not that day's publication. The pin moves earlier, in `sealArchive`'s committing batch, and that move does not lift the pause. There is no business TTL. An in-flight holder may renew; a new acquire, a reconcile create, a rollover and a manual or admin lease may not. EPG's own acquire is exempt. A failed, quarantined, stalled or missing EPG run keeps the pause; the existing EPG `late` / `stalled` read model and the end-of-day alert are the escalation, and Discovery health for this wait is `waiting`. An owner override admits only the programme id the pointer already names, for that owed date.

The lease `UPDATE` carries the clock, the owed date and `published_epg_authority.madrid_run_key` in its own `WHERE`, so a still-`clear` row cannot admit and a pre-read of the control document is not the proof. A refused update writes no lease, so the same `batch()` adds a second statement that sets `paused` only where that predicate is still true. The lease-free generation writers carry the same predicate. There is no 16:55 cron. A 60 s poll tells the caller when to look again and does not lift the pause. Expected contention (`epg_priority`, `projector_window`, `lease_held`, `lost_race`) does not change `consecutive`, `total` or `cooldownUntil` and is not `step_failed`, `unknown` or HTTP 502. When the pause and a projector window both apply, the reason is `epg_priority`, so the window deadline is not the end of the pause. The projector window's own 300 s deadline is unchanged. D1 errors and held or loading authority stay fail-closed. A requested id other than the pointer's programme id is `stale_generation`, including under an override. The pause row is cleared in the pointer batch of `publishGeneration` when the pin already equals that run, or later by the replay branch or the next acquire once both match.

The diagnostic fields are the reason, the owed date, the lease owner kind (`discovery`, `projector`, `epg`, `none`) and the hold expiry. No Film id, SQL or continuation body.

## EPG checkpoint ownership ([ADR 0185](../adr/0185-epg-checkpoint-d1-authority.md) and [ADR 0199](../adr/0199-retire-the-epg-checkpoint-r2-arm.md), Accepted; D1-authoritative)

**D1-authoritative since 21 Nov 2026** (marker `d1` / `open` / generation 2; [cutover](../evidence/d1-migration/air-551-checkpoint-cutover-2026-11-21.md), [first natural run](../evidence/d1-migration/air-551-h5-natural-run-2026-11-22.md)). The run checkpoint `sync.json` and the ingest status `watchlist-ingest.json` are D1 rows; the R2 objects are a frozen image, unread and unwritten, and the R2 arm is retired for production (marker `r2`, tables absent or an unreadable state is closed, never R2; only the local stand-in `EPG_CHECKPOINT_DB_OPTIONAL` serves R2). The repository is `src/epg-checkpoint-d1.js`; the contract below applies while the `epg_checkpoint_authority` marker is `d1`, which is the only state production serves. Schema: [D1 schema](data/d1-schema.md#epg-checkpoint-authority-schema-v30-d1-authoritative).

- **Fenced save.** Every checkpoint save is one D1 batch (each guard is an upsert of the singleton fence row, so a missing row can never let a stale write pass; a missing row is also a closed state): authority fence, in-batch EPG step fence (mode revision and live step lease), compare-and-swap on the single run row `(run_id, revision)`, then the body and the changed film rows. A save with no step is refused; a stage or seal-phase regression, a change of `completed_at` and a stale run, revision, generation or lease are refused and write nothing. The writer re-reads and decides; no blind retry.
- **Stages.** `metadata`, `epg`, `seal` (`ledger`, `catalog`, `publish`, `finalize`, `queue`), `complete`; forward only within a run. `error` is a field on a stage. A new run replaces the row in one batch that also records ingest success, after its film rows were staged and read back. The run row states the watchlist (present or absent, count, aggregate digest) and a reader fails closed on any missing, extra, duplicated or reordered row; completion removes the film rows, so a completed run has no watchlist.
- **Completion and certificate.** One completion operation is the only way to `complete`, used by both the seal queue step and the single-call route (which attempts the queue refresh first in this mode). Its one batch completes the run, removes the film rows, writes the certificate and clears the pause; the certify update is conditional and non-aborting and requires a complete checkpoint with `queue_attempted`, so no route can certify before its queue attempt. A non-matching certify still lets the run complete and is reported as `certificate: owed` (repaired by `certifyComplete`, which reads the D1 checkpoint). Event flushes stay after the batch. In `r2` mode the order stays R2 complete save, then certificate, then flushes.
- **Unknown outcome and old versions.** Every write has a receipt row; applied, not applied and superseded are told apart by it, and an advanced revision without a receipt in the retained window is `indeterminate` (the step stops as unsafe evidence and never replays the batch). A Worker version that does not know the table cannot be fenced by D1; activation therefore happens only with the deployed version proven, no older instance alive and the run at a `complete` boundary. Rollback of data is a separate owner-approved export, never a code revert and never a lease reset.
- **Ingest status.** Success is written in the run-creation batch. A failure is an upsert guarded by the authority fence only and ordered by attempt: it applies only if its attempt is newer than both the stored success attempt and the stored failure attempt, so a late failure of an old attempt is superseded and writes nothing. Counters are bounded and the existing document fields keep their meaning.

## EPG seal in a successor instance ([ADR 0144](../adr/0144-epg-seal-successor-workflow-instance.md), implemented in code by AIR-484; production acceptance awaits a natural EPG run)

**Behaviour after AIR-484 and ADR 0145 (code merged is not production proof):** the instance `epg_<YYYYMMDD>_<series>` runs up to the durable `epg_commit` and the seal ledger phase; the seal then runs in the next series. The staged publication is `epg/seal/<runId>/publication.json` (`layout: 2`, no catalog). A leftover `payload.json` run is finished by the legacy reader. A fresh isolate is not claimed; whether the successor lowers memory is to be observed on natural runs. Per the ADR:

- **Boundary.** After the staged object and `sync.json` (`stage: seal`) are durable, the producing instance ends. The successor is the **next series** of the id family, `epg_<YYYYMMDD>_<series+1>` (a terminal Workflow id can never be created again), claimed in the `control` document by a compare-and-set before `create()` with `handoff: {sealRunId, fromSeries, toSeries}`. The hand-off records no failure and spends no budget. A new instance is not assumed to give a new isolate.
- **Recovery by observed state (hourly `ensure`, no new schedule, Task or flag).** Claim whose `sealRunId` is still `stage: seal`: successor absent or `create()` unknown: read status, then idempotent `create()` of the same id or attach (`already_exists` is an attach), bounded by `create_uncertain`. Alive: attach and wait. `errored` or `terminated`: record the failure against the existing budget and cooldown, then compare-and-set to a new recovery series; the seal resumes from the durable ledger, `seal.units` and the step lease; `restart()` is not used; repeated failure ends in quarantine. `complete` while `sync.json` says `seal`: fail closed, `evidence_contradictory`.
- **Day-roll.** The owner of an unfinished seal is the control record holding its claim, keyed by that run's own `runKey`, which may be a previous Madrid day (`foreign_run_sealed`). `ensure` checks the claim before today's start; while it is pending, today's run is not started and today's compare-and-set does not replace it; `ensure` answers `in_progress` (live successor), `cooldown`, `status_unknown`, `create_uncertain`, `evidence_contradictory` or `quarantined` for the claim, never a start of today. The `day_rolled` stop in `act()` is implemented as a guard: an admitted instance whose control `handoff.sealRunId` equals the unfinished `sync.json` seal passes it, any other instance of a rolled day stops; the claimed completion never marks today's run complete.
- **Orphaned claim after a lost `act-N` result (AIR-520).** If the platform loses the result of the `act-N` that committed the claim, the retry of the old series reads `not_owner`. `recoverOrphanClaim` then lets that old instance create exactly the claimed successor (same id and params, through the idempotent `handoff` step) when the control record, `sync.json` (`stage: seal` of the claimed run) and the Cloudflare status (`absent`) all agree; an alive, terminal or unknown child, a cooldown, quarantine, done run, moved epoch or any mismatch keeps the `not_owner` stop. An unreadable status or an unproven create is recorded as `create_uncertain` with a cooldown and left to the hourly `ensure` (the fallback is unchanged). The recorded `stopReason` follows the `ensure` cooldown guards (`status_unknown` or `create_uncertain`), so repeated ensures inside the cooldown spend no budget. `readModel().handoff.successorPending` is true only for a verified `absent` child; `alive`, `unknown` and `finished` are told apart by `owner.liveness`. Evidence: [AIR-520](../evidence/orchestration/air-520-orphan-handoff-claim-rca-2026-11-17.md).
- **Mixed versions and rollback.** Older code does not recognize `handoff` (extra control fields are accepted under `schemaVersion: 1`, `admit()` checks id, series and `runKey`) and may execute a claimed seal ignoring the claim. Deploy of the implementation and any rollback therefore happen only with no unfinished claim and no live successor (drain holdpoint). A seal started without a claim is finished by the existing path.
- **Staged publication (ADR 0145).** Layout 2 writes `publication.json` before `sync.json` moves to `seal`. `run.seal.sourceKey` and `run.seal.etag` remain the generation ledger; `run.seal.publicationKey` and `run.seal.publicationEtag` are the publication. A mismatch or missing publication fails closed before any later write. After a finished ledger the next phase is `publish`; there is no `seal_catalog` work on a layout-2 run. Abandoned-object GC is not part of this record.
- **`finalize_scan` cost (AIR-532, [ADR 0173](../adr/0173-watchlist-retention-observed-at-is-state-start.md)).** The retention scan writes only Films whose watchlist state changed (first observation, exit, re-add); a scan that repeats the stored boolean writes no Film row, no receipt and no revision, and one fenced write per scan moves the single-row watermark `film_retention_scan` (schema 25, an owner-approved apply is needed; before it the producer rewrites every Film as before, so the benefit does not exist on deploy alone; at schema 25 without the table it fails closed). An observation older than the watermark is stale, in the plan, in the write batch and, for any writer, in two database triggers. The producer reads the three Film/Person marker rows with one statement, plans a Film with one, and reads the route once per slice. `UNIT_CAP=12` is unchanged, so an unchanged daily watchlist of 400 Films is still 34 slices, each about 46 to 53 D1 round trips on the offline stand-in (389 before), with no write batch. The lease, the completion clock and `publishedAt` are unchanged; see the [lease analysis](../evidence/orchestration/air-532-seal-lease-analysis-2026-11-18.md).
- **Unchanged.** D1 ledger completes before the atomic pointer; the pointer moves once; generation, lease and epoch fences; idempotent publish, finalize and queue units; one EPG generation; the Producer Workflow of ADR 0140 is a separate chain.

## Discovery intent after an EPG publication

The published D1 pointer is the source of truth for whether Discovery owes work. Admission reads that pointer from `PublishedEpg.currentGeneration()` and requires the Discovery `published_programme_run_id` to match it; a missing pointer, a null pin, or an A→B lag is a bounded wait (`generation_unpublished` / `generation_handoff`) and does not reconstruct from `programme_run_id` or R2. After that match, `ensure Discovery` compares the published `programmeRunId` with the Discovery control record and, when the record does not name it and the generation has no terminal outcome, creates the intent by one CAS (run key `programmeRunId` + series 0, generation pin, Discovery authority fence). The receipt is the control record read back naming `programmeRunId` with the owner epoch. A held or `loading` marker writes nothing (`unsafe`). The EPG publication's own queue write is a fast path using the same CAS; its failure never fails or unpublishes the EPG run. The worst-case delay of a missing intent is one cron period. While Discovery is not activated, the existing generation handoff applies.

## Time rules

- A daily domain is due when the Europe/Madrid local time is at or after its scheduled time and that Madrid date has no successful run. Conversion uses the IANA zone.
- Cron expressions are UTC. They must fire at least once after the scheduled local time in both CET (UTC+1) and CEST (UTC+2), and again later the same local date for catch-up.
- The run is created by CAS on the day key; duplicate firings attach to it.
- A missed date is not backfilled once the next date is due.

### EPG correlation and memory-boundary markers (AIR-462)

Passive, best-effort log lines that tie a Workflow `act-N` callback to the phases it drove. They write nothing to R2 or D1, add no endpoint, flag, cron or Task, and a logging failure never changes a result.

- `epg_act` (`edge` `enter`, `exit` or `error`): `at`, `runKey` (a date or `null`), `instanceId`, `actStep` (`act-N`), `attemptTraceId`, and on `exit` `elapsedMs` and `kind` (`continue`, `sleep`, `stop`). `attemptTraceId` is minted per execution of the callback, so a platform retry of the same `act-N` has another id; it is a local correlator, **not** a Cloudflare attempt id. Since AIR-522 the line also carries `attempt`, the platform's own 1-based attempt number of the step (from the callback context; absent when the platform does not pass one).
- `epg_act_stored` (AIR-522): `at`, `runKey`, `instanceId`, `actStep`, `kind` (`continue`, `sleep`, `stop`, `handoff` or `null`). A best-effort line written **outside** `step.do`, after it resolved to this Workflow execution. A present line proves only that `step.do` returned to this execution; it is not a receipt of persisted output, and Cloudflare documents that side effects outside a step may be duplicated when the engine restarts, so repeats are possible. An absent line is **inconclusive on its own** (log delivery can be lost). On the [17 Nov 2026](../evidence/orchestration/air-522-workflow-internal-error-rca-2026-11-17.md) failures an `epg_act exit` was logged and the platform then reported the attempt failed with no stored line before the retry; that correlation is a lead, not proof of the internal boundary. Always correlate with the Workflow history and read back the relevant durable state (control record, `sync.json`) before concluding persistence or non-repetition.
- `epg_phase` lines of the step an action drives carry the same `instanceId`, `actStep` and `attemptTraceId`. The trace is bound to the run only while that step runs (the step lease allows one), and a step without a trace (an external caller, the start request) logs as before.
- `epg_memory_boundary` (`edge` `enter` or `exit`): a closed set of `boundary` names (`seal_stage_archive_begin`, `seal_stage_archive_segments` every 16th segment, `seal_stage_emit_begin`, `seal_stage_payload_put`, `seal_ledger_begin`, `seal_ledger_read`, `seal_ledger_batches` every 25th batch, `seal_ledger_archive`, `seal_payload_get`, `seal_payload_text`, `seal_payload_parse`) and only non-negative integer fields from `elapsedMs`, `bytes`, `items`, `batches`, `cursor`, `total`, `count`, `segments`. `bytes` of `seal_payload_text` and `seal_stage_payload_put` is the string length in UTF-16 code units. These are sizes the code already knows, **allocation proxies, not heap or isolate measurements**: workerd offers no heap figure and none is read.

Pairing rule. Paired boundaries log `enter` and a matching `exit` when the operation completes, and no `exit` when it throws: `seal_payload_get`, `seal_payload_text`, `seal_payload_parse`, `seal_stage_payload_put`, `seal_ledger_read`, `seal_ledger_archive`. One-sided milestones are never a pair: `seal_stage_archive_begin` and `seal_stage_emit_begin` (`enter` only; the matching `epg_phase` exit or error of `seal_stage_archive` and `seal_stage` closes them), `seal_ledger_begin`, `seal_ledger_batches` and `seal_stage_archive_segments` (`exit` only, progress points). `epg_act` logs `exit` when the action returns and `error` (no `exit`, no error text) when it rejects; the Workflow still receives the unchanged `act_failed` sleep result.

A few dozen lines per action, none per observation or film. The last line of an attempt that was killed is its last confirmed point, not the instruction that killed it: a line written just before death can be lost, and a long synchronous allocation shows only as the gap after its `enter`.

## Rollout and rollback

Each domain moves alone: inert code with mode `external`; an owner-approved three-step mode switch to `cloudflare` (close admission, verified drain, complete); real production acceptance from the read model; then, separately, disabling that domain's ChatGPT task path. Rollback is the same three-step switch in the other direction (close admission, verified drain, second CAS), then re-enabling the task path. A code rollback changes neither data, mode, cron nor the task registry. Operator steps: [deployment runbook](../runbooks/deployment.md#moving-a-pipeline-to-a-cloudflare-executor).
