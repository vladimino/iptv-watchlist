**Relation to the live prompt.** Core Taste Profile and scoring rules are carried over from [`hourly-predictions-only.md`](hourly-predictions-only.md) (Taste Profile use, `fingerprint.evidence` map, scale and reference films, `unknown` instead of invention, no `confidenceAssessment`, no version changes); the batch v2 research quality gate is stricter. The protocol changes are: one `prediction_batch_start` with an optional client `manifestSize` (1..100, default 100; this template uses 5) replaces `prediction_start` plus `prediction_next` and the profile/schema/metadata reads; films are generated in `generationSize` cycles (template 1), accumulated, and flushed through `prediction_batch_validate` then `prediction_batch_submit` at `submitBatchSize` (template 5) or the 56 KiB limit; a short run ends with `prediction_complete` reason `manifest_spent` when every selected manifest film is settled even if the global queue still has ready films (ADR 0136). Several independent hourly v2 Tasks may share one lease/queue ([AIR-451](https://trello.com/c/NN3N6kRp)); legacy v5 must stay disabled during cutover. The single-film `prediction_validate` is not used because the Worker validates each film again at submit (still authoritative). The Task makes no `prediction_validate`, `prediction_next`, `prediction_submit` or `prediction_start` call.

**Production research and validation contract (not installed):** the scheduled prompt obtains a fresh live manifest and follows the real batch_v2 lease, submit and completion protocol. Web research is permitted for film criticism, while IPTV state is accessed exclusively through MCP. Research audit fields are not added to the fixed schemas. Frozen samples, private Google Docs, synthetic run IDs, dry-run transport and one-off scheduling are not part of the production prompt. The separate A/B template retains its frozen-manifest transport and is not a production invocation. This documentation changes no Scheduled Task.

## Execution playbook

One execution, from a clean context:

1. `enrichment_runner`: require the `batchRunner` block and `requires.predictionAuthority: "d1"`; otherwise stop as `batch_runner_unavailable`.
2. `prediction_batch_start({trigger:'scheduled', manifestSize:5})` once (this template). Outcome table:

| Answer | Task action |
| --- | --- |
| `running` | keep `runId`, `lease.epoch`, `profile`, `contract`, `films[]`, `manifestHash`, `manifestSize`, `filmsSelected`; generate |
| `already_running` | success (another v2 Task or leftover legacy); do not adopt the `runId`; end, no `prediction_complete` |
| `noop`, `blocked` (`quota`, `retry_backoff`) | no run exists; end, report the reason |
| `manifest_too_large` | nothing created or shortened; report `bytes`, `limit`, `largestFilmBytes`; end |
| `batch_runner_requires_d1`, `prediction_catalog_held`, `prediction_retry_heal_pending` | nothing created; report the `code`; end |

3. Generate in `generationSize` cycles (this template: 1 film per cycle). Accumulate independently generated items; when the buffer reaches `submitBatchSize` (this template: 5) or the next item would exceed 56 KiB, run `prediction_batch_validate({items})` then `prediction_batch_submit`, clear the buffer, continue; flush any remainder at the end of the manifest. Keep the newest `epoch`. `prediction_heartbeat` before a long generation and at least every 10 minutes (lease TTL 15 minutes).
4. Handle `results[]` and errors as the prompt's step 8 says: `validation_failure` is not resubmitted in the run; `deferred_budget` is resubmitted and blocks `manifest_spent` until cleared; a lost answer, timeout or `502 recoverable` replays the **same body**; `submit_in_flight` waits `retryAfterMs` then replays; `epoch_mismatch` takes the epoch from the last answer.
5. Profile change: `profile.changed` carries the new profile and `regenerate[]`; `action: "complete"` (global) ends with `prediction_complete` reason `profile_changed`. A `409` profile/contract answer to `manifest_spent` ends with `profile_changed` / `runner_aborted`.
6. End: `prediction_complete` only for an owned run: no reason when the queue is empty; reason `manifest_spent` when every selected manifest film is settled and ready films may remain — that is a normal `status: complete` with a truthful Event (not `time_budget`, not «Прогнозы приостановлены», not a false `queue_empty`). No completion after `already_running`, `manifest_too_large`, `wrong_protocol`, `prediction_catalog_held` or `lease_lost`. Re-read `enrichment_status` and `enrichment_queue` and compare.

### Dry run and A/B (separate procedure, not this Task)

The dry run is an owner-approved manual experiment (AIR-450), never the schedule. It follows [ADR 0122](../../adr/0122-prediction-batch-runner-v2-dual-protocol.md) decision 10: **one** read-only `prediction_batch_start(dryRun)` takes the manifest (optionally with `manifestSize` and/or `pin`), and the ten size passes replay that one frozen manifest and **never call start again**. The start is a separate owner-run freeze step; each pass is the second prompt below, `DRY RUN PROMPT`, which takes the whole frozen manifest as an explicit input and has `prediction_batch_submit(dryRun)` as its only writer-shaped tool. Generation steps 4, 5 and 6 are byte-identical to the scheduled prompt's (a test compares them), so a size-A/B changes grouping only. The freeze, the private handoff and retention, the result contract and the comparison criteria are in the [dry-run A/B runbook](../../runbooks/prediction-batch-v2-dry-run-ab.md) and the machine-readable [sample and result schema](batch-v2-ab.schema.json).

The exact MCP calls (the frozen dry-run manifest has `runId: null`, and the MCP schema and the Worker still require a non-empty `runId` and a positive integer `epoch` on a dry-run submit; the dry-run branch never dereferences a run, so the fixed synthetic pair `runId: "dry-run"`, `epoch: 1` is used):

```
prediction_batch_start({trigger:"manual", dryRun:true, pin:{filmIds:[...]}})   // ONCE, by the owner's freeze step; never inside a pass; optional manifestSize
prediction_batch_submit({runId:"dry-run", epoch:1, dryRun:true, manifestHash:"<from start>", items:[{filmId, fingerprint?, prediction, inputHash:"<from start>"}, ...]})
```

Nothing is written (no lease, run, queue, fingerprint, prediction, version object or view-index entry); `tests/scheduled-task-prompt-v2.mjs` hands one serialized manifest to ten independent passes, counts a single start in total and checks zero D1 and R2 change.

### Owner activation gate: short-run completion

Owner decision 13 November 2026 (AIR-463): spending the selected manifest is a **normal** completion (`reason: manifest_spent`, `status: complete`, truthful Event with selected/created/outstanding counters). Do not use `time_budget` for a spent short run and do not describe it as «Прогнозы приостановлены». Enabling up to four independent hourly v2 Tasks that share one lease/queue remains [AIR-451](https://trello.com/c/NN3N6kRp) and needs a separate operation-specific owner GO; this prompt file alone edits no Scheduled Task registry. Legacy v5 must stay disabled for the whole cutover.

### Installation, activation and rollback (owner gates)

- **Install (disabled):** creating the Task, setting its schedule and every prompt edit need the owner's operation-specific approval. Create it disabled; paste the text below; compare the registry readback (length and SHA-256) with this header.
- **Activation (AIR-451):** the approved Predictions Tasks are enabled. The owner disables the legacy hourly Task and enables the v2 Task(s) in the approved order, then reads the registry back. There is no feature flag, and the Worker does not read the registry.
- **Rollback:** disable the v2 Tasks and re-enable the legacy hourly Task. No data migration; runs, retries and predictions already written stay valid under the same contract.

Для каждой группы СНАЧАЛА предпроверка: prediction_batch_validate({items}) с теми же объектами, которые собираешься отправить ({filmId,fingerprint,prediction,assessment,metadata} с modelMetadata фильма из FROZEN_MANIFEST только если evidence или assessment.sources ссылаются на metadata:*; {filmId,prediction,assessment} для prediction_only, с metadata (modelMetadata фильма) и там, где assessment.sources ссылается на metadata:*; assessment по шагу 3а; без inputHash и других ключей, metadata только в предпроверке). Она read-only, не проверяет манифест, inputHash и профиль. Исправляй только то, что подтверждено реальным знанием фильма или реально использованным источником; НИКОГДА не выдумывай refs, не добавляй model_knowledge или web_research без реальной основы и не подтверждай качество исполнения одним metadata (в том числе stakes). Не более ОДНОЙ повторной предпроверки группы (только исправленных фильмов), без циклов. Фильм, у которого остаются issues, подай как {filmId,failure:{kind:'parse_error'}}. Для каждого фильма запиши preflight {valid,attempts (1 или 2),issues[{path,code}] последней попытки}; каждый вызов prediction_batch_validate это вызов в calls[] с kind 'preflight' (callId из той же сквозной последовательности, groupIndex, itemCount, bodyBytes, toolMs, observedProfileHash null), вызов submit с kind 'submit'. ПОТОМ отправка: prediction_batch_submit({runId:'dry-run',epoch:1,dryRun:true,manifestHash,items}). runId 'dry-run' и epoch 1 это фиксированные синтетические значения, настоящего run нет. Item как в боевой задаче ({filmId,fingerprint,prediction,assessment}, {filmId,prediction,assessment} для prediction_only или {filmId,failure:{kind:'parse_error'}}, если по шагу 5 честную карту составить нельзя), плюс inputHash этого фильма из FROZEN_MANIFEST. Не добавляй других ключей. КАЖДОМУ реальному MCP-вызову (prediction_batch_validate, повторная предпроверка, отказ по размеру, prediction_batch_submit, каждый вызов разбитой группы) присвой callId из ОДНОЙ сквозной последовательности 0, 1, 2… строго в порядке вызовов, без повторов и пропусков (например: предпроверка 0, submit 1, следующая предпроверка 2, следующий submit 3); фильму запиши callId ИМЕННО вызова prediction_batch_submit, в ответе которого записан его результат (никогда вызова предпроверки; null у not_submitted); groupIndex фильма это номер его группы в порядке films[] (позиция фильма делённая нацело на GROUP_SIZE). ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА ПРОФИЛЯ после КАЖДОГО submit: сравни profile.hash из ответа с manifest.profile.hash из FROZEN_MANIFEST и запиши его как observedProfileHash этого вызова. Если они различаются, профиль сдвинулся после заморозки: НЕ отправляй больше ни одной группы, остальным фильмам поставь submitStatus 'not_submitted', в результате укажи stoppedReason 'profile_moved' и закончи проход. Группа больше 56 KiB отклоняется целиком: с assessment группа из 10 фильмов с полным fingerprint обычно не помещается, поэтому раздели её заранее на части (например 5+5, при необходимости по одной), запиши каждый вызов в calls[] и фильму callId его submit; GROUP_SIZE (сколько фильмов генерируешь) от числа items в одном вызове не зависит.
8. Результаты: would_write, already_current, not_eligible, validation_failure; liveInput same|changed|not_eligible. Записывай liveInput как есть: фильм с liveInput не same в сравнение качества не попадает. После validation_failure при submit ничего не повторяй и не исправляй: просто запиши validation {stage, issues[{path,code}]}. Для каждого фильма с validation_failure (в том числе с failure parse_error, поданным тобой) запиши failureReason ровно одним из: insufficient_metadata (в metadata фильма нет данных для честной evidence-карты), insufficient_knowledge (знаний модели недостаточно для честной карты), json_unparseable (валидный JSON сформировать не удалось), other; у остальных фильмов null. Выбирай по фактической причине, не подгоняй её под желаемый результат и не меняй правила evidence.
