# Prediction schedule and run diagnostics

> **Operator procedure:** safe verified status and queue diagnostics are standing-authorized L0 under [authorization policy](../process/authorization-and-escalation.md). Do not launch extra production predictions, clear/reset leases or edit Scheduled Tasks without the appropriate existing L2 execution contract or owner-approved L3 plan. This document grants no new automatic model runs.

[Prediction-runner API contract](../reference/api/prediction-runner.md). Expected task behavior and hourly discovery catch-up are defined in [Scheduled Tasks](../reference/scheduled-tasks.md); verify actual settings in the live registry.

## Proportionate triage

For a single deferred film, ordinary backoff or an interrupted but recoverable run, prefer the next Scheduled Task and its built-in retry/resume. Do **not** require a complete queue audit, full R2 snapshot, new model batch, manual lease reset or per-item diagnostic inspection just to establish that one retryable failure occurred. Read the queue/runner summary first; use film diagnostics only for persistent, identity-sensitive or unexplained failures, and broad parity only for a demonstrated cross-film inconsistency. Keep owner gates for manual producer calls and hard ownership/lease fences: retrying a non-idempotent model submission blindly can duplicate work or corrupt run state. [Risk-proportional policy](../process/agent-workflow.md#risk-proportional-operational-safeguards).

## Hourly discovery preflight and orphaned checkpoints

The hourly Task's discovery catch-up runs **before** prediction processing, but a blocked discovery continuation must not stop safe prediction work. Read `probe_read`, `epg_status` and `epg_pipeline_status`; verify the currently published `programmeRunId` and the pinned continuation generation. Only a server-authorized existing-generation continuation may be advanced by a separate, owner-authorized writer execution. A healthy paused checkpoint may allow ordinary sequential `epg_sync_step` calls; each call runs no more than one discovery chunk.

For `continuation.stage=running`, do **not** treat elapsed wall time, a stale event, or the `running` value alone as permission to recover. Use the Worker's read-only `continuationHealth`:
- **`live` / live lease:** another writer may still own the work. Do not call `epg_sync_step`.
- **`orphaned` with `lease=expired|none`:** the Scheduled Task may issue one ordinary step **only** after independently confirming an exact match with the published generation in both read-only status responses, `generationConflict=false`, positive integer `remainingChunks`, `resumeBudget` within that budget, and no other active lease, hard wait or future retry timestamp. The Worker, not the caller, settles a hop-marked completed chunk or safely resumes an unmarked/incomplete chunk. A missing hop marker does not prove that the older chunk completed.
- **Missing/unknown health, wrong generation, `settled`, `busy`, or conflicting lease:** fail closed; never reset the lease, overwrite the checkpoint, force a retry, or launch a new EPG run from the hourly task.

After the step, inspect `discovery.nextAction`: `continue` permits only the next verified step on the same published generation; `wait` honors backoff and `nextCatchUpAt`; `stop` ends discovery. An MCP error, a timeout or a lost response is not proof the underlying write was rolled back: the chunk's checkpoint is written before the lease release, the diagnostics entry and the response, so re-read `epg_pipeline_status` first; a `settled` continuation whose `hopId` matches `lastBatch.hopId` means the step committed and only its response was lost, and the next ordinary step continues it (after the lease expires if its release was lost too). A published programme and a completed discovery continuation are separate milestones. For deeper checkpoint interpretation see [MCP connectivity and recovery](mcp-connectivity.md); for the caller's expected rules see the [Scheduled Task contract](../reference/scheduled-tasks.md).

## ChatGPT Scheduled Tasks: timing and troubleshooting

**The hourly schedule is a target, not an exact Worker execution time.** The ChatGPT Scheduled Task is external to Cloudflare Worker `iptv` (there is no hourly Cloudflare Cron driving predictions). The nominal trigger is **`:20` Europe/Madrid every hour**; an invocation can begin after it rather than precisely at `:20`; delays can vary and there is **no documented guaranteed ±10-minute window**. The footer's `Следующий запуск по расписанию: около HH:MM` is the nominal trigger from `nextScheduledRun` (see [timing](../reference/scheduled-tasks.md#timing-nominal-trigger-versus-server-gate)), an **estimate of the schedule**, not a countdown, SLA, or evidence that a new run has started or that the external task can run; it reads `—` when the Worker cannot compute the schedule. A recognition warning that execution was not confirmed is not a stored usage-limit stop, and it is withheld when the discovery batch or the checkpoint time is missing, unparseable or from another generation: the recognition line is then unknown evidence. Only a prediction run that recorded `stopReason` `quota` is shown as a usage limit, at that run's finish time. The Worker does not read the task registry or a usage account ([what the footer can tell](../reference/scheduled-tasks.md#what-the-footer-can-tell-about-a-missed-hourly-run)). Times shown in the app use Europe/Madrid. A discovery `nextCatchUpAt` on the whole hour is the server's earliest permitted step, not the task's run time; the catch-up is expected at `discovery.nextScheduledRunAt`.

**Do not infer scheduler accuracy from /events timestamps.** A `Прогнозы запущены` event records a server-side run start; `Прогнозы восстановлены` or `Прогнозы продолжены` describes a lease recovery/continuation, not necessarily a fresh scheduled trigger. Progress/completion events can appear much later. In the Events history captured on 15–21 October 2026, visible event times included minutes around `:50` through `:07`, plus a `:22` outlier; these mixed event types do **not** establish a reliable scheduler start-time distribution. For exact scheduler triggers, inspect the Scheduled Task execution history separately.

**An unchanged status is not a missed trigger.** The footer can retain a previous `storage_error` until a later run emits updated state, and an invocation with `already_running`, `busy`, or `noop` may not produce a new Events entry. Verify independently:

1. Check the ChatGPT Scheduled Task is enabled and review its last execution time/result; do not treat the next nominal clock hour as a deadline.
2. Via authorized IPTV Watchlist MCP, inspect `enrichment_runner`, `enrichment_status`, and `enrichment_queue`, including `runId`, `state`, `lastHeartbeatAt`, `hotRemaining`, `coldRemaining`, and retry/backoff.
3. `pendingCount=0` only means no immediate *hot/watchlist* work. It does **not** mean the full database is complete if `coldRemaining>0` (the queued runner can process off-watchlist cold films). Validate complete coverage using `confirmedFilmsTotal` versus `currentPredictionsTotal`, not the viewing-window counter. `localPercent` and `windowPercent` are tenths of a percent. The value `100` means the two counts are equal, or that the denominator was empty. An incomplete pair stays at or below `99.9`. A finished run is separate from a drained queue: `queue_empty` is stored only when the refreshed queue has no outstanding film, and `eligible_queue_empty` means films remain that the run could not take (deferred by retry or waiting behind hot work). The footer line and the completion Event say which: «все фильмы с актуальными прогнозами» (drained), «N фильмов ожидают повторной попытки не раньше HH:MM» (deferred; the time is the film's stored `retryAt` in Europe/Madrid, not the next scheduled run) or «N фильмов готовы к следующему запуску» (eligible now). The footer detail «Отложены до повтора» and `prediction_queue_overview` (`pending.deferredByRetry`, `pending.nextRetryAt`) show the same slices; a deferred film needs no action, the ordinary schedule retries it. See [the completion semantics](../reference/api/prediction-runner.md#run-completion-drained-queue-eligible-and-deferred-work) and [the recorded investigation of the earlier mismatch](../evidence/prediction/air-82-prediction-rca.md).
4. Check /events for the corresponding run's start/resume, progress, and terminal event. If a run is stuck or `storage_error` recurs, inspect authorized Cloudflare logs and stored checkpoints rather than forcibly clearing leases or resetting the queue.
5. When a run reports `failed > 0` with item `parse_error` rows, read `prediction_film_diagnostics` for each deferred film id (`prediction_pending` with `filter: deferred` lists them) and look at `retry.validation`. `stage: fingerprint_schema` or `prediction_schema` with `issues` such as `fingerprint.execution.payoff invalid_enum` or `fingerprint.moodLabels required` means the model output violated the published contract: the fix is in the caller's generation (compare with `enrichment_schema` `contract`), not in the Worker. `stage: caller_reported` means the caller itself could not parse the model output; `validation: null` with `classification: storage_error` is a system failure. A retry record without a validation summary has `validation: null`; it gains a summary only after a subsequent rejection. Do not reset `retryAt` or restart the runner to see the summary sooner; the deferred film is retried by the ordinary schedule. Field paths and codes are defined in [the submit validation contract](../reference/api/enrichment.md#submit-validation-contract).
6. Read-only check of the validation contract after a Worker deploy: call `enrichment_schema` and confirm `contract.version`, `contract.issueCodes` and the `execution` enum lists; call `prediction_validate` with a deliberately wrong sample (for example `execution.payoff: "medium"`, no `moodLabels`) and expect `success: false`, `valid: false` with those two issues and `storage: not_accessed`, and with a sample that follows the contract expect `success: true`, `valid: true` and empty `issues`; then read `prediction_film_diagnostics` for a currently deferred film and confirm its `retry.attempts`, `retryAt` and `classification` are what they were before the deploy. None of these steps writes. A live `results[].validation` on a real rejection is observed on the next authorized or scheduled run, not forced for a smoke test. If the connector does not list `prediction_validate`, its tool list is cached: refresh or reconnect the server in the client; do not work around it with a run. The hourly production task already requires `prediction_validate` before **every** `prediction_submit`. If the tool is unavailable, fail closed with `prediction_validate_unavailable`, never bypass it. For `fingerprint_and_prediction`, both checked flags must be true; for `prediction_only`, only the prediction is checked and the existing Worker fingerprint is reused. Require `success: true`, `valid: true`, matching contract version and the exact unchanged payload; correct and revalidate any changed fields. A tool error or a report without `success` and `valid` is the validator being unavailable, not a schema failure of the film: it must not be submitted as a per-item `validation_error`. Future changes to the task prompt or schedule still require separate owner approval and documentation review.

## Evidence confidence assessment

`src/domain/prediction-confidence.js` scores the fingerprint of one submit. The contract is [prediction confidence](../reference/domain/prediction-confidence.md). Submit stores `confidenceAssessment` on that new prediction snapshot and leaves the model's `prediction.confidence` unchanged. A caller value of the same name is discarded. Catalog, view, Finds, Similar, EPG and the hourly task do not call the function. A read does not recompute a stored object and does not add the key to an older snapshot.

Merging the Worker deploy is what makes the next natural submit write the field. A `prediction_only` item reuses its stored fingerprint: with no usable evidence the new snapshot is `legacy` or `insufficient` and its effective level is `low`, so it can leave Finds even when the model said `high`. That is the intended fail-closed result. It is also why merge needs a separate owner GO: a code deploy starts this write on the next scheduled submit. Do not start a model run, edit the hourly task, bump a prompt version, or recompute history to manufacture a sample. ## Prediction domain marker

Mutable prediction state is now D1-authoritative after migration `0007` and activation on 3 November 2026 ([ADR 0078](../adr/0078-d1-authoritative-prediction-domain.md), [D1 reference](../reference/data/d1-schema.md#prediction-domain-schema-v7)). A code deploy does not apply the file and does not switch the marker. Production cutover and the first successful natural run are recorded in [dated evidence](../evidence/d1-migration/air-317-production-cutover-2026-11-03.md). That marker switch does not change the hourly schedule and does not add a flag or a cron. The external Stage B prompt is the evidence instruction in the section above. Schema version 7 or newer without the prediction tables or a valid marker fails the prediction step and does not read the objects. A contract older than version 7 stays on the objects. The deployed Worker sets `PREDICTION_DB_REQUIRED` to `on`, so a missing `DB` binding fails closed. A local caller that omits that variable and the binding stays on the objects.

The offline script is `scripts/prediction-domain-authority.mjs`. With no write flag it prints status and writes nothing. It refuses a database path that names production and it does not call the network.

- `--load --confirm load --database <file> --snapshot <file>` copies that snapshot in one fenced batch per unit and leaves `mode` at `r2`. The fence is the generation just read. The load does not advance it, and a generation that is already above 0 does not block the load. An active runner or writer lease refuses the load before a write.
- `--activate --confirm activate --database <file>` sets `d1` only when those generations still match the load.
- `--revert --confirm r2 --database <file>` rewrites the mutable mirrors the rows still have, deletes a mutable mirror the rows no longer have, and checks each result. It sets `r2` only after that check. A missing or mismatched immutable body, or a delete that does not stick, leaves `mode` at `d1`. The rows and the immutable bodies stay.

The production entry is `scripts/prediction-domain-production.mjs`. It is not a substitute for the offline script. With no command it prints `{configured:false,writes:false}` and does not call the network. A write names `--target iptv` and its own confirm: `--apply` / `--confirm apply` plus `--producers-drained`, `--load` / `--confirm load`, `--activate` / `--confirm activate`, `--revert` / `--confirm r2`, `--release` / `--confirm release`, `--reconcile` / `--confirm reconcile`, `--materialize-fingerprints` / `--confirm materialize`. `--producers-drained` is the operator's statement that this Worker build is the one serving, that no prediction request is in flight, and that no request which read prediction state on the previous build is still between that read and its put. Deploying the code is not that drain. `--apply` then reads the runner and writer leases and sends no migration statement if either lease is active or those objects cannot be read. It sends only `0007` as one `{sql}` request when the contract is version 6 or higher, these tables are absent, and the version is not below 6. Version 6 reads back as 7. A higher version reads back as that same version, mode `r2`, generations 0, `writes` `open`. It does not lower the contract. `--load` copies the live mutable objects while both leases are idle. Its snapshot keeps only mutable prediction keys: the queue, the profile pointer, each `fingerprint.json` and `predictions.json`, the run files, the latest-run pointer and the two leases. Immutable bodies and the other objects under `enrichment/` are not part of that listing, and their number does not refuse the snapshot. More than 5000 fingerprint pointers or 5000 prediction bundles refuses with `prediction_domain_budget` before those films are read and before any D1 write. The body read accepts a Worker object with `text()` or `json()`, or the production reader's body stream, and reads that stream once as text. A fingerprint whose immutable body is missing, or whose hash does not match that body, refuses with `prediction_domain_body_missing` or `prediction_domain_body_mismatch` before the hold: `writes` stays `open` and `writeState` is `none`. The load then sets `writes` to `held`. `--materialize-fingerprints` reads the mutable fingerprint pointers and writes only a missing immutable body, create-only, when stripping the pointer's provenance leaves a body whose content hash is the pointer's `fingerprintHash`. An existing body is left in place when it is that body. A pointer that does not reconstruct, or an existing body that differs, refuses before any put. The command does not write a generation record, does not change D1, and does not apply `0007`. A put that has already created a body and then cannot prove the next object is that body reports `writeState` `partial`. An unacknowledged PUT is `writeState` `unknown`, `writes` true, and is not retried; a later run inventories create-only state again. A HEAD that fails before that PUT is not an uncertain write: acknowledged bodies stay `partial`, and a failure before any body is `writes` false. The command does not open a D1 connection. An open intent refuses the copy. It reads the snapshot again after the hold, one unit per `{sql}` request, and reads the snapshot again when a compare-and-swap commits nothing. A queue above 900000 characters, a film history above 80 rows, or a statement that cannot fit 100 parameters or 100 KB refuses that unit. It leaves mode `r2`. `--activate` holds writers, reads the snapshot again, and sets `d1` only when no intent remains and that snapshot still matches the rows. `--revert` repairs the mutable mirrors the rows still have, deletes a mutable mirror the rows no longer have, and sets `r2` with `writes` `open` only after each remaining mirror reads back equal, each removed mirror is gone, and no intent remains. It writes and deletes only when the install credential names the production account, the bucket `iptv`, and that account's `r2.cloudflarestorage.com` endpoint. Any other bucket or endpoint refuses before a request and does not change D1. A repair that cannot verify an immutable body, or cannot remove a stale mirror, leaves mode `d1`. A revert that has already put or deleted a mirror and then fails reports `writeState` `partial`, or `unknown` when that later request's outcome is not known. A queue or lease head captured before these tables existed does not put after the marker is `d1`. `--release` sets `writes` back to `open` only while mode is `r2` and no intent remains. `--reconcile` deletes an intent only when the object bytes match the hash stored before the put. A put that threw is not cleared by a later load. A lost write response is `writeState` `unknown` and is not retried. A failure after a committed unit, including the hold, is `writeState` `partial`. A busy lease before the hold is `writes` false. An unrecognized failure stays `reason` `failed` and adds `detail`: the error name, a short code or kind, and a message with hashes, film ids, credentials and stored bodies removed. `detail` names the failure. It does not authorize another attempt.

Do not perform those production state changes without the applicable owner-approved L3 plan and its holdpoints. Safe read-only preflight/readback may be included in that plan without separate per-read approval. Applying `0007`, the load, the activation, the revert, the release and the reconcile are each their own approval. After any future activation or re-activation, the next check is a read of the queue, the active profile and one film pointer, plus the immutable object each pointer names. Do not start a model run to produce that read. The live queue length and the longest history were not measured for this delivery; an over-cap snapshot is an activation refusal, not a guess.

While `mode` is `d1`, a prediction read that cannot verify the immutable body fails. Do not copy the mirror object back over the row. A queue conflict is still five attempts and then `prediction_queue_conflict`. The stored queue text is at most 900000 characters, and one film keeps at most 80 history rows. The queue is stored plain while its plain JSON fits and in the compact `dict1` encoding when it does not; readers always get the plain document ([reference](../reference/api/prediction-runner.md#queue-writes)). A write that does not fit even encoded fails and changes nothing.

## Prediction queue conflicts

A runner step (`next`, `submit`, `complete`) advances the stored queue and does not rebuild it, so Discovery chunks do not stall a run ([ADR 0113](../adr/0113-prediction-runner-advances-persisted-queue.md)); a `start` answer with `queueStale` means the rebuild could not read the catalog and the run uses the stored queue (read it as the state of its `refreshedAt`). Every writer of the prediction queue writes conditionally and rebuilds on conflict ([queue writes](../reference/api/prediction-runner.md#queue-writes), [ADR 0064](../adr/0064-prediction-queue-conditional-writes.md)). Until the schema v7 marker is `d1`, the condition is the object etag. In that mode it is the D1 generation. A conflict that outlasts 5 attempts is reported, never written over:

| Where | What it looks like | What to do |
| --- | --- | --- |
| prediction run | a `storage_error` stop, with `Prediction queue changed during write (<trigger>)` in Cloudflare logs; `retryHeal: "pending"` in the stop answer if the stop could not write the run's retries either | Nothing. The next scheduled run continues. The run's retries are written by its stop or, failing that, by the next start before it selects anything. Do not reset `retryAt`, clear leases or delete the queue |
| prediction start | `503 {status: "blocked", code: "prediction_retry_heal_pending", pendingRunId}` | Nothing. The previous run's retries could not be written yet, so this start selected nothing. It is not a stop: it writes no Event, and the last run shown stays the previous run. The next scheduled start tries again. Do not reset or delete the runner lease: it is what names the run whose retries are pending. If it persists across many hours, report it to the owner with `pendingRunId` |
| prediction start | `503 {status: "blocked", code: "prediction_catalog_held", cause}` | Nothing. An EPG publication is sealing and holds the catalog (`cause` `discovery_fence` or `discovery_incomplete`). The start kept no lease and wrote no Event. The next scheduled start tries again after the publication; read `epg_status` to see the seal. Do not repeat the start in a loop and do not touch the Discovery authority or leases |
| prediction next, submit or complete | `503 {status: "blocked", code: "prediction_catalog_held", cause}` | Nothing on the Worker. The catalog is held during an owned run. The run stays `running`, committed predictions are kept, there is no stop Event. `submit` may already have written the film (`results`, `committed`); an identical retry is `already_current`. Retry the same step with the same `runId` for at most `leaseTtlMs` (15 minutes), with `prediction_heartbeat` about every 10 minutes; if still held, stop calling and leave the lease to expire — do not `prediction_complete` and do not treat it as `storage_error`. The live Task prompt still treats a mid-run 503 as a systemic error until an owner-approved prompt edit Since AIR-431 this appears only when the step needs the catalog (a rebuild after a programme, profile or contract change, or the by-id read of a new batch); a Discovery chunk alone no longer causes it. |
| EPG commit | `enrichmentQueueError` on `sync.json` | Nothing. The commit is complete, and the next rebuild (any prediction step, profile update or resolver chunk) refreshes the queue |
| resolver chunk | `prediction_queue_checkpoint: …` in the discovery status | Nothing beyond the ordinary discovery steps |
| owner reconcile | `409 {code: "prediction_queue_conflict"}` | Another writer is active. Read `enrichment_queue` later; a repeated reconcile still needs its own owner approval |

Repeated conflicts across many hours are a finding for the owner. Look in the logs for which writers overlap; never fall back to an unconditional write.

**Budget refusals.** `enrichmentQueueError: prediction_domain_budget:<guard>` in `epg_status` names the limit that refused the rebuild; the Worker also writes one log line `{"event":"prediction_domain_budget","guard":"<guard>"}` without film ids. `queue_chars` means the document is over 900000 characters even encoded; `overlay_rows` means a prediction table holds more than 20000 rows (the view-index overlay reads the rows, not the index keys); `statement_bytes`, `bind_limit`, `history_limit` and `mirror_list` are the other fixed limits. A refusal writes nothing, so the queue keeps its previous generation and `prediction_queue_overview` shows `queue_programme_differs`. Do not start a prediction run to test it: a start that cannot rebuild the queue still takes the runner lease.

**A start that answered 502 `storage_error`.** The answer does not say where it failed. Read the Worker log line `prediction_boundary_failed` for that start (`requestId`, `runId` as in the run's diagnostics): `stage` names the step and `code`/`guard` the error. `stage: queue_refresh` with `code: prediction_domain_budget` and a `guard` is a queue or overlay budget refusal; `stage: unknown` means the error did not cross a named step. A failed start released its runner lease. Do not repeat the start to look again: each attempt takes the lease and writes a blocked run.

**A start whose answer never arrived.** A caller that reports an unserializable or missing `prediction_start` answer while `enrichment_status` shows a `running` run with `delivery: unconfirmed` did not get a Worker error body. Read the Worker invocation for that minute in Cloudflare telemetry: `outcome: exceededMemory` with HTTP 503 means the isolate was ended after the run was saved and before the answer was formed; there is then no `prediction_boundary_failed` line, because the isolate did not survive to write it. The run is real: leave it to the ordinary lease expiry and recovery, do not adopt its `runId` from a read, and do not repeat the start to check.

**Rollback.** A code revert restores the previous blind writes; the stored queue format is the same while the queue is plain, so no data step is needed. Once the queue is stored in the `dict1` encoding, a build without that support cannot read it, fails closed (`prediction_domain_unavailable`) and cannot rebuild it, so a blind code rollback leaves the prediction steps failing. Roll back only to a build that still reads `dict1`, or first ship a compatible build that rewrites the queue as plain (a rebuild that fits under the cap writes plain text). Do not edit or reset the queue rows to bypass this. A revert does not restore retry metadata that an earlier overwrite already lost. Continue with the ordinary schedule; do not reconcile or edit the queue to "repair" it without a separate owner approval.

## Reading the step timing line (AIR-438)

`next` and `submit` log one `prediction_step_timing` line each ([fields](../reference/api/prediction-runner.md#step-timing-line-air-438)). It is a safe read: nothing starts, retries or writes. To see where a run's time went:

1. Query Workers Observability for the Worker `iptv` with the needle `prediction_step_timing` and the time range of the run (the recipe used for the `epg_phase` events works the same: `POST /accounts/{id}/workers/observability/telemetry/query`, view `events`, filter `$metadata.service = iptv`, a `needle`). The line is the event's `source`.
2. Compare `wallMs` with `busyMs`: a large `unattributedMs` is awaits and scheduling (the Workers clock may advance only across I/O, so synchronous compute can read as near zero), a large `busyMs` is storage. `overlapMs` says how much of the storage time ran in parallel.
3. Read `classes` for the stage that holds the time: `r2:queue` and `d1:*` for the stored queue and the prediction tables, `r2:view_index`, `r2:film_state`, `r2:lease`, `r2:run`.
4. Group by `step`, by the deploy (`$workers.scriptVersion.id`) and by `notes.selected` or `notes.bodyItems` before taking p50 and p95; a mix of deploys or batch sizes hides the cause.

Since AIR-442 a `next` or `submit` reads the run record, its diagnostics row, the queue and the runner lease once each and writes the view index once per film, so `r2:run`, `r2:lease`, `r2:view_index` and `r2:queue` counts drop against a Worker that predates it: compare only the same step (`next` with `next`, one-film `submit` with one-film `submit`) and the same deploy. The diagnostics row (`run-diagnostics`) is written from the same values as before; its `hotRemaining` and `coldRemaining` come from the queue counters the step last held, not from a separate queue read.

A missing line for a step means the Worker that served it predates the instrument or the step failed before answering. Telemetry is not a stored record: its retention is the platform's (the Observability tool reported a seven-day queryable range on 11 November 2026; confirm it before relying on older runs). The query shape above is the one used for the `epg_phase` events on that date; the first read of a `prediction_step_timing` line is the check that `source` carries the fields described here. No production write or run is needed to read it, and none is authorized by this page.

## One film without a current prediction

Open `/admin/limb`, find the film among the prediction or fingerprint items and press «Разобрать прогноз» (or read `GET /api/admin/prediction-recovery?film=<storedId>`, [contract](../reference/api/admin.md#prediction-recovery-get-apiadminprediction-recovery)). The read writes nothing and starts nothing. There is no targeted retry or requeue of one film ([why](../reference/api/admin-actions.md#prediction-recovery)); act on the verdict instead:

| Verdict | What to do |
| --- | --- |
| `prediction_current`, `index_ahead_of_queue` | Nothing. The next queue refresh drops a film whose prediction is already current |
| `queued_ready`, `in_flight`, `run_active`, `waiting_behind_hot` | Wait for the ordinary schedule. The time shown for the next run is the nominal trigger, an estimate |
| `retry_backoff` | Wait for the shown retry time. Do not reset `retryAt` or restart the runner |
| `queue_refresh_pending` | Wait for the next refresh (any prediction run, EPG commit or profile update). A manual `POST /api/enrichment/queue/reconcile` is a production write that rebuilds the whole queue; it needs separate owner approval and is not a per-film fix |
| `ready_no_runs` | Check the prediction Scheduled Task as in the section above: enabled, last execution, result. Do not start a run from the page |
| `repeated_failures` | Follow the reason. Model output (`validation_error`, `parse_error`): read `prediction_film_diagnostics` for `retry.validation` and fix the caller's output against the submit contract (step 5 above). Infrastructure (storage, quota, time budget, model availability, lease): check that cause in run diagnostics, Cloudflare logs and the Task history; the model output is not at fault. Unrecognised kind: investigate the classification and the run history first. In every case do not reset `retryAt` or restart the runner |
| `index_inconsistent` | The view index and the film objects disagree: investigate the index, not the queue |
| `not_in_catalog` | The film is in neither the published programme nor the catalog: an identity question for the resolver, not a prediction one |
| `snapshot_partial`, `profile_missing`, `queue_unavailable`, `film_unreadable`, `queue_state_unknown` | Press «Проверить заново» later. Persistent disagreement after the next refresh is a finding for the owner, not a reason to write |

«состояние запуска неизвестно» means the lease or the latest run could not be read or is malformed; it is not evidence that no run is active, so do not clear a lease on its basis. «Состояние изменилось» after a recheck means one of the read objects (queue, profile, index, programme, film objects, lease or latest run) changed since the previous check; the panel shows the fresh verdict.

Keep existing Cloudflare Access protections; don't embed auth tokens in links, logs or documentation. Do not trigger extra production sync or prediction runs just to test timestamps. The legacy Sites-specific prompt in [prediction-scheduled-prompt.md](../archive/legacy-sites/prediction-scheduled-prompt.md) is historical and must remain disabled.

The Scheduled Task itself is outside this repository. Compare explicitly timezone-qualified iCalendar recurrence and `default_timezone` metadata separately: metadata disagreement is not by itself proof of an incorrect trigger. For scheduling accuracy use actual task execution history. Until that task sends `fault` and echoes `receivedRequestId`, caller-reported metadata on a production run stays unconfirmed. The Worker records the attempt and the response it formed either way. The caller change is specified in [AIR-88](../reference/api/run-diagnostics.md).
