# ADR 0193: A Scheduled Task starts a prediction run with a server-issued key and a fast receipt; the heavy preparation runs in a Cloudflare Workflow and is read back as an immutable manifest

**Status:** Proposed (the target direction is approved by the Product Owner in the AIR-573 handoff of 2026-11-21; the concrete choices below await review and acceptance)  
**Original decision date:** 2026-11-21 (direction); the concrete design is recorded with the implementation PR  
**Recorded at:** 2026-11-21  
**Approval source:** The Product Owner's handoff comment on [AIR-573](https://trello.com/c/4pD66DLd#comment-6b01d7b358e86c3c2baa6752), 2026-11-21 17:41 UTC: approved a fast asynchronous start with a server-side idempotency key and a later readback of the prepared manifest, replacing the long synchronous start for Scheduled Tasks, with all four existing Tasks moved together after delivery.  
**Related work:** [AIR-573](https://trello.com/c/4pD66DLd) (P0 incident); implemented on top of [PR #854](https://github.com/vladimino/iptv-watchlist/pull/854) ([ADR 0188](0188-idempotent-keyed-batch-start-and-early-start-claim.md)); the health contract of [AIR-556](https://trello.com/c/ZjqzW7EB) is extended, not duplicated; [AIR-574](https://trello.com/c/ZyUoLRki), [AIR-575](https://trello.com/c/4ncE69Ic), [AIR-560](https://trello.com/c/NZ70Dzom) and the recovery-priority work are not touched.  
**Supersedes:** In part [ADR 0188](0188-idempotent-keyed-batch-start-and-early-start-claim.md): its caller-composed key and the validation gate for its source (section 5), and the synchronous join with a bounded wait as the protocol of the Tasks. The claim, the fencing, the join eligibility (`clientSubmitAt`), the field-preserving lease writes, the commit guard and the no-foreign-adoption rule of ADR 0188 stay in force and are reused.  
**Superseded by:** None

## Context

Confirmed from the AIR-573 traces of 21 Nov 2026 (Europe/Madrid), recorded on the card and in [the evidence note](../evidence/prediction/air-573-deferred-start-offline-2026-11-21.md):

- A synchronous `prediction_batch_start` took 75–90 s (S5 `:15`: 90.166 s; `:30`: 78.883 s, a 39,372 byte manifest, 325 D1 calls, 51 R2 operations, three preflights, a 20.758 s queue refresh and a 36.017 s persist). A second HTTP start arrived about 60.6 s after the first and was answered `already_running`; the Task treated that as a lost slot and ended, leaving its own run in a live lease.
- After [PR #854](https://github.com/vladimino/iptv-watchlist/pull/854) the keyed start is correct, but it stays dormant: a natural `:15` probe found the `invocationKey` schema present and **no** scheduler invocation id, `scheduled_for` or source available to the Task. ADR 0188's key (derived per Task and slot) therefore has no provable source, and its validation gate cannot be passed.
- At `:30` a different failure appeared: the Task received `runId` and `selected=5` and ended about 3 s after the Worker logged a successful start, with no heartbeat, submit or complete.

**Not established:** who issues the repeated request, and why the Task ends after a receipt. Neither a faster synchronous path nor a stricter "do not repeat" prompt rule addresses both, so this ADR does not depend on either answer.

## Decision

1. **The server issues the key before the start.** The MCP tool `prediction_batch_key` returns `{status:'issued', invocationKey}` with `dk1.<32 hex>` (128 random bits from the platform). It reads and writes **nothing**: no lease, no run, no storage. A lost answer leaves nothing behind, and a repeat only returns another unused key. A Task calls it once per execution, keeps the key and sends the **same** key on every repeat of that start. The key is not composed from the model, the clock, the Task name or the slot, and the Worker does not need the scheduler's invocation id.
2. **The run id is derived from the key, and one attempt per key is enforced by a marker written before the dispatch.** A deferred start's run id is `dk-` plus the first 32 hex characters of the SHA-256 of the key (a one-way derivation: the key is never stored or logged), so a retry of the same invocation finds its attempt, its terminal outcome and its manifest without any index, and a new invocation cannot reuse the id (fresh executions use fresh keys). Two create-only records live under `enrichment/batch-start/`: the **attempt marker** (`attempt/<runId>.json`, argument hash and epoch) and the **terminal outcome** (`<runId>.json`: `ready`, `refused` with the existing refusal code, or `failed`). The marker is written **after the claim and before the Workflow instance is created**, so it exists whenever a dispatch is possible, even if the request then dies. A replayed or stale instance never overwrites either record.
3. **The start decides in a fixed order and never dispatches the same invocation twice.** `prediction_batch_start({deferred:true, invocationKey})` requires an issued-shape key (`dk1.…`) and is never a dry run or a pin. (a) A terminal `refused` or `failed` outcome of this key is answered as the typed `409 start_refused` / `start_failed` (with `outcomeCode`), whatever the lease is doing now, including when another run owns it. (b) A live lease of this run id with the same argument hash and no client submit answers the **receipt**: `accepting` when no marker exists yet (the first request has claimed but not written its marker: repeat the same start), `preparing` or `ready` otherwise; the holder is read again after the records, so a takeover between the reads is refused. Another argument set is `already_running` with `key_args_mismatch`. (c) A `ready` outcome with no live lease is `409 start_finished`. (d) A marker with no live holder and no outcome means the attempt ended unrecorded: it is recorded once as `failed` and answered typed, never dispatched again. (e) Otherwise it takes the 180 s claim under the derived run id (another live holder is `already_running`), writes the create-only marker, and only then creates one Workflow instance whose id is the run id. **A claim that finds the marker already written lost the race to an earlier attempt** (which may have finished and released while this request was between its reads and its claim): it releases itself, fenced by its own epoch, answers what is known and never dispatches, so no lease is retained and no second preparation exists. If the Workflow binding is absent the answer is `503 deferred_start_unavailable` before any claim; if the marker cannot be written, the claim is released with the same answer and nothing was dispatched, so the same key may start again.
4. **An error from `create` is reconciled, not assumed, and the attempt is one-shot.** If `create` throws, the platform is asked about the instance identity (the run id). An instance that exists keeps the claim and is accepted (it may already be preparing; the earlier assumption that an instance only starts after the claim is released is withdrawn). A definite "not found" ends the attempt typed (a `failed` outcome `deferred_start_unavailable`, the claim released by its epoch, `503 deferred_start_unavailable`): the same key then gets that typed failure and is **not** dispatched again; the next execution uses a fresh key. An unknown state keeps the claim and answers `503 deferred_start_ambiguous`; a retry gets the live receipt, and if no instance ever ran the claim expires and the next retry is the typed `start_failed`, bounded by the 180 s claim. A request that dies after the marker leaves an attempt that ends typed the same way; a request that dies between the claim and the marker never reached the platform, its claim expires, and the same key may claim again (a new epoch) and dispatch once.
5. **The preparation is durable and adopts its claim.** A Cloudflare Workflow (`iptv-prediction-start`, class `PredictionStartWorkflow`, one instance per run id) runs one step `prepare` with **no retries** and a 4 minute timeout. It runs exactly the keyed start of ADR 0188 (preflights, queue refresh when needed, revalidation under the claim, conversion under the same epoch, the fenced persist, the stored manifest) and then records the terminal outcome. The instance is bound to the epoch it was dispatched with (its payload carries it, and every release on this path names it): a claim that is not live, not this key's or of another epoch ends it before any side effect (`start_claim_lost`), and a delayed handler of an earlier epoch can neither release nor prepare against a later epoch of the same run id. A refused or failed preparation releases its claim, and a refusal with `prediction_catalog_held` still leaves the neutral skipped Event of [ADR 0190](0190-catalog-held-start-is-a-skipped-event.md) (the preparation does not pass the route exit that records it, so it records it itself). `waitUntil` is not used.
6. **Readback uses the existing manifest tool, with a typed result for every ending.** `prediction_batch_manifest` answers, for a deferred run id: the terminal `start_refused` / `start_failed` outcome **first**, even when a partial run row exists; `manifest_pending` (HTTP 409, `retryAfterMs` 5000) while the claim is live and while the preparation mark is set; the usual envelope, profile, contract and film parts once the run is ready; and, when there is no run, no outcome and no live claim, the typed `start_failed` with `outcomeCode: 'start_lost'`, never `unknown_run`. The polling interval is 5 s because a Scheduled Task cannot be assumed to honour arbitrarily many short polls.
7. **Readiness is one atomic, owner-fenced edit, and the preparation holds the short lease throughout.** While a deferred run is being prepared the lease carries a preparation mark; the claim, the persist gate (set, renew, clear) and every renewal made by the preparation use the **180 s** TTL, so a Workflow timeout or crash at any point leaves at most about 3 minutes, never 15; only a renewal by the client (a heartbeat, which records `clientAckAt`) restores the full TTL, and the ordinary submit, keyless and synchronous keyed paths are unchanged. The last write of the preparation is one lease edit, fenced by the run, the epoch and the gate token, that removes the gate and the preparation mark and keeps the short expiry unless the client already renewed (an acknowledged renewal is never shortened). The manifest is stored before it but **served only after it**; if it does not happen the start fails typed and the lease is released. A client heartbeat during the persist is serialized by the prediction writer (it answers `busy` and is retried).
8. **Isolation.** A receipt needs the same run id (derived from the key), argument hash and no client submit on a live holder; four concurrent Tasks with four issued keys produce one accepted run and three `already_running` answers, as today. A key that was issued but never used writes nothing. **A full loss of the key or the Task context is not recoverable by this protocol**: the next start gets `already_running` until the live claim or short lease expires (at most about 3 minutes), then proceeds with a new key; the lost invocation's own record ends typed (`start_failed` / `start_finished`). No source of correlation beyond the issued key is claimed.
9. **Observability.** The start's step-timing line carries counters `deferredAccepted`, `deferredReplay`, `deferredUnavailable` next to the ADR 0188 ones; the Workflow step logs one sanitized `prediction_start_prepared` line (phase, code, `prepareMs`, preflights, refresh rounds, claim renewals; no key, no payload). **Repeated orphan starts become one more reason of the shared AIR-556 verdict** (`predictionStallAssessment`, used by the Footer and the Monitor, not a second monitor): with eligible work, at least three ownerless starts since the last confirmed progress (a start turned away with `already_running`, or a run abandoned without a film; a run still `running` is not counted) and at least 20 minutes without progress give `no_progress` with `reason: 'repeated_orphan_starts'`. The existing 60-minute rule is unchanged. A `start=200`, an `accepted` receipt or an `already_running` is never progress.
10. **Compatibility and rollback.** The synchronous start, the synchronous keyed start of ADR 0188, a keyless start and `dryRun` are unchanged and remain until the Tasks are moved. Rollback is a prompt change back to the synchronous start plus, if wanted, a code revert; the Workflow definition then stays inert. No schema change, no feature flag, no migration.

Not decided here: the Task prompt change and the rollout order (owner and Controller, after delivery; the minimal prompt delta is in [the delta note](../reference/scheduled-task-prompts/hourly-predictions-batch-v2-deferred-start-delta.md)), any manual run, lease reset, flag or schedule change, the manifest size, the recovery ranking, the S7 research and AIR-574/575.

## Alternatives considered

- **Only speed up the synchronous start.** Rejected as the fix: it is already optimised in AIR-471 and AIR-486 and still takes 75–90 s; it also leaves the Task exposed to any later slowness and does not explain the `:30` end after a receipt. It remains useful work, not the protocol.
- **A stricter prompt rule against repeating the start.** Rejected: the source of the second request is not proven, and the rule cannot be tested offline.
- **A key composed by the Task from its schedule** (ADR 0188 section 5). Rejected: the natural probe shows no scheduler invocation id or scheduled time reaches the Task, and a model-composed time or random value is not stable across a re-issue.
- **A signed or stored issued key.** Rejected: a signature needs a new secret, a stored key needs new state, and neither adds isolation over 128 random bits that are used only for correlation behind the owner-only Access boundary; a forged or reused key can only collide with itself.
- **`ctx.waitUntil` for the preparation.** Rejected: the platform grants a bounded time after the response (about 30 s), shorter than the measured preparation.
- **A Durable Object or a Queue.** Rejected: a new class with a migration or a new binding and delivery semantics for no gain over a Workflow, which this Worker already uses and which keeps one instance per run id.
- **Precomputing manifests on the hourly cron.** Rejected: manifests would be stale against the queue, and ADR 0122's revalidation would refuse many of them.
- **A fresh random run id per start, with the key matched only against a live lease** (the first design of the implementation). Rejected in review: after a preparation refuses or fails and releases its claim, a retry of the same key (its receipt lost) acquires a new run id and starts a second preparation, and the caller can never discover the first outcome. The derived run id and the attempt record fix exactly that.
- **Re-dispatching an ambiguous attempt under a new epoch** (the second design: the marker written after `create`, an instance adopting whatever claim is live). Rejected in review: a repeat that read "no outcome, no marker" before an earlier attempt finished could then reacquire the run id and be answered with the earlier, already terminal instance (the platform rejects a duplicate id), and a delayed handler of one epoch could release another's lease. The one-shot attempt with a marker before the dispatch and an epoch-bound preparation replaces it.
- **A long synchronous wait on the repeat (ADR 0188's `start_pending` bound).** Kept only for the synchronous keyed start; the deferred start never waits.

## Consequences

- The request path of a start is a claim and an instance creation (offline: 5 D1 round trips and 4 R2 operations); the measured 148 D1 round trips of the preparation move off the caller's critical path. The preparation is somewhat heavier than the unkeyed synchronous start (claim, gate and guard overhead; about 148 against 84 D1 round trips offline), which matters only for its own duration.
- Deploying creates the `iptv-prediction-start` Workflow definition (a Cloudflare resource, no data). It is inert until a Task sends a deferred start.
- A Task must poll with the returned `retryAfterMs`, then heartbeat soon after the manifest is ready (the short lease lasts 180 s); the delta note gives the minimal prompt change.
- A client heartbeat that arrives while the persist runs is answered `busy` (the prediction writer serializes it) and succeeds when repeated right after readiness; the prompt delta says so.
- Four Tasks that start within one preparation window still lose the slot to the first, as before; the loser is `already_running`, which is a lost slot, not an incident.
- One more verdict reason in the shared progress assessment can raise the alert earlier than 60 minutes; it can be wrong only for a run that is not abandoned yet, which the assessment excludes while the lease is live and young.

## Recovery and migration boundary

Code only: no schema, no flag, no data migration. The Workflow definition created by the deploy is inert and stays after a code rollback; removing it is a separate owner-gated operation. A prompt rollback restores the synchronous start. Terminal outcomes and attempt markers under `enrichment/batch-start/` are small create-only records and need no cleanup. This ADR authorizes no production operation: moving the four Tasks, any run, lease reset or Worker setting remains owner-gated.
