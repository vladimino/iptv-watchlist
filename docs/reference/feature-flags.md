# Runtime feature flags

**Maintained contract; dated observations, not a live configuration dashboard.** Reviewed against GitHub `main` and Trello evidence on 2026-10-25 for [AIR-146](https://trello.com/c/qfqYibFB). All flags below are Cloudflare Worker **environment variables**, not switches managed by GitHub. [`wrangler.jsonc`](../../wrangler.jsonc) uses `keep_vars: true` and deliberately does not declare their production values. A code deploy does not reset these variables. The currently deployed value must be read from authorized Cloudflare settings or from the owner-only MCP tool `feature_flags` (see [Reading the deployed values](#reading-the-deployed-values)) before making operational decisions.

Do **not** interpret a source default, a dated Trello comment, or a prior deployment as proof of the live value. This page does not authorize toggling flags, launching EPG/resolver/prediction jobs, or editing R2/D1, schedules or Access. Consult the [deployment runbook](../runbooks/deployment.md) and obtain action-specific owner approval.

Once an archive exists, `full` acts as `frozen` and never rebuilds the full ledger |

When that mode is `d1`, they come from `metadata_cache`, and a failed read stops the run before a write. The projector never writes that table. A schema v6 metadata save while the marker is `r2` advances `cache_generation` before the object put and does not write `metadata_cache` rows. |

`PREDICTION_DB_REQUIRED` is not an operational flag. `wrangler.jsonc` sets it to `on` next to the `DB` binding. The deployed Worker then fails a prediction read or write when that binding is missing, and does not fall back to the R2 objects. The local API does not set the variable, so a caller that also omits `DB` stays on the objects. It does not apply migration `0007`, switch `prediction_domain_authority.mode`, or change `D1_ENRICHMENT_WRITE`. Removing the variable from the deploy config is a code change, not a settings toggle ([ADR 0078](../adr/0078-d1-authoritative-prediction-domain.md)).

`RATINGS_PIPELINE` is retired ([ADR 0074](../adr/0074-retire-ratings-pipeline-switch.md)). The Worker ignores the binding. After the storage migration is complete the ratings pipeline is permanently separate. An incomplete migration fails closed: the EPG commit does not read Diary, look up films or enqueue. It keeps each generation's removal references on the sync run until migration is complete. Ratings start and step answer `not_migrated`.

`LETTERBOXD_DIARY_HISTORY` is retired ([ADR 0075](../adr/0075-retire-letterboxd-diary-history-switch.md)). The Worker ignores the binding. A migrated ratings run reads Diary page 1 once whatever the binding holds. `diary.enabled` on `ratings_sync_status` and `enabled` on `GET /api/letterboxd/diary` stay true: that is the capability, not a fetch and not proof the binding is absent. `feature_flags` `effective` is null. A set binding has `issue: retired` and is valid only while absent. Setting it to `off` or deleting it does not stop Diary. After the binding is deleted, code from before this retirement must not be deployed until `LETTERBOXD_DIARY_HISTORY=on` is restored and read back. This code change does not delete the binding (`keep_vars: true`).

`REMOVAL_RATING_LOOKUP` is retired ([ADR 0077](../adr/0077-retire-removal-rating-lookup-switch.md)). The Worker ignores the binding. On a migrated ratings run the removal phase still requests the member page of at most five due films the Diary did not rate. A confirmed stored rating for a film the current Diary page did not list is not requested, including after a new reference reopens the entry. A film that page lists without a rating is still looked up. A null or absent rating is not watched. `removal.lookupEnabled` on `ratings_sync_status` stays true: that is the capability, not a fetch and not proof the binding is absent. `feature_flags` `effective` is null. A set binding has `issue: retired` and is valid only while absent. Setting it to `off` or deleting it does not stop the lookup. After the binding is deleted, code from before this retirement must not be deployed until `REMOVAL_RATING_LOOKUP=on` is restored and read back. This code change does not delete the binding (`keep_vars: true`).

The explicit `off` values in this table describe **effective behavior**, not necessarily accepted textual configuration tokens. For `LIFECYCLE_LOCALIZATION`, write `on:metadata` or `shadow:metadata`, not `on`; a token for `epg`, `programme` or `watchlist` has no effect, and removing one from a binding is a settings change that needs its own owner approval.

### Interactions and operational safeguards

- The scored acceptance gate is the **only** EPG resolver; no variable selects it ([ADR 0036](../adr/0036-scored-resolution-only.md)). The former `SCORED_RESOLUTION` variable is retired: the Worker ignores it whatever value a stale binding carries, so `off` or `shadow` cannot bring the legacy resolver back. Removing a leftover binding is a separate owner-approved settings change; rolling the resolver back is a code revert, never a flag, and reverting code does not undo committed R2 objects.
- Variant discovery is an independent optional gate on that resolver: `CANDIDATE_DISCOVERY=on` adds the bounded variant searches and nothing else needs to be set. Optional searches consume TMDB budget and carry distinct throttling and skip counters; see [candidate discovery](domain/candidate-discovery.md).
- `LIFECYCLE_LOCALIZATION` reaches the metadata sync only: a mode switch changes what the next metadata sync writes into `titles.json`, `people.json` and `metadata.json`, and is not evidence that the sync ran. The EPG commit and the programme/watchlist reads apply the domain localization rule without a switch ([ADR 0037](../adr/0037-domain-localization-only.md)); rolling that back is a code revert, never a flag, and reverting code does not undo titles and names already written at an EPG commit. A binding that still carries the retired path tokens is inert for those paths.
- The owner-triggered ratings-only refresh is retired ([ADR 0040](../adr/0040-retire-ratings-only-refresh.md)). `POST /api/enrichment/ratings/refresh` answers `410 Gone` before it reads the body, the bucket or Letterboxd, so no value of the former `RATINGS_REFRESH` variable opens it. Ratings arrive on the ratings run (Diary page 1 and the per-film lookup); the EPG commit does not read Diary. The stored ratings objects stay readable through `GET /api/enrichment/ratings/status`. Removing a leftover binding is a separate owner-approved settings change; bringing the refresh back is a code change under a new ADR, never a flag. See [ratings reference](integrations/letterboxd-ratings.md).
- Every committed prediction is written as its own immutable version object, with no switch any more ([ADR 0045](../adr/0045-retire-prediction-version-objects-switch.md)). A submit that creates or recalculates a prediction writes `enrichment/films/<id>/predictions/versions/<sha256>.json` before the bundle, as it did with the former `PREDICTION_VERSION_OBJECTS=on`; the former `PREDICTION_VERSION_OBJECTS` variable is retired and inert whatever it holds, so `off` no longer stops the writer. A version-write storage error or byte conflict fails the item with `storage_error` and leaves the bundle unchanged. Objects already written stay in R2 (the Worker never deletes). Stopping the writer is a code revert, never a flag. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `PREDICTION_VERSION_OBJECTS=on` restored, or new submits write unlinked records.
- The one-time historical materialization route `POST /api/enrichment/predictions/materialize` is retired ([ADR 0050](../adr/0050-retire-prediction-materialization-route.md)): it answers `410 Gone` before reading the body, and the former `PREDICTION_MATERIALIZATION` variable is retired and inert whatever it holds. The run it served is complete (28 October 2026); objects, rewritten bundles and receipts stay. Reopening it is a code change under a new ADR, never a flag. See the [prediction versions runbook](../runbooks/prediction-versions.md#2-historical-materialization-completed-the-route-is-retired).
- `POST /api/enrichment/catalog/posters` has no switch any more ([ADR 0048](../adr/0048-permanent-catalog-poster-maintenance-route.md)): it is a permanent owner-only maintenance route behind the Worker's Cloudflare Access, and the former `CATALOG_POSTER_HYDRATION` variable is retired and inert whatever it holds. The dry run stays read-only. Each execution call is a separate, owner-approved production operation that makes bounded TMDB detail requests and writes the `poster` field of catalog records in R2 under the resolver lease, so it competes with discovery for that lease and is refused while a chunk holds it; posters already written stay. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch needs `CATALOG_POSTER_HYDRATION=on` restored before any execution call. The owner page `/admin/posters` adds no variable either: it calls the same route only after the owner confirms one bounded run, and reintroducing a switch for it is a code change under a new ADR, never a flag. See the [poster hydration runbook](../runbooks/catalog-poster-hydration.md) and [ADR 0020](../adr/0020-owner-triggered-catalog-poster-hydration.md).
- Letterboxd facts are the only model for watched, rating and watchlist, with no switch any more ([ADR 0055](../adr/0055-retire-letterboxd-facts-switch.md)). The EPG commit's diary evidence ([Diary-first ADR 0054](../adr/0054-diary-first-epg-ratings.md)), the direct films-list scan, the per-film lookup (and the removal lookup and the repairs that use it), the owner `PUT /api/enrichment/actual-ratings`, the owner watched mark and the completed watchlist sync always write fact records and scan summaries under `letterboxd/facts/` and project `actualRating`, `watched` and `watchlist` into the view index, as they did with the former `LETTERBOXD_FACTS=on`; absence from a list never clears a rating. The former `LETTERBOXD_FACTS` variable is retired and inert whatever it holds, so `off` no longer brings back the legacy writers, and the legacy observation log `enrichment/diagnostics/rating-observations.json` is no longer written (it stays readable history). Objects already written stay. Returning to the legacy writers is a code revert, never a flag. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `LETTERBOXD_FACTS=on` restored before that code is deployed, or the next sync clears ratings by absence.
- The Letterboxd baseline import route (`/api/letterboxd/baseline/validate`, `/commit`, `/rollback`) has no switch any more ([ADR 0053](../adr/0053-permanent-letterboxd-baseline-import-route.md)): it is a permanent owner-only maintenance route behind the Worker's Cloudflare Access, and the former `LETTERBOXD_BASELINE_IMPORT` variable is retired and inert whatever it holds. It needs no other switch either: the routine writers always record facts ([ADR 0055](../adr/0055-retire-letterboxd-facts-switch.md)), so the next sync cannot clear imported ratings by absence. Every production `validate`, `commit` or `rollback` is a separate owner-approved operation; nothing runs by itself. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch needs `LETTERBOXD_BASELINE_IMPORT=on` restored before any import call. See the [baseline import runbook](../runbooks/letterboxd-baseline-import.md).
- The Finds display-only title exclusion has no switch any more ([ADR 0041](../adr/0041-retire-finds-title-exclusion-switch.md)). `GET /api/catalog/available` reads `letterboxd/display-exclusion.json` on every request and applies it, as it did with the former `FINDS_TITLE_EXCLUSION=on`; the former `FINDS_TITLE_EXCLUSION` variable is retired and inert whatever it holds. A missing or invalid list still hides nothing. To show every film, remove or replace the list object (a separate owner-approved R2 operation, [runbook](../runbooks/finds-display-exclusion.md#replace-disable-roll-back)); a code revert restores the switch. Removing the leftover binding is a separate owner-approved settings change.
- The owner's «Смотрел» mark on Finds has no switch of its own any more ([ADR 0042](../adr/0042-retire-finds-watched-mark-switch.md)). The button and `POST /api/catalog/watched` are always available, as they were with the former `FINDS_WATCHED_MARK=on` and `LETTERBOXD_FACTS=on` ([ADR 0055](../adr/0055-retire-letterboxd-facts-switch.md)); the former `FINDS_WATCHED_MARK` variable is retired and inert whatever it holds. Each mark is an owner-fact write to R2 (`letterboxd/facts/`, the link index and the view-index projection) and every other guard of the route is unchanged. To stop new marks, revert the code. Marks already written stay valid facts. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `FINDS_WATCHED_MARK=on` restored.
- The taste-profile compatibility rule has no switch any more ([ADR 0044](../adr/0044-retire-profile-compatibility-switch.md)). Every consumer (view, catalog, Finds, coverage, the queue, the runner steps and diagnostics) uses the selective rule of [ADR-0031](../adr/0031-selective-prediction-profile-compatibility.md), as it did with the former `PREDICTION_PROFILE_COMPATIBILITY=selective`: a prediction stays current only across published, owner-approved change impacts that do not reach it, and an unknown, unapproved or global change fails closed. The former `PREDICTION_PROFILE_COMPATIBILITY` variable is retired and inert whatever it holds; the queue still counts the strict outcome beside the decision. Returning to exact equality is a code revert, which also needs the binding `selective` restored if it was removed; strict would requeue every non-exact prediction. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent.
- The fingerprint transition rule decides fingerprint and prediction freshness for every consumer, with no switch any more ([ADR 0047](../adr/0047-retire-fingerprint-compatibility-switch.md)), as it did with the former `PREDICTION_FINGERPRINT_COMPATIBILITY=selective`; the former `PREDICTION_FINGERPRINT_COMPATIBILITY` variable is retired and inert whatever it holds, so `strict` no longer brings back exact equality. The queue still counts the strict outcome beside the decision; the D1 projection and the benchmark stay strict by contract. Fail-closed outcomes for unknown or unapproved transitions are unchanged. Returning to exact equality is a code revert, never a flag. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `PREDICTION_FINGERPRINT_COMPATIBILITY=selective` restored to keep today's behaviour.
- Every accepted fingerprint is written as its immutable content body and generation record before `fingerprint.json` moves, with no switch any more ([ADR 0046](../adr/0046-retire-fingerprint-version-objects-switch.md)), as it was with the former `FINGERPRINT_VERSION_OBJECTS=on`; the former `FINGERPRINT_VERSION_OBJECTS` variable is retired and inert whatever it holds, so `off` no longer stops the writer. A body or record conflict fails the film with `storage_error` before the pointer or the index moves. Objects already written stay in R2 (the Worker never deletes) and are the only source a pointer restore can use; a film whose fingerprints predate the writer has none. Stopping the writer is a code revert, never a flag. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `FINGERPRINT_VERSION_OBJECTS=on` restored, or new fingerprints get no immutable objects. `PREDICTION_FINGERPRINT_COMPATIBILITY` is a separate, active switch.
- `DISCOVERY_LEDGER_MODE=bounded` changes what the **routine EPG commit writes to R2** on its next run: new archive objects and a smaller active ledger. Once an archive exists, the manual scan and canonicalization routes answer `409`. It is a production writer change that needs its own owner approval ([AIR-222](https://trello.com/c/9Y4G9DG6)) after the offline rehearsal ([AIR-221](https://trello.com/c/9ZiVygrd)). Switching to `frozen` is rollback R1: archiving stops, and nothing is rebuilt or deleted. Removing the value later does not restore the single ledger, because `full` acts as `frozen` while an archive exists.
- `REMOVAL_RATING_LOOKUP` is retired ([ADR 0077](../adr/0077-retire-removal-rating-lookup-switch.md)). The Worker ignores the binding, so `off`, absence or a malformed value does not stop the member-page lookup on a migrated ratings run. That lookup stays bounded: at most five films per step, at most three attempts, and a six-hour pause of the queue after a 403 or 429. A film the Diary already rated, or absent from the current Diary page with a confirmed stored fact, is not requested, including after a new reference reopens the entry. A film that page lists without a rating is still looked up. A null or absent rating is not watched. The EPG commit does not make those requests ([ADR 0074](../adr/0074-retire-ratings-pipeline-switch.md)). The queue object and ratings already written stay. Removing the leftover binding is a separate owner step after this code is deployed; it is not a way to turn the lookup off.
- `LETTERBOXD_DIARY_HISTORY` is retired ([ADR 0075](../adr/0075-retire-letterboxd-diary-history-switch.md)). The Worker ignores the binding, so `off`, absence or a malformed value does not stop Diary page 1 on a migrated ratings run. That page remains the routine source of watched and rating facts, with no facts switch since `LETTERBOXD_FACTS` was retired ([ADR 0055](../adr/0055-retire-letterboxd-facts-switch.md)): every film on that page gets `watched: true` and, where the diary proves it, a rating observed at the watched date. The EPG commit does not read Diary ([ADR 0074](../adr/0074-retire-ratings-pipeline-switch.md)). Stored history stays. Removing the leftover binding is a separate owner step after this code is deployed; it is not a way to turn Diary off.
- `RATINGS_PIPELINE` is retired ([ADR 0074](../adr/0074-retire-ratings-pipeline-switch.md)). The Worker ignores the binding whatever it holds, so removing it or setting it to `inline` does not put Diary back inside the EPG commit. When the storage migration is complete the pipeline is permanently separate: the commit only enqueues removal references, and the ratings run reads Diary page 1 and makes at most five lookups per step. When migration is `none`, `partial` or `regressed`, the commit publishes and fails closed (no Diary, no lookup, no enqueue, no automatic migration) and start and step answer `not_migrated`. The queue's `schemaVersion: 2` and the Diary cursor's merge form still come only from the owner-approved `ratings_storage_migrate` tool. After that migration a code revert is not a rollback of R2. After the leftover binding is deleted, deploying code that treats a missing binding as `inline` also needs `RATINGS_PIPELINE=separate` restored first. The binding deletion is a separate owner step and is not performed by a deploy (`keep_vars: true`).
- These switches are **not** Cloudflare Worker Cron settings, external ChatGPT Scheduled Tasks, secrets, API tokens or `wrangler.jsonc` deployment/binding parameters. `BUCKET`, `TMDB_API_READ_ACCESS_TOKEN`, `LETTERBOXD_USERNAME`, and `EPG_XML_URL` are dependencies/configuration, not feature flags.

## Reading the deployed values

The MCP tool `feature_flags` ([MCP contract](api/mcp.md), [ADR 0039](../adr/0039-allowlisted-feature-flag-readout.md)) returns, in one call, every flag of this page plus the retired `REMOVAL_RATING_LOOKUP`, `LETTERBOXD_DIARY_HISTORY`, `RATINGS_PIPELINE`, `SCORED_RESOLUTION`, `RATINGS_REFRESH`, `FINDS_TITLE_EXCLUSION`, `FINDS_WATCHED_MARK`, `PREDICTION_PROFILE_COMPATIBILITY`, `PREDICTION_VERSION_OBJECTS`, `FINGERPRINT_VERSION_OBJECTS`, `PREDICTION_FINGERPRINT_COMPATIBILITY`, `CATALOG_POSTER_HYDRATION`, `PREDICTION_MATERIALIZATION`, `LETTERBOXD_BASELINE_IMPORT` and `LETTERBOXD_FACTS`, from the bindings of the Worker version that answers. The registry it reads is `src/feature-flags.js`; a test keeps it, the contract table above and the governance checker's flag list in step.

| Field | Meaning |
| --- | --- |
| `state` | `absent` (no binding) or `set` |
| `raw` | The literal value when every comma-separated part, after trimming, is one of the flag's accepted or retired tokens and the value is at most 200 characters; otherwise `null` |
| `redacted`, `shape` | `true` with `{type, length}` (or `{type}` for a non-string) when the value is not made of known tokens. A typo or a pasted secret is never echoed |
| `valid`, `issue` | `valid` is `true` for an absent binding or a value the code accepts as written. `issue` is `case_or_whitespace` (a known token with other case or padding where the code does not trim), `unrecognized`, `not_string`, `unrecognized_tokens` or `retired_tokens` (for `LIFECYCLE_LOCALIZATION`), or `retired` (a `REMOVAL_RATING_LOOKUP`, `LETTERBOXD_DIARY_HISTORY`, `RATINGS_PIPELINE`, `SCORED_RESOLUTION`, `RATINGS_REFRESH`, `FINDS_TITLE_EXCLUSION`, `FINDS_WATCHED_MARK`, `PREDICTION_PROFILE_COMPATIBILITY`, `PREDICTION_VERSION_OBJECTS`, `FINGERPRINT_VERSION_OBJECTS`, `PREDICTION_FINGERPRINT_COMPATIBILITY`, `CATALOG_POSTER_HYDRATION`, `PREDICTION_MATERIALIZATION`, `LETTERBOXD_BASELINE_IMPORT` or `LETTERBOXD_FACTS` binding exists) |
| `effective` | The mode the code uses, computed by the consumer's own function; `null` for a retired flag |
| `requires`, `effectiveWithRequirements`, `unmetRequirements` | For a flag whose route also needs another flag; no registered flag has one at present |
| `registryVersion`, `readAt`, `summary` | Registry version, read time, and counts of registered, set, absent, invalid and redacted flags |

The tool reads no other binding, no storage and no Cloudflare API. It does not say who set a value or when, and for `DISCOVERY_LEDGER_MODE` it does not see whether an archive makes `full` act as `frozen`. A read through it is a verified read for the ledger below; it authorizes no change.
