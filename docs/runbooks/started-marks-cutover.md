# Started marks: R2 to D1 cutover

Procedure for moving the Started marks (the owner's «Начал просмотр» state) from the R2 objects `started/<id>.json` to D1 (schema v29). **Every production step below needs its own operation-specific owner GO**, and code delivery is not activation. The procedure was executed on 20 Nov 2026: [production evidence](../evidence/d1-migration/air-549-started-marks-cutover-2026-11-20.md). The event journal `events/items/` is not part of this procedure: it stays R2-authoritative, no event is copied and no event is created by the import.

## What is safe before any GO

The code is dormant. With the v29 tables absent **and `schema_contract` answering a version below 29**, or with the marker in `mode r2` and writes `open`, the routes serve R2 exactly as before; the only added cost is a few small D1 reads per request. A D1 error on those reads, a missing `DB` binding, a database without `schema_contract`, version 29 without the tables or a half-installed set of tables answers `503` for `GET`/`POST /api/started` and `POST /api/events/bootstrap` only and never reaches R2 (the explicit local stand-in `STARTED_DB_OPTIONAL=standin` exists for tests and is never set in production). Limit: a binding that points at a different database that is itself below version 29 is indistinguishable from the true pre-migration state; the preflight therefore reads the database id. The routes never read or write D1 mark rows while the marker is `r2`.

## The in-flight writer problem and the fence

An R2 mark write is an unconditional `put`: it has no compare-and-swap, and a request admitted before the hold can still be suspended and land after the export. The marker hold alone is therefore **not** the fence. The code narrows the window (the R2 branch reads the marker again right before its `put` and answers `503` when writes are held or the marker moved), and the procedure closes it by observation, not by assumption: after the hold, wait out the longest request the route can have, then take a **bound snapshot** of `started/` that ties every downloaded byte to a listed version (two equal listings alone are two observations, not a snapshot): (1) an opening complete paged listing with each object's **strong, non-empty ETag** and `customMetadata`; (2) for every listed key a **conditional GET** (`If-Match` the listed ETag, `Accept-Encoding: identity`) whose response ETag equals the listed one and whose bytes are saved raw; a `412` or a different ETag means a write landed, so repeat from the drain; (3) a closing complete listing taken after the last body, identical to the opening one (keys, ETags, metadata). The export used for the import is exactly those bodies with those ETags. The existing fenced exporter ([R2 snapshot export](r2-snapshot-export.md): opening listing, conditional reads of the listed version, closing listing, fence, `consistent_fenced` manifest) performs the same proof for the whole bucket and may be used instead of a hand-made export; either way the evidence records the opening and closing inventory digests and the `etagsSha256` of the export. A missing, empty or weak ETag in the export is a blocker of the generator.

## Preconditions (read-only, each recorded in the evidence)

1. The deployed Worker contains `src/started-d1.js` (the bundle names it `StartedD1`); `Deploy to Cloudflare` succeeded for the exact commit.
2. The Worker's `DB` binding resolves to D1 `iptv` (id as in `wrangler.jsonc`), and D1 `iptv` reports `schema_contract.version = 28` and none of the three `started_*` tables; or, after step 1 below, version 29 with the marker `r2`, generation 0, writes `open`, and `SELECT COUNT(*) FROM started_mark` equal to 0. Filter presets stay at `d1`/1 and are not touched.
3. A fresh, complete, paged read of the prefix `started/` of the R2 object store through the approved read-only export ([R2 snapshot export](r2-snapshot-export.md)) bound to the listed versions as described above: every object key, strong ETag, `customMetadata` and raw body, tombstones (`started:false`) and legacy objects without `lastEvent` included. Save it as `started-export.json` in the shape the generator documents (`[{key, etag, customMetadata, body}]`). An empty prefix is a valid state only if the listing proves it; an unreadable, partial or truncated listing is a **blocker**, never a reason to import fewer marks.
4. `node scripts/started-d1-sql.mjs digest started-export.json` prints `{count, started, sha256, etagsSha256}` and exits 0. Exit 2 is a blocker (a key outside `started/<id>.json`, a body that is not a JSON object, a body id that differs from the key, a `started` state on which the list read (`customMetadata.started` is anything but `'false'`) and the write read (`body.started !== false`) disagree (this includes `started:false` with an absent flag, which the live `GET` lists as started and the live `POST` treats as unstarted), an object without a strong ETag, a malformed `startedAt` or `lastEvent`, a duplicate key): fix the source by a separate owner decision, do not edit the export by hand.
5. Record the current number of events in the journal only as a count; the import must not change it.

## Steps

Apply SQL with the approved D1 execution path; every file is guarded so that a wrong state aborts it before it changes anything.

1. **Apply `migrations/0029_started_authority.sql`.** It refuses anything but a complete version 28. Readback: version 29; marker `r2`, generation 0, writes `open`; three tables; zero rows. The code and R2 continue to serve; nothing else changes.
2. **Hold mark writes.** `node scripts/started-d1-sql.mjs hold` prints one guarded update (`writes='held'` only from `r2`/`open`/generation 0). From now on every request that starts afterwards answers `503` ("temporarily read-only") on `POST /api/started`, replays included; reads still come from R2. Confirm the refusal with one owner-approved write attempt or by the Worker log, not with a test mutation.
2b. **Drain and prove.** Wait at least the longest request the route can have (the Worker wall-time limit, recorded in the evidence) so any write admitted before the hold has finished or been refused by the marker re-read. Then take the bound snapshot of precondition 3 (opening listing, conditional GET of every listed version, closing listing identical to the opening one). `started-export.json` is exactly those bodies and ETags; its `digest` is the source. If a conditional GET fails or the listings differ, repeat; run `release` if it cannot be completed.
3. **Import.** `node scripts/started-d1-sql.mjs import started-export.json > import.sql`, review it (one guarded update to generation 1, the fence, then one `INSERT` per object in R2 key order, revision 1), apply it. The file is guarded: it changes nothing unless the marker is `r2`, writes `held`, generation 0 and the table is empty, so a repeat, a retry after a crash or a double apply is refused by its own guard and never duplicates a row. The marker stays `r2`: D1 does not serve yet. Tombstones, `startedAt: null`, legacy objects without an event and every spelling of an id are written as they are.
4. **Parity readback (read-only).** Compare `SELECT id,started,started_at,last_event_json,rev FROM started_mark ORDER BY id` with the export: same count, same `started` count, every field equal, `rev` 1, the `lastEvent` ids unchanged. Marker: `r2`, generation 1, writes `held`. The journal count is unchanged.
5. **Activate.** `node scripts/started-d1-sql.mjs activate started-export.json > activate.sql`, apply it. The file has one short statement per mark that aborts the file when that row differs from the export, then one short guarded update that switches `mode` to `d1` and `writes` to `open` only at generation 1 with the expected total and started counts, then the fence. A mismatch stops the file before the switch. Readback: marker `d1`, generation 1, writes `open`; `GET /api/started` through the Access-protected read (the [Access read skill](../../.claude/skills/cloudflare-access-read/SKILL.md)) returns exactly the started ids of the export in the order of the R2 listing.
6. **Diagram.** The activation evidence delivery adds the Worker to D1 Started marks arrow to the persistence graph in `docs/architecture/persistence-and-migration.md` (with GitHub-rendered Mermaid QA); until then no diagram names this domain, because the code is dormant and no authority has moved.
7. **Acceptance.** One «Начал просмотр» set and one unset from the owner UI are confirmed in the rows (revision rises by one per write, `lastEvent` stored, `startedAt` set then null), a repeat of the same click returns the same event (no second journal object), the started filter and the Events screen show the same marks, and `POST /api/events/bootstrap` is not run. Record all readbacks in a dated evidence report. The R2 `started/` objects are neither deleted nor changed by this procedure; decommissioning them is a separate GO.

## Recovery and rollback limits

- **Before step 5 (activation):** `node scripts/started-d1-sql.mjs release` restores writes (`open`) while the marker is `r2` (generation 0 or 1). R2 was never changed, so nothing is lost. Imported rows may stay (a later import is refused by its guard) or be removed by the owner's explicit decision (marker back to generation 0 and `DELETE FROM started_mark`, a new GO).
- **A failed or partial apply of step 3:** the guard stops the file before any row; a file that stopped after some rows leaves the marker at generation 1 with a partial table. Do not activate (the parity statements refuse it): compare with the export, and either complete the missing rows under a new GO or reset the table under a new GO, then repeat step 3.
- **After activation:** D1 is the only authority and the R2 objects are stale from that moment. A code revert does **not** move data and does not restore R2 as the authority; the route keeps reading the marker. Returning to R2 is a separate fenced, owner-approved procedure (hold, export the D1 rows, write the objects, set the marker back to `r2`); marks written in D1 after activation exist only in D1 until then.
- **Event delivery** needs no recovery step of its own. A request that committed a mark and died before writing the event is repaired by the next request for that id, whichever state it asks for: a same-state request writes the stored event under its own id, and an opposite transition first writes the stored event (an idempotent write under its key) and commits only if that write succeeded, so an event is never replaced before it reached the journal.
