## Collaboration and delivery

- ChatGPT coordinates, reviews and may directly author *approved documentation-only* work; Cursor normally implements code tasks. The exact card and owner agreement determine who authors a change. Work on diagrams may require a PR and **owner visual review** even if it is documentation-only.
- Follow the **actual Trello card scope** and native prerequisite checklist. **Before creating a `Prerequisites` checklist, inspect and reuse any existing prerequisites checklist** (including differently named equivalents); never create a duplicate checklist or duplicate items. **Each prerequisite item is exactly one bare Trello card URL** (`https://trello.com/c/...`), with no Markdown `[AIR-N](url)`, AIR-ID prefix, label or extra prose, so Trello shows the live card title and status. See [Trello conventions](docs/process/trello-card-conventions.md). Keep cards atomic; separate offline implementation, tests, shadow, production cutover and stabilization. Do not pick a next task merely from a remembered AIR number.
- Trello cards/comments and messages to Cursor are **Russian**; GitHub PR/reviews, repository docs and technical code discussions **English**. Preserve code identifiers.
- No direct commit to `main` without explicit owner approval for that delivery. Normally use a branch and PR. **Approval of a card and its ordinary PR delivery includes permission for ChatGPT to merge** after a positive independent review, green CI for the reviewed head, and resolution of blocking findings; do not request another per-PR merge approval. Recheck the actual head/base and exceptions in the [workflow](docs/process/agent-workflow.md). An explicit owner pre-merge gate, including rendered Mermaid visual approval, still must be satisfied.
- Before changing a local checkout, run `git fetch origin main` and inspect remotes, HEAD, branch, tracked/untracked changes, and divergence from `origin/main`. Preserve other work; no force push, destructive reset or silent overwrite. When working solely through GitHub APIs, read current `main` and use expected-head checks on ref updates.
- Validate changes with `npm ci`, `npm test`, `npm run build` when running locally, then check GitHub Actions. A PR run tests/build only; after merge or owner-approved direct main commit, confirm **both** `Test and build` and `Deploy to Cloudflare` reached success before marking Done. Report exact commit, PR, evidence and limitations in Trello.
- [Documentation routing and acceptance](docs/process/documentation-governance.md) is mandatory for every technical task. Each card, implementation handoff and review must state affected documentation paths, or `Documentation impact: none` with a concrete reason. Missing required documentation blocks acceptance.
- Documentation is part of Definition of Done. Changes to runtime topology, persistent data flow, security/trust boundaries, integrations, deployment or operations must update the affected [architecture diagrams](docs/architecture/README.md), [reference](docs/reference/README.md) and [runbooks](docs/runbooks/README.md) in the same PR. Record material durable decisions as [new ADRs](docs/adr/README.md); supersede rather than silently rewrite accepted decisions. Dated test results belong in [evidence](docs/evidence/README.md). Check whether this guide, `CONTRIBUTING.md` and root `README.md` also need changes.
- For UI work, follow [Visual QA](docs/process/agent-workflow.md): check a local browser at desktop and mobile widths and put a short written report in the PR. Do not create, save, download, attach, or commit screenshots. For Mermaid work, syntax or CI alone is not visual QA: inspect actual GitHub rendering, legibility and arrow semantics.

## Ways of work with the owner

- Address the owner informally in Russian («ты», never «вы»/«ваш»). Chat with the owner and Trello comments are Russian; GitHub PRs, review replies, commit messages and repository docs are English.
- Times in chat with the owner and in Trello comments are Europe/Madrid (state the zone, e.g. «09:52 Madrid»), with UTC added in parentheses only where it matters for logs, CI runs or snapshot identities. Repository docs and evidence stay in UTC. Schedule windows (Scheduled Tasks, quiet windows) are reasoned about in Madrid time as well, DST included.
- Roles: the agent is the developer; ChatGPT is the project manager and reviewer and alone moves or closes Trello cards. The agent posts only handoff-to-review and fix-note comments on the card, never "Done" evidence comments.
- Independent review is mandatory: open a PR, answer every inline comment on its thread, and mark each answered or fixed thread **Resolved** before requesting re-review. ChatGPT merges already approved routine PR deliveries once the review and CI gates are green; the owner decides exceptional pre-merge gates and scope changes, not each ordinary merge.
- An agent that can follow PR activity subscribes to every PR it opens as soon as it opens it, without asking, and watches it until merge or close (review comments, CI, conflicts).
- Approval is action-specific for **non-routine operations**: a direct commit to `main`, production writer call, flag, Access, Scheduled Task, migration or cutover change each needs separate explicit owner authorization. Routine PR merge of already approved work is covered by the card's approved delivery path; it never authorizes these operations.
- Report outcomes plainly with commit, PR, CI run and test evidence; say what was skipped or could not be verified rather than rounding up.

## Production and security boundaries

- GitHub `main` is authoritative code. Production runs on Cloudflare Worker `iptv` with authoritative R2 bucket `iptv`; the historical ChatGPT Site is **reserve**, not a parallel writer. D1 schema/repositories and offline imports are not evidence of a live D1 cutover. See [deployment](docs/runbooks/deployment.md), [persistence diagram](docs/architecture/persistence-and-migration.md).
- `/mcp` uses owner-only `IPTV MCP` Cloudflare Access with Managed OAuth **and** signed JWT checks in the Worker (issuer, audience, expiry and identity). The broader Worker is also Access-protected. Never weaken Access, add bypasses, expose credentials or allow arbitrary MCP URL/R2 keys/routes. See [MCP reference](docs/reference/api/mcp.md).
- External ChatGPT Scheduled Tasks are **not** Worker Cron. Deployment does not trigger EPG, discovery, TMDB, predictions, ratings refresh, scheduled Tasks or R2 migration. Verify present task/flag/run state from authorized live sources; never infer from historical docs.
- No production sync, prediction/model run, ratings refresh, discovery, lease reset, destructive cleanup, flag/schedule change, storage import, R2/D1 backfill or authority cutover without **separate action-specific owner approval**. A code deploy is not approval for live data writes.
- The discovery pipeline executes **one chunk per explicit request**; internal `DiscoveryContinuation` is not a public API, independent Worker or self-fetch with forwarded cookies/tokens. Some GET endpoints may perform recovery writes; consult [side-effect tests](tests/get-side-effects.mjs) and [runbook](docs/runbooks/deployment.md) before treating a production read as safe.
- Code rollback does **not** restore R2, Cloudflare Access configuration, secrets, or external Task schedules. Do not republish, browse or operate the legacy Site without separate approval; preserve confidential production payloads outside public docs, fixtures, GitHub and logs.
