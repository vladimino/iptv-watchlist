# Film and Person — domain lifecycle contract

**Role:** active technical reference for the **implemented, storage-neutral contract**, not a claim that Film/Person entities have replaced production R2 records. Verified against `src/domain/film-person.js`, `src/domain/film-person-reader.js`, `src/domain/film-person-backfill.js`, and the current Worker/sources on **2026-10-24**. GitHub main and authorized runtime diagnostics are still required for current implementation/flag claims.

## Where the model runs (do not confuse with source of truth)

`DOMAIN_CONTRACT_VERSION=1` describes pure lifecycle projections and guarded transitions. `film-person.js` has no HTTP/R2 effects and is not the deployed authoritative Film/Person storage adapter. `film-person-reader.js` constructs views from records already loaded by a caller; `film-person-backfill.js` computes desired lifecycle sidecars and a **dry-run** reconciliation; it does not write production storage. Diagnostics and offline parity are views/measurements, not cutover evidence. Since [ADR 0056](../../adr/0056-d1-enrichment-write-through.md), the Worker bundle carries the reader in its own scope for the D1 enrichment projector only. The projector calls it with `entitiesOnly`, which returns the Films and People without sidecars or legacy parity. The reader's per-object lookup indexes return what its linear scans returned.

The foundation of a future canonical D1 authority is in the repository and **inactive**: migration `0013`, the marker reader and the fenced mutation API ([schema reference](../data/d1-schema.md#canonical-filmperson-authority-schema-v13), [ADR 0099](../../adr/0099-canonical-film-person-d1-authority.md)). It is not applied in production and is not bundled into the Worker; the enrichment projector remains the only writer of Film and Person, and R2 remains the source it reads.

The baseline tooling is prepared the same way, **inactive** ([AIR-373](https://trello.com/c/ugu3sQmp), [runbook](../../runbooks/film-person-baseline.md), `src/film-person-baseline.js`): a parity ledger of D1 against the state derived from R2 (per-class counts, order-independent digests, differences classified missing, extra and differs, by key only, explained only by an explicit rule or an owner exception), a keyset D1 reader with a consistent-read check, a bounded delta plan, an importer driver that applies a unit only through an injected writer (the projector's repository under its lease in production) with a write-ahead checkpoint, resume and readback of unknown outcomes, and a baseline gate whose recorder moves `film_person_baseline` to verified in one fenced batch and never moves the marker. Through `r2` and `prepared` the projector stays the only canonical writer; the production baseline and the `r2` to `prepared` move are separate owner decisions.

AIR-373 stage B adds the narrow projector-input capture, also **inactive** and not bundled (`scripts/film-person-capture.mjs`, [runbook](../../runbooks/film-person-baseline.md#stage-b-the-narrow-projector-input-capture-offline-code-nothing-executed)): a one-constant allowlist of the keys the projector itself reads, a versioned manifest with ETags before and after, and a measurement report that never records a baseline. It changes no table, contract or runtime path.

AIR-374 H0 adds the offline operator preflight kit for migration 0019 (`scripts/film-person-0019-preflight.mjs`, [procedure](../../runbooks/film-person-0019-apply.md#4a-the-offline-tool-identity-emitted-statements-verification-of-pasted-results)): it recomputes the file identity, emits the read-only preflight and readback statements and judges pasted results; the GO-specific verification fails closed without the exact accepted baseline reference (and, for the readback, the preflight results bundle, against which the projector lease, window, Discovery lease and baseline reference are compared). It is not bundled, applies nothing and authorizes nothing.

The baseline also has a separately named, versioned `cutover_minimum` gate, **inactive** ([AIR-373](https://trello.com/c/ugu3sQmp), `src/film-person-cutover-minimum.js`, [runbook](../../runbooks/film-person-baseline.md#the-cutover_minimum-gate-offline-code-nothing-executed)): `cutoverMinimumGate(ledger)` returns `{pass, accepted, notProved, reasons}`, checks the 15 classes other than `ownerLink` fully, excludes only the `ownerLink` values `identity_link` / `identity_state` (owner-review keys, count and facts stay mandatory), accepts exactly one waiver (`OWNER_LINK_WAIVER`, `ownerLink` / `link_values`, the AIR-373 owner decision of 2026-11-10, pinned in code) and never bypasses `source_unverified`. The strict `baselineGate` is unchanged and the default path of `recordBaselineVerified` still refuses such a ledger; a baseline is recorded only by a separate owner-approved production step.

`recordBaselineVerified(env, {ledger, expectedGeneration, at, path})` has three explicit recording paths, chosen by the caller and never by the ledger ([runbook](../../runbooks/film-person-baseline.md#recording-paths-and-the-measuring-run-offline-code-nothing-executed)). With `path` omitted or `RECORDING_PATHS.strict` it consults only `baselineGate` and stores the bare ledger digest, as before. With `path` deeply equal to `RECORDING_PATHS.cutover_minimum` (`{gate:'cutover_minimum', version:1}`) it consults only `cutoverMinimumGate`, requires the ledger to have been measured with the marker `r2` at `expectedGeneration`, and stores `cutover_minimum/v1:<cutoverDigest>`. There is no fallback between the paths, an unrecognized `path` is `baseline_path_invalid`, no waiver other than `OWNER_LINK_WAIVER` passes, a `source_unverified` ledger is recorded on neither path, a replay writes nothing, a different ledger over a verified baseline is refused, and the marker is never moved. `film_person_baseline` has only `state` and `reference` (migration `0013`, no new migration), so the gate and its version are carried in the reference text and in the digest it names. `scripts/film-person-cutover-run.mjs` (`runCutoverMinimum`, **inactive**, no CLI) is the one measuring operation that can produce such a ledger: the narrow capture plus the stage A cut with the lease row as its only write. Its `source.verified` is derived, not passed: every check of the run's own evidence must hold (otherwise no ledger is built) and the transports must be the ones `openProductionSource` registered for the production endpoints, so a synthetic or rehearsal run is always `verified:false`. That is provenance by construction, not authentication of a ledger, and the production path has never been executed.

**Production status (11 Nov 2026, UTC):** the baseline was recorded as `verified` on this third path and the `film_person_authority` marker moved `r2` to `prepared` at generation 1 ([evidence](../../evidence/d1-migration/air-373-baseline-prepared-2026-11-11.md)). Behaviour is unchanged: the projector is the only writer and R2 the authority; the reader and producer code below stays inactive until the marker is `open`.

A third recording path, `RECORDING_PATHS.cutover_accepted` (`{gate:'cutover_accepted', version:2}`, [ADR 0110](../../adr/0110-film-person-operator-copy-and-accepted-discrepancies.md), [runbook](../../runbooks/film-person-baseline.md#connector-path-offline-code-nothing-executed)), consults only `cutoverAcceptedGate` (`src/film-person-cutover-accepted.js`, **inactive**) and stores `cutover_accepted/v2:<acceptedDigest>`. That gate is `cutover_minimum` v1 with two differences, each a constant a ledger must carry deeply equal. `ACCEPTED_DISCREPANCIES` v2 (version 1 of 10 Nov 2026 is superseded and no longer accepted; the caps are the 11 Nov 2026 measurement, total 1,605, [amendment](../../adr/0110-film-person-operator-copy-and-accepted-discrepancies.md#amendment-2026-11-11); owner decision of 10 Nov 2026, "ignore the discrepancies and prepare the migration") together with the owner decision "exact measured numbers" ([PR #501](https://github.com/vladimino/iptv-watchlist/pull/501#issuecomment-6780196358)) accepts unexplained missing or extra rows up to a per-class cap that is exactly the count measured on 11 Nov 2026 (1,605 in total, no headroom); a differing value, a class above its measured count or an unlisted class fails, and a higher count needs a fresh owner approval. `OPERATOR_COPY_PERMISSION` v1 (owner decision of the same day, "no token is needed, use the same path as before the pause") lets a source of kind `operator-copy` be `verified`, and only by derivation from the evidence files of the run: production equal at three reads except the Discovery statements, the copy equal to production at the second read, the Discovery tables resynchronised at one generation, the production projector lease held by the run at all three reads and released, unchanged R2 ETags, a complete probe and a consistent read. The statements that must be present at every read and in the copy comparison are fixed by `requiredStatementIds()` (every witness and gate statement and one row count per table of `COPY_TABLES`), not by the evidence. That verdict is operator attestation, not cryptographic proof. ADR 0110 is **Accepted** following the [owner decision](https://github.com/vladimino/iptv-watchlist/pull/501#issuecomment-6780196358) and [successful independent re-review](https://github.com/vladimino/iptv-watchlist/pull/501#pullrequestreview-5850223602). Baseline recording nevertheless requires a separate operation-specific owner GO. `scripts/film-person-connector-run.mjs` (**inactive**, not bundled) is the tool of that path: it never calls the connector, reads D1 only from the operator's local copy, runs the merged `captureProjectorInputs` and `runParity` unmodified, and renders the SQL the recorder and `transitionAuthority` would execute without executing it. At `prepared` the projector stays the only canonical writer and R2 the authority, so the accepted differences (most of them the empty `film_rated_admission`, `film_retention` and `tmdb_retirement_decision` tables) change nothing there; they remain open gaps for the `d1` activation.

Automatic localization sources and the precedence contract are prepared the same way, **inactive** ([AIR-368](https://trello.com/c/RxZ3aOQB), [schema reference](../data/d1-schema.md#automatic-localization-sources-schema-v14)): automatic title and name candidates with provenance are stored apart from the effective dimension, and the effective value is resolved as owner > reviewed dictionary > automatic. `owner_review_entry` stays authoritative in the owner-review domain, a late `metadataSync`, projector or automatic localization never replaces an owner or reviewed value, and no writer, route or consumer uses it before the owner-approved handoff (AIR-371) and the read model (AIR-372).

The canonical bulk read model is prepared the same way, **inactive** ([AIR-372](https://trello.com/c/weKsBJdQ), `src/canonical-read-model.js`): `canonicalReaderMode` gates a future reader on the marker (legacy, `r2` and `prepared` keep the existing runtime; `open` reads D1; `held` and unreadable states fail closed and never name R2), and `readFilms` / `readPersons` answer an id set in a fixed number of queries per chunk of 80 ids (at most 200 ids per call) with typed external ids, redirect resolution with cycle and depth guards, role-specific Person records, credits with role and ordinal, a bounded filmography, the owner > reviewed dictionary > automatic title and name of [AIR-368](https://trello.com/c/RxZ3aOQB) (the owner value read from `owner_review_entry`, redirect-aware: a verified owner link on any id of the redirect chain that ends at the Film counts, because a Film merge does not rewrite the owner-review store, and an ambiguous or too deep chain fails closed with `canonical_read_owner_redirect`, and the number of retired ids collected per read call is capped at 300 (`CANONICAL_OWNER_ANCESTOR_CAP`, next to the 200-id and 500-credit caps; one row more than the cap is the most that is ever read, and exceeding it fails closed with `canonical_read_owner_fanin`, never a partial result or a lower-tier fallback); two source keys that link one Film with different owner titles give the explicit outcome `owner_conflict` with `ownerConflict` listing the candidates, never a value picked by row order and never a lower tier in its place), and a refusal when the marker generation moved during the read. Person grouping stays derived (ADR 0058/0059/0062). It is read-only, not bundled and not wired into any route: `GET /api/d1/*`, Finds, the Admin, the film page and the programme/watchlist overlays are unchanged until a later owner-approved cutover.

The second reader slice (AIR-374 P4b) moves the `titles.json` consumers `GET /api/programme` and `GET /api/watchlist` behind the same gate: at `open` `catalogTitlesFromD1` returns, for the Films of the two documents, the `titles.json`-shaped rows `{title, tmdbId, status:'provisional', sources}` from bounded SELECTs of at most 1500 ids each (provisional localization dimension, trusted non-conflicting `tmdb` claim typed like the document's, the Film's own id spelling before its `tmdb_<n>` spelling); `programme.json` and `watchlist.json` are independent EPG mirrors and stay as they are. `CANONICAL_READER_REGISTRY` lists every remaining reader or writer of a former mutable mirror as `{name, file, class:'freeze'|'exception', moved}`; a `test` fails when a source file names a mirror and is in neither the registry nor the documented non-readers.

The first Film/Person reader slice is **dormant at `prepared`** ([AIR-374](https://trello.com/c/ha7ais3w) P4, `src/canonical-catalog-reader.js`, the one canonical read module the Worker bundles; `canonical-read-model.js` now re-exports its gate as `canonicalReaderMode`, and `film-admission.js` re-exports `readAdmissions` / `loadAdmissionRows` from it): `catalogReaderGate` keeps the existing runtime for `legacy`, `r2` and `prepared`, reads D1 at `open`, and refuses `held` and every unreadable marker; the `/api/d1/*` views and the catalog film route's rated-archive fallback use it. At `open` the fallback reads `film_rated_admission`, the identity claims, `film_redirect` and the retirement ledger from D1 and never the frozen R2 receipt (owner decision 4). Responses before `open` are byte-identical to today's. The remaining R2 readers of the canonical mirrors are listed in the [P4 evidence](../../evidence/d1-migration/air-374-p4-readers-offline-2026-11-11.md); nothing here moves the marker.

The admission side is prepared the same way, **inactive** ([AIR-369](https://trello.com/c/GlAKWxvw), [schema reference](../data/d1-schema.md#verified-rated-admission-and-retention-schema-v15)): a verified rated-only Film (one entry of `letterboxd/admissions/verified-films.json`, ADR 0087) and the watchlist retention fact (ADR 0086) get D1 rows and fenced writers. Only an entry with every verification fact becomes a Film; a candidate, a short code, a `tmdb_tv` id or an entry with a `watchlist` field never does, a Film that already holds the movie id as a trusted `tmdb` id stays one Film, a movie id with an untrusted or conflicting claim is held (`admission_identity_held`) and never promoted, and a Film that left the watchlist persists on its retention fact. The R2 object stays the immutable receipt, the pre-Film queue stays with AIR-343, and nothing writes these rows before the owner-approved handoff.
The fenced writers can apply a durable write receipt inside their own batch through an optional `receiptMark` (AIR-374 P3-0a; see [D1 schema](../data/d1-schema.md)); the applied update is verified inside the batch against the stored receipt row (request id, pending state, attempt, target, planned revision and marker generation); nothing passes one yet.

The producer side of that receipt is the dormant adapter `src/canonical-producer-adapters.js` (AIR-374 P3-0b, [ADR 0123](../../adr/0123-producer-receipt-adapter-film-facts.md)): operation kind `film_facts`, a no-op skipped before any receipt, request ids from the source event, target and content digest, and an own-origin bounded inline reconcile; nothing calls it and it is not bundled.

Producer adapters and the single-writer routing are prepared the same way, **inactive** ([AIR-371](https://trello.com/c/gt1afd0C), `src/canonical-producers.js`): `writerRoute` decides from the marker which one of the projector (legacy, `r2`, `prepared`) and the fenced adapters (`open`) may write, held and unreadable markers fail closed; `projectorFence(gate)` is the SQL assertion a future projector batch adds; `planEpgIdentity`, `planDiscoveryAdmission`, `planRatedAdmission`, `planRetention`, `planRetirement` and `planLocalization` are pure planners onto the AIR-367..370 fenced calls (credits are upserts only, `tmdb` and `tmdb_tv` stay distinct, only verified admissions, automatic localization only); `dispatch` runs a plan only when the route is canonical, reports an unknown batch outcome instead of retrying and reports a partial multi-call plan (`partial`, `complete`; the EPG plan runs Persons first, then the Film, and is not one atomic batch); `readback` never calls a call applied from the entity revision alone (a competing producer moves it): it answers `not_applied`, `settle_by_request_id` (the writers that dedupe by request id), `content_present` (only when D1 holds EXACTLY the state the call would have left: the row fields it sets, each external id with trust, conflict flag and provenance, each removal, alias and credit), `reread_and_replan` (anything else; re-read with `readRevisions`) or `unsupported`, and a re-planned `mutateFilm`/`mutatePerson` replay goes through the revision check and keeps existing aliases and credits, so it converges without a duplicate (it is not blind: an id row is re-written with the call's trust and provenance, so a conflicting decision on that id is the caller's to resolve); `shadowCompare` (at most 200 Films per call) and `handoffReadiness` are read-only. Producer writes that no fenced mutation covers yet are listed in `GAPS` and keep the readiness false: `film_metadata`, `film_dimension`, `film_sync_state`, `watchlist_film` membership, `person_dimension`, `localization_conflict` outside a merge, the overwrite of `canonical_identity`/`original_title` and the projector's revision bumps. Nothing calls the module before AIR-374.

The film-side producer writes are prepared the same way, **dormant** ([AIR-374](https://trello.com/c/ha7ais3w) P2a, [ADR 0120](../../adr/0120-canonical-film-writers-identity-metadata-membership.md), `src/canonical-film-writers.js`): `writeFilmFacts` is ONE fenced batch per Film (marker generation, Film revision and no-redirect proven in the batch, revision bumped) for the overwrite of `canonical_identity`/`original_title`, `film_metadata` (set, field-wise merge, clear), `film_sync_state` (set, release), `watchlist_film` membership (set, clear) and the `film_dimension` identity, metadata and effective localization rows; automatic localization sources are written together with the resolved effective row so `catalog-d1` never sees a source without it. `planFilmFacts(snapshot,input)` is pure and gives the projector's rows for the same inputs (checked on shared fixtures; the P6 harness runs both). Rules ([ADR 0120](../../adr/0120-canonical-film-writers-identity-metadata-membership.md); accepted: the title order and the sync rule; the others still draft): `original_title` (only) follows `owner > dictionary > tmdb > letterboxd > watchlist > epg > discovery`, the source of the stored title is the key `titleSource` = `{"source","at"}` inside `film_dimension.identity.provenance_json` (other keys preserved, `identity.source` untouched, a row without it is unranked); a missing or null sync clock keeps the stored one and clearing is `sync.clear` or `sync: null`; a blank never overwrites; reviewed and owner rows are never replaced by an automatic write; `canonical_identity` needs a trusted `tmdb` id and, to change, verified evidence. The differences from the projector are the machine-readable `P6_DIFFERENTIAL_EXCEPTIONS` for the P6 harness. Idempotency is by stable `requestId` plus content: a call whose rows are already stored opens no batch, an unknown outcome is settled by `readback` (`content_present`/`not_applied`); replay by content is not a durable receipt: receipts stay a prerequisite before producer wiring (ADR 0119, PR #530) and this change authorizes no migration and no live writer. It writes no external id, alias, credit, person, fingerprint or prediction, is not bundled, and the producer entry `planFilmWrite` changes no routing: at `prepared` the projector stays the only writer. `GAPS` is unchanged.

The Person-side canonical state writers are prepared the same way, **dormant** ([AIR-374](https://trello.com/c/ha7ais3w) P2b, `src/canonical-person-state.js`, accepted owner decisions 1 and 5 of [ADR 0117](../../adr/0117-film-person-d1-handoff-owner-decisions.md)). `recordPersonState` writes, in ONE fenced batch (marker `d1`/`open` at the read generation plus the Person revision, one revision bump), the `person_dimension` rows (identity and the effective localization) and what the projector's `noteHeldLocalization` does for a Person: the alias and the `localization_conflict` row of a held incoming value. `recordLocalizationConflicts` writes the `localization_conflict` rows of one Film or Person outside a merge; ids are the projector's content ids, so a repeat is a no-op, and nothing here deletes a conflict (the projector clears a Film's conflicts only when it retires the Film, which is the fenced `mergeFilms`). Neither writer touches the person row, `person_external_id`, credits, other aliases or any Film (`mutatePerson` owns identity). An owner or reviewed localization is never downgraded: `guardReviewed` (the projector's rule, now a pure export) keeps the stored value and records the incoming one as an alias and a conflict (`owner_kept` or `reviewed_kept`), and the SQL upsert repeats the guard inside the batch, so an owner review that lands between the snapshot and the batch still wins. The pure planners (`planPersonState`, `planConflicts`) return the same statements and final rows the projector's `writePerson` produces for the same stored state and input (proved on shared fixtures offline), so a differential harness can run both on one fixture. Idempotency follows owner decision 5 without a new table: `requestId` is a required stable key that is validated and returned, a replay is recognised by CONTENT (the rows already equal the wanted state: `already: true`, no batch, no revision bump), a stale writer fails the revision check, and an unknown batch outcome is settled by `readback` (`settle_by_replay`) and a replay. A durable receipt per request id would need its own table in a later schema and an owner GO; this change adds no migration. Before `open` both writers refuse before any statement and the producer routing module dispatches nothing, so the projector stays the only canonical writer. Their `GAPS` entries stay until the computed readiness of the differential harness (P6).

The handoff readiness is **computed**, still read-only and dormant ([AIR-374](https://trello.com/c/ha7ais3w) P6, `handoffReadiness` in `src/canonical-producers.js`, data in `src/canonical-differential-registry.js`, both unbundled). A former producer gap counts as cleared only when its fenced writer is registered in the dispatch table (`CALLS`) and the readback table (`RECONCILE`) and the differential registry marks it covered; `tests/canonical-differential.mjs` checks that registry against the scenarios it really ran. Every other condition is a named blocker: `exception_not_accepted:<id>` for each named projector-versus-canonical difference the owner has not accepted, the receipt blockers read from the live database and the registry of `src/canonical-receipts.js` (`receipts_schema_missing` while the contract is below 19 or a receipt or baseline table is absent; `receipts_baseline_missing` once the marker is `open` or `held` without a sealed baseline, because the baseline is recorded by the activation operation after the flip; `receipts_baseline_unverified`; `unreceipted_changes`; `receipts_attention_open`), `receipts_protocol_unregistered` (no atomic operation registered; derived, not a flag), `producer_not_wired:<epg_commit|metadata_sync|discovery_admission|rated_admission_retention>` (a producer is wired only when the receipts registry holds an atomic operation for every kind it needs), `reader_not_moved:<name>` (derived from `CANONICAL_READER_REGISTRY` of `src/canonical-catalog-reader.js`: class `freeze`, `moved:false`; an `exception` entry never blocks and must not be marked moved), `empty_class_not_loaded:<class>:<found>/<expected>` (708, 401, 4), `projector_lease_live`, `projector_window_not_idle:<state>`, and the marker, baseline and schema blockers. `ready` is true only when none remains; it is information for the owner, never a permission. The registries are frozen data (a comment changes nothing); the PR that wires a producer registers its atomic operations, the PR that moves a reader changes its entry, and a test refuses an entry the repository contradicts. The differential harness compares the projector path and the canonical writers table by table; the differences it classifies are the named exceptions of `P6_DIFFERENTIAL_EXCEPTIONS` (`src/canonical-film-writers.js`) and `EXTRA_EXCEPTIONS` (registry module), see the [P6 evidence](../../evidence/d1-migration/air-374-p6-differential-harness-offline-2026-11-11.md).

Handoff and recovery (design only): see [ADR 0117](../../adr/0117-film-person-d1-handoff-owner-decisions.md) and the [runbook](../../runbooks/film-person-open-handoff.md). After `open` the recovery is `held` plus a forward fix proven on a safe copy; a return to `r2` or a revert after D1-only writes is not a rollback; canonical R2 `titles.json`/`people.json` are frozen at `open`.

Projector fence ([ADR 0116](../../adr/0116-projector-marker-and-generation-fence-on-every-batch.md)): `PROJECTOR_MARKER_GUARD` asserts `mode=? AND cutover='open' AND generation=?` in every projector batch; legacy databases keep a guard that holds only while the marker table is absent.

Owner TMDB retirement decisions are prepared the same way, **inactive** ([AIR-370](https://trello.com/c/wZmtK9tS), [schema reference](../data/d1-schema.md#owner-tmdb-retirement-decisions-schema-v16)): an append-only history of owner `retire` and explicit `restore` decisions with request-id replay, typed `tmdb` / `tmdb_tv` ids and held conflicts, plus a prepare-only loader of `identity/tmdb-retirements.json`. The semantics of ADR 0057 do not change, no un-retirement is implied, and the projector and the R2 object stay as they are until the owner-approved handoff and load.

Production retains Film/Person, ratings, discovery ledger/catalog and other remaining authoritative objects in **Cloudflare R2**. Published programme generations and watchlist membership are now D1-authoritative after activation on 3 November 2026; their R2 documents and pointer are mirrors. The metadata cache working set stays `metadata.json` until `metadata_cache_authority.mode` is `d1` ([ADR 0073](../../adr/0073-metadata-cache-d1-authority.md)). The pending rule is unchanged: missing `metadataAt`, `peopleVersion` other than 1, `peopleNamesVersion` other than 2, missing `synopsisFetchedAt`, or `metadataAt` older than 30 days. In `d1` mode that rule reads the D1 payload, including a key that has no Film row. A cache commit does not change the owner-review overlay or D1-only credits. The D1 schema and repository adapters support a separately approved migration path; a schema and offline importer do not make D1 authoritative. The programme and watchlist reads and the EPG commit apply the domain localization rule unconditionally: a cached automatic title or name goes through the guarded transition, a reviewed value is never downgraded, and an owner-authored or unexplained reviewed value is kept with an explicit `titleConflicts` / `nameConflicts` entry ([ADR 0037](../../adr/0037-domain-localization-only.md)). An owner confirmation is stored in `admin/owner-reviews.json` and applied in memory before the dictionary: an owner-reviewed name, then `data/film-titles.json` / `data/person-names.json`, then `titles.json` / `people.json`. An alias stored without an owner-reviewed localization does not replace the preferred title or name ([ADR 0072](../../adr/0072-owner-reviewed-localization-overlay.md), Accepted). The overlay is not copied back into those objects, and D1 is not the authority for it. The `LIFECYCLE_LOCALIZATION` runtime flag selects the localization of the metadata sync only (`on:metadata`, `shadow:metadata`; off by default); verify the **live** binding before claiming a particular metadata mode is active. The original [rollout log](../../evidence/film-person/lifecycle-audit-and-rollout.md) describes the 22–23 October staged switch of the other paths, whose tokens the Worker no longer reads. Neither setting is equivalent to deploying the full lifecycle entity repository.

## Identity and canonical records

- Letterboxd watchlist films retain their `lid` as the existing stored ID. A discovered, verified TMDB movie is usually stored as `tmdb_<tmdbId>`; if the TMDB id is already owned by a watchlist entry, that entry is reused. Neither storage ID nor discovery observation key (`normalizedTitle|year`) should be confused with the canonical TMDB identity (`tmdb:<id>`).
- `localFilmId()` mints `film:<letterboxd lid>`, `film:tmdb:<id>`, or a sorted `film:conflict:<ids>` for conflicting TMDB claims without Letterboxd. A previously assigned `localId` is preserved; it is not recomputed merely because new evidence appears.
- `canonicalFilmId()` is the one rule from a stored spelling back to the canonical id: `tmdb_<n>` → `film:tmdb:<n>`, a Letterboxd `lid` → `film:<lid>`, a `film:` id unchanged, an empty value `null`. It never mints: a result that names no stored Film is left unresolved by its caller. The offline importer loads this function from the domain source rather than keeping a copy.
- `externalIds` carry scheme, value, trusted/conflicting flags and provenance. Two different verified TMDB identities or distinct Letterboxd identities are collisions, **not** automatic merges. `canonicalIdentity` becomes `tmdb:<id>` only after identity is resolved against trusted evidence; an accepted score or search hit alone does not promote it.
- **Letterboxd slug alias** ([ADR 0052](../../adr/0052-letterboxd-slug-film-alias.md), [AIR-276](https://trello.com/c/PeWwEti8)): see [below](#letterboxd-slug-alias). A slug is never an identity and never links two records.
- **TMDB TV identity** ([ADR 0057](../../adr/0057-tmdb-tv-identity-and-retired-movie-ids.md), Accepted, [AIR-290](https://trello.com/c/70ldvbUB)): see [below](#tmdb-tv-identity-and-retired-movie-ids). `tmdb` is a movie id and `tmdb_tv` a TV id; an equal number in the two schemes is never evidence.
- `linkFilms(existing, incoming, at, evidence)` preserves the existing entity ID, payloads and reviewed localization. Linking separate entities requires matching Letterboxd evidence, the same *trusted* TMDB identity on both sides, or `evidence.verified === true`. Shared **proposed/untrusted** TMDB IDs are insufficient. Conflicts yield `identity_collision` or `unverified`/`unrelated` without changing entities.
- A successful link adds aliases and an old→surviving ID redirect, preserving existing fingerprint, prediction and metadata; incoming prediction and history are retained as history/preserved results, without repeat duplicates. A reviewed value must not be silently replaced with an automatic or conflicting incoming value.
- `localPersonId()` prefixes the **role-specific** ID: `person:actor/<slug>`, `person:director/<slug>`, `person:role/<name>`, `person:tmdb_actor/<id>`, or `person:tmdb_director/<id>`. Same real human appearing under different roles/authorities is **not** merged in storage. Embedded credits and localized names are not by themselves a canonical Person repository. The pure [canonical Person contract](canonical-person.md) ([ADR 0058](../../adr/0058-canonical-person-grouping.md)) groups those records by source key, verified coCredit or an owner decision. The [person identity projection](person-identity-projection.md) ([ADR 0059](../../adr/0059-person-identity-projection.md), Accepted) is the one consumer reference over that grouping: a watchlist filter and a catalog filter call it with records already loaded and receive the same human id, or an explicit unresolved, ambiguous or conflicting state. The watchlist grid still matches the stored role id. `GET /api/d1/persons/<role>/<key>/identity` is the one route that loads a D1 neighborhood and calls the projection ([ADR 0062](../../adr/0062-d1-person-identity-read.md)). The Finds actor and director filter reads that GET ([ADR 0065](../../adr/0065-finds-person-filter-d1-read.md)). A shared name never adds a member.

## Film page URL identity (AIR-387)

The film page URL is a presentation of identity, not a new identity. `/film/tmdb_<n>` is the permanent URL of a TMDB movie and `/film/<letterboxd id>` is its alias; both open the same page. A watchlist film uses the TMDB URL only when its record proves a movie (`tmdbLink` resolved to a `/movie/` page of the same number as `tmdbId`) and no other loaded film proves the same number; otherwise its Letterboxd id stays the URL. A catalog-only film's URL is `tmdb_<n>` for its verified `tmdb:<n>` admission. Titles, years, a TMDB redirect on letterboxd.com and a TV id of the same number are never identity. The URL changes no storage id, fact, rating, prediction key, canonical Film/Person record or provenance; see [UI and read models](../../architecture/ui-and-read-models.md#one-permanent-film-url-air-387) and the [catalog API](../api/catalog.md#permanent-catalog-film-api-catalog-film-tmdbid). A canonical Film admitted by the verified rated archive resolves on the same permanent URL even when Discovery never admitted it (AIR-409, a read-only fallback to one key of `letterboxd/admissions/verified-films.json`, only while the authority marker names R2 and bounded by the owner's retirements and D1 contradictions; never in `open`, `held` or an unreadable marker; see the [catalog API](../api/catalog.md#permanent-catalog-film-apicatalogfilmtmdbid)).

## Letterboxd slug alias

A Letterboxd film slug is kept as its own `externalIds` entry: `{scheme: 'letterboxd_slug', value, trusted: false, conflicting, provenance}`. It is separate from the lid (`scheme: letterboxd`), from TMDB ids and from title aliases.

- **Source.** `letterboxdSlugFromUrl` accepts only `https://letterboxd.com/film/<slug>/` and `https://letterboxd.com/<member>/film/<slug>/`: same origin, no query, fragment or credentials, lowercased. A title, a lid, a TMDB URL or Wikidata never yields a slug.
- **Attached only to a Film with a lid:**
  - `current`: the Film's own permalink, when every stored record of the lid that carries one agrees. The records are the programme, the watchlist, `metadata.json` and the record itself. Provenance: `source: letterboxd_film_url`, `records` (which of them carry it), canonical `url`, `observedAt`.
  - `ambiguous`: the same records carry different permalinks, such as a rename seen by one record and not yet by another. Every slug is kept with its `records`, and none is current, because no record is proved fresher.
  - `observed`: a slug from a Letterboxd Diary entry with the same lid (`source: letterboxd_diary`, `entry`), when the caller passes `store.diaryHistory`. An alias stamped by the diary writer keeps its own `firstObservedAt` as `observedAt`. An older alias without one has `observedAt: null` and `observedBetween {from, to}`, the entry's first and latest read; no exact time is claimed. One slug in several entries of the lid: `from` is the earliest lower bound (unknown if any is unknown), `to` the earliest upper bound, and `observedAt` is exact only when the two are equal;
  - `historical`: a slug stored on the same Film by an earlier backfill that the Film no longer carries, so a renamed permalink still names it.

  A TMDB-only Film, and a diary row without a lid, get no slug.
- **Stable.** The backfill keeps each stored slug's stored time: an exact `observedAt`, otherwise its stored `observedBetween`. A replay with the stored sidecars is therefore unchanged, even after later diary reads.
- **Collision.** One slug on two Films marks the entry `conflicting` on both and is reported as `aliasConflicts` by `readLifecycle` and in the backfill report. Nothing is merged, moved or re-rated.
- **Unchanged by the alias:** `id`, `canonicalIdentity`, the lid, TMDB trust, readiness, fingerprint, prediction and the Film count.
- **Storage.** The alias is part of `externalIds`: the R2 lifecycle sidecars and the D1 `film_external_id` rows hold it without a schema change. `trusted: false` keeps it outside the unique index on trusted identities.
- **Inventory.** `scripts/letterboxd-slug-inventory.mjs --snapshot <dir>` counts the aliases a snapshot's stored records would yield. It makes no request and writes nothing; running it on a production export needs owner approval for that export.

## TMDB TV identity and retired movie ids

A miniseries that TMDB keeps as a TV entry is identified by `{scheme: 'tmdb_tv', value, trusted, conflicting, provenance}` ([ADR 0057](../../adr/0057-tmdb-tv-identity-and-retired-movie-ids.md), Accepted). The functions live in `src/domain/tmdb-tv-identity.js`, which is loaded beside this file. The Worker bundle loads it at top level: `parseFilm` keeps the typed link and the lifecycle reader applies the retirements object ([below](#runtime-projection)).

- **Separate namespaces.**
  - `tmdb` (movie) and `tmdb_tv` values are never compared.
  - `tmdbTvCollisions(films)` reports a trusted `tmdb_tv` held by two Films as a collision for owner review, and the same number as a movie id on another Film as a `numericOverlap` only.
  - `linkFilms` keeps refusing a Film whose `tmdb` value differs (`identity_collision`). It never links on a TV value.
- **Letterboxd link.**
  - `letterboxdTmdbLink(html)` returns the single visible `https://www.themoviedb.org/(movie|tv)/<id>` link, typed. Only an anchor's `href` counts, not a URL in text, a `<link>` or another element, with the page's `data-tmdb-type`/`data-tmdb-id` attributes.
  - The status is `resolved` only when exactly one link agrees with exactly one attribute pair.
  - The status is `review` for `link_disagrees_with_attributes`, `multiple_tmdb_links`, `contradictory_attributes` or `attributes_missing`.
  - With no link the status is `unresolved` (`no_tmdb_link`).
  - It never corrects a Film.
- **Retirement.**
  - `tmdbRetirement(entry)` validates an owner-confirmed retirement: `filmId` `film:<lid>`, `lid`, `movieId`, `tvId`, `evidence` and `confirmation` (`by: owner`, `at`, `source`).
  - The evidence must contain:
    - `movieStatus: 404` and `movieCheckedAt`;
    - the Letterboxd permalink in `letterboxdUrl`;
    - `link: tv/<tvId>` and `linkCheckedAt`;
    - `tvResponseId` equal to `tvId`, and `tvCheckedAt`.
  - Each missing or different piece is a named reason.
- **Applying it.**
  - `applyTmdbRetirement(film, retirement, at)` changes only that Film:
    - the `tmdb` entry becomes `trusted: false`, keeping its value; its provenance gets `status: retired`, `reason: tmdb_movie_404`, `replacement`, `evidence`, `confirmation` and `previous`;
    - a trusted `tmdb_tv` entry is added after it, with provenance `source: letterboxd_tmdb_link`;
    - `canonicalIdentity` becomes `tmdb_tv:<id>`;
    - the identity dimension stays `resolved`, with `sourceVersion` `tmdb_tv:<id>` and both ids in its provenance.
  - Everything else is unchanged.
  - The result depends on the Film and the retirement only, never on the time of the run (except the dimension's `updatedAt`), so any writer's correction reads back identically.
  - A Film carrying exactly the result is returned with `changed: false`. Exactly means all of these: the retired `tmdb` entry with its full provenance (including `previous`), the trusted `tmdb_tv` entry with its full provenance, `canonicalIdentity`, and the identity dimension's `sourceVersion` and both ids. Key order is ignored. Any other trace of a correction is `partial_correction`.
  - These states are refused, not repaired: `film_mismatch`, `lid_mismatch`, `identity_not_resolved`, `conflicting_tmdb`, `movie_id_mismatch`, `tv_id_mismatch`, `partial_correction`, `movie_not_trusted_identity`.
- **Storage.** The retirements are one owner-approved R2 object, `identity/tmdb-retirements.json`, applied by the projection ([below](#runtime-projection)). The records keep the movie id Letterboxd shows. D1 holds the untrusted retired `tmdb` row, the trusted `tmdb_tv` row and `canonical_identity` `tmdb_tv:<id>`; the unique index on trusted `(scheme, value)` separates the namespaces without a schema change.
- **Plan.** `scripts/tmdb-tv-identity-plan.mjs` plans exactly the four confirmed Films from the private AIR-286 artifact. It reads either D1 or a snapshot, writes nothing, and states each Film's expected D1 identity; `d1Readback` compares D1 with it ([runbook](../../runbooks/tmdb-tv-identity-correction.md)). D1 is written by the enrichment projector ([ADR 0056](../../adr/0056-d1-enrichment-write-through.md)), not by this tool.

### Runtime projection

- **The page link in the records.** `parseFilm` adds `tmdbLink`, the full `letterboxdTmdbLink(html)` result, to the record it returns. `tmdbId` is unchanged: it is still the first `data-tmdb-id` number, whatever the link or `data-tmdb-type` says.
  - The metadata refresh writes the record to `metadata.json` and to the sync run's watchlist. The completed sync writes the run's films to `watchlist.json`, and the EPG commit carries them into `programme.json`.
  - The field appears on a record only when the regular sync re-parses its page: a stale record (30 days) or a missing synopsis. A record written before has no field and stays valid. A fresh record keeps the field it has.
  - No Film view, readiness rule or change key reads `tmdbLink`, so the field alone changes nothing in D1.
- **The retirements object.** `readLifecycle(store, now, options)` applies `store.tmdbRetirements`, the body of `identity/tmdb-retirements.json`, only when it is not `null`.
  - Absent: the reader calls none of this and the view is exactly what it was. Nothing creates the object; it is written only by an owner-approved run ([runbook](../../runbooks/tmdb-tv-identity-correction.md)).
  - `tmdbRetirementSet(body)` checks the whole object first: `schemaVersion: 1`, a `retirements` array, every entry valid under `tmdbRetirement`, and no two entries naming the same Film, lid, movie id or TV id. One failure fails the object (`valid: false`, reasons such as `entry_0:owner_confirmation` or `entry_1:duplicate_tvId`), and no retirement of it applies.
  - `applyTmdbRetirements` runs after the watchlist and programme Films are built and before catalog records are linked, so a retired movie id, no longer trusted, links no catalog record. A retirement is **held**, and its Film stays as the records build it, when:
    - the Film is not in the view (`film_missing`);
    - a stored record of its lid (programme, watchlist, `metadata.json`) with a `tmdbLink` no longer shows the confirmed divergence, checked per record by `tmdbLinkChange`. That divergence is exactly one link, `tv/<tvId>`, with exactly one attribute pair, `movie`/`<movieId>`. Anything else is held:
      - no link, several links, another link or an unreadable field (`link_changed`);
      - attributes that are missing, several, of another type or another id (`attributes_changed`), including Letterboxd switching only the type, or type and id, to the TV entry;
    - `applyTmdbRetirement` refuses it (`movie_id_mismatch`, `lid_mismatch` and the other reasons above).
  - A record without a `tmdbLink` field (written before the field existed) is no evidence either way. The correction uses the identity dimension's own `updatedAt` as its time, so it is the same on every read.
  - `settleTmdbRetirements` checks the corrections against the whole view once catalog records are linked. A trusted `tmdb_tv` on a second Film (`tmdb_tv_collision`) or a second Film still trusting the retired movie id (`retired_movie_on_other_film`) undoes the correction and holds every Film involved.
  - The view then carries `tmdbRetirements: {valid, reasons, retirements, applied, held: [{filmId, reason}], numericOverlaps}`, with `entitiesOnly` too. It is absent when the object is absent. `numericOverlaps` (a TV id equal to a movie id on another Film) is reported only.
- **Consumers.** The corrected Film keeps its id, lid, slug alias, localization, fingerprint, prediction, history and redirects; `catalogReady` and `displayReady` still hold through the lid. Movie-only consumers read the records' `tmdbId`, which keeps the movie number, and never see `tmdb_tv`: EPG matching and discovery `knownTmdb`, catalog keys `tmdb_<n>`, posters, Wikidata P4947 and the model's TMDB URI (for a corrected Film still the retired movie URL, as before the correction). The retired movie ids answer `404`, so no TMDB movie can be verified under them. `recordsFor` adds catalog records only for a trusted `tmdb` id, so a `tmdb_tv` number never pulls the catalog record of an equal movie id into a Film's credits. The admin Film record (`src/admin/read.js`) builds its identity from the records and still shows the movie id; it reads, and writes nothing.
- **Offline tools.** `scripts/snapshot-store.mjs` loads the object into `store.tmdbRetirements` when a snapshot holds it (`null` otherwise), so the offline import, the projection seed and the lifecycle scripts derive the same corrected view as the Worker.

### Watchlist fact admission

[ADR 0086](../../adr/0086-durable-watchlist-film-retention.md) (Accepted). The reader still builds Films from the current programme list, or from the watchlist list when the programme list is absent, and then from discovered films. It also keeps a Letterboxd lid whose `watchlistAdmissions` value is a boolean. The projector fills that map from `enrichment/view-index.json`: a lid matching `^[A-Za-z0-9_-]{1,80}$` and not starting with `tmdb_`, and only when `watchlist` is `true` or `false`. A missing index admits nobody.

The metadata cache is the body of an admitted lid only when the row's id is absent or equals the lid. A row whose id names another film is not that body, and the lid stays a Film. A lid with no usable cache row is still a Film and keeps the Letterboxd id. A `tmdb_<n>` key, a mood facet, a watched flag, a rating, a diary title, a fingerprint, a slug, or a title and year do not mint a Film. `watchlist: false` is a removal of membership. It is not `watched: true` and it does not place the film on the watchlist grid. The grid still reads the watchlist document. Re-adding the same lid returns one Film.

When that lid is on neither current list and has no usable cache, the enrichment writer does not replace an existing Film. It writes watchlist membership only. Credits, metadata, trusted external ids, identity and metadata dimensions, and sync clocks stay as stored. A Film that has no row yet is still inserted.

`reconcileDepartedFilms` classifies rows that are no longer on the current lists. It writes nothing. Join an existing Film by its lid, or by exactly one trusted movie id, and keep that id. Two trusted owners of one movie id, a lid whose trusted movie id disagrees with the Film that holds it, a `tmdb_tv` id together with a movie id, and two lids that share a slug are `conflict`. Two lids that share one unverified movie id are `ambiguous`. A lid with a watchlist boolean and no Film is `resolved` as a watchlist fact the reader already keeps. A lid or trusted movie id with neither, and a row with no id, stay `unresolved`.

### Rated archive admission

[ADR 0087](../../adr/0087-rated-archive-film-admission.md) (Accepted). [ADR 0090](../../adr/0090-rated-identity-redirect-proof-and-retry.md) (Accepted) lets a later identity-step prove the short code by the `boxd.it` hop when the HTML shortlink tag is absent, and returns a stored `shortlink_missing` review to pending only through an owner retry. A verified movie from a confirmed rated ZIP is `letterboxd/admissions/verified-films.json`: schema version 1, films keyed `tmdb_<n>`, each value `{tmdb, sourceCode, archiveSha256, title, year}` and no `watchlist` field. A later explicit continuation may also store synopsis, credits, runtime, genres and a provisional Russian title on that same value, and only when the fetched page still matches that short code, path and movie id. The reader adds that key when the current programme, watchlist and discovered films do not already contain the same movie id. `listedOnWatchlist` stays false. A missing object admits nobody. An item that carries `watchlist`, a key that is not `tmdb_` plus its own `tmdb`, or a movie id already on another Film is dropped. When the only occupant of that movie id is this thin archive record and a discovered film of the same id is richer, the discovered film replaces the stub. A programme or watchlist film of that movie id is not replaced. The same verified movie on a later EPG airing stays one Film. The rating is a fact on that movie id and is not membership. Preview and the candidate queue do not admit a Film.

## Lifecycle dimensions and transition rules

`FILM_DIMENSIONS` defines **five independent state dimensions**; availability is a time-bound projection, **not** a sixth status. Every dimension state may hold `status`, `updatedAt`, `source`, `sourceVersion`, `provenance`, `lastError`, `failureReason`, `retryAt`, `attempts` and `nextAction`; localization alone also has `value`. These status envelopes do **not** contain entire fingerprint, metadata, or prediction payloads.

| Dimension | Status vocabulary | Conditions and consequences |
| --- | --- | --- |
| Identity | `unresolved / resolving / resolved / ambiguous / rejected` | Keep Letterboxd ID without inventing TMDB; `excluded_nonfilm` creates no Film. Historical/expired or unchanged terminal discovery is `wait_new_evidence`; future retry is `wait_retry`; only **eligible current** discovery can `continue_discovery`. Distinct verified IDs surface conflict. |
| Metadata | `missing / fetching / partial / fresh / stale / failed` | 30-day freshness threshold. Letterboxd metadata and TMDB-only metadata choose different next actions. A synopsis-only update that retains older credits is `partial`; `peopleNamesVersion: 2` means the name attempt finished, not that all names are reviewed. The decision clocks that are not columns of `film_metadata` are projected separately ([below](#metadata-sync-clocks)). |
| Localization | `missing / provisional / reviewed` | Verified dictionary/owner choice cannot be downgraded by Wikidata/cache; provisional transcription is **provisional** even when stored in a reviewed dictionary. Conflicting inputs remain aliases/provenance or `localizationConflicts`. |
| Fingerprint | `missing / generating / current / stale / failed` | Schema v1 and no `invalidatedAt` make the fingerprint current. Profile changes alone do **not** invalidate/recreate fingerprints. The reader and domain accept the fingerprint transition verdict per film (`fingerprintCompatible` on the store, [fingerprint compatibility](fingerprint-compatibility.md#readers-and-diagnostics)): a kept fingerprint of another schema version is current with its own version as provenance; an invalidated one never is. |
| Prediction | `missing / generating / current / stale / failed` | Current means fingerprint current **and** matching profile version/hash, fingerprint hash, schema and prompt version 1. Failures retain retries/backoff; profile changes make prediction stale, with `prediction_only` when fingerprint is still current. Every consumer compares the profile by strict version and hash equality; [ADR-0031](../../adr/0031-selective-prediction-profile-compatibility.md) defines the selective rule that replaces it once connected and activated; its evaluator and the one switch that moves every consumer to it are described in [prediction compatibility](prediction-compatibility.md); the lifecycle reader and domain accept its verdict per film (`predictionCompatible` on the store): a positive verdict keeps a prediction that names the usable fingerprint current over another profile or prediction-prompt version, with its own provenance; a negative one is stale even over an exact match. |

`transition()` rejects edges not permitted by the domain graph (for example, `resolved` identity cannot regress to `unresolved`, and reviewed localization cannot become provisional). `applyAutomaticLocalization()` cannot set `reviewed` and records attempted overrides; only `applyReviewedLocalization()` with `authority: dictionary` or `owner` can promote reviewed content. `observeMetadata()` does not rewrite fingerprint or prediction. `invalidatePredictionForProfile()` preserves fingerprint and chooses the appropriate next action.

## Metadata sync clocks

`metadataSync` still decides freshness from `metadata.json`. The clocks it branches on, and that `film_metadata.updated_at` folds together, are `metadataAt`, `synopsisFetchedAt`, `peopleNamesVersion` and `peopleLocalizedAt`. `peopleVersion` is already `film_metadata.people_version`. Reviewed titles and reviewed names stay on the localization dimension; `titles.json` and `people.json` feed that dimension and are not copied into the clock row.

D1 table `film_sync_state` ([ADR 0070](../../adr/0070-metadatasync-freshness-clocks.md)) stores those four clocks and nothing else. For a Film that already has a row, no sync row means `metadata.json` has no entry for that Film. A NULL clock means the entry exists and the clock is absent. The integer 2 is the only `people_names_version` that means the name attempt finished. The 30-day window is not stored. The enrichment projector writes the row from R2 after schema version 5, including after the Film has left the view while the cache entry remains. A cache key with no Film row does not create one. Until that migration is applied the table is absent and nothing reads it. No sync step and no page reads the row to choose an R2 write. The contract is the [D1 schema](../data/d1-schema.md#metadata-sync-clocks-schema-v5).

## Readiness is derived, not a new entity status

- `displayReady`: non-rejected identity, a resolved identity or a Letterboxd external ID, and a usable preferred title (reviewed/provisional, original or EPG). Missing translation, fingerprint or prediction must **not** hide a film.
- `catalogReady`: stable Letterboxd ID or trusted, non-conflicting TMDB ID **and** fresh or partial metadata.
- `predictionReady`: both fingerprint and prediction are `current`. Neither a valid catalog id nor a fresh profile alone suffices.
- `preferredTitle()` uses reviewed/localized value first, otherwise original, otherwise EPG. UI parity must still compare the **actual displayed title** in existing programme/watchlist read paths, not assume it equals the domain projection.

## Availability and published generations

`availabilityProjection()` computes `availableUntil` as the latest known show start plus **72 hours**; `hot` evaluates shows from **72 hours back** through **24 hours ahead** (upper bound exclusive). Shows and `epgLastAiring` are not stable Film attributes and never invalidate fingerprint.

An explicit `shows: []` is known **no availability**. When a published programme run is known, missing `shows` or a mismatched `showsProgrammeRunId` must not produce hot. `epgLastAiring` is a fallback only when no explicit shows, no shows programme run and no published run are known. A new published EPG generation atomically replaces the current show set; it does not append old availability. See [candidate discovery](candidate-discovery.md).

When `published_epg_authority.mode` is `d1` ([ADR 0079](../../adr/0079-d1-authoritative-published-epg.md), Accepted; production marker activated on 3 November 2026), availability is that generation's D1 document plus `published_epg_show`. `film_epg_last_airing` is not a write of this publisher. `programme.json` and `watchlist.json` are the compatibility mirror, not a second authority. An explicit empty show list is still a member and zero show rows. The publisher does not mint a Film for a programme id.

| `enrichment/films/<id>/fingerprints/<hash>.json`, `fingerprint-generations/<hash>-s<schema>-p<prompt>.json` | Immutable fingerprint content bodies and generation records, written create-only for every accepted fingerprint ([fingerprint compatibility](fingerprint-compatibility.md#storage)); never identity, never read by display |
| `enrichment/view-index.json`, `enrichment/prediction-queue.json` | Derived dashboard/queue projections. Neither defines Film identity or personal truth. A view-index entry with a fingerprint also carries `impactFeatures`, a copy of the full fingerprint's mechanics and execution bound to its hash ([prediction compatibility](prediction-compatibility.md#prediction-queue)) |
| `enrichment/profile/current.json` and `profile/versions/<n>.json` | Taste-profile version/hash that controls prediction freshness |
| `letterboxd/diary/history.json`, `letterboxd/diary/state.json` | Letterboxd Diary viewing history, read as page 1 of a migrated ratings run. `LETTERBOXD_DIARY_HISTORY` is retired ([ADR 0075](../../adr/0075-retire-letterboxd-diary-history-switch.md)). One entry per viewing-id row, otherwise per film and day with a viewing count (a lower bound unless proved by one page), the ratings and re-watch rows, plus the incremental run state. A record links to a Film only through its Letterboxd lid; a slug is an observation, not an identity. Not a rating or watched fact ([contract](../integrations/letterboxd-diary-history.md), [ADR 0049](../../adr/0049-letterboxd-diary-viewing-history.md)) |

The reader's `*.lifecycle.json` sidecars are **computed views**, not permission to overwrite current `programme.json`, `people.json`, `epg/discovery-latest.json` or `enrichment/prediction-queue.json`. The offline backfill compares `create/update/unchanged/orphan/conflict` without deleting orphaned data. Reviewed downgrades, unapproved identity replacement and prediction-history loss are explicit conflict types; `updatedAt` and redirect observation times alone do not constitute a changed entity. Tests for this scope include `tests/film-person.mjs`, `tests/film-person-reader.mjs`, `tests/film-person-backfill.mjs`, `tests/lifecycle-parity.mjs`, `tests/film-person-localize.mjs`.

## Architecture and operational boundaries

- Match scoring and canonical identity have separate owners: scoring cannot silently verify a TMDB identity. `src/domain/resolution-acceptance.js` requires trusted existing decision/owner evidence or valid TMDB movie-detail confirmation and a matching actionable programme generation.
- The localization of the reads and of the EPG commit has no runtime switch; the metadata sync's localization is still flag-gated, and neither is a Film/Person persistent-entity cutover. Do not change `LIFECYCLE_LOCALIZATION` or any production writer while maintaining this reference.
- D1 repositories `src/canonical-repository.js`, `src/epg-repository.js` and `src/prediction-repository.js` were developed for migration work but must not be portrayed as authoritative until a separately approved live migration. Historical parity observations remain in [the original audit and rollout record](../../evidence/film-person/lifecycle-audit-and-rollout.md); follow Trello for current rollout completion and flags.
- Owner admin search, quality queues, and a later live read API use the contract in [admin read boundaries](admin-read-contract.md). That page does not add a route or change this domain.
- **Do not rewrite historical evidence.** Material new architecture choices need future ADRs; current reference and historical audit have different jobs.
