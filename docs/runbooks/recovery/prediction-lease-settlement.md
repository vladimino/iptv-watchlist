# Prediction expired-lease settlement

A prediction run whose runner lease has expired is **shown** by `GET /api/enrichment/status`, `GET /api/enrichment/runs` and MCP `enrichment_status` as `interrupted` / `lease_expired`. Those reads compute that from the diagnostic row and the clock. They do not rewrite the run, the diagnostic object or the journal ([ADR 0107](../../adr/0107-get-head-read-side-effect-boundary.md), [AIR-415](https://trello.com/c/NHyIKM6z)).

A start (`prediction_start` / `prediction_batch_start`) still marks the previous lease holder interrupted when it recovers that `runId`. Historic rows under `enrichment/run-diagnostics/` are settled by `POST /api/enrichment/complete` / MCP `prediction_complete` under the same Predictions writer fence: at most 10 keys per successful complete, resuming from `enrichment/run-diagnostics-settle.json`. GET still projects an expired row that the cursor has not reached yet. A list or get error does not fail the complete; the next complete retries the same page. Already-settled rows are no-ops. The hourly Predictions Scheduled Task is that writer when it completes a run. No extra cron or Task.

Do not probe production status or runs to “heal” a stall. Do not invent a new cron, Task or owner command for this. Delivery of a run event that did not reach the Events Log is a different repair with the same owner: the next `prediction_start` delivers it under the writer lease, and `GET /api/events` never does ([events](../../reference/domain/events.md#delivery-of-prediction-run-events), [AIR-416](https://trello.com/c/f7FX4Elk)). `eventOutbox.quarantined` above zero in the status read means an event failed eight deliveries and stays stored but unpublished; replaying it is a separate owner-approved operation, not a probe.

Rollback of the Worker code restores start-path settlement of a 100-key page; it does not un-write a run that a start or complete already persisted.
