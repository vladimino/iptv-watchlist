# Batch runner v2 dry-run A/B procedure (AIR-450 input, proposed)

**Status: proposed procedure, nothing authorized.** This page is the repeatable procedure for the dry-run A/B experiment of [AIR-450](https://trello.com/c/VPd21Y9d)'s scope. Delivered by AIR-449 as documentation. Running it needs the owner's explicit, operation-specific approval. Creating, editing, enabling or running a Scheduled Task, any production `prediction_batch_start` or `prediction_batch_submit` (dry run included), flags and authority changes stay unauthorized until then ([authorization](../process/authorization-and-escalation.md#chatgpt-scheduled-task-authorization)). The dry run writes nothing to prediction state: no lease, run, queue, fingerprint, prediction, version object or view-index entry ([contract](../reference/api/prediction-runner.md#batch-runner-v2-proposed-contract)).

## Frozen manifest (one start, ten passes)

[ADR 0122](../adr/0122-prediction-batch-runner-v2-dual-protocol.md) decision 10: the caller keeps the **one** dry-run manifest it received and replays the same complete film metadata, plans, stored fingerprints, profile and contract at generation sizes 1 to 10, and does not call `batch_start` between passes, because live input moves. So the experiment has two kinds of step:

1. **Freeze (once, owner-run).** The owner, under the AIR-450 approval, runs `prediction_batch_start({trigger:"manual", dryRun:true, pin:{filmIds:[...]}})` once with the frozen sample's ids. The whole answer is the **frozen manifest**: `manifestHash`, `profile` (with its body), `contract` (with the schema), and every film with `plan`, `modelMetadata`, the stored `fingerprint` of a `prediction_only` film and its `inputHash`. Record the sample as `$defs.sample` of [`batch-v2-ab.schema.json`](../reference/scheduled-task-prompts/batch-v2-ab.schema.json) (ids, `frozenAt`, `source`, `approvedBy`, and the `manifestHash` once known). **Size preflight (gate).** The manifest is not shortened: it carries the full `modelMetadata` and every stored fingerprint of a `prediction_only` film, and its whole serialized answer is bounded by `maxManifestBytes` (256 KiB = 262,144 since the owner's measured AIR-450 decision, raised from the initial 160 KiB). 100 films do **not** always fit, even at 256 KiB: [AIR-447's measurement](../evidence/prediction/air-447-batch-start-manifest-2026-11-12.md) found 100 metadata-only films at 141,205 bytes and 100 `prediction_only` films with stored fingerprints at 253,499 bytes. The second answer was over the **initial 160 KiB** limit but **fits the current 256 KiB** ceiling with 8,645 bytes to spare; 100 films with larger stored fingerprints, or a larger share of long metadata, can still exceed 262,144 bytes and are refused. If the freeze start answers `409 manifest_too_large`, nothing was created and the experiment stops: report `bytes`, `limit` and `largestFilmBytes` to the owner and wait for an owner-scoped decision on the sample or the limit (the owner already raised the ceiling once from 160 to 256 KiB; a further change or another sample is again the owner's decision). The tool result is about twice the answer on the MCP wire (`text` plus `structuredContent`), and whether the client delivers a result of this size to the model intact is unproven: report what the freeze returns, do not assume it. Do not shorten the manifest, drop or replace films, or retry with another pin to get under the limit. A sample the owner fixes at 100 films is run only if its freeze start fits.
2. **Ten passes (no start).** Each pass is a clean-context run of the `DRY RUN PROMPT` with `SAMPLE_ID`, `GROUP_SIZE` (1 to 10) and `FROZEN_MANIFEST` (the full manifest text, byte for byte the same in all ten) filled in. A pass calls only `prediction_batch_validate` (read-only preflight, [ADR 0131 (Accepted)](../adr/0131-batch-candidate-preflight-tool.md)) and `prediction_batch_submit(dryRun:true)`: it never calls `prediction_batch_start`, reads nothing, and takes profile, rules, metadata and fingerprints only from the manifest. Run the order 1, 10, 5, then the rest, so a context or quota limit shows early.

**Private handoff and retention.** The manifest carries the Taste Profile body and film metadata, which is private user context. It never goes into this repository, a PR, `docs/evidence/`, a Trello card or comment, a screenshot, a log or an issue. The owner decides how it reaches the ten passes (a private chat or a private note the owner controls) and deletes every copy when the AIR-450 report is accepted. A pass whose manifest fails the check of its step 1 (`manifest_invalid`) is discarded. **Report boundary.** The per-pass `$defs.result` records carry the raw model outputs (`films[].fingerprint` and `films[].prediction`), which are private user taste context like the manifest. The full result records and any raw output stay in the owner-controlled private trial channel or storage the AIR-450 approval names, under the same retention and deletion rule as the manifest. Public `docs/evidence/` may hold only sanitized aggregates: safe sample and film identifiers, `manifestHash`, profile and contract identity, group sizes, the comparison statistics and timings, quota figures and counts per `submitStatus`, and redacted representative examples after a privacy review. No manifest, profile body, film metadata, fingerprint or prediction object is published. AIR-449 stores no real record.

## Calls (exact)

```
prediction_batch_start({trigger:"manual", dryRun:true, pin:{filmIds:[...]}})   // once in total, by the freeze step; never inside a pass
prediction_batch_validate({items:[{filmId, fingerprint?, prediction, metadata?}, ...]})   // in a pass, before each submit: the same objects, no inputHash; read-only, no storage
prediction_batch_submit({runId:"dry-run", epoch:1, dryRun:true, manifestHash, items:[{filmId, fingerprint?, prediction, inputHash}, ...]})   // in a pass: 1..GROUP_SIZE items
```

`runId` and `epoch` are required by the MCP schema and by the Worker even in a dry run, and the frozen manifest has no run, so the fixed synthetic pair `"dry-run"` and `1` is used. The Worker's dry-run branch never dereferences a run. `manifestHash` and each item's `inputHash` come from the frozen manifest, so the Worker reports per film whether the live input is still the manifest's (`liveInput`). A group over 56 KiB is refused by the MCP tool with nothing submitted: that is itself a result (record it, resubmit one film at a time).

## Output contract

Each pass ends with one JSON object shaped as `$defs.result` of the schema: identity (`sampleId`, `groupSize`, `manifestHash`, profile and contract identity), per-film records (`plan`, `groupIndex`, the generated `fingerprint` and `prediction`, `submitStatus`, `liveInput`, sanitized `validation`, `generationMs`), per-call records (`itemCount`, `bodyBytes`, `toolMs`, `ok`) and `telemetry` (model, tokens, quota before and after, wall time). A value the platform does not show is `null` and its name goes into `telemetry.unavailable`; nothing is estimated. The pass returns it in the chat and the pass itself saves nothing; the owner copies it to the approved private location above, never to the repository and never as a screenshot.

## Comparison criteria

1. **Same input.** All ten results carry the same `sampleId`, `manifestHash`, profile and contract identity, and every film `liveInput` is `same`. Because no pass starts anew, a different `manifestHash` means the wrong manifest was pasted: discard and rerun that pass. A `liveInput` of `changed` means the live queue or catalog moved after the freeze; report it, it does not alter the frozen replay.
2. **Reliability per size.** Share of films per `submitStatus` (`would_write` against `validation_failure`), the issue paths and codes that recur, and groups refused for size.
3. **Quality against the size-1 pass.** For each film present in both: the absolute difference of `predictedRating` and `probability4Plus`, agreement of `confidence`, and whether the fingerprint evidence map validates. Report the distribution (median, p90, maximum), not one average. Only a stable result across sizes supports a larger `generationSize`; a drift that grows with the size is a finding against it.
4. **Model cost against tool latency.** Model generation (`generationMs`, or `wallMs` minus the sum of `toolMs`) is reported separately from MCP and Worker latency (`toolMs`) so a slow model is not read as a slow Worker. Where only `wallMs` is visible, say so.
5. **Quota.** Quota before and after each pass, and tokens where shown, per film and per pass. Unavailable stays unavailable.
6. **Decision output.** A table of the ten sizes against 2–5 and a recommended `generationSize` with the evidence. The owner decides the value; the Worker's range stays 1–10.

## Preflight before submit (AIR-450, accepted architecture after checkpoint C6)

C4 to C6 showed the typical content failures of a generated group (an unsupported `evidence.execution.stakes`, a `metadata`-only execution-quality claim, a bad enum) reach the Worker only at submit. The owner accepted the read-only group preflight architecture on 13 November 2026 ([ADR 0131 (Accepted)](../adr/0131-batch-candidate-preflight-tool.md), [explicit approval](https://github.com/vladimino/iptv-watchlist/pull/576#issuecomment-6838792033)); separate owner permission remains necessary for every Scheduled Task operation or experiment: after generation and **before** `prediction_batch_submit`, a pass calls `prediction_batch_validate` with up to 10 candidates (the objects it intends to submit, no `inputHash`, `metadata` only when the evidence cites `metadata:*`). It reads and writes nothing and does not check the frozen manifest, `inputHash` or live profile, so `observedProfileHash` still comes from the submit answer.

Rules of the pass (both prompts): read `results[]` by `index` and `filmId`; correct only what real knowledge of the film or a really used source supports (drop the unsupported claim, set `unknown` instead of an unproven execution quality); never invent a ref, add `model_knowledge` or `web_research` without a basis, or confirm an execution-quality claim (`stakes` included) with metadata alone; **at most one** re-preflight of the corrected films, no self-check loop; a film that still has issues goes to the submit as a `failure.kind: parse_error` item with an honest `failureReason`, never hidden and never resubmitted. A dry-run result records `calls[].kind` (`preflight` or `submit`, each with its own `callId`, `itemCount`, `bodyBytes` and `toolMs`) and `films[].preflight {valid, attempts, issues}`; the report counts `preflightCalls` and, per size, `preflight {checked, invalidFirst, recovered, unresolved}`, and `cost.mcpCalls` counts every call, so the extra call is measured, never assumed away.

The tool is light CPU (offline: ten realistic candidates are about 44 KB in, 1.6 KB out, median 3.9 ms in process, no storage I/O; [evidence](../evidence/prediction/air-450-batch-preflight-2026-11-12.md)); the production latency and the effect on model usage and Codex quota are **not** measured and no saving is claimed. A request over 56 KiB (57,344 bytes) or with more than 10 items is refused whole: split the group.

## Source fields and failure reasons (AIR-450 checkpoint C3 follow-up)

The C3 checkpoint (size 10, first ten films of the frozen manifest) failed because the generator computed `sourceBasis`/`sourceRefs` by hand and put an empty `sourceRefs` beside correct evidence. Since [ADR 0129](../adr/0129-fingerprint-source-fields-derived-from-evidence.md) the Worker derives both fields from a valid evidence map when they are omitted, and the dry-run prompt tells the pass not to send them. A manifest frozen **before** this change carries the previous `contract.schema` text, which still lists the two fields among the required ones: the prompt overrides it explicitly, and the frozen manifest is not re-frozen for this. An invalid evidence map is still rejected with its own issues, a supplied aggregate must still equal the derived one, and no evidence rule was softened.

The five `caller_reported parse_error` of C3 are a different question (missing metadata or knowledge against worse completeness when ten films are generated at once). The private result therefore carries an honest `films[].failureReason` per failed film (`insufficient_metadata`, `insufficient_knowledge`, `json_unparseable`, `other`; `null` otherwise) and the report counts them per size (`failureReasons`, `unspecified` for a missing value). The reason is a diagnostic of the data: it never feeds a rule and the pass must not choose it to improve a result.

**Next owner-approved checkpoint (C4).** A short diagnostic on the **same frozen manifest**: exactly the first group of ten films, generation size 10, `prediction_batch_submit(dryRun)` only, no production writes, compared with C2 (size 1) and C3. It runs only on the owner's separate GO; the ChatGPT side starts it and reads the result. A successful C4 means the derivation works inside the real Task; only then may the owner separately allow the 100-film C5. No Scheduled Task is created or edited by the delivery of this change.

## Sample selection and ground truth

The card asks for 100 films with a user rating the generator never sees, so that MAE and bias can be measured against a real rating. Two facts limit that, and the owner decides at the AIR-450 approval:

- **A pinned dry run selects queued films only.** `pin` returns a film that is not eligible (not queued, current or in backoff) in `notEligible` with reason `not_queued`, and never puts it in the manifest. A film that is already rated and watched is normally not queued. Whether 100 films exist that are both queued and have a hidden rating is unknown without a production read, which AIR-450 does not do without the owner's GO.
- **Without ground truth the report is agreement to the size-1 baseline only.** The aggregator says so explicitly (`quality.truth.basis: agreement_to_baseline_only`), and a model prediction is never called the truth. A larger decision (a separate, owner-scoped delivery that admits non-queued rated films to a dry-run manifest, or a smaller sample) is the owner's and is not made here.

The truth file, if any, is a private `{filmId: rating}` JSON object kept in the same private storage as the manifest. The generator never receives it: the manifest holds no prediction, rating or personal field (`modelMetadata` is limited to `id`, `letterboxdUri`, `tmdbUri`, `title`, `original`, `year`, `genres`, `synopsis`, `directors`, `actors`, `runtime`, asserted by `tests/prediction-dry-run-isolation.mjs`), and a film with a current prediction is never in it.

## Report

After the ten passes, the owner runs the offline aggregator on the private result records (it reads no production, model or network):

```
node scripts/prediction-ab-report.mjs --results <private-dir> [--truth <private-truth.json>] [--model-label <label>] --out report.json --markdown report.md
```

**Privacy by construction.** Every input record is first validated against the closed `$defs.result` (strict enums, hex hashes, lowercase ids, no extra key at any level); a defect is a refusal whose message names paths and keywords only, never a value, and a JSON parse error names the file only. The report is then built field by field from numbers, enums, hex hashes and film ids: nothing is copied from a free-text field, and the model name is never read from a record (the owner passes a public `--model-label`). The finished report must equal the closed `$defs.report` or the tool refuses. The only owner-chosen strings in the report are `sampleId` and that label, both restricted to short lowercase or alphanumeric tokens. Adversarial tests put a secret into every string field of an input and show it cannot reach the JSON, the Markdown or the CLI output.

**Explicit call association.** A film names the call that recorded its result by `films[].callId` (`calls[].callId` is unique, in call order); the array position of a call means nothing. A retry, a size refusal and each call of a group split into single films is a call of its own. The aggregator refuses (fail closed, never certifies a group by another group's hash) a duplicate or dangling `callId`, a film that names a call of another group, a `groupIndex` that differs from the frozen grouping (position divided by `GROUP_SIZE`), a `not_submitted` film that names a call, and a call that holds fewer items than films name it; a call named by no film (a refused attempt) is not a profile mismatch. Tests cover the reordered and split cases.

**Comparable films only.** A film enters a quality metric only when its status is `would_write` or `already_current`, its `liveInput` is `same` and its call's observed profile hash equals the manifest's. A changed live input, a moved profile or a stopped pass is counted and excluded, not averaged in.

**Completeness gate.** A report over fewer than the ten sizes or fewer than the 100 films of the card is a **partial diagnostic** (`completeness.final: false`, `unknown: partial_sizes`/`partial_films`, and the Markdown says so); it is never the final AIR-450 comparison. Even a complete report carries `ownerAcceptance: required`.

It refuses (fails closed, exit 1) when the passes are not one experiment: another `manifestHash`, `sampleId`, profile or contract identity, another film order, a repeated group size or a call above its group size. Its output is the sanitized `$defs.report` of the schema (a test validates it): validity and status counts per size, per-size cost (MCP calls, body bytes, tool and generation time, model, tokens and quota only where the pass recorded them, otherwise `null` and named in `unknown`), the distribution (mean, median, p90, max) of the absolute differences of `predictedRating` and `probability4Plus` against the size-1 pass, agreement of the 4.0 threshold and of `confidence`, overlap of `matchSignals`, `mainRisk`, execution values and plot mechanics, the spread of each film across sizes and, with a truth file, MAE, bias and 4.0 threshold accuracy per size. The report holds numbers, enums, safe identifiers and hashes only; a guard rejects any payload key or free text. After a privacy review the report and its Markdown form may go to `docs/evidence/prediction/`; the result records and the truth file never do.

**A profile that moved after the freeze.** `liveInput` compares the film inputs, not the profile. When the live profile changes after the freeze, a dry-run submit still answers `would_write`/`same` for those films and names the live profile in its `profile {version, hash}`. The dry-run prompt therefore makes the check mandatory after every submit: the pass compares the answer's `profile.hash` with `manifest.profile.hash`, records it as `calls[].observedProfileHash`, and on a difference stops, marks the remaining films `not_submitted` and returns `stoppedReason: profile_moved`. The aggregator excludes every film of a call whose observed hash differs from the manifest's (or is missing) from all quality metrics and names it (`excluded.staleProfile`, `profileMismatchCalls`, `unknown: profile_moved`); the pass is rerun after a new freeze. `tests/scheduled-task-prompt-v2.mjs` runs this stop on a moved profile.

## Isolation proof (offline)

`tests/prediction-dry-run-isolation.mjs` runs every dry-run RPC on the real Worker code while any R2 put or delete and any D1 write statement or batch is a fault: default and pinned start (a current film, an unknown id, a 100-film pin, a bad pin), submit of valid, invalid, failure-only and unknown-film items, repeated trials, a wrong or malformed `manifestHash`, a changed contract, a missing `runId`, `epoch` 0, a group of 11, a profile that moved after the freeze, all beside a live run that holds the lease. It counts write attempts (none are allowed) and compares the whole D1 dump and every R2 object before and after. It also asserts the production surface is unchanged: the v5 tools take no dry-run argument, the v5 `next` and `submit` refuse a v2 run, and the runner contract is pipeline 5 with model batching off.

## Not part of this procedure

Any non-dry-run call, a Scheduled Task, an installed prompt, a production write, flags and the cutover (AIR-451). The [bounded-run signal](../reference/scheduled-task-prompts/hourly-predictions-batch-v2.md#owner-activation-gate-bounded-run-signal) is a separate owner decision before activation.
