# Runtime feature flags

**Maintained contract; dated observations, not a live configuration dashboard.** Reviewed against GitHub `main` and Trello evidence on 2026-10-25 for [AIR-146](https://trello.com/c/qfqYibFB). All flags below are Cloudflare Worker **environment variables**, not switches managed by GitHub. [`wrangler.jsonc`](../../wrangler.jsonc) uses `keep_vars: true` and deliberately does not declare their production values. A code deploy does not reset these variables. The currently deployed value must be read from authorized Cloudflare settings (or a verified read-only diagnostic that actually exposes that setting) before making operational decisions.

Do **not** interpret a source default, a dated Trello comment, or a prior deployment as proof of the live value. This page does not authorize toggling flags, launching EPG/resolver/prediction jobs, or editing R2/D1, schedules or Access. Consult the [deployment runbook](../runbooks/deployment.md) and obtain action-specific owner approval.

The explicit `off` values in this table describe **effective behavior**, not necessarily accepted textual configuration tokens. For `LIFECYCLE_LOCALIZATION`, write `on:epg` or `shadow:epg`, not `on`. To disable one path while retaining other paths, omit that path's token rather than deleting the whole variable.

### Interactions and operational safeguards

- Variant discovery is independently gated: useful `shadow` comparison pairs `CANDIDATE_DISCOVERY=shadow` with `SCORED_RESOLUTION=shadow`; live variant searching requires both `CANDIDATE_DISCOVERY=on` and `SCORED_RESOLUTION=on`. Changing one alone does not enable the intended variant search. Optional searches consume TMDB budget and carry distinct throttling/defer counters; see [candidate discovery](domain/candidate-discovery.md).
- `SCORED_RESOLUTION=on` changes which resolver may write **authoritative candidate decisions and catalog identity**. Switching back affects **future execution**, not already committed R2 objects. Rollback needs separate owner approval and read-only verification; no implicit R2 data rollback.
- Localization modes can affect persisted content on a subsequent EPG/metadata run or presentation on reads. A mode switch is not evidence that the next scheduled sync actually ran. Preserve all separately approved path tokens when adjusting one path.
- `RATINGS_REFRESH=on` only removes an endpoint gate; a manual refresh remains a separately authorized operation. A Letterboxd 403 retains the last good ratings generation and imposes backoff; see [ratings reference](integrations/letterboxd-ratings.md).
- `PREDICTION_VERSION_OBJECTS=on` changes what the next prediction submit **writes to R2**; it is a production writer change and needs its own owner approval before the value is set. Switching back to `off` stops new version objects; objects already written stay in R2 (the Worker never deletes) and remain valid, referenced bodies. The flag does not perform the one-time materialization of historical versions, but that operation requires it on (see `PREDICTION_MATERIALIZATION`) and it must stay on afterwards so new submits keep bundles linked.
- `PREDICTION_MATERIALIZATION=on` only removes the gate of the materialization route; it starts nothing. Each `apply` against production is a separate owner-approved operation that writes version objects and rewrites prediction bundles under the prediction writer lease. It refuses to write unless `PREDICTION_VERSION_OBJECTS` is on too. Switch it back to `off` after the run; objects, rewritten bundles and receipts stay. See the [prediction versions runbook](../runbooks/prediction-versions.md#2-one-time-materialization-of-historical-versions-implemented-no-production-execution-recorded-here).
- `CATALOG_POSTER_HYDRATION=on` only removes the execution gate of `POST /api/enrichment/catalog/posters`; it starts nothing by itself. Each execution call is a separate, owner-approved production operation that makes bounded TMDB detail requests and writes the `poster` field of catalog records in R2 under the resolver lease, so it competes with discovery for that lease and is refused while a chunk holds it. Switching back to `off` refuses further execution calls; posters already written stay, because they are TMDB assets of the verified id. See the [poster hydration runbook](../runbooks/catalog-poster-hydration.md) and [ADR 0020](../adr/0020-owner-triggered-catalog-poster-hydration.md).
- `LETTERBOXD_FACTS=on` changes what the **routine EPG sync writes to R2** on its next run (new `letterboxd/facts/` objects and view-index fields) and stops the films-list scan from clearing ratings by absence; it is a production writer change that needs its own owner approval before the value is set. Switching back to `off` restores the legacy writers for future runs; objects already written stay and are ignored by them.
- `LETTERBOXD_BASELINE_IMPORT=on` only removes the gate of the baseline import route; it starts nothing. Every `commit` or `rollback` against production is a separate owner-approved operation, and the route refuses to work unless `LETTERBOXD_FACTS` is on too, so the routine sync cannot clear imported ratings by absence.
- `FINDS_TITLE_EXCLUSION=on` changes only what Finds show; it writes nothing and starts nothing. It has an effect only once the private list has been placed in R2, which is a separate owner-approved operation ([runbook](../runbooks/finds-display-exclusion.md)). Switching back to `off` shows every film again on the next request; the list object stays until it is deleted separately.
- `FINDS_WATCHED_MARK=on` only shows the «Смотрел» button and opens the owner route; it starts nothing and writes nothing until the owner marks a film. Each mark is an owner-fact write to R2 (`letterboxd/facts/`, the link index and the view-index projection). Switching back to `off` hides the button and refuses new marks; marks already written stay valid facts and keep their films out of Finds. The owner revokes a single mark from the notice right after marking it.
- `PREDICTION_PROFILE_COMPATIBILITY=selective` changes which predictions are shown as current (view, catalog, Finds, coverage), which films the queue and the runner treat as outstanding, and so how much model work the next runs do; it writes no prediction itself, but the runner's `next` repairs index entries of kept predictions. It is a production behavior change that needs its own owner approval and staged activation. Switching back to `strict` returns every consumer to exact equality on its next request and the queue on its next refresh; no record changes.
- `DISCOVERY_LEDGER_MODE=bounded` changes what the **routine EPG commit writes to R2** on its next run: new archive objects and a smaller active ledger. Once an archive exists, the manual scan and canonicalization routes answer `409`. It is a production writer change that needs its own owner approval ([AIR-222](https://trello.com/c/9Y4G9DG6)) after the offline rehearsal ([AIR-221](https://trello.com/c/9ZiVygrd)). Switching to `frozen` is rollback R1: archiving stops, and nothing is rebuilt or deleted. Removing the value later does not restore the single ledger, because `full` acts as `frozen` while an archive exists.
- These switches are **not** Cloudflare Worker Cron settings, external ChatGPT Scheduled Tasks, secrets, API tokens or `wrangler.jsonc` deployment/binding parameters. `BUCKET`, `TMDB_API_READ_ACCESS_TOKEN`, `LETTERBOXD_USERNAME`, and `EPG_XML_URL` are dependencies/configuration, not feature flags.

## Updating this register

Update **contract** rows whenever relevant Worker code changes, with tests/source links in the same delivery. Append or revise an **evidence** entry only after a documented observation: exact setting value (redact secrets), observation timestamp/timezone, source (Cloudflare binding or read-only diagnostic), deployment/version where known, authorizing Trello card, and any confidence limits. Preserve earlier changes as history. Never silently turn a previous observation into a current assertion; never store credentials or confidential runtime payloads here.
