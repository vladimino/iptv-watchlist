## What is stored where

An observation key such as `heat|1995` is a `candidate` row. It is not a `film.id`. `film.id` starts with `film:`. A trusted external id is unique per scheme. `tmdb` holds TMDB movie ids and `tmdb_tv` TMDB TV ids ([ADR 0057](../../adr/0057-tmdb-tv-identity-and-retired-movie-ids.md), Accepted): the same number in the two schemes is two different entries, and `film.canonical_identity` is `tmdb:<id>` or `tmdb_tv:<id>`. A retired movie id stays as an untrusted `tmdb` row whose `provenance_json` has `status: retired`. A redirect keeps the retired id without creating a second Film. `accepted_tmdb_id` on a score does not reference `film`.

A generation has a phase of `published` or `withheld`. `published_generation` is the one current pointer, the same role as `epg/published-generation.json`. Moving it from generation A to generation B leaves A's rows in place. `published_film_show` reads only that pointer, and only when the pointed generation is `published`. `film_generation` is the membership row. Zero `film_show` rows under that membership are an explicit empty show list. A film show keeps `channel`, `epg_title`, `basis`, and `match_reason`, so a `title_duration` showing still explains the cautious mark. `film_epg_last_airing` is a historical fact and is not a show.

`candidate` is the latest observation: title, normalized title, year, raw titles, durations, description, airings, and `confirmed_tmdb_id`. A later broadcast may change that row. `candidate_generation` keeps the `observation_json`, schema version, and `evidence_key` for the generation that was scored, so generation A stays reconstructable after generation B. Shows for that generation stay on `candidate_show`. `confirmed_tmdb_id` does not insert a Film.

`film_metadata.payload_json` is the watchlist and `parseFilm` record: year, runtime, genres, synopsis, poster, and url. `film_person_credit` orders the director and the cast. `film_dimension` remains the lifecycle status and is not that record. `people.json` remains the name cache, not the credit edges.

`candidate_decision` is the AIR-48 decision: status, catalog film id, optional Film reference, TMDB id, identity source, provenance, and the attempt fields. `candidate_decision_history` keeps the decision it replaced. `score_result` is not that decision. A verified or terminal ambiguous decision does not need a score row.

Fingerprint, profile, and prediction bodies stay immutable R2 objects addressed by `r2_key` and `content_sha256`. `prediction_history.payload_json` is the full former prediction, and its `r2_key` names that version. It does not point at the mutable `predictions.json` bundle. A localization conflict keeps `source`, `provenance_json`, and `authority` beside the value and reason.

`identity_assertion`, `identity_rule_version`, and `identity_application` are separate from `film`. No workflow writes them yet.

`import_receipt` records one source key and checksum against one target. The same mapping a second time is a duplicate. There is no shared transaction with R2.

## EPG repository

[AIR-71](https://trello.com/c/UAUUQ2jh) is `src/epg-repository.js`. The Worker bundle does not include it, and it does not open R2 or a production D1 database. The caller passes a database. [AIR-43](https://trello.com/c/7NY6n1Az) still decides whether a score is accepted. [AIR-48](https://trello.com/c/rVf8rRoJ) still decides which observation is current. This module stores the result.

`publishGeneration` writes a new generation's film shows and candidate shows, including an explicit empty list, and the observation snapshot for that generation. A new `published` run must name the generation it succeeds (`expectedProgrammeRunId`, null only when nothing is published). That check is a statement in the same write: a delayed run that still names an older pointer is rejected and writes nothing. Replaying a committed run with the same payload does nothing, and a different payload for that run is rejected. A withheld generation stores its snapshot and shows without changing the latest candidate projection or the pointer. A candidate omitted from a new published generation keeps its observation and decision, loses `seen_in_latest`, and is no longer `current`. An empty show list does not clear `film_epg_last_airing`. When the published evidence key changes, the projection clears its terminal reason, retry time, attempt count, and last attempt time. The decision row stays until a decision for the new evidence is accepted.

`recordDecision` writes only when the published pointer, the generation membership, and the evidence key match, and that predicate is part of the same write. `applied` is true only when that fence still matches and the stored decision equals the input. An identical earlier decision for a candidate omitted from the current generation is rejected. A terminal decision is replaced only when the published generation carries a new evidence key. This is not a historical import. `recordScore` inserts a score in that same write only when both its id and its observation, generation, and scorer version are absent. Considered rows and the detail are inserted only when that statement inserted the parent, so a rejected repeat cannot append them. The call accepts the result only when this id is the stored row and the body matches. `score_result` already has that triple as a table unique key, so a second id cannot commit. An accepted score does not become a verified decision and does not insert a Film. An observation key that starts with `film:` or `person:` is rejected.

One publish, decision, or score is one database transaction. A failed statement leaves the earlier commit in place and does not leave the failed call half-written.

## Canonical repository

[AIR-70](https://trello.com/c/8PRWRx2C) is `src/canonical-repository.js`. It does not open R2 or a database itself. Since [ADR 0056](../../adr/0056-d1-enrichment-write-through.md), the Worker bundle carries it in its own scope for the enrichment projector only. The caller passes a database and the Film or Person view already produced by the lifecycle contract. [AIR-42](https://trello.com/c/drLBuWjl) still decides a link, a reviewed value, and an identity collision. This module stores that result.

**Projector scheduling ([AIR-388](https://trello.com/c/fFvwYLjM)).** The write step of an enrichment projector run is three lanes that share one budget (800 queries, 60 s): Films, Persons and housekeeping (the Film sync clocks, then the absent entities). Each step takes the lane with the lowest spent cost divided by its weight (Films 3, Persons 2, housekeeping 1), the cost being the lane's own queries; a tie goes to Films, so a run begins with the first Film. A Film's own batch starts only inside the budget: the budget is checked between the groups of its Persons and again just before the Film, so a run with almost no budget left writes only that Film's Persons (checkpointed) and the Film follows in the next run; it is never an error. Films a verified archive admitted and D1 never projected go first, and the priority ends once they are projected. A Film's credits reference Person rows, so the Persons a Film needs are written just before it in the same step (in groups of 25). Budget, wall time, window, lease, fences, change keys and cron are unchanged. See the [evidence](../../evidence/d1-migration/air-388-projector-lane-starvation-2026-11-09.md).

**Grouped write path ([ADR 0106](../../adr/0106-bulk-projector-write-path.md), flag `D1_ENRICHMENT_BULK`, off by default).** The repository, its statements, its row format and the change keys do not change; only how the projector calls it. With the flag `on` in a `D1_ENRICHMENT_WRITE=on` run, a Film lane step writes a group and a Person lane step writes a group of up to 25 Persons (`d1EnrichmentGroupCycle`):

0. **Plan generation.** Before the diff the run reads the Film/Person marker (`mode`, `cutover`, `generation`). Absent, unreadable or not `r2`/`prepared` with cutover `open`: the run ends `deferred` (`authority_unavailable`) with nothing written and no diff. Otherwise that generation is the one every group and write batch of the run asserts, so a transition between the diff and a prefetch is refused, not adopted.
1. **Trace.** The repository's own planning runs once against a recording database that answers every read with nothing. The distinct reads it issues (SQL and parameters) are the group's dependencies.
2. **Prefetch, one batch.** The Film/Person authority marker read and, for every traced read, the read itself and its digest (the rows as one JSON text, `json_group_array(json_array(columns))` over the same SELECT) go out as one read batch. A read the digest cannot express (a function call in the column list, `GROUP BY`, `UNION`, more than 99 parameters) sends the group to the per-entity path before any round trip.
3. **Collect.** The unchanged `projectPerson`, `projectFilm` and `projectFilmSyncState` run against the prefetched answers and their writes are collected, with the change-key rows. A read that was not in the trace is a miss, and a miss refuses the group.
4. **Apply, one atomic batch.** The batch holds, in order: the projector lease fence (or, inside a held window, the window fence), the marker assertion (`mode` `r2` or `prepared`, `cutover` `open`, the `generation` the group was planned under), one assertion per traced read that it still digests to what the prefetch saw, the collected writes (a Film's Persons before the Film) and the fence delete. Any difference fails a `CHECK` and rolls the whole batch back. The prefetch and the batch are two round trips and not one snapshot, so no timing is assumed.

A group that is not applied is written by the per-entity path (one fenced transaction per Person group and per Film), so the final rows are the same. The causes: a failed assertion (`guard_refused`), an unseen or undigestable read (`prefetch_miss`, `undigestable_read`), a planning error, a batch over the statement cap (the group is first halved; one Film that still does not fit goes alone), a constraint (a trusted external id another Film of the group takes, a missing Person, a duplicate role id; the batch rolled back whole), an unreadable digest, and an unknown batch outcome (a D1 limit, a network error; the replay is idempotent and the grouped path is off for the rest of the run). A Film with redirects never joins a group, because its link writes depend on rows another item of the group may retire. A lost lease, a lost window or a marker that is no longer `r2` or `prepared` stops the run: nothing more is written through any path and the run ends `lease_lost`, `deferred` with `window_lost`, or `deferred` with `authority_moved`. Every write of a run with the flag on, grouped or per entity, also asserts the marker generation the run was planned under, so a marker that moves stops the run (`deferred`, `authority_moved`) whichever path was writing. With the marker table absent (schema below 13) the run writes nothing: the authority is unknown, never assumed.

The lanes keep their weights (Films 3, Persons 2, housekeeping 1), the tie order and the admitted-first order; with the flag on their cost is the number of statements sent (reads, single writes and batch statements), not queries. The grouped path starts no step it cannot finish: the clock left is the wall budget or the held window's absolute expiry, whichever is first, minus a reserve (default 15 s), and it must cover the longest group seen in the run (5 s for the first). The wall budget is **180 s from the grant** when the grouped path runs inside a held window with the planning marker read, and the 60 s of every other run otherwise (a caller's explicit `wallMs` wins; the value is clamped to the 300 s of the window); the held window's absolute expiry also bounds the per-entity steps, less the reserve, so a late grant leaves the budget it leaves (a grant needs 120 s left) and no step starts inside the reserve. The group size (10 Films, 25 Persons), the statement cap (1,500 per batch), the reserve and an optional run statement budget (a hard cap on the statements sent, the diff's included, enforced by the database adapter during the write phase on every path: a read, a single write or a batch that would pass it is not sent, checked on its actual statement count before submission, and the step it belonged to ends the run without counting as an error; a group is also admitted only if its whole cost fits what is left, the read batch, the write batch and the replay of a refused group, halved until one Film fits) are parameters of the run, not decisions; the query budget (800), the window and its 300 s bound, which includes waiting and release, are unchanged. The run summary then carries `bulk` (see the [monitoring runbook](../../runbooks/monitoring.md#d1-projector-grouped-write-path)).

`saveFilm` and `savePerson` replace the external ids and the dimension rows other than a held localization. Aliases are added to the stored set. A later save does not remove an alias already stored. Credits are replaced only when the call passes `credits`, including an empty list. An omitted `credits` leaves the stored edges. A repeated payload does not add another alias, credit, external id, conflict, or redirect. A stored `reviewed` localization stays in place when the incoming value is weaker. An owner-reviewed value also stays when the incoming value is dictionary-reviewed. That check is part of the write, so a plan that read an older row cannot replace an owner value committed before that write. The rejected value stays as one alias and one conflict. Two records cannot both hold the same trusted external id. The second write is rejected and does not insert that record.

`applyLink` stores the survivor and, in that same transaction, retires the other id: its external ids are released, its aliases, credits, and localization conflicts move to the survivor, its row is removed, and `film_redirect` points at the survivor. Redirects that already pointed at the retired id are retargeted in that same write. A read of either earlier id follows to the surviving film. Watchlist membership moves to the survivor. A film that already belongs to a generation, or that has an EPG last-airing row, is not retired. Replaying the same link leaves the survivor record as it was, including adopted aliases, credits, conflicts, and external ids. A failed statement, including a credit whose person is absent, leaves the previous commit unchanged.

The module does not insert a candidate, a score, a programme generation, or prediction history.

## Prediction repository

[AIR-72](https://trello.com/c/MfAGc1Dd) is `src/prediction-repository.js`. The Worker bundle does not include it, and it does not open R2 or a production D1 database. The caller passes a database and the records already produced. This module does not generate a fingerprint or a prediction, and it does not write a Film, a candidate, or an identity assertion.

The fingerprint body, the taste-profile body, and the current prediction body stay immutable R2 objects. The repository stores `r2_key` and `content_sha256`. `prediction_history.payload_json` is the former prediction record, and its `r2_key` is that version's object. A new profile version does not set `invalidated_at` on the fingerprint. A prediction replaces the current row only when its `updated_at` is later than the stored row, and that write archives the row that is current at commit time. A null stored field still differs from a filled value, so that predecessor is archived once. An older or repeated prediction leaves the newer row and its history unchanged. The same `updated_at` with a different prediction is rejected. A fingerprint pointer is replaced only by a later `generated_at`. A pointer with no `generated_at` stays until a dated pointer replaces it. Another undated pointer with a different hash is rejected. The same hash, including one with no `generated_at`, can still be invalidated, and an earlier or undated pointer does not restore itself. An actual rating is replaced only by a later `recorded_at`. The same timestamp leaves the stored rating in place. A failed statement leaves the previous current prediction, its history, the fingerprint, and the actual rating in place. The view and queue values are derived from those rows. They are not copies of `view-index.json` or the prediction queue, and producing them does not call a model.

None of these repositories run in production.

## Offline importer

[AIR-73](https://trello.com/c/gX2xdQAz) is `scripts/offline-import.mjs` and `src/offline-importer.js`. The Worker bundle does not include them. The command reads one owner-provided snapshot directory, the same manifest and checksum check as `scripts/lifecycle-parity.mjs`, and writes a local SQLite file outside this repository. It does not read production R2, call a model, or apply the schema to a production database.

The report names the snapshot `finishedAt` and aggregate checksum. The read-back streams SQLite's JSON output instead of stopping at the CLI's 1MB capture, so the person table from the historical archive still returns every row. The 19 October 2026 run, including that interruption, is [docs/air-73-offline-run.md](../../evidence/d1-migration/air-73-offline-run.md). Import counts are separate from parity. The expected rows come from the verified source objects, so a unit left out of the write list is still expected. Parity reads the local tables back and compares film title, identity, localization, aliases, external ids, metadata, ordered credits, person name and identity, redirects, fingerprint hash and pointer, ratings, prediction and profile content checksums, prediction history payload, generation membership including a film with no shows, the published pointer, decisions, and candidate evidence. A dropped, extra, or different stored row fails that comparison. `--limit <units>` bounds one run; the units left over are reported as `pending` and the next run resumes from the receipts.

**Identity.** Every stored spelling of a Film id goes through `canonicalFilmId()` from the [domain model](../domain/film-person.md): the catalog form `tmdb_<n>` is `film:tmdb:<n>`, a Letterboxd slug is `film:<slug>`, a canonical id is kept as written. The importer loads that function from `src/domain/film-person.js` and keeps no copy of the rule. An id resolves to a stored Film directly or through that Film's stored redirect to the survivor (`via` `direct` or `redirect` in the ledger); the receipt keeps the source key as written. An id that names no stored Film is **unresolved**, never minted: `film_unresolved` when nothing claims it, `identity_conflict` when two Films or a conflict record claim its TMDB id, `identity_unlinked` when one Film carries the TMDB id but no redirect links the retired id. One exception widens `film_unresolved` for owner ratings only ([ADR-0027](../../adr/0027-owner-rating-tmdb-identity.md)): a rating (`actual.json`) whose Letterboxd id has no Film resolves through the TMDB id of its own `metadata.json` record when exactly one Film holds that TMDB id trusted and without conflict, no other metadata record carries it, the Film holds no other Letterboxd id and gets no other rating (`via` `metadata_tmdb`, with `tmdbId` and `metadataSha256` in the provenance); otherwise it stays unresolved as `film_unresolved`, `identity_conflict`, `identity_unlinked` or `rating_conflict`. The write list and the source projection use the same `ratingIdentity` result. A second exception covers redirect collisions of fingerprints and prediction bundles ([ADR-0029](../../adr/0029-superseded-redirect-payloads.md)): when a stored id resolves through a redirect to a Film that holds exactly one payload of the same family under its own id, both payloads are portable and carry manifest checksums, and the canonical one is strictly newer, the retired payload is `superseded_by_canonical`. It writes no row and takes no receipt, keeps its source key, checksum, time and the canonical `supersededBy` `{key, sha256, at}` in the ledger, and the projection expects only the canonical payload. Otherwise the collision keeps its class A outcome, and the refusal reason (`canonical_missing`, `canonical_ambiguous`, `canonical_unportable`, `source_unportable`, `checksum_missing`, `canonical_not_newer`) is recorded. A bundle without immutable version objects is never superseded. Enrichment objects, programme membership, discovered-film records, watchlist and metadata records and decision `filmId` values all use the same resolution. Two stored Films that claim one trusted TMDB id remain an `identity_collision` conflict in the repository; the generation that lists the colliding Film is a `reference_missing` conflict.

**Evidence.** Discovery items carry no evidence key. The importer derives it with `candidateEvidence()` from `src/discovery.js`, the resolver's own function loaded from the source, and records `derived` on each candidate and decision. A decision with no stored key takes the derived key; a decision whose stored key equals the derived key is `stored`; both are written into the decision's `provenance_json` as `importEvidence`, with `importIdentity` naming how its Film id resolved. A decision whose stored key **differs** from the derived key was taken against earlier airings: it is imported with its own stored key and `importEvidence: "stale_evidence"`, still fenced on the candidate's current key in the published generation, and counted under `provenance.evidence.stale_evidence` ([ADR-0022](../../adr/0022-stale-decision-evidence-import.md)); the runtime treats such a decision the same way. A stored key that disagrees with the derived key on a discovery **item** is a blocker: the run stops before the database is created or written and reports `evidence_mismatch` with the stored and derived values. A decision whose candidate is not in the latest discovery ledger is unresolved (`decision_without_candidate`); the repository only records decisions for candidates of the published generation.

**Coverage.** Every manifest object is `mapped`, `r2_only`, `excluded`, or `unmapped`. Excluded is one declared prefix, `epg/raw/`, the raw EPG dumps that the publication decision keeps as archive: counted, not parsed. No current writer produces XML or an `archive/` prefix, so any other XML-shaped or archive-shaped key is unknown and fails closed rather than being excluded by its name. R2-only keys match a declared family with a disposition stage: derived projections (view index, prediction queue, mood facets, score preview, diagnostics moods, uncertain list; recomputed from rows at the read cutover), runtime coordination (resolver and enrichment leases, continuation record and diagnostics, discovery status and variant plan, `sync.json`, `watchlist-ingest.json`, ratings status, pending and lease, and the removal rating lookup queue `enrichment/removal-rating-lookups.json` (ADR 0043); redesigned at the write cutover), run records (enrichment runs, sources, run and ratings diagnostics, stop and start events, benchmarks, latest run, published ratings and ratings generations; decided before legacy retirement), user state (`started/`, `events/`, `letterboxd/facts/` (Letterboxd fact records and scan summaries, mapped to D1 by ADR-0023 decision 7 in a later migration), `letterboxd/imports/` (baseline import intents, receipts and rollbacks), `ui/filter-presets.json`, `letterboxd/display-exclusion.json` (the owner-approved Finds display-only exclusion list of [ADR-0028](../../adr/0028-finds-display-only-watched-exclusion.md), a curated input the Worker only reads), `admin/owner-reviews.json` (the owner name and title review object of [ADR 0072](../../adr/0072-owner-reviewed-localization-overlay.md); the `people` map is written by the person-name confirmation, and the `films` map is reserved for AIR-53); a D1 home or an explicit stays-in-R2 decision is **required** before any reader serves from D1, so the report lists these families as `decisionRequired`), and archive (generation copies, the before-canonical discovery copies and the discovery archive's write-once source-ledger copy; stay in R2). Discovery archive manifest and segment versions that the published ledger does not name are mapped keys with disposition `unreferenced`, as unreferenced prediction versions are; any other key under `epg/discovery-archive/` is unknown. The immutable fingerprint objects follow the same rule: a body or generation record whose film and hash are the current `fingerprint.json` is `mapped` through that pointer (`via` `fingerprint_pointer`); a valid older generation, or a body whose record write never followed, is `unreferenced` (`fingerprint_version_unreferenced`) and listed in `classes.B.unreferencedVersions`. `fingerprint_payload` keeps only the current pointer; the history stays in R2, where the Worker's `restoreFingerprint` reads it. A key that names a film but breaks either pattern (another hash length, another suffix, a nested path, a version with a leading zero, or a film segment that is not exactly `encodeURIComponent` of its id) is unknown. An `unmapped` key matches no family at all: it is unknown and the import **fails closed** with `unknown_key`, zero writes, exit code 3. The declared prefixes and their dispositions are also tabulated in the [readiness evidence](../../evidence/d1-migration/air-74-backfill-readiness-2026-10-26.md).

**Three classes, never one verdict.** `classes.A` is mapped-domain parity: the read-back, the conflicts, explained, partial and uncheckpointed units, and the mandatory families. The prediction family is mandatory: `classes.A.mandatory.prediction` reports its keys, applied and unportable units, and `blockers` carries `prediction_family_absent` or `prediction_family_unportable` whenever the family is missing or a bundle has no immutable version object; a report can never hide that by leaving predictions out. A bundle record is carried only when its pointer is well formed by the shared rule (the key names the film's own version object and the record's checksum), the object is in the manifest, the manifest checksum of the object's bytes equals the pointer, and the SHA-256 of the bytes the shared rule derives from the bundle record itself equals the pointer too, so record, pointer and stored bytes are one value; otherwise the record is unportable with `prediction_version_object_missing`, `mutable_bundle_is_not_a_version_object`, `prediction_version_pointer_malformed`, `prediction_version_object_absent`, `prediction_version_checksum_mismatch` or `prediction_version_body_mismatch`. A version object some bundle points at is `mapped` through that pointer. One nothing points at was written before a bundle write that never followed: it yields no row, the Worker never deletes it, and it is listed with disposition `unreferenced` in `parity.records` and in `classes.B.unreferencedVersions` rather than hidden; it does not block the parity claim because no row can or should be derived from it. `classes.B` is the R2-only count per family with the stage that must decide it. `classes.S` lists the payloads superseded by their canonical Film (ADR-0029) with counts per family: they are neither a class A gap nor a class C record to acknowledge, and like class C they keep `claimsFullParity` false. `classes.C` is the unresolved identity and source-quality records, each with source key, checksum, reason and the identity resolution that failed; the source objects stay where they are and no row is invented for them. `provenance` counts identities resolved directly, through a redirect or through the rating's metadata TMDB id (`metadata_tmdb`) and evidence keys stored or derived. `receipts` reconciles the receipt table against this manifest, the baseline identity of the run: `matching` receipts name the manifest checksum; `superseded` receipts are older checksums of a source key whose same target table and id also carry a receipt with the manifest checksum, so the revision landed and was read back; `stale` receipts are older checksums with no such receipt, so the revised object did not land; `foreign` receipts name a source key this manifest does not list. Stale and foreign receipts are class A blockers (`receipts_stale`, `receipts_foreign`): a clean read-back alone is not accepted while the database carries rows this baseline cannot vouch for. `claimsFullParity` is true only when every family is present, class A has no blocker, no receipt is stale or foreign, the expected denominator is nonempty, no key is unmapped or unprojected, every record is mapped, the read-back matches, and that run has nothing pending, unportable, unresolved, partial, conflicting, explained, or uncheckpointed. It is the lossless statement and stays false while any class C record exists. Acceptance of a live backfill is a separate judgement: its blocking condition on class C is that the list is complete, explained and acknowledged by the owner (`classes.C.acknowledgementRequired` is true whenever the list is nonempty), and that acknowledgement records a known gap in the acceptance report; it never turns `claimsFullParity` true or makes the backfill a lossless migration.

A receipt is written only after the stored Film or Person matches the unit's title, name, identity, aliases, credits, and localization. A different source checksum does not receipt a row that still has the old value. If the receipt write fails, the run reports `uncheckpointed`; the next run receipts a matching row and re-applies a row that no longer matches. A decision the repository rejects is not receipted. Explicit directors and actors are stored as ordered credits when each person id resolves; a missing or ambiguous person leaves the film partial, with the unmatched count, and a later run can add the edges. Profile versions are applied before the predictions that reference them, fingerprints before predictions, ratings last. The private historical archive is not in this repository. The command reports the checksum and `finishedAt` of the snapshot directory it is given and does not read production R2 to obtain one. Live backfill remains [AIR-74](https://trello.com/c/5AdAmKPe), after [AIR-69](https://trello.com/c/FlcWZX7W).

## Production baseline manifest

`scripts/r2-snapshot-export.mjs` writes the same directory layout and `manifest.json` shape as the historical exporter (`schemaVersion` 1, per-object `key`, `file`, `size`, raw-byte `sha256` and listing `metadata`, listing page count, totals with the aggregate SHA-256, and `changes`), so `verifySnapshot` re-reads it unchanged. It differs in its provenance fields: `sourceSiteId` and `sourceOrigin` are `null`; `source` names the kind `cloudflare-r2-s3`, the bucket, the account id, the endpoint host and that the exporter is read-only; `status` is `consistent_fenced` or `no_go` with `noGoReasons` (`source_changed`, `inventory_changed`, `deletion_observed`, `fence_changed`); `fence` lists each coordination object with its opening and closing ETag and a status (`unchanged`, `absent`, `changed`, `created`, `missing_after`); `baselineIdentity` carries the published `programmeRunId`, the `sync.json` `updatedAt`, the continuation `at` and `hopId`, and the latest enrichment run id, read from the downloaded bytes. The object `metadata` holds the key, size, ETag and `Last-Modified` the listing reported; the S3 API exposes no separate version id, so the ETag is the version a conditional read is pinned to.

`loadLifecycleSnapshot` accepts two source identities: the historical Site archive (`provisional_no_change_detected`), or a production manifest whose `source.kind` is `cloudflare-r2-s3`, whose `sourceSiteId` and `sourceOrigin` are `null`, and whose status is `consistent_fenced` with no NO-GO reason and a passed fence; any other production manifest is refused with exit code 3. The importer report labels a production run `scope: production-baseline`. A manifest whose status is `no_go` is never imported. The procedure is the [snapshot export runbook](../../runbooks/r2-snapshot-export.md).

## Backfill executor

`scripts/d1-backfill.mjs` imports one verified production baseline into the target D1 database through the Cloudflare D1 HTTP API (`--target d1`), or into a local SQLite file with the same rules and report (`--target sqlite`, the dry-run). It never reads or writes R2, never uses a Worker binding, and `wrangler.jsonc` gains no D1 binding. The procedure, limits and evidence template are in the [backfill runbook](../../runbooks/d1-backfill.md).

**Source identity.** The input is a snapshot directory whose manifest the [read-only exporter](../../runbooks/r2-snapshot-export.md) wrote: `verifyProductionSnapshot` re-reads every object, and anything but `consistent_fenced` is a NO-GO before the target is contacted. The manifest's aggregate SHA-256 is the baseline identity of the run.

**Target identity.** The target is named by the environment only (`D1_BACKFILL_ACCOUNT_ID`, `D1_BACKFILL_API_TOKEN`, `D1_BACKFILL_DATABASE_ID`, `D1_BACKFILL_DATABASE_NAME` defaulting to `iptv`). `D1_BACKFILL_SCRATCH_DATABASE_ID` is not read. Before any write the executor requires: the database description returned for the configured uuid carries that uuid and the configured name; every table of the frozen schema v1 exists; and every database identity receipt in `import_receipt` (`source_key` `manifest.json`, `target_table` `database`) names this database id; a receipt for another database id is `database_identity_conflict`. The baseline lineage only moves forward. The newest identity receipt, ordered by `imported_at` (the baseline's `finishedAt`), is the high-water mark: re-running that baseline is allowed; a never-imported baseline newer than the mark is `baseline_changed` and accepted only with `--delta`; re-running an older baseline after a newer one, or importing a never-seen baseline that is not newer than the mark, is `baseline_rollback` and refused whatever the flags, because the executor has no reconciliation path back to an older baseline; two different checksums at the same newest instant are `baseline_ambiguous`. The run then records its own identity receipt with the manifest checksum.

**A unit is one `{sql}` query.** The repositories write each unit as one buffered statement list. `transaction()` sends that list as one D1 query whose body is `{sql}`: the statements joined by newlines. That is the request the scratch measurement exercised ([ADR 0076](../../adr/0076-backfill-single-database-batch.md)). The executor does not send transaction-control statements, does not open a second database and does not create a probe table. The caps are `D1_BACKFILL_MAX_BATCH_STATEMENTS` (default 1,000), `D1_BACKFILL_MAX_BATCH_BYTES` (default 1 MiB) and 100 KB per statement. A unit above a cap is `batch_too_large`: it is never split across requests, because a split unit is not one request. The response shape of that query is one result object per statement. Each object must have `success: true`. A missing or null `success`, or a short result array, is `write_uncertain`. An object with `success: false` is a statement error. `executeRendered` is a separate `{batch}` body used by the metadata-cache operator; it is not this unit, and this contract does not treat that REST body as the Worker binding's batch transaction.

**Receipt lifecycle.** A unit's receipt `(source_key, source_sha256, target_table, target_id)` is written in its own request after the stored rows read back equal to the unit. A write is sent once. If its response is lost, it answers `429` or `5xx`, or a success body does not prove every statement (the request may have committed), the run stops with `write_uncertain`, the identity receipt or a unit alike, and the next run reads the target back, receipts a row that matches (`reconciled`) and re-applies one that does not. Only read requests are retried, a bounded number of times, on `429` and `5xx`; a refused credential stops the run. Every receipt is then audited against this manifest (`matching`, `superseded`, `stale`, `foreign`, as in the offline importer section).

**Fail-closed stop rules.** The executor runs the importer with `stopOn`: the first conflict or uncheckpointed unit stops the run (`unexpected_conflict`); the first unportable class A unit, such as a prediction bundle without a version object, stops it (`class_a_blocker`); the first class C record that is not in the owner's acknowledged list stops it (`unacknowledged_record`). The acknowledged list names class C records only by source key, target table, target id and reason; a class A record is never acknowledgeable. A superseded record (class S, ADR-0029) does not stop the run and is not part of the acknowledged list; every other class A collision still does. Units after a stop are reported `pending` and are not written. `claimsFullParity` keeps its offline meaning and stays false with any class C record, acknowledged or not.

## Staged generation import (schema v2)

The programme generation unit is the one unit the executor cannot send as one request. `publishGeneration` emits `3 + F + F·sf + F + 2C + C·sc + 1` statements for `F` films with `sf` shows and `C` candidates with `sc` shows: about 73,500 to 122,500 statements and 63 to 75 MiB at the production order of magnitude, and its absent-candidate `UPDATE` lists every key (about 710 KB), above the documented D1 limit of 100,000 bytes per statement. Without `--staged-generation` the executor stops at that unit with `batch_too_large`. `scripts/d1-generation-size.mjs` measures the unit for any size without touching R2 or a database ([size evidence](../../evidence/d1-migration/generation-unit-size-2026-10-26.md)).

[ADR-0021](../../adr/0021-staged-atomic-generation-import.md) replaces that unit with a staged import, implemented in `src/generation-stage.js` over `migrations/0002_generation_stage.sql`. The historical scratch measurements stay evidence of those runs; the executor does not open a second database to repeat them ([ADR 0076](../../adr/0076-backfill-single-database-batch.md)):

- **Schema v2.** Migration `0002` adds `generation_stage` (one row per programme run: baseline checksum, phase, `published_at`, expected run, `state`, owner token, the exclusive claim of one execution (`claim_nonce`, the fencing counter `claim_generation`, `claim_expires_at`), planned chunk and row counts, failure reason), `generation_stage_chunk` (write-once receipt per chunk: row count and SHA-256), and `stage_film_generation`, `stage_film_show`, `stage_candidate`, `stage_candidate_show` (the staged rows with their `chunk_index`; stage foreign keys make chunks load in order). It sets `schema_contract.version` to 2 and changes nothing of `0001`. No read path reads these tables. It is applied to no database by this repository.
- **One projection.** `generationProjection` in `src/epg-repository.js` produces the rows both `publishGeneration` and the staged path write, so the two cannot drift.
- **Plan.** Rows are ordered deterministically (films by id, each followed by its shows; candidates by key, each followed by its shows) and cut into chunks of at most 950 statements and 1,000,000 bytes per request, counting the guard, state and receipt statements, and never above the configured batch limits. A staged row whose statement exceeds 90,000 bytes stops the unit with `stage_row_too_large` before any write; a repeated key is refused before any write. Each chunk's checksum covers the run, the chunk index and every row value.
- **Requests.** Open (one statement); each chunk (guard, state, rows, receipt); validate (one conditional `UPDATE` comparing receipts and every staged count with the plan); read-back of every staged row in pages of 5,000, field by field against the plan; commit (12 set-based statements for a published generation, 8 for a withheld one, about 4.4 KB). The commit is the only write to final tables. After it, the executor reads the generation back (equal to the input), and for a published generation checks that the pointer names it, that every staged candidate's projection equals the staged row and that no absent candidate is still current.
- **Stage lifecycle.** `new`, `loading`, `validated`, `published` (committed; for a withheld stage, recorded), `superseded` (a later commit), `failed` (counts or read-back mismatch, or the pointer moved). The owner token is the SHA-256 of the target database id and the baseline checksum: a run of another baseline stops with `stage_baseline_changed`, another token with `stage_owned_elsewhere`, a changed plan (counts, chunking, phase, expected run) with `stage_plan_changed`, a receipt whose checksum differs from the plan with `chunk_conflict`, receipts that are not a prefix with `chunk_receipts_out_of_order`, a failed or superseded stage with `stage_failed` or `stage_superseded`.
- **Resume and uncertain writes.** A write is sent once. A lost response, a `429`/`5xx`, or a success body that does not prove every statement stops the run as `write_uncertain`. The next run resumes at the first chunk without a receipt, re-sends a validation that did not land, and resolves an uncertain commit by reading the final tables: an equal committed generation is a replay, and the unit is receipted as usual.
- **Cleanup.** Only an approved command removes staged rows: `discardStage` deletes at most a bounded number of rows per table per request, children before parents, only for a `failed` or `superseded` stage; it removes a failed stage's row so the run can be staged again, and keeps a superseded stage's row as the record of its commit. `abandon` first marks a never-committed stage failed; a committed stage is never abandoned. Final tables are never touched.
- **Executor.** `--staged-generation` routes the generation unit through the stage. Every run, staged or not, requires schema version 4 (below) on the target (`schema_missing`, `schema_version_mismatch`). The report's `staged` section lists, per generation, the chunks planned, sent and already received, rows, bytes, largest chunk and row, read and write requests, phase durations and the commit's statements, bytes and duration, and `staged.gate` compares the slowest commit with the 10-second budget of ADR-0021.

## Enrichment projector (schema v4)

[ADR 0056](../../adr/0056-d1-enrichment-write-through.md): migration `0004` adds three tables.

| Table | Holds |
| --- | --- |
| `projection_state` | Per projection (`enrichment`), kind (`film`, `person`) and id: the change key of the last input written, or `absent`, and when. |
| `projection_run` | One row per projection: the lease (`lease_id`, `lease_until`, wall clock) and the last run's start, finish, outcome and summary. |
| `projection_fence` | Always empty. Every projector batch inserts the count of live leases held by its run and deletes it again at the end. `CHECK (held=1)` fails the whole batch once the run has lost its lease. |

The repository's projector methods differ from `saveFilm`, `savePerson` and `applyLink` in what they own:

- **`projectFilm`** writes the identity and metadata dimensions only, never fingerprint or prediction. On a watchlist Film it keeps the stored `person:tmdb_*` credits the R2 roster does not list. They are appended after the R2 credits of their role in their stored order, in the same batch.
- **`projectFilm` with `redirects`** (the redirects a Film carries when the view has linked it to another stored Film). The trusted external ids are unique over all Films (`film_external_id_one_trusted`), and the Film a link retires still holds the ids the survivor now carries. So `projectFilm` first plans every redirect the way `projectLink` does (the redirect must target this Film, must not repeat a stored redirect to another target, and the retired Film must have no generation and no EPG history; any of these refuses the whole write, with its own reason), then accepts as owners of the Film's trusted ids only the Films those redirects retire that have not been retired before, deletes their external ids, and writes the Film, all in the caller's one transaction. An owner no redirect names, a retired Film with history, or a redirect to another Film still refuses the Film, and nothing is written. A Film whose trusted id is held by a Film the view does not link is refused with `identity_collision`: retiring it would drop facts only D1 holds, so it is a decision for the owner, not a rewrite. When the Film a redirect would retire holds D1-authoritative prediction-domain facts (a row of `candidate_decision`, `candidate_decision_history`, `fingerprint_payload`, `prediction_current` or `prediction_history`; none of them moves with a retire and the rows that reference the Film refuse its delete), `projectFilm` throws `duplicate_film_retained` (an error with `code` and the names of the tables that hold the rows) before anything is written. The projector reads that as a skip on purpose, not a failure: the catalog Film and every row of it stay as they are, no redirect is made, the Letterboxd Film is not written, it gets no checkpoint (so it is planned again on every run and when its input changes), `writtenFilms` does not count it and the run is not `partial` because of it. The run summary names it in `retainedCount` and `retainedFilms` (at most 20 entries of `id`, `reason` and `held`). It is classified only by this exact condition: a foreign key of any other table, an unrelated owner of a trusted id, EPG history on the retired Film and every other error stay refusals with their own error. Owner decision of 10 November 2026: prediction, fingerprint and candidate facts are not moved or merged for these Films. ([AIR-405](../../evidence/d1-migration/air-405-identity-collision-fix-2026-11-10.md).)
- **`projectLink`** works like `applyLink` with the same ownership, inside the caller's transaction. It may be given the other Films the same write retires (`releasing`), so that a Film with several redirects is accepted by each link. Adopting the credits only the retired Film holds, a role with any ordinal already taken on the survivor moves all of them by one shift after the survivor's highest ordinal; a role with none keeps its ordinals.
- **`projectPerson`** works like `savePerson`, inside the caller's transaction.
- **`releaseFilm`** removes only the watchlist membership of a Film no source lists. It skips a redirected id. A Film the view still contains is not released. That includes a Film admitted by a watchlist boolean after the current lists dropped it ([ADR 0086](../../adr/0086-durable-watchlist-film-retention.md), Accepted). The projector marks absent only a stored Film the view does not contain. When the view still contains an admitted lid that is on neither current list and has no usable metadata, `projectFilm` updates `watchlist_film` only if the Film row already exists. It does not delete credits, `film_metadata`, external ids, or identity and metadata dimensions, and the sync-clock pass leaves `film_sync_state` unchanged. A missing Film row is still inserted.

None of these methods reads back.

A projected `film_metadata` row has `r2_key` `metadata.json` and `content_sha256` NULL: it comes from a live read, not from a pinned object version. A row the reload wrote keeps the snapshot object's checksum until the projector rewrites it.

The projector fails closed on its R2 inputs. Missing, malformed or unpublished inputs stop a run before any write. A live writer, or an object whose etag changed during the reads, defers it. It also holds a run with more than 25 absent Films or 250 absent Persons (`absent_guard`), or more lost watchlist memberships than the larger of 5 and 2 % of the members (`membership_guard`). See [ADR 0056](../../adr/0056-d1-enrichment-write-through.md).

**TMDB retirements** ([ADR 0057](../../adr/0057-tmdb-tv-identity-and-retired-movie-ids.md)). The projector also reads the optional R2 object `identity/tmdb-retirements.json`, under the same etag fence, and the lifecycle reader applies it ([contract](../domain/film-person.md#runtime-projection)). No schema change:

- **Absent.** One `GET` of the key returns nothing, and the head check repeats it. The view, the change keys and the writes are as before. An object that appears during the run defers it (`input_changed`).
- **Present and valid.** A corrected Film's change key changes once, and its batch writes the untrusted retired `tmdb` row, the trusted `tmdb_tv` row, `canonical_identity` `tmdb_tv:<id>` and the identity dimension. The same batch keeps the D1-only `person:tmdb_*` credits as for any watchlist Film. Predictions, ratings, redirects, aliases and localization are not touched. Later runs over unchanged R2 are no-ops, and a later metadata refresh does not undo the correction.
- **Invalid as a whole** (bad JSON, schema, entry or a duplicate). The run stops before any write, with `outcome: failed`, `reason: input_invalid`, `inputKey: identity/tmdb-retirements.json`.
- **Held Film** (review, see the contract). It is neither written nor released, also when it has left every R2 source (`film_missing`): its D1 rows, watchlist membership and change key stay as they are until the review settles, and the membership guard does not count it. The summary carries `tmdbRetirements: {valid, applied, held, reasons}` (at most 20 entries each) whenever the object exists.
- **Rollback.** Deleting the object makes the next run write each Film's previous identity back from the records.

The same enrichment projector writes it when `schema_contract.version` is 5, 6 or 7 and the table exists. There is no new flag and no new cron. `metadataSync` does not read the table. While the schema v6 marker is `r2` or absent, the clocks still come from `metadata.json`.

| Column | Holds |
| --- | --- |

| `metadata_at` | The `metadataAt` string from `metadata.json`, or NULL when that clock is missing or empty. |
| `synopsis_fetched_at` | The `synopsisFetchedAt` string, or NULL. |
| `people_names_version` | The integer `peopleNamesVersion`, or NULL when the value is not an integer. The integer 2 means the name attempt finished. |

`people_version` stays on `film_metadata`. The 30-day window is not a column. Reviewed titles and reviewed names stay on `film_dimension` and `person_dimension`. `titles.json` and `people.json` are inputs to those dimensions and are not copied here.

For a Film row that exists, no sync row means `metadata.json` has no entry for that Film. The entry is matched by the Film id (`film:<slug>`, or `film:tmdb:<n>` as `tmdb_<n>`) or by the Film's stored `letterboxd` external id. A row of NULLs means the entry exists and its clocks are absent. Deleting the entry deletes the sync row and stores the sync change key `absent`. Releasing a Film removes watchlist membership only. The sync row stays while the cache entry stays, and a later change to that entry is still written. The Film row stays. A `metadata.json` key with no Film row does not create a Film and does not create a sync row.

**How the projector reads the checkpoints ([AIR-395](https://trello.com/c/RbPf1nPj)).** The format and the meaning of a `projection_state` row do not change. The diff must know whether D1 already holds each entity's fresh change key. For a view of at least 5,000 entities it asks D1 for one digest per bucket of the stored keys (bucket: kind and a hash of the last four **UTF-8 bytes** of `'0000'` followed by the id, the same integer arithmetic over `hex(substr(CAST(... AS BLOB),-4))` in SQL and over `TextEncoder` in JavaScript, so the database and the Worker place every id in the same bucket whatever its characters, and an id shorter than four bytes still has one; digest: the count and two 32-bit sums of the hash part, the last 28 characters, of every key that is not `absent`) and compares it with the same digest computed from the fresh keys. A bucket that agrees holds exactly the view's entities with their fresh keys and no other live entity; only the buckets that differ are read row by row, and the unchanged plan function runs over those entities and rows. A collision of a changed key needs both 32-bit sums to agree, about 2^-64 for one change (accepted by the owner on AIR-395); a backlog (many more entities in the view than rows in the table), more than 40 % of buckets differing, a smaller view or a key of another shape read the whole table as before. Two further checks keep a disagreement about the mapping from going unnoticed: a fresh id that is not well-formed UTF-16 (a lone surrogate, which the database stores as U+FFFD) is not bucketed, and a digest row without a valid bucket name, or a row read for a differing bucket whose JavaScript bucket is not a differing one, shows the two sides disagree; each reads the whole table and says so in the summary (`skipped` `unsafe_id` or `bucket_mismatch`). A misplaced id could in any case only add differing buckets, because both of its buckets then hold a count that does not match; it could hide a change only through the same checksum collision as above. Nothing is written or indexed differently.

The sync change key is a second `projection_state` projection, `metadata_sync`, kind `film`. ## Canonical Film/Person authority (schema v13)

[ADR 0099](../../adr/0099-canonical-film-person-d1-authority.md) (Accepted): migration `0013` adds the foundation of a canonical Film/Person authority. It is **in the repository and not applied in production**; applying it is a separate owner-approved operation, and applying it changes no authority.

- `film_person_authority` (`id` = 1; `mode` of `r2`, `prepared` or `d1`; `cutover` of `open` or `held`; `generation`; `held` only with `d1`). States: `r2` (the projector is the only writer), `prepared` (a verified baseline, R2 still authoritative, the projector still the only writer), `d1`/`open` (only the fenced mutations write), `d1`/`held` (a freeze: writers refuse and readers fail closed, never back to R2). Triggers allow only `r2`→`prepared`, `prepared`→`r2`, `prepared`→`d1`, `d1`→`held` and `held`→`d1`, one generation each, a move out of `r2` needs a verified baseline (a verified baseline cannot be reopened while the marker is `prepared` or `d1`, so both stand on a verified one), and the row cannot be deleted. - `film_person_cas` is the batch fence. Every assertion is an upsert of `ok` = 1 or 0 whose value also requires the fence row to exist when the statement runs, so a missing row fails the CHECK and rolls the batch back (a zero-row `UPDATE` would pass silently); a trigger also refuses deleting the row, and the assertions do not rely on it. `film_person_baseline` (`state` of `empty`, `loading`, `verified`; `reference`; `updated_at`) moves only `empty`→`loading`→`verified` and back to `loading` while the marker is `r2`; a partial (`loading`) baseline cannot become `prepared`.
- `canonical_revision` (`kind` of `film` or `person`, `id`, `revision` from 1): the per-entity revision. An entity with no row has revision 0 and each fenced mutation moves it by exactly one. The enrichment projector does not write it.
- The migration inserts the marker as `r2` / `open` / generation 0, copies no row and writes no Film or Person. From schema 13 on, a missing table, row or fence, a malformed marker, a read error and a held or unreadable marker fail closed. Before 13 (no table) the behaviour is the legacy one.
- The fenced mutations (`src/canonical-mutations.js`) and the marker reader (`src/film-person-authority.js`) are **not bundled into the Worker**; nothing calls them. They refuse in every state but `open`, prove the generation and every touched entity's expected revision in one atomic batch, never renumber credits (keyed upserts; the D1-only AIR-286 credits survive), never write localization, dimensions, metadata, the watchlist link, a fingerprint or a prediction, and merge films with a redirect whose target is not itself a redirect. A merge never drops the retired Film's data silently: a row the survivor lacks is moved and an identical one is dropped; different metadata, identity, metadata-lifecycle, fingerprint or prediction rows, a reviewed or owner localization the survivor would not keep, and a sync-clock row the survivor does not cover refuse the batch (`film_person_data_conflict`) unless the caller chose a side for that kind (`resolve.metadata`, `.identity`, `.metadataState`, `.localization`, `.fingerprint`, `.prediction`: `survivor` or `retired`; `.sync`: also `newest`, the field-wise newest non-null clock), reported in `discarded`; an automatic retired localization yields to the survivor's and is recorded as a `localization_conflict`. A retired `film_sync_state` row is dropped only when it adds nothing (each clock null or covered by the survivor's, and the survivor's metadata body stands); a missing row and null clocks differ (ADR 0070).

## Durable canonical write receipt (schema v19)

[ADR 0119](../../adr/0119-durable-canonical-write-receipts.md) (Accepted; [ADR 0117](../../adr/0117-film-person-d1-handoff-owner-decisions.md) owner decision 5), [AIR-374](https://trello.com/c/ha7ais3w) P2c: migration `0019` adds `canonical_write_receipt`, one row per cross-domain canonical operation (EPG, Discovery, metadata, ratings, admission, retention into canonical Film/Person). It is **in the repository and not applied in production**; it follows a **complete version 18** (the first statement inserts a second `schema_contract` row and so aborts the file on anything else), creates an empty table, writes no row and moves no authority. Applying it to production D1 is a separate owner GO with its own preflight and readback.

- **Key and content.** `request_id` is the stable idempotency key the caller derives from the source event (identifier characters only, at most 200). `operation` and `origin` are lowercase identifiers (the code-reviewed set is `OPERATION_KINDS` in `src/canonical-receipts.js`). `target_kind` (`film` or `person`) and `target_id` name the entity. `content_digest` is the SHA-256 of the planned content, `planned_revision` the entity revision it was planned against and `applied_revision` the revision after it applied (set only when `applied`). `marker_generation` is the marker generation at plan time.
- **State.** `pending` (an attempt may be in flight; `next_attempt_at` is its deadline), `applied` (terminal), `failed` (a definite rollback; `next_attempt_at` is the earliest retry), `unknown` (outcome not known; `next_attempt_at` is the earliest readback), `abandoned` (terminal: attempts exhausted, expired or a permanent refusal; needs repair). `attempts` is 1 to 16 and moves only with a new attempt; `error_class` is a short lowercase code, never a message. **No payload, title, name or personal data is stored.**
- **Fence.** Triggers allow an insert or update only while `film_person_authority` is `d1`/`open`, and an insert only under the live `generation`; at `r2`, `prepared` and `held` the table stays empty or frozen. A new attempt carries the live generation, other moves keep the planned one. The legal moves are `pending` to any state, `failed` to `pending`, `applied` or `abandoned`, `unknown` to `pending`, `applied`, `failed` or `abandoned`; identity columns never change; rows are never deleted (pruning is not decided).
- **Indexes.** `(state, next_attempt_at)` serves the bounded reconcile read; `(target_kind, target_id, applied_revision)` serves `unreceipted` detection.
- **Activation baseline (three insert-only tables, built so a failure is retryable).** `canonical_receipt_baseline` (one row per entity: `kind`, `id`, `revision`), `canonical_receipt_watermark` (one row: the boundary marker generation, the entries total and, per kind, the count and highest revision) and `canonical_receipt_baseline_seal` (one row: the per-kind SHA-256 digest of the ordered (id, revision) pairs, the committed pointer, written last). `recordBaseline` copies `canonical_revision` in ONE fenced batch with a single SELECT and inserts the watermark computed in SQL from the copied rows (a trigger refuses a watermark that disagrees with them; the batch asserts the cap and is one transaction, so a failure leaves nothing); the seal is then computed from the immutable copied rows and, if it fails, is completed by calling `recordBaseline` again. Baseline rows are only insertable before the watermark and while the marker is `d1`/`open`; the seal only after the watermark; a receipt cannot be inserted until the seal exists. `verifyBaseline` recomputes everything read-only. A `canonical_revision` at or below its baseline entry is `pre_receipt_baseline`: it predates receipts, is counted apart and is never `unreceipted` nor retrospectively receipted. Capacity: at most 5,000 rows, expected 0 at the planned boundary; above it `recordBaseline` refuses (`baseline_over_capacity`).
- **Retention.** Append-only during initial stabilization: no TTL, pruning, cleanup or archival; rows are never deleted and terminal rows never rewritten; `listAttention` lists abandoned and unknown receipts. A retention/lifecycle decision is not made; growth and cost must be measured first.
- **Reads.** `readUnreceipted` verifies the baseline and lists `canonical_revision` rows ABOVE their baseline entry whose current revision has no applied receipt with that applied revision (`unreceipted`); it is non-clean for any such change and for a baseline that does not verify, and it refuses without the baseline. `src/canonical-receipts.js` is not bundled into the Worker and nothing calls it.
- **`receiptMark` on the fenced writers (AIR-374 P3-0a, dormant).** `mutateFilm`, `mutatePerson`, `writeFilmFacts`, `recordPersonState`, `recordLocalizationConflicts`, `recordLocalizationSources`, `admitRatedFilm`, `retainFilm` and `recordRetirementDecision` take an optional `receiptMark` `{requestId, attempt, now, target:{kind,id}}` (the values `receiptedWrite` hands to `run`, plus the clock). Without it a writer is unchanged. With it the writer appends the two `appliedStatements` to its OWN batch AFTER the revision bump; they sit on top of `MUTATION_STATEMENT_CAP` (the writer's own statements stay capped at 60, the tail is at most 2), and a receipt that is not this attempt's pending row rolls the whole mutation back. The applied update matches the STORED row, not the mark: `request_id`, `state='pending'`, `attempts`, the stored `target_kind` and `target_id` (the entity the writer bumps), `planned_revision + 1` equal to the entity revision after the writer's bump (the receipt never claims a revision other than the one this batch produced; a retry re-plans `planned_revision` to the current revision first, so the rule holds on a retry too) and the stored `marker_generation` equal to the live marker generation (already proven equal to the writer's generation by its own fence statement). Any mismatch updates no row, `changes()>=1` fails, and entity data, revision and receipt roll back together. A mark whose target is not the entity the writer bumps is refused with `film_person_invalid` before any statement; nothing is written unless the marker is `open`. A writer that finds nothing to write (replay, already stored) opens no batch and does not apply the receipt: the receipt ends `unknown` (`atomic_mark_missing`) and is settled by readback, never by a second batch ([owner decision E5 of 12 Nov 2026](../../runbooks/film-person-holdpoint-decision-pack.md)); skipping a no-op BEFORE the receipt is created is the producer adapter's job (P3-0b). `mergeFilms` is not covered (two entities, no producer). The parameter is named `receiptMark` because `admitRatedFilm` already takes the Letterboxd `receipt` entry as `receipt`. Nothing passes a mark yet.
- **Producer receipt adapter and the `origin` filter (AIR-374 P3-0b, dormant; [ADR 0123](../../adr/0123-producer-receipt-adapter-film-facts.md)).** The closed operation kinds gain `film_facts` (one `writeFilmFacts` call, target: that Film); the SQL column is unchanged, so there is no migration. `listReceipts` and `reconcileReceipts` take an optional `origin` (a lowercase identifier, validated before any statement, applied in SQL so another origin never uses up the limit). `src/canonical-producer-adapters.js` (not bundled, imported by nothing, no call site) pre-plans with the writer's own planner and creates NO receipt for a no-op (E5), builds the request id from the source event, the target and the content digest (never the content alone; the digest drops the write clocks `at` and `updatedAt`), applies the facts through `receiptedWrite` in atomic mode, and reconciles only its own origin (the adapter is dormant; schema 19 itself is already applied in production, 12 Nov 2026; a readback may declare a moved source as a typed terminal abandon, ADR 0123 decision 5) inline, at most 10 due receipts per call, with no cron and no global pass (E2). A race that leaves nothing for the writer to write ends the receipt `unknown` (`atomic_mark_missing`), never a second marking batch. The table stores no payload, so a replay needs the producer to re-plan the facts from its own source.
- **What `applied` proves.** A production adapter applies the receipt inside its own fenced batch (`appliedStatements`, atomic mode, required); structured request evidence (`{requestId, target, appliedRevision, contentDigest}`, validated by the module against the receipt) settles an exception-gated legacy receipt; a content digest alone never does ([ADR 0119](../../adr/0119-durable-canonical-write-receipts.md)).

The view `tmdb_retirement_current` gives each Film's latest decision: **there is no implicit un-retirement**, only a `restore` row moves a Film back, and a later `retire` is a new owner decision. `film_id` is not a foreign key (the history outlives a Film row), so a Film merge refuses while the Film has a decision.
- The table holds decisions only; it does not write `film_external_id`, the canonical identity or the identity dimension. Applying a decision (the retired `tmdb` row untrusted with `retired` provenance, the trusted `tmdb_tv` row, the canonical identity) belongs to the producer integration of AIR-371 behind the fenced mutation boundary of schema 13.
- `src/tmdb-retirement-decisions.js` is **not bundled into the Worker** and nothing calls it. `recordRetirementDecision` validates its input before any SQL, refuses unless the marker is `open`, proves the marker generation and the Film's revision in one batch, appends exactly one row and moves the revision. A `retire` is held (refused, nothing written) when another Film trusts the TV entry (`retirement_tv_collision`) or the retired movie id (`retirement_movie_on_other_film`), the Film has no `tmdb` row for the retired movie id (`retirement_movie_missing`), or it trusts another TMDB id (`retirement_identity_mismatch`); the same checks run inside the batch. `prepareRetirementImport` is the pure, prepare-only loader of the R2 object: it validates the body exactly like `tmdbRetirementSet` (tested for parity) and returns decisions with deterministic request ids, so a second load is all replays; it reads and writes nothing. `compareRetirementImport` is the compare-only classification (`same`, `missing`, `restored`, `differs`, `extra`). The actual load is a separate owner-gated step of AIR-373.

## Projector window (schema v18)

[`migrations/0018_projector_window.sql`](../../../migrations/0018_projector_window.sql) ([ADR 0103](../../adr/0103-projector-exclusive-window.md)) adds one table, `projector_window`, with one seeded row: `id` 1, `state` one of `idle`, `requested`, `held` (`idle` has no `owner`; the other two have an `owner`, a `requested_at` and a positive `expires_at`), `owner` (the projector's lease id), `requested_at` and `expires_at` (epoch milliseconds, one absolute deadline for `requested` and `held` together, never extended; an expired row is idle for every reader and writer). It follows a complete version 17 and refuses anything else before the table is created; the version becomes 18 and never goes down. It writes no Film, Person or Discovery row. The file was applied to production on 2026-11-08 ([apply record](../../evidence/d1-migration/air-383-0018-apply-2026-11-08.md)). The Worker treats an absent table as no window, so a deploy before the file is applied changes nothing, and applying it changes nothing until the owner sets `D1_ENRICHMENT_WINDOW`.


## EPG diagnostic database (separate D1, not part of this chain)

[`diagnostic-migrations/0001_epg_diagnostic_identity.sql`](../../../diagnostic-migrations/0001_epg_diagnostic_identity.sql) ([ADR 0121](../../adr/0121-epg-diagnostic-rehearsal-design.md), AIR-453) is the schema contract of a **separate** diagnostic D1 that the owner provisions later (AIR-456). It is not in `migrations/`, `wrangler.jsonc` names no migration directory for it, and a deploy never applies it, in particular never to the production database `iptv`. The diagnostic database holds the production chain of migrations (schema only, so the real seal path, the EPG step lease and the Discovery and published-EPG fences find their tables) followed by this file, which adds one table, `epg_diagnostic_identity` (`id` 1 only, `domain` = `epg-diagnostic`, `resource_id`, `created_at`). The matching R2 record is the object `diagnostic/identity.json` of the diagnostic bucket. `src/epg-diagnostic.js` refuses every write until both name the same `resourceId`, and `provision` writes the identity only into a database that holds no row beyond the singleton rows the migrations seed and a bucket that holds no object. Nothing in this repository creates, binds or applies either resource. The seeded singleton list in `src/epg-diagnostic.js` must grow with any migration that seeds a row (`tests/epg-diagnostic-context.mjs` applies the whole chain and provisions, so an omission fails CI).

`diagnostic-migrations/0002_epg_diagnostic_receipt.sql` (AIR-455, [ADR 0124](../../adr/0124-epg-diagnostic-canary-run-contract.md)) adds the durable receipt of the canary, `epg_diagnostic_receipt`: `idempotency_key` primary key (an atomic reservation), `fingerprint` of the immutable configuration, deterministic `instance_id` (unique), `status` (`reserved`, `created`, `running`, `complete`, `failed`, `stopped`), `slot` (1 while active, NULL otherwise, with a CHECK that ties it to the status and a unique index, so at most one active canary), `config_json`, `report_json`, `failure`, `revision`, timestamps. Like 0001 it is outside the production chain and never applied by a deploy. The table is empty at provisioning, so `provision` accepts it.
