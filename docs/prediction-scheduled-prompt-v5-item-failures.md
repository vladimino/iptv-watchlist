# Почасовые прогнозы «В эфире» — continuous drain с item-level retry

Это полный текст инструкции для существующей Site-aware задачи «Почасовые прогнозы «В эфире»». Сохрани её текущую привязку к сайту и почасовое расписание Europe/Madrid. Не создавай другую задачу и не меняй расписание.

## Доступ и неизменные правила

В начале получи Sites get_site для сайта appgprj_REPLACE_ME. Используй current_live_url и siwc_bypass_bearer_token только для запросов к этому сайту. Передавай токен заголовком OAI-Sites-Authorization: Bearer <token>; не записывай его в URL, файлы, сообщения, output или Events.

Проверь GET /api/enrichment/runner, GET /api/enrichment/schema и GET /api/enrichment/profile. Серверный runner contract — источник истины для текущего протокола. Эта инструкция заменяет прежнее правило «ошибка любого item → завершить run». Если get_site, current_live_url, token, schema или profile недоступны, уведомь с конкретной стадией и безопасной краткой причиной. Не генерируй данные без актуального профиля и схемы.

Не меняй Taste Profile, fingerprint semantics, prediction rules или правила оценки. Не запрашивай и не используй actual rating целевого фильма. Переиспользуй актуальные сохранённые fingerprints и predictions. Повторный эфир не делает prediction stale. Совместный model batching выключен: модельные результаты рассчитывай по одному фильму.

## Запуск и single-flight

POST /api/enrichment/start с JSON {"scope":"watchlist_all","mode":"queued","trigger":"scheduled"}, без фиксированного batchSize. Если фактический остаток usage доступен, можно передать capacity.remainingPercent; неизвестное значение не выдумывай.

- already_running: штатный успешный no-op. Сразу закончи этот trigger, не присоединяйся к чужому runId и не вызывай для него next, submit, heartbeat или complete.
- busy: временная блокировка записи. Повтори запрос с небольшим backoff; не запускай конкурентную обработку.
- noop: успешная пустая проверка, закончить silent.
- blocked: очередь сохранена, сервер сообщил причину; это не пустая очередь. При реальной quota/API/storage причине уведомь о стадии. retry_backoff означает отложенные повторные попытки, не аварию модели.
- running: сохрани собственный runId в памяти текущего исполнения и начинай непрерывный drain.

Lease серверный, атомарный и persistent, TTL 60 минут. POST /api/enrichment/heartbeat с {"runId":"..."} перед model call; если один call длится долго, продлевай heartbeat параллельно каждые 10 минут. Submit также продлевает lease после checkpoint. При lease_lost прекращай запись: не присваивай чужой run и не создавай дубли. Если среда убила процесс без cleanup, сохранённые результаты остаются, следующий trigger заберёт lease после TTL.

## Непрерывный цикл

1. POST /api/enrichment/next с {"runId":"..."}. Сервер выбирает текущий adaptive batch и заново применяет urgent hot → остальные hot → допустимый cold/background. Используй серверный размер; не вводи ограничение общего количества фильмов или длительности run.
2. Для каждого возвращённого item выполняй только requiredWork. prediction_only использует переданный сохранённый fingerprint. fingerprint_and_prediction использует metadata и текущую схему. Если доказательств качества недостаточно, следуй существующим правилам unknown/confidence; не заполняй поля выдуманными фактами ради прохождения валидации.
3. Сразу после каждого результата POST /api/enrichment/submit с {"runId":"...","items":[{"filmId":"...","fingerprint":{...},"prediction":{...}}]}. При prediction_only fingerprint можно не отправлять. Не накапливай весь batch перед checkpoint.
4. После обработки item и batch снова вызывай next. Один run проходит сколько угодно последовательных adaptive batches до исчерпания eligible работы или настоящего системного stop condition.

При сетевом сбое на submit повтори тот же payload с небольшим bounded backoff и проверь результат: запись идемпотентна. Не генерируй прогноз заново только потому, что HTTP-ответ на checkpoint потерялся.

## Ошибка одного фильма — продолжить

Malformed JSON, отсутствующие обязательные поля, неверный тип, значение вне схемы или другая ошибка разбора/валидации ответа ОДНОГО фильма — retryable/item-level failure, а не причина завершать run.

Если локальный parser не смог получить валидный результат, не отправляй сырую строку модели и не делай malformed HTTP JSON. Отправь нормальный JSON-отчёт:

{"runId":"...","items":[{"filmId":"...","failure":{"kind":"parse_error"}}]}

Для разобранного, но невалидного ответа можно использовать kind validation_error. Можно также отправить разобранный fingerprint/prediction обычным submit: серверная валидация сама классифицирует ошибку.

Сервер сохранит failure с scope item и retryable true, увеличит failed, оставит фильм без нового успешного prediction в очереди, назначит retryAt и исключит его из дальнейших попыток этого run. Уже сохранённый валидный fingerprint переиспользуется при повторе. Backoff: 1 час, затем 2/4/6 часов при повторных неудачах. Retry state сохраняется сразу, не только при завершении run. Повторная отправка того же failure не увеличивает счётчики второй раз.

Если submit сообщает retryable_failure, failureScope item и mustComplete false: продолжай следующий item, затем следующий batch. Не вызывай complete с parse_error/validation_error из-за одного фильма. Не зацикливайся на повторе этого же фильма внутри текущего run.

## Системная остановка и нормальное завершение

Останавливай run только при настоящем системном условии: фактическая quota, недоступный model/API/storage, потеря lease, изменение профиля/контракта, мешающее безопасной записи, или подтверждённый сервером format_error_storm. Сервер определяет storm как пять ошибок формата подряд у разных фильмов; успешный item сбрасывает последовательность. Одна ошибка или отдельные ошибки в разных batch не являются storm.

Если next или submit возвращает mustComplete true, вызови POST /api/enrichment/complete с собственным runId и возвращённым stopReason. Не продолжай generation после системного stopReason. При настоящем внешнем quota/model/API/storage error сообщи complete короткую безопасную причину, когда доступ ещё позволяет это сделать, затем проверь GET /api/enrichment/status. Не включай в причины сырые ответы, секреты, hashes или prompt noise.

next stopReason queue_empty означает, что работа исчерпана. eligible_queue_empty означает, что доступная этому run работа исчерпана, но отдельные failed/deferred фильмы остаются на будущий retry. В обоих случаях complete с соответствующим stopReason — нормальное завершение; наличие item-level failed counter не означает «проход прерван». Не утверждай, что вся persistent queue равна нулю, если hotRemaining/coldRemaining ещё положительны.

## Events и уведомления

Не создавай пользовательское событие после каждого item/batch: сервер агрегирует прогресс примерно каждые 30 минут или 50 успешно сохранённых predictions и пишет отдельное финальное событие.

Item failures показываются в обычном прогрессе: «добавлено: 48 · не удалось: 2». «Проход прерван» допустим только при run-level остановке. При нормальном eligible_queue_empty сообщается, что фильмы с ошибками сохранены для повторной попытки.

Успешный run, штатный already_running/noop и завершение с отложенными item retries — silent. Уведомляй только о реальном системном сбое, с конкретной стадией, безопасной причиной и оставшимися hot/cold счётчиками, если они доступны. Никогда не выводи токены, heartbeat-технические детали, hashes или текст внутренних prompts.
