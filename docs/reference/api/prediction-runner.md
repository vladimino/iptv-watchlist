# Prediction runner

Batch runner v2 is the only prediction runner protocol ([ADR 0122](../../adr/0122-prediction-batch-runner-v2-dual-protocol.md), [ADR 0167](../../adr/0167-retire-prediction-runner-v5.md)); its contract is [Batch runner v2](#batch-runner-v2) below. The same protocol serves manual and scheduled triggers. ChatGPT reaches it through the MCP tools in [MCP](mcp.md): `enrichment_runner`, `prediction_batch_start`, `prediction_batch_manifest`, `prediction_batch_validate`, `prediction_batch_hold`, `prediction_batch_submit`, `prediction_heartbeat` and `prediction_complete`. `GET /api/enrichment/runner` publishes the live contract (`protocol: "batch_v2"`, `retiredProtocols: ["v5"]`, the `batchRunner` limits). The external ChatGPT Scheduled Tasks are managed independently of deploying this Worker contract; always verify their live state and do not change them without owner approval.

**Retired one-film runner v5.** `POST /api/enrichment/start`, `POST /api/enrichment/next`, `POST /api/enrichment/submit` and the MCP tools `prediction_start`, `prediction_next`, `prediction_submit` and `prediction_validate` are removed. A removed route answers the Worker's `404 {error: "Not found"}`; a removed tool is the JSON-RPC error `-32602 Unknown tool`. Neither writes anything. Run records v5 wrote stay readable: their `protocol` is absent or `"v5"`, the v2 submit, hold and manifest answer them `409 {code: "wrong_protocol"}`, a live lease they still hold turns a batch start away with `already_running`, an expired one is settled by the next batch start, and `heartbeat`, `complete`, diagnostics, history and Events keep reading them. Predictions require `prediction_domain_authority.mode` `d1`: with `r2` the batch start refuses `batch_runner_requires_d1` and no runner writes predictions.

**Shared runner rules.** A 12-minute lease (`leaseTtlMs` 720000 in `enrichment_runner`; 15 minutes until the [AIR-588](https://trello.com/c/vyxbU1l0) containment of 24 Nov 2026) stores owner/runId, heartbeatAt, expiresAt and the ownership `epoch`: set when a run acquires or takes over the lease, kept by every renewal, heartbeat, checkpoint and release, and incremented by the next acquire. A renewal that loses the compare-and-swap to another write of the lease is read again and retried up to three times; it is `lease_lost` only when the lease read afterwards names another holder, has another epoch or has expired. When the lease is still this run's and alive after the attempts, the answer is `409 {status: "busy", reason: "lease_contention"}`, a retryable answer that is not a stop. With the marker `d1` the compare-and-swap is the D1 row token. Expired owners cannot submit. Renew `POST /api/enrichment/heartbeat` before long model calls and at least every 5 minutes during one (every start, hold and submit also renews the lease, so the TTL bounds the silence between calls, not the length of a run). A per-film failure is persisted as a retryable item failure with a 1-hour exponential retry (maximum 6 hours) and never ends the run. Progress Events aggregate the run; the final event is separate. A formed response does not prove the client received it: send or read `X-Request-Id`; the same id is returned as `requestId`. On an external or systemic stop, `complete` may include `fault` (`origin`, `failedStep`, `providerErrorCode`, `httpStatus`, `receivedRequestId`); omit `fault` when the cause is unknown, and a fault on a normal completion is rejected ([run diagnostics](run-diagnostics.md)).

## Run completion, drained queue, eligible and deferred work

Four observations are kept apart. **Run completion** is `status: complete` (or `partial` when a stop reason or a still-pending selected film remains); a run that ends with item failures deferred to a retry is `complete` with `failed > 0`, not an error. **Drained** means the refreshed queue has no outstanding film: `complete` stores `stopReason: queue_empty` only when `hotRemaining + coldRemaining` is zero after its final queue refresh, whatever reason the caller sent. **Eligible** is the subset of outstanding films the runner would take now (`queueReadyIds`: the hot lane while any *non-exhausted* hot film is outstanding, otherwise the cold lane, minus films whose stored `retryAt` is in the future and minus films whose stored `attempts` is at least 10); when work remains but none of it is eligible, `complete` stores `eligible_queue_empty`. **Deferred** films are the outstanding films held back by a retry timestamp. **Retry-exhausted** films have ten saved per-film retryable failures (`attempts >= 10`); they leave the pending lanes, stay in `retries` for diagnostics, and are never selected until an owner-approved reset (not this contract). They are not counted as predicted. A batch start on a queue that is outstanding but not eligible answers `retry_backoff` instead of opening a run. The completion Event and the footer status publish these counts as `snapshot.queue` / `predictions` (`outstanding`, `eligibleNow`, `deferredByRetry`, `retryExhausted`, `nextRetryAt`, see [the footer and Event slices](enrichment.md#failure-behavior)); the retry time of a film is not the time of the next scheduled run.

## Queue writes

A confirmed [scoped recovery intent](admin-actions.md#scoped-prediction-recovery-intent) ([ADR 0165](../../adr/0165-scoped-prediction-recovery-intent.md), Accepted) is not a queue writer. The freshness rule reads the active intents (one D1 read batch per call) and treats a film's exact denied version as not current; the rebuild stamps `recoveryRevision` (and `recovery {revision, activeIntents, denied}`), and the advance gate of `start` and of the batch v2 preflight answers `recovery_changed` when the revision moved, so the next start rebuilds the queue the ordinary way. Denied films carry `work.reason = recovery_intent`. Without migration `0024` nothing of this applies and the queue carries no stamp. A batch selection reserves a share of the manifest for these films: see [Recovery slots](#recovery-slots-in-the-manifest).


`enrichment/prediction-queue.json` has several writers ([ADR 0064](../../adr/0064-prediction-queue-conditional-writes.md), Accepted 2026-10-31):

- the runner routes (`start`, `next`, `submit`, `complete`);
- the EPG commit tail (`programme_updated`) and the EPG scan (`epg_scan`);
- the profile publication (`profile_updated`);
- the resolver checkpoint (`resolver_checkpoint`);
- `POST /api/enrichment/queue/reconcile` (`manual_reconcile`).

Every write is conditional. Until the schema v7 marker is `d1`, the condition is the etag of the object the writer read (`etagMatches`, or `etagDoesNotMatch: '*'` when absent). When that marker is `d1`, the condition is the D1 generation read with the document, and the object is written afterwards as a mirror. On schema version 7 or newer while this domain is installed and the marker is still `r2`, the writer advances `generation` and records an intent, including the hash of the bytes it is about to put, before the object put. It deletes that intent only after the put returns. A put that throws leaves the intent. A queue or lease write reads the marker again immediately before the put. A head captured while these tables were absent does not put once the marker is `d1`. A load, activation or release that still sees the intent does not copy, flip or reopen writers. A later contract with none of the prediction tables stays on the objects. A partial set of those tables fails the write and does not use the object. With `PREDICTION_DB_REQUIRED=on`, a missing `DB` binding or a bound database without `schema_contract` fails closed. Migration `0007` is applied; it does not lower a higher contract version. The retry, the five attempts and `prediction_queue_conflict` are the same in both modes ([ADR 0078](../../adr/0078-d1-authoritative-prediction-domain.md)).

- **A runner step advances the stored queue; it does not rebuild it** ([ADR 0113](../../adr/0113-prediction-runner-advances-persisted-queue.md)). `next`, `submit` and `complete` read the stored queue and use it as it is while it passes the advance gate: valid shape, the same profile hash and version, fingerprint schema, fingerprint and prediction prompt versions and fingerprint registry digest. A different `programmeRunId` is not a gate failure ([ADR 0154](../../adr/0154-prediction-eligibility-independent-of-epg.md)). A queue that fails the gate is rebuilt. `submit` removes the films it wrote (`created`, `recalculated`, `already_current`) from the queue's lists, `priority`, `work` and `retries` and recomputes the counters (`priorityCount`, `coldRemaining`, `urgentCount`, `coldWithoutPrediction`, `hotPredicted`) in one conditional write (`trigger: batch_progress`, `advancedAt`); a replayed submit settles nothing twice. The metadata of a new batch is read by id (watchlist programme, then `readAdmissionsById`: indexed `film_id` lookups in chunks of 80, current rows only, no generation compare), never from the whole catalog; a listed film whose admission is gone is settled out of the queue and replaced (in `start` as well as `next`; with nothing left `start` answers `noop`). Every settlement repeats the advance gate on the queue the conditional write mutates, so a queue rebuilt for another generation after the step's read is not changed by it; a `start`/`next` selection that cannot settle missing admissions answers `503 {status: "blocked", reason: "queue_changed", code: "prediction_queue_changed"}`. A `submit` whose prediction already committed still returns its per-film result, even if its queue settlement lost the race; a later refresh reconciles the queue. `complete` preserves the newer queue's `lastBatch` and counters and adds only the run's own retries. `compatibility`, `fingerprintCompatibility` and `discovery` are statistics of the last rebuild until the next one. A film admitted mid-run reaches the queue through the named refresh (EPG tail, resolver checkpoint, profile update, reconcile), and a normal `queue_empty` means empty as of the last rebuild.
- **A rebuild** (`refreshPredictionQueue`, its `trigger` stored on the queue) reads the queue first and its inputs after it. When the stored queue names another programme generation than the caller's programme, the rebuild uses the published programme. `retries` of films still outstanding, plus exhausted records (`attempts >= 10`) even if the film left the catalog, `lastBatch`, `lastCheckAt` and `metrics` come from the queue just read. Exhausted identities are omitted from `hotPending` / `coldPending` / `pending` and do not raise `hotPredicted`. At most 500 exhausted records are kept, newest `failedAt` first.
- **The stored form** is plain JSON while it fits 900000 characters and the `dict1` encoding above that ([schema](../data/d1-schema.md#prediction-domain-schema-v7)). Readers always receive the plain document. A refusal carries `code: prediction_domain_budget` and a `guard` naming the limit that refused (`queue_chars`, `overlay_rows`, `statement_bytes`, `bind_limit`, `history_limit`, `mirror_list`); on the EPG commit it appears as `enrichmentQueueError: prediction_domain_budget:<guard>`. The encoded text starts with `dict1:`, so a Worker build without `dict1` support fails closed with `prediction_domain_unavailable` on that queue and cannot rebuild it: only a build that supports `dict1` can rewrite the queue as plain.
- **The derived view index** (`PredictionD1.derivedIndex`, called by `derivedViewIndex` in `src/worker.js`; the only view index, with no read selector, [ADR 0192](../../adr/0192-retire-view-index-selector-and-raw-object.md)) reads `prediction_fingerprint` and `prediction_pointer` in keyset pages of 300 rows ordered by `film_id` and builds an entry for every film id in either table. Its cost follows the number of D1 rows. It refuses (`prediction_domain_not_authoritative`) unless the prediction marker is `d1`, and with `prediction_domain_budget` (`guard: overlay_rows`) above the 20,000-row cap per table, returning nothing. See the [view index contract](../domain/view-index-read-model.md).
- **A step reads and writes each object once (AIR-442).** `next` and `submit` carry a request scope, created per request on the step's own copy of the environment and never shared with another request. It holds only what the step itself read or wrote: the run record, its diagnostics row and `latest-run.json` are read at most once and written through; a write of bytes identical to the value the step already knows is skipped (the first save of a steady-state `next` is identical to the stored record, and so is then `latest-run.json`, which the step's own final save rewrites); the runner lease value the step just wrote, and the queue counters it last read or wrote, are what the diagnostics row reports, so a scoped step reads neither the queue nor the lease from storage for its diagnostics. The queue mutation of a step (`batch_progress`, the settlement of `next`, the completion) starts from the head `currentPredictionQueue` read for that queue object instead of reading it again; the write stays conditional on that head (the object etag, or the D1 queue generation when the queue is D1-authoritative), and a conflict retries from a fresh read. `submit` writes no view-index entry: the view index is derived from D1 at read and has no stored object any more ([ADR 0192](../../adr/0192-retire-view-index-selector-and-raw-object.md)), so the whole-index reads and writes that [AIR-442](../../evidence/prediction/air-442-r2-roundtrips-2026-11-11.md) measured are gone. Authority objects are never answered from the scope: the queue, the leases as fences, the film files and the immutable bodies are read and written as before, and the lease renewals, the writer lease and every conditional write are unchanged. On the offline fixture (one film per step, twelve selected) a steady-state `next` makes 43 R2 calls (before 55) and a `submit` 31 (before 41), as measured on 11 November 2026 before the raw view index was retired. The stored result is the same as before ([evidence](../../evidence/prediction/air-442-r2-roundtrips-2026-11-11.md)).
- **One start reads each large input once.** The queue rebuild of a start hands its programme, catalog, view index and profile to the batch selection and to the start event, so the catalog and the index are not read again in the same request. The start answer is a few kilobytes: the run summary, counters and the runner contract, never the queue, the index or film metadata.
- **Discovery chunks do not reach the runner.** A fenced catalog read (`discovery_fence`: the Discovery generation moved between its statements) is repeated up to three times inside a rebuild; `next`, `submit` and `complete` do not read the catalog at all while the stored queue passes the gate, so a Discovery chunk cannot fail them. `start` always rebuilds; if the catalog is held or all three reads are fenced and the stored queue still passes the gate and is not older than 12 hours, the run starts on it and the answer carries `queueStale {reason, ageMs}`. An Event snapshot whose programme, catalog or view index cannot be read has `snapshot.coverage: null` and `delta.predictionGain: null`; it never computes coverage from a missing catalog. `enrichment/status` reads no catalog (`selectedCount` is `hotCount + coldCount` of the queue, or the watchlist count without a queue) and reports `discoveryStatus: "unavailable"` with `discovery: null` when the Discovery status record cannot be read.
- **A catalog held by an EPG publication.** While the Discovery authority is held, or loading as a catalog replacement, the catalog cannot be read and a rebuild cannot run. A `loading` **ledger seal** (an EPG publication moving the ledger: the transfer is `loading` for another programme or over retiring rows, and no admission is pending; [ADR 0091](../../adr/README.md)) is not a hold since AIR-574: the by-id admission lookups and the catalog read stay open under it, so a `start` whose films were already selected from the consistent queue runs and is not refused by the gate (before AIR-574 the global gate refused it with `discovery_incomplete` and 0 films after a successful preflight). The by-id admission reader closes the same bounded read fence as `routeRead` (programme, transfer epoch, and the seal classification; Discovery generation-only progress is not a fence), so a catalog replacement, an ABA through `loading` or a programme change between its statements is a typed `discovery_fence` and never a transient absence that a refresh could settle out of the queue; a genuinely revoked admission under a valid seal is still a real absence. A pending admission under `loading` and a `loading` transfer that is not a ledger seal answer `503 prediction_catalog_held` with `cause: discovery_incomplete`. A real (non-dry-run) `start` refused with that 503 leaves one neutral `batch_v2_skipped` Event with `reason: catalog_held` and the `cause` ([ADR 0190](../../adr/0190-catalog-held-start-is-a-skipped-event.md), AIR-575): the recorder writes only that Event and its outbox entry, invents no run and no stop Event, returns the original 503 unchanged, and states nothing about effects the start had before the refusal (a keyed start's own claim, acquired and released; a guarded queue settlement made by the queue refresh, ADR 0188). The `502 discovery_unavailable` of a held cutover and a dry run write no Event. A held cutover (`cutover` not `open`) is refused by `readAuthority` itself ([ADR 0162](../../adr/README.md)) with `502 {error: "discovery_unavailable"}`, not the 503: nothing is delivered, and no run, manifest or live lease remains; the `held` branch of the start gate is defensive only. A keyless `start` checks the authority before it takes the runner lease; a keyed `start` ([ADR 0188](../../adr/README.md)) first holds its own short claim of the lease and releases it, owner-fenced, on every refusal here, so no refusal leaves a live lease, run or manifest. It answers `503 {status: "blocked", reason: "catalog_held", code: "prediction_catalog_held", cause}` with `cause` `discovery_fence` or `discovery_incomplete`. A rebuild that meets the same refusal after the lease was taken releases the lease and gives the same answer. `next`, `submit` and `complete` of an owned run answer the same 503 only when a step that really needs the catalog (a rebuild after a programme, profile or contract change, or the by-id read of a new batch) is refused with those codes: they keep the runner lease, do not stop the run, and include `leaseTtlMs` (15 minutes). A later identical `submit` of a film already written in that request is `already_current` (no second version or history row); the 503 body carries `results`, `committed` and `identicalSubmit: "idempotent"`. `complete` does not persist a completed run or Event while the catalog is held. A `discovery_fence` outside `queue_refresh` stays `502 storage_error`. The caller retries the same step with the same `runId` at most for one lease TTL, with heartbeat; if still held, it leaves the run for ordinary lease expiry and does not `prediction_complete`. The live ChatGPT Task prompt does not yet name this wait (see [AIR-424 evidence](../../evidence/prediction/air-424-next-discovery-fence-2026-11-10.md)); this page does not edit that prompt.
- **A failed boundary** (`start`, `next`, `submit`, `heartbeat`, `complete`) still answers `502 storage_error`. The Worker also writes one log line `{"event":"prediction_boundary_failed","boundary","stage","code","guard","kind","requestId","runId"}`. `stage` is the first named step the error crossed (`settle_previous`, `runner_lease`, `writer_lease`, `queue_refresh`, `film_state`, `run_save`, `runner_started`); on `next`/`submit`/`complete` a catalog hold is `queue_refresh`. `code` and `guard` are the error's own and are reported only when they are plain identifiers, otherwise `unknown`. The line carries no message, stack, film id or body.
- **A recorded change** is the submit's per-film retry, the start's idle check (`lastBatch` with `runId: null`) or a stopped run's missing retries. It is applied to the queue just read and never creates an absent queue.
- **The completion** writes its retries, `lastBatch`, `lastCheckAt` and `metrics.hotProcessedTotal` inside its own `batch_complete` write (a mutation of the stored queue, which also settles every successful film of the run once more). The counter moves only when `lastBatch.runId` is not yet the run, so a repeated completion counts once.
- **A retry record only grows while its film is outstanding.**
  - `attempts` is the larger of the run's count and the stored count plus one, and only for a retryable per-film `parse_error` / `validation_error` / `validation_failure`. A `storage_error`, run-scoped stop, `deferred_budget` or `needs_regeneration` does not increment it.
  - Ten saved attempts exhaust automatic selection ([ADR 0152](../../adr/0152-prediction-retry-attempt-budget.md)).
  - `retryAt` is the latest of the run's time, the stored time and the backoff of that count.
  - A record whose `lastRunId` is the run is written once.
  - The completion and every stop add any *per-film retryable* failure of the run that the submit did not land (below).

  The submit answer and the run record follow a merged record that came out larger.
- **On conflict** the writer re-reads and starts again, at most 5 attempts with a short jittered pause. Exhaustion throws `PredictionQueueConflictError` (`code: prediction_queue_conflict`), and nothing of the caller's is written.
  - The reconcile route answers `409 {error, code: "prediction_queue_conflict"}`.
  - A runner route ends through its ordinary error path as a `storage_error` stop.
  - The EPG commit tail records `enrichmentQueueError` and completes the commit.
  - The resolver records `prediction_queue_checkpoint: …` in its status.
  - The profile publication stands; the next rebuild picks the new profile up.
- **A put that throws** is an unknown outcome. It is not repeated, and the error propagates. A lease holder's `beforeWrite` renews before every attempt, so a lost lease writes nothing.

**A run's retries survive a queue write that fails.** A queued run's per-film failure is saved on the run record, with `retryHeal: "pending"`, before the submit writes it to the queue. The mark is cleared only by a queue write that confirms every failure of the run.

- **At the stop.** Every stop writes the run's missing retries again before it marks the run `partial` and releases the lease. This covers a `storage_error` stop after a submit conflict and a `complete` with a systemic reason. A normal completion writes them in its `batch_complete` rebuild. A write that still fails keeps the mark. The stop answer then carries `retryHeal: "pending"`.
- **At the next start.** A released or expired runner lease keeps naming its last run. Before acquiring the lease, `start` reads that run. If the run is still marked, `start` writes its retries to the queue first, in a recorded change with trigger `start_retries`. When that write fails, `start` selects nothing, takes no lease and answers `503 {status: "blocked", reason: "retry_heal_pending", code: "prediction_retry_heal_pending", pendingRunId}`. This is a start outcome, not a stop, because no run exists to stop. No run record, stop record or Event is written, and `latest-run.json` keeps naming the marked run. Only the start's own diagnostic row records `blocked`. The lease keeps naming the marked run, so every later start tries again.
- **Unknown outcome.** A write with an unknown outcome is not repeated blindly. The next attempt re-reads the queue, and a record that already carries the run's `lastRunId` is left as it is.
- **No queue object.** If the queue object is absent, the retries cannot be confirmed, and the mark stays until a rebuild creates the queue.

The queue format, the retry policy, hot-first selection and batch sizing do not change. Tests: `node tests/prediction-queue-cas.mjs`.

Run counters and film outcomes persist after each submission. Current-batch film reads stay bounded; completed batches are counted from saved outcomes rather than loading every completed film on every next request.

Which films are outstanding after a taste-profile change is decided by the queue rule in [prediction compatibility](../domain/prediction-compatibility.md#prediction-queue): the selective profile rule, with no switch ([ADR 0044](../../adr/0044-retire-profile-compatibility-switch.md)). The runner's own checks (pending count, completion, `already_current`) use the same rule, so a kept prediction is never recalculated.

Tests: node tests/continuous-drain.mjs; node tests/queue-compatibility.mjs; node tests/fingerprint-migration-queue.mjs; node tests/throughput.mjs; node tests/enrichment.mjs. The multi-batch integration test uses an isolated R2 implementation and deterministic validated model outputs; it is not a production LLM throughput benchmark.


## Step timing line

Every `batch/start`, `batch/submit` and `batch/hold` writes one log line `{"event":"prediction_step_timing", ...}` after it answers (`step` is `batch_start`, `batch_submit` or `batch_hold`); `heartbeat` and `complete` do not. Each holds the request's authority-marker scope (below) only until its own first database write. It is observation only: the Worker's environment is replaced for the length of the step by a copy whose R2 bucket and D1 database time each call and forward it unchanged, so no call is added, reordered, retried or awaited differently and the answer, the leases and the compare-and-swap writes are those of an uninstrumented step ([evidence](../../evidence/prediction/air-438-step-latency-and-batch-sizing-2026-11-11.md)). A failure of the timing code is swallowed and never changes the outcome.

| Field | Meaning |
| --- | --- |
| `step`, `requestId`, `runId`, `status` | The step (`batch_start`, `batch_submit` or `batch_hold`), the request id the answer carries, the run id (`null` when not a safe token) and the HTTP status (`0` when the step threw) |
| `wallMs` | The step's wall time as the Worker sees it, including the lease, the diagnostics appends and the answer |
| `busyMs` | The **union** of the intervals of every R2 and D1 call: calls that run in parallel are counted once |
| `overlapMs` | By how much the sum of the calls' times exceeds `busyMs` (parallelism) |
| `unattributedMs` | `wallMs` minus `busyMs`: the awaits and scheduling between calls, and any compute the clock sees. The Workers clock advances across I/O and not during synchronous execution, so compute reads as zero: on 11 November 2026 `unattributedMs` was 0 in every line while the platform's `cpuTimeMs` for the same invocations was 0.4 to 1.6 s ([evidence](../../evidence/prediction/air-441-d1-round-trips-2026-11-11.md)). Read CPU from the invocation record, not from this field. Always reported, never folded into a stage |
| `r2` | `n` operations (a `get` that reads its body counts twice: the answer, then the `body`), summed `ms`, `busyMs`, `bytesIn` (approximate for a string: characters) and `bytesOut` (object size at a body read) |
| `d1` | `n`, `ms`, `busyMs`, `statements`, `batches`, `rowsRead`, `rowsWritten` (from the answers' own metadata, never a new read) |
| `classes` | Per class `{n, ms, maxMs, bytes, ops}`. R2 classes (`r2:other` is the exception since AIR-471; the bulk is now named): `r2:epg_generation`, `r2:sync`, `r2:profile_version`, `r2:catalog`, `r2:events`, `r2:diagnostics` (run diagnostics rows), `r2:run`, `r2:run_latest`, `r2:profile`, `r2:lease`, `r2:film_state`, `r2:film_other`, `r2:source`, `r2:view_index`, `r2:queue`, `r2:programme`, `r2:diagnostics`, `r2:list`, `r2:other`. D1 classes: `d1:<table>` from the table name in the statement's static SQL text (up to 60 characters of `[a-z0-9_]`), `d1:batch` for a batch, `d1:other`. At most 40 classes |
| `notes` | Whitelisted counters: `bodyItems`, `created` and the other per-film counters of `batch_submit`; `manifestFilms`, `manifestBytes` (`batch_start`, when it delivered or measured a manifest); `batch_start` also `preflights` (selection passes of the start: 1 for a refusal or dry run, 2 on a current queue, 3 after a refresh), `refreshRounds`, `scannedFilms` (films read across all passes), `settledFilms`, `leaseRefused` (1 when a live lease turned the start away, at the early check or at the acquire), `leaseRefusedAtAcquire` (1 when a competing start won the lease after the early check) and `liveLeaseAgeMs` (time since the live lease was last written, from its `heartbeatAt`, so it stays exact for a lease written under an earlier TTL; estimated from the expiry minus the current TTL only when the lease has no `heartbeatAt`; correlates a repeated start with the run it met). Since [AIR-588](https://trello.com/c/vyxbU1l0): `claimChecks` (stage-boundary checks of a young claim made by a read, below) beside `claimRenewals`; `orderingDeferred` (1 when the start delivered from the stored queue instead of rebuilding it for ordering drift, [ADR 0204](../../adr/0204-prediction-ordering-drift-leaves-the-start.md)) and `orderingDeferredWindow` (1 when that drift was a window edge); `answerBytes` (the bytes of the answer actually delivered) and `envelopeAnswer` (1 when it was the compact envelope, [ADR 0205](../../adr/0205-batch-start-compact-ready-envelope.md)). Counters only, no id, key or payload |
| `stages` | ([AIR-471](https://trello.com/c/rFBAixZe), extended by [AIR-553](https://trello.com/c/ouMIBO00)) sequential sections `{stage, ms, r2, d1}` (wall time and the R2 and D1 calls that finished inside), from the closed list `preflight`, `turned_away`, `idle`, `settle_previous`, `catalog_gate`, `queue_refresh`, `preflight_refreshed`, `runner_lease`, `preflight_lease`, `persist`, and, since AIR-553, `event_delivery` (the outbox drain of an authorized start), `manifest_ready` (the manifest write and the deferred readiness edit) and `terminal_event` (the run's terminal write and its Event delivery in `complete`) (at most 16; `idle` can appear twice). Stages are exclusive: a stage that runs inside another (`event_delivery` and `manifest_ready` inside `persist`) is subtracted from the outer one. The steps `batch_prepare` (the Workflow preparation of a deferred start), `batch_manifest` (a part readback), `batch_heartbeat` and `batch_complete` now emit their own line, so every phase of a Task cycle (receipt, preparation, readback, submit, heartbeat, complete, delivery) can be measured in production without added storage calls |
| `truncated` | Present and `true` when the interval list (4,000) or the class list overflowed; the totals stay exact |

The line never holds a film id, a key, a statement, a body, a fingerprint, a prediction or a model output. An R2 class is a name from a closed vocabulary; a D1 class is a table identifier, never a value. Percentiles are not computed in the Worker; they are read from the logs ([runbook](../../runbooks/prediction-operations.md#reading-the-step-timing-line-air-438)).

**`batch_start` cost (AIR-471).** A start reads the marker through the request's authority scope of AIR-441 for its read-only passes only: the scope is dropped before the idle outcome, the settlement of the previous run, the queue refresh, the lease acquire and the post-lease preflight, so every write and the revalidation that fences the run see the marker afresh (a concurrent genuine change still ends as `queue_changed`; a drift proven to be only a re-rank does not, AIR-542: one rebuild per start, then the start continues on the last safe queue or rebases once onto the post-lease preflight when every non-priority field of the queue, the per-film `work` classification and its set of films are unchanged, see the runbook). The queue refresh and settlement look at the first `manifestSize` films the manifest would hold, not at a default 100, and the freshness check of a film reads its fingerprint and its **current** prediction without the replaced versions (no lineage query, no body per replaced version); the manifest and its hash are unchanged. The selected films' state and metadata are read again after the lease is taken. Offline counts are in the [evidence](../../evidence/prediction/air-471-batch-start-latency-2026-11-14.md); production p95 is a later measurement.

**Request-scoped reuse and lease writes (AIR-588, A1).** Inside the same request scope a **schema-shape probe** (a plain `SELECT` whose every named table is `sqlite_master` or `schema_contract`, without a comment or a comma-joined `FROM` list) is read once and its answer reused (as a copy) until the next authority boundary (`forgetRequestAuthority`, called before every fenced stage of a start), an `exec`, a DDL statement or a batch the scope cannot classify; ordinary writes keep it, because only an owner-run migration changes the schema. Every authority **marker** row (this domain's through the AIR-441 rule above, every other domain's own) is read as before, and every fenced write still carries the generation it read. Each domain module asked these probes before its marker, about a hundred times per start in production. A claimed synchronous start (a Task's labelled or keyed start) checks a **young** claim at a stage boundary by a read of the lease (same run, epoch, alive) when its last write is less than 30 s old, and renews it otherwise (the claim lives 180 s); its persist checks a young gate (less than 20 s since its last renewal; the gate lives 60 s) by a read, as the deferred preparation already did. A lost claim or gate is still seen at the next check (`start_claim_lost`, nothing committed). Each remaining lease write keeps its one non-authoritative R2 mirror PUT; there are fewer writes. Offline on the built bundle (S7): runner lease mirror PUTs 13 to 6, schema probes 36 to 8, D1 calls 172 to 131 ([evidence](../../evidence/prediction/air-588-start-latency-offline-2026-11-24.md)).

**Authority marker reads.** `readPredictionAuthority` asks for the schema contract, the table list and the `prediction_domain_authority` row in **one D1 batch**; any refusal of the batch falls back to asking them one at a time, with the old classification of failures. Inside a batch step, and only there, the answer is then held for the request until its own first database write: `PredictionD1.scopeRequest` wraps that request's database, shares a read that is in flight, and drops the answer when the request's own database does anything but a plain read: only a single `SELECT` with nothing before it is one; a `WITH`, a `PRAGMA`, a commented or multi-statement text, a statement the scope did not prepare, a statement run, a batch that is not all such reads, `exec` and a session's write all drop it. The scope lives on the request's database object. Every other route, the cron tick, scripts and the next request read the marker afresh, and no write depends on the held answer: each carries the generation it was read at in its own fenced batch, so a marker that moved fails the write closed (`prediction_domain_cas`) and the failed write drops the held answer. What the hold can miss is a routed **read** after an external change of the marker, for at most the length of the request. The historical round-trip measurement of the retired v5 steps is in the [evidence](../../evidence/prediction/air-441-d1-round-trips-2026-11-11.md).

**Batch sizes the contract has.** A batch start selects at most `manifestSize` films (1..100, default and ceiling 100); a batch submit, hold or validate takes 1 to 10 items and at most 56 KiB. The limits are published in `batchRunner` of `GET /api/enrichment/runner`.

## Batch runner v2

**Status.** This section is the contract of [ADR 0122](../../adr/0122-prediction-batch-runner-v2-dual-protocol.md) as extended by [ADR 0136](../../adr/0136-prediction-batch-manifest-size-and-spent-complete.md) (optional client `manifestSize` and normal `manifest_spent` completion) and narrowed by [ADR 0167](../../adr/0167-retire-prediction-runner-v5.md) (the only protocol). Nothing here enables or authorizes a run, a dry run or a Scheduled Task change. Sizes marked *initial* are staged defaults subject to later measured gates, not measured limits ([sizes and limits](../../evidence/prediction/air-446-batch-runner-limits-2026-11-12.md), [manifest size measurement](../../evidence/prediction/air-447-batch-start-manifest-2026-11-12.md)).

v2 uses the queue, runner lease, retry records, fingerprint and prediction storage and D1/R2 write order the retired v5 runner used. A run has `protocol` `"batch_v2"`; a stored legacy run has `"v5"` or no `protocol`, and `batch_submit`, `batch_hold` and `prediction_batch_manifest` refuse it with `409 {code: "wrong_protocol"}`. One lease serves every run: a second `batch_start` while a lease is held answers `already_running` and the caller stops without adopting the `runId`.

`GET /api/enrichment/runner` publishes `protocol`, `retiredProtocols`, the `batchRunner` block (`version`, `protocol`, `start`, `submit`, `hold`, `manifestFormat`, the limits, `requires.predictionAuthority: "d1"`) and the item failure and validation vocabulary; `pipelineVersion` stays 5 because it names the stored run format.

**Flow.** `batch_start` (once, optional `manifestSize`) → repeat { generate up to `generationSize` films, `batch_submit` 1 to 10 items } until the selected manifest is spent, a `mustComplete` or `action: "complete"` answer → `complete` with reason `manifest_spent` when every selected film is settled while ready films may remain (ADR 0136). `heartbeat` and `complete` are the existing routes. At most `manifestSize` films per execution (default and ceiling 100).

### `POST /api/enrichment/batch/start`

Request: `{scope: "watchlist_all", mode?: "queued", trigger: "scheduled"|"manual", capacity?: {remainingPercent}, manifestSize?: integer 1..100, dryRun?: boolean, pin?: {filmIds: string[1..manifestSize]}, answer?: "full"|"envelope"}`. `answer` (AIR-588, [ADR 0205](../../adr/0205-batch-start-compact-ready-envelope.md)) chooses the shape of a real start's answer; omitted is `full` ([compact ready envelope](#compact-ready-envelope-adr-0205)). `manifestSize` omitted → **100** (ADR 0122 compatibility); invalid → `400`, no writes. `pin` is accepted only with `dryRun: true` and must not exceed the effective `manifestSize` (no silent truncate). Capacity is reported as in `start`: `remainingPercent: 0` stops the start as `blocked` with reason `quota` (no run, the lease released); any other value does not shorten a manifest. `generationSize` / `submitBatchSize` are client/prompt parameters and are never derived from `manifestSize`. A body that does not match answers `400`. The prediction authority marker must be `d1`; with `r2` the start answers `409 {status: "blocked", code: "batch_runner_requires_d1"}` and writes nothing.

Answer `200 {status: "running", runId, protocol: "batch_v2", dryRun: false, lease {expiresAt, ttlMs, epoch}, limits, manifestSize, filmsSelected, manifestFormat, manifestHash, profile, contract, films, queueRefreshed, queueSettled?, eligible {hot, cold, ready}, skipped {missingAdmission, alreadyCurrent}, pendingCount, hotRemaining, coldRemaining, queueStale?}`:

#### Recovery slots in the manifest

([ADR 0197](../../adr/0197-recovery-slots-in-the-ordinary-batch-manifest.md), Accepted.) An unpinned `batch_start` (a real start, a dry run and the queue refresh's own settlement window) reserves a share of the manifest for films with an active, unexpired, owner-confirmed [recovery intent](admin-actions.md#scoped-prediction-recovery-intent), independent of hot or cold.

- **Quota.** For a manifest size `N` the target is `N >= 2 ? max(1, floor(N * 0.4)) : 0` recovery slots (`RECOVERY_BATCH_SHARE = 0.4`): 5 gives 2 + 3, 7 gives 2 + 5, 10 gives 4 + 6, 15 gives 6 + 9, 20 gives 8 + 12, and `N = 1` keeps the ordinary policy. It is a ceiling on the privileged slots, not a guaranteed throughput.
- **Candidates.** A film with an active intent that is queued in either lane (its true lane stays in `films[].lane`), not retry-exhausted, not in retry backoff and not already staged. When the film is read, its stored current prediction must still be the exact version the intent denies; a film that is current or whose admission is gone is skipped as before, and one whose stored version moved on takes no recovery slot.
- **Order.** The owner's confirmation time of the cohort (oldest first), then the film's position in the stored queue (hot lane, then cold lane), then the film id. The other slots are filled by the unchanged ordinary order without the films already chosen; the recovery films come first in `films[]`.
- **Hard cap.** The quota caps recovery films in the whole manifest: free slots return to the ordinary queue, and every candidate that did not take a recovery slot is excluded from the ordinary fill, so `filmsSelected` is smaller when the ordinary queue offers nothing. Recovery probing reads at most 100 films (inside the 300-read bound), so unusable candidates cannot use the ordinary fill's budget.
- **Migration share.** The fingerprint migration share (`ceil(slots * 0.5)`) applies to the slots left to the ordinary queue; a recovery film carries no migration work.
- **Boundary.** A call with a `pin` is not reordered and has no `recovery` block. The stored queue (membership, lane, priority, retries), the lease and epoch, the `taskId` ownership, validation, the durable hold, idempotent submit, retry and backoff gates and the immutable lineage are unchanged. A recovery store that cannot be read fails the start closed.
- **Diagnostics.** While an active intent exists the answer (and a dry run) carries `recovery {target, selected, probed, ordinary, active, eligible {hot, cold}, deferredByRetry, retryExhausted, notQueued, noCandidates}`: counts only, no film id or payload. `active` counts active intent rows (a satisfied intent ends itself without a write and is then counted in `notQueued`). Without an active intent the answer has no `recovery` key.

Tests: `node tests/prediction-recovery-slots.mjs`.

**Precedence of a real start.** A live runner lease answers first (`already_running`, naming the holder, below), then an idle outcome on a current queue (`quota`, `noop`, `retry_backoff`), then the size refusal. A dry run does not look at the lease: it is the read-only manifest path and answers beside a live run.

**Owned-run readback (AIR-510).** A truncated MCP `prediction_batch_start` text is not a usable manifest. A persisted start stores that exact answer at `enrichment/batch-manifest/<runId>.json`. MCP `prediction_batch_manifest` returns **one** bounded part (`envelope`, `profile`, `contract`, one `film`, `hold`, or one held `item`) while the runner lease names that run. It writes nothing and is not a second start. Assemble envelope + profile + contract + every film; a missing part is `incomplete_manifest`. Missing, expired, v5 or spent runs are `409`. Dry-run starts store nothing. Fail closed: do not invent films from a prefix. After a valid `prediction_batch_validate` (still no I/O, ADR 0131), `prediction_batch_hold` CAS-merges a **transferable** stage at `enrichment/batch-stage.json` (per-film `batchItemDigest`; origin `runId` is provenance; `origin.filmInputHash` binds plan and model metadata). Write still requires the generating run's lease. The next `prediction_batch_start` excludes staged ids from hot/cold lane choice, drains fresh items onto the new run, and drops stale profile/contract/input; the returned `films[]` are new work. Transient drain refusals leave remaining rows on the stage and off `selectedIds`. `useHeld` remains for same-run recovery. `prediction_complete({reason:'external_termination'})` is HTTP 200 and releases the lease (installed A/B/C/D). The installed prompt does not call hold until a separate owner GO.

**Fail-closed size.** The manifest holds the first `manifestSize` eligible films (all of them when fewer; default 100). Selection reads only as many film payloads as that cap needs. `batch_start` first runs a **read-only preflight**: the dry-run read path, which reads the stored queue (and its own generation), profile, programme and film states and does not heal, rebuild, settle, take a lease or emit an Event. `maxManifestBytes` bounds the **whole serialized answer**: the preflight measures the manifest together with every field the answer carries (`manifestSize`, `filmsSelected`, `queueRefreshed`, `queueSettled`, `eligible`, `skipped`, the counts, the scheduled-run fields and, in a dry run, `notEligible[]`) using the widest values those fields can take, and the exact answer is measured again before anything is persisted. If it does not fit the Worker answers `409 {status: "blocked", code: "manifest_too_large", bytes, limit, films, largestFilmBytes, largestFilmId}` and, when the stored queue was current, writes **nothing**: no lease, run record, Event, diagnostics row, `latest-run`, queue or film write. It never shortens the selection, truncates a film's `modelMetadata` or stored fingerprint, or skips an oversized film; one film that alone exceeds the limit gives the same refusal (`films: 1`) and the refusal is for the owner to decide on (reducing client `manifestSize` is the accepted path, not auto-truncation). A refusal is never passed through the start's stop recorder: it creates no synthetic run or stop Event.

When the stored queue fails the advance gate, or the preflight found films that are already current or whose admission is gone, `batch_start` **invokes** the ordinary refresh (a refresh, not a rebuild on every start) and one guarded settlement of those films (`queueRefreshed: true`, `queueSettled`), and then repeats the preflight on the result. That second preflight is the baseline. These queue writes are effects of `batch_start`, so a `manifest_too_large` found after them is not write-free, but it still creates no lease, run, Event, diagnostics row or `latest-run` (the refresh is the only effect). The owner selected this self-healing behavior and rejected the strict read-only `queue_stale` alternative for the real start; only a dry run answers `409 {code: "queue_stale"}`.

A live runner lease (an earlier v2 run, or a stored legacy v5 run) turns the attempt away with `already_running` before the refresh and the settlement: it writes nothing to the queue, the run, the lease or the films, delivers no manifest and is recorded as a start attempt. Since AIR-548 ([ADR 0180](../../adr/0180-skipped-predictions-start-is-a-neutral-event.md)) each such `already_running` answer, on this early check and at the lease acquire alike, also records one neutral `enrichment` Event `presentation: "batch_v2_skipped"` for that request (id `enrichment-skipped-<requestId>`, no run, no counts), parked in `enrichment/stop-events/skipped-<requestId>.json` and delivered through the existing outbox; the recorder is best-effort and never changes this answer, the lease, the queue, the run or a film. `409` refusals, `manifest_too_large`, idle `noop`/`blocked` and a dry run write no such Event; a real start refused with `prediction_catalog_held` leaves a skipped Event of its own, `reason: catalog_held` (below, [ADR 0190](../../adr/0190-catalog-held-start-is-a-skipped-event.md), [events reference](../domain/events.md)). (A lease taken by another start between that check and this start's own acquire is still `already_running`, after queue writes that named writers also make.) After a fitting baseline the Worker runs the guards a start runs before its lease (the previous run's retry heal, the catalog gate), takes the lease and **revalidates before anything else is written**: the queue's own generation must equal the baseline's (any queue write by another writer in between, including one that only touches films outside the delivered 100, changes it), and the selection and the manifest must hash the same. Otherwise the answer is `409 {status: "blocked", code: "queue_changed"}`, the lease is released, and the only effects are the lease acquire and release (no run, Event, diagnostics row or `latest-run`, no film write). The exact answer, with the real `runId`, lease and extra fields, is measured against the limit at this point too, with the same outcome (`manifest_too_large`). Only then does the start write its diagnostics row, settle the expired diagnostics and pending Events, mark a recovered run, and save the run record and the run's `sources` object.

The run's films are selected once: the recovery slots first (below), then hot first, cold only while no hot film is outstanding, films with a future `retryAt` excluded; a film whose prediction is already current or whose admission is gone is skipped (a usable stored prediction is never regenerated) and the manifest is filled from the next ready films; at most 300 queued films are read. Each film's state is read in parallel and the catalog by id. `503 {status: "blocked", code: "prediction_catalog_held"}` and `prediction_retry_heal_pending` are the `start` answers they are for v5. With nothing eligible the answer is the `start` one: `noop`, or `blocked` for `quota` (a reported `remainingPercent` of 0) and `retry_backoff`. These idle outcomes take no lease and create no run, and they are not passed through the stop recorder, so no synthetic stopped run, stop Event or `latest-run` is written; the attempt is recorded and the queue's `lastBatch` is kept as a v5 start keeps it. `already_running` names the holder's `runId` and delivers no manifest.

**Dry run (frozen snapshot).** Isolation is proved offline by `tests/prediction-dry-run-isolation.mjs`: every dry-run RPC runs while any R2 or D1 write is a fault and none is attempted. `dryRun: true` uses a separate read-only path: it reads the stored queue, profile, programme and film states and writes nothing (no lease, run record, `sources` object, queue rebuild or retry-heal, Event, diagnostics row or D1/R2 write). A stored queue that fails the advance gate answers `409 {code: "queue_stale"}` instead of being rebuilt. The answer is the manifest with `runId: null`, `dryRun: true`, `manifestHash`, `notEligible[{filmId, reason}]` (`not_queued` or `retry_backoff`), `eligible` and `skipped` counts; a pinned film appears in the pinned order. **The caller keeps this one manifest** and replays the same films, metadata, plans and fingerprints from the held copy at every generation size; it does not call `batch_start` again between passes, because a live queue changes. A dry run may coexist with a live run. A pinned film that is no longer eligible is listed in `notEligible[]` and not replaced.

### Lid-only Films are excluded while they have no TMDB movie (ADR 0217 decision 9, choice M1, AIR-673, dormant)

ADR 0154 decision 1 does not require a TMDB claim, so a trusted `letterboxd` identity could make a lid-only Film eligible. [ADR 0217](../../adr/0217-source-independent-film-admission.md) extends the policy with **one temporary exclusion**, decided by **one cohort rule on the resolved Film** (`src/prediction-lid-only-exclusion.js`):

> a Film is in the cohort when its **survivor** (the end of its redirect chain) is the Film of a `film_lid_admission` row (the row's own Film or any redirect source that ends at the survivor: a merge moves the proof) **and** the survivor holds **no current trusted `tmdb` claim** (a trusted, non-conflicting claim of a movie that no non-superseded owner retirement retires).

The same statement (`COHORT_SQL`) serves every enforcement point and the unified read, so they cannot disagree. An id only **nominates** Films: a `film:` id is that Film; a bare lid, `lb-<lid>` or `film:lb:<lid>` nominates the Films of the lid (its trusted `letterboxd` claim and its proof row); a `tmdb_<n>` movie id nominates nothing. The spelling of an id never decides.
- **Queue rebuild.** The Film is not admitted to the rebuilt queue; an unreadable answer fails the rebuild closed.
- **Manifest build.** A film named by a stale queue (or a pinned list) is never put in a manifest, costs no slot and is reported in `notEligible[]` with `reason: "lid_only_deferred"`.
- **Per-film `submit`.** The item is answered `status: "not_eligible", reason: "lid_only_deferred"` before anything is read or written for it, so a manifest built before the Film became lid-only cannot submit it. An unreadable answer is a storage error, never permission.

The exclusion ends when the survivor holds a current trusted `tmdb` claim (an attach); the ordinary gates then apply at all three points. While migration `0048` is not applied no lid-only Film exists, nothing is excluded and behavior is unchanged. The exclusion is **temporary**: planning prediction support for lid-only Films is an explicit near-term follow-up (M2), not an indefinite deferral; nothing here authorizes scoring, a model call or a prompt change. The unified read reports the same verdict in [`predictions.eligibility`](film-aggregate.md). `tests/prediction-lid-only-real-path.mjs` proves the three points on the real Worker code (queue rebuild, manifest, a stale manifest through the real `batch/submit`, a merge to an arbitrary survivor, an attach).

### Ordering drift leaves the start (ADR 0204)

A real start no longer rebuilds the queue for **ordering drift of its own completed generation** (`priorityCause` `shows_signature_changed` or `window_transition`) when the stored queue passes the advance gate, is ranked on the published generation with a stored (verified) `showsSignature`, its preflight selected at least one film, and its last rebuild (`refreshedAt`) is younger than 90 minutes. It delivers from the stored queue (the accepted lag of AIR-542) and notes `orderingDeferred`. Films found already current or without an admission are still settled in the same start, without a forced rebuild. Everything else is unchanged: a stale queue, `shows_signature_unreadable`, a new or carried generation, a queue without a stored signature, an idle queue (AIR-529 reconciles before `noop`) and a queue older than 90 minutes are refreshed by the start, or refused, as before. A dry run still reports `priorityDue` and `priorityCause`.

The writer `reconcilePredictionOrdering` runs on the hourly cron tick beside `EpgOrchestration.ensure` and `Monitor.run`. It rebuilds only a queue that is current for its generation, has a verified signature and owes ordering drift; it waits up to 5 minutes (every 15 s) while a start claim or a live commit gate holds the runner lease. Every rebuild attempt (and each retry after a lost compare-and-swap) re-reads the queue head, profile and programme and decides that admission again on that snapshot, builds with the ordinary queue builder (trigger `ordering_reconcile`), refuses a candidate that is not a verified ranking of the same generation (`candidate_unverified`, `candidate_basis_changed`, `candidate_not_current`), re-checks the lease and writes against the head it admitted. A run in its research phase does not block it. One rebuild per tick at most and one log line `{"event":"prediction_ordering_reconcile","outcome":"rebuilt"|"current"|"skipped"|"failed", "cause"?, "reason"?, "code"?, "attempts"?, "ms"}` with codes only. The ranking is never more than about 90 minutes behind its own generation: the writer repairs it on the first free tick, and the start repairs a queue past the bound itself.

### Compact ready envelope (ADR 0205)

`answer: "envelope"` (real synchronous starts only; with `dryRun` or `deferred` the start answers `400 {code: "envelope_needs_stored_manifest"}` and writes nothing; another value is `400 {code: "invalid_answer"}`) answers, after the manifest has been stored, `200 {kind: "envelope", answer: "envelope", status: "running", runId, protocol, dryRun: false, lease {expiresAt, ttlMs, epoch}, limits, manifestFormat, manifestHash, manifestSize, filmsSelected, queueRefreshed, eligible, skipped, pendingCount, hotRemaining, coldRemaining, drained?, …, parts: [{kind: "profile"}, {kind: "contract"}, {kind: "film", index, filmId}…], read: {tool: "prediction_batch_manifest", parts: ["profile", "contract", "film"]}}`: the stored manifest without `films`, `profile` and `contract`, identical to the `envelope` part `prediction_batch_manifest` serves for that run. The run, its id, epoch, hash, the stored manifest and every later step are those of a `full` start. The caller reads `profile`, `contract` and each `film` part with `prediction_batch_manifest`, checks every part's `runId` and `manifestHash`, assembles the manifest in envelope order and only then works and submits; the parts assembled are field for field the stored full answer. A same-Task repeat while the lease lives answers the same envelope when it asks for `envelope` and the full stored manifest when it asks for `full`; `answer` is not a start argument, so a different value is never `task_args_mismatch`. Without `answer` (every installed prompt) nothing changes. Offline S7: envelope about 1.3 KB against a 13.8 KB fixture manifest, and its size does not grow with the films' metadata ([evidence](../../evidence/prediction/air-588-start-latency-offline-2026-11-24.md)).

### Task label and owner-scoped run calls (ADR 0195)

The four standing Tasks send `taskId` (`task00`, `task15`, `task30`, `task45`; closed enum, not a secret, not an identity; Access and the JWT are unchanged). HTTP: `POST /api/enrichment/batch/start` accepts `taskId` only with `trigger: "scheduled"` (`400 task_id_requires_scheduled`, `400 invalid_task_id`); a dry run ignores it. With `invocationKey` or `deferred` (ADR 0188 / 0193, dormant) the label is only a correlation stored on the lease and the run: the key still decides the join. The MCP tool requires it for a real scheduled start and for every run-scoped call (see [the MCP reference](mcp.md)); the HTTP start without it keeps today's behaviour for owner-run diagnostics.

| Situation | Answer |
| --- | --- |
| first `start(taskId)`, no live lease | claims the lease before the heavy work (ADR 0188 early claim), creates the run and stores `taskId` on the run and on the lease (kept by every renewal, heartbeat, gate write and conversion; dropped by a release) |
| the same `taskId` repeats while its lease is live, same arguments, same epoch | no new run: the **same stored manifest** (run id, epoch, hash, films, profile, contract), also after the first client submit; while the first start still prepares it, after the 10 s join bound `200 {status: "start_pending", runId, epoch, taskId, retryAfterMs, read: {tool: "prediction_batch_manifest", pendingCode: "manifest_pending"}}`. Never `already_running` to its own live lease; writes nothing and extends no TTL |
| the same `taskId`, other start arguments | `409 task_args_mismatch` (an argument conflict, not a foreign owner) |
| another `taskId`, or a run without a label, holds a live lease | `already_running` naming the holder as before; nothing assigned |
| no live lease (released or expired) | a **new** run and epoch; the earlier run is never restored |
| heartbeat, hold, submit, complete or manifest read of a **labelled** run with another or no `taskId` | `409 {error: "wrong_owner", code: "wrong_owner"}` with no `status` field and no payload; refused before the step recorder, the writer lease and any write; it never records a stop of the real owner's run |
| an unknown `taskId` value on any of these | `400 invalid_task_id` |
| any call of a run **without** a label (manual, keyless, keyed or deferred start without `taskId`) | operated only by a caller **without** a label, as before; a call that carries a label is `wrong_owner` (presence must match and the values must be equal), so a Task can neither operate nor read a label-free run. Such a run is therefore not operable through the MCP run tools, which require the label; it stays reachable through the owner-only HTTP routes |

`runId`, `epoch`, the lease compare-and-swap, the submit gate and the commit guard decide every write exactly as before; the label is a correlation, never a replacement. A repeated confirmed submit is handled by the existing server-side idempotency per film, run and `inputDigest`; the label bypasses neither validation nor fencing. Observability: the start step records `taskRepeat: 1` for a same-label repeat, `joined`, `startPending` and `keyArgsMismatch` as for ADR 0188.

### Deferred start and the issued key (ADR 0193)

`prediction_batch_key` (MCP only; it reads and writes nothing) answers `{status: "issued", invocationKey: "dk1.<32 hex>"}`. `POST /api/enrichment/batch/start` with `deferred: true` needs that key shape in `invocationKey` (otherwise `400 invalid_deferred_key`), is never a dry run or a pin (`400 deferred_not_dry_run`), and answers `200 {status: "accepted", protocol: "batch_v2", deferred: true, runId, epoch, phase, next, retryAfterMs, read: {tool: "prediction_batch_manifest", part: "envelope", pendingCode: "manifest_pending"}, lease: {epoch, claimTtlMs, readyTtlMs, ttlMs}}` within seconds. The `runId` is derived from the key (`dk-` + 32 hex of its hash), so a retry of the same invocation finds its attempt without an index. `phase` is `preparing`, `ready`, or `accepting` (the first request has not confirmed its dispatch yet: `next: "repeat_start"`, repeat the same start after `retryAfterMs`); otherwise `next` is `poll_manifest` and `retryAfterMs` is 5000. Refusals: `503 deferred_start_unavailable` (the Workflow binding is absent, the attempt marker could not be written, or the platform definitely did not create the instance: the claim is released; after a definite not-created the key is one-shot and a retry gets the typed `start_failed`, so the next execution takes a fresh key) and `503 deferred_start_ambiguous` (the state of the instance is unknown: the claim is kept, repeat the same start). The request takes the runner claim and creates one Workflow instance (`iptv-prediction-start`, instance id = `runId`); the preparation (preflights, queue refresh, revalidation, fenced persist) runs there, not in the request. A repeat is decided in this order: a terminal `refused`/`failed` outcome of the key (typed `409`, even when another run owns the lease), a live attempt of the same key and arguments (the receipt), a `ready` outcome without a live lease (`409 start_finished`), an attempt marker with no holder and no outcome (recorded once as `failed`, never dispatched again), then a new claim, the create-only attempt marker (written before the dispatch; a claim that finds it already written releases itself and dispatches nothing) and only then the instance.

| Readback | Meaning |
| --- | --- |
| `prediction_batch_manifest` → `409 manifest_pending` + `retryAfterMs` (5000) at the HTTP level of the read; the MCP tool returns it as a **successful** result `{httpStatus: 200, kind: "pending", status/code: "manifest_pending", retryAfterMs}` (no `error`, no `isError`) | the claim is live, or the preparation mark is still set (the manifest is stored but **not served** before the readiness edit): poll again |
| `prediction_batch_manifest` → the envelope and parts | ready: the manifest is the same immutable stored answer as a synchronous start |
| `prediction_batch_manifest` → `409 start_refused` (`outcomeCode`, `reason`) | final: the start was refused (`noop`, `quota`, `manifest_too_large`, `prediction_catalog_held`, …); no run exists |
| `prediction_batch_manifest` → `409 start_failed` (`outcomeCode`) | final: `start_claim_lost`, `storage_error`, or `start_lost` (no run, no outcome and no live claim); the terminal outcome wins over a partial run row |
| the same keyed deferred start again | the same receipt with `phase: "preparing"` or `"ready"`; no second preparation, no wait; `already_running` for another key, `key_args_mismatch` for other arguments, or after a client submit |

The terminal outcome is a create-only record `enrichment/batch-start/<runId>.json` (`ready`, `refused`, `failed`) and the attempt marker is `enrichment/batch-start/attempt/<runId>.json`; a replayed or stale Workflow instance never overwrites either. The preparation holds the **180 s** TTL throughout (the claim, the persist gate and every renewal of the preparation); readiness is one owner-fenced lease edit that removes the gate and the preparation mark and keeps the short expiry unless the client already renewed. The first `prediction_heartbeat` or `batch_submit` of the client renews to the full TTL (a heartbeat during the persist is answered `busy` by the prediction writer and succeeds when repeated). A caller that never returns blocks the runner for minutes, and the next start recovers the run as `recovered_stale_lease`. Keyless starts, the synchronous keyed start (ADR 0188) and `dryRun` are unchanged.

### `POST /api/enrichment/batch/submit`

Request: `{runId, epoch, items[1..10], dryRun?: boolean, manifestHash?: string, contract?: {fingerprintSchemaVersion, fingerprintPromptVersion, predictionPromptVersion, registryDigest}}`; each item is `{filmId, fingerprint?, prediction, assessment?}` or `{filmId, failure: {kind: "parse_error"|"validation_error"}}`, plus `inputHash` in a dry run. The optional `assessment` ([contract](prediction-assessment.md), ADR 0132) is a sibling of `prediction`; the item `inputDigest` includes `assessmentSha256` only when one is sent, so every existing digest and replay is unchanged. The Worker writes it as its own create-only R2 object after the version object and before the guarded D1 commit; an identical replay is `present`, a different assessment for a settled film is `conflict`, and `already_current`, `needs_regeneration` and failure items are `not_applicable`. `epoch` is the lease epoch the start and every answer return. A body is valid only if every `filmId` appears once and no key outside the item contract is present (`400` otherwise). The MCP transport rejects a body over 64 KiB with `413` before any processing, and the MCP tool `prediction_batch_submit` refuses a group over 56 KiB with a clear tool error and **nothing submitted**: the caller splits the group. The size of ten rich items is in the [measurement](../../evidence/prediction/air-448-batch-submit-size-and-cost-2026-11-12.md); ten fingerprints at the contract's 12,000-character maximum do not fit one call, and the batch size is not reduced by the Worker.

**Validation happens once, here, per film.** The same validators and issue vocabulary as the [submit validation contract](enrichment.md#submit-validation-contract) run on each item (fingerprint schema and evidence against the run's stored `modelMetadata`, prediction schema, prompt and contract versions). This validation is authoritative and no other call is required for it. An **accepted** optional read-only group preflight (ADR 0131), the MCP tool `prediction_batch_validate` ([ADR 0131 (Accepted)](../../adr/0131-batch-candidate-preflight-tool.md), no HTTP route), runs the same validators on 1 to 10 candidates before the submit and checks no state (no manifest, `inputHash`, profile, run or epoch). One film's failure does not touch the others.

Answer `200 {runId, epoch, results[], committed, queueSettlement, profile, regenerate?, action?, remaining, hotRemaining, coldRemaining, mustComplete, stopReason}` plus the run summary. `results[]` has one entry per item, in request order:

| `status` | Meaning |
| --- | --- |
| `created`, `recalculated` | The prediction was written (immutable version object, then the D1 pointer) and checkpointed. After a profile change a film the change does not reach also carries `compatibility: "compatible"`: the record keeps the profile identity it was made with |
| `already_current` | A usable prediction already exists; nothing is regenerated |
| `needs_regeneration` | The profile moved under the run and the change reaches this film (`compatibility` `impacted`, or `unknown` when the film's features cannot answer the declared selectors). The prediction is **not** written, no failure or retry record is created, and a valid fingerprint of the item is kept, so the next manifest asks only for the prediction. Never `validation_failure` |
| `validation_failure` | A per-film schema failure: `error: "parse_error"`, `retryable`, `retryAt`, and `validation {stage, reportedBy, issues[{path, code}]}`, sanitized codes and field paths only, never a payload or the profile. It is deferred by the existing retry policy (1-hour exponential backoff, maximum 6 hours), saved as a retry record at once, and not retried in the run: the identical payload returns the stored failure with `replayed: true`, a different payload is `conflict`. Ten saved attempts of the same Film ID exhaust automatic selection. Five consecutive *worker* contract failures stop the run (`format_error_storm`); a caller-reported claim with a closed reason (including `insufficient_evidence`, `preflight_validation_failed`, `json_unparseable`, `request_too_large`) does not increment that streak |
| `blocked` | The call stopped before this film: `reason` is `gate_lost`, `lease_lost` or `storage_error` |
| `deferred_budget` | The soft per-call budget was spent between items; nothing is written for this film; resubmit it |
| `not_in_manifest` | The film is not selected by this run. Nothing is written |
| `conflict` | A different payload for a film this run already settled. Nothing is written |

Any result of a film this run already settled comes back with `replayed: true` and writes nothing. ADR 0122 names two of these `stale_profile` and `validation_error`; this contract uses `needs_regeneration` and `validation_failure`, the names the delivery scope fixed, with the semantics the ADR gives.

**One call, a sequence of commits.** A call is not atomic. Each film is committed in turn: the immutable body and the generation record (R2, create-only), then **one D1 batch** that moves the fingerprint pointer or the prediction pointer and also carries a guard statement, and the film's result is checkpointed in the run record (itself saved with the same guard) before the next film. After the loop one conditional `batch_progress` write removes every written film of the run from the queue, and the remaining retry state of a failed film was already saved. A crash, a timeout or a lost answer is recovered by submitting the **same body** again: films already committed come back `replayed`, the rest are processed, and the queue is settled again from the run record. If the queue write loses its attempts the committed results are still returned with `queueSettlement: "pending"` and the next call completes it.

**Input identity.** An item is identified by `(runId, filmId, inputDigest)`. `inputDigest` is one SHA-256 over the canonical JSON of the tuple `{filmId, fingerprint, prediction, failure}`, each component being its reproducible projection or `null`: for a prediction, its model-supplied fields after the Worker's normalization (`predictedRating`, `probability4Plus`, `confidence`, `matchSignals`, `mainRisk`, `moodLabels`); for a fingerprint, its content `fingerprintHash`; for a failure-only item, `{kind, reason, preflightIssues?}` with the issues sorted by `path` then `code` and deduplicated; a historical record that was stored without a claim used the bare string `failure.kind`. The same projection feeds the crash-window comparison. The run record keeps `submitted[filmId] = {outcome, inputDigest, committedAt}`. In the crash window before that entry exists, a stored prediction that carries this `runId` and whose model fields hash to the request's digest is recognized and answered `replayed`; a different digest is `conflict`. It is not the stored version object's own `contentSha256`, which also covers Worker-generated fields. No version object, history row or view-index entry is written twice.

**Ownership, the gate and the commit fence.** The lease carries an `epoch`, fixed when the run takes the lease. `epoch` in the request must be the run's (`409 {code: "epoch_mismatch"}` otherwise, a caller error that never stops the run); a lease that has expired, or that another run took, answers `lease_lost`. The **gate comes first, before the global writer lease**: at the start of a call the lease's own compare-and-swap records `submitGate {token, requestId, bodyHash, startedAt, expiresAt}` (60 s), where `token` is generated by the Worker for each call and the caller's `X-Request-Id` is only a log field. **While any gate is live no second acquisition succeeds**, whatever its body and whatever request id it carries: the call answers `409 {status: "busy", code: "submit_in_flight", retryAfterMs}` and writes nothing, not even a diagnostics step, so an overlapping call never reaches the writer lease. Global writer exclusion is unchanged: every real call then takes the one prediction writer lease, under its gate. The call renews the lease and the gate after every film and clears the gate, by its token, at the end. A check before a write is not a fence: the D1 batch of **every authoritative write** of the call (the film commits, the run record, a failed film's retry record, the queue settlement and the progress record) also commits only while the lease row still names this `runId`, this `epoch` and this gate **token** and is alive. A handler whose gate was reassigned or whose epoch changed commits nothing and clears nothing, even if the new gate carries the same request id; loss of the gate is terminal for every mutable operation that follows (no checkpoint, no retry record, no settlement, no progress). A result that was only in memory when the gate was lost (a failure, a regeneration) is answered `blocked`, because nothing of it was persisted; the next holder decides it again and settles the films the earlier call committed. An immutable R2 body written earlier is content-addressed, create-only and unreferenced. A renewal that loses the compare-and-swap is read again and answers `busy / lease_contention` only while the run still owns the lease. A v2 submit is **not** passed through the shared step recorder of the start, which would append diagnostics steps and, for a lost lease or a storage failure, write a stop of the run, a stop Event, `latest-run` and the queue's retries without the gate and the epoch: a call whose lease another run took answers `409 {status: "lease_lost", results, committed}` and writes nothing that it does not own, and an unexpected error is a recoverable `502`. A **progress Event** (every 50 written films or 30 minutes) is ordered behind an authoritative checkpoint: the run record is saved first, guarded, with the Event as `progressIntent`; only then is the Event written (its id is fixed, the write is idempotent) and the intent cleared by a second guarded save. A handler that lost its gate before the Event write leaves the intent, and the next call publishes it first, once. The call requires the `d1` prediction authority marker.

**Profile change.** When the current profile's hash differs from the run's, the profile block is `{changed: true, from, to, scope: "identity"|"selective"|"global", body, lineage}` (the new profile once, at the top level, never inside a per-film payload) and the answer lists `regenerate[]`. Each film's prediction is judged with the existing combined verdict (the selective rule over the profile lineage, the film's impact features and the fingerprint transition rules): a film the change does not reach is written with the profile identity it was made with; the others are `needs_regeneration`. `scope: "global"` answers `action: "complete"`: call `complete` with `reason: "profile_changed"` (without a reason `complete` is refused `409` while the profile differs), which ends the run `partial`, releases the lease, writes the run's missing retries and settles nothing else; the next `batch_start` builds the queue for the new profile. `selective` answers `action: "continue"` (films the change does not reach can still be written). A change of the fingerprint or prediction contract is `409 {code: "contract_changed"}` before any film, stopped with `complete` and the existing reason `runner_aborted`.

**Refusals before the first film** write no film or run record: `404 {error: "Unknown run"}`, `409 {code: "wrong_protocol"}` (a stored legacy v5 run), `409 {error: "Run already complete"}`, `409 {code: "epoch_mismatch"}`, `409 {status: "lease_lost"}`, `409 {code: "contract_changed"}`, `409 submit_in_flight`, `409 {code: "batch_runner_requires_d1"}` (only the local stand-in without the prediction tables; with `PREDICTION_DB_REQUIRED` on, a marker that is not `d1`, a missing table or a missing binding is `502 {error: "prediction_domain_unavailable"}`, [ADR 0162](../../adr/0162-d1-only-authority-retire-rollback-toolchain.md)), `400`, `413`. A failure after processing began answers `502 {error: "storage_error", recoverable: true, results, committed}` or `409 {status: "gate_lost"|"lease_lost", results, committed}`, with the results of the films already processed; the `502` is **not** a stop of the run (a persistent failure is ended by `complete`). The caller replays the same body. `prediction_catalog_held` while the queue is settled answers `503` with `results`, `committed` and `queueSettlement: "pending"`.

**Dry run.** `dryRun: true` takes neither the writer lease nor the step recorder and writes nothing: no lease, gate, run, queue, fingerprint, prediction or version object. It validates each item with the same validators against the current contract and profile and answers `{status: "dry_run", dryRun: true, runId: null, manifestHash, profile {version, hash}, results[]}` with `results[].status` `would_write`, `already_current`, `not_eligible` or `validation_failure` and `liveInput` `same`, `changed` or `not_eligible`. A dry-run manifest (`batch/start` with `dryRun`) names each film's `inputHash`; sending it back lets the Worker report whether the film's input is still the manifest's (the Worker has no persisted run, so it cannot check membership of a manifest). A `contract` that is not the current one answers `409 {code: "contract_changed", dryRun: true}`.

### Caller failure claim

A batch v2 failure item is `{filmId, failure:{kind, reason, preflight?:{issues:[{path,code}]}}}`. `reason` is required: one of `preflight_validation_failed`, `insufficient_evidence`, `json_unparseable`, `request_too_large`. Omitting it answers `400 Invalid item` with `failure.reason required` and writes nothing, including when other items in the same body are valid. `preflight.issues` is optional, at most 20 entries; each is exactly `{path, code}` with `path` one of the paths the Worker validators can report (`fingerprint`, `fingerprint.<rule field>`, `fingerprint.execution.<dimension>`, `fingerprint.evidence`, `fingerprint.evidence.plotMechanics[.<mechanic>]`, `fingerprint.evidence.execution[.<dimension>]`, `prediction`, `prediction.<model field>`, the listed `assessment.*` paths; `callerFailurePathAllowed` in `src/enrichment.js`, checked against the validator literals by `tests/fingerprint-evidence.mjs`) and `code` one of the contract issue codes. A syntactically valid but unknown path such as `fingerprint.notARealField` is refused. The MCP tool schema publishes the same object shape (`path`, `code` enum, both required, no extra keys) and requires `kind` and `reason`. Anything else (an unknown key at any level, another reason, path, code, type or a list over 20) answers `400 Invalid item` with sanitized issue paths and nothing is recorded or echoed.

The claim is stored as `validation.claimed = {reason, preflightIssues?}` beside the unchanged `{stage:'caller_reported', reportedBy:'caller', issues:[]}`; it never enters `issues`, which stay Worker-verified. It is a caller claim: the Worker may never have seen the preflight it echoes, so it does not prove that a `prediction_batch_validate` ran. A claim does not make a candidate acceptable: an item with a fingerprint or prediction is still validated by the Worker, and a failure item writes nothing. `kind`, retry backoff, `format_error_storm` and the queue are unchanged. Replay: the identical claim is `replayed`; another reason or issue set is `conflict`. A kind-only item is refused before identity, so it cannot replay a stored claim. Run records that were committed as kind-only keep their stored digest; a new kind-only submit is not a way to replay them. Rollback of the required-reason gate is a code deploy. Stored `claimed` values stay in run and retry records.

### `prediction_complete` and `manifest_spent` (ADR 0136)

For a `batch_v2` run, when every selected manifest film is settled (`created` / `recalculated` / `already_current` or a recorded per-film retry failure), `POST /api/enrichment/complete` with `{runId, reason: "manifest_spent"}` is a **normal** completion: `status: "complete"`, lease released, one truthful Event carrying `presentation: "batch_v2_terminal"`, `stopReason: "manifest_spent"`, `selectedCount`, `manifestSize` when known, created/recalculated/failed counters and the real global `hotRemaining` / `coldRemaining` — even when ready films remain in the queue. It is not `partial`, not `time_budget`, not «Прогнозы приостановлены», and not a false `queue_empty`. The Events screen uses the presentation marker for «Пакет прогнозов обработан» (or «… с ошибками») and does not print the raw `manifest_spent` code ([ADR 0146](../../adr/0146-batch-v2-single-terminal-prediction-event.md)). The run does not write a start or progress Event. Unsubmitted slots and `deferred_budget` answer `409 {code: "manifest_not_spent"}`. Profile / contract / lease / storage failures keep existing stop semantics. Replay of a finished run re-emits the same Event and does not create a second one. A reasonless complete while ready films remain outside the spent selection is still refused (`Queue not empty`).

### Error shape and bounds

Errors keep the existing shape `{error, code, status?, reason?}` plus `requestId`. Per execution: at most `manifestSize` films delivered (default/ceiling 100); per call at most 10 items, a soft `callBudgetMs` checked between items (it does not bound one slow I/O call or guarantee the absence of partial effects) and one queue settlement. The step timing line ([above](#step-timing-line)) is written with `step` `batch_start` or `batch_submit` and counters `manifestFilms`, `manifestBytes`, `items`, `created`, `recalculated`, `alreadyCurrent`, `failures`, `deferredBudget` and `staleProfile`. A dry run writes the line too (a log, not storage).

### Compatibility, rollback and authorization

There is one protocol and no feature flag; clients that omit `manifestSize` get the 100-film selection. The former rollback (disable the v2 Tasks, re-enable the v5 Task) no longer exists: v5 can return only through a code rollback to a Worker that still contains it, plus separate owner-approved Scheduled Task actions ([ADR 0167](../../adr/0167-retire-prediction-runner-v5.md)). A code rollback does not revert D1, R2, the queue or stored predictions. Deploying this contract authorizes no run, dry run or Task change: each needs a separate owner approval ([scheduled tasks](../scheduled-tasks.md)).

### Retired materialization route

`POST /api/enrichment/predictions/materialize` is retired ([ADR 0050](../../adr/0050-retire-prediction-materialization-route.md)). Any method and body answers `410 Gone` with `{error: "gone", detail}` before the body is read; nothing is read, written or locked, and no value of the former `PREDICTION_MATERIALIZATION` binding reopens it. The historical run it served is complete and reconciled ([runbook](../../runbooks/prediction-versions.md#2-historical-materialization-completed-the-route-is-retired)); its receipts under `enrichment/predictions-materialization/` stay in R2.

## Auxiliary state storage (ADR 0194; D1 authority since 24 Nov 2026)

The request and response contracts of `batch_start`, `batch_hold`, `batch_submit`, `heartbeat`, `complete` and the manifest readback are **unchanged**; `manifestHash` is unchanged. Where the held stage, the run sources, the persisted manifest and the event outbox live depends on the marker `prediction_aux_authority`: `d1` (production since 24 Nov 2026) serves them from D1 only; `r2` was the state before the cutover, kept the R2 objects and cannot be reached again from `d1`; an unavailable authority is `502 prediction_aux_unavailable`. The manifest is create-only (an equal replay is a no-op, other bytes are a conflict, never an overwrite); the readback of one part verifies the pieces that cover it; the live `hold` and `item` reads come from the transferable stage, not from the manifest. See [schema v34](../data/d1-schema.md), the [runbook](../../runbooks/prediction-aux-state-cutover.md) and [ADR 0194](../../adr/0194-prediction-auxiliary-state-d1-checkpoint-and-outbox.md).

**Closed auxiliary state (ADR 0196).** While the marker `prediction_aux_authority` reads `closed` (the pre-activation window of the AIR-554 cutover), `batch_start`, `batch_hold`, `batch_submit` and `complete` answer HTTP 503 `{status:'blocked', code:'prediction_aux_closed', reason:'prediction_aux_closed', retryable:false}` with `Retry-After: 60`, before any object-store or D1 write, whatever the caller (Task, manual MCP or HTTP). A `dryRun` start or submit, `heartbeat`, `prediction_batch_manifest`, `enrichment_status` and the event reads are not refused. The Worker side also refuses a put or delete of the four R2 families with the same typed error. A caller must not retry in a tight loop; the state ends by a reopen (`r2`) or by the activation (`d1`), both owner operations.

Implementation contract (ADR 0194, as built; it refines the ADR text where the lease document carries no protocol field). Every auxiliary write is one D1 batch whose guards share the transaction; the fence class is explicit and a missing or incomplete one throws `prediction_aux_guard`, never a weaker write:

- **`run`** (stage, sources, manifest of a run): the runner lease of that run (id, epoch, unexpired; the gate token where the writer holds one, none for the keyless path), the prediction domain marker (`mode` `d1`; the `writes` column is the r2-mode import fence and is `held` in production in mode d1, [ADR 0162](../../adr/0162-d1-only-authority-retire-rollback-toolchain.md), so it is not part of the predicate) and, once the run row exists, the run row's `protocol` (`batch_v2`); the writer lease where the caller holds it.
- **`writer`** (a delivery or terminal write under the writer lease the caller holds; the owner id is threaded from `predictionWriter`).
- **`target`** (lease-free admission of a skipped request; recovery of an expired predecessor): the caller's own compare-and-swap on the target row (identity, state, attempts, `recoveredByRunId`) is the fence, named on purpose.
- **Source and run.** The run document carries `sourceRevision` and `sourceHash`; the first revision and every drain revision commit **in the same batch as the run write**, behind a compare-and-swap on the head, and the readers check the binding (a mismatch or a head without its run row is `prediction_aux_corrupt`; a run without a binding is a legacy or imported run).
- **Terminal run and outbox.** The run's terminal transition (`complete`, a stop, a recovery) and its stop outbox row are one batch, with a compare-and-swap that the run was not recovered by a successor meanwhile; the journal delivery follows and is retried independently. A supersession is decided against the target run's own row in the same snapshot.
- **Stage.** A drain deletes the staged row in the same batch as the film's prediction, and every other drop names the rows it **observed** (film, digest, holder); the head and rows are read in one snapshot and checked against each other.
- **Manifest.** A missing row of a ready run is `manifest_unavailable` (`manifest_pending` only while the claim's `prep` mark or the persist gate is live); a replay verifies the stored bytes; every part checks the run id and the epoch stored with the manifest.
