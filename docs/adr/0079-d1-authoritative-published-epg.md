# ADR 0079: D1 owns the published EPG generation only after its own marker is switched

**Status:** Proposed  
**Original decision date:** 2026-11-01  
**Recorded at:** 2026-11-01  
**Approval source:** not an owner acceptance. This record is proposed with the AIR-319 implementation. Accepting it is a later owner decision and authorizes no production write.  
**Related work:** [AIR-319](https://trello.com/c/pQL8NUTC), [ADR 0008](0008-atomic-epg-publication.md), [ADR 0021](0021-staged-atomic-generation-import.md), [ADR 0073](0073-metadata-cache-d1-authority.md), [ADR 0051](0051-d1-domain-r2-blobs.md)  
**Supersedes:** [ADR 0008](0008-atomic-epg-publication.md) in part, and only while `published_epg_authority.mode` is `d1`: the coherent snapshot is the D1 generation, and `epg/published-generation.json` is its compatibility mirror. The coherent-snapshot rule stands. [ADR 0073](0073-metadata-cache-d1-authority.md) decisions 3 and 5 in part: a contract version of 6 or later, with the cache tables present, follows the metadata marker. The accepted decision text of both records stays.  
**Superseded by:** None

## Context

The published programme, its pointer, the show list and the watchlist order are R2 objects. [ADR 0008](0008-atomic-epg-publication.md) requires one coherent generation: readers pin that generation, and a writer that lost it does not update it. The v1 D1 tables `published_generation`, `film_generation`, `film_show` and `watchlist_film` cannot take that role on the live path. They reference `film(id)`. A publish that inserted them would mint a Film for a programme id that has none, and `src/epg-repository.js` `publishGeneration` also writes discovery candidates. Canonical Film and Person, credits, owner-reviewed names, the discovery ledger, ratings and prediction state are other domains. AIR-317, if it lands, is a separate marker and migration `0007`. It is not a prerequisite. Its open pull request already holds ADR 0078, so this record is 0079. Production today is schema v6. The metadata cache marker is `d1`. The cron is `37 * * * *` and runs only the enrichment projector.

There is no transaction that covers D1 and R2 together. The Worker publisher uses the Worker binding `D1Database.batch`. The backfill's multi-statement `{sql}` body is a different transport. It is not evidence that this publisher's batch is atomic, and this delivery did not measure production D1.

## Decision

1. **New tables, no Film foreign key.** Migration `migrations/0008_published_epg_authority.sql` adds the published generation, its documents, members, shows, staging tables, one marker row and one fence row. `film_id` is the id carried by the published document. It is not a foreign key. The publisher does not insert `film`, `candidate`, `watchlist_film`, credit or prediction rows. Display fields stay in the chunked JSON document so an API read does not take canonical Film authority. Show rows are the availability facts (`channel`, start, end, title, basis, reason). `film_epg_last_airing` is not updated. Programme membership is kind `programme`. Watchlist order is kind `watchlist` and `ordinal`. Explicit `shows: []`, or a film with no `shows`, is a member and zero show rows. A `withheld` generation is stored and bumps `generation`. It does not move `programme_run_id`.
2. **One marker, default `r2`.** `published_epg_authority.mode` is `r2` or `d1`. The migration inserts `r2`, generation 0 and a null pointer. `published_epg_cas` fails a batch whose compare-and-swap matches nothing. It is not a switch. Applying `0008` does not publish a generation and does not set `d1`. A deploy does not apply the file. Schema v6 stays on R2: this migration refuses to create the tables there. Once the tables exist the contract is version 8 and the marker decides. A published table below version 8 fails the read. A missing binding fails closed, and so does a bound database with no `schema_contract`. The local stand-in opt-out is `PUBLISHED_EPG_DB_OPTIONAL=standin` and the Worker does not set it. Schema v8 with a missing published-EPG table, or a marker other than `r2` or `d1`, fails the read and does not fall back to R2.
3. **The contract version only moves forward, and only after the prediction schema.** The production order is `0007` then `0008`. This file does not add prediction tables. Its first statement refuses a version below 7, and a version 7 that is missing any of the ten prediction-domain tables, before it creates a table. When that prerequisite holds it creates the published tables and sets the version to 8. A trigger rejects any later update that lowers the version, including an unconditional `SET version = 7`. Readers do not treat version 8 as proof that prediction tables exist. Version 6 is not a published-EPG schema. Metadata-cache and enrichment reads that required version exactly 6 now require version 6 or later, and the sync clocks require version 5 or later, so the cache marker and the projector survive version 8. Version 8 without the cache tables is not a healthy metadata schema. Version 8 without these published tables fails the published read.
4. **The Worker publisher stages, then commits a fixed-size batch.** Chunk caps match `src/generation-stage.js`: 950 statements, 1,000,000 bytes, 90,000 bytes per statement. The claim TTL is 15 minutes. Those numbers are duplicated in `src/published-epg.js` because the Worker bundle cannot import the repository. Tests assert they are equal. A statement over the cap is refused before a write. The commit batch starts with the live stage claim (owner, nonce, claim generation, unexpired lease) and the fence, and only then moves the pointer and copies the rows. A claim that expired or was taken over fails that batch whole. The commit is `INSERT … SELECT` plus the fence update, not one statement per show. The same run id and the same payload hash is a replay. The same run id and a different hash is a conflict. A live claim held by someone else is a lease. An expected pointer that no longer matches rolls the commit back. If that generation row is absent and this owner still holds the stage, the failed stage is abandoned so a corrected retry can proceed. A killed commit leaves the stage. After the claim expires, the same payload resumes. A programme patch records the generation it read and commits only that generation; success is that generation plus one, not an unchanged fence. The module does not call `publishGeneration` in `src/epg-repository.js`.
5. **While the marker is `d1`, D1 is the published generation.** Programme, watchlist, availability, the EPG pin, catalog generation selection, admin snapshot, poster generation selection, the discovery observation index, the ratings start pin and the enrichment projector's programme and watchlist read that generation. A failed D1 read fails the caller. It does not serve a different R2 generation. `programme.json`, `watchlist.json`, their generation copies and `epg/published-generation.json` are written after the D1 commit as a compatibility mirror, each put conditional on the etag just read. Repair compares every one of those objects with the D1 documents, not only the pointer etag, and an ordinary programme or watchlist read invokes it. A pin stores the generation. `/api/programme` and `/api/watchlist` take one pin for both documents, and a patch between those reads is `published_epg_fence` with a retry, not a mixed body. While the marker is `d1`, `/api/watchlist` returns the watchlist document and does not replace it with the programme's films. A document read checks that generation before and after the read. Production activation re-reads R2 after a fresh idle check and refuses a watchlist that changed after the earlier source read. A production revert that mutates one mirror object and then fails reports that write as partial and leaves the marker at `d1`. If the mirror put fails, D1 stays the authority. Returning the marker to `r2` repairs all of those objects first and refuses while any one differs. `EPG_GENERATION_KEY` reads the live pointer, not a stale pin. Discovery candidate and decision objects stay R2. Continuation fences on the token `d1:<generation>:<runId>`. The generation copy is written before the D1 commit. The public discovery key is used only when the R2 pointer names that same run. It is not a fallback to another generation.
6. **What does not move.** Canonical Film and Person, credits, owner-reviewed names, the discovery ledger and its decisions, ratings, prediction mutable state, and `watchlist_film`. R2 remains the store for raw EPG XML and generation archives. The cron expression does not change. External Scheduled Tasks do not change. No Worker flag is added.

Not decided here, and not authorized by proposing or accepting this record: applying `0008` to production, importing the live programme, setting the marker to `d1`, reverting it, any Time Travel restore, and any manual EPG, discovery, TMDB, ratings, prediction, sync or lease operation.

## Alternatives considered

- **Reuse the v1 programme tables and `publishGeneration`.** Rejected. The Film foreign key would mint Films, and that function writes candidates.
- **One statement per show in the commit.** Rejected. A production-sized generation does not fit one request. [ADR 0021](0021-staged-atomic-generation-import.md) already separates chunk size from the fixed commit.
- **Treat the backfill `{sql}` measurement as this publisher's atomicity proof.** Rejected. The Worker uses the binding's `batch`. The operator's REST `batch` is a third transport and is not that proof either.
- **Fall back to R2 when D1 fails in `d1` mode.** Rejected. The mirror can be the stale copy the failure just left behind.

## Consequences

Two writers are refused by the claim and by the pointer compare-and-swap. A reader pinned to an old run keeps that run's document. A large show title that blows one statement fails before the pointer moves. The enrichment projector, once the marker is `d1`, ignores a stale R2 pointer and uses the D1 run; the catalog copy of that run is still required and a missing copy fails closed. Metadata sync keeps working at version 8 only because the version check is no longer exact. Code that still assumes version 6 and only version 6 would treat this schema as "not the cache" and would read `metadata.json` again.

The rendered Mermaid in the EPG, persistence and scheduling architecture pages changes. Those diagrams need a separate visual approval. This record does not grant it.

## Recovery and migration boundary

A code rollback while the marker is `r2` leaves readers on R2, whether or not `0008` has been applied. Applying `0008` leaves `mode` at `r2`. Activation is a separate command and a separate owner GO. After activation, a code rollback that only understands R2 would read a mirror that may lag. Returning the marker to `r2` is `--revert` with `--confirm r2`. Both the offline script and `scripts/published-epg-production.mjs` repair the pointer, `programme.json`, `watchlist.json` and the generation copies from D1 first, then set `mode` back to `r2` only when those objects and the membership order match. A missing confirm is a refusal. Neither script calls Time Travel restore. A successful revert keeps the rows. The production command was not run. Restoring the database is a Time Travel of the whole database and is its own approval.

`scripts/published-epg-production.mjs` is status unless given `--target iptv` and a matching `--confirm`. `--apply` sends only `0008`, and only when the version is 7, every prediction-domain table is present, and every new table is absent. Version 6 sends nothing. `--load` and `--activate` are separate confirms. The offline script refuses a database path that contains the production database id or a path segment `iptv`. Running either script against production is not authorized by this record.

## Evidence

- **Prior measurements used, not repeated:** [generation unit size, 26 October 2026](../evidence/d1-migration/generation-unit-size-2026-10-26.md) (synthetic, local; one statement per show does not fit) and the metadata-cache marker cutover pattern in [ADR 0073](0073-metadata-cache-d1-authority.md). The local tests in [the AIR-319 note](../evidence/d1-migration/air-319-published-epg-authority-2026-11-01.md) cover the marker, the fence, the lease, resume, empty shows, withhold, ordering, a killed commit, a failed mirror and a production revert that repairs a stale watchlist. They are SQLite stand-ins and a fake HTTP API. They are not a production D1 timing or atomicity measurement, and they do not treat the backfill `{sql}` body as the Worker batch.
- **Uncertainty:** production D1 batch behavior for a real programme was not measured here. `0007` is not in this tree. The agreed production order is `0007` then `0008`; applying this file first is refused, and a later `SET version = 7` is rejected.

## Follow-ups

Accept or decline this record, and visually approve or reject the changed Mermaid, are owner gates. Schema apply, import and activation are later action-specific GOs. Discovery decisions become D1-authoritative only on AIR-320, after an accepted production cutover of this domain; until then they stay R2. That card is not this one. Canonical credits and reviewed names stay on their own cards.
