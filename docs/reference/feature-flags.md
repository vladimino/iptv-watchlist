# Runtime feature flags

**Maintained contract; dated observations, not a live configuration dashboard.** Reviewed against GitHub `main` and Trello evidence on 2026-10-25 for [AIR-146](https://trello.com/c/qfqYibFB). All flags below are Cloudflare Worker **environment variables**, not switches managed by GitHub. [`wrangler.jsonc`](../../wrangler.jsonc) uses `keep_vars: true` and deliberately does not declare their production values. A code deploy does not reset these variables. The currently deployed value must be read from authorized Cloudflare settings or from the owner-only MCP tool `feature_flags` (see [Reading the deployed values](#reading-the-deployed-values)) before making operational decisions.

Do **not** interpret a source default, a dated Trello comment, or a prior deployment as proof of the live value. This page does not authorize toggling flags, launching EPG/resolver/prediction jobs, or editing R2/D1, schedules or Access. Consult the [deployment runbook](../runbooks/deployment.md) and obtain action-specific owner approval.

The explicit `off` values in this table describe **effective behavior**, not necessarily accepted textual configuration tokens. For `LIFECYCLE_LOCALIZATION`, write `on:metadata` or `shadow:metadata`, not `on`; a token for `epg`, `programme` or `watchlist` has no effect, and removing one from a binding is a settings change that needs its own owner approval.

### Interactions and operational safeguards

- The scored acceptance gate is the **only** EPG resolver; no variable selects it ([ADR 0036](../adr/0036-scored-resolution-only.md)). The former `SCORED_RESOLUTION` variable is retired: the Worker ignores it whatever value a stale binding carries, so `off` or `shadow` cannot bring the legacy resolver back. Removing a leftover binding is a separate owner-approved settings change; rolling the resolver back is a code revert, never a flag, and reverting code does not undo committed R2 objects.
- Variant discovery is an independent optional gate on that resolver: `CANDIDATE_DISCOVERY=on` adds the bounded variant searches and nothing else needs to be set. Optional searches consume TMDB budget and carry distinct throttling and skip counters; see [candidate discovery](domain/candidate-discovery.md).
- `LIFECYCLE_LOCALIZATION` reaches the metadata sync only: a mode switch changes what the next metadata sync writes into `titles.json`, `people.json` and `metadata.json`, and is not evidence that the sync ran. The EPG commit and the programme/watchlist reads apply the domain localization rule without a switch ([ADR 0037](../adr/0037-domain-localization-only.md)); rolling that back is a code revert, never a flag, and reverting code does not undo titles and names already written at an EPG commit. A binding that still carries the retired path tokens is inert for those paths.
- The owner-triggered ratings-only refresh is retired ([ADR 0040](../adr/0040-retire-ratings-only-refresh.md)). `POST /api/enrichment/ratings/refresh` answers `410 Gone` before it reads the body, the bucket or Letterboxd, so no value of the former `RATINGS_REFRESH` variable opens it. Ratings arrive with the EPG commit and the per-film lookup; the stored ratings objects stay readable through `GET /api/enrichment/ratings/status`. Removing a leftover binding is a separate owner-approved settings change; bringing the refresh back is a code change under a new ADR, never a flag. See [ratings reference](integrations/letterboxd-ratings.md).
- Every committed prediction is written as its own immutable version object, with no switch any more ([ADR 0045](../adr/0045-retire-prediction-version-objects-switch.md)). A submit that creates or recalculates a prediction writes `enrichment/films/<id>/predictions/versions/<sha256>.json` before the bundle, as it did with the former `PREDICTION_VERSION_OBJECTS=on`; the former `PREDICTION_VERSION_OBJECTS` variable is retired and inert whatever it holds, so `off` no longer stops the writer. A version-write storage error or byte conflict fails the item with `storage_error` and leaves the bundle unchanged. Objects already written stay in R2 (the Worker never deletes). Stopping the writer is a code revert, never a flag. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `PREDICTION_VERSION_OBJECTS=on` restored, or new submits write unlinked records.
- `PREDICTION_MATERIALIZATION=on` only removes the gate of the materialization route; it starts nothing. Each `apply` against production is a separate owner-approved operation that writes version objects and rewrites prediction bundles under the prediction writer lease. Switch it back to `off` after the run; objects, rewritten bundles and receipts stay. See the [prediction versions runbook](../runbooks/prediction-versions.md#2-one-time-materialization-of-historical-versions-implemented-no-production-execution-recorded-here).
- `CATALOG_POSTER_HYDRATION=on` only removes the execution gate of `POST /api/enrichment/catalog/posters`; it starts nothing by itself. Each execution call is a separate, owner-approved production operation that makes bounded TMDB detail requests and writes the `poster` field of catalog records in R2 under the resolver lease, so it competes with discovery for that lease and is refused while a chunk holds it. Switching back to `off` refuses further execution calls; posters already written stay, because they are TMDB assets of the verified id. See the [poster hydration runbook](../runbooks/catalog-poster-hydration.md) and [ADR 0020](../adr/0020-owner-triggered-catalog-poster-hydration.md).
- `LETTERBOXD_FACTS=on` changes what the **routine EPG sync writes to R2** on its next run (new `letterboxd/facts/` objects and view-index fields) and stops the films-list scan from clearing ratings by absence; it is a production writer change that needs its own owner approval before the value is set. Switching back to `off` restores the legacy writers for future runs; objects already written stay and are ignored by them.
- `LETTERBOXD_BASELINE_IMPORT=on` only removes the gate of the baseline import route; it starts nothing. Every `commit` or `rollback` against production is a separate owner-approved operation, and the route refuses to work unless `LETTERBOXD_FACTS` is on too, so the routine sync cannot clear imported ratings by absence.
- The Finds display-only title exclusion has no switch any more ([ADR 0041](../adr/0041-retire-finds-title-exclusion-switch.md)). `GET /api/catalog/available` reads `letterboxd/display-exclusion.json` on every request and applies it, as it did with the former `FINDS_TITLE_EXCLUSION=on`; the former `FINDS_TITLE_EXCLUSION` variable is retired and inert whatever it holds. A missing or invalid list still hides nothing. To show every film, remove or replace the list object (a separate owner-approved R2 operation, [runbook](../runbooks/finds-display-exclusion.md#replace-disable-roll-back)); a code revert restores the switch. Removing the leftover binding is a separate owner-approved settings change.
- The owner's «Смотрел» mark on Finds has no switch of its own any more ([ADR 0042](../adr/0042-retire-finds-watched-mark-switch.md)). The button and `POST /api/catalog/watched` are available exactly while `LETTERBOXD_FACTS` is `on`, as they were with the former `FINDS_WATCHED_MARK=on`; the former `FINDS_WATCHED_MARK` variable is retired and inert whatever it holds. Each mark is an owner-fact write to R2 (`letterboxd/facts/`, the link index and the view-index projection) and every other guard of the route is unchanged. To stop new marks, switch `LETTERBOXD_FACTS` off, which also stops every other fact writer, or revert the code, which restores the switch. Marks already written stay valid facts. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `FINDS_WATCHED_MARK=on` restored.
- The taste-profile compatibility rule has no switch any more ([ADR 0044](../adr/0044-retire-profile-compatibility-switch.md)). Every consumer (view, catalog, Finds, coverage, the queue, the runner steps and diagnostics) uses the selective rule of [ADR-0031](../adr/0031-selective-prediction-profile-compatibility.md), as it did with the former `PREDICTION_PROFILE_COMPATIBILITY=selective`: a prediction stays current only across published, owner-approved change impacts that do not reach it, and an unknown, unapproved or global change fails closed. The former `PREDICTION_PROFILE_COMPATIBILITY` variable is retired and inert whatever it holds; the queue still counts the strict outcome beside the decision. Returning to exact equality is a code revert, which also needs the binding `selective` restored if it was removed; strict would requeue every non-exact prediction. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent.
- The fingerprint transition rule decides fingerprint and prediction freshness for every consumer, with no switch any more ([ADR 0047](../adr/0047-retire-fingerprint-compatibility-switch.md)), as it did with the former `PREDICTION_FINGERPRINT_COMPATIBILITY=selective`; the former `PREDICTION_FINGERPRINT_COMPATIBILITY` variable is retired and inert whatever it holds, so `strict` no longer brings back exact equality. The queue still counts the strict outcome beside the decision; the D1 projection and the benchmark stay strict by contract. Fail-closed outcomes for unknown or unapproved transitions are unchanged. Returning to exact equality is a code revert, never a flag. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `PREDICTION_FINGERPRINT_COMPATIBILITY=selective` restored to keep today's behaviour.
- Every accepted fingerprint is written as its immutable content body and generation record before `fingerprint.json` moves, with no switch any more ([ADR 0046](../adr/0046-retire-fingerprint-version-objects-switch.md)), as it was with the former `FINGERPRINT_VERSION_OBJECTS=on`; the former `FINGERPRINT_VERSION_OBJECTS` variable is retired and inert whatever it holds, so `off` no longer stops the writer. A body or record conflict fails the film with `storage_error` before the pointer or the index moves. Objects already written stay in R2 (the Worker never deletes) and are the only source a pointer restore can use; a film whose fingerprints predate the writer has none. Stopping the writer is a code revert, never a flag. The last step of the retirement is the owner-authorized removal of the leftover binding, read back as absent; after it, a revert to code that reads the switch also needs `FINGERPRINT_VERSION_OBJECTS=on` restored, or new fingerprints get no immutable objects. `PREDICTION_FINGERPRINT_COMPATIBILITY` is a separate, active switch.
- `DISCOVERY_LEDGER_MODE=bounded` changes what the **routine EPG commit writes to R2** on its next run: new archive objects and a smaller active ledger. Once an archive exists, the manual scan and canonicalization routes answer `409`. It is a production writer change that needs its own owner approval ([AIR-222](https://trello.com/c/9Y4G9DG6)) after the offline rehearsal ([AIR-221](https://trello.com/c/9ZiVygrd)). Switching to `frozen` is rollback R1: archiving stops, and nothing is rebuilt or deleted. Removing the value later does not restore the single ledger, because `full` acts as `frozen` while an archive exists.
- `REMOVAL_RATING_LOOKUP=on` changes what the **routine EPG commit requests from Letterboxd and writes to R2**: one member-page request per due removed film (at most five per commit, at most three attempts per film, the whole queue paused for six hours after a 403 or 429) and the queue object `enrichment/removal-rating-lookups.json`, plus the rating writes the per-film lookup already makes. It is a production writer change that needs its own owner approval before the value is set ([AIR-268](https://trello.com/c/7ePpEYev)). Switching back to `off` stops queueing and requests on the next commit; the queue object and ratings already written stay.
- `LETTERBOXD_DIARY_HISTORY=on` changes what the **routine EPG commit requests from Letterboxd and writes to R2**: up to three diary pages per commit and two new objects under `letterboxd/diary/`. It never writes a rating, watched or watchlist fact and never changes `actualRating`. It is a production writer change that needs its own owner approval before the value is set ([AIR-51](https://trello.com/c/33d4hKJ3)). Switching back to `off` stops the requests and writes on the next commit; stored history stays.
- These switches are **not** Cloudflare Worker Cron settings, external ChatGPT Scheduled Tasks, secrets, API tokens or `wrangler.jsonc` deployment/binding parameters. `BUCKET`, `TMDB_API_READ_ACCESS_TOKEN`, `LETTERBOXD_USERNAME`, and `EPG_XML_URL` are dependencies/configuration, not feature flags.

## Reading the deployed values

The MCP tool `feature_flags` ([MCP contract](api/mcp.md), [ADR 0039](../adr/0039-allowlisted-feature-flag-readout.md)) returns, in one call, every flag of this page plus the retired `SCORED_RESOLUTION`, `RATINGS_REFRESH`, `FINDS_TITLE_EXCLUSION`, `FINDS_WATCHED_MARK`, `PREDICTION_PROFILE_COMPATIBILITY`, `PREDICTION_VERSION_OBJECTS`, `FINGERPRINT_VERSION_OBJECTS` and `PREDICTION_FINGERPRINT_COMPATIBILITY`, from the bindings of the Worker version that answers. The registry it reads is `src/feature-flags.js`; a test keeps it, the contract table above and the governance checker's flag list in step.

| Field | Meaning |
| --- | --- |
| `state` | `absent` (no binding) or `set` |
| `raw` | The literal value when every comma-separated part, after trimming, is one of the flag's accepted or retired tokens and the value is at most 200 characters; otherwise `null` |
| `redacted`, `shape` | `true` with `{type, length}` (or `{type}` for a non-string) when the value is not made of known tokens. A typo or a pasted secret is never echoed |
| `valid`, `issue` | `valid` is `true` for an absent binding or a value the code accepts as written. `issue` is `case_or_whitespace` (a known token with other case or padding where the code does not trim), `unrecognized`, `not_string`, `unrecognized_tokens` or `retired_tokens` (for `LIFECYCLE_LOCALIZATION`), or `retired` (a `SCORED_RESOLUTION`, `RATINGS_REFRESH`, `FINDS_TITLE_EXCLUSION`, `FINDS_WATCHED_MARK`, `PREDICTION_PROFILE_COMPATIBILITY`, `PREDICTION_VERSION_OBJECTS`, `FINGERPRINT_VERSION_OBJECTS` or `PREDICTION_FINGERPRINT_COMPATIBILITY` binding exists) |
| `effective` | The mode the code uses, computed by the consumer's own function; `null` for a retired flag |
| `requires`, `effectiveWithRequirements`, `unmetRequirements` | For `LETTERBOXD_BASELINE_IMPORT`: the flag the route also needs, and the mode once that need is applied |
| `registryVersion`, `readAt`, `summary` | Registry version, read time, and counts of registered, set, absent, invalid and redacted flags |

The tool reads no other binding, no storage and no Cloudflare API. It does not say who set a value or when, and for `DISCOVERY_LEDGER_MODE` it does not see whether an archive makes `full` act as `frozen`. A read through it is a verified read for the ledger below; it authorizes no change.
