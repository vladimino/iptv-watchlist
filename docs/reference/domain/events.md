# Events log

The activity list reads objects under `events/items/`. The key is `events/items/<reverse-timestamp>-<id>.json`, so a page is newest first. `GET /api/events` returns one page and writes nothing: it does not deliver or recover anything, however often it is read or paged ([ADR 0107](../../adr/0107-get-head-read-side-effect-boundary.md), [AIR-416](https://trello.com/c/f7FX4Elk)); see [delivery of prediction run events](#delivery-of-prediction-run-events). Clients ignore an event type they do not render. A rendered event shows its `at` in Europe/Madrid and does not show storage keys, hashes, prompts or profile text.

| `type` | When it is written | What the list shows |
| --- | --- | --- |
| `epg` | The successful end of an EPG run (its completion time) | Counts of films and broadcasts |
| `watchlist` | A watchlist commit | Added and removed films |
| `discovery` | One **scheduled hourly firing** of the Discovery reconcile, for its UTC hour ([ADR 0111](../../adr/0111-discovery-hourly-reports.md)) | One compact report: the deltas of the hour (new films, observations resolved, reused, screened, TMDB calls), what is left in the queue and the state at the firing, even while a Workflow runs |
| `ratings` | A Ratings run that ended (finished, error or closed as unknown) | One compact result: Diary rows checked, new facts, removals handled, honest error or interruption |
| `started`, `unstarted` | An owner mark on one film | The film title |
| `enrichment` | A prediction run's start, progress, stop or completion | Queue progress, separate from profile publication |
| `taste_profile` | One committed move of the taste-profile current pointer | Version transition, a short category and selective or global scope |

## Taste-profile publication

`PUT /api/enrichment/profile` writes this event only after compare-and-swap has made the version current ([publication contract](../api/enrichment.md#taste-profile-publication)). A dry run, a refusal, a lost compare-and-swap and a version record that is not current write none. The current pointer may be the R2 object or the D1 profile row. The event is always the R2 object above. The two writes are not one transaction.

```json
{"id":"taste-profile-3","type":"taste_profile","at":"2026-11-02T20:15:00.000Z","fromVersion":2,"toVersion":3,"changedFields":["horrorPreferences"],"scope":"selective"}
```

`id` and `at` come from the committed version (`taste-profile-<toVersion>` and that record's `updatedAt`), so a replay stores the same object and does not append another. `fromVersion` is the previous lineage link, or `null` when this version has no stored predecessor. `changedFields` are the field names the publisher already accepted, not the field text. `scope` is `selective`, `global`, `identity`, or `null` for the first version. The profile body, `profileHash`, approval and declaration hash are not copied.

The list turns one known field into a short category, several known fields into one summary line, and `identity` with no known field into a line that the content did not change. `selective` and `global` become «Влияние: выборочное» and «Влияние: глобальное». Any other scope adds no impact line. An unknown field name is not printed. Nothing in this event is a count of recalculated predictions.

If the event put fails, the publication response stays HTTP 200 and adds `publicationEvent: {recorded: false}`. Current stays where it is. The identical request then answers HTTP 409 `version_not_increasing`, does not move current, and records the missing event only when the committed version body has `tasteProfileEventExpected: true`. That field is server-written on the immutable version record. A version without it, including one that was already current before this writer, stays without an event; a caller-supplied field does not create one. A different body for that same version does not. The procedure is in the [publication runbook](../../runbooks/taste-profile-publication.md).

## EPG and watchlist events: publication, retry and idempotency

Contract of [AIR-359](https://trello.com/c/0IV9qKWR).

- **One `epg` event per published generation.** Its id is `<runId>-epg`, and `films`, `archive`, `future` and `broadcasts` are counted from the published report. Its `at` is the **successful end of the run**: `run.completedAt`, the value that becomes `sync.json` `updatedAt` when the run is `complete`. The header «Обновлено», the compact and detailed EPG footer (`integrations.sources[id=epg].lastSuccessAt`) and `GET /api/programme` `publishedAt` use that same instant. It is not the scan time (`report.updatedAt` / D1 `published_epg_generation.published_at`, which still copies the scan clock at pointer switch and still defines the archive and future windows). A later in-flight or failed run carries `sync.json` `lastEpgPublishedAt` so those surfaces keep the last completion and never show `startedAt` or `dueAt`. A missing or invalid clock is omitted (`null` / «нет данных»), never wall-clock now. The event is written only **after the run record is durably `complete`**: by `finishSync`, or at the end of the staged seal `queue` phase, never in `finalize`. A run that has not published or whose complete record could not be saved leaves no event, so there is no false «Обновлён EPG». Pointer switch can precede run completion (catalog/tail); the UX clock waits for completion so it matches this event, and stored events are not rewritten.
- **Order and recovery.** The completion step fixes `run.completedAt`, parks the finished event in `run.epgEventPending` and saves the complete run record (`stage: complete`, `updatedAt = completedAt`, the mark) in one write. Only then is the event put and the mark cleared. If the record save fails, nothing was exposed and the retry completes the run. If the event put or the clearing save fails, the persisted complete run keeps the mark and the next step on it (the complete-run continuation) writes the same event again and clears it: the event is then late, never false, and never duplicated. The key `events/items/<reverse-timestamp>-<runId>-epg.json` is derived from the parked `at`, so every retry hits the same key, and `sync.json` `updatedAt` carries the same time. Only the `epg` timestamp changed: the watchlist event, its removal-reference key rules and the other event types are untouched, and events already written are never rewritten, moved or deleted (the 8 November 17:01 entry keeps its scan time).
- **Run in flight across the deploy.** A staged run whose `epg` event was already written under the scan time by earlier code (its `finalize` ran before the deploy) keeps that event and gets no second one; its `completedAt` stays unset.
- **Rescan inside a run.** If an earlier attempt of the same run failed before the pointer moved, the next scan builds the events again for the scan it is about to publish (`epgSync` rebuilds them when the saved `epg` event does not carry the new `updatedAt`). A run saved by earlier code that still carries an `epg` event of a superseded scan has that event rebuilt from the published report when the run completes (its `at` is then the completion time).
- **Watchlist event.** Its diff (`added`, `removed`, `total`, `baseline`) is computed from the watchlist before the run and the run's watchlist, so a rescan yields the same delta. An event with no removal is rebuilt for the new scan and carries the published time. An event that reports removals keeps its key, and with it the time of the first scan of the run: the removal hand-over references the event by key (`events/items/<reverse-timestamp>-<id>.json`, derived from `at`), the commit hands the references to the removal queue **before** it publishes, and a queue entry cannot be re-pointed afterwards, so a rebuilt key would leave that reference dangling. For such an event `at` therefore denotes the watchlist observation (the first scan of the run that saw the removal), not the EPG publication. This is a contract decision that needs the owner's approval ([AIR-359](https://trello.com/c/0IV9qKWR) records the request); the alternative is to hand the references over only after the publication, which changes the commit order and needs its own card.
- **Ratings at the first display.** The watchlist event is written with the confirmed ratings the fact store already holds for its removed films (at most 25 probed; stored facts only, no Diary, no Letterboxd request, no wait; see the [ratings reference](../integrations/letterboxd-ratings.md#the-epg-commit-under-the-separate-pipeline)). A film rated before the publication is shown with its rating at once (the half-star value is kept); a film with no stored fact, a null rating or no probe stays unrated and is listed as «Остальные удаления», never as viewed on the strength of a missing rating. A removed film that carries a confirmed half-star rating is listed as «Просмотрены»: the rating on an event comes only from a confirmed fact (the fact store, Diary or the owner's film page), never from a prediction or from the removal itself, so the group states a known viewing. A rating that arrives later enriches the **same** event (same key, same `at`, one event, other confirmed ratings kept) through `settleRemovalRefs`. Listing events (`GET /api/events`) looks nothing up. On the daily schedule the Ratings run (17:00 Madrid, seconds long) normally finishes before the EPG commit, so a rating that Diary shows that day is already stored; a rating that Diary does not show yet waits for the next daily Ratings run, which settles it on the same event.
- **Idempotency.** A repeated `finishSync`, a resumed committed run and an events refresh write the same keys; no second event is created. Events written by earlier code are not rewritten, and ordering and pagination by key are unchanged.
- **Not covered.** A one-off correction of an event that was already written with a stale time (the 5 November 17:03 entry and the 8 November 17:01 entry) is a separate owner-approved action: exact key, idempotency and readback. This contract changes code only.

## Ratings run result (`ratings`)

Contract of [AIR-361](https://trello.com/c/pKYwrxcZ). One immutable event per Ratings run that reached a terminal state in the run record (`finished`, `error`, or `unknown` when a stale or interrupted run is closed). Never one per film, per step or per heartbeat, and none for a run that never started or whose terminal state was not persisted.

| Field | Meaning |
| --- | --- |
| `id`, `runId` | `<runId>-ratings` and the run id. The Workflow instance id, the hour and the generation time play no part |
| `at` | The run's real end (`finishedAt`, or `closedAt` for an unknown close); the key is `events/items/<reverse-timestamp>-<id>.json` as for every event |
| `state`, `cause` | `finished` / `error` / `unknown`; `cause` is one of `failed`, `blocked`, `rate_limited`, `interrupted`, `abandoned`, `diary_off` or null |
| `trigger` | `scheduled` or `manual` |
| `coverage` | `recent_window` while only Diary page one was read; never «whole history checked» |
| `diary` | Counts only: `pages`, `rows` (checked), `added` and `updated` (Diary entries), `written` (facts written), `unchanged`, `skipped` (already recorded), `conflicts` |
| `removal` | `pending` at the start, `checked` lookups, `rated` (removed films whose rating was found in this run, by Diary or by a lookup) and `resolved` (removal references of the Events Log settled with a rating, including films rated earlier). The two count different things and do not overlap; a rating whose reference could not be settled counts as `rated` only |
| `details` | Optional, [AIR-393](https://trello.com/c/45smSEfH). Only for the films this run **changed**, absent when it changed none and on every event written before the field (those render as the short summary, with no backfill). Groups, each a list of `{id, title, year, tmdb, rating}`: `added` (a new watched fact; `rating` null for a view without a rating), `updated` (a different rating, with `from` only when the earlier one was a stored number), `rated` (a removed film whose rating a member-page lookup found for the first time in this run) and, on events written before [AIR-443](https://trello.com/c/Av5rDn3M), `resolved`. **The lists are news, the counters are work.** A rating the user was already told about is never announced again: a removed film whose rating the Diary supplies is either `added` in the same run (a first fact) or already known from an earlier run, so it is not listed as `rated`; settling a removal reference with a rating that is already known is service work and has no list at all (new events carry no `resolved` list; `removal.resolved` keeps counting the references settled), and a film the run reported as `added` or `updated` is not also listed as `rated`. A film appears once per group, so a film with two references is listed once while `removal.resolved` counts both. The removed film in `added` is named from its removal event when the metadata does not know it. **Records written before AIR-443** carry no `news` marker on their Diary page contributions; their `rated` and `resolved` lists mixed Diary reconciliation with news and cannot be told apart, so neither is passed on when such a record builds its event, while the removal contribution (lookups only) is kept. The hidden `resolved` remainder never makes an event `incomplete`; a page marked incomplete or an overflow of a visible group still does. Events already published are not changed. At most 25 films per group; `more: {<group>: n}` counts the rest, so nothing is cut silently. `incomplete: true` states that some change could not be captured or named. `id` is the Letterboxd film id (never shown as a title); `title`/`year` are null when no stored source knew them; `tmdb` is set only where every stored id agrees |

Written, read and unchanged are different numbers: 50 rows checked with one new fact reads «записей проверено 50, новых фактов 1». The aggregates carry only numbers. The optional `details` carry titles, years and ratings of the changed films only, never Diary rows, URLs, the unchanged 50 or raw Letterboxd content.

**Delivery.** The D1 run record is the source and R2 is a projection, and the two are not atomic. An event is built from a **committed** terminal record only and put with a create-only precondition, so a repeat finds the key and writes nothing; a close that a start has not committed (a compare-and-swap that is lost) publishes nothing. It is delivered right after the terminal commit and again at the next look: a start (after its own commit), a terminal read by the Cloudflare executor, the closing of a stale run, or the hourly executor tick, so a missed event is repaired without starting Ratings again. The run is marked `ratingsEventAt` once delivered. If the record is replaced before delivery, the owed event moves to the new record (`pendingEvents`) with a retry time (15 minutes, doubling to a day), so the attempt rate is bounded but the outcome is never given up on. Only when more than 60 outcomes are owed at once (about two months of daily runs with the Events Log unreachable) is the oldest discarded, and `eventsDropped` on the run record counts it. The owner accepted this bounded policy on 2026-11-06 (AIR-361 review); keeping overflow without loss would need another store and a new decision. A failed put never fails the run, never reads Diary again and never repeats a step; the status reads and writes nothing. Events for runs that ended before this change are not created.

**How the details are taken (AIR-393).** They are recorded on the run record while the run works and are never rebuilt afterwards. A plan is an intent and a receipt is a fact, and only receipts reach the event. For the Diary page, the films it will change (a new watched fact, a different rating, a removed film whose queue entry the Diary will resolve) are **planned from the view index before any fact is written** and saved on the record under the page's own key, `diary.pageChanges[<page>]`, in state `planned`, so a kill after the facts are written cannot lose them. The page checkpoint then saves the contribution in state `applied`: on the first attempt narrowed to the writes that really happened (`applyDiaryEvidence` outcomes and the queue entries the Diary resolved); on a replay of the page (a plan already stored) narrowed to what the stored view and queue show now (a film that is watched, a rating equal to the planned one, a queue entry resolved by the Diary), so a write another writer won, or one the page lost as older, is not claimed. This is a check of the stored **state**, not of who wrote it: a replay cannot tell this page's own earlier write from another writer's identical value stored after the plan, so for a replayed page `details` state what the stored data shows changed during the run, not a proof of which writer changed it. A first attempt is stricter: it claims only the writes its own `applyDiaryEvidence` reported. A contribution that stays `planned` (the page never completed: a failed, blocked or abandoned run) is ignored by the event. The plan and the confirmed contribution keep **every** candidate of the page (a page holds about 50 rows; the hard ceiling is 100 per group), so the confirmation covers the whole page, not only the films an event can show; the event is built from the confirmed lists and only then shows the first 25 and counts the rest, so the remainder is exact. A replay replaces its page's contribution instead of adding to it, so a remainder is never counted twice. Past the ceiling the count is a lower bound and the event carries `details.incomplete`. If the planning, reading or saving of a page's details fails, the facts are still written and the contribution is saved as `incomplete`: the event then carries `details.incomplete: true` and the screens say the list is incomplete, never a complete-looking list. The removal steps work the same way. Before a step settles a reference or looks a film up, it saves an **intent** (`removal.intents`: the film, and the reference's event key for a settlement) on the run record; after the effects it confirms each intent against the stored queue (a `rated` film is a queue entry in state `rated` with a half-star rating; a `resolved` film is a reference that is marked resolved) and moves the confirmed films into `removal.changes`, clearing the intents. A kill after a lookup or a settlement, before that confirmation, leaves the intents on the record, and the **next step confirms them before it starts**, so the film is neither lost nor claimed twice. An intent whose effect did not happen (a film that was not rated, a reference whose event is missing) is dropped, not claimed. As for a replayed Diary page, this confirms the stored state, not which writer produced it. `rated` (rating discovery) and `resolved` (reference settled) stay separate groups, a film with several references appears once in `resolved`, and the counters keep their meaning. `removal.changeSteps` keeps the recent confirmation tags, so a repeated merge of one confirmation is ignored. The event merges the applied page contributions and the removal contribution. The counters of the Diary page are still saved with the step summary, as before this change, so a step killed after its page checkpoint loses that step's counters (the event can then show `0` written next to a list of films), never its films; the list is the receipt, the counter is the older, coarser number. The names come from what is already stored: the removal event that listed a removed film, otherwise the metadata cache and the title dictionary. No Letterboxd or TMDB request is made for a name, and `GET /api/events` reads nothing extra. Because the event is built from the committed record, a retry, a checkpoint between steps, a lost create-only put and the carried delivery all produce the same `details`; a repeated delivery changes no stored event. `rated` and `resolved` are different measures: the same film may be in both, and neither list is added to the other's count. The details are bounded by construction (4 groups, 25 films per contribution and in the event), also in the carried `pendingEvents` list.

The events screen and the compact feed draw each non-empty group as an expandable list like the watchlist event. A film is a local link to `/film/tmdb_<id>` only when `tmdb` is present; without a stored title it reads «Название недоступно», never its id; a rating is shown only when it is a half-star between 0.5 and 5.

## Discovery hourly report (`discovery`)

**Boundary (AIR-410 v2, [ADR 0111](../../adr/0111-discovery-hourly-reports.md)).** Every **real scheduled hourly cron** of the Worker writes exactly one `discovery` event for its UTC hour, whatever the Discovery pipeline is doing: a Workflow chain that runs for hours across rollovers (with or without results in the hour), a wait for a successor, a typed refusal (`projector_window`, authority held, generation handoff...), exhausted recovery, a generation handoff, nothing to run, or a confirmed empty queue. The chain and its terminal stop write no event of their own. An unscheduled caller (an operator or MCP reconcile, a test) writes none, a cron tick without Workflow admission writes the report of its hour as the typed refusal, and no report is invented for an hour in which the cron did not fire: a missed hour is not backfilled (a gap is for the Monitor), and the next report says how far back it reaches in `from`.

**Identity.** `id` is `discovery-hour-<first 12 characters of the published generation without dashes>-<UTC hour as YYYYMMDDTHH>`; `at` is the start of that UTC hour. The same generation and hour always have the same key, so a duplicate, delayed or concurrent cron of the hour finds its report and writes nothing. A firing of an hour that is not later than the last closed one (`lastClosedHour`; the compact UTC keys sort chronologically) is rejected without changing the record, so a delayed or replayed old hour can never close an accumulator that already holds the chunks of a later period under an existing id; it may still drain the outbox. UTC hours make the key independent of DST: the repeated local 02:00 hour of the October change is two different hours with two reports. `generation` is the first 8 characters of the generation.

**Fields.** `kind` is `hour`. `from` is the end of the previous period (the `at` of the previous closed report, `null` before the first; after an hour whose close failed it reaches back past that hour). `status` is one of: `running` (a chain was started by this firing or is in progress), `waiting` (`recovery_waiting`: a successor waits for its backoff), `blocked` (a typed refusal in `reason`, or `other` / `unknown`), `failed` (`recovery_exhausted`), `empty` (the queue is a confirmed zero) or `idle` (stopped, nothing to start, the queue is not proven empty); `reason` is the typed reason or `null`. `chunks` is the number of chunks whose checkpoint was saved in the period. The counters are `checked` (observations processed), `added` (new catalog films), `reused`, `screenedOut`, `touched` and `tmdbCalls`, **deltas of the period**, not lifetime totals: the sum of the counters of consecutive reports equals the sum of the committed chunks. `remaining` is the last known queue size (`null` when unknown), `queueEmpty` is `true` only when the queue is a proven zero, `queueUnreadable` is `true` when the queue could not be read while the deltas of the period are real, `incomplete` is `false` on every event written since [ADR 0118](../../adr/0118-discovery-report-failure-notice.md) (an event written earlier can carry `true` with every number `null`), and `error` is a code from a fixed list or `null`. No film, title, key or free text is stored.

**Counting model.** Attribution is by **commit time**. The executor record (`epg/discovery-workflow.json`, D1 when the Discovery authority is `d1`) carries one open accumulator `report`. Each chunk checkpoint adds that chunk's summary to it inside the owner's compare-and-swap and records the chunk key (`<instance id>:<ordinal>`) in a bounded `seen` list, so a retried or replayed checkpoint adds nothing a second time. A chunk belongs to the period in which its checkpoint was saved, whatever series or generation it ran in. The cron closes the period in **one** compare-and-swap of the same record: it appends the report event to the `outbox`, resets the accumulator (`since` = the hour start, `lastClosedHour` = the hour) and keeps `seen`. A checkpoint racing the close either lands before it (in this report) or after it (in the next), never in both: the compare-and-swap decides, and the close reads the record again after losing it. A checkpoint that is not saved loses its numbers, so the counters are a lower bound by exactly that.

**Empty and unknown.** The queue is empty only when `remaining` **and** the cheap-pass remainder are proven numeric zeros, with no error, **and** the continuation of the generation says `complete`. A missing, `null`, negative, fractional or non-numeric part is unknown and never read as zero. The period's own chunks are the freshest reading **only for the generation that wrote them**: the accumulator remembers the generation of its last chunk (`queueGeneration`), and a report of another generation (the record was replaced after the chunk) keeps the committed deltas but never reuses that backlog or `empty` state. Without a reading of its own generation, the last saved status of the published generation is used (a status of another generation is not), and otherwise the queue is unknown (`remaining` `null`, `queueEmpty` `false`). An unreadable queue source leaves `remaining` `null`, `queueEmpty` `false` and sets `queueUnreadable`; the deltas of the period are still reported. When the record cannot be read or written (no record, an unreadable record, a held projector window, lost compare-and-swaps, an outbox at its limit), the close writes one **`report_failed` notice** for the hour instead of a report ([ADR 0118](../../adr/0118-discovery-report-failure-notice.md)) and leaves the accumulator untouched, so the deltas appear once in the next report, whose `from` reaches back to the last closed report. The notice has `kind` `report_failed`, **the same id as the report of that hour** (`discovery-hour-<generation>-<UTC hour>`, one canonical identity per generation and hour), `at` the hour start, `generation`, a typed `reason` (`no_record`, `state_unreadable`, `outbox_full`, `projector_window`, `write_conflict`) and `status`, which is `failed`, `waiting` or `blocked` only when the reconcile of that firing confirmed that Discovery state and `null` otherwise. It has no counter, no `remaining`, no `from`: nothing is shown as a number, an unknown or a zero, and a report failure never implies a Discovery failure. It is not stored in the executor record (that write is what failed): it is put create-only straight into `events/items/` and never replaces anything, while a **report of the same hour replaces its notice** by a compare-and-swap on the notice's etag (an existing report is kept), so the journal holds exactly one event per hourly firing. When the journal refuses a notice, it waits in a separate ledger (`events/discovery-report-faults.json`, its own compare-and-swap) that never evicts: one compact tuple per undelivered hour, at most 8,760 (a year of hours; at the bound the newest is refused and logged `lost`), drained oldest first, at most 64 entries a firing, before each later scheduled close. Delivery is eventual during a journal outage; with the journal and the ledger both refusing, only the log line `discovery_hour_close_failed` (`notice`: `delivered`, `queued` or `lost`) remains. A report of an hour that already holds its notice replaces it.

**Delivery and idempotency.** The event is written create-only under its id in `events/items/`; a second put finds the key and keeps the first. The one deliberate exception is the Discovery `report_failed` notice of an hour: the report of the same hour replaces it by a compare-and-swap on its etag, and nothing else is ever replaced. The report is first durable in the `outbox` of the executor record (the same compare-and-swap that closes the period), and delivered after it by the closing cron or by the next one; an entry leaves the outbox only after its put is confirmed, and the record is written back with `updatedAt` unchanged so delivery never hides a stalled instance. A lost put is therefore never a lost report, and a crash between the put and the removal only repeats an idempotent put. The outbox holds at most 64 entries and drops nothing: at the limit a close first tries to drain it, writes the `report_failed` notice of the hour with the reason `outbox_full`, leaving the deltas in the accumulator (coalesced into one later report). The close never starts a Discovery step or a TMDB call, uses no lease, takes only the existing record compare-and-swap that a held projector window already refuses softly, and a replacement of the executor record (a newer generation) carries `report` and `outbox` into the new record. `GET /api/events` returns the stored event unchanged and writes nothing for it.

**Compatibility.** Events of the earlier per-chain model (`kind` `run` or `empty`, written before ADR 0111) stay readable and keep their card. A legacy `tick` left in an executor record is delivered once if it was settled and not yet delivered, and an open legacy `tick` is dropped (its lifetime totals are not a report). The legacy `outbox` entries are delivered as they were.

**Window wait and provisional empty.** The hourly close waits out a held projector window (at most three tries, each bounded by the window deadline) and re-reads the record before retrying. If the window outlasts the firing and the queue is proven empty for the same generation with zero deltas, a confirmed `empty` status of this firing and a record of that same generation, the normal `kind=hour,status=empty` event is published with `provisional: true` and the record is not written. A report of the same hour replaces a notice or a provisional event by compare-and-swap; a provisional event never replaces a report. See [ADR 0118](../../adr/0118-discovery-report-failure-notice.md).

**Display.** The events screen and the compact feed draw one compact card from fixed sentences chosen by `status` («Найдено новых фильмов: N», «Новых фильмов не найдено», «Discovery работает, новых результатов за час нет», «Очередь Discovery пуста», «Discovery ждёт повтора», «Discovery не запустился: временный отказ», «Discovery остановлен после повторных ошибок», «Discovery не работает: запуска не требовалось»), the three numbers (new films, observations resolved, left in the queue), one line with reused, screened and TMDB counts and the start of the period. A proven zero is drawn as `0`; a part that is `null` or not a non-negative integer is drawn as «неизвестно», a `report_failed` notice as «Отчёт за час не удалось сформировать. Если за этот период что-то было найдено, оно войдёт в следующий успешный отчёт.» with no numbers (plus the fixed sentence of a confirmed Discovery state), an event stored before ADR 0118 with `incomplete` `true` as «Отчёт за час неполный», an unread remainder beside real numbers as «не удалось прочитать» with one note, and nothing stored reaches the page as markup (no reason code or error text is printed).

## Delivery of prediction run events

A prediction run writes two kinds of `enrichment` events at fixed points: `prediction-start-<runId>` when it starts and `enrichment-<runId>` when it stops for a systemic reason (quota, a provider or storage error, a lost or expired lease). Each has a **durable record** written before the journal item: `enrichment/start-events/<runId>.json` and `enrichment/stop-events/<runId>.json` hold `{event, delivered}`. The journal key is derived from the event's `id` and `at`, so writing the same event again rewrites the same item: a repeated or concurrent delivery cannot duplicate it.

**Owner.** Delivery belongs to the Predictions writer ([ADR 0107](../../adr/0107-get-head-read-side-effect-boundary.md), [AIR-416](https://trello.com/c/f7FX4Elk)); no read delivers anything.

- **At the event.** The start and the stop each try the journal three times. On failure the record stays `delivered: false`, the stop answers `eventPending: true`, and the record's key is noted in the outbox index `enrichment/event-outbox.json` (`{pending: {<key>: {since, attempts, lastAttemptAt, quarantined}}}`).
- **At the next authorized start** (`POST /api/enrichment/start`, MCP `prediction_start`), inside the writer lease and before the new run is admitted, `deliverPendingEvents` spends a budget of 20 entries a start, in a fixed order: first the two records of the latest run (so a process that ended between the record and the journal is covered without any note), then the pending index entries, oldest first. Quarantined entries are counted for the status and never take a slot, so any number of them cannot keep a later event from being delivered. An undelivered start event is written to the journal; an undelivered stop is completed through the same idempotent stop path the run took (run record, diagnostic row, journal item). A stop that a later run superseded is settled without a journal item. The start never fails or waits because of the outbox, and with nothing pending it writes nothing for it. It lists no prefix, so its cost does not grow with history.
- **Bounded retries.** A failed delivery stays in the index with one more attempt. After 8 attempts the entry is `quarantined`: it is not retried and not read again, its record is kept, and it is not published until a separate owner-approved replay.
- **Visibility.** `GET /api/enrichment/status` returns `eventOutbox: {pending, quarantined, oldestSince, maxAttempts}` from the index (a pure read), and every sweep that found work logs one `prediction_event_outbox` line with its counts.

**Limits.** An event appears without anyone opening the page, at the latest when the next run starts (the hourly Predictions Task). If no run starts, an undelivered event waits. A record that was left undelivered before this delivery existed, belongs to a run that is not the latest and is not in the index, is not found by the start; publishing it is a one-off owner-approved replay. A code rollback does not remove journal items, records or the index.

## Type filter on the events screen

The events screen (`/events`) shows the one feed of `GET /api/events` in its main column; its sidebar holds a single-select group of seven buttons, «Тип событий». The filter is applied in the browser to the events already loaded, never on the server, and it never changes the loaded set or the cursor. The compact feed of the programme and film pages is not filtered.

| Button | Stored `type` values it shows |
| --- | --- |
| «Все события» (default) | Every loaded event, including a type the page does not know |
| «Watchlist и просмотр» | `watchlist`, `started`, `unstarted` |
| «Программа» | `epg` |
| «Находки» | `discovery` (one Discovery hourly report, separate from the prediction runs of «Прогнозы») |
| «Оценки» | `ratings` |
| «Прогнозы» | `enrichment` (start, progress, stop and completion of a prediction run) |
| «Модель вкуса» | `taste_profile` (a profile publication, not a prediction run) |

The choice is the `type` query parameter of the events URL, next to the `return` target of the programme page; the default needs no parameter, an unknown value means «Все события», and a deep link, a reload and Back or Forward restore the pressed button. Changing the choice replaces the current history entry.

**Automatic pagination.** Choosing a type (and opening `/events` with one) loads the following pages by itself, in cursor order and one request at a time, until 10 loaded events match or the cursor is exhausted. A page with no match neither stops the search nor needs a click, and events that are already loaded are reused, so nothing is read twice. While it searches the page says «Ищем более давние события…» with the number of matches found among the loaded events, and the matches found so far are listed. When 10 are loaded the search stops and «Более давние события» stays for manual paging. «Все события» never searches: it shows the first page and the manual button.

The search stops at once, and its request is aborted, when the type or the screen changes. It stops on an API error (the reason is shown with «Повторить»; there is no automatic retry, and the retry resumes from the cursor that failed) and on a cursor that repeats or does not advance (a visible message and the same «Повторить»). An empty result is reported only when the whole archive has been read: «Во всём доступном архиве событий этого типа нет.» Before that, a type with no loaded match says «Среди загруженных событий этого типа пока нет.» A count is always a count of the loaded events, not a total. Events are keyed by `id`, so a page that repeats an event does not list it twice. Each page is a normal read of `GET /api/events`, which may also recover an undelivered prediction stop event (see above): this is not a safe production probe.
