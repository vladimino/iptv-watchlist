# ADR 0019: Live D1 backfill reads a verified production R2 baseline and maps identities by rule

**Status:** Proposed

## Context

[ADR-0017](0017-staged-d1-migration.md) stages the migration: offline parity, then a separately approved live backfill, then shadow writes and reads. The offline stage is complete and honest about its limits: against the 19 October 2026 archive the importer stored 18,412 receipts but reported 1,591 `reference_missing` conflicts, 45,586 unportable units and 2,533 unmapped objects, and `claimsFullParity` was false ([AIR-73 report](../evidence/d1-migration/air-73-offline-run.md)). Running that importer unchanged against production would reproduce those gaps, so it cannot satisfy the AIR-74 acceptance (a reconciled current baseline, idempotent reruns, recovery, manifest).

The repository today has no read path for a *current* production baseline. The only exporter (`migrationExportRoute` in `src/worker.js`, `scripts/migration-export.mjs`) is pinned to the legacy Site origin and refuses the Worker origin by design. Production R2 is written continuously by the two external Scheduled Tasks (hourly discovery and predictions, daily EPG publication), so an R2 listing is never an atomic snapshot. The D1 repositories (`src/canonical-repository.js`, `src/epg-repository.js`, `src/prediction-repository.js`) perform every write as a buffered, write-only transaction (the offline adapter rejects a read inside one), which is the shape a D1 batch can execute atomically. `wrangler.jsonc` carries only the R2 binding; the Worker must keep running on R2 throughout this stage.

## Decision

This ADR proposes the boundaries of the first live backfill. Nothing here is decided until the owner accepts it; nothing here authorizes a read of production R2, a D1 resource, a token or a write.

1. **Baseline source.** The backfill imports a verified baseline of the production bucket `iptv`, never the 19 October archive and never the legacy Site. The baseline is a local snapshot in the existing manifest shape (per-object key, size, ETag, raw-byte SHA-256, aggregate SHA-256, two bracketing listings), taken with read-only credentials scoped to the bucket. The preferred mechanism is a read-only R2 API token used by a local exporter over the S3-compatible API, because it needs no production Worker change, no Access change and cannot write by scope; the alternative is extending the Worker export route to the Worker origin behind Access, which deploys export code into production and needs an Access service token. The owner picks one; both are read-only by construction.
2. **Consistency proof while writers continue, or an explicit alternative gate.** R2 listings are paged and not atomic, so two equal listings alone do not prove that the downloaded bytes form one cut. The proof the exporter must produce is this, and an attempt that cannot produce it is discarded, not accepted:
   - *Per object:* every download is a conditional read of the exact listed version (ETag and R2 `version`, as the existing exporter already does with `head` before and after and `If-Match` on the GET), so each stored byte sequence is provably the listed version of its key, never a newer or partial one.
   - *Across objects:* every multi-object write in this Worker runs under a lease object (`epg/resolver-lease.json` for discovery and publication, `enrichment/writer-lease.json` and `enrichment/runner-lease.json` for predictions) or inside an EPG run recorded in `sync.json`; acquiring, renewing or releasing a lease rewrites its object and therefore its ETag. The cut is the closing listing. A **final fence** re-reads, after the closing listing has finished, the lease objects, the generation pointer, `sync.json`, the continuation record and `enrichment/profile/current.json`, and requires each to have the ETag the opening listing saw. Unchanged fence objects prove that no leased writer and no EPG run started between the opening listing and the fence, so the per-key cuts of the closing listing belong to one quiescent interval.
   - *Unleased writers:* the remaining writers are owner actions (profile publication, actual-ratings `PUT`, started markers, filter presets) and read-path recovery writes (`events/`, stop events, the view-index ratings seed). The owner refrains from the first group during the window and the fence covers the profile; the second group touches only R2-only keys. Each remaining key is still a single document read as one version.
   - *Deletions:* the Worker never deletes an R2 object (no `delete` call in `src/`), so a key `missing_after` or recreated with another ETag between the listings is an anomaly: the attempt stops and the owner is told, nothing is imported as "deleted".
   - *If the proof cannot be produced* (a fence object changed, or the listings never settle within the bounded rounds), the gates are, in the owner's choice: a short owner-approved writer freeze (pausing the Scheduled Tasks for the window is a Task change with its own approval), or the durable change journal that [AIR-75](https://trello.com/c/AXPYIVCa) designs for shadow writes, used here as the replay source. Neither is assumed by this ADR.
   The manifest records the **baseline identity** (published `programmeRunId`, `sync.json` `updatedAt`, continuation `at`/`hopId`, latest enrichment run id) to label the cut and to check that a later export moved forward; it is not a change log. A **delta** is a complete fresh inventory with its own proof, diffed against the baseline manifest by key and checksum: changed keys are re-downloaded and re-imported through the same receipts, new keys are imported, and keys absent from the new inventory are listed as anomalies for the owner, never deleted in D1. A key revised during an import run is caught by the next inventory and re-imported or stopped the same way.
3. **Identity reconciliation by rule, not by invention.** The enrichment spelling `tmdb_<n>` is the catalog form of the canonical Film id `film:tmdb:<n>` (the lifecycle reader emits it in `src/domain/film-person-reader.js`; `catalogId` in `src/domain/film-person-diagnostics.js` maps back). The importer resolves `enrichment/films/tmdb_<n>/…` to `film:tmdb:<n>`, a Letterboxd slug to `film:<slug>`, and a retired id to its survivor through the stored redirect, using one shared function. The receipt keeps the source key as written. A key that resolves to no stored Film stays a conflict: the importer never mints a Film from an enrichment key or a metadata record.
4. **Immutable prediction versions are a prerequisite, not a workaround.** `prediction_current.r2_key` and `prediction_history.r2_key` must name immutable objects; the mutable `predictions.json` bundle does not qualify. Before the prediction family enters the backfill, the Worker must write each new prediction version as its own object alongside the bundle (a separate code change with its own review), and existing versions must be materialized as new objects under a separate, explicit owner approval, or the prediction family is excluded from this backfill and the exclusion is written into the acceptance.
5. **Discovery evidence is derived by the resolver's own rule.** `epg/discovery-latest.json` items carry no `evidenceKey`; the resolver computes it from the observation's own fields (`candidateEvidence` in `src/discovery.js`) and stores it on decisions. The importer derives the key with that same shared function and marks it `derived` in the receipt. A decision whose stored key disagrees with the derived key is a conflict, not a repair.
6. **R2-only keys are declared, justified and dated, not unknown.** Objects with no D1 table are an explicit allowlist in which every family states why it stays in R2 and what later stage must decide about it: derived projections (view index, queue, mood facets, score preview) are recomputed from rows under ADR-0001 and need no import; runtime coordination state (leases, continuation record and diagnostics, `sync.json`, variant plans) belongs to the R2 writers until the write-authority cutover redesigns it; archive copies (raw XML, generation copies) are archive by ADR-0008; user-visible state without a table yet (`started/` markers, `events/`) must receive a D1 home or an explicit "stays in R2" decision **before** the read cutover ([AIR-77](https://trello.com/c/f3QzcNYf)), so they are R2-only *now*, not forever. Coverage reports `r2_only` separately from `unmapped`; a full mapped-domain parity claim requires `unmapped` to be empty and every mapped family to read back equal, and prints the `r2_only` counts beside it. The family table is in the [readiness assessment](../evidence/d1-migration/air-74-backfill-readiness-2026-10-26.md).
7. **D1 resource and executor.** The database is created and the frozen `migrations/0001_schema_v1.sql` is applied by the owner, separately approved. The backfill runs as a local command against that database through an adapter whose multi-statement batch is atomic; atomicity is demonstrated on a scratch database with a deliberately failing last statement before the first production write. `wrangler.jsonc` does not gain a D1 binding in this stage; the Worker neither reads nor writes D1 until [AIR-75](https://trello.com/c/AXPYIVCa).
8. **Bounded batches, receipts, fences, stop, and four acceptance classes.** Units are imported in bounded batches; each unit is receipted by source key and checksum after read-back; an interrupted run resumes from receipts; the second and third runs must apply zero rows; parity is read back against the baseline manifest, not against the import's own write list. The result is reported in four classes that are never merged into one verdict: **(A) mapped-domain parity**, every mapped family read back equal to the baseline, a blocker for AIR-74 Done; **(B) R2-only operational artifacts**, the dated allowlist of item 6, not a blocker for AIR-74, each with its later-stage decision; **(C) identity and source-quality exceptions**, rows the importer refuses to invent (metadata-only films, slug-only fingerprints, a stored decision whose evidence key disagrees with the derived one), which stay open in the conflict ledger; AIR-74 Done requires the list to be complete, explained and acknowledged by the owner, and the rows remain **blockers for the read cutover** ([AIR-77](https://trello.com/c/f3QzcNYf)) until resolved or retired by an identity decision; **(D) an excluded authoritative family** (the prediction family under item 4), which makes AIR-74 Done "backfill of the mapped scope without that family", stated in those words, and is a **blocker for shadow writes of that family** ([AIR-75](https://trello.com/c/AXPYIVCa)) and for every later stage. An owner acknowledgement of (C) or (D) records a known gap; it never turns the backfill into a lossless migration or a completed operational state. Any conflict outside the acknowledged (C) list stops the run.

Not decided here: the name of the database, the exact R2-only allowlist and its per-family later-stage decisions, whether the prediction family is in or out of this backfill, the acknowledged class (C) exceptions, and the gate to use when the consistency proof fails (writer freeze or change journal). Those are GO/NO-GO items in the [readiness assessment](../evidence/d1-migration/air-74-backfill-readiness-2026-10-26.md).

## Alternatives considered

- **Import the 19 October archive into D1.** Rejected by the card itself: it is not current production, and it reproduces the known gaps.
- **Rewrite legacy ids inside the importer ad hoc.** Rejected: AIR-73 deliberately refused to rewrite ids; a mapping is acceptable only as one shared, tested rule that production code already embodies.
- **Point `prediction_current.r2_key` at the mutable bundle.** Rejected: it contradicts the schema contract and ADR-0001.
- **Pause the Scheduled Tasks for a clean freeze.** Not proposed: a Task change is a separate owner-approved operation, and bracketing listings plus a delta replay achieve a verifiable baseline without it.
- **Run the backfill from inside the Worker.** Not proposed: it would put D1 writes into the production code path before shadow writes are designed ([AIR-75](https://trello.com/c/AXPYIVCa)).

## Consequences

The backfill becomes verifiable and repeatable: every row traces to a source key and checksum, every mapped key traces to a receipt, a conflict or an allowlisted `r2_only` entry, and a rerun is provably empty. The costs are new code (a live exporter, the shared identity and evidence rules, an allowlist, a D1 adapter and a backfill command), a Worker change for immutable prediction versions, and an owner-run resource setup. The archive importer's reports remain valid history; the new rules make earlier conflict counts shrink by rule, which the readiness report records rather than hides.

## Recovery and migration boundary

R2 is not written by the backfill: the credentials are read-only by scope, and the Worker is untouched. D1 is not read by the runtime during this stage, which bounds the blast radius of a bad import to the database itself; it does not make dropping the database an automatic or sufficient rollback. Rolling back a populated production D1 is an owner-approved procedure: an export or point-in-time backup of the database first, a target-identity fence (the database identifier recorded in the manifest and in every receipt must match the one being dropped), then the drop and a fresh import from the same verified baseline. Receipts make a partial run resumable without a drop. A later delta import replaces nothing without a changed checksum and deletes nothing. This ADR never authorizes creating a token, a database, a binding, writing a row or dropping a database; each of those is an explicit owner approval recorded on [AIR-74](https://trello.com/c/5AdAmKPe).
