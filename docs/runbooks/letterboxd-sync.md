# Letterboxd Sync runbook

The Letterboxd Sync Workflow runs one slot at 04:30, 10:30, 16:30 and 22:30 Europe/Madrid: Diary and Ratings, a complete Watchlist scan, then removal reconciliation, and writes exactly two Events per slot (`ratings`, `watchlist`). Design: [ADR 0186](../adr/0186-letterboxd-sync-and-independent-watchlist-authority.md); control plane: [scheduling and orchestration](../architecture/scheduling-and-orchestration.md); tables: [D1 schema](../reference/data/d1-schema.md).

## State today

The code is dormant. With the mode table empty or `external` nothing is created, no cron or binding exists, and the legacy Ratings writer and the EPG Watchlist fetch are unchanged. **Nothing on this page is authorized by a deploy or a green test run.** Every production step below is a separate owner-approved operation (L3).

## Observing (read-only)

- `status().letterboxdSync` of the Ratings status and the `letterboxd` monitor stream (the read model: mode, epoch, current and next slot, overdue slots, per-source `lastSuccessAt`, health, pending Events). Both are absent while no mode row exists. They write nothing.
- A slot row's `status` and its three outcomes; a pending `letterboxd_slot_event` row means an Event is owed, not that the scan failed.
- `late`: a due slot was never claimed (the `:30` tick did not run or `ensure` is refusing). `stalled`: an earlier slot is still unclosed after its own window ended. `missed`: a slot was recorded `skipped_missed`. `failed`: the last closed slot errored in both sources. `watchlist_stale`: no complete scan for 24 hours; `watchlist_never_succeeded`: none at all since the executor started 24 hours ago.

## Holdpoint (c): the bootstrap import (prepared, not performed)

The operator `scripts/watchlist-bootstrap-production.mjs` imports the current published watchlist into snapshot version 1 while the Watchlist marker is still `epg` ([ADR 0186](../adr/0186-letterboxd-sync-and-independent-watchlist-authority.md) decision 8.2(c)). It is an import, not a scan: one atomic D1 batch writes the staging row, the ordered member rows, the snapshot row and the pointer, and nothing else (no change, effect or pending-admission row, no fact, no marker move). It needs its own owner GO and the prerequisite O4 (the EPG checkpoint cutover verified by a natural EPG run).

- **Read-only first:** `node scripts/watchlist-bootstrap-production.mjs --target iptv` (`status`, the default) prints the decision (`ready` or the refusal), the marker, the pointer, the published generation and its certificate, and the source count with **two** digests: `membersSha256` (ids in order) and `sha256` (the raw stored list, titles included), bound to the printed `epgGeneration`. It writes nothing.
- **Two separate pins, because the API presents localized titles.** `GET /api/watchlist` applies the owner-reviewed and cached titles at read time (`presentLocalized`), which can change a title without a new generation. Membership and order are not affected, so they are pinned apart from the raw payload:
  1. *Membership and order (`--expect-members-sha256`)*: the owner saves the authoritative, non-degraded `GET /api/watchlist` response to a file and runs `node scripts/watchlist-bootstrap-production.mjs --digest --file <response.json>` (local, no network, no target). It prints the count and the SHA-256 of the lines `ordinal<TAB>id<NEWLINE>`; titles are never hashed. A same-count change of membership or order differs. The saved response is evidence only when it is **bracketed**: read the published run id and generation with `status` before the request and again after it, require both reads equal and equal to `--expect-run` and `--expect-epg-generation`, and reject any degraded or fallback-labelled response operationally (a response that carries a degraded or stale label, an error body, or a non-200 status is not evidence). No new API is needed.
  2. *Raw payload (`--expect-sha256`)*: the digest `status` printed for the stored published document at the generation named by `--expect-epg-generation`. It is the digest the import writes, so a title presented differently by the route never refuses a valid current list.
  The two must describe the same generation: the operator refuses unless the run id, the generation, the count and both digests equal the stored source (`pin_mismatch`, with the list of failed pins).
- **The write:** `node scripts/watchlist-bootstrap-production.mjs --bootstrap --target iptv --confirm bootstrap --expect-run <programmeRunId> --expect-epg-generation <n> --expect-count <n> --expect-members-sha256 <digest> --expect-sha256 <digest>`. Every pin is required.
- **Preflight (fail closed):** the marker is `epg`, writes `open`; the pointer is version 0 with no snapshot; every watchlist table is empty; the published generation is `d1`/`open` and certified complete (`finalized_run_id` equals `programme_run_id`) and equals the pin; the source normalizes (unique ids, shape, order) and its member rows agree with the document; no executing EPG step, and both liveness records valid: a missing record is idle, a PRESENT record that does not satisfy the contract of `src/epg-orchestration.js` is unknown (`liveness_unknown`), never idle. The contract: `control` is an object with `schemaVersion` 1, a `budget` with integer `consecutive` and `total` and a known `phase` (`idle`, `starting`, `running`, `waiting`, `done`, `stopped`); `lease` is an object with a `holder`, a normalized-UTC parseable `expiresAt` and a boolean `released`. Busy means a `starting`, `running` or `waiting` phase, or an unreleased lease whose expiry plus the 15 s boundary margin is still ahead.
- **Guards inside the one batch:** the same marker, pointer, empty-table and certified-generation checks, **and** the EPG liveness proof, written in SQL with the same contract (NULL counts as invalid): the `control` and `lease` records are pinned by revision (absence included), a present record must satisfy its contract, and neither may show an active phase or a live lease. A writer that appears after the preflight, a record that changes revision, and a valid-JSON record of the wrong shape all trip the batch and nothing is imported. This is the only liveness check: there is no wider global drain check.
- **Readback (independent):** pointer version 1 with the snapshot id, digest, count and `effects_drained_version` 1; one staging and one snapshot row, the pinned number of members, zero change, effect and admission rows; the member rows in order reproduce the digest; the marker is unchanged; the published generation did not move; the stable fields (mode, cutover, writes) of the other domains are unchanged (live counters are never compared). A Time Travel bookmark is read before and after.
- **Stop conditions:** any refusal changes nothing. A transport or unproven outcome is `write_uncertain` (writeState `unknown`, `retry:false`) even when the readback looks untouched; only a proven rejected statement with an untouched readback is `statement_failed`. Nothing is retried or repaired without a separate GO.
- **Running it again (`already_applied`).** An existing import is verified read-only, never trusted from the pointer: the snapshot, staging and every member row (count, order, digest), the absence of change, effect and admission rows, the pointer, and then the **current** published source against the pins. `already_applied` with `receipt: verified_equal` means the stored import is complete and equals the current source at the pinned generation. A missing or altered member is `snapshot_inconsistent`; a newer publication, another generation or changed source content is `source_moved`; pins of another import are `already_bootstrapped`. The receipt is a statement of equality at that moment and **never an authorization for the next holdpoint**.
- **Holdpoint (d) revalidates.** Between the import and the marker switch the EPG may publish a newer generation. The hold/switch step must re-read the published generation and compare it with the snapshot's run (and re-import, with a new owner decision, if they differ) instead of assuming it cannot advance.
- **Rollback:** none by code. The snapshot is inert while the marker is `epg`; there is no delete path (immutability triggers). A wrong import is handled by the owner-approved data procedure, not by this operator.

## Holdpoint (d): the Watchlist marker transitions (dormant: NOT production-ready)

**These commands are dormant and are not ready to run in production.** The root `watchlist.json` mirror is now fenced (see "The root mirror fence" below), but the cutover still depends on pieces that are prepared only offline: the independent Letterboxd-side root writer and its reconciliation, the Ratings and Letterboxd writer handover, and the activation plan. Until they are delivered and verified, `hold`, `activate` and `release` must not be run against production. The rollback path (`hold-rollback`, `export-rollback`, `revert-authority`, `release-rolled-back`) exists in the operator but is reviewed only offline: **`hold-rollback` is never run before the rest of the rollback path is approved by its own owner GO**, because it freezes `d1` and only the export and the revert bring the list back to the EPG. Prerequisites also include the bootstrap import (holdpoint c) and O4 (the EPG checkpoint cutover completed and verified by a natural EPG run).

The operator `scripts/watchlist-cutover-production.mjs` moves the Watchlist marker. It is owner-only, needs its own owner GO **per command**, and runs only after the bootstrap import (holdpoint c) and the prerequisite O4. It writes the marker row and nothing else: not the pointer, a snapshot, a member or a journal row, not the EPG, R2, a flag or another domain. Every transition is ONE batch with an explicit `--confirm <command>`, the expected generation, the verified facts re-asserted inside the batch, an independent readback, no retry and no repair.

| Command | Transition | Pins |
| --- | --- | --- |
| `hold` | `epg`/`open` G to `epg`/`held` G+1 | the five bootstrap pins and `--expect-snapshot-id` |
| `release-abort` | `epg`/`held` G to `epg`/`open` G (back out before the switch) | the generation only |
| `fence-root` | `epg`/`held` G, no D1 write: changes the etag of the root `watchlist.json` mirror in R2 (see below) | the generation and `--expect-root-etag` read before |
| `activate` | `epg`/`held` G to `d1`/`held` G+1 | the same pins as `hold`, plus `--expect-root-etag` of the fenced root |
| `release` | `d1`/`held` G to `d1`/`open` G | the run, count, both digests and `--expect-snapshot-id` of the import |
| `hold-rollback` | `d1`/`open` G to `d1`/`held` G+1 (first step of the data rollback) | the snapshot pins plus `--expect-version` and `--expect-revision` of the current pointer |
| `export-rollback` | `d1`/`held` G, no marker move: the current snapshot is written into the published generation's watchlist part | the snapshot pins, the pointer version and revision, `--expect-run` and the published `--expect-epg-generation` read before |
| `revert-authority` | `d1`/`held` G to `epg`/`held` G+1 | the same pins, with the EPG generation the export PRODUCED |
| `release-rolled-back` | `epg`/`held` G to `epg`/`open` G | the generation only |

Use `node scripts/watchlist-cutover-production.mjs --target iptv` (`status`, the default) first: it is read-only and prints the marker, the pointer, whether the snapshot is whole, the EPG liveness, the checkpoint authority and the Letterboxd mode. A write is `node scripts/watchlist-cutover-production.mjs --<command> --target iptv --confirm <command> --expect-generation <G> <pins>`.

- **Facts verified before and re-asserted in the batch.** The marker is exactly the expected mode, writes and generation. For `hold` and `activate` the pointer is the bootstrap import (version 1, effects drained, the pinned revision, every member present) and the published generation is still the source of the import: the same run and EPG generation, certified complete, the same member count; the full read-only proof of the bootstrap operator is repeated. For `release` the full import proof of the bootstrap operator is repeated without requiring the old EPG source to remain current (the snapshot, the staging receipt, every member, the pins), and the import-only row invariants are asserted inside the batch for `hold`, `activate` and `release`: one staging receipt of the import, one snapshot, exactly the pinned members and no change, effect or pending-admission row; a scan journal row that appeared, or a missing receipt, means it is no longer the bootstrap import. For `hold-rollback`, `export-rollback` and `revert-authority` the pointer and its snapshot are the pinned current ones (version and revision), validated separately, **and their durable causal effects are all done**: `effects_drained_version` equals the version and no `watchlist_effect` row is pending (`effects_pending`). Once the Letterboxd mode is `external` and the authority is `epg`, nothing could drain that journal, so an undrained rollback would lose unapplied facts, retention or removal work even though the membership was exported. Mirror delivery, Events and pending identity admission are not part of this check. The drain happens before the Letterboxd writer is closed (the handover step implements that orchestration); recovering an already closed, undrained journal is an explicit owner decision, never a silent discard. The EPG liveness proof (the contract of the bootstrap section: control and lease valid, no active phase, no live lease, revisions pinned) is part of `hold`, `activate` and `hold-rollback`. The EPG checkpoint authority must already be **`d1` and `open`** for `hold`, `activate` and `release` (ADR 0186 decision 8.3 and O4: the checkpoint cutover comes first); `r2` is refused (`checkpoint_not_d1`), a held marker is refused (`checkpoint_not_settled`), and the same condition is asserted inside the batch, so a change after the read aborts it. The natural-run acceptance of O4 is confirmed by the owner; the operator checks only the marker. The Letterboxd mode row is absent or `external`, pinned by revision, so there is no new writer. `release-abort` needs only the marker, so backing out is never blocked by an unreadable EPG record.
- **The root mirror fence (C3).** The root `watchlist.json` mirror is written, on the EPG side, only by `PublishedEpg.putWatchlistRoot`. Inventory of the root writers: the part replacement (`replacePart`, after `saveWatchlist`), the mirror writer `writeMirrors` (the cron repair `reconcileMirrors` and `repairMirrors` call it), and the three Worker fallback tails (`persistWatchlist`, the seal mirror unit and the commit tail), which reach it through `saveJSON` and `saveWatchlistRoot`; no other file writes the key (a test pins the inventory). The generation-addressed copies `epg/generations/<run>/watchlist.json` and the programme mirrors do not depend on the marker and are written as before, also when the root fails; nothing is paused.
  - **Who may write.** Only a marker that is POSITIVELY `epg` and `open` (a verified singleton row with a valid mode, writes, generation and its fence row), or the legacy case of the maintained Watchlist authority contract (`WatchlistD1.readAuthority`): a stored schema version BELOW 31 with none of the Watchlist tables (a test pins the version and the table set to that module). `d1`, `held`, a missing singleton row, a missing fence row, an unexpected value, a partial table set, a schema at or above 31 without the tables (a contradiction, not a legacy database) and an unreadable answer all block (fail closed). A state known not to be writable is refused BEFORE the object is touched, so a root error in a state the EPG does not own cannot stop the generation copy, the programme mirrors or the repair; in `epg`/`open` a failing root is a failed mirror, never a false success.
  - **The write path.** Read the object and its etag, read the marker AGAIN after that read, put only if the etag is still the one read. A plain re-check of the mode is not enough because the PUT is not conditional on the marker, and a content etag is not enough either: identical bytes give the same etag again (an ABA). So every root write, on every side, carries a **token no JSON reader sees**: a trailing whitespace suffix after the document (`\n`, an optional run of tabs naming the held generation of a fence, `\n`, then a 64-symbol space/tab nonce), with a FRESH nonce for each write. A write is skipped only when the stored list is semantically equal (the parsed document, the suffix ignored), so a steady state does not churn, and no representation is ever restored: an etag read before a fence can never match again, however many fences, flips, rollbacks and equal-content writes follow. The future Letterboxd-side root writer must follow the same contract (read, check the marker, conditional put with a fresh nonce), and the return to `epg` repeats the fence from that side.
  - **The fence (`fence-root`).** After `hold`, the operator rewrites the SAME list (the parsed content is checked equal before and after) with a new suffix that names the held generation, by a conditional put on the etag it read, so every in-flight conditional put loses and a writer that reads after it finds the marker `held`. It needs the R2 read credential and the R2 install credential (it may write only the key `watchlist.json`); a lost compare-and-swap is `root_moved` and wrote nothing; an unproven put is `write_uncertain` with `retry:false`.
  - **`activate` requires the proof of THIS generation.** It reads the root and requires a fence suffix whose generation equals the held generation (`root_not_fenced` otherwise: no fence at all, or the proof of an earlier hold after an abort and a new hold) and the etag the fence produced (`root_fence_mismatch` if the root changed again, which means a writer got through: the fence is repeated, never assumed). Order: `hold`, `fence-root`, `activate`.
- **Order and windows.** `hold` to `activate` is a short window: between them the EPG may start a daily run, and `activate` then refuses under the liveness proof; back out with `release-abort` and retry. In `d1`/`held` the EPG start fails closed and the snapshot is refused, never read as the EPG generation. `activate` re-reads the published generation, so a publication after the bootstrap is refused (`source_moved`) and needs a new owner decision (a new import), never a silent switch.
- **Readback.** The marker equals the target; the pointer, the row counts of every watchlist table, the checkpoint authority, the Letterboxd mode and the stable fields (mode, cutover) of the other domains are unchanged; live counters are never compared. A Time Travel bookmark is read before and after.
- **Stop conditions.** Any refusal changes nothing (`state_mismatch`, `pin_mismatch`, `snapshot_inconsistent`, `source_moved`, `checkpoint_not_settled`, `letterboxd_not_closed`, `writer_active`, `liveness_unknown`). A transport or unproven outcome, or a marker moved by another writer, is `write_uncertain` (writeState `unknown`, `retry:false`); only a proven rejected statement with the marker untouched is `predicate_refused`. Nothing is retried or repaired without a separate GO.
- **The data rollback (ADR 0186 decision 8.5).** Order: drain the causal effects and close the Letterboxd mode (it must be `external` or absent, else every step refuses `letterboxd_not_closed`), `hold-rollback`, `export-rollback`, `revert-authority`, `release-rolled-back`, then re-open the Ratings daily mode (its own step). The export is the **EPG writer path** (`PublishedEpg.saveWatchlist`: a staged commit that replaces the watchlist part and moves the EPG generation by exactly one, compare-and-swapped on the generation read). Its own preconditions are asserted **inside the final replacement batch** through the writer's optional commit guard (`guards`, at most eight statements, absent for every other caller): the marker is `d1`/`held` at the generation read, the pointer and snapshot are the pinned ones with their effects done, the Letterboxd mode row is closed and pinned by revision, the EPG liveness proof holds and the publication is the pinned run, certified, at the pinned generation. A lease, a pointer move, a marker move, a mode change or an uncertified publication during the multi-batch staging aborts the replacement and nothing authoritative is written: the stored films keep every other field they already had, the snapshot owns id, title, year and url, the programme document and the shows are not touched, and the R2 mirrors are not written here (the EPG owns the root mirror again only after the revert, and its named writer reconciles it). It needs the list to differ and a certified, current published run; an equal list at the pinned generation answers `already_exported` and writes nothing. Its readback is digest, membership and order parity of the stored document and the member rows, the marker, the pointer, the row counts and the stable fields of other domains unchanged. **Two different facts are reported.** `authoritative` says whether the published list was replaced (`unchanged`, `replaced`, `moved_by_another_writer`, `unknown`), read from the generation and the stored list. `writeState` says whether any database write was made: a staged commit writes its claim, chunks and validation in earlier batches, so an unchanged generation does NOT prove `none`; `none` only when no batch completed and the failure is a proven rejection (or nothing was sent), otherwise `unknown` with no retry, the batches counted and the surviving staging rows reported (`stage`). A lost compare-and-swap writes nothing over the other writer and is never retried. `revert-authority` proves the stored document, not only the ids: the operator reads the published list and requires the normalized digest (title, year and url included) and the member order to equal the snapshot, the run to be certified (`published_not_certified`) and the generation to be the pinned one, and the batch binds that proof: the certified run at the exact generation, the stored payload digest of the generation (any later replacement changes it), the member rows joining the snapshot on ordinal and id, the pinned pointer with its effects done, the liveness proof and the Letterboxd mode. The same ids and order with another title, year or url (`parity_mismatch`), an uncertified publication, or a replacement after the read refuse; if the EPG published its own list in between, the export is repeated with a new owner decision. A list that already equals the snapshot needs no export. Snapshots stay as inert history; a code revert does not undo a marker.
- **Not here.** The Ratings close, the Letterboxd mode switch, the root mirror reconciliation, the Workflow binding and the cron are separate steps with their own operators and GOs.

## Holdpoint (e): the Ratings and Letterboxd writer handover (prepared, not performed)

The owner's Letterboxd Sync mode control is a route of the Worker under the same Access protection as the Ratings executor route (`/api/letterboxd/ratings/executor`): `GET /api/letterboxd/sync/mode` is read-only, `POST /api/letterboxd/sync/mode` takes ONE command. It reuses the three-step switch of the control plane (`close_admission`, `complete`, `clear_quarantine`) and adds `abort`; there is no second control plane. Every command needs `confirm` equal to the action name and, except `clear_quarantine`, the **pins** of the row the owner read: `expectEpoch` and `expectRevision` (revision 0 = no row yet). A command with a stale pin is refused (`pin_mismatch`, naming the pin) and writes nothing; it is never retried, and a competing owner's write between the read and the write is a stale pin, not a blind retry. Nothing on this page is authorized by a deploy: each command is a separate owner GO, after O4, the bootstrap import (c) and the marker switch (d).

- **Read first (`GET`).** The mode row (`mode`, `target`, `epoch`, `revision`, `drain`, quarantine), the drain of the executor's instances (`verified`, `instance_live`, `unreadable`), the five-part handover proof read from live state, the causal effects of the current snapshot (`drained`, `pending`, `version`, `drainedVersion`), whether the legacy entry is fenced and how many Letterboxd writers are admitted. It writes nothing.
- **The handover proof and its protection.** `complete` toward `cloudflare` requires the proof: the Ratings executor closed (`external`), its step lease and instance drained, the legacy `ratings_sync_start` and `ratings_sync_step` fenced (an `external` marker alone is not the fence), the Watchlist authority an open `d1`, and every phase present. The proof is read OUTSIDE the commit and **pinned AT the commit**, from the evidence the proof itself captured (never from a second read): the facts are read before and after the proof and must be identical, otherwise the whole proof reads false. The same batch that writes the mode row asserts the Watchlist marker (`d1`/`open` at the generation read), the Ratings domain authority (`d1`/`open` at the generation read, which every authoritative Ratings commit bumps) and the stored etags of the Ratings mode, control and run records (absence included). A fact that changed after the proof aborts the completion (`handover_changed`) and nothing is written; a proof that cannot be pinned (`handover_unprotected`) does not complete a handover.
- **An already admitted legacy request.** The legacy `ratings_sync_start`/`ratings_sync_step` admission records the Letterboxd mode revision it saw (while the Letterboxd schema exists), and every authoritative Ratings commit of that request asserts it in its own batch. A close, completion or abort of the Letterboxd mode after the admission therefore rejects the request's commit and writes nothing, not only the next admission. (Known window: if the Letterboxd schema is applied between a legacy admission and its commit, that one request carries no pin; the mode row is empty then and a switch needs the whole proof.)
- **Forward order.** (1) Close the Ratings Cloudflare executor to `external` through its own route (its three-step switch) and wait for its drain. (2) `close_admission` with target `cloudflare` and the pins: the epoch moves, so an in-flight old writer is fenced at its own commit, and while `switching` the legacy Ratings entry is fenced. (3) `complete` with the pins once `GET` shows the whole proof: exactly one admitted writer from that batch on.
- **Reverse order.** (1) The durable causal effects of the current snapshot are done BEFORE the running writer is closed: `close_admission` toward `external` refuses `effects_pending` (with the versions and the pending count), `effects_unreadable` or `effects_unproven` otherwise, because once the epoch is closed the writer is fenced and nothing could drain them; there is no silent discard. The check is also asserted AT the commit: the batch that closes the epoch re-asserts the version read and that no effect row is undone, so a promotion that commits between the read and the write aborts the close (`effects_changed`, nothing written); a port that cannot pin it leaves the close refused (`effects_unprotected`). Mirror delivery, Events and pending identity admission are not part of this gate. (2) `close_admission` toward `external`, then the Watchlist data rollback operators (holdpoint d: hold-rollback, export, revert) until the marker is `epg`/`open` again. (3) `complete` toward `external` (the drain of the executor's instances must be verified; an unreadable drain is refused and nothing is written) is refused with `watchlist_rollback_pending` until that rollback is done, because `complete` reopens the legacy Ratings entry and the legacy writer rewrites the root mirror; while the mode stays `switching` the entry remains fenced. Only after `complete` is the Ratings Cloudflare executor re-opened through its own route. A drain mode that stops new scans and promotions while the effects finish is NOT part of this slice: until it is delivered, the owner closes when `GET` shows the effects drained.
- **`abort`.** Recovery from an open `switching` back to the mode it started from (`external` or `cloudflare`), with the pins. The epoch was already raised by the close, so a writer of the old epoch stays fenced; an abort admits no writer, and the legacy entry reopens only when the mode is `external` again; an abort toward `external` has the same condition as the reverse `complete` (`watchlist_rollback_pending` until the Watchlist is back on `epg`/`open`). An abort back to `external` after a forward close leaves the Ratings executor closed: re-open it through its own route, a separate step, so the writer count is read from `GET` after every command (one admitted writer is the goal, zero is a visible state and two is never reached by these commands).
- **Stop conditions.** Any refusal changes nothing: `pin_mismatch`, `switch_open`, `already_in_mode`, `not_switching`, `handover_not_proven` (with the missing parts), `handover_unprotected`, `handover_changed`, `drain_not_verified`, `effects_pending`, `effects_changed`, `effects_unprotected`, `effects_unreadable`, `effects_unproven`, `watchlist_rollback_pending`, `evidence_unreadable`. The one answer that is NOT a proven non-write is `write_uncertain` (`retry: false`): the storage failed or the reply was lost, so the command may or may not have committed; read `GET` again and decide with new pins, never repeat the command. A lost compare-and-swap is a proven rejection (the batch ends with a fence on the changed-row count) and reads as a stale pin. Nothing is retried or repaired without a separate GO. A Time Travel bookmark before and after each command is the operator's receipt.
- **Not here.** The Workflow binding, the cron `:30`, the flags, the Tasks and the first slot (the activation plan), and the root mirror reconciliation writer.

## Rollback

Close admission with target `external` and complete: the epoch moves, a stale instance is refused, and exactly one legacy Ratings writer is admitted again. Code rollback does not revert D1 rows, slots, outbox rows, the mode row or Events already written.

## Do not

Do not delete or edit a slot or outbox row to "retry" it; do not start a slot manually; do not set the Ratings mode to `external` and call that a fence. A pending Event is delivered by `ensure` and by the next run.

The dated read-only preflight, the gap analysis and the proposed holdpoints of the production cutover are in the [cutover GO/no-GO package](../evidence/d1-migration/air-571-go-no-go-package-2026-11-21.md). It authorizes nothing: every holdpoint needs its own owner GO.
