# Prediction incident response and controlled diagnostics

Use this runbook when the Predictions pipeline stops making durable progress, repeatedly loses an owned run, or Scheduled Tasks report completion without performing their required work. For isolated retryable film failures, ordinary backoff or a genuinely empty queue, use [normal prediction operations](prediction-operations.md) instead.

**Operator entry point:** "Follow the prediction incident runbook" means execute the read-only triage below, maintain the active incident card, propose the smallest discriminating next experiment and report its outcome. It does not grant permission to create, run, edit, pause or resume a Task, execute a model producer, reset a lease or mutate production. Read [authorization and escalation](../process/authorization-and-escalation.md), [MCP safe probes](mcp-connectivity.md), the [runner contract](../reference/api/prediction-runner.md), [Scheduled Tasks](../reference/scheduled-tasks.md) and the live incident card. Use the current deployed contract and saved prompts, not the configuration in historical evidence.

## 1. Establish the incident and its boundary

1. Locate the active incident card (or register a new one if appropriate). Record the user-visible symptom, first observed time, affected domain and current impact. Keep the investigation in that card; do not require the owner to reconstruct earlier chats. Check [monitoring](monitoring.md), but do not treat a green footer or successful notification delivery as proof of predictions being committed.
2. Read the live Task registry, individually when a listing is incomplete: exact IDs, enabled states, recurrence/timezone, prompts, actual last-run records and saved reports. Snapshot relevant prompt character/UTF-8 byte counts and hash or exact equality. Record changes relative to the intended deployed prompt and last known good configuration; do not silently normalize the per-Task ownership label. Save pertinent reports before reusing a diagnostic Task because later runs can replace the accessible report.
3. With verified L0 reads, inspect queue consistency and eligible-now work, runner/authority, current run and lease (owner label, epoch, expiry), last committed progress and actual run outcomes. Distinguish an eligible backlog with no progress from future retry-only work, a typed hold, normal contention, quota, empty queue and a deferred submission. Use the current [prediction operations](prediction-operations.md) procedures; never run a writer merely to obtain a status.
4. Establish **last good durable commit** and **first failed execution**, not just the first alarm or the next slot refused by an abandoned lease. Use actual run times, not nominal schedule times. Compare several preceding successes and failures, including comparable manifest sizes, long starts and recovered timeouts. Narrow the change window between the last good and first bad invocation. Examine deployed Worker versions, actual commit diffs (including prompt, contract, configuration, authority, schema and queue changes), deployment timestamps, storage and connector behavior. A docs-only deploy is not evidence of an executable code change; equally, a code diff alone cannot exclude external/runtime changes.
5. Correlate Scheduled Task actual start/end, matching saved report, Worker request logs, run/epoch and durable commit receipts. For a Task marked completed, look for the **last actually completed stage** and the first missing mandatory stage. A Task's report can say FAIL even though scheduler metadata says completed. A Worker HTTP 200 is a successful server response, not proof that the caller received or used its full payload.

For telemetry use the authorized Cloudflare Workers Observability query surface, read-only query mode (`dry: true`), service `iptv`, actual run window in UTC with a small margin. Inspect `mcp_tool_call`, `prediction_step_timing` and the underlying requests; record request ID, Worker script version, status, elapsed wall time, manifest and answer bytes (when available), D1/R2 counts and rows/bytes written, preflights, refreshes and lease refusals. Recheck a broader service/time filter when a narrow query omits an expected event; respect ingestion delay and log-retention limitations. No matching log is not automatically proof of no invocation. Separate end-to-end Task wall time, Worker time and time remaining between the last logged tool response and Task completion. Cloudflare logs do not independently prove web searches, article reads, model identity or receipt of a response in model context.

## 2. Classify before changing anything

| Observed boundary | Next discriminating check |
| --- | --- |
| No invocation or runner call | Registry actual runs, authorization/connectivity, available MCP schema, reported tool/usage errors; use the safe connectivity procedure. Do not call a producer. |
| Runner succeeds, mandatory next call absent | Inspect report and actual trace; a small response, no manifest or no research yet rules out their size/workload as necessary triggers of this occurrence. Compare an exact scheduled control and an interactive read-only control. |
| Start slow, lost response, repeat or `start_pending` | Compare same-owner versus foreign ownership, overlapping requests, expiry and stored readback; use the accepted runner recovery protocol and offline replay. Do not infer a duplicate writer from an overlap alone. |
| Typed blocked/noop, stale or inconsistent queue | Follow the specific current contract, authority and queue diagnostics. Do not classify a valid skip as an agent failure. |
| Response cannot be parsed or is truncated | Verify actual transport wrapper and response completeness; controlled response-size ladder, not arbitrary changes to scoring. Do not infer a token cap from bytes or film count. |
| Complete manifest, early exit in research or local generation | Functional ladder below; isolate workflow execution rather than rewriting the entire production prompt. |
| Valid local candidate, real validate/hold/submit/complete fails or is missing | Examine real-run tool calls, exact payload/replay identity, receipts and server validation codes. Dry-run success cannot diagnose every real writer path. Never submit locally fabricated diagnostic candidates. |
| No recent durable progress despite apparent healthy starts | Correlate commits and terminal outcomes, not lease freshness; use the monitor policy. |

A successful earlier run of an exact workflow makes it a useful positive control, not a permanent guarantee. Prefer a specific, reproducible server defect for a code fix. If the service obeys the contract and execution stops on the client, investigate the caller and platform separately from backend optimization.

## 3. Authorize and design a bounded experiment

Use the current incident card to state the hypothesis, one changed variable, control, actual proposed inputs, tool sequence, success/failure predicate, cost and maximum attempts, side-effect boundary, expected time and next decision for each outcome. Obtain operation-specific owner approval for each Scheduled Task create/edit/reschedule/run/enable/disable and any model invocation outside an existing authorized contract. An explicitly approved staged series may cover named operations and holdpoints; do not add a replacement experiment without authorization.

Prefer a one-shot Scheduled Task in the normal task execution environment, a few minutes in the future, with the user's configured timezone and no recurrence. Separate actual run windows; a nominal spacing is not proof of no overlap. Do not schedule unrelated reminders or monitoring Tasks. Confirm a new Task's ID, enabled state, schedule and exact stored prompt by readback. Check the existing production Tasks individually before and after. If isolation requires pausing production, obtain specific approval and preserve its configuration; never assume permission to resume or change it. Disabling a Task need not cancel an invocation already in progress.

Derive the diagnostic prompt from the **live, approved production prompt** and actual MCP contract. Keep the original language, research/scoring safeguards, schemas and relevant workflow blocks. Remove only operations outside the diagnostic scope; document an exact diff, expected unchanged blocks and scope differences. Distinguish manifest size, number of films actually processed, prompt size, model context projection and final report size. They are separate variables. Use actual manifest films for research, not arbitrary fixed titles or a web-first sequence that cannot be used by the production workflow. An intentionally tiny connectivity test is not a substitute for the production-derived functional test.

### Read-only diagnostic boundary

When the deployed contract still supports it, use the read-only manifest path, after verifying its side effects and deployed schema. For batch v2 the example is:

```text
enrichment_runner({taskId: "<approved diagnostic label>"})
prediction_batch_start({trigger: "scheduled", taskId: "<same label>",
                        manifestSize: <approved size>, dryRun: true})
```

Use actual accepted arguments (including scope/mode where required), current limits and authority; do not invent capacity or ownership. Do not request an envelope or deferred start in this dry-run example: a dry run returns a full manifest and does not create a persisted owned run or lease. Do not attempt owned-run part recovery on an unpersisted dry run. Verify the current [runner contract](../reference/api/prediction-runner.md) before using pinning, alternate answer formats or any other mode. Never fall back to a real start when dry-run parsing fails. A diagnostic scenario with this boundary does not call real start, heartbeat, hold, submit, complete, retry, discovery, direct HTTP or other writers; no live validator call unless explicitly scoped and verified safe. Keep all generated candidates local. Reconcile observed write counts and runtime state, not just the declared dry-run flag.

For the coordinator and the Task, handle the actual transport format explicitly:

- Accept a complete structured object or the complete JSON in the MCP text content. Check types before array operations; inspect a supported structured-content field, or the actual text block in a content array, and parse the entire JSON string. A response may already be the manifest root rather than a nested `manifest` object. Use a bounded unwrap (for example at most three wrapper levels); stop at a complete expected root or report the actual missing/invalid field. Never invent an envelope or recover JSON from an incomplete prefix.
- Verify authority, limits, expected status, no owned run for the dry run, unique film IDs, declared/actual count (account for an honestly shorter eligible queue), complete profile, contract and film metadata/work plans, including the required stored fingerprint for prediction-only work. Capture the logical manifest hash where present, profile/contract identity and ordered film identity in private evidence. If a tool's output is projected for context, retain the full information required for the target films, the complete applicable profile/contract and count/identity/plan checks for all films. Record the projection as a changed variable. Do not call partial context a complete manifest.
- An observed wrapper/parser error is a targeted test/fix, not a reason to rewrite the remaining prompt. Explicitly check that a structured object is not mistakenly treated as an array or string. Retry only under the approved plan and current contract.

### Diagnostic ladder (select the next useful rung, not all rungs by default)

| Rung | Required result / controlled change |
| --- | --- |
| A. Connectivity and manifest | Runner, authority, one dry-run start, complete manifest validation. Establish the minimal safe path. |
| B. Transport size (only when parsing/truncation is implicated) | Hold the production-derived instructions fixed; vary only selection size and matching count assertions, starting with a small size and the intended size. Use intermediate sizes only to bracket an observed failure. Record actual bytes and reported tokens, not a guessed threshold. Repeat a matched input/control to distinguish intermittent failure. |
| C. Research | Same manifest path and complete applicable instructions, one or two actual selected films. Carry out the research and quality gate; no generation or writes. |
| D. Minimal local generation | Add the real fingerprint/prediction block appropriate to each work plan. Complete the research and generate locally; intentionally excluded evidence/assessment/scoring are not product acceptance. |
| E. Evidence and assessment | Add the actual production evidence block, then the assessment block, as separately observable increments. Preserve contract fields, evidence coverage, source semantics and byte limits. Validate locally only, report exact missing fields or violations. |
| F. Complete functional dry-run | Add full evidence-aware scoring and local checks. Keep the same research requirements and all applicable output fields. If work volume is implicated, process one target film while keeping the same manifest and full instructions. A failure before the reduced-work stage is not a negative test of that workload. |
| G. Real-run canary | Only after specific owner GO and a verified safe lease/authority/writer state, run one existing production Task naturally or an explicitly approved isolated real canary. See recovery below. |

The research audit must distinguish searches, original URLs, authors, access outcomes and full/partial/snippet (F/P/S); follow the current production query budget and mandatory alternate-search/full-text fallback rules. Opening a URL is not reading it. Do not infer actual reads from snippets or citations, or fabricate authors, research or source access. A completed, honest limited/blocked research gate is not the same as abandoning a required search or read attempt. Keep unknown execution evidence unknown; do not turn it into a negative finding or inflate scores. Use the current fingerprint/evidence/assessment/scoring contract, not historical enum lists or size limits.

For local outputs require complete compact machine-readable candidate objects (or precise per-film failure) and local contract checks appropriate to the rung, followed by a compact audit, without duplicating entire inputs or candidate payloads in narrative. Separate execution PASS, local structure/content quality and server acceptance. Report each stage as pass, fail, not reached or not observable, rather than labeling all earlier stages failed. A report may itself be truncated; check whether the required JSON objects are actually complete before calling the report a pass. Never claim production validation or durable progress from local JSON alone.

## 4. Check reproducibility and investigate the platform

If a rung fails, distinguish a failure *in* the newly added stage from a regression in an earlier stage. Repeat the exact last-known-good prompt and, if needed, the failed prompt once under comparable conditions before changing it again. Compare actual manifest hash/targets, profile and contract, Worker version, response size, timings and run environment. Avoid attributing different outcomes to a single variable when film mix, latency, context or model routing changed. A failed shorter prompt or a failed exact replay undermines a deterministic prompt-length explanation. Do not repeatedly delete quality or safety rules to make the report green.

An interactive comparison should execute the same scoped instructions, including **real** web tool calls and original-source reads, with the same input and output checks. Preserve prior-context differences and tool projections as confounders. If web calls were not executed or their evidence cannot be inspected, state this explicitly; do not count the interactive comparison as an end-to-end PASS. Never claim a provider request or tool result that was not actually observed.

When a broad regression is plausible, correlate the narrow onset window with public provider status history, release notes and independent reports (including developer forums). Record dates/time zones, similar and differing symptoms, direct links and confidence; distinguish a release, an outage and a user's anecdote. A same-day rollout is a meaningful lead, not proof of account-level routing or the causal mechanism. Do not disclose private prompts, payloads, account identifiers, logs or secrets publicly, and do not make support contact a prerequisite or send it without the owner's agreement.

If model identity is relevant, add the same small self-identification instruction to matched diagnostic prompts: before the first tool and immediately before the final report, record model, version, reasoning effort and basis, or `unknown` for each unavailable field; no guessing, extra tool calls or early finish merely to emit the first snapshot. Label the result **self-report**, not authoritative runtime telemetry. Inspect real registry/UI settings if accessible. Do not assume a model name in prompt, a parent chat selection, or inherited environment metadata sets the actual Scheduled Task model. If a parent-model inheritance or Task-identity control has already failed, do not repeat it without new capability/evidence. Before reusing a previously successful diagnostic Task preserve its old report and the exact original prompt. Compare original and clone using identical candidate prompts, changing only the intended identity/context variable; verify actual non-overlap.

## 5. Stop, decide and restore

After every experiment, record the result and the next decision in the active incident card. **Stop a diagnostic branch** when its planned test and exact control are exhausted, when the target stage has not been reached and the proposed change cannot affect the failure, or when no new discriminating hypothesis remains. Repeated unexplained early completion across simpler and formerly successful prompts, especially with correct server responses, is grounds to recommend a platform-side regression as the working cause, with its uncertainty explicitly recorded. Do not confuse absence of a proven internal cause with absence of useful RCA conclusions. State what is ruled out as a necessary condition, what remains plausible and what would change the conclusion.

Use separate deliverables for an actionable Worker/contract defect and any approved remediation, with ordinary independent review, CI/CD and production acceptance. Do not reopen settled architecture/cost/quality decisions merely because the current service has an incident; the owner controls material trade-offs. A pause of investigation or later canary may be more valuable than another variant. Offer the owner a concrete stop/recovery plan; no automatic rollback, scheduled follow-up or production enablement.

For owner-approved recovery, re-read the live registry, queue, authority, runner and lease. Confirm that the selected existing Task is using the intended approved production prompt, fixed ownership label and schedule, and that other writers/Tasks cannot interfere with the approved isolation plan. Do not force-expire an abandoned run, edit unrelated settings or start manually to hurry the canary. Enable only the explicitly named Task (or use the exact separately approved isolated canary), observe its **natural** execution, correlate report and durable commits, check research quality and ordinary terminal/lease behavior. On failure, retain evidence, stop rollout and follow the explicitly approved containment plan; do not silently re-enable the rest. A single successful commit is evidence of recovery, not proof of sustained stability; agree the observation window and repeat-success/quality criteria with the owner before expansion. Report any isolated retry/skip honestly. Resume other Tasks only under the agreed owner authorization after successful acceptance. Close the incident with verified durable progress, current configuration and owner acceptance, not just deploy success or a successful diagnostic report.

## 6. Evidence and handoff

Maintain a concise per-experiment private record: hypothesis, owner GO and scope, source/candidate prompt identity/diff, Task ID/schedule/actual run and matching report ID, model self-report, runtime version, manifest identity/size, observed calls/request IDs, timings/write counts, stage/quality/coverage results, precise missing stage, limitations and next decision. Keep the approved prompt and old reports available privately; do not publish raw private prompts, taste profiles, candidate payloads or confidential logs to the public repository. Use UTC in repository evidence and Europe/Madrid in owner-facing chat and Trello. For durable findings add a sanitized dated report and index entry according to [documentation governance](../process/documentation-governance.md). Preserve the live incident state and blockers in the card so another session can continue directly from this runbook.
