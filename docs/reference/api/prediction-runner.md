# Continuous prediction runner v5

The same start/next/submit/complete protocol serves manual and scheduled triggers. Read GET /api/enrichment/runner before every launch. Its contract supersedes the obsolete v3 single-batch/deadline instructions. ChatGPT reaches this protocol through the MCP tools in [docs/mcp.md](mcp.md): `enrichment_runner`, `prediction_start`, `prediction_next`, `prediction_submit`, `prediction_heartbeat`, and `prediction_complete`. Those tools fix the scope to `watchlist_all`, the mode to `queued`, and each next/submit step to one film. The HTTP routes remain the contract. The external ChatGPT Scheduled Task is managed independently of deploying this Worker contract; always verify its live state and do not change it without owner approval.

1. POST start with scope watchlist_all, mode queued and trigger scheduled/manual. Supply real known capacity only. Do not impose a total-film or time cap.
2. already_running is a successful no-op: never adopt another trigger's runId. busy is transient contention; retry with bounded backoff, without starting concurrent generation.
3. Read next, generate only requested work using the unchanged schema/profile/scoring rules, and submit each film immediately. Repeat next/submit across batches continuously.
4. Before model calls renew POST heartbeat; renew concurrently every 10 minutes if an individual call can last that long. Checkpoints also renew automatically. A 15-minute lease stores owner/runId, heartbeatAt and expiresAt. Until the schema v7 marker is `d1`, the compare-and-swap is the object etag. In that mode it is the D1 row token. Expired owners cannot submit. Crash checkpoints survive takeover. Migration `0007` is not applied, so the live lease is the object.
5. next re-evaluates hot urgency before every selection. Cold may run only while hot has no outstanding work. Model call batching remains disabled. Valid fingerprints/predictions are reused; timeslot changes never invalidate them.
6. Before submit, call `prediction_validate` with the complete generated fingerprint and prediction (no storage, not a submit; submit only when its `success` and `valid` are both true, otherwise fix the listed `issues`) or check them against `contract` from GET /api/enrichment/schema (`enrichment_schema`): every required `execution` dimension present, every enum value from its list, `moodLabels` 2–4 labels. Fix every reported issue first. An isolated malformed/invalid film output is reported through submit items[].failure.kind (parse_error or validation_error), is persisted as a retryable item failure and must not end the run. A Worker schema rejection is the same retryable item failure and additionally returns `results[].validation` with `stage` and `issues[{path, code}]` naming the field (for example `fingerprint.execution.payoff invalid_enum`, `fingerprint.moodLabels required`); fix that field for the following films and do not resubmit the deferred one in the same run. See [the submit validation contract](enrichment.md#submit-validation-contract). Failed items are skipped within that run and deferred by a 1-hour exponential retry (maximum 6 hours). Five consecutive distinct format failures trigger format_error_storm. mustComplete means call complete with stopReason. At actual quota/model/API/storage error, complete with a short safe reason and retain all saved predictions. No credentials in outputs, URLs, Events or persisted error reasons. A killed process recovers through lease expiry.
7. Progress Events aggregate the run every 50 successful predictions or 30 minutes, whichever comes first; the final event is separate. Check heartbeat/next/submit to emit time-based progress during active work. Successful empty checks don't spam Events. Eligible queue exhaustion with deferred item retries is a normal completion, not a run interruption.
8. A formed response does not prove the client received it. Send or read `X-Request-Id`; the same id is returned as `requestId`. On an external or systemic stop, `complete` may include `fault` (`origin`, `failedStep`, `providerErrorCode`, `httpStatus`, `receivedRequestId`). Omit `fault` when the cause is unknown. A fault on `queue_empty` or another normal completion is rejected. `receivedRequestId` acknowledges only the matching step. `firstNextAt` is not a successful `next`. See [run diagnostics](run-diagnostics.md).

## Run completion, drained queue, eligible and deferred work

Four observations are kept apart. **Run completion** is `status: complete` (or `partial` when a stop reason or a still-pending selected film remains); a run that ends with item failures deferred to a retry is `complete` with `failed > 0`, not an error. **Drained** means the refreshed queue has no outstanding film: `complete` stores `stopReason: queue_empty` only when `hotRemaining + coldRemaining` is zero after its final queue refresh, whatever reason the caller sent. **Eligible** is the subset of outstanding films the runner would take now (`queueReadyIds`: the hot lane while any hot film is outstanding, otherwise the cold lane, minus films whose stored `retryAt` is in the future); when work remains but none of it is eligible, `complete` stores `eligible_queue_empty`, and `next` answers the same with `mustComplete: true`. **Deferred** films are the outstanding films held back by a retry timestamp; `start` on a queue that is outstanding but not eligible answers `retry_backoff` instead of opening a run. The completion Event and the footer status publish these counts as `snapshot.queue` / `predictions` (`outstanding`, `eligibleNow`, `deferredByRetry`, `nextRetryAt`, see [the footer and Event slices](enrichment.md#failure-behavior)); the retry time of a film is not the time of the next scheduled run. None of this changes the retry policy, the delay, the batch size or which films are selected.

## Queue writes

`enrichment/prediction-queue.json` has several writers ([ADR 0064](../../adr/0064-prediction-queue-conditional-writes.md), Accepted 2026-10-31):

- the runner routes (`start`, `next`, `submit`, `complete`);
- the EPG commit tail (`programme_updated`) and the EPG scan (`epg_scan`);
- the profile publication (`profile_updated`);
- the resolver checkpoint (`resolver_checkpoint`);
- `POST /api/enrichment/queue/reconcile` (`manual_reconcile`).

Every write is conditional. Until the schema v7 marker is `d1`, the condition is the etag of the object the writer read (`etagMatches`, or `etagDoesNotMatch: '*'` when absent). When that marker is `d1`, the condition is the D1 generation read with the document, and the object is written afterwards as a mirror. On schema v7 while the marker is still `r2`, the writer advances `generation` before the object put, and a failed compare-and-swap does not put. Migration `0007` is not applied. The retry, the five attempts and `prediction_queue_conflict` are the same in both modes ([ADR 0076](../../adr/0076-d1-authoritative-prediction-domain.md)).

- **A rebuild** (`refreshPredictionQueue`, its `trigger` stored on the queue) reads the queue first and its inputs after it. When the stored queue names another programme generation than the caller's programme, the rebuild uses the published programme. `retries` of films still outstanding, `lastBatch`, `lastCheckAt` and `metrics` come from the queue just read.
- **A recorded change** is the submit's per-film retry, the start's idle check (`lastBatch` with `runId: null`) or a stopped run's missing retries. It is applied to the queue just read and never creates an absent queue.
- **The completion** writes its retries, `lastBatch`, `lastCheckAt` and `metrics.hotProcessedTotal` inside its own `batch_complete` rebuild. The counter moves only when `lastBatch.runId` is not yet the run, so a repeated completion counts once.
- **A retry record only grows while its film is outstanding.**
  - `attempts` is the larger of the run's count and the stored count plus one.
  - `retryAt` is the latest of the run's time, the stored time and the backoff of that count.
  - A record whose `lastRunId` is the run is written once.
  - The completion and every stop add any failure of the run that the submit did not land (below).

  The submit answer and the run record follow a merged record that came out larger.
- **On conflict** the writer re-reads and starts again, at most 5 attempts with a short jittered pause. Exhaustion throws `PredictionQueueConflictError` (`code: prediction_queue_conflict`), and nothing of the caller's is written.
  - The reconcile route answers `409 {error, code: "prediction_queue_conflict"}`.
  - A runner route ends through its ordinary error path as a `storage_error` stop.
  - The EPG commit tail records `enrichmentQueueError` and completes the commit.
  - The resolver records `prediction_queue_checkpoint: …` in its status.
  - The profile publication stands; the next rebuild picks the new profile up.
- **A put that throws** is an unknown outcome. It is not repeated, and the error propagates. A lease holder's `beforeWrite` renews before every attempt, so a lost lease writes nothing.

**A run's retries survive a queue write that fails.** A queued run's per-film failure is saved on the run record, with `retryHeal: "pending"`, before the submit writes it to the queue. The mark is cleared only by a queue write that confirms every failure of the run.

- **At the stop.** Every stop writes the run's missing retries again before it marks the run `partial` and releases the lease. This covers a `storage_error` stop after a submit conflict and a `complete` with a systemic reason. A normal completion writes them in its `batch_complete` rebuild. A write that still fails keeps the mark. The stop answer then carries `retryHeal: "pending"`.
- **At the next start.** A released or expired runner lease keeps naming its last run. Before acquiring the lease, `start` reads that run. If the run is still marked, `start` writes its retries to the queue first, in a recorded change with trigger `start_retries`. When that write fails, `start` selects nothing, takes no lease and answers `503 {status: "blocked", reason: "retry_heal_pending", code: "prediction_retry_heal_pending", pendingRunId}`. This is a start outcome, not a stop, because no run exists to stop. No run record, stop record or Event is written, and `latest-run.json` keeps naming the marked run. Only the start's own diagnostic row records `blocked`. The lease keeps naming the marked run, so every later start tries again.
- **Unknown outcome.** A write with an unknown outcome is not repeated blindly. The next attempt re-reads the queue, and a record that already carries the run's `lastRunId` is left as it is.
- **No queue object.** If the queue object is absent, the retries cannot be confirmed, and the mark stays until a rebuild creates the queue.

The queue format, the retry policy, hot-first selection and batch sizing do not change. Tests: `node tests/prediction-queue-cas.mjs`.

Run counters and film outcomes persist after each submission. Current-batch film reads stay bounded; completed batches are counted from saved outcomes rather than loading every completed film on every next request.

Which films are outstanding after a taste-profile change is decided by the queue rule in [prediction compatibility](../domain/prediction-compatibility.md#prediction-queue): the selective profile rule, with no switch ([ADR 0044](../../adr/0044-retire-profile-compatibility-switch.md)). The runner's own checks (pending count, completion, `already_current`) use the same rule, so a kept prediction is never recalculated.

Tests: node tests/continuous-drain.mjs; node tests/queue-compatibility.mjs; node tests/fingerprint-migration-queue.mjs; node tests/throughput.mjs; node tests/enrichment.mjs. The multi-batch integration test uses an isolated R2 implementation and deterministic validated model outputs; it is not a production LLM throughput benchmark.


## Stored prediction record and its lineage

A committed prediction (`enrichment/films/<id>/predictions.json` `current`, the same record in `history` with `replacedAt` once replaced) holds the model's fields as submitted (`predictedRating`, `probability4Plus`, `confidence`, `matchSignals`, `mainRisk`, `moodLabels`) and the Worker's: `filmId`, `generatedAt`, `tasteProfileVersion`, `tasteProfileHash`, `fingerprintHash`, `fingerprintSchemaVersion`, `fingerprintPromptVersion`, `predictionPromptVersion`, `runId` and `trigger` (`scheduled` or `manual`) of the run that produced it. The bundle keeps every replaced record; a recalculation never removes one. `fingerprintPromptVersion`, `runId` and `trigger` exist only on records committed since they were added ([ADR 0038](../../adr/0038-durable-rating-and-prediction-lineage.md)); an older record without them has an unknown prompt version and run, and no reader may fill them from the current state. Why a record was replaced is derived from the two records (a different profile, fingerprint or prompt version), not stored. One film's records and rating events are read through [the film history API](film-history.md).

## Immutable prediction version objects

Each committed prediction is also written once as its own object; the writer has no switch ([ADR 0045](../../adr/0045-retire-prediction-version-objects-switch.md), [feature flag register](../feature-flags.md)). A submit that creates or recalculates a prediction first writes `enrichment/films/<id>/predictions/versions/<sha256>.json`, where `<id>` is the stored film id as used in the bundle key and `<sha256>` is the SHA-256 of the object's exact bytes: the prediction record with its keys sorted recursively, without the pointer fields and without the history-only `replacedAt`. The write is conditional on the key being absent. If the key exists, its bytes are read back and must equal the bytes about to be written; a retry of the same record is therefore idempotent and a differing object is a storage conflict that fails the item and leaves the bundle unchanged. Only then is `predictions.json` rewritten with `current` carrying `r2Key` and `contentSha256`; a replaced record moves into `history` with its own pointer intact. A crash between the two writes leaves an unreferenced version object and an unchanged bundle, never a bundle pointer at a missing object. The view index receives the same record as the bundle.

Freshness is still decided by profile version and hash, fingerprint hash and schema version, and prompt version. Until the schema v7 marker is `d1`, readers use the objects. In that mode they use the D1 pointers and verify the immutable body; a missing or mismatched body fails the read, and the mirror is not a fallback. The view index prediction and fingerprint fields are replaced from those pointers on read. Migration `0007` is not applied. Records written before the writer was on carry no pointer and stay valid for the runtime. The shared rules (`src/domain/prediction-versions.js`) are the only definition of the body, the key and what counts as a linked pointer; the offline importer loads them from that source. Records without a pointer were linked once by the historical materialization ([ADR-0026](../../adr/0026-historical-prediction-version-materialization.md), [runbook](../../runbooks/prediction-versions.md)); its route is retired ([ADR 0050](../../adr/0050-retire-prediction-materialization-route.md)), and `scripts/prediction-versions-plan.mjs` remains the read-only check of a snapshot.

## Immutable fingerprint objects

A fingerprint has the same shape of storage ([fingerprint compatibility, Storage](../domain/fingerprint-compatibility.md#storage)), with no switch ([ADR 0046](../../adr/0046-retire-fingerprint-version-objects-switch.md)): a submit that accepts a fingerprint writes its content body (`enrichment/films/<id>/fingerprints/<fingerprintHash>.json`) and its generation record (`fingerprint-generations/<fingerprintHash>-s<schema>-p<prompt>.json`) create-only, then moves `fingerprint.json`; a body whose key already holds different bytes, or a record key holding anything but a valid record of the same identity with a stored body, is a storage conflict and the film fails with `storage_error` before the pointer or the index move. The pointer carries `fingerprintPromptVersion` (the Worker's `FINGERPRINT_PROMPT_VERSION`), `produced` and `previous`, and the new prediction carries the fingerprint's own `fingerprintSchemaVersion`. Readers are unchanged. A run is bound to the fingerprint schema, the fingerprint prompt, the prediction prompt and the transition registry it started with, next to the profile hash: `next`, `submit` and a `complete` without a reason answer `409 {code: "contract_changed"}` after a deploy that changed any of them, and the caller starts a new run. `next` reports the three versions with the profile. Which films are outstanding after a fingerprint schema or prompt change, how migration work is bounded within a batch, and when `next` restores a rolled-back fingerprint from a stored record, are in [fingerprint compatibility](../domain/fingerprint-compatibility.md#queue-and-runner).

### Retired materialization route

`POST /api/enrichment/predictions/materialize` is retired ([ADR 0050](../../adr/0050-retire-prediction-materialization-route.md)). Any method and body answers `410 Gone` with `{error: "gone", detail}` before the body is read; nothing is read, written or locked, and no value of the former `PREDICTION_MATERIALIZATION` binding reopens it. The historical run it served is complete and reconciled ([runbook](../../runbooks/prediction-versions.md#2-historical-materialization-completed-the-route-is-retired)); its receipts under `enrichment/predictions-materialization/` stay in R2.
