# Events log

The activity list reads objects under `events/items/`. The key is `events/items/<reverse-timestamp>-<id>.json`, so a page is newest first. `GET /api/events` returns one page and writes nothing: it does not deliver or recover anything, however often it is read or paged ([ADR 0107](../../adr/0107-get-head-read-side-effect-boundary.md), [AIR-416](https://trello.com/c/f7FX4Elk)); see [delivery of prediction run events](#delivery-of-prediction-run-events). Clients ignore an event type they do not render. A rendered event shows its `at` in Europe/Madrid and does not show storage keys, hashes, prompts or profile text.

| `type` | When it is written | What the list shows |
| --- | --- | --- |
| `epg` | The successful end of an EPG run (its completion time) | Counts of films and broadcasts |
| `watchlist` | A watchlist commit | Added and removed films |
| `discovery` | One **scheduled hourly firing** of the Discovery reconcile, for its UTC hour ([ADR 0111](../../adr/0111-discovery-hourly-reports.md)) | One compact report: the deltas of the hour (new films, observations resolved, reused, screened, TMDB calls), what is left in the queue and the state at the firing, even while a Workflow runs |
| `ratings` | A Ratings run that ended (finished, error or closed as unknown) | One compact result: Diary rows checked, new facts, removals handled, honest error or interruption |
| `started`, `unstarted` | An owner mark on one film | The film title |
| `enrichment` | A prediction run's start, progress, stop or completion. A new `batch_v2` run writes only the terminal completion or stop ([ADR 0146](../../adr/0146-batch-v2-single-terminal-prediction-event.md)) | Queue progress of the retired v5 runner (historical Events); one packet result for a new batch v2 run |
| `catalog_posters` | One weekly poster retry report, `deferred` or `final` ([below](#catalog-poster-weekly-report-catalog_posters)) | A compact weekly card: films checked, posters found, films still without a poster, and a retry time when deferred |
| `taste_profile` | One committed move of the taste-profile current pointer | Version transition, a short category and selective or global scope |
| `canonical_producer` | One outcome row of the Canonical Producer, delivered by the hourly reconcile: a completed pass `P:g`, a recorded stop, an in-flight pass a newer publication superseded, or a held automatic recovery ([below](#canonical-producer-outcome-report-canonical_producer)) | «Обогащение каталога»: units in the plan, processed, applied, no-op, kept, failed, remaining, and a closed technical group with the stop code, the recovery and the chain counts |

## Taste-profile publication

`PUT /api/enrichment/profile` writes this event only after compare-and-swap has made the version current ([publication contract](../api/enrichment.md#taste-profile-publication)). A dry run, a refusal, a lost compare-and-swap and a version record that is not current write none. The current pointer may be the R2 object or the D1 profile row. The event is always the R2 object above. The two writes are not one transaction.

```json
{"id":"taste-profile-3","type":"taste_profile","at":"2026-11-02T20:15:00.000Z","fromVersion":2,"toVersion":3,"changedFields":["horrorPreferences"],"scope":"selective"}
```

`id` and `at` come from the committed version (`taste-profile-<toVersion>` and that record's `updatedAt`), so a replay stores the same object and does not append another. `fromVersion` is the previous lineage link, or `null` when this version has no stored predecessor. `changedFields` are the field names the publisher already accepted, not the field text. `scope` is `selective`, `global`, `identity`, or `null` for the first version. The profile body, `profileHash`, approval and declaration hash are not copied.

The list turns one known field into a short category, several known fields into one summary line, and `identity` with no known field into a line that the content did not change. `selective` and `global` become «Влияние: выборочное» and «Влияние: глобальное». Any other scope adds no impact line. An unknown field name is not printed. Nothing in this event is a count of recalculated predictions.

If the event put fails, the publication response stays HTTP 200 and adds `publicationEvent: {recorded: false}`. Current stays where it is. The identical request then answers HTTP 409 `version_not_increasing`, does not move current, and records the missing event only when the committed version body has `tasteProfileEventExpected: true`. That field is server-written on the immutable version record. A version without it, including one that was already current before this writer, stays without an event; a caller-supplied field does not create one. A different body for that same version does not. The procedure is in the [publication runbook](../../runbooks/taste-profile-publication.md).

## EPG and watchlist events: publication, retry and idempotency

Contract of [AIR-359](https://trello.com/c/0IV9qKWR).

- **One `epg` event per published generation.** Its id is `<runId>-epg`, and `films`, `archive`, `future` and `broadcasts` are counted from the published report. Its `at` is the **successful end of the run**: `run.completedAt`, the value that becomes `sync.json` `updatedAt` when the run is `complete`. The header «Обновлено», the compact and detailed EPG footer (`integrations.sources[id=epg].lastSuccessAt`) and `GET /api/programme` `publishedAt` use that same instant. It is not the scan time (`report.updatedAt` / D1 `published_epg_generation.published_at`, which still copies the scan clock at pointer switch and still defines the archive and future windows). A later in-flight or failed run carries `sync.json` `lastEpgPublishedAt` so those surfaces keep the last completion and never show `startedAt` or `dueAt`. A missing or invalid clock is omitted (`null` / «нет данных»), never wall-clock now. The event is written only **after the run record is durably `complete`**: by `finishSync`, or at the end of the staged seal `queue` phase, never in `finalize`. A run that has not published or whose complete record could not be saved leaves no event, so there is no false «Обновлён EPG». Pointer switch can precede run completion (catalog/tail); the UX clock waits for completion so it matches this event, and stored events are not rewritten. A seal step that fails after the pointer switch (for example `rated_admission_incomplete` in `finalize_scan`) stores `sync.json` `error`, and the retry that completes the same run does not clear it; since [AIR-518](https://trello.com/c/9TuQIIud) that kept error is read as a recovered earlier attempt, so the surfaces above still show this run's `completedAt` (the event `at`) when the published programme names this run, and the next run carries it as `lastEpgPublishedAt`. The read model is described in the [footer API reference](../api/enrichment.md#compact-footer-read-model).
- **Order and recovery.** The completion step fixes `run.completedAt`, parks the finished event in `run.epgEventPending` and saves the complete run record (`stage: complete`, `updatedAt = completedAt`, the mark) in one write. Only then is the event put and the mark cleared. If the record save fails, nothing was exposed and the retry completes the run. If the event put or the clearing save fails, the persisted complete run keeps the mark and the next step on it (the complete-run continuation) writes the same event again and clears it: the event is then late, never false, and never duplicated. The key `events/items/<reverse-timestamp>-<runId>-epg.json` is derived from the parked `at`, so every retry hits the same key, and `sync.json` `updatedAt` carries the same time. Only the `epg` timestamp changed: the watchlist event, its removal-reference key rules and the other event types are untouched, and events already written are never rewritten, moved or deleted (the 8 November 17:01 entry keeps its scan time).
- **Run in flight across the deploy.** A staged run whose `epg` event was already written under the scan time by earlier code (its `finalize` ran before the deploy) keeps that event and gets no second one; its `completedAt` stays unset.
- **Channel policy fields.** In every scan since AIR-565 (`filtered` or `degraded` mode, [ADR 0191](../../adr/0191-epg-channel-policy-in-the-scan.md)), the `epg` event also carries `channels` (`total` channels the feed schedules, `discover`, `denyAll`, `knownOnly`, `new` declared ids the pinned snapshot does not hold, `undeclared` scheduled ids no `<channel>` declares (never registered), `unclassified` without category or override), `programmes` (`raw` programmes read, `filteredDenyAll`, `skippedKnownOnly`, `discoveryEligible`, `unclassified`, all counted over in-window programmes except `raw`) and `policy` (`mode`, the owner Channel page path `href`, and in `filtered` mode the `revision` and the SHA-256 `digest` of the applied map; in `degraded` mode a `reason` and **no** revision or digest). `channels.registered` (filtered only) is the number of channels actually written, against `channels.new` detected. A degraded scan adds `warning: {code: 'channel_policy_degraded', reason}` and a failed registration `warning: {code: 'channel_registration_failed', reason}`; the events screen says in words that the blacklist was not applied. An event from before the policy was applied unconditionally (a legacy scan) carries none of these fields, so a missing block means `legacy`; no new scan produces one. `films`, `archive`, `future` and `broadcasts` keep their meaning and are post-filter. A scan without a policy adds none of these fields, and a stored event is never recomputed: older events render without the block. The events screen renders `policy.href` (a same-origin path validated by the page) as the link «Admin Channels»; the public bundle itself names no admin path.
- **Rescan inside a run.** If an earlier attempt of the same run failed before the pointer moved, the next scan builds the events again for the scan it is about to publish (`epgSync` rebuilds them when the saved `epg` event does not carry the new `updatedAt`). A run saved by earlier code that still carries an `epg` event of a superseded scan has that event rebuilt from the published report when the run completes (its `at` is then the completion time).
- **Watchlist event.** Its diff (`added`, `removed`, `total`, `baseline`) is computed from the watchlist before the run and the run's watchlist, so a rescan yields the same delta. `at` is the run's successful completion (`run.completedAt`), the same clock as the `epg` event, not the scan (`run.watchlistObservedAt` / `report.updatedAt`). The journal object is written only after the complete run record is saved, so an interrupted run does not announce a successful watchlist update. The removal hand-over is fixed in that same completion step: the removed films are remembered on the run at scan time (`watchlistRemovalFilms`), and the reference `{eventKey, sourceRunId, at}` is created only once `at` is the completion time. The key `events/items/<reverse-timestamp>-<id>.json` is derived from that `at`, so the reference and the object name the same key. Ratings is given that reference only after the journal object exists; a failed event put leaves the hand-over on the run. The Cloudflare EPG executor (`EpgOrchestration.drive`) treats a published `stage: epg` run and a complete run that still owes an event as usable: it posts `/api/sync/epg` instead of `/api/sync/start`, including on the next Madrid day, so a delayed Workflow action cannot drop the pending delta. A complete run that still owes the journal after that step sleeps the first orchestration cooldown (`journal_pending`) instead of spinning; clearing `watchlistEventPending` is persisted, and a failed clear leaves the marker so the same event key is retried. A retry after the complete record is saved writes that same key and does not mint another timestamp. A reference or object that already exists for the event (a run that crossed this change with the previous scan-time key) is not retimed. Events already stored are not rewritten. This replaces the AIR-359 rule that a removal event kept the first scan time ([AIR-513](https://trello.com/c/Ktfi8lRR)); the owner accepted it for new events only.
- **Started and unstarted marks (AIR-516).** `POST /api/started` takes `{id, started}` where `id` is the spelling the mark is stored under (a Letterboxd lid or `tmdb_<n>`; the key `started/<id>.json` is unchanged). For a new mark the Film is the **canonical D1 Film**, read through `CanonicalCatalogReader.catalogStartedFilm` (the verified identity bridge of [AIR-475](https://trello.com/c/9OniH9d9), a typed trusted claim, never a title, a year or a slug), whether or not the Film is in the programme, the watchlist or Discovery. The event title is the reviewed, then the provisional localization, then the original title; `year` is the stored metadata year; `film.tmdb` is present only for the Film's one trusted, non-conflicting TMDB movie claim, so a Film with a Letterboxd id and no TMDB claim gets no TMDB link. The frozen `metadata.json` and `programme.json` are **never read** for this and there is no R2 fallback. Answers, all given before any R2 write: unknown Film `404`; conflicting, untrusted or ambiguous identity `409`; a redirected or owner-retired Film `410`; a held, not-open or unreadable Film/Person marker, an unreadable D1 or a generation that moved during the read `503` (`storage_unavailable` with `reason`). The D1 read comes first for every request, so a repeated `started` (or `unstarted`) for the existing state, which re-delivers the stored `lastEvent` under its own key, is fenced the same way: a held, not-open or unreadable marker answers `503` with zero R2 writes, and an open marker writes only the existing event key. A new `started` takes only D1 values: a Film with no title or year gets the neutral placeholder «Фильм» and a null year, never the values of an earlier stored event. `unstarted` removes an existing mark and never creates or switches an identity: it describes the film from D1 when the Film still resolves to the same verified TMDB movie the mark was made for, and keeps the mark's own last known `lastEvent.film` when the identity no longer resolves or now names a different verified TMDB movie (nothing is matched by title or year; an old event without `tmdb` cannot be compared and is described from D1). It still fails closed (`503`) while the Film/Person marker is not readable. `at` is the time of the new action; stored events are not migrated. **Storage authority of the marks (AIR-549 stage 2).** One marker row (`started_authority`, schema v29, independent of the Filter presets marker) decides, per request, where the marks live. Until the activation of 20 Nov 2026 the marker was `r2`, so the marks were the R2 objects `started/<id>.json` with `customMetadata.started`; that branch stays in the Worker only for a database that proves it is pre-migration, and its mark write has no compare-and-swap (two concurrent writes of one mark are last-writer-wins). Since the owner-approved activation of 20 Nov 2026 ([evidence](../../evidence/d1-migration/air-549-started-marks-cutover-2026-11-20.md)) the marker is `d1` and the marks are the rows of `started_mark` (`id` as spelled, `started` true or false, `startedAt`, the stored `lastEvent`, a per-row revision) and R2 `started/` is neither read nor written again: `GET /api/started` lists the started ids from D1 in the order the R2 listing had, `POST /api/started` commits one row with a compare-and-swap on that row's revision, and `bootstrapEvents` reads the marks from D1. A request that loses the race decides again on the state the winner left, so a same-state loser becomes the idempotent repeat of the winner's event and is never a second event. A marker that cannot be read, a held marker, a wrong database or a half-installed schema answers `503` (`Started marks storage unavailable`, or `Started marks are temporarily read-only` while writes are held) with zero writes and never reaches R2; while the marker is `r2` and writes are held (the import window), reads still come from R2 and every write answers `503`. The marker is read once more right before an R2 mark write, so a request admitted before the hold or the activation cannot write after it. The order of effects is unchanged: the mark is committed first, then the event is written under the id stored with the mark; a request that dies in between is repaired by the next request for that id: a same-state repeat delivers the stored event under its own id, and an opposite transition first writes the stored event to the journal (an idempotent write) and commits only when that write succeeded, so an event is never overwritten before it was journaled. No import or bootstrap creates an event of its own. The event journal `events/items/` stays R2-authoritative. `GET /api/started` and `GET /api/events` stay read-only. Cutover procedure: [Started marks cutover](../../runbooks/started-marks-cutover.md).
- **Film links.** The events screen and the compact feed (one renderer) link each title in the watchlist groups «Добавлены фильмы», «Просмотрены» and «Остальные удаления», and in `started` / `unstarted`, to the local film page. `eventFilm` stores numeric `tmdb` only for a trusted TMDB movie (`tmdbId` plus `tmdbLink.status=resolved` to a `/movie/` page of the same id). A stored event that already carries `tmdb` keeps it through `GET /api/events`. An unresolved, TV, mismatched or bare numeric `tmdbId` is not stored and is not turned into `/film/tmdb_<n>`. Otherwise the stored film id is the href when it matches the film-route id and does not start with `tmdb_`. A missing or invalid id stays plain text. Nothing is guessed from the title or the year, and the screen performs no extra read. A Letterboxd id opens the loaded programme film; a retained film that the catalogue read cannot open is [AIR-475](https://trello.com/c/9OniH9d9), not a second identity invented here.
- **Ratings at the first display.** The watchlist event is written with the confirmed ratings the fact store already holds for its removed films (at most 25 probed; stored facts only, no Diary, no Letterboxd request, no wait; see the [ratings reference](../integrations/letterboxd-ratings.md#the-epg-commit-under-the-separate-pipeline)). A film rated before the publication is shown with its rating at once (the half-star value is kept); a film with no stored fact, a null rating or no probe stays unrated and is listed as «Остальные удаления», never as viewed on the strength of a missing rating. A removed film that carries a confirmed half-star rating is listed as «Просмотрены»: the rating on an event comes only from a confirmed fact (the fact store, Diary or the owner's film page), never from a prediction or from the removal itself, so the group states a known viewing. A rating that arrives later enriches the **same** event (same key, same `at`, one event, other confirmed ratings kept) through `settleRemovalRefs`. Listing events (`GET /api/events`) looks nothing up. On the daily schedule the Ratings run (17:00 Madrid, seconds long) normally finishes before the EPG commit, so a rating that Diary shows that day is already stored; a rating that Diary does not show yet waits for the next daily Ratings run, which settles it on the same event.
- **Idempotency.** A repeated `finishSync`, a resumed committed run and an events refresh write the same keys; no second event is created. Events written by earlier code are not rewritten, and ordering and pagination by key are unchanged.
- **Not covered.** A one-off correction of an event that was already written with a stale time (the 5 November 17:03 entry and the 8 November 17:01 entry) is a separate owner-approved action: exact key, idempotency and readback. This contract changes code only.

## Ratings run result (`ratings`)

Contract of [AIR-361](https://trello.com/c/pKYwrxcZ). One immutable event per Ratings run that reached a terminal state in the run record (`finished`, `error`, or `unknown` when a stale or interrupted run is closed). Never one per film, per step or per heartbeat, and none for a run that never started or whose terminal state was not persisted.

| Field | Meaning |
| --- | --- |
| `id`, `runId` | `<runId>-ratings` and the run id. The Workflow instance id, the hour and the generation time play no part |
| `at` | The run's real end (`finishedAt`, or `closedAt` for an unknown close); the key is `events/items/<reverse-timestamp>-<id>.json` as for every event |
| `state`, `cause` | `finished` / `error` / `unknown`; `cause` is one of `failed`, `blocked`, `rate_limited`, `interrupted`, `abandoned`, `diary_off` or null |
| `trigger` | `scheduled` or `manual` |
| `coverage` | `recent_window` while only Diary page one was read; never «whole history checked» |
| `diary` | Counts only: `pages`, `rows` (checked), `added` and `updated` (Diary entries), `written` (facts written), `unchanged`, `skipped` (already recorded), `conflicts` |
| `removal` | `pending` at the start, `checked` lookups, `rated` (removed films whose rating was found in this run, by Diary or by a lookup) and `resolved` (removal references of the Events Log settled with a rating, including films rated earlier). The two count different things and do not overlap; a rating whose reference could not be settled counts as `rated` only |
| `details` | Optional, [AIR-393](https://trello.com/c/45smSEfH). Only for the films this run **changed**, absent when it changed none and on every event written before the field (those render as the short summary, with no backfill). Groups, each a list of `{id, title, year, tmdb, rating}`: `added` (a new watched fact; `rating` null for a view without a rating), `updated` (a different rating, with `from` only when the earlier one was a stored number), `rated` (a removed film whose rating a member-page lookup found for the first time in this run) and, on events written before [AIR-443](https://trello.com/c/Av5rDn3M), `resolved`. **The lists are news, the counters are work.** A rating the user was already told about is never announced again: a removed film whose rating the Diary supplies is either `added` in the same run (a first fact) or already known from an earlier run, so it is not listed as `rated`; settling a removal reference with a rating that is already known is service work and has no list at all (new events carry no `resolved` list; `removal.resolved` keeps counting the references settled), and a film the run reported as `added` or `updated` is not also listed as `rated`. A film appears once per group, so a film with two references is listed once while `removal.resolved` counts both. The removed film in `added` is named from its removal event when the metadata does not know it. **Records written before AIR-443** carry no `news` marker on their Diary page contributions; their `rated` and `resolved` lists mixed Diary reconciliation with news and cannot be told apart, so neither is passed on when such a record builds its event, while the removal contribution (lookups only) is kept. The hidden `resolved` remainder never makes an event `incomplete`; a page marked incomplete or an overflow of a visible group still does. Events already published are not changed. At most 25 films per group; `more: {<group>: n}` counts the rest, so nothing is cut silently. `incomplete: true` states that some change could not be captured or named. `id` is the Letterboxd film id (never shown as a title); `title`/`year` are null when no stored source knew them; `tmdb` is set only where every stored id agrees |

**Interrupted Ratings run (AIR-694).** An interrupted run is a result of unknown outcome, not a confirmed error. The slot Ratings phase reports `outcome=interrupted` (with the bounded `reason` and `phase`) when a step lost its lease (`lease_lost`), the pipeline no longer recognises the run (`unknown`, `run_mismatch`, `not_running`) or the run's own record is already `unknown`; `storage_unsupported` stays an error. When the reconciliation phase meets the interruption (a lost lease in removal, or the run's own `unknown` record), the reconciliation outcome is `error` and the interruption travels beside it: it never changes a finished Diary outcome, never adds a third Event and never reruns a stale run. The frozen `ratings` Event takes **the pipeline's own contract whenever the run record can supply it** (`ratingsEventOf`): for a run closed as `unknown` it carries `state=unknown`, `cause` (`interrupted` or `abandoned`) and `interruptedPhase` (`diary` or `removal`). Groups follow what was **committed**: `diary` is present only when the step summary (counts and facts) was committed, `removal` only when a removal step committed its settled/lookup counters; a checkpoint, an applied page record or an intents-only container is not an aggregate. Otherwise the group is `null` (unknown, never zero); confirmed `details` are kept and genuine committed zeros stay zeros. When a step loses its lease and the slot's own run is still `running`, the same builder turns that record into the contract in memory (nothing stored, no terminal state invented, no rerun), so confirmed Diary counts survive a lost removal lease. Only when the pipeline supplied no contract, the slot freezes `state=unknown`, `cause=interrupted`, `interruptedPhase` (when known) and null groups. The slot's bounded `reason` (for example `lease_lost`) stays on the Event; the screens show the specific reason before the generic cause. The Events screen and the compact feed classify the event as interrupted (badge «Прервано», «Результат» filter «Прервано»); `error` stays for confirmed failures, `blocked` and `rate_limited` stay warnings. An already stored event with neither `state` nor `cause` (the earlier fallback shape: `outcome` + `reason` only) is classified from `outcome`/`reason` by the same reader; stored events are not rewritten.

Written, read and unchanged are different numbers: 50 rows checked with one new fact reads «записей проверено 50, новых фактов 1». The aggregates carry only numbers. The optional `details` carry titles, years and ratings of the changed films only, never Diary rows, URLs, the unchanged 50 or raw Letterboxd content.

**Delivery.** The D1 run record is the source and R2 is a projection, and the two are not atomic. An event is built from a **committed** terminal record only and put with a create-only precondition, so a repeat finds the key and writes nothing; a close that a start has not committed (a compare-and-swap that is lost) publishes nothing. It is delivered right after the terminal commit and again at the next look: a start (after its own commit), a terminal read by the Cloudflare executor, the closing of a stale run, or the hourly executor tick, so a missed event is repaired without starting Ratings again. The run is marked `ratingsEventAt` once delivered. If the record is replaced before delivery, the owed event moves to the new record (`pendingEvents`) with a retry time (15 minutes, doubling to a day), so the attempt rate is bounded but the outcome is never given up on. Only when more than 60 outcomes are owed at once (about two months of daily runs with the Events Log unreachable) is the oldest discarded, and `eventsDropped` on the run record counts it. The owner accepted this bounded policy on 2026-11-06 (AIR-361 review); keeping overflow without loss would need another store and a new decision. A failed put never fails the run, never reads Diary again and never repeats a step; the status reads and writes nothing. Events for runs that ended before this change are not created.

**How the details are taken (AIR-393).** They are recorded on the run record while the run works and are never rebuilt afterwards. A plan is an intent and a receipt is a fact, and only receipts reach the event. For the Diary page, the films it will change (a new watched fact, a different rating, a removed film whose queue entry the Diary will resolve) are **planned from the view index before any fact is written** and saved on the record under the page's own key, `diary.pageChanges[<page>]`, in state `planned`, so a kill after the facts are written cannot lose them. The page checkpoint then saves the contribution in state `applied`: on the first attempt narrowed to the writes that really happened (`applyDiaryEvidence` outcomes and the queue entries the Diary resolved); on a replay of the page (a plan already stored) narrowed to what the stored view and queue show now (a film that is watched, a rating equal to the planned one, a queue entry resolved by the Diary), so a write another writer won, or one the page lost as older, is not claimed. This is a check of the stored **state**, not of who wrote it: a replay cannot tell this page's own earlier write from another writer's identical value stored after the plan, so for a replayed page `details` state what the stored data shows changed during the run, not a proof of which writer changed it. A first attempt is stricter: it claims only the writes its own `applyDiaryEvidence` reported. A contribution that stays `planned` (the page never completed: a failed, blocked or abandoned run) is ignored by the event. The plan and the confirmed contribution keep **every** candidate of the page (a page holds about 50 rows; the hard ceiling is 100 per group), so the confirmation covers the whole page, not only the films an event can show; the event is built from the confirmed lists and only then shows the first 25 and counts the rest, so the remainder is exact. A replay replaces its page's contribution instead of adding to it, so a remainder is never counted twice. Past the ceiling the count is a lower bound and the event carries `details.incomplete`. If the planning, reading or saving of a page's details fails, the facts are still written and the contribution is saved as `incomplete`: the event then carries `details.incomplete: true` and the screens say the list is incomplete, never a complete-looking list. The removal steps work the same way. Before a step settles a reference or looks a film up, it saves an **intent** (`removal.intents`: the film, and the reference's event key for a settlement) on the run record; after the effects it confirms each intent against the stored queue (a `rated` film is a queue entry in state `rated` with a half-star rating; a `resolved` film is a reference that is marked resolved) and moves the confirmed films into `removal.changes`, clearing the intents. A kill after a lookup or a settlement, before that confirmation, leaves the intents on the record, and the **next step confirms them before it starts**, so the film is neither lost nor claimed twice. An intent whose effect did not happen (a film that was not rated, a reference whose event is missing) is dropped, not claimed. As for a replayed Diary page, this confirms the stored state, not which writer produced it. `rated` (rating discovery) and `resolved` (reference settled) stay separate groups, a film with several references appears once in `resolved`, and the counters keep their meaning. `removal.changeSteps` keeps the recent confirmation tags, so a repeated merge of one confirmation is ignored. The event merges the applied page contributions and the removal contribution. The counters of the Diary page are still saved with the step summary, as before this change, so a step killed after its page checkpoint loses that step's counters (the event can then show `0` written next to a list of films), never its films; the list is the receipt, the counter is the older, coarser number. The names come from what is already stored: the removal event that listed a removed film, otherwise the metadata cache and the title dictionary. No Letterboxd or TMDB request is made for a name, and `GET /api/events` reads nothing extra. Because the event is built from the committed record, a retry, a checkpoint between steps, a lost create-only put and the carried delivery all produce the same `details`; a repeated delivery changes no stored event. `rated` and `resolved` are different measures: the same film may be in both, and neither list is added to the other's count. The details are bounded by construction (4 groups, 25 films per contribution and in the event), also in the carried `pendingEvents` list.

The events screen and the compact feed draw each non-empty group as an expandable list like the watchlist event. A film is a local link to `/film/tmdb_<id>` only when `tmdb` is present; without a stored title it reads «Название недоступно», never its id; a rating is shown only when it is a half-star between 0.5 and 5.

## Discovery hourly report (`discovery`)

**Boundary (AIR-410 v2, [ADR 0111](../../adr/0111-discovery-hourly-reports.md)).** Every **real scheduled hourly cron** of the Worker writes exactly one `discovery` event for its UTC hour, whatever the Discovery pipeline is doing: a Workflow chain that runs for hours across rollovers (with or without results in the hour), a wait for a successor, a typed refusal (`projector_window`, authority held, generation handoff...), exhausted recovery, a generation handoff, nothing to run, or a confirmed empty queue. The chain and its terminal stop write no event of their own. An unscheduled caller (an operator or MCP reconcile, a test) writes none, a cron tick without Workflow admission writes the report of its hour as the typed refusal, and no report is invented for an hour in which the cron did not fire: a missed hour is not backfilled (a gap is for the Monitor), and the next report says how far back it reaches in `from`.

**Identity.** `id` is `discovery-hour-<first 12 characters of the published generation without dashes>-<UTC hour as YYYYMMDDTHH>`; `at` is the start of that UTC hour. The same generation and hour always have the same key, so a duplicate, delayed or concurrent cron of the hour finds its report and writes nothing. A firing of an hour that is not later than the last closed one (`lastClosedHour`; the compact UTC keys sort chronologically) is rejected without changing the record, so a delayed or replayed old hour can never close an accumulator that already holds the chunks of a later period under an existing id; it may still drain the outbox. UTC hours make the key independent of DST: the repeated local 02:00 hour of the October change is two different hours with two reports. `generation` is the first 8 characters of the generation.

**Fields.** `kind` is `hour`. `from` is the end of the previous period (the `at` of the previous closed report, `null` before the first; after an hour whose close failed it reaches back past that hour). `status` is one of: `running` (a chain was started by this firing or is in progress), `waiting` (`recovery_waiting`: a successor waits for its backoff), `stalled` ([AIR-534](https://trello.com/c/90dyx0Ai); `recovery_overdue`: the series stopped without a terminal reason, the queue is not proven empty, and its recovery was already due at the firing with no successor started; a recovery not yet due is `waiting`), `blocked` (a typed refusal in `reason`, or `other` / `unknown`), `failed` (`recovery_exhausted`), `empty` (the queue is a confirmed zero) or `idle` (stopped for a terminal reason, nothing to start, the queue is not proven empty; a `running` hour with `chunks` 0 is shown as started without useful progress, never as working); `reason` is the typed reason or `null`. `chunks` is the number of chunks whose checkpoint was saved in the period. The counters are `checked` (observations processed), `added` (new catalog films), `reused`, `screenedOut`, `touched` and `tmdbCalls`, **deltas of the period**, not lifetime totals: the sum of the counters of consecutive reports equals the sum of the committed chunks. `remaining` is the last known queue size (`null` when unknown), `queueEmpty` is `true` only when the queue is a proven zero, `queueUnreadable` is `true` when the queue could not be read while the deltas of the period are real, `incomplete` is `false` on every event written since [ADR 0118](../../adr/0118-discovery-report-failure-notice.md) (an event written earlier can carry `true` with every number `null`), and `error` is a code from a fixed list or `null`. No film, title, key or free text is stored.

**Counting model.** Attribution is by **commit time**. The executor record (`epg/discovery-workflow.json`, D1 when the Discovery authority is `d1`) carries one open accumulator `report`. Each chunk checkpoint adds that chunk's summary to it inside the owner's compare-and-swap and records the chunk key (`<instance id>:<ordinal>`) in a bounded `seen` list, so a retried or replayed checkpoint adds nothing a second time. A chunk belongs to the period in which its checkpoint was saved, whatever series or generation it ran in. The cron closes the period in **one** compare-and-swap of the same record: it appends the report event to the `outbox`, resets the accumulator (`since` = the hour start, `lastClosedHour` = the hour) and keeps `seen`. A checkpoint racing the close either lands before it (in this report) or after it (in the next), never in both: the compare-and-swap decides, and the close reads the record again after losing it. A checkpoint that is not saved loses its numbers, so the counters are a lower bound by exactly that.

**Empty and unknown.** The proof is the shared, strict one of the [Discovery queue state](../api/enrichment.md#discovery-queue-state) (`discoveryQueueProof`), so a report says «Очередь Discovery пуста» exactly when the footer, the Monitor, the operational status and the admin data health classify the same records as `empty`: the status written by the continuation's own last chunk (same generation and `hopId`) with `remaining`, `cheapRemaining`, `deferred` and `waitingRetry` all the number 0 and no error, no quarantined executor record and no live Discovery writer. The period's accumulated reading is shown as the report's numbers, never as a proof. A stored event is a snapshot of its hour and is never recomputed from the current state; an event of the earlier per-chain model keeps its own historical `queueEmpty` rule. The queue is empty when the continuation of the generation says `complete` with that reading. [AIR-595](https://trello.com/c/dPjrNIbQ) adds the one other proof, for a series that drains while the legacy alias sweep of [ADR 0158](../../adr/0158-epg-title-alias-provenance.md) is still open (the sweep keeps the continuation from `complete`): the executor record of the generation is stopped with the terminal reason `backlog_empty`, the continuation of the same generation is paused on `chunk_budget` with `remainingChunks` 0, and the status file written by that same chunk (the same `hopId`, the same generation) has `remaining`, `cheapRemaining`, `deferred` and `waitingRetry` all the number 0 and no error. Nothing runs again for that generation, and the open sweep re-checks aliases of films already decided, so it is not part of the queue; the report then says `status` `empty`, `reason` `queue_empty`, `remaining` 0, with the real deltas of the period. Any part missing, unknown, of another hop or of another generation keeps the report `idle` (`reason` the terminal reason). A missing, `null`, negative, fractional or non-numeric part is unknown and never read as zero. The period's own chunks are the freshest reading **only for the generation that wrote them**: the accumulator remembers the generation of its last chunk (`queueGeneration`), and a report of another generation (the record was replaced after the chunk) keeps the committed deltas but never reuses that backlog or `empty` state. Without a reading of its own generation, the last saved status of the published generation is used (a status of another generation is not), and otherwise the queue is unknown (`remaining` `null`, `queueEmpty` `false`). An unreadable queue source leaves `remaining` `null`, `queueEmpty` `false` and sets `queueUnreadable`; the deltas of the period are still reported. When the record cannot be read or written (no record, an unreadable record, a held projector window, lost compare-and-swaps, an outbox at its limit), the close writes one **`report_failed` notice** for the hour instead of a report ([ADR 0118](../../adr/0118-discovery-report-failure-notice.md)) and leaves the accumulator untouched, so the deltas appear once in the next report, whose `from` reaches back to the last closed report. The notice has `kind` `report_failed`, **the same id as the report of that hour** (`discovery-hour-<generation>-<UTC hour>`, one canonical identity per generation and hour), `at` the hour start, `generation`, a typed `reason` (`no_record`, `state_unreadable`, `outbox_full`, `projector_window`, `write_conflict`, `epg_priority`) and `status`, which is `failed`, `waiting` or `blocked` only when the reconcile of that firing confirmed that Discovery state and `null` otherwise. **`epg_priority`** ([AIR-595](https://trello.com/c/dPjrNIbQ)) is the planned EPG-priority pause of [ADR 0135](../../adr/0135-epg-priority-discovery-pause.md) / [ADR 0175](../../adr/0175-epg-priority-holds-until-run-complete.md): the record write of the close was refused with the typed `discovery_epg_priority` answer of the D1 gate (never inferred from the time of day). It is not retried inside the firing (the pause lifts only when the publication is handed off and, with migration 0026, certified complete), and when the reconcile of the same firing was refused by the same pause the notice names no other state (`status` `null`); a different confirmed state (`failed`, `waiting`, another refusal as `blocked`) is still named. A genuine lost compare-and-swap stays `write_conflict`, retried as before. When a queue read of the same close also failed (the continuation or status read threw), the notice keeps that independent fault beside the pause as `fault: "queue_unreadable"` (no number, no queue fact), so a read failure is never hidden behind the planned pause; a clean pause has no `fault`. It has no counter, no `remaining`, no `from`: nothing is shown as a number, an unknown or a zero, and a report failure never implies a Discovery failure. It is not stored in the executor record (that write is what failed): it is put create-only straight into `events/items/` and never replaces anything, while a **report of the same hour replaces its notice** by a compare-and-swap on the notice's etag (an existing report is kept), so the journal holds exactly one event per hourly firing. When the journal refuses a notice, it waits in a separate ledger (its own compare-and-swap) that never evicts: one compact tuple per undelivered hour, at most 8,760 (a year of hours; at the bound the newest is refused and logged `lost`), drained oldest first, at most 64 entries a firing, before each later scheduled close. Since [AIR-595](https://trello.com/c/dPjrNIbQ) this one logical ledger is stored in two objects, so that a code rollback evicts nothing: `events/discovery-report-faults.json` holds only the four-element tuple `[generation, hour, reason index, status index]` with one of the five reasons a Worker before AIR-595 decodes (that Worker drops any tuple it cannot decode when it writes the ledger back), and `events/discovery-report-faults-v2.json` holds the five-element tuple `[..., fault index]` of a notice it cannot rebuild (`epg_priority`, or a `fault`). The exact guarantees across both ([ADR 0209](../../adr/0209-discovery-report-fault-ledger-in-two-objects.md), option A accepted by the owner on 24 Nov 2026): each object is written under its own compare-and-swap, never evicts and refuses the newest entry once the combined count it observed (both objects) has reached 8,760; the admission also refuses an hour already queued in either object. That combined check is **best effort under simultaneous writers to different objects**: two firings that read the same count can each add one entry (so the total can stand one entry per simultaneous writer above 8,760), and a simultaneous repeat of one hour with two reason classes can queue two tuples; the journal's create-only identity still shows one event for the hour, and the next admission sees the bound and is refused. The drain bound is strict: a firing merges both objects, drains the oldest hours first with at most 64 journal puts in total (the batch is fixed before the first put, so a failure of either object's cleanup never lets the other spend more), then cleans each object under its own compare-and-swap; an uncertain cleanup answers `pending: null` and the next firing finds those hours `exists` and removes them. An older Worker never reads or writes the v2 object, so after a rollback its entries wait unevicted and are delivered once after the roll forward; meanwhile the older Worker bounds and drains only its own object, so after a roll forward the combined count can stand above 8,760 by at most the v2 entries that were pending at the rollback, in which case no new entry is admitted until the drain brings it under the bound. Delivery is eventual during a journal outage; with the journal and the ledger both refusing, only the log line `discovery_hour_close_failed` (`notice`: `delivered`, `queued` or `lost`) remains. A report of an hour that already holds its notice replaces it.

**Delivery and idempotency.** The event is written create-only under its id in `events/items/`; a second put finds the key and keeps the first. The one deliberate exception is the Discovery `report_failed` notice of an hour: the report of the same hour replaces it by a compare-and-swap on its etag, and nothing else is ever replaced. The report is first durable in the `outbox` of the executor record (the same compare-and-swap that closes the period), and delivered after it by the closing cron or by the next one; an entry leaves the outbox only after its put is confirmed, and the record is written back with `updatedAt` unchanged so delivery never hides a stalled instance. A lost put is therefore never a lost report, and a crash between the put and the removal only repeats an idempotent put. The outbox holds at most 64 entries and drops nothing: at the limit a close first tries to drain it, writes the `report_failed` notice of the hour with the reason `outbox_full`, leaving the deltas in the accumulator (coalesced into one later report). The close never starts a Discovery step or a TMDB call, uses no lease, takes only the existing record compare-and-swap that a held projector window already refuses softly, and a replacement of the executor record (a newer generation) carries `report`, `outbox` and the last closed hour into the new record, including the first series of a new generation started by the reconcile (that path dropped them before [AIR-595](https://trello.com/c/dPjrNIbQ), so the first report after a publication had `from` `null`). `GET /api/events` returns the stored event unchanged and writes nothing for it.

**Compatibility.** Events of the earlier per-chain model (`kind` `run` or `empty`, written before ADR 0111) stay readable and keep their card. A legacy `tick` left in an executor record is delivered once if it was settled and not yet delivered, and an open legacy `tick` is dropped (its lifetime totals are not a report). The legacy `outbox` entries are delivered as they were.

**Window wait and provisional empty.** The hourly close waits out a held projector window (at most three tries, each bounded by the window deadline) and re-reads the record before retrying. If the window outlasts the firing and the queue is proven empty for the same generation with zero deltas, a confirmed `empty` status of this firing and a record of that same generation, the normal `kind=hour,status=empty` event is published with `provisional: true` and the record is not written. A report of the same hour replaces a notice or a provisional event by compare-and-swap; a provisional event never replaces a report. See [ADR 0118](../../adr/0118-discovery-report-failure-notice.md).

**Display.** The events screen and the compact feed draw one compact card from fixed sentences chosen by `status` («Найдено новых фильмов: N», «Новых фильмов не найдено», «Discovery работает, новых результатов за час нет», «Очередь Discovery пуста», «Discovery ждёт повтора», «Discovery не запустился: временный отказ», «Discovery остановлен после повторных ошибок», «Discovery не работает: запуска не требовалось»), the three numbers (new films, observations resolved, left in the queue), one line with reused, screened and TMDB counts and the start of the period. A proven zero is drawn as `0`; a part that is `null` or not a non-negative integer is drawn as «неизвестно», a `report_failed` notice as «Отчёт за час не удалось сформировать. Если за этот период что-то было найдено, оно войдёт в следующий успешный отчёт.» with no numbers (plus the fixed sentence of a confirmed Discovery state), a notice with `reason` `epg_priority` instead as «Discovery приостановлен на время обновления программы. Пауза снимается, когда обновление программы опубликовано и подтверждено как завершённое. Если за этот период что-то было найдено, оно войдёт в следующий отчёт.» with no numbers, no report-failure text and no promise that Discovery resumes (plus «Кроме того, состояние очереди Discovery в этот час прочитать не удалось.» for `fault` `queue_unreadable`, and the sentence of an independent confirmed state, whose badge stays an error for `failed` / `stalled`), an hourly report with `status` `blocked` and `reason` `epg_priority` with the same first sentence and its proven counters, an event stored before ADR 0118 with `incomplete` `true` as «Отчёт за час неполный», an unread remainder beside real numbers as «не удалось прочитать» with one note, and nothing stored reaches the page as markup (no reason code or error text is printed).

## Delivery of prediction run events

A run of the retired **v5 / continuous** runner wrote two kinds of `enrichment` events at fixed points: `prediction-start-<runId>` when it started and `enrichment-<runId>` when it stopped for a systemic reason (quota, a provider or storage error, a lost or expired lease). Progress Events (`enrichment-<runId>-progress-<n>`) may appear during a long run. Each start or stop has a **durable record** written before the journal item: `enrichment/start-events/<runId>.json` and `enrichment/stop-events/<runId>.json` hold `{event, delivered}`. The journal key is derived from the event's `id` and `at`, so writing the same event again rewrites the same item: a repeated or concurrent delivery cannot duplicate it.

A **`protocol=batch_v2` run** does not write a start Event or a progress Event ([ADR 0146](../../adr/0146-batch-v2-single-terminal-prediction-event.md)). After the terminal commit (normal `complete`, including `manifest_spent`, or a systemic `partial`) it writes one `enrichment-<runId>` parked in `enrichment/stop-events/<runId>.json`. New objects carry `presentation: "batch_v2_terminal"`. A persist failure after the start has allocated that `runId` (including `prediction_domain_cas` at `runner_started`, before a film is submitted) still goes through the same stop recorder with `protocol=batch_v2` and that `runId`: the Event is `stage: partial`, `details.processed: 0`, empty success/failure lists (a blocked start is not a per-film failure), and the packet interruption title. The stop identity is the run's, so a repeated delivery rewrites the same parked record. If the process ends after the completed run (and `run.event`) is saved and before that stop record exists, the next authorized start reconstructs the missing `stop-events` object from `latest-run.event` and then delivers it once through the same quarantine-aware outbox path. An existing parked record is never flushed by that reconstruction step. The Events screen uses that marker for the packet titles («Пакет прогнозов обработан», «… с ошибками», «Пакет прогнозов прерван») and does not print the raw code `manifest_spent`. Objects stored without the marker keep their previous cards. A start that never creates a run (`manifest_too_large`, idle `noop`/`blocked`, a `409` refusal, a dry run) writes no Event. There are exactly two exceptions, and both leave only the neutral `batch_v2_skipped` Event of the refused attempt, never a run, a stop Event or a terminal Event: a start turned away with `already_running`, and a real (non-dry-run) start refused with `prediction_catalog_held`. See **Skipped starts** below and **Skipped starts of a held catalog** below it.

**Skipped starts (`presentation: "batch_v2_skipped"`, AIR-548, [ADR 0180](../../adr/0180-skipped-predictions-start-is-a-neutral-event.md)).** A real `batch_start` that a live runner lease turns away (`already_running`, on the early lease check or at the lease acquire after the preflight) records one `enrichment` Event: `id` `enrichment-skipped-<requestId>`, `stage` `skipped`, `protocol` `batch_v2`, `reason` `already_running`, `at` of the refusal, `requestId`, `trigger` (`scheduled`/`manual`, only when the request stated it) and, when known, `holderRunId` and `holderAgeMs` (time since the holder's last lease write, from its `heartbeatAt`; since AIR-588 it is no longer derived from the expiry, so it stays exact when the lease TTL changes). It has no `runId` of its own, no `queueSchemaVersion`, no counts and no `details`: it never claims that films were processed. The identity is the request: a replayed request id is one journal item (the durable record `enrichment/stop-events/skipped-<requestId>.json` is created once, so the time and the journal key are stable), and a different request id is a different Event; nothing is merged by time. The count of such cards is a count of refused start **attempts**, not of separate Scheduled Task ticks. Delivery uses the outbox below, **index entry first**, then the parked record, then the journal item (bounded retries, quarantine); a journal outage never changes the `already_running` answer, the card appears at the next successful start (any request id), and a parked record always has an index entry. The parked record is the request's identity (it keeps `at`, part of the journal key): no journal item exists for a request without it, it is deleted only when a `head` proves the item absent, and a replayed request id never produces a second item, even when the journal outcome or the `delivered` marker was uncertain. Limitation: with the journal and the index both unwritable at the refusal (or a failed park), that one Event is not recorded (nothing is orphaned). `409` refusals, `manifest_too_large`, `queue_changed`, idle `noop`/`blocked` and a dry run write none. The Events screen draws a neutral card «Запуск прогнозов пропущен: предыдущий ещё выполняется» (time, trigger, holder and age when stored, request id, code `already_running`), with no error styling and no Telegram alert. Earlier refusals are not backfilled. It is listed under «Прогнозы» and «Все события» with the result `warning`; since AIR-584 it has no «Тип событий» button of its own (see the type filter below).

**Skipped starts of a held catalog (`reason: "catalog_held"`, AIR-575, [ADR 0190](../../adr/0190-catalog-held-start-is-a-skipped-event.md)).** A real `batch_start` answered `503 prediction_catalog_held` (any of the gate, preflight, queue refresh, lease revalidation and persist paths) records the same neutral Event with `reason` `catalog_held` and `cause` `discovery_fence` or `discovery_incomplete` (only when it is one of those); it has no holder fields, no `runId`, no counts and no film ids. It is recorded at the route's exit from the answer itself, never for `dryRun`, and the identity, the outbox delivery and the limitation are those above (a request id is one attempt; a replay refused for another reason reads back the first record). The recorder mutates only the Event and its outbox entry: it creates no run and no stop Event, never changes the 503, and says nothing about effects the start had before the refusal (a keyed start's own claim, acquired and released, or a guarded queue settlement by the queue refresh, ADR 0188), which remain as the runner defines them. The card reads «Запуск прогнозов пропущен: каталог временно недоступен», states only that the attempt was refused and that its films were not processed, gives a fixed cause sentence that does not name an EPG publication (the cause may also be a genuine catalog replacement hold), the request id and the code `prediction_catalog_held`; its result is `warning`. It is shown in «Все события» and «Прогнозы» (with the result `warning`). The 21 November 2026 refusal is not backfilled.

**Named films on a new terminal object.** New `batch_v2_terminal` objects also carry a compact `details` snapshot of **this run**, recorded when each film settled and copied onto the Event at the terminal commit. It is not rebuilt from the live queue or from a later `latest` prediction. `GET /api/events` returns the stored object and writes nothing.

**Stop code on an interrupted packet (AIR-508).** A `batch_v2_terminal` Event that is neither a normal `complete` nor `complete` with per-film errors shows the stored `stopReason` (else `reason`) as `Код: <code>` beside its plain-language sentence, so `storage_error`, `external_termination`, `api_error`, `lease_lost` and the other mapped reasons stay distinguishable under the one title «Пакет прогнозов прерван». Only a code in the fixed list of the renderer (`BATCH_V2_STOP_CODES` in `public/app.js`) is printed; a missing or unlisted value reads «Код не указан», and no raw backend text, stack or secret reaches the page. The code is the one frozen on the terminal Event, not current diagnostics. Coverage, percentages and global queue figures stay out. No schema or writer change; Events stored earlier render the same way from the fields they already hold.

| Field | Meaning |
| --- | --- |
| `details.processed` | Films this run actually settled (`created`, `recalculated`, `already_current`, or a recorded per-film failure). Not the manifest size and not global coverage |
| `details.success[]` | Films that received a prediction in this run (`created` or `recalculated`). Each row is `{filmId, title?, year?, status, rating?, source}`. `source` lists recorded `assessment.sources[].kind` values (`metadata`, `model_knowledge`, `web_research`) and optional `accesses` for web research (`full_text`, `partial_text`, `search_snippet`). Up to three `authors` are copied only from conflict positions whose linked source is `web_research` with `full_text` or `partial_text` (never a `search_snippet`). No URL, `usedFor` text, `ratingBasis`, stance, or assessment body |
| `details.failure[]` | Recorded per-film failures of this run. Each row is `{filmId, title?, year?, kind, attempts?, exhausted?, claimed?}`. `attempts` is the stored retry count including the current try, omitted when unknown. `exhausted` is true only when that count has reached the ten-failure parking budget. `claimed` is a closed caller reason when one was stored. Unsubmitted slots and a systemic stop are not listed here |

The Events screen for an object **with** `details` shows «Обработано: N», «Осталось в очереди: hot N · cold M» (a missing remainder is «нет данных», never a guessed zero), and expandable groups «Успешно добавлены прогнозы» or «Добавлены/обновлены прогнозы» and «Не удалось получить прогноз», each a named list with a `/film/<filmId>` link when the id is a safe identifier. Empty groups are omitted. Coverage percentages, the local/window totals and the raw `manifest_spent` code are not shown on this card (they remain on the footer and on older events). An object **without** `details` (every Event written before this snapshot) keeps the earlier packet counters and coverage lines; it is not backfilled and is not drawn as empty film lists. A `complete` run with per-film failures stays `complete` («… с ошибками»), not «прерван». A systemic `partial` with `processed: 0` shows the interruption sentence and no fake groups. A `search_snippet` is never described as a read review.

**Owner.** Delivery belongs to the Predictions writer ([ADR 0107](../../adr/0107-get-head-read-side-effect-boundary.md), [AIR-416](https://trello.com/c/f7FX4Elk)); no read delivers anything.

- **At the event.** The start and the stop each try the journal three times. On failure the record stays `delivered: false`, the stop answers `eventPending: true`, and the record's key is noted in the outbox index `enrichment/event-outbox.json` (`{pending: {<key>: {since, attempts, lastAttemptAt, quarantined}}}`).
- **At the next authorized start** (`POST /api/enrichment/batch/start`, MCP `prediction_batch_start`), inside the writer lease and before the new run is admitted, `deliverPendingEvents` spends a budget of 20 entries a start, in a fixed order: first the two records of the latest run (so a process that ended between the record and the journal is covered without any note), then the pending index entries, oldest first. Quarantined entries are counted for the status and never take a slot, so any number of them cannot keep a later event from being delivered. An undelivered start event is written to the journal; an undelivered stop is completed through the same idempotent stop path the run took (run record, diagnostic row, journal item). A stop that a later run superseded is settled without a journal item. The start never fails or waits because of the outbox, and with nothing pending it writes nothing for it. It lists no prefix, so its cost does not grow with history.
- **Bounded retries.** A failed delivery stays in the index with one more attempt. After 8 attempts the entry is `quarantined`: it is not retried and not read again, its record is kept, and it is not published until a separate owner-approved replay.
- **Visibility.** `GET /api/enrichment/status` returns `eventOutbox: {pending, quarantined, oldestSince, maxAttempts}` from the index (a pure read), and every sweep that found work logs one `prediction_event_outbox` line with its counts.

**Limits.** An event appears without anyone opening the page, at the latest when the next run starts (the hourly Predictions Task). If no run starts, an undelivered event waits. A record that was left undelivered before this delivery existed, belongs to a run that is not the latest and is not in the index, is not found by the start; publishing it is a one-off owner-approved replay. A code rollback does not remove journal items, records or the index.

ADRs 0180 and 0190 stay the historical record of the decision to keep these Events.

**Automatic pagination.** Choosing a type (and opening `/events` with one) loads the following pages by itself, in cursor order and one request at a time, until 10 loaded events match or the cursor is exhausted. A page with no match neither stops the search nor needs a click, and events that are already loaded are reused, so nothing is read twice. While it searches the page says «Ищем более давние события…» with the number of matches found among the loaded events, and the matches found so far are listed. When 10 are loaded the search stops and older events continue to load by scrolling (below). «Все события» never searches: it shows the first page and then loads by scrolling.

The search stops at once, and its request is aborted, when the type or the screen changes. It stops on an API error (the reason is shown with «Повторить»; there is no automatic retry, and the retry resumes from the cursor that failed) and on a cursor that repeats or does not advance (a visible message and the same «Повторить»). An empty result is reported only when the whole archive has been read: «Во всём доступном архиве событий этого типа нет.» Before that, a type with no loaded match says «Среди загруженных событий этого типа пока нет.» A count is always a count of the loaded events, not a total. Events are keyed by `id`, so a page that repeats an event does not list it twice. Each page is a normal read of `GET /api/events`, which writes nothing and does not deliver or recover prediction events (see above).

**Scroll-driven pagination and the end of history (AIR-530).** There is no «Более давние события» button in the normal flow. A sentinel at the end of the list, inside the real scroll container `.activity-scroll` (the compact feed and the expanded `/events` screen use the same one), is watched by one `IntersectionObserver` with a bottom prefetch margin; only while it is in view is the next page requested, so nothing is fetched while the user does not scroll down (a list too short to fill its container keeps asking until it does). The observer is re-armed after every page, so a page with no visible change (for example no match of the selected type) asks for the next one while the sentinel stays in view. Requests are sequential: a request in flight (the scroll, the type search, a refresh of the first page) blocks every other one, the same cursor is never requested twice, and a cursor that repeats or does not advance stops the scroll with «Архив событий не продвигается дальше.» and the explicit «Повторить». A refresh of the first page keeps the paging cursor once older pages were loaded. While a page is loading the list shows «Загружаем более давние события…» (a `role="status"` line with a spinner that respects `prefers-reduced-motion`, and `aria-busy` on the scroll region). A failed page shows «Не удалось загрузить события.» and «Повторить»; nothing retries by itself, the scroll does not ask while the error stands, and the retry continues from the saved cursor. Event groups (`<details>`) keep their open or closed state and the viewed event keeps its position when a page is added. The scroll's prefetch is bounded: pages requested by the sentinel with no user scroll, wheel, touch or key in between (a list too short to fill its container, for example a type whose matches are rare) stop after three pages, the sentinel is released and the button «Более давние события» takes over; a real scroll renews the allowance, a click on the button loads one page and at most one more bounded batch, and a change of type or screen starts again. A background refresh of the first page never clears an older-page error: only the explicit «Повторить» does. Without `IntersectionObserver` the button «Более давние события» remains as the only way to the older pages.

The end marker «Это самое раннее доступное событие.» is shown only when the server returned no next cursor and at least one event is shown. It is never shown for an error, a stuck cursor, a search that has not finished, ten matches found with a cursor left, or an empty result of a type (that is «Во всём доступном архиве событий этого типа нет.»); an empty archive keeps «Здесь появятся события списка.». It is a client-side reading of the existing `GET /api/events` contract: the API, the event writer, storage and the event format are unchanged.

## Canonical Producer outcome report (`canonical_producer`)

Contract of [AIR-594](https://trello.com/c/iPaLDfzP) and [ADR 0208](../../adr/0208-producer-outcome-events-delivery-store.md) (Accepted, option B). The canonical Film/Person Producer ([driver](../data/producer-driver.md), [ADR 0141](../../adr/0141-producer-workflow-chain-protocol.md)) works in a chain of Workflow instances per published programme run `P`; each published generation `g` of that run is one logical pass with one run row `P:g`. The Events Log carries one report per **outcome**, never per instance, slice, heartbeat, handoff, takeover, relaunch, budget yield or idle hourly reconcile, and no hourly summary.

**Outcomes and identity.** Each outcome is one row of the D1 table `canonical_producer_outcome` (migration `0038`), inserted **last and asserted** (`changes()=1`) in the very batch that makes the outcome, after that batch's run and chain updates and their compare-and-swap assertions, so the row reads the state those updates just wrote. A missing or conflicting row fails the whole batch: a transition is never committed without its outcome.

| `outcome` | The batch that writes the row | `id` | `at` |
| --- | --- | --- | --- |
| `passed` | the pass completion (`commitPassComplete`, chain `complete` and run `passed` together) or the `already_complete` path (`completeChain`); the insert requires the passed run of that `P:g`, so a completion without one fails its batch | `canonical_producer-<P>-g<g>-passed`: one per `P:g` | the passed run's own `completed_at` on both paths (the chain closure is only the enqueue time) |
| `stopped` | every `stopChain` (Workflow and rebase stops) | `canonical_producer-<P>-e<e>-stopped`: one per owner epoch | the stop |
| `superseded` | the hourly reconcile's `supersedeChain` of a chain it read `pending`, `active` or `released`, guarded by that read's revision | `canonical_producer-<P>-e<e>-superseded` | the supersede |
| `held` | the hourly reconcile, in the tick where `recoverChain` or `reopenChain` answered `held` for a stop whose row says `eligible`, guarded by the chain's current epoch, state and revision | `canonical_producer-<P>-e<e>-held` | that tick |

`<P>` is a canonical UUID without dashes, or a bounded slug plus a hash of the exact id. A stop recovered by the hourly reconcile continues in a **new** epoch, so a later stop of that `P:g` is a new event and the later success is the `passed` event. A chain that already completed and is then superseded gets no second event; neither does an owner supersede through `producer_chain_operator`. (A stopped chain of an older run is not superseded at all today: a pre-existing CHECK of the chain table refuses it; a separate fix is proposed.) On the `already_complete` path, a run that passed before activation and whose chain closes after it is reported once, dated by the run's completion; a chain that closed before activation is never reported. An eligible stop whose chain a newer publication supersedes gets no further event: it is not resumed, and its card never said it would be. A stop that was never recorded (an instance that died and whose lease lapsed) is not an outcome: it shows as a takeover count. A stop before the run row of that `P:g` exists (for example an identity refusal while the plan is formed) keeps a row with **null** counters (a `LEFT JOIN`), never zeros.

**Fields.** `outcome`, `inputGeneration` (`g`), `programme` (8 characters of `<P>`, for operators; not rendered), `passNo`, `runRecorded` (`false` when no run row of this `P:g` existed in the batch), and from the run row as written in the batch: `unitCount`, `processed` = `applied` + `noop` + `kept` + `failed`, `applied`, `noop`, `kept`, `failed`, `remaining`, `openResults` (`open_at_completion`, `passed` only), `startedAt` (the run row's creation) and `durationMs`. `reason` is the stop code (`stopped`, `held`) or `newer_publication` (`superseded`); `recoveryClass` the chain's recovery class. `recovery` is `eligible` when, **at the stop**, the class and the counters allowed an automatic restart (`transient` or `receipt` within the attempt cap and the 24-hour streak window, or `authority`, and in every case an epoch left under the epoch cap), `owner` otherwise and on `held`, `none` on `superseded`: eligibility, never a promise. A `held` event follows only when the reconcile itself holds that stop; a stop whose programme a newer publication replaces is not retried and gets no further event. `priorState` says which in-flight state a superseded chain had. `chain` holds `epoch`, `handoffs`, `takeovers`, `relaunches`, `reopens`, `rebases` and `recoveryAttempts`.

**Run versus chain.** Unit counts belong to the **run** `P:g`: they add up over every pass of that run, so after a replay (pass 2 and later, a changed plan restarts the cursor and keeps the counters) `processed` can exceed `unitCount` and `remaining` is unknown. `remaining` is `0` only for `passed`; for a stop or a superseded pass it is `unitCount - processed` in pass 1 only. Chain counts belong to the **chain** of `P` and add up over its generations. Every number that is missing or not proven is `null`, never `0`. Units are plan units (Film facts, Person rows, credits, releases), not films.

**Delivery.** Only the hourly `reconcileProducerChain` delivers, after all its decisions of the tick: at most 8 pending rows that are due, ordered by `next_attempt_at`, then `at`, then id (indexed). Each row's event is built from its frozen columns and put **create-only** to `events/items/<reverse-timestamp>-<id>.json` (two tries; a put that finds the key counts as delivered), then the row is marked `delivered` by a compare-and-swap on `attempts`. A failed put adds one attempt and moves the row one hour back, so a failing row never starves the others; a pending row is never evicted or given up. A replayed drain or a lost response never writes a second item. R2 never blocks or fails the Producer, and nothing here runs inside a Workflow instance except the asserted insert, which is charged to the existing terminal-batch ceilings ([instance budget](../data/producer-driver.md#instance-budget-inside-the-workflow-chain-adr-0141-d5-air-572)). A tick that delivered or failed logs `canonical_producer_outcomes`; a `held` insert that failed logs `canonical_producer_held_failed`. `GET /api/events` returns the stored items and writes nothing.

**Retention.** Every row is kept **indefinitely**, pending and delivered alike: no TTL, pruning, delete or cleanup job (the migration refuses a delete and any change of the identity and payload columns; only the delivery columns move, one way). The row is the permanent delivery evidence and keeps the id for deduplication.

**Activation, schema and failures.** Each Workflow invocation and each reconcile tick probe the schema once (`schema_contract.version` and the table's presence). A **proven absent** schema (a real integer version below 38 and no outbox object) writes no outcome row: today's behaviour, before the migration is applied. An unreadable probe, a missing or non-integer contract version, or an inconsistent or malformed outbox (a version-38 schema without the whole table, index and triggers) never counts as absent: the Workflow then writes nothing and returns (the claimed lease lapses and the reconcile takes over), or stops the chain `producer_outcome_schema_invalid` (`fail_closed`) for an inconsistent schema; the reconcile supersedes no in-flight chain, records no `held` and drains nothing that tick. A failed outcome insert rolls its terminal batch back, and the Producer follows its existing fenced recovery. Outcomes made while the table is inactive (before the apply, by old instances still running while it is applied, after a code rollback) are never reported: there is no backfill, including P518 and every earlier outcome. Order: the code is deployed inert; applying `0038` is a separate owner GO; the next invocation and tick find the table and start writing. Events already in the journal are never rewritten, and a code rollback leaves them and every outcome row in place; older clients do not render the unknown type.

**Visibility.** The hourly Monitor stream `canonical_producer` carries the fact `outcomeDelivery` (`active`, `readable`, `pending`, `oldestPendingAt`). It is shown, never judged: a healthy Producer with undelivered reports stays healthy, and no alert or reminder comes from it ([monitor reference](../api/monitor.md#canonical-producer-stream)).

**Display.** The events screen and the compact feed draw one card: «Обогащение каталога завершено» (with «… с ошибками» when `failed` > 0 and «…, остались незакрытые результаты» when `openResults` > 0), «Обогащение каталога остановлено, допускает автоматический повтор» or «…, нужно решение владельца», «Автоматический повтор обогащения каталога не состоялся, нужно решение владельца» (`held`), «Обогащение каталога прервано: вышла новая программа». The numbers «Единиц в плане», «Обработано», «Применено», «Без изменений», «Оставлено как есть», «Ошибки», «Осталось» (and «Незакрытых результатов» for a pass) read «неизвестно» unless they are non-negative integers; notes give the programme generation and pass, the duration, «Счётчики включают более ранние проходы этого поколения» from pass 2, and «Проход остановился до записи прогона: числа неизвестны» without a run row. A closed group «Технические подробности» shows the stop code and class (lowercase codes only), the eligibility at the stop («…Это не обещание: если часовой запуск откажет в повторе этой программы, будет отдельное событие; программа, вытесненная новой публикацией, не повторяется и отдельного события не получает») or the owner decision, and the chain counts. No film, title, run id, key or fingerprint is shown.

## Catalog poster weekly report (`catalog_posters`)

The automatic weekly poster retry ([ADR 0179](../../adr/0179-weekly-automatic-catalog-poster-retry.md)) writes at most **two reports per logical week** (weeks start Sunday 00:00 UTC) into `events/items/`: a `deferred` report the first time a run carries over, and a `final` report when it completes or fails. A zero-result week writes only `final`. A deferred report is never terminal success. An idle daily firing writes no event.

**Identity.** `id` is `catalog_posters-<YYYY-MM-DD of the week start>-<deferred|final>`; the key is `events/items/<reverse-timestamp>-<id>.json` with the entry's frozen `at`. **Fields:** `type` `catalog_posters`, `outcome` (`deferred`, `completed`, `failed`), `final`, `weekStart`, `runId`, `scanned`, `due`, `checked`, `hydrated`, `noPoster`, `retryable`, `deferredBusy`, `pending`, `rateLimit`, `durationMs`, and `nextRetryAt` on a deferred report. The events screen shows a product-level card, a type filter and a detail view, not raw logs.

**Bounded outbox and idempotency.** The checkpoint `epg/catalog-poster-weekly.json` holds an `outbox` of at most 8 entries `{id, at, payload, deliveredAt|null}`. `at` and `payload` are frozen when the entry is created, in the same compare-and-swap that commits the run result, so a replay overwrites the same object. Order: (1) commit the result and append the entry; (2) put the event; (3) compare-and-swap `deliveredAt`. A lost put or a crash after the put leaves `deliveredAt` empty and the next firing replays it **without any TMDB request**. Entries are delivered oldest first and before the week rotates: the rotation keeps undelivered entries and drops delivered ones, so a deferred report that failed to deliver is never overwritten by the final one. A full outbox of undelivered entries creates no new report, or an undelivered entry older than 52 hours marks the stream `stalled` in the [Monitor](../api/monitor.md#catalog-poster-stream). A firing with an undelivered entry is not idle.

**Write budget.** A successful zero-due week is exactly two checkpoint writes and one event put. A week that carries over adds one more report with the same two writes and one put, plus one checkpoint write per executed batch or retry attempt (bounded by five batches a firing and a retry cap of six). `GET /api/events` writes nothing and delivers nothing.

## Accepted design (not implemented): Letterboxd Sync run Events ([ADR 0186](../../adr/0186-letterboxd-sync-and-independent-watchlist-authority.md), Accepted; not implemented)

Each scheduled Letterboxd Sync run would leave exactly two Events, including no-op, partial, error, skipped and interrupted runs: `type: ratings` and `type: watchlist`. Both come from a slot-owned outbox written by the batch that closes the slot (or by `ensure` for a missed slot), with a frozen time and payload, independent of whether a snapshot was promoted; delivery is create-only, retried without gating a scan, and the ids are slot-derived, `lbsync-<YYYYMMDDTHHMM>-ratings` and `lbsync-<YYYYMMDDTHHMM>-watchlist`, and `at` is the real end of that phase. The `watchlist` Event carries `outcome`, `snapshotVersion`, `lastSuccessAt`, the diff against the previous version (`added`, `removed`, `total`, `baseline`) and removed films with the ratings already stored; a removed film may carry `explainedBy` (`watched`, `rated`), which no writer reads. The `ratings` Event keeps its contract and gains `slot`. Reconciliation produces no Event and patches the removal Event of the run that observed the removal. A no-op has a neutral presentation. Events written by earlier code stay readable and are not rewritten.

## Prediction event outbox in D1 (ADR 0194; D1 authority since 24 Nov 2026)

Delivery of the batch_v2 terminal Event and of the neutral skipped Events to the journal is recorded in `prediction_event_outbox` since the marker `prediction_aux_authority` became `d1` on 24 Nov 2026 (R2 records and the index before that). Meaning is unchanged: one terminal Event per run; a skipped request is keyed by its request id with the first `at` and a deterministic journal key; delivery is at least once to the keyed journal and acknowledged only after the write is proven; drain is 20 records per authorized start, three journal attempts each, oldest first with the latest run's records first, quarantine at the 8th failed attempt. A settled record's payload is compacted 14 days after settlement and is never rebuilt or re-enqueued; its identity, original time and journal key stay. At most 256 skipped records may be active pending; a replay of an existing identity is always idempotent.
