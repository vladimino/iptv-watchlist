# Filter presets: R2 to D1 cutover

Procedure for moving the saved main-page filter presets from the R2 object `ui/filter-presets.json` to D1 (schema v28). **Every production step below needs its own operation-specific owner GO** ([authorization](../process/authorization-and-escalation.md), L2/L3). Deploying the code applies nothing, loads nothing and switches nothing; reading this page authorizes nothing. Contract and states: [programme filters](../reference/domain/programme-filters.md#saved-filter-presets-api-and-storage-contract), schema: [D1 schema](../reference/data/d1-schema.md#filter-presets-authority-schema-v28-repository-only), architecture: [persistence](../architecture/persistence-and-migration.md#filter-presets-authority-schema-v28-dormant).

## What is safe before any GO

The code is dormant. With the v28 tables absent **and `schema_contract` answering a version below 28**, or with the marker in `mode r2` and writes `open`, the route serves R2 exactly as before; the only added cost is a few small D1 reads per presets request. A D1 error on those reads, a missing `DB` binding, a database without `schema_contract`, or version 28 without the tables answers `503` for the presets routes only and never reaches R2 (the explicit local stand-in `FILTER_PRESETS_DB_OPTIONAL=standin` exists for tests and is never set in production). The route never reads or writes D1 preset rows while the marker is `r2`. Limit: a binding that points at a different database that is itself below version 28 is indistinguishable from the true pre-migration state; the cutover preflight therefore reads the database id.

## Preconditions (read-only, each recorded in the evidence)

1. The deployed Worker contains `src/filter-presets-d1.js` (the bundle names it `FilterPresetsD1`); `Deploy to Cloudflare` succeeded for the exact commit.
2. The Worker's `DB` binding resolves to D1 `iptv` (id as in `wrangler.jsonc`), and D1 `iptv` reports `schema_contract.version = 27` and none of the three `filter_preset*` tables; or, after step 1 below, version 28 with the marker `r2`, generation 0, writes `open`, and `SELECT COUNT(*) FROM filter_preset` equal to 0.
3. A fresh read of the R2 object (`ui/filter-presets.json`) through the approved read-only export ([R2 snapshot export](r2-snapshot-export.md)): save its content locally as `r2-export.json` and record its ETag and byte size. An absent object is a valid state only if the export procedure proves absence; an unreadable or partial object is a **blocker**, never a reason to import an empty set.
4. `node scripts/filter-presets-d1-sql.mjs digest r2-export.json` prints `{count, sha256}` and exits 0. Exit 2 is a blocker (the Worker itself could not read that document).

## Steps

Each numbered step is one GO. Apply SQL with the approved D1 execution path (`wrangler d1 execute iptv --remote --file ...`); every file is guarded so that a wrong state aborts it before it changes anything.

1. **Apply `migrations/0028_filter_preset_authority.sql`.** It refuses anything but a complete version 27. Readback: version 28; marker `r2`, generation 0, writes `open`; three tables; zero rows. The code and R2 continue to serve; nothing else changes.
2. **Hold presets writes.** `node scripts/filter-presets-d1-sql.mjs hold` prints one guarded update (`writes='held'` only from `r2`/`open`/generation 0). From now on every request that starts afterwards answers `503` ("temporarily read-only") on writes; reads still come from R2. The hold alone does **not** stop a write that was admitted earlier and is suspended, so it is not the fence. The fence is step 2b.
2b. **Fence the R2 object (one R2 write, inside the same GO).** Read `ui/filter-presets.json`, then write the identical content back with the condition `etagMatches` on the ETag just read (an absent object: create `{"schemaVersion":1,"presets":[]}` with `etagDoesNotMatch: "*"`). If the condition fails, an earlier writer landed: repeat the read and the fence write. The new ETag invalidates every in-flight writer that read the old one (their conditional PUT fails with `412`, nothing is lost). A writer that read R2 after this write must have started after the hold and re-reads the D1 marker right before its PUT, so it answers `503`. Together: after step 2b no R2 write can succeed until `release`. **Export the content of the fence write's result** as `r2-export.json` and record its new ETag; that, not the earlier read in precondition 3, is the source of the import. Run `release` and start over if the fence write cannot be completed.
3. **Import.** `node scripts/filter-presets-d1-sql.mjs import r2-export.json > import.sql` (from the export of step 2b), review it (one guarded update to generation 1, the fence, then one `INSERT` per preset in document order), apply it. The generator writes the presets as the Worker serves them (normalized), at most 30. The file is guarded: it changes nothing unless the marker is `r2`, writes `held`, generation 0 and the table is empty, so a repeat, a retry after a crash or a double apply is refused by its own guard and never duplicates a row. The marker stays `r2`: D1 does not serve yet.
4. **Parity readback (read-only).** Compare `SELECT id,position,name,query,created_at,updated_at FROM filter_preset ORDER BY position` with the export: same count, same order, same fields. Marker: `r2`, generation 1, writes `held`.
5. **Activate.** `node scripts/filter-presets-d1-sql.mjs activate r2-export.json > activate.sql`, apply it. The file has one short statement per preset that aborts the file when that row differs from the export (D1 refuses a statement over 100,000 bytes and 30 valid presets exceed that in one statement), then one short guarded update that switches `mode` to `d1` and `writes` to `open` only at generation 1 with the expected row count, then the fence. A mismatch stops the file before the switch. Readback: marker `d1`, generation 1, writes `open`; `GET /api/ui/filter-presets` through the Access-protected read (the [Access read skill](../../.claude/skills/cloudflare-access-read/SKILL.md)) returns the same presets and the ETag `"d1:1"`.
6. **Acceptance.** A client that held an R2 token gets `412` with the current document and refreshes; one create/rename/delete from the owner UI is confirmed in the rows and the revision rose by one per write. Record all readbacks in a dated evidence report. The R2 object is neither deleted nor changed by this procedure; decommissioning it is a separate GO.

## Recovery and rollback limits

- **Before step 5 (activation):** `node scripts/filter-presets-d1-sql.mjs release` restores writes (`open`) while the marker is `r2` (generation 0 or 1). R2 was never changed, so nothing is lost. Imported rows may stay (a later import is refused only if they differ) or be removed by the owner's explicit decision.
- **A failed or partial apply of step 3:** the fence stops the file before any row; a file that stopped after some rows leaves the marker at generation 1 with a partial table. Do not activate (the parity guard refuses it): compare with the export, and either complete the missing rows under a new GO or reset the table (marker back to generation 0, `DELETE FROM filter_preset`) under a new GO, then repeat step 3.
- **After activation:** D1 is the only authority and R2 is stale from that moment. A code revert does **not** move data and does not restore R2 as the authority; the route keeps reading the marker. Returning to R2 is a separate fenced, owner-approved procedure: hold writes, export the D1 document, write it to R2, set the marker back to `r2`. Presets written in D1 after activation exist only in D1 until then.
- **Never** copy the R2 object over D1 or D1 over R2 after activation without the hold, and never delete the marker or a table to "reset" a domain: with a table present and the marker unreadable the route answers `503` on purpose.
- Lost replies: step 3 and 5 are idempotent through their guards; read the marker and the row count before repeating anything. A D1 write whose reply was lost is reported as success only when the stored rows are exactly that request's document; otherwise the client gets `412` and refreshes.
- After activation, an R2 write cannot succeed: the marker is `d1` and the route never takes the R2 branch. A deployment with a missing or wrong D1 binding answers `503`; it does not serve the stale R2 object.

## Out of scope

Started marks, the Events journal and any other R2 object; those are separate domains with their own contracts and GOs.
