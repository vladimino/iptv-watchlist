# ADR 0019: Live D1 backfill reads a verified production R2 baseline and maps identities by rule

**Status:** Accepted (design decision only; it authorizes no production token, export, resource, write or Task change)  
**Original decision date:** 2026-10-26 (owner's explicit G0 decision recorded on the card)  
**Recorded at:** 2026-10-26  
**Approval source:** [AIR-74](https://trello.com/c/5AdAmKPe), owner decision comment of 26 October 2026 ("явное решение владельца по G0/ADR-0019, design approval, не production approval")  
**Related work:** [AIR-74](https://trello.com/c/5AdAmKPe), [AIR-73 offline parity](../evidence/d1-migration/air-73-offline-run.md), [AIR-74 readiness assessment](../evidence/d1-migration/air-74-backfill-readiness-2026-10-26.md)  
**Supersedes:** None (extends [ADR-0017](0017-staged-d1-migration.md) at its "separately approved live backfill" stage)  
**Superseded by:** None

## Context

[ADR-0017](0017-staged-d1-migration.md) stages the migration: offline parity, then a separately approved live backfill, then shadow writes and reads. The offline stage is complete and honest about its limits: against the 19 October 2026 archive the importer stored 18,412 receipts but reported 1,591 `reference_missing` conflicts, 45,586 unportable units and 2,533 unmapped objects, and `claimsFullParity` was false ([AIR-73 report](../evidence/d1-migration/air-73-offline-run.md)). Running that importer unchanged against production would reproduce those gaps, so it cannot satisfy the AIR-74 acceptance (a reconciled current baseline, idempotent reruns, recovery, manifest).

The repository today has no read path for a *current* production baseline. The only exporter (`migrationExportRoute` in `src/worker.js`, `scripts/migration-export.mjs`) is pinned to the legacy Site origin and refuses the Worker origin by design. Production R2 is written continuously by the two external Scheduled Tasks (hourly discovery and predictions, daily EPG publication), so an R2 listing is never an atomic snapshot. The D1 repositories (`src/canonical-repository.js`, `src/epg-repository.js`, `src/prediction-repository.js`) perform every write as a buffered, write-only transaction (the offline adapter rejects a read inside one), which is the shape a D1 batch can execute atomically. `wrangler.jsonc` carries only the R2 binding; the Worker must keep running on R2 throughout this stage.

## Decision

These are the boundaries of the first live backfill as the owner decided them on 26 October 2026. The decision is a design decision: nothing here authorizes a read of production R2, the creation of a token or a database, a write, a materialization or a Scheduled Task change; each of those is a separate, action-specific owner approval.

1. **Baseline source.** The backfill imports a verified baseline of the production bucket `iptv`, never the 19 October archive and never the legacy Site. The baseline is a local snapshot in the existing manifest shape (per-object key, size, ETag, raw-byte SHA-256, aggregate SHA-256, opening and closing listings), taken by a **local S3-compatible exporter with a tightly scoped read-only R2 API token**. No export route is opened on the production Worker and the Access configuration is not changed. The token is created under its own approval and lives outside the repository.
2. **Consistency proof while writers continue, or an explicit alternative gate.** R2 listings are paged and not atomic, so two equal listings alone do not prove that the downloaded bytes form one cut. The proof the exporter must produce is this, and an attempt that cannot produce it is discarded, not accepted:
   - *Per object:* every download is a conditional read of the exact listed version (ETag and R2 `version`, as the existing exporter already does with `head` before and after and `If-Match` on the GET), so each stored byte sequence is provably the listed version of its key, never a newer or partial one.
   - *Across objects:* every multi-object write in this Worker runs under a lease object (`epg/resolver-lease.json` for discovery and publication, `enrichment/writer-lease.json` and `enrichment/runner-lease.json` for predictions) or inside an EPG run recorded in `sync.json`; acquiring, renewing or releasing a lease rewrites its object and therefore its ETag. The cut is the closing listing. A **final fence** re-reads, after the closing listing has finished, the lease objects, the generation pointer, `sync.json`, the continuation record and `enrichment/profile/current.json`, and requires each to have the ETag the opening listing saw. Unchanged fence objects prove that no leased writer and no EPG run started between the opening listing and the fence, so the per-key cuts of the closing listing belong to one quiescent interval.
   - *Unleased writers:* the remaining writers are owner actions (profile publication, actual-ratings `PUT`, started markers, filter presets) and read-path recovery writes (`events/`, stop events, the view-index ratings seed). The owner refrains from the first group during the window and the fence covers the profile; the second group touches only R2-only keys. Each remaining key is still a single document read as one version.
   - *Deletions:* the Worker never deletes an R2 object (no `delete` call in `src/`), so a key `missing_after` or recreated with another ETag between the listings is an anomaly: the attempt stops and the owner is told, nothing is imported as "deleted".
   - *If the proof cannot be produced* (a fence object changed, or the listings never settle within the bounded rounds), the attempt is discarded. The only fallback the owner admits is a **short freeze of the Scheduled Tasks for the export window**, and only as a future fallback design when a consistent snapshot cannot be proven otherwise; it is a Task change that needs its own action-specific approval before anything is paused, and this ADR does not grant it. A verified snapshot without a freeze is preferred. No change log is invented: the proof is conditional object reads, fencing and a complete fresh inventory.
   The manifest records the **baseline identity** (published `programmeRunId`, `sync.json` `updatedAt`, continuation `at`/`hopId`, latest enrichment run id) to label the cut and to check that a later export moved forward; it is not a change log. A **delta** is a complete fresh inventory with its own proof, diffed against the baseline manifest by key and checksum: changed keys are re-downloaded and re-imported through the same receipts, new keys are imported, and keys absent from the new inventory are listed as anomalies for the owner, never deleted in D1. A key revised during an import run is caught by the next inventory and re-imported or stopped the same way.
3. **Identity reconciliation by rule, not by invention.** The enrichment spelling `tmdb_<n>` is the catalog form of the canonical Film id `film:tmdb:<n>` (the lifecycle reader emits it in `src/domain/film-person-reader.js`; `catalogId` in `src/domain/film-person-diagnostics.js` maps back). The importer resolves `enrichment/films/tmdb_<n>/…` to `film:tmdb:<n>`, a Letterboxd slug to `film:<slug>`, and a retired id to its survivor through the stored redirect, using one shared function. The receipt keeps the source key as written. A key that resolves to no stored Film stays a conflict: the importer never mints a Film from an enrichment key or a metadata record.
4. **The prediction family is mandatory, and immutable versions are its prerequisite.** A complete backfill includes the prediction family; excluding it is not an accepted design. `prediction_current.r2_key` and `prediction_history.r2_key` must name immutable objects; the mutable `predictions.json` bundle does not qualify. Two separate deliveries precede the prediction import: the Worker writes each new prediction version as its own immutable object alongside the bundle (a separate atomic card and PR with its own review), and the existing versions in production R2 are materialized once as new objects under a separate, explicit, action-specific owner approval (a production R2 write; never an overwrite of an existing key).
5. **Discovery evidence is derived by the resolver's own rule.** `epg/discovery-latest.json` items carry no `evidenceKey`; the resolver computes it from the observation's own fields (`candidateEvidence` in `src/discovery.js`) and stores it on decisions. The importer derives the key with that same shared function and marks it `derived` in the receipt. A decision whose stored key disagrees with the derived key is a conflict, not a repair.
6. **R2-only keys are declared, justified and dated, not unknown.** The owner accepted the principle that temporary runtime leases, diagnostics and event logs, caches and derived projections, and historical raw archives may stay R2-only, on the condition that **every concrete prefix** carries its own justification and a disposition plan toward [AIR-77](https://trello.com/c/f3QzcNYf), [AIR-78](https://trello.com/c/COdMTjqU) or [AIR-79](https://trello.com/c/485tlGLA): derived projections (view index, queue, mood facets, score preview) are recomputed from rows under ADR-0001 and need no import; runtime coordination state (leases, continuation record and diagnostics, `sync.json`, variant plans) belongs to the R2 writers until the write-authority cutover redesigns it; archive copies (raw XML, generation copies) are archive by ADR-0008. `events/` and `started/` are **not** excluded automatically: they need an explicit disposition (a D1 home or a recorded stays-in-R2 decision) before the read cutover. A key that matches no allowlisted prefix and no mapped family is an **unexpected key and fails closed**: the import stops and reports it. Coverage reports `r2_only` separately from `unmapped`; a full mapped-domain parity claim requires `unmapped` to be empty and every mapped family to read back equal, and prints the `r2_only` counts beside it. The prefix table with dispositions is in the [readiness assessment](../evidence/d1-migration/air-74-backfill-readiness-2026-10-26.md).
7. **D1 resource and executor.** The database is named **`iptv`**. It is created and the frozen `migrations/0001_schema_v1.sql` is applied by the owner under a separate approval. The backfill runs as a local command against that database through an adapter whose multi-statement batch is atomic; atomicity is demonstrated on a scratch database with a deliberately failing last statement before the first production write. `wrangler.jsonc` does not gain a D1 binding during AIR-74; the Worker neither reads nor writes D1 until [AIR-75](https://trello.com/c/AXPYIVCa).
8. **Bounded batches, receipts, fences, stop, and four acceptance classes.** Units are imported in bounded batches; each unit is receipted by source key and checksum after read-back; an interrupted run resumes from receipts; the second and third runs must apply zero rows; parity is read back against the baseline manifest, not against the import's own write list. The result is reported in three classes that are never merged into one verdict: **(A) mapped-domain parity**, every mapped family including predictions read back equal to the baseline, a blocker for AIR-74 Done; **(B) R2-only operational artifacts**, the dated allowlist of item 6, not a blocker for AIR-74, each prefix with its disposition; **(C) identity and source-quality exceptions**, source records the importer refuses to turn into rows because doing so would invent an identity (metadata-only films, slug-only fingerprints and ratings, a stored decision whose evidence key disagrees with the derived one). Class C records are **preserved as unresolved source records**: the R2 objects stay, every one is listed in the reconciliation ledger with its source key, checksum and reason, no Film id is minted for them, and they **gate the read cutover** ([AIR-77](https://trello.com/c/f3QzcNYf)) until a separate identity-resolution decision resolves or retires each one. AIR-74 Done requires the class C list to be complete and explained; the owner's acknowledgement of that list records a known gap and is never reported as lossless parity or a completed operational state. An authoritative family is never excluded to reach Done (item 4). Any conflict outside the acknowledged class C list stops the run.

Still open after this decision: the exact R2-only prefix list with its per-prefix dispositions (the principle is decided, each prefix is confirmed in the readiness report before the dry-run), the concrete class C list (produced by the dry-run and acknowledged before the production run), and whether the freeze fallback is ever needed (only if the proof fails, and then under its own approval). Those are GO/NO-GO items in the [readiness assessment](../evidence/d1-migration/air-74-backfill-readiness-2026-10-26.md).

## Alternatives considered

- **Import the 19 October archive into D1.** Rejected by the card itself: it is not current production, and it reproduces the known gaps.
- **Open the Worker's export route on the Worker origin behind Access with a service token.** Rejected by the owner: it deploys export code into the production Worker and changes Access; the scoped read-only token and a local exporter need neither.
- **Exclude the prediction family from the backfill.** Rejected by the owner: the family is authoritative and mandatory; the prerequisite deliveries (immutable version objects, approved materialization) come first.
- **Use the AIR-75 change journal as the consistency gate.** Not adopted: the only admitted fallback is a short, separately approved Task freeze; the proof itself is conditional reads, fencing and a full inventory.
- **Rewrite legacy ids inside the importer ad hoc.** Rejected: AIR-73 deliberately refused to rewrite ids; a mapping is acceptable only as one shared, tested rule that production code already embodies.
- **Point `prediction_current.r2_key` at the mutable bundle.** Rejected: it contradicts the schema contract and ADR-0001.
- **Pause the Scheduled Tasks for a clean freeze.** Not proposed: a Task change is a separate owner-approved operation, and bracketing listings plus a delta replay achieve a verifiable baseline without it.
- **Run the backfill from inside the Worker.** Not proposed: it would put D1 writes into the production code path before shadow writes are designed ([AIR-75](https://trello.com/c/AXPYIVCa)).

## Consequences

The backfill becomes verifiable and repeatable: every row traces to a source key and checksum, every mapped key traces to a receipt, a ledger entry or an allowlisted `r2_only` prefix, an unexpected key stops the run, and a rerun is provably empty. The costs are new code (a local S3-API exporter with the consistency proof, the shared identity and evidence rules, the prefix allowlist, a D1 adapter and a backfill command), a Worker change plus an approved materialization for immutable prediction versions before the prediction family can be imported, and an owner-run resource setup. The archive importer's reports remain valid history; the new rules make earlier conflict counts shrink by rule, which the readiness report records rather than hides.

## Recovery and migration boundary

R2 is not written by the backfill: the credentials are read-only by scope, and the Worker is untouched. D1 is not read by the runtime during this stage, which bounds the blast radius of a bad import to the database itself; it does not make dropping the database an automatic or sufficient rollback. Rolling back a populated production D1 is an owner-approved procedure: an export or point-in-time backup of the database first, a target-identity fence (the database identifier recorded in the manifest and in every receipt must match the one being dropped), then the drop and a fresh import from the same verified baseline. Receipts make a partial run resumable without a drop. A later delta import replaces nothing without a changed checksum and deletes nothing. This ADR never authorizes creating a token, a database, a binding, writing a row or dropping a database; each of those is an explicit owner approval recorded on [AIR-74](https://trello.com/c/5AdAmKPe).
