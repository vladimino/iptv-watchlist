# Continuous prediction runner v5

The same start/next/submit/complete protocol serves manual and scheduled triggers. Read GET /api/enrichment/runner before every launch. Its contract supersedes the obsolete v3 single-batch/deadline instructions. ChatGPT reaches this protocol through the MCP tools in [docs/mcp.md](mcp.md): `enrichment_runner`, `prediction_start`, `prediction_next`, `prediction_submit`, `prediction_heartbeat`, and `prediction_complete`. Those tools fix the scope to `watchlist_all`, the mode to `queued`, and each next/submit step to one film. The HTTP routes remain the contract. The external ChatGPT Scheduled Task is managed independently of deploying this Worker contract; always verify its live state and do not change it without owner approval.

1. POST start with scope watchlist_all, mode queued and trigger scheduled/manual. Supply real known capacity only. Do not impose a total-film or time cap.
2. already_running is a successful no-op: never adopt another trigger's runId. busy is transient contention; retry with bounded backoff, without starting concurrent generation.
3. Read next, generate only requested work using the unchanged schema/profile/scoring rules, and submit each film immediately. Repeat next/submit across batches continuously.
4. Before model calls renew POST heartbeat; renew concurrently every 10 minutes if an individual call can last that long. Checkpoints also renew automatically. A 15-minute lease stores owner/runId, heartbeatAt and expiresAt. Until the schema v7 marker is `d1`, the compare-and-swap is the object etag. In that mode it is the D1 row token. Expired owners cannot submit. Crash checkpoints survive takeover. Migration `0007` is applied with marker `d1`, so the live lease is the D1 row token.
5. next re-evaluates hot urgency before every selection. Cold may run only while hot has no outstanding work. Model call batching remains disabled. Valid fingerprints/predictions are reused; timeslot changes never invalidate them.
6. Before submit, call `prediction_validate` with the complete generated fingerprint and prediction (no storage, not a submit; submit only when its `success` and `valid` are both true, otherwise fix the listed `issues`) or check them against `contract` from GET /api/enrichment/schema (`enrichment_schema`): every required `execution` dimension present, every enum value from its list, `moodLabels` 2–4 labels. Fix every reported issue first. An isolated malformed/invalid film output is reported through submit items[].failure.kind (parse_error or validation_error), is persisted as a retryable item failure and must not end the run. A Worker schema rejection is the same retryable item failure and additionally returns `results[].validation` with `stage` and `issues[{path, code}]` naming the field (for example `fingerprint.execution.payoff invalid_enum`, `fingerprint.moodLabels required`); fix that field for the following films and do not resubmit the deferred one in the same run. See [the submit validation contract](enrichment.md#submit-validation-contract). Failed items are skipped within that run and deferred by a 1-hour exponential retry (maximum 6 hours). Five consecutive distinct format failures trigger format_error_storm. mustComplete means call complete with stopReason. At actual quota/model/API/storage error, complete with a short safe reason and retain all saved predictions. No credentials in outputs, URLs, Events or persisted error reasons. A killed process recovers through lease expiry.
7. Progress Events aggregate the run every 50 successful predictions or 30 minutes, whichever comes first; the final event is separate. Check heartbeat/next/submit to emit time-based progress during active work. Successful empty checks don't spam Events. Eligible queue exhaustion with deferred item retries is a normal completion, not a run interruption.
8. A formed response does not prove the client received it. Send or read `X-Request-Id`; the same id is returned as `requestId`. On an external or systemic stop, `complete` may include `fault` (`origin`, `failedStep`, `providerErrorCode`, `httpStatus`, `receivedRequestId`). Omit `fault` when the cause is unknown. A fault on `queue_empty` or another normal completion is rejected. `receivedRequestId` acknowledges only the matching step. `firstNextAt` is not a successful `next`. See [run diagnostics](run-diagnostics.md).

## Run completion, drained queue, eligible and deferred work

Four observations are kept apart. **Run completion** is `status: complete` (or `partial` when a stop reason or a still-pending selected film remains); a run that ends with item failures deferred to a retry is `complete` with `failed > 0`, not an error. **Drained** means the refreshed queue has no outstanding film: `complete` stores `stopReason: queue_empty` only when `hotRemaining + coldRemaining` is zero after its final queue refresh, whatever reason the caller sent. **Eligible** is the subset of outstanding films the runner would take now (`queueReadyIds`: the hot lane while any hot film is outstanding, otherwise the cold lane, minus films whose stored `retryAt` is in the future); when work remains but none of it is eligible, `complete` stores `eligible_queue_empty`, and `next` answers the same with `mustComplete: true`. **Deferred** films are the outstanding films held back by a retry timestamp; `start` on a queue that is outstanding but not eligible answers `retry_backoff` instead of opening a run. The completion Event and the footer status publish these counts as `snapshot.queue` / `predictions` (`outstanding`, `eligibleNow`, `deferredByRetry`, `nextRetryAt`, see [the footer and Event slices](enrichment.md#failure-behavior)); the retry time of a film is not the time of the next scheduled run. None of this changes the retry policy, the delay, the batch size or which films are selected.

## Queue writes

`enrichment/prediction-queue.json` has several writers ([ADR 0064](../../adr/0064-prediction-queue-conditional-writes.md), Accepted 2026-10-31):

- the runner routes (`start`, `next`, `submit`, `complete`);
- the EPG commit tail (`programme_updated`) and the EPG scan (`epg_scan`);
- the profile publication (`profile_updated`);
- the resolver checkpoint (`resolver_checkpoint`);
- `POST /api/enrichment/queue/reconcile` (`manual_reconcile`).

Every write is conditional. Until the schema v7 marker is `d1`, the condition is the etag of the object the writer read (`etagMatches`, or `etagDoesNotMatch: '*'` when absent). When that marker is `d1`, the condition is the D1 generation read with the document, and the object is written afterwards as a mirror. On schema version 7 or newer while this domain is installed and the marker is still `r2`, the writer advances `generation` and records an intent, including the hash of the bytes it is about to put, before the object put. It deletes that intent only after the put returns. A put that throws leaves the intent. A queue or lease write reads the marker again immediately before the put. A head captured while these tables were absent does not put once the marker is `d1`. A load, activation or release that still sees the intent does not copy, flip or reopen writers. A later contract with none of the prediction tables stays on the objects. A partial set of those tables fails the write and does not use the object. With `PREDICTION_DB_REQUIRED=on`, a missing `DB` binding or a bound database without `schema_contract` fails closed. Migration `0007` is applied; it does not lower a higher contract version. The retry, the five attempts and `prediction_queue_conflict` are the same in both modes ([ADR 0078](../../adr/0078-d1-authoritative-prediction-domain.md)).

- **A runner step advances the stored queue; it does not rebuild it** ([ADR 0113](../../adr/0113-prediction-runner-advances-persisted-queue.md)). `next`, `submit` and `complete` read the stored queue and use it as it is while it passes the advance gate: valid shape, the programme the caller reads, the same profile hash and version, fingerprint schema, fingerprint and prediction prompt versions and fingerprint registry digest. A queue that fails the gate is rebuilt. `submit` removes the films it wrote (`created`, `recalculated`, `already_current`) from the queue's lists, `priority`, `work` and `retries` and recomputes the counters (`priorityCount`, `coldRemaining`, `urgentCount`, `coldWithoutPrediction`, `hotPredicted`) in one conditional write (`trigger: batch_progress`, `advancedAt`); a replayed submit settles nothing twice. The metadata of a new batch is read by id (watchlist programme, then `readAdmissionsById`: indexed `film_id` lookups in chunks of 80, current rows only, no generation compare), never from the whole catalog; a listed film whose admission is gone is settled out of the queue and replaced (in `start` as well as `next`; with nothing left `start` answers `noop`). Every settlement repeats the advance gate on the queue the conditional write mutates, so a queue rebuilt for another generation after the step's read is not changed by it; a `start`/`next` selection that cannot settle missing admissions answers `503 {status: "blocked", reason: "queue_changed", code: "prediction_queue_changed"}`. A `submit` whose prediction already committed still returns its per-film result, even if its queue settlement lost the race; a later refresh reconciles the queue. `complete` preserves the newer queue's `lastBatch` and counters and adds only the run's own retries. `compatibility`, `fingerprintCompatibility` and `discovery` are statistics of the last rebuild until the next one. A film admitted mid-run reaches the queue through the named refresh (EPG tail, resolver checkpoint, profile update, reconcile), and a normal `queue_empty` means empty as of the last rebuild.
- **A rebuild** (`refreshPredictionQueue`, its `trigger` stored on the queue) reads the queue first and its inputs after it. When the stored queue names another programme generation than the caller's programme, the rebuild uses the published programme. `retries` of films still outstanding, `lastBatch`, `lastCheckAt` and `metrics` come from the queue just read.
- **The stored form** is plain JSON while it fits 900000 characters and the `dict1` encoding above that ([schema](../data/d1-schema.md#prediction-domain-schema-v7)). Readers always receive the plain document. A refusal carries `code: prediction_domain_budget` and a `guard` naming the limit that refused (`queue_chars`, `overlay_rows`, `statement_bytes`, `bind_limit`, `history_limit`, `mirror_list`); on the EPG commit it appears as `enrichmentQueueError: prediction_domain_budget:<guard>`. The encoded text starts with `dict1:`, so a Worker build without `dict1` support fails closed with `prediction_domain_unavailable` on that queue and cannot rebuild it: only a build that supports `dict1` can rewrite the queue as plain.
- **The view-index overlay** (`PredictionD1.overlayIndex`) reads `prediction_fingerprint` and `prediction_pointer` in keyset pages of 300 rows ordered by `film_id` and applies the rows of films that are in the view index. Its cost follows the number of D1 rows, not the number of view-index keys; a table above 20000 rows is refused with `guard: overlay_rows` and nothing is returned. The result for a given index and set of rows is the one the per-film reading gave.
- **One start reads each large input once.** The queue rebuild of a start hands its programme, catalog, view index and profile to the batch selection and to the start event, so the catalog and the index are not read again in the same request. The start answer is a few kilobytes: the run summary, counters and the runner contract, never the queue, the index or film metadata.
- **Discovery chunks do not reach the runner.** A fenced catalog read (`discovery_fence`: the Discovery generation moved between its statements) is repeated up to three times inside a rebuild; `next`, `submit` and `complete` do not read the catalog at all while the stored queue passes the gate, so a Discovery chunk cannot fail them. `start` always rebuilds; if the catalog is held or all three reads are fenced and the stored queue still passes the gate and is not older than 12 hours, the run starts on it and the answer carries `queueStale {reason, ageMs}`. An Event snapshot whose programme, catalog or view index cannot be read has `snapshot.coverage: null` and `delta.predictionGain: null`; it never computes coverage from a missing catalog. `enrichment/status` reads no catalog (`selectedCount` is `hotCount + coldCount` of the queue, or the watchlist count without a queue) and reports `discoveryStatus: "unavailable"` with `discovery: null` when the Discovery status record cannot be read.
- **A catalog held by an EPG publication.** While the Discovery authority is held or loading (an EPG seal), the catalog cannot be read and a rebuild cannot run. `start` checks the authority before it takes the runner lease and answers `503 {status: "blocked", reason: "catalog_held", code: "prediction_catalog_held", cause}` with `cause` `discovery_fence` or `discovery_incomplete`. A rebuild that meets the same refusal after the lease was taken releases the lease and gives the same answer. `next`, `submit` and `complete` of an owned run answer the same 503 only when a step that really needs the catalog (a rebuild after a programme, profile or contract change, or the by-id read of a new batch) is refused with those codes: they keep the runner lease, do not stop the run, and include `leaseTtlMs` (15 minutes). A later identical `submit` of a film already written in that request is `already_current` (no second version or history row); the 503 body carries `results`, `committed` and `identicalSubmit: "idempotent"`. `complete` does not persist a completed run or Event while the catalog is held. A `discovery_fence` outside `queue_refresh` stays `502 storage_error`. The caller retries the same step with the same `runId` at most for one lease TTL, with heartbeat; if still held, it leaves the run for ordinary lease expiry and does not `prediction_complete`. The live ChatGPT Task prompt does not yet name this wait (see [AIR-424 evidence](../../evidence/prediction/air-424-next-discovery-fence-2026-11-10.md)); this page does not edit that prompt.
- **A failed boundary** (`start`, `next`, `submit`, `heartbeat`, `complete`) still answers `502 storage_error`. The Worker also writes one log line `{"event":"prediction_boundary_failed","boundary","stage","code","guard","kind","requestId","runId"}`. `stage` is the first named step the error crossed (`settle_previous`, `runner_lease`, `writer_lease`, `queue_refresh`, `film_state`, `run_save`, `runner_started`); on `next`/`submit`/`complete` a catalog hold is `queue_refresh`. `code` and `guard` are the error's own and are reported only when they are plain identifiers, otherwise `unknown`. The line carries no message, stack, film id or body.
- **A recorded change** is the submit's per-film retry, the start's idle check (`lastBatch` with `runId: null`) or a stopped run's missing retries. It is applied to the queue just read and never creates an absent queue.
- **The completion** writes its retries, `lastBatch`, `lastCheckAt` and `metrics.hotProcessedTotal` inside its own `batch_complete` write (a mutation of the stored queue, which also settles every successful film of the run once more). The counter moves only when `lastBatch.runId` is not yet the run, so a repeated completion counts once.
- **A retry record only grows while its film is outstanding.**
  - `attempts` is the larger of the run's count and the stored count plus one.
  - `retryAt` is the latest of the run's time, the stored time and the backoff of that count.
  - A record whose `lastRunId` is the run is written once.
  - The completion and every stop add any failure of the run that the submit did not land (below).

  The submit answer and the run record follow a merged record that came out larger.
- **On conflict** the writer re-reads and starts again, at most 5 attempts with a short jittered pause. Exhaustion throws `PredictionQueueConflictError` (`code: prediction_queue_conflict`), and nothing of the caller's is written.
  - The reconcile route answers `409 {error, code: "prediction_queue_conflict"}`.
  - A runner route ends through its ordinary error path as a `storage_error` stop.
  - The EPG commit tail records `enrichmentQueueError` and completes the commit.
  - The resolver records `prediction_queue_checkpoint: …` in its status.
  - The profile publication stands; the next rebuild picks the new profile up.
- **A put that throws** is an unknown outcome. It is not repeated, and the error propagates. A lease holder's `beforeWrite` renews before every attempt, so a lost lease writes nothing.

**A run's retries survive a queue write that fails.** A queued run's per-film failure is saved on the run record, with `retryHeal: "pending"`, before the submit writes it to the queue. The mark is cleared only by a queue write that confirms every failure of the run.

- **At the stop.** Every stop writes the run's missing retries again before it marks the run `partial` and releases the lease. This covers a `storage_error` stop after a submit conflict and a `complete` with a systemic reason. A normal completion writes them in its `batch_complete` rebuild. A write that still fails keeps the mark. The stop answer then carries `retryHeal: "pending"`.
- **At the next start.** A released or expired runner lease keeps naming its last run. Before acquiring the lease, `start` reads that run. If the run is still marked, `start` writes its retries to the queue first, in a recorded change with trigger `start_retries`. When that write fails, `start` selects nothing, takes no lease and answers `503 {status: "blocked", reason: "retry_heal_pending", code: "prediction_retry_heal_pending", pendingRunId}`. This is a start outcome, not a stop, because no run exists to stop. No run record, stop record or Event is written, and `latest-run.json` keeps naming the marked run. Only the start's own diagnostic row records `blocked`. The lease keeps naming the marked run, so every later start tries again.
- **Unknown outcome.** A write with an unknown outcome is not repeated blindly. The next attempt re-reads the queue, and a record that already carries the run's `lastRunId` is left as it is.
- **No queue object.** If the queue object is absent, the retries cannot be confirmed, and the mark stays until a rebuild creates the queue.

The queue format, the retry policy, hot-first selection and batch sizing do not change. Tests: `node tests/prediction-queue-cas.mjs`.

Run counters and film outcomes persist after each submission. Current-batch film reads stay bounded; completed batches are counted from saved outcomes rather than loading every completed film on every next request.

Which films are outstanding after a taste-profile change is decided by the queue rule in [prediction compatibility](../domain/prediction-compatibility.md#prediction-queue): the selective profile rule, with no switch ([ADR 0044](../../adr/0044-retire-profile-compatibility-switch.md)). The runner's own checks (pending count, completion, `already_current`) use the same rule, so a kept prediction is never recalculated.

Tests: node tests/continuous-drain.mjs; node tests/queue-compatibility.mjs; node tests/fingerprint-migration-queue.mjs; node tests/throughput.mjs; node tests/enrichment.mjs. The multi-batch integration test uses an isolated R2 implementation and deterministic validated model outputs; it is not a production LLM throughput benchmark.


## Step timing line (AIR-438)

Every `next` and `submit` writes one log line `{"event":"prediction_step_timing", ...}` after it answers; `start`, `heartbeat` and `complete` do not. It is observation only: the Worker's environment is replaced for the length of the step by a copy whose R2 bucket and D1 database time each call and forward it unchanged, so no call is added, reordered, retried or awaited differently and the answer, the leases and the compare-and-swap writes are those of an uninstrumented step ([evidence](../../evidence/prediction/air-438-step-latency-and-batch-sizing-2026-11-11.md)). A failure of the timing code is swallowed and never changes the outcome.

| Field | Meaning |
| --- | --- |
| `step`, `requestId`, `runId`, `status` | The step (`next` or `submit`), the request id the answer carries, the run id (`null` when not a safe token) and the HTTP status (`0` when the step threw) |
| `wallMs` | The step's wall time as the Worker sees it, including the lease, the diagnostics appends and the answer |
| `busyMs` | The **union** of the intervals of every R2 and D1 call: calls that run in parallel are counted once |
| `overlapMs` | By how much the sum of the calls' times exceeds `busyMs` (parallelism) |
| `unattributedMs` | `wallMs` minus `busyMs`: the awaits and scheduling between calls, and any compute the clock sees. The Workers clock may advance only across I/O, so synchronous compute can read as close to zero. Always reported, never folded into a stage |
| `r2` | `n` operations (a `get` that reads its body counts twice: the answer, then the `body`), summed `ms`, `busyMs`, `bytesIn` (approximate for a string: characters) and `bytesOut` (object size at a body read) |
| `d1` | `n`, `ms`, `busyMs`, `statements`, `batches`, `rowsRead`, `rowsWritten` (from the answers' own metadata, never a new read) |
| `classes` | Per class `{n, ms, maxMs, bytes, ops}`. R2 classes: `r2:run`, `r2:run_latest`, `r2:profile`, `r2:lease`, `r2:film_state`, `r2:film_other`, `r2:source`, `r2:view_index`, `r2:queue`, `r2:programme`, `r2:diagnostics`, `r2:list`, `r2:other`. D1 classes: `d1:<table>` from the table name in the statement's static SQL text (up to 60 characters of `[a-z0-9_]`), `d1:batch` for a batch, `d1:other`. At most 40 classes |
| `notes` | Whitelisted counters: `items`, `selected`, `pending`, `batchSize` (`next`); `bodyItems`, `predictionOnly`, `fingerprintAndPrediction`, `created`, `recalculated`, `alreadyCurrent`, `failures` (`submit`) |
| `truncated` | Present and `true` when the interval list (4,000) or the class list overflowed; the totals stay exact |

The line never holds a film id, a key, a statement, a body, a fingerprint, a prediction or a model output. An R2 class is a name from a closed vocabulary; a D1 class is a table identifier, never a value. Percentiles are not computed in the Worker; they are read from the logs ([runbook](../../runbooks/prediction-operations.md#reading-the-step-timing-line-air-438)).

**Batch sizes the contract has.** The selection batch of a run is `min(adaptive plan, body.batchSize)` with the plan capped at 12 while `capacity.remainingPercent` is unknown and at 20 (`MAX_PREDICTION_BATCH`); `start` refuses more than 20. HTTP `next` accepts `batchSize` 1 to 20 and HTTP `submit` 1 to 10 items. The MCP tools send `batchSize: 1` for `prediction_next` and accept exactly one item in `prediction_submit`, and `enrichment_runner` publishes `modelBatching.enabled: false` with one ready fingerprint per call. Each `next` reads the stored fingerprint and prediction of every film in the run's selection, so its cost grows with the selection batch; its calls do not grow with the number of items it returns.

## Stored prediction record and its lineage

A committed prediction (`enrichment/films/<id>/predictions.json` `current`, the same record in `history` with `replacedAt` once replaced) holds the model's fields as submitted (`predictedRating`, `probability4Plus`, `confidence`, `matchSignals`, `mainRisk`, `moodLabels`) and the Worker's: `filmId`, `generatedAt`, `tasteProfileVersion`, `tasteProfileHash`, `fingerprintHash`, `fingerprintSchemaVersion`, `fingerprintPromptVersion`, `predictionPromptVersion`, `runId`, `trigger` (`scheduled` or `manual`) of the run that produced it, and, on a snapshot written by this submit path, `confidenceAssessment`. The bundle keeps every replaced record; a recalculation never removes one. `fingerprintPromptVersion`, `runId` and `trigger` exist only on records committed since they were added ([ADR 0038](../../adr/0038-durable-rating-and-prediction-lineage.md)); an older record without them has an unknown prompt version and run, and no reader may fill them from the current state. Why a record was replaced is derived from the two records (a different profile, fingerprint or prompt version), not stored. One film's records and rating events are read through [the film history API](film-history.md).

`confidence` on that record is the model's `low` / `medium` / `high`. It is not an evidence score. Submit replaces any caller `confidenceAssessment` with the result of [prediction confidence](../domain/prediction-confidence.md) for the fingerprint being stored, and leaves `confidence` as submitted. The immutable version body includes that object because the body is the snapshot minus `r2Key`, `contentSha256` and `replacedAt`. A record written before this path has no `confidenceAssessment` key; a reader does not add one. The hourly task still must not call the assessor or send the field ([active task contract](../scheduled-tasks.md#fingerprint-evidence-instruction-in-the-live-hourly-task-air-335-2026-11-03)). Prompt versions stay 1. Deploying this Worker is what starts writing the field on the next natural submit. Accepting one such production snapshot is a separate check and is not claimed here.

## Immutable prediction version objects

Each committed prediction is also written once as its own object; the writer has no switch ([ADR 0045](../../adr/0045-retire-prediction-version-objects-switch.md), [feature flag register](../feature-flags.md)). A submit that creates or recalculates a prediction first writes `enrichment/films/<id>/predictions/versions/<sha256>.json`, where `<id>` is the stored film id as used in the bundle key and `<sha256>` is the SHA-256 of the object's exact bytes: the prediction record with its keys sorted recursively, without the pointer fields and without the history-only `replacedAt`. The write is conditional on the key being absent. If the key exists, its bytes are read back and must equal the bytes about to be written; a retry of the same record is therefore idempotent and a differing object is a storage conflict that fails the item and leaves the bundle unchanged. Only then is `predictions.json` rewritten with `current` carrying `r2Key` and `contentSha256`; a replaced record moves into `history` with its own pointer intact. A crash between the two writes leaves an unreferenced version object and an unchanged bundle, never a bundle pointer at a missing object. The view index receives the same record as the bundle.

Freshness is still decided by profile version and hash, fingerprint hash and schema version, and prompt version. Until the schema v7 marker is `d1`, readers use the objects. In that mode they use the D1 pointers and verify the immutable body; a missing or mismatched body fails the read, and the mirror is not a fallback. The view index prediction and fingerprint fields are replaced from those pointers on read. Migration `0007` is applied and the marker is `d1`. Records written before the pointer rule carry no pointer and stay valid for the runtime. The shared rules (`src/domain/prediction-versions.js`) are the only definition of the body, the key and what counts as a linked pointer; the offline importer loads them from that source. Records without a pointer were linked once by the historical materialization ([ADR-0026](../../adr/0026-historical-prediction-version-materialization.md), [runbook](../../runbooks/prediction-versions.md)); its route is retired ([ADR 0050](../../adr/0050-retire-prediction-materialization-route.md)), and `scripts/prediction-versions-plan.mjs` remains the read-only check of a snapshot.

## Immutable fingerprint objects

A fingerprint has the same shape of storage ([fingerprint compatibility, Storage](../domain/fingerprint-compatibility.md#storage)), with no switch ([ADR 0046](../../adr/0046-retire-fingerprint-version-objects-switch.md)): a submit that accepts a fingerprint writes its content body (`enrichment/films/<id>/fingerprints/<fingerprintHash>.json`) and its generation record (`fingerprint-generations/<fingerprintHash>-s<schema>-p<prompt>.json`) create-only, then moves `fingerprint.json`; a body whose key already holds different bytes, or a record key holding anything but a valid record of the same identity with a stored body, is a storage conflict and the film fails with `storage_error` before the pointer or the index move. Optional `evidence` on a new body is hashed with that content and is not written into the D1 `features_json` index ([submit validation](enrichment.md#optional-fingerprint-evidence)). A body that omits it stays legacy. `fingerprintSchemaVersion` remains part of the hash; `fingerprintPromptVersion` does not. This page does not bump either version. The pointer carries `fingerprintPromptVersion` (the Worker's `FINGERPRINT_PROMPT_VERSION`), `produced` and `previous`, and the new prediction carries the fingerprint's own `fingerprintSchemaVersion`. Readers are unchanged. A run is bound to the fingerprint schema, the fingerprint prompt, the prediction prompt and the transition registry it started with, next to the profile hash: `next`, `submit` and a `complete` without a reason answer `409 {code: "contract_changed"}` after a deploy that changed any of them, and the caller starts a new run. `next` reports the three versions with the profile. Which films are outstanding after a fingerprint schema or prompt change, how migration work is bounded within a batch, and when `next` restores a rolled-back fingerprint from a stored record, are in [fingerprint compatibility](../domain/fingerprint-compatibility.md#queue-and-runner).

### Retired materialization route

`POST /api/enrichment/predictions/materialize` is retired ([ADR 0050](../../adr/0050-retire-prediction-materialization-route.md)). Any method and body answers `410 Gone` with `{error: "gone", detail}` before the body is read; nothing is read, written or locked, and no value of the former `PREDICTION_MATERIALIZATION` binding reopens it. The historical run it served is complete and reconciled ([runbook](../../runbooks/prediction-versions.md#2-historical-materialization-completed-the-route-is-retired)); its receipts under `enrichment/predictions-materialization/` stay in R2.

## Operator procedure

External ChatGPT Tasks, schedule timing and troubleshooting are documented in [prediction operations](../../runbooks/prediction-operations.md); this page defines the runner protocol, idempotency and queue semantics. A caller must not infer task execution from code deployment.
