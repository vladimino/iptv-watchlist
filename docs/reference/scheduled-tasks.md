# Production ChatGPT Scheduled Tasks — operational contract

This is the maintained **expected behavior** of the two production ChatGPT Scheduled Tasks for IPTV Watchlist. The authoritative status, schedule, timezone and executable prompt are in the **live ChatGPT Scheduled Tasks registry**, outside GitHub. GitHub Actions deployment does not run, edit or enable these tasks. An enabled task is not proof of successful execution. For runner and MCP details see [prediction runner](api/prediction-runner.md), [MCP tools](api/mcp.md), [prediction operations](../runbooks/prediction-operations.md) and [scheduling architecture](../architecture/scheduling-and-orchestration.md).

## Daily programme update

- **Task:** `Обновление программы «В эфире»`. **Expected:** enabled; daily at **17:00 Europe/Madrid** (local civil time; daylight saving changes apply); `default_timezone: Europe/Madrid`.
- **Authority:** connected owner-only IPTV Watchlist MCP to Cloudflare Worker `iptv`, authoritative R2 `iptv`. Never use legacy Sites, direct HTTP, Cloudflare Cron, a browser or local CSV as a production substitute.
- **Preflight:** `probe_read`, `epg_status`, `epg_pipeline_status`; stop safely if unavailable, unauthorized or inconsistent.
- **Execution:** exactly one `epg_sync_start({})` for this invocation, using only its returned `runId`; sequential `epg_sync_step({runId})` through metadata and programme publication; stop on ownership/lease conflicts, terminal errors or unsafe retries. Do not adopt another run.
- **After programme publication:** follow `discovery.nextAction`: `continue` means one further explicit `epg_sync_step` (at most one discovery chunk per call), `wait` means honor `nextCatchUpAt`/backoff, `stop` ends that sequence. Persisted outstanding chunks may be continued by the hourly task. EPG completion does not imply discovery completion.
- **Completion:** read `epg_status`, `epg_pipeline_status` and `enrichment_queue`; distinguish published programme, pending discovery and `ratingsPending`. Ratings/Letterboxd HTTP 403 are not reasons to restart EPG. Do **not** run predictions or modify the Taste Profile in this task.

## Hourly discovery catch-up and predictions

- **Task:** `Почасовые прогнозы «В эфире»`. **Expected:** enabled; **hourly, nominally :00 Europe/Madrid**; `default_timezone: Europe/Madrid`. The scheduler may execute late; nominal time is not an SLA.
- **Stage A — safe existing-generation discovery catch-up:** call `probe_read`, `epg_status` and `epg_pipeline_status`. Never call `epg_sync_start`. Continue discovery only when the published `programmeRunId` is unambiguous, outstanding chunks exist, the checkpoint explicitly allows continuation, and no lease, backoff, retry or generation mismatch blocks it. Call `epg_sync_step({runId})` sequentially, one chunk per call, following `nextAction` and `nextCatchUpAt`. Do not manufacture run IDs, reset leases, force retries or start a separate TMDB/discovery job. If stage A cannot proceed, still attempt stage B **if safe**.
- **Orphaned `running` continuation — fail-closed exception:** A raw `continuation.stage=running` does **not** authorize a step. Only a fresh, read-only `epg_pipeline_status` from a compatible Worker can establish `continuationHealth.status=orphaned`, `lease=expired|none`, `generationConflict=false`, no live competing owner, and an exact match between the pinned `continuation.programmeRunId` and the published `programmeRunId` confirmed by `epg_status` and `epg_pipeline_status`. Require `remainingChunks` to be a positive integer and `resumeBudget` an integer from zero through `remainingChunks`. No hard wait or future `retryAt`/`nextCatchUpAt` may apply. Only then may the hourly task call **one ordinary** `epg_sync_step({runId:publishedRunId})` for the same generation; the Worker is responsible for CAS, fencing and settle/resume. Missing health (including a pre-recovery Worker), `live`, `settled`, `unknown`, ambiguous owner, generation mismatch, invalid budget or a `busy` response means **do not call or retry**. Never infer recovery authority from an expired lease alone, change the task itself, reset a lease or create a new EPG generation. After any successful step, honor server `nextAction=continue|wait|stop`, current generation and budget; do not chain steps against a changing checkpoint.
- **Stage B — full prediction queue:** read `enrichment_runner`, `enrichment_schema`, `enrichment_profile`, `enrichment_queue`, `enrichment_status`; ensure `prediction_validate` is exposed before a new prediction run. Run `prediction_start({trigger:'scheduled'})` once; for a fresh owned `runId`, call `prediction_next` immediately and process server-sized batches without an invented time or film cap. Respect `already_running`, leases and retry/backoff. Consider **hot, cold and deferred** coverage, not just `pendingCount`.
- **Required validation before every prediction submit:** generate the complete intended `prediction` and, only for `fingerprint_and_prediction`, the complete intended `fingerprint`. Invoke `prediction_validate` on those **exact** objects. Require `valid===true` and `contractVersion===enrichment_schema.contract.version`. For `fingerprint_and_prediction`, both `fingerprint.checked` and `prediction.checked` must be true. For `prediction_only`, `prediction.checked===true` and `fingerprint.checked===false`; reuse the Worker-supplied fingerprint. Revalidate after any change. Validation issues must be corrected and rechecked, with a bounded retry count; do not submit unvalidated payloads. An unavailable validator is a **fail-closed** condition (`prediction_validate_unavailable`), not permission to bypass preflight. A contract-permitted per-item validation failure may be submitted as a failure result; never fabricate a successful prediction.
- **Completion and evidence:** use `prediction_submit` only after successful preflight; inspect **each** item result (HTTP 200 alone is insufficient). Process `prediction_next` and `prediction_heartbeat` as required by the lease, then call `prediction_complete` only for an owned run and an allowed stop condition. Re-read `enrichment_status` and `enrichment_queue`; failures or deferred items must not be described as full coverage. Do not mutate profile, flags or other running tasks.

## Operational controls and drift

Only authorized, action-specific owner approval permits **changing either production task's prompt, schedule, enabled state or triggering a production writer**. Updating this reference or merging a PR is **not** such approval. Changes to the live task must be followed by a semantic comparison against this contract and same-delivery updates to affected reference, diagrams and runbooks. The external registry wins on what is currently configured; this document defines what is expected.

When auditing, compare the two tasks by identity, enabled state, effective iCalendar recurrence and timezone, stage ordering, permitted MCP tools, fail-closed preflight and stop conditions. Check `default_timezone` metadata separately from the explicitly timezone-qualified recurrence; a mismatch merits investigation, but alone does not prove an incorrect trigger. For actual execution, correlate the Scheduled Task execution history and server run IDs; never substitute an Events timestamp or a GitHub deployment for scheduler evidence. A read-only drift review must not call production writers or edit either task.
