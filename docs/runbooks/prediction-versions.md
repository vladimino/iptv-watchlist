# Immutable prediction versions: activation and one-time materialization (owner approval required)

The Worker can write each committed prediction once as its own R2 object beside the mutable `predictions.json` bundle; the rule, the key and the pointer shape are in the [prediction runner reference](../reference/api/prediction-runner.md#immutable-prediction-version-objects) and the design decision in [ADR-0019](../adr/0019-live-d1-backfill-boundaries.md) item 4. This page is the procedure for the two production steps that follow the code. Neither is performed by a deploy, a merge or this page: each needs its own action-specific owner approval.

## 1. Activating the writer (`PREDICTION_VERSION_OBJECTS=on`)

Effect: from the next prediction submit on, every created or recalculated prediction is also written once to `enrichment/films/<id>/predictions/versions/<sha256>.json` before the bundle is rewritten, and the bundle record carries `r2Key` and `contentSha256`. Nothing else changes: the submit contract, the queue, the readers and the view are the same, and the flag is read per request.

1. Risk review before the value is set: the writer is additive (one write-once object per committed prediction, about the size of the prediction record), fails closed on a conflicting existing object, and never deletes. The only new failure mode is a storage error on the version write, which fails that item exactly as a bundle write failure does and leaves the bundle unchanged.
2. The owner sets the Worker environment variable in Cloudflare under its own approval and records the time in the [feature flag register](../reference/feature-flags.md). Nothing in the repository holds the value; `wrangler.jsonc` keeps `keep_vars: true`.
3. Verification is read-only: after the next scheduled run, an authorized read of one touched film's bundle shows `current.r2Key` ending in `/predictions/versions/<current.contentSha256>.json`; the object exists; a local SHA-256 of its bytes equals `contentSha256`. No manual run is started to verify.
4. Rollback: set the variable back to `off` (or unset it). New submits stop writing version objects. Objects already written **stay in R2**: they are referenced by bundle pointers, remain valid bodies, and are classified by the offline importer; there is no deletion step and none is to be invented. A code rollback behaves the same way, because the deployed code with the flag unset writes the bundle alone.

## 2. One-time materialization of historical versions (design; no execution recorded here)

Records written before the rule, in `current` and in `history`, carry no pointer. The backfill needs each of them as an immutable object. The procedure is one explicit, separately approved production operation, not a background job and not a Scheduled Task change.

- **Input.** A verified snapshot of the bucket taken with the [read-only exporter](r2-snapshot-export.md) with status `consistent_fenced`. It is the plan's source and the recovery source for every bundle the operation rewrites.
- **Plan.** `node scripts/prediction-versions-plan.mjs --snapshot /absolute/private/snapshot` reads the snapshot only, applies the shared rule to every bundle and prints, per film, the records that already link, the records that need an object (role, index, key, checksum, byte count), records whose pointer is malformed, objects that already exist and only need the pointer (`link_only`), objects whose stored bytes differ from the body the bundle implies (`checksum_mismatch`, a stop condition), and version objects no bundle references. It writes nothing and needs no credential.
- **Body and key.** The object for a historical record is exactly what the writer would have written at the time: the record with keys sorted, without `replacedAt` and without pointer fields; the key is `enrichment/films/<id>/predictions/versions/<sha256>.json` with the SHA-256 of those bytes. Old bodies are therefore preserved byte-for-byte in the objects; nothing is re-predicted and no field is edited.
- **Writes, in this order per film, under the prediction writer lease.** First every pending version object with a create-only condition (an existing object with the same bytes is accepted, a differing one stops the operation for that film). Then one rewrite of the bundle with a compare-and-swap on the ETag the plan was made from, adding `r2Key` and `contentSha256` to each record and a `materialized` provenance block (`at`, `from: 'predictions.json'`, the previous bundle ETag and SHA-256). A changed ETag means a submit intervened: the film is skipped and re-planned, never overwritten.
- **History links.** Each history record keeps its `replacedAt` and its order; the pointer is the only addition. The bundle rewrite never drops or reorders history.
- **Verification.** A fresh snapshot after the operation: every bundle record links, every linked object's manifest checksum equals its pointer, `scripts/prediction-versions-plan.mjs` reports zero pending records and zero mismatches, and the offline importer's prediction family reports `portable: true` with no `prediction_version_*` reasons.
- **Rollback.** The version objects are additive and stay. A bundle can be restored to its pre-rewrite bytes from the input snapshot (its manifest holds the key, the bytes and the checksum) under a separate approval; the `materialized` block names the ETag and checksum that bundle had. No deletion is part of rollback.
- **Approvals.** Reading production for the snapshot, writing the objects and rewriting the bundles are each separate owner approvals. This page records the design only.
