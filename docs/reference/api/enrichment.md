# Enrichment API for «В эфире»

The production API is Cloudflare Worker `iptv` at `https://iptv.vladimino.workers.dev/`, private behind Cloudflare Access. External ChatGPT Scheduled Tasks for EPG/watchlist and predictions were restored under [AIR-62](https://trello.com/c/CU71gW4c) and observed enabled with recent executions on 24 October 2026. These use owner-only IPTV MCP, not Worker Cron; check live task state separately from the repository or Worker `schedules=0`.

`get_site`, `siwc_bypass_bearer_token`, and `OAI-Sites-Authorization` belong only to the legacy Site. They are not credentials for the Cloudflare Worker. Do not send them to `workers.dev`.

Legacy prediction-launch instructions have been separated into [the archive](../../archive/superseded/enrichment-v3-batch.md). The maintained protocol is [the continuous runner contract](prediction-runner.md). Do not start additional production writers without specific owner approval.

This subsystem uses a separate `enrichment/` R2 namespace. It does not write programme, watchlist, metadata, sync, or started records. It is safe for programme sync to work without it.

## Taste-profile publication

`PUT /api/enrichment/profile` publishes a new immutable taste-profile version under the change-impact model of [ADR-0031](../../adr/0031-selective-prediction-profile-compatibility.md). Publishing is a separate owner-approved operation ([procedure](../../runbooks/taste-profile-publication.md)); the scheduled runner only reads the profile.

Body: `{version, schemaVersion: 1, profile, changeImpact, dryRun}`. `version` is an integer greater than the current one; `profile` passes the same field validation as before; `dryRun` is optional and boolean. `changeImpact` is required for every version after the first and refused on the first (HTTP 409 `from_mismatch`, there is no predecessor):

```json
{"impactSchemaVersion": 1,
 "from": {"version": 4, "profileHash": "<profileHash of the current version>"},
 "scope": "identity | selective | global",
 "changedFields": ["horrorPreferences"],
 "selectors": [{"kind": "genre", "values": ["horror"]},
               {"kind": "execution", "dimension": "horror_rule_consistency", "values": ["weak", "mixed"]}],
 "rationale": "optional text, at most 2000 characters",
 "approval": {"approvedBy": "owner", "approvedAt": "<ISO time>", "reviewRef": "<owner decision reference>",
              "declarationSha256": "<64 hex>"}}
```

- The Worker computes the changed top-level profile fields itself; `changedFields` must list exactly those. `identity` needs the same `profileHash` as `from` and no changed field; `global` and `identity` carry no selectors and need no approval.
- `selective` needs at least one selector covering every changed field under the field table of ADR-0031 section 4 (`ratingScale`, `calibration`, `anchorFilms` are global only; the genre sections need their genre selector), and a complete owner `approval`. Selector kinds are `mechanic` (values from the fingerprint mechanics), `execution` (one dimension and its concrete values, never `unknown` or `not_applicable`) and `genre` (the canonical genres of the ADR). Values in one selector are distinct; unknown keys anywhere in the impact or a selector are refused.
- `declarationSha256` is the SHA-256 of the UTF-8 bytes of `JSON.stringify` of `[from.version, from.profileHash, version, profileHash, scope, changedFields sorted, selectors]` with every object's keys sorted, where `version` and `profileHash` are the new version's. The new `profileHash` is computed by the Worker, so the hash is obtained from a dry run.
- A dry run validates everything and writes nothing. It answers `{dryRun: true, valid: true, version, profileHash, changedFields, declarationSha256, from}`. A selective impact without its approval is refused like a real publication, but the refusal also carries `declarationSha256` and `profileHash`: that is the hash the owner approves.

Refusals write nothing and leave `current.json` unchanged. They answer `{error, code, changedFields, profileHash, declarationSha256}` with HTTP 400 for `impact_missing`, `impact_schema_unknown`, `scope_unknown`, `identity_requires_same_hash`, `changed_fields_mismatch`, `global_field_requires_global`, `selective_requires_selectors`, `selector_kind_unknown`, `selector_invalid`, `field_not_covered`, `genre_floor_missing`, `selective_requires_owner_approval` and `approval_mismatch`, and HTTP 409 for `from_mismatch` (the current version moved since the impact was written) and `version_not_increasing`. A body or profile that fails the field validation is HTTP 400 without a code, as before.

Write order: the version record `enrichment/profile/versions/<n>.json` (`{version, schemaVersion, updatedAt, profileHash, profile, changeImpact}`, `changeImpact` null on the first version) is written create-only; then `current.json` is replaced by compare-and-swap on the ETag read at the start (create-only when there is none). `current.json` holds the same record plus `lineage`: the `(version, profileHash, changeImpact)` of up to the 32 most recent versions, oldest first; a current record written before lineage existed starts it with its own link. When the version record already exists, a retry with the same `profileHash` and `changeImpact` reuses it (a crash between the two writes is completed by sending the same request again); a different record under that number answers HTTP 409 `version_exists` and is never overwritten. When `current.json` changed between the read and the swap, the answer is HTTP 409 `profile_changed`: read the current profile and publish again. After a successful swap the prediction queue is refreshed as before. The answer is the new `current.json`. `GET /api/enrichment/profile` and the MCP tool `enrichment_profile` return that record, including `changeImpact` and `lineage`.

Freshness is unchanged by this contract: every consumer still compares the profile version and hash strictly, so any new version makes every prediction stale until the selective evaluator of ADR-0031 is implemented and activated.

## Actual ratings

Actual Letterboxd ratings are stored separately with `PUT /api/enrichment/actual-ratings`:

```json
{"items":[{"filmId":"123456","rating":4.5}]}
```

Use `rating:null` to clear one. The film's actual rating never enters the `/next` model payload. The owner's UI can display actual and predicted ratings together. `GET /api/enrichment/view` supplies current predictions to the UI while preserving stale prediction history internally. Its fingerprint facet also includes the thirteen general `execution` dimensions when they were saved, omitting `unknown` and `not_applicable`. Genre-specific execution fields are not part of that facet. An older index entry receives the compact execution object from `POST /api/enrichment/fingerprint-view/backfill` or the next fingerprint save; the view request does not reread every fingerprint. Each `films[id]` also includes `watched`: `true` when that view-index entry stores the boolean `true`, `false` when it stores `false`, and `null` when the field is absent, `null` or not a boolean. `null` means the fact is unknown. It is not a stored `false`. The route copies `watched` from the index entry after the prediction overlay. That overlay does not replace `watched` or `actualRating`. When the prediction marker is `d1` on schema version 7 or newer, prediction, fingerprint, impact and mood on this response come from the overlay, and a film with no prediction row does not keep those prediction fields from the object. The route does not read fact records, resolve a Letterboxd id to a TMDB id, or write. The fact projection stores the same boolean under a film's Letterboxd id and its `tmdb_<n>` id; this response keeps those keys separate.

## Failure behavior

`GET /api/enrichment/status` returns the latest run with trigger, start/finish, checked/added/updated/failed, and queue status with remaining count, last batch stage/reason, and the next nominal hourly Scheduled Task trigger (`nextScheduledRunAt`; `nextCatchUpAt` in prediction responses is a compatibility name for the same value, `null` when the schedule is unknown; see [timing](../scheduled-tasks.md#timing-nominal-trigger-versus-server-gate)). The programme API does not read enrichment storage. A failed recompute keeps the previously committed prediction and its history, and the UI continues to show the programme. Ordinary successful checks need no ChatGPT notification; the Site's Events panel and footer expose progress. `GET /api/enrichment/footer/status` also returns `integrations` for that footer: watchlist, ratings, EPG ingestion, film recognition and predictions. Its `predictions` object and the `snapshot.queue` of every prediction Event (start, progress, stop and completion) carry the same read-only slices of the stored queue: `outstanding` (films without a current prediction, hot plus cold), `eligibleNow` (the films the runner would take at that moment, by the runner's own eligibility rule), `deferredByRetry` (outstanding films whose stored `retryAt` is still in the future) and `nextRetryAt` (the earliest such `retryAt`, UTC, or `null`). The footer's `nextScheduledRun` is the nominal trigger of the external hourly Scheduled Task (`:20` Europe/Madrid, `null` when the schedule is unknown) and is a different time from `nextRetryAt`. All four come from the queue object as stored; the route does not refresh the queue, and the slices are `null` when the queue has no `hotPending` / `coldPending` lists. The UI derives its wording from these slices, never from the stop reason alone: an explicit `outstanding: 0` reads as every film having a current prediction only while the stored coverage agrees (`currentPredictionsTotal` equal to `confirmedFilmsTotal`), otherwise as a neutral remainder; deferred films name their earliest retry time; films eligible now are reported as ready for the next run; and a record without slices reads as a neutral remainder whatever its `hotPending` / `coldPending` counters say, zeros included, because counters alone are not evidence of a drained queue. The states come from the stored job results. The route still does not start a sync, a ratings refresh, or recognition. The `letterboxd_ratings` state describes the routine ratings read of the EPG commit and comes from `sync.json` alone: a completed sync whose `ratingPending` is still set without a `ratingError` reads as `degraded` / `ratings_pending` with `pendingSince` (that sync's `updatedAt`), because the outcome of the read was never recorded and the cause is unknown, not as a specific HTTP 403; a `ratingError` timestamped by `updatedAt` reads as `ratings_blocked` (403 or anti-bot), `ratings_rate_limit`, `ratings_incomplete` or `failed` / `ratings_failed`; `ratingObservedAt` is the last committed read and gives `healthy` or `stale` (older than 48 hours); the later of the success and the error wins, so an error older than the last success is history in `lastFailureAt`; a sync still in its `metadata` or `epg` stage has not reached the ratings step and reports the previous success; and with no sync record or no ratings fields the state is `unknown` / `no_data`, never `healthy`. The frozen `enrichment/ratings/status.json` of the retired ratings-only refresh ([ADR 0040](../../adr/0040-retire-ratings-only-refresh.md)) never sets that state; when the document exists it is reported only as `retiredRefresh` (`state: "retired"`, `lastOutcome` `failed` / `succeeded` / `unknown`, the sanitized `code` and its `lastSuccessAt` / `lastFailureAt`), and is `null` otherwise. `manualRefreshEnabled` stays in the response for compatibility and is always `false`; the UI does not render it and labels the history line as a retired refresh, so it never suggests a manual refresh can be turned on. A watchlist fetch that fails before `sync.json` is replaced is recorded in `watchlist-ingest.json` with a fixed code and a timestamp. Recognition uses the current programme run. A continuation that is `running`, `busy`, `epg_committed`, or paused with `remainingChunks` still positive is in progress (`running`, or `stale` once the checkpoint is older than 48 hours). A paused `chunk_budget` with `remainingChunks` 0 is `waiting` / `resolver_waiting` while `nextCatchUpAt` is still ahead, and it stays `waiting` until two nominal hourly triggers after that gate have passed and another 45 minutes have elapsed. Exactly at that instant it is still `waiting`. `waiting` does not count as attention. After the grace, the state is `degraded` / `resolver_no_recent_progress` only when the continuation pins the published generation, `sync.stage` is `complete` without an error, no resolver lease is unexpired, no `retryAt` is still ahead, `readyNow` is a positive count, both `continuation.at` and `discoveryStatus.finishedAt` parse, `discoveryStatus.programmeRunId` is that same generation, and that `finishedAt` is not later than the gate. That code means a same-generation batch was stored and none newer than the gate was. A missing discovery status, a missing or unparseable checkpoint or `finishedAt`, or a status whose `programmeRunId` is absent or belongs to another generation is `unknown` / `no_data` once the grace has passed: missing evidence is not a confirmed lack of progress, and another generation's `finishedAt` is not progress on this one. A same-generation `finishedAt` later than the gate stays `waiting`. The stall code does not mean an external usage quota was reached: the Worker cannot read the task registry or a usage account, and the only quota it names is a prediction `stopReason` of `quota` that a run actually stored, shown on the prediction line as a usage limit confirmed at that run's finish time. A missing or different generation pin, an EPG stage that is not complete, an unparseable gate, a checkpoint or batch time more than five minutes in the future, an empty or unknown ready count, or a schedule the Worker cannot compute stays `waiting` or `unknown` / `no_data` and does not use the stall code. A future `retryAt` stays `resolver_backoff`. A previous generation's completion is not this generation's success. The prediction line stays the stored run: a drained queue is still a drained queue when recognition is the source of attention. The footer's next-run line is the nominal schedule (`Следующий запуск по расписанию`), an estimate, not a promise that the external task will run. The same continuation read by the admin health evaluator uses that evaluator's own grace and is not this footer state ([data health](../domain/data-health.md)). A stored ratings or watchlist failure does not change the EPG or prediction state.

## Submit validation contract

One declarative contract drives both the `POST /api/enrichment/submit` validator and `GET /api/enrichment/schema`, so a caller can run the same checks before `prediction_submit` and, when the Worker still rejects an item, learn which field failed. The rule tables (`FINGERPRINT_RULES`, `PREDICTION_RULES` in `src/enrichment.js`) are the only source of field names, enum lists, list sizes and lengths; the validator interprets them, and the schema route serialises them. Among the rules: `payoff` and `ending_quality` take `weak | mixed | strong | unknown`, `hero_vulnerability` takes `low | mixed | high | unknown`, `moodLabels` holds 2–4 labels of at most 45 characters, the thirteen general `execution` dimensions are required and the genre dimensions are optional. A fingerprint or prediction that the rules accept is stored unchanged; the rules do not alter the stored payload.

`GET /api/enrichment/schema` returns its descriptive fields and `contract`:

| Field | Meaning |
| --- | --- |
| `contract.version` | `1` |
| `contract.fingerprint.rules`, `contract.prediction.rules` | One rule per field. `kind` is `const` (`value`), `enum` (`values`), `enum_list` (`values`), `enum_object` (`fields` with the allowed values per key, `required`, `optional`), `text_list` (`minItems`, `maxItems`, `maxLength`), `ref_list` (as `text_list`; each item is an `https://` URL or `model_knowledge`), `number` (`min`, `max`, optional `step`) or `text` (`maxLength`, `nullable`) |
| `contract.fingerprint.maxChars` | Serialised size cap of an otherwise valid fingerprint (`12000`) |
| `contract.issueCodes` | `required`, `invalid_type`, `invalid_version`, `invalid_enum`, `too_few`, `too_many`, `empty`, `too_long`, `out_of_range`, `invalid_step`, `invalid_ref`, `too_large` |

A rejected item in the `submit` response keeps its previous shape (`status: retryable_failure`, `error: parse_error`, `failureScope: item`, `retryable`, `retryAt`) and adds `validation`:

```json
{"filmId":"tmdb_1","status":"retryable_failure","error":"parse_error","failureScope":"item","retryable":true,"retryAt":1792957895257,
 "validation":{"stage":"fingerprint_schema","reportedBy":"worker","issues":[{"path":"fingerprint.execution.payoff","code":"invalid_enum"},{"path":"fingerprint.moodLabels","code":"required"}]}}
```

`stage` is `fingerprint_schema` or `prediction_schema` (the Worker rejected the submitted object), `fingerprint_missing` (the film has no current fingerprint and none was submitted; `issues` is `[{path: "fingerprint", code: "required"}]`) or `caller_reported` (the caller sent `failure.kind`; `issues` is empty). `path` is `fingerprint` or `prediction`, optionally followed by the field and, for `execution`, the dimension; a list issue names the list, not the item. At most 20 issues are reported, in rule-table order. The same `validation` object is stored on `run.failures[filmId]` and copied into the queue `retries` record, and [`prediction_film_diagnostics`](prediction-diagnostics.md) returns it as `retry.validation` after re-checking every path and code against the vocabulary. A system failure (`storage_error`, run scope) carries no `validation`: a schema violation, a model output the caller could not parse and a storage or API failure are three different records.

### Preflight before submit

The executable preflight is the read-only MCP tool `prediction_validate` ([MCP reference](mcp.md)): the caller passes the complete `fingerprint` and/or `prediction` it intends to submit and receives `success` and `valid` (one verdict, true only when every supplied object is free of issues) plus the same `issues[{path, code}]` the submit would report, with no storage access, no run or lease involvement and no recorded failure. A client that cannot call the tool can evaluate `contract` itself; `tests/submit-validation.mjs` contains a generic evaluator over the published JSON that reproduces the server's issues, which is the parity test for the contract. Either way the Worker validates again on `submit` and is the enforcement point: a caller that skips the preflight is not blocked, it is corrected per field after the fact. Whether the external ChatGPT Scheduled Task performs the preflight is decided by that task's prompt, which is outside this repository and changes only with owner approval; the repository can offer the tool and the contract, not make the client call them.

The validation summary does not alter item-failure semantics: a rejected item is a retryable `parse_error` with the ordinary backoff, re-delivery of the same film is idempotent and returns the stored `validation`, five consecutive distinct format failures stop the run as `format_error_storm`, and the [run-step diagnostic](run-diagnostics.md) `itemValidation.stages` entries keep their `{stage, reportedBy}` shape. The thrown validator message, the payload, the model output and the film title are never copied into the response, the run record, the queue or a log line; only paths and codes from the closed vocabulary are. The runner contract (`GET /api/enrichment/runner`, `itemFailures.validation`) and the MCP tool descriptions point the caller at the contract before `submit`. A retry record without a validation summary gains one only at that film's next rejection; nothing resets or retries deferred films.

## Letterboxd personal ratings and runtime

Film runtime is already parsed from each Letterboxd film page as minutes and is included in the programme snapshot. Some unreleased films have no published runtime; their value remains `null` until Letterboxd supplies it. The card displays runtime when available.

The user's own rating is fetched from the public member-film page (`https://letterboxd.com/demo-user/film/<slug>/`) and identity-checked against the exact film URL and member before persistence. It is stored in `enrichment/films/<id>/actual.json`, never in a fingerprint or prediction input. A missing member-film page means no verified rating from that source; it does not erase an older known rating.

After a successful programme commit, the existing daily sync checks newly added watchlist IDs (including re-added films with cached metadata), refreshes already known ratings, and retries transient rating failures on the next run. A failed rating lookup never rolls back programme or watchlist data. One-time or later manual audits can call `POST /api/enrichment/ratings/backfill` with `{"cursor":0,"batchSize":10}` and continue using `nextCursor` until `done`; pass the first response's `programmeRunId` to detect a changing source snapshot. Results include saved, unchanged, not_found, not_rated or a per-film error. This endpoint only writes ratings; it does not update the programme timestamp.

`enrichment/diagnostics/rating-observations.json` (the accuracy diagnostic's change log) is no longer written: its legacy writers were removed with the retired `LETTERBOXD_FACTS` switch ([ADR 0055](../../adr/0055-retire-letterboxd-facts-switch.md)). The stored log stays readable history for the accuracy and film-history readers, and the change history of a rating is the fact record's `ratingHistory` ([user facts](../integrations/letterboxd-user-facts.md)).

These writers always record Letterboxd facts and never write the view index directly; no switch selects another path ([ADR 0055](../../adr/0055-retire-letterboxd-facts-switch.md), [feature flags](../feature-flags.md)): the films-list scan of the programme commit and of the ratings refresh stores one scan summary and rewrites only changed fact records, so a film missing from the list keeps its rating, and a listed film without a rating becomes watched and not rated; the member-film lookup and `PUT /api/enrichment/actual-ratings` record one observation each (`letterboxd_film_page`, `owner`), which a later scan does not override. The owner edit applies the fact first: `status: saved` (and `actual.json` written) only when the edit became the current value, `status: older` with the current rating when a newer observation already stands, and an item error when the film's ids conflict. The view index (`actualRating`, `watched`, `watchlist`) is then projected under the film's Letterboxd id and its `tmdb_<n>` id. Contract: [Letterboxd user facts](../integrations/letterboxd-user-facts.md). A stale `LETTERBOXD_FACTS` binding of any value changes none of this.

## EPG resolver / hot–cold pipeline (v2)

Normalization, service prefix/year extraction and explicit series/show filtering run locally, without an LLM. Candidate title keys are **not** film identities: only a confirmed TMDB movie ID is canonical (`canonicalIdentity: tmdb:<id>`). RU/UK/EN translations and alternative titles are retained as aliases; yearless aliases are reused only when the cached identity and runtime are unambiguous. Unconfirmed candidates remain unresolved with a bounded retry time.

The canonical cache is persistent, independently of current broadcasts. `hot` is evaluated against the actual current clock: show start in the last 72 hours or next 24 hours. Older cache records temporarily use `epgLastAiring` until the next EPG scan supplies actual timeslots. The forecast queue contains missing/stale **hot** catalogue films, then any remaining watchlist work; cold EPG catalogue films are deferred. Newly resolved/promoted hot films sort before the older hot backlog. Repeat broadcasts update availability/aliases only, without changing fingerprint or prediction freshness.

`POST /api/enrichment/discovery/resolve` keeps the existing `limit` (1–24) contract. A chunk is also bounded by 22 seconds and 16 TMDB requests, with 200 ms pacing. Each confirmed cache record and resolution decision is persisted individually; a conditional R2 lease prevents overlapping resolver writers. On restart, already confirmed identities are reused. HTTP 429 retains work and stores `retryAt`; no busy retry loop. Ambiguous/no-match decisions remain unresolved with exponential daily retry, capped at seven days.

One request runs one discovery chunk and does not schedule another. A separate HTTP request does not guarantee a new Cloudflare isolate; one chunk per request is a memory hypothesis to verify in production after this change is deployed. `chunks:0` reports the contract without running a chunk. The `DiscoveryContinuation` entrypoint (`src/continuation.js`) stays internal-only and also runs one chunk. Public HTTP always reaches the default export, so the entrypoint has no internet-facing route. A public self-fetch is not a fallback: Access would refuse it, and Cloudflare rejects a Worker's subrequest to its own zone (error 1042). No cookie, Access JWT, `OAI-Sites-Authorization`, or other credential is forwarded or stored. The Sites-era `EPG_SITE_SERVICE_TOKEN` is no longer read.

`epg/resolver-continuation.json` (shown as `continuation` in pipeline status) records `paused` (`epg_committed`, `scan_committed`, `chunk_budget`, `backoff`, `programme_changed`, `interrupted`), `running`, `complete`, or `error`. A live lease (`expiresAt` still in the future) returns `discovery.state: busy` and `nextAction: wait` without overwriting the continuation or writing decisions. An expired lease is not deleted ahead of that call.

### Live and orphaned `running` records

A `running` record names the hop (`hopId`) that opened it and the budget that hop had (`remainingChunks`). The raw record cannot say whether that hop is still writing, so pipeline status derives `continuationHealth` from the record, the resolver lease `epg/resolver-lease.json` and the last discovery status `epg/discovery-status.json`, and every continuation response carries the same derivation as `diagnostic.health`:

| `continuationHealth.status` | Meaning | Contract for a `running` record |
| --- | --- | --- |
| `live` | The lease is unexpired (`leaseHop` says whether it belongs to the record's hop or to another one). A writer is active. | `state: running`, `reason: busy`, `nextAction: wait`, `nextCatchUpAt` = the lease expiry (`leaseExpiresAt`) |
| `orphaned` (fail-closed) | As below, but the orphan's chunk did not finish and the record already carries an interruption (`interruptions` ≥ 1): resuming would be the second hop in a row to end before its checkpoint. | `state: running`, `reason: interrupted`, `nextAction: stop`; the next step writes the stop instead of resuming (see *Repeated interruptions*) |
| `orphaned` | The lease is expired or missing: the hop did not reach its checkpoint and has been silent for at least one lease TTL. The most likely cause is an invocation that ended between the status write and the checkpoint write (a thrown handler normally leaves an `error` record); a failure of the checkpoint write itself leaves the same picture, so the cause of a given orphan is an inference, not something the record proves. An invocation that ended later, during the trailing writes or while the response was in flight, is not an orphan: its checkpoint is already stored (see the order of the hop's final writes below). | `state: running`, `reason: orphaned`, `nextAction: continue`, `remainingChunks` = `resumeBudget` |
| `settled` / `idle` | The record is not `running` / there is no record. | Unchanged contract |

For an orphan, `chunkCompleted` says whether the dead hop's own chunk finished. Every status a chunk writes to `epg/discovery-status.json` (the cheap-pass checkpoint, the final summary, the programme-changed summary; `lastBatch` in pipeline status) carries the `hopId` of the lease that wrote it, and a `running` record names the published generation it pins to. The chunk counts as completed only when the last status has a `finishedAt`, names the same `hopId` and the same `programmeRunId` as the record, matches the published generation, and started after the record was opened (`startedAt` ≥ `record.at`). The status object is shared, so a newer status written by another hop, a status without a hop marker (written before statuses carried one) or a cheap-pass checkpoint is not attributed to the orphan: the chunk is then run again with the budget the hop had, which can cost one extra chunk but never repeats a decision or resets the series. `resumeBudget` is the hop's budget minus one when the chunk is attributed, otherwise the full budget.

The next explicit `epg_sync_step` (or `POST /api/enrichment/discovery/resolve`) recovers an orphan in one call, atomically against the record it read:

1. **Generation handoff.** When the record does not belong to the published generation, it is superseded by the checkpoint the EPG commit would have queued: `paused` / `epg_committed` with `remainingChunks: 12` and `programmeRunId` = the published generation, written as a compare-and-swap against the record that was read. This covers an orphan pinned to an earlier generation (`generationConflict: true`), a finished or paused series of an earlier generation, a `programme_changed` stop of an earlier generation, and a `programme_changed` record of the published generation itself, which a chunk writes when it runs while the publication is still copying the shared programme. The superseded record's hop is never resumed and its decisions, statuses and catalog writes stay as written; the step then continues as an ordinary call on the new series (`diagnostic.branch: chunk`, `recovery.action: generation_recovered`, `recovery.superseded` = the earlier generation). The handoff happens only once the published generation is in place, that is when the generation pointer names it **and** the shared `programme.json` already carries it; until then the call writes nothing and answers `wait` (`diagnostic.branch: generation_pending`). A live writer is never superseded (`busy` / `wait` until its lease expires), a record without a generation pin cannot be judged and is continued as before, and a `complete` or `paused` record of the published generation is not a handoff. This is also how a commit that was interrupted after publication but before its discovery checkpoint is restored: the next ordinary `epg_sync_step` of the same run re-queues the published generation idempotently, without publishing anything again.
2. **Settle.** When `chunkCompleted` is true, the record is replaced by the checkpoint the dead hop would have written from the persisted status (the same rule that turns a chunk result into `paused`, `chunk_budget`, `backoff`, `complete` or `programme_changed`), under the dead hop's `hopId`. The chunk's decisions and catalog writes were already stored individually, so nothing is repeated and `remainingChunks` moves by exactly that one chunk.
3. **Resume.** The ordinary decision then applies to the settled record: a chunk runs under a new lease and a new `hopId` when budget and backoff allow (`diagnostic.branch: chunk`, `recovery.action: settled`), or the call reports the settled contract without running one (`diagnostic.branch: orphan_settled`, for example `chunk_budget` / `wait` or `complete` / `stop`). When the chunk had not finished, the record is resumed directly with the hop's full budget (`recovery.action: resumed`), and the new `running` record carries `interruptions` (the number of hops in a row that ended before their checkpoint).

**Repeated interruptions (fail-closed).** A stored checkpoint drops `interruptions`; a settled orphan (its chunk finished) is never counted. When an orphan whose chunk did not finish already carries `interruptions: 1`, the next explicit step does not resume it: it replaces the record, as a compare-and-swap, with `paused` / `reason: interrupted`, the same `hopId`, budget and `programmeRunId`, and `interruptions: 2`, runs no chunk, takes no lease, and answers `stop` (`diagnostic.branch: interrupted`, `recovery.action: interrupted`). Every later scheduled step answers the same `stop`. Two hops of one series that both end before their checkpoint point to a chunk that kills its invocation (for example the Workers memory limit) rather than to a transient fault, and repeating it on every hourly call would only repeat the failure without progress. The stop lasts until the next EPG commit opens a new series for a new generation (a re-commit of the same generation keeps it), or until an owner-approved forced `POST /api/enrichment/discovery/resolve` runs the chunk again; a stored checkpoint of that chunk clears the count. No lease is reset and no record is edited by hand.

**Order of the hop's final writes.** The continuation checkpoint is the very next durable write after the hop-marked final status: the chunk saves `epg/discovery-status.json`, then its checkpoint (`paused`, `chunk_budget`, `backoff`, `complete` or `programme_changed`, under its own `hopId`), and only then the trailing writes: the score preview, the variant plan, the lease release, the diagnostics ring entry and the response. An invocation that ends during those trailing writes, or whose response never reaches the client (a client timeout, a dropped connection, an MCP error shown by the client), therefore leaves a settled record, not an orphan, and nothing is rolled back: `continuationHealth` is `settled`, `lastBatch.hopId` equals the checkpoint's `hopId`, and the checkpoint's `at` is later than the step's diagnostics entry. That entry is `phase: checkpointed` with the stored checkpoint (written right after the checkpoint and before the trailing writes), so it states that the step committed; a later step closes it as `interrupted` with `committed: true`. The next ordinary call simply continues the series; when the lease release was lost too, that call answers `busy` / `wait` until the lease expires (at most one TTL), then continues. The step response reports the tail in `diagnostic.leaseReleased` (whether the lease was released after the checkpoint) and `diagnostic.trailingError` (the classified code of a write that failed after the checkpoint, `null` otherwise); a failed release or trailing write never turns a committed step into an `error` record or a failed step. The orphan settle above remains the repair for an end between the status write and the checkpoint write.

Two fences protect the writes. **Continuation checkpoints** are compare-and-swap writes on the object's etag, and the final checkpoint is written only while the record still names the writing hop; `diagnostic.saved.write` reports `saved`, `other_hop` (another hop owns the record) or `write_conflict` (both conditional writes were rejected while the record still named this hop; the checkpoint is then reported as not stored, the record stays `running` and the next step settles it from the hop-marked status). A call whose record moved between its read and its write (another hop settled or opened it) releases its lease and answers `busy` / `wait` with `diagnostic.branch: record_changed`. **Chunk side effects** are each preceded by a renewal of the hop's lease, immediately before the individual write and inside the helper that performs it: both catalog copies (generation and shared), the programme showing, each decision save, each status save, the score preview, the variant plan and the prediction-queue checkpoint (the queue refresh takes the fence from the chunk and renews after its reads, right before its write). The renewal is a conditional write that fails as soon as another hop holds the lease, and a failed renewal aborts the chunk before that write (`chunk.error: resolver_busy`, checkpoint `other_hop`); a stall between two writes of one helper, or between the reads and the write of the queue refresh, is therefore fenced like any other. A lease expires only after the hop has been silent for a whole TTL (90 s), and a hop that stalls past it cannot write over its replacement; the residual window is one storage write of the old hop that is already in flight and itself lasts longer than the TTL. Concurrent callers end with exactly one owner per chunk and one budget decrement. One chunk per explicit call, the 12-chunk budget, backoff and `wait` times, idempotent decisions and the owner boundary are unchanged by recovery; no lease is reset and nothing is forced.

A caller that decides from the raw `continuation.stage` alone treats every `running` record as a live writer and never calls on an orphan. To recover one it must read `continuationHealth` (or the `discovery` contract of a `chunks: 0` report) and call `epg_sync_step` when the status is `orphaned`. The instructions of an external scheduled caller are operational configuration outside this repository; changing them is a separate, owner-approved step, and until it is taken an orphan is recovered only by an explicit, approved call.

Every EPG commit and discovery response includes `discovery`:

| Field | Meaning |
| --- | --- |
| `state` | `paused`, `running`, `complete`, `error`, or `busy`. A finished response is not left `running`; a `running` state in a report is a live writer (`reason: busy`) or an orphan (`reason: orphaned`), see above. |
| `remainingChunks` | Chunks still allowed in this series. A new series starts at 12. |
| `nextAction` | `continue`: call again now. `wait`: do not call before `nextCatchUpAt`. `stop`: do not call until the next EPG commit. |
| `reason` | Why the series is paused or waiting (`epg_committed`, `scan_committed`, `chunk_budget`, `backoff`, `programme_changed`, `busy`, `orphaned`, `interrupted`, `idle`, `missing_secret`, an error code), or `null` between chunks. |
| `nextCatchUpAt` | Earliest time for the next call when `nextAction` is `wait` (the next whole UTC hour, the backoff time or a lease expiry). A gate, not a scheduled run. |
| `nextScheduledRunAt` | On `wait` only: the first nominal hourly Scheduled Task trigger at or after `nextCatchUpAt`, when the catch-up is expected; `null` otherwise or when the schedule is unknown. Informational; it never replaces the gate. |
| `retryAt` | Discovery backoff, when one is stored. |
| `programmeRunId` | Programme the chunk was reading, when known. |

`continue` is the response after the EPG commit (`reason: epg_committed`, `remainingChunks: 12`) and after a chunk that still has candidates and budget. `wait` covers the 12-chunk budget, a TMDB or storage backoff, a live lease, and an error whose catch-up time has not arrived. A call before that time does not start another series. Once `nextCatchUpAt` has passed, one new series may start. `stop` means the backlog is finished, the programme changed during the chunk, there is nothing to resolve, or the series failed closed after repeated interruptions (`interrupted`). `epg_sync_step` obeys `stop` until the next EPG commit. `POST /api/enrichment/discovery/resolve` may run one more chunk after `stop` when the catalog has new candidates; it still honors a live lease, `chunk_budget`, and `backoff`. A programme change skips the prediction-queue refresh; the next EPG commit queues discovery again. Decisions already saved for that chunk stay.

### One observation: no targeted retry

There is no request that resolves or retries one observation. `POST /api/enrichment/discovery/resolve` takes only `limit` and `chunks`. It runs one chunk over every actionable candidate in priority order (hot first, then with a year, then the latest airing), with its own TMDB calls, and still honours a live lease, `chunk_budget` and a backoff. A forced call is therefore a series-level operation, not a retry of a chosen key.

Whether a retry of one observation would help follows from the resolver's own rules:

- An actionable observation (no decision, retry due, or new evidence) is already taken by the next chunk.
- A future per-observation `retryAt` is policy and is never bypassed.
- A terminal decision on unchanged evidence would repeat the same search; a new airing resets its attempts on its own.
- An `ambiguous` decision needs identity review rather than another attempt.
- A candidate outside the current EPG window is not looked up at all.
- A series gate (TMDB or storage backoff, the chunk budget, an error delay) and a live resolver lease hold every observation back, and a retry must respect them too.
- A `missing_secret` stop is cleared only by restoring the TMDB configuration, not by a retry or a new generation.

The [recovery assessment](../domain/discovery-recovery.md) states this per observation. For exactly one of these cases, a terminal decision on unchanged evidence, the owner can lift the terminal fence with the guarded action [`discovery_reconsider`](admin.md#discovery-observation-recovery-get-apiadmindiscovery-recovery). It writes one decision and looks nothing up: the next ordinary chunk of this route, or of `epg_sync_step`, takes the observation with its usual pacing, throttle and lease rules. After each chunk the resolver also writes the generation's [observation index](../domain/discovery-observation-index.md), fenced by the resolver lease; an index failure other than a lost lease never fails the chunk.

Since [AIR-151](https://trello.com/c/iZ7TR7y0) a continuation response from `POST /api/sync/epg` and every `POST /api/enrichment/discovery/resolve` response also carry `diagnostic`: the branch `advanceDiscovery` took and its intermediate outcomes (continuation record before, lease state, decision, hop id, chunk summary, continuation record after). The same step is logged as `{"event":"epg_continuation"}` lines sharing one `id` (`entered` before any storage access, `checkpointed` once the hop's checkpoint is stored, then the outcome; `interrupted` when a later step closes an entry left without a terminal phase) and stored best effort in `epg/resolver-continuation-diagnostics.json`, a ring of the last 20 step entries that `GET /api/enrichment/pipeline/status` returns as `continuationDiagnostics`. Every value is a code from a closed vocabulary, a UUID, a timestamp or a count; thrown messages are classified into error codes, never copied. The field list is in [the MCP contract](mcp.md#continuation-diagnostics). Nothing in it changes a decision, retries a call or writes on a `GET`.

`LETTERBOXD_DIARY_HISTORY` is retired ([ADR 0075](../../adr/0075-retire-letterboxd-diary-history-switch.md)) and does not select a diary read. A sync status written while Diary still ran inside the commit may still show `diaryHistory` from that older stage ([ADR 0054](../../adr/0054-diary-first-epg-ratings.md)). The current ratings run reads Diary page 1 when migration is complete. The sync status also returns `ratingAttempt`, the durable marker of the post-commit ratings work; a step on a completed run closes a stale `started` attempt as `unknown` without retrying Letterboxd ([ratings attempt](../integrations/letterboxd-ratings.md#ratings-attempt)). `REMOVAL_RATING_LOOKUP` is retired ([ADR 0077](../../adr/0077-retire-removal-rating-lookup-switch.md)) and does not select the member-page lookup. The ratings run looks up a removed film the Diary did not rate; the EPG commit does not. A confirmed stored rating for a film the current Diary page did not list is not requested, including after a new reference reopens the entry. A film that page lists without a rating is still looked up. A null or absent rating is not watched. An older sync status may still show `removalRatingLookup`; see [removed films](../integrations/letterboxd-ratings.md#removed-films). `ratingsPending` on a completed sync is not a discovery signal. A later `epg_sync_step` does not retry Letterboxd. The rating attempt that belongs to the EPG commit still runs once inside that commit. Under an active `RATINGS_PIPELINE=separate` the commit runs no ratings work and carries `ratingsPipeline: separate`; the ratings have their own status ([separate ratings pipeline](../integrations/letterboxd-ratings.md#separate-ratings-pipeline)). The separate [AIR-64](https://trello.com/c/WTnyO8bX) request `POST /api/enrichment/ratings/refresh` is retired ([ADR 0040](../../adr/0040-retire-ratings-only-refresh.md)): it answers `410 Gone` for every method, body and `RATINGS_REFRESH` value, before it reads the body, the bucket or Letterboxd. `GET /api/enrichment/ratings/status` only reads and returns the last state the refresh stored, with `enabled: false`. See the [retired ratings contract](../integrations/letterboxd-ratings.md).

`POST /api/sync/epg` queues discovery as soon as the commit's generation is published (after the pointer switch and the copy into the shared objects, or after the copy on the commit's resume path), before `finishSync`, the prediction-queue refresh and the ratings attempt, and again, idempotently, when the commit returns ([ADR 0030](../../adr/0030-discovery-queued-at-publication.md), [AIR-212](https://trello.com/c/c1NQNHRa)). A commit killed in its tail therefore leaves the published generation's series open, and `sync.json` may stay in stage `epg` meanwhile; a step in that state is a commit retry on the resume path (no EPG download, no TMDB), not a chunk, and the hourly task does not make it ([Scheduled Task contract](../scheduled-tasks.md)). `POST /api/enrichment/discovery/scan` queues it after scanning `EPG_XML_URL`. Both write the `epg_committed` / `scan_committed` record with the `programmeRunId` of the generation they committed, as a compare-and-swap, and only when that generation is still the published one: a commit that paused after its programme write and resumed after a newer publication is refused and leaves the newer series untouched. A stored series of the same generation keeps its record and progress (a re-entered commit is idempotent; only a `programme_changed` artefact of that generation is replaced), and a live writer's `running` record stays in place (that writer's own checkpoint names the generation it read). The returned contract is always that of the record left in place. Neither request runs the chunk. The prediction runner never waits for TMDB. No schedule change, new LLM invocation or recalibration is required. The calls come from external ChatGPT Scheduled Tasks; the Worker installs no Cron triggers.

`GET /api/enrichment/pipeline/status` separates normalized EPG candidate titles, excluded non-movies, unresolved candidates, unique confirmed TMDB films, hot/cold cached films, queued predictions, hot predictions and cold deferred work. These populations differ; candidate counts must never be presented as film counts.

**Bounded ledger ([ADR 0034](../../adr/0034-bounded-discovery-ledger.md), implemented in [AIR-220](https://trello.com/c/uPvMc5ww); inactive by default).**

- **Modes.** `DISCOVERY_LEDGER_MODE` ([feature flags](../feature-flags.md)) is `full` by default: `epg/discovery-latest.json` holds every candidate ever seen, as above. With `bounded` it holds only the latest scan's candidates. Candidates that left the EPG move losslessly into the archive `epg/discovery-archive/v1/`: write-once hash-segment and manifest versions behind the compare-and-swap pointer `current.json`. The EPG commit writes the archive under the discovery lease, fenced on the published pointer etag it read, and merges re-entering candidates back from it. With `frozen` archiving stops, and an existing archive stays history.
- **Decisions.** `epg/discovery-resolution.json` is never touched by archiving.
- **Ledger fields.** The active ledger object then carries `ledgerMode` and `archive` (`version`, `manifestId`, `segments`, `items`, `bytes`, `alsoArchived`, `uniqueArchivedItems`).
- **Pipeline status.** It adds `archive` = `{ledgerMode, activeItems, uniqueArchivedItems, manifestId, segments, items, bytes}` and reports `ledgerTotal` as the unique keys of active ∪ archive. Per-activity counters, `rejectedNonfilm` and `recognizedFilms` cover the active ledger. Status never reads segments.
- **Disabled routes.** `POST /api/enrichment/discovery/scan` and `/reconcile` answer `409` whenever the mode is not `full` or an archive exists.
- **Operations.** See the [runbook](../../runbooks/discovery-ledger.md).

## Throughput v3

Urgent hot films expiring within 24 hours precede other hot films; cold backfill runs only when no hot predictions remain. Each next request rechecks priority, so newly urgent films preempt reserved cold work. Each submission checkpoints independently, and persisted forecasts survive an interrupted index update. Writer leases serialize mutations; failures retain retry state with bounded backoff.

Run results expose batchSize, hotProcessed, coldProcessed, failed, hotRemaining, coldRemaining and a sanitized reason. Discovery readiness is reported at 100 hot EPG predictions, with target 200, independently of backlog completion.

The isolated benchmark start/trial routes store shadow results only, without overwriting production predictions. The offline benchmark compares JSON payload overhead and parsing at 4/8/12/20; it does not measure model latency, billed tokens or prediction quality. Multiple fingerprints per model call remain disabled until an actual model benchmark establishes comparable outputs.

## Controlled mood vocabulary v1

Mood presentation uses 28 stable canonical IDs. The original fingerprint/prediction JSON, hashes, generatedAt, rating, probability and immutable histories are unchanged. `/api/enrichment/view` exposes only canonical moodIds and Russian vocabulary labels; raw values are not UI options or card tags. Count each film once per canonical ID, combining fingerprint and prediction labels. Pure plot mechanics produce no mood option. Unknown labels remain diagnostic only.

`POST /api/enrichment/moods/backfill` takes a cursor and optional limit (server caps the R2 scan to 12 objects per invocation). Continue nextCursor until done; retries are idempotent. It reads all persisted film records, including films outside the watchlist, and saves derived mood-facet sidecars and view-index facets. Historical raw labels are included in sidecar historyMoodFacets. Source records are never rewritten. New submissions apply the same versioned mapping when writing the view index and sidecar. `GET /api/enrichment/moods/diagnostics` exposes raw-to-canonical mappings, unknown labels and canonical per-film counts. Mapping changes do not invalidate fingerprints or forecasts.

URL mood params contain canonical IDs (e.g. mood=dark&mood=military). Exact legacy Russian vocabulary labels migrate to IDs; unknown old values are ignored. OR within moods and AND across filters are preserved.

[AIR-47](../../evidence/taxonomy/air-47-taxonomy-audit.md) audits this vocabulary and does not change it. Mapping v1 stays in force until [AIR-108](https://trello.com/c/QIke4H2N) implements an accepted successor.
