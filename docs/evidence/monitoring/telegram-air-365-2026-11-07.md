# Monitor Telegram transport: offline evidence (AIR-365)

Captured 2026-11-07 (UTC) from the repository only. **No production read or write, no Cloudflare secret or setting, no Telegram call and no network call was made.** The token and chat id in the tests are fixtures, not credentials.

`tests/monitor-telegram.mjs` runs the monitor over an in-memory bucket with a fake `api.telegram.org` whose every answer is scripted. `tests/monitor-runtime.mjs` (the generic webhook) passes unchanged.

| Scenario | Result |
| --- | --- |
| Request shape | one `POST` to the fixed `https://api.telegram.org/bot<token>/sendMessage`; body keys `chat_id`, `text`, `disable_web_page_preview` only (no markup mode); a needs-owner alert delivered once and counted |
| Kinds | `ALERT`, `REMINDER`, `ESCALATION`, `RECOVERED` and `TEST` are told apart in the first line |
| Plain text | markup characters, control characters, non-ASCII and a newline inside a field cannot change the structure; the text stays far below 4096 characters |
| Failed answers | HTTP 200 with `ok:false`, 401, 403, a 500 with no body, malformed JSON, a network error and a timeout are each not a delivery: the message stays queued, `sendCount` and `lastSentAt` do not move, a fixed reason is recorded and the next tick delivers it |
| No leak | the state document, the status and every log line contain no token, chat id or Telegram description in any failure case, including an exception whose message names the URL |
| 429 | `retry_after` becomes a persisted hold; no request is made inside it, the status shows it, `test` answers `rate_limited`, the message is neither lost nor counted and the first tick after the hold delivers; the hold is capped at one hour, defaults to one minute and reads `Retry-After`; nothing sleeps |
| Fail-closed configuration | a missing or malformed token or chat id, a token with a path, an empty chat id and an invalid or unknown transport value send nothing to any channel, keep the alert queued and show `alerting: false`; a valid configuration afterwards delivers it |
| Transport choice | with the Telegram secrets present and no `MONITOR_TRANSPORT`, the generic webhook is used and Telegram is not; a chosen Telegram never falls back to the webhook |
| `off` and `dry` | `run()` makes no request and no write; `test()` is refused (`off` or `dry`) with no request and no bucket write, for Telegram and for the generic webhook (a regression the first review found) |
| AIR-349 semantics | thirty queued messages on a failing Telegram cost two attempts per tick, none is lost, failed heads rotate to the tail, and recovery drains five per tick; concurrent ticks send once; a pending recovery is superseded by a reoccurrence; the synthetic test claims its cooldown first, restores it on a failed delivery and two concurrent tests send once |
| Wiring | no token or chat id literal in the source, one fixed Bot API host, no inbound or polling method, nothing added to `wrangler.jsonc` |

Limitations: Telegram's real rate-limit behavior, latency and the owner's receipt are not observed. Telegram has no idempotency key, so a crash after Telegram accepted a message and before the state commit can repeat it; this is documented, not tested against Telegram. Activation stays with [AIR-349](https://trello.com/c/VUyampoh) and its owner gates.
