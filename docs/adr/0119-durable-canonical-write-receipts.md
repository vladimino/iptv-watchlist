# ADR 0119: Durable canonical write receipts for cross-domain operations (schema 19)

**Status:** Accepted as DESIGN for offline implementation only. Owner decisions 1 to 3 below are ACCEPTED (source: [PR #530 comment 6802553275](https://github.com/vladimino/iptv-watchlist/pull/530), 2026-11-11). This is not merge approval and not a production GO: migration 0019 stays unapplied.

## Context

[ADR 0117](0117-film-person-d1-handoff-owner-decisions.md) owner decision 5 requires that operations from EPG, Discovery, metadata and ratings into canonical Film/Person have durable receipts stored in the existing D1 (no new event platform), stable idempotency and request ids, bounded safe retries and a separate reconciliation of pending and failed operations; a periodic reconcile is only a safety net, and the absence of a record without a receipt is never safe. The fenced writers of P2a and P2b are idempotent by content and by the entity revision CAS, but they keep no durable record of a request: after a lost answer, the only evidence that a write landed is its content, and a change nobody recorded cannot be told from a safe one. The Controller reviews of those PRs state that content replay is not a substitute and that the receipt requirement cannot be waived. Schema 18 has no such table (`film_localization_source` carries a `request_id` for one writer only).

## Decision

1. **A table, `canonical_write_receipt`, in the existing D1, schema 19** (`migrations/0019_canonical_write_receipt.sql`). One row per cross-domain canonical operation, keyed by the stable request id: operation kind, origin, target (kind, id), the SHA-256 digest of the planned content, the planned and applied entity revision, the marker generation at plan time, state (`pending`, `applied`, `failed`, `unknown`, `abandoned`), attempts, `next_attempt_at`, a short lowercase error class, and timestamps. **No payload, title, name, message or personal data is stored**; the CHECK constraints admit identifiers and digests only.
2. **The marker fence in SQL.** Triggers allow an insert or update only while the marker is `d1`/`open`, and an insert only under the live generation. At `r2`, `prepared` and `held` the table stays empty or frozen and a producer cannot write it; reads are always allowed. The state machine is in SQL too: `pending` to any state; `failed` to `pending`, `applied` or `abandoned`; `unknown` to `pending`, `applied`, `failed` or `abandoned`; `applied` and `abandoned` are terminal; identity columns (id, operation, origin, target, digest, creation time) never change; the attempt counter moves only with a new attempt; rows are never deleted.
3. **The protocol** (`src/canonical-receipts.js`, dormant, unbundled, nothing imports it; `src/canonical-mutations.js` is wrapped, not edited): record `pending` (attempt 1) in a batch carrying the same fence head as every canonical mutation; run the writer's own fenced commit; mark `applied`. A definite rollback marks `failed`, a permanent refusal marks `abandoned`, any other outcome marks `unknown`; a `pending` receipt past its attempt window is treated as `unknown`.
4. **ATOMIC receipt and write is REQUIRED (accepted owner decision 1).** Every production adapter, in particular every new P3 producer, performs its canonical mutation AND the receipt's transition to `applied` in the SAME fenced D1 batch, with `appliedStatements()` placed after the revision bump: they commit together or not at all (no mutation without an applied receipt, no applied receipt without its mutation, whatever is lost: the response, the request, or the middle of the batch). A two-batch commit-then-mark path is **NOT approved for production adapters and NOT approved for P3**. In code, `defineOperation`, `operationRegistry` and `receiptedWrite` refuse (`receipt_atomic_required`) anything that is not `atomic:true`, before anything is read or written, unless it carries a named `exception` record (id, independent review, safety proof, owner acceptance id) whose id is in `APPROVED_EXCEPTIONS`; that list is empty, no operation has an exception today, and the separate-mark path survives only behind such an exception as a clearly named legacy mechanism, never as a default. Under `atomic` the module never second-marks: a writer that returns without the receipt applied leaves it `unknown` (`atomic_mark_missing`). Settling is by each request's OWN proof, never by content: the operation's `readback` returns `{digest, revision, proof}`; `proof: 'request'` (request-id evidence written inside the writer's own batch) at the revision this request landed at makes the receipt `applied`, even if the content was overwritten since; a digest equal to the planned one **without** that proof (another actor may independently reach identical content) is `content_match_unproven`: abandoned for review (`needsReview`), never applied, and the writer does not run again.
5. **Retries are never blind (stale revision).** A retry, direct or by the reconcile pass, reads the CURRENT canonical revision. Unchanged since planning, it runs. If an unrelated writer advanced it, the operation's `revalidate(env, receipt, {currentRevision, observed})` must answer `proceed` (the writer re-checked its preconditions and re-plans against `currentRevision`; `planned_revision` follows) or `superseded` (abandoned, `superseded_by_newer_revision`); with no `revalidate`, or any other answer, the receipt is abandoned for repair (`stale_revision_needs_repair`). The writer's own revision CAS stays the last guard. Newer content is never overwritten by default.
6. **Reconciliation** is a pure `reconcilePlan` plus one bounded pass (`reconcileReceipts`: at most 50 receipts, one target read each) that a later reconciler (P3) calls; this ADR schedules nothing: there is **no timer, cron or Scheduled Task**. Due times come from stored fields (`attempts`, `next_attempt_at`, `created_at`) against a clock the caller passes in.
7. **The historical baseline is PROVEN, RECORDED and VERIFIED; the receipt contract starts at an explicit boundary (accepted owner decision 2).** A freshly applied schema 19 is empty by design while `canonical_revision` may predate it. No `applied` receipt is ever fabricated for a historical write, and no pre-boundary revision is classified as a fault merely because the receipt table started empty. **Recording:** the activation operation of the owner-authorized `open` flip (under the same lease and window, once) calls `recordBaseline`: it reads `canonical_revision`, computes per kind (film, person) the count, the highest revision and the SHA-256 of the ordered (id, revision) pairs, and in ONE fenced batch first asserts in SQL that `canonical_revision` still has exactly that snapshot and that the marker is `d1`/`open` at the generation it read (a moved marker or a revision written in between fails the whole batch and records nothing), then inserts the watermark (that proof, the entries total and the boundary generation) and copies the rows into `canonical_receipt_baseline`. Both tables are insert-only, only fillable while `open` and before the first receipt, and a receipt cannot be inserted until the watermark exists; at most 5,000 entities are copied. **Verifying:** `verifyBaseline` recomputes the per-kind count, highest revision and digest and the entries total from the stored rows read-only and compares them with the watermark, checks that the boundary generation is not ahead of the marker and that no entity regressed below its baseline revision; it returns reasons rather than throwing. **Classification:** a revision at or below its baseline entry is `pre_receipt_baseline` (counted apart, not `unreceipted`). Any revision ABOVE the baseline without an applied receipt for it is `unreceipted` (`no_receipt`, or `receipt_not_applied` when a non-terminal receipt exists) and makes `readUnreceipted` non-clean (`safe` false), as does a baseline that does not verify: a post-boundary mutation cannot pass readiness without a genuine receipt. Writes outside the protocol after the boundary (owner tools, the P5 loader) are reported the same way until they register their own operation kind.
8. **Registration points.** `OPERATION_KINDS` is the closed, code-reviewed set (the SQL accepts any lowercase identifier); `defineOperation` takes the adopter's `readback`, `replay`, optional `revalidate` and `atomic`; `requestIdOf` derives the stable id from the origin, the operation and a digest of the source key. P2a and P2b writers and the P3 producers adopt it later; this change edits none of their files.
9. **No receipt table, no baseline, no canonical write.** `receiptedWrite` refuses with `receipt_schema_missing` when schema 19 is absent and `receipt_baseline_missing` when the baseline is not recorded, so a producer never writes canonical unreceipted.
10. **Append-only retention during stabilization (accepted owner decision 3).** `canonical_write_receipt` has no TTL, pruning, automatic cleanup or archival: rows are never deleted (a trigger refuses it), terminal rows are never rewritten, and no code path does either. `abandoned` stays visible for remediation: `listAttention` lists every abandoned and unknown receipt (flagging the classes that need a person: `content_match_unproven`, `atomic_mark_missing`, `stale_revision_needs_repair`, `superseded_by_newer_revision`). The 7-day abandon rule is about the state of an operation, not about deleting rows. Growth, query impact and cost must be measured; a separate owner retention/lifecycle decision returns later.

### Accepted decisions versus safe initial defaults

- **Accepted owner decisions** ([PR #530 comment 6802553275](https://github.com/vladimino/iptv-watchlist/pull/530), 2026-11-11): (1) atomic receipt and write is required, the separate-mark path is exception-gated legacy and not approved for P3; (2) the historical baseline is verified and an explicit generation boundary starts the new contract, with no fabricated receipts; (3) the table is append-only during initial stabilization (no TTL, pruning, cleanup or archival), with `abandoned` visible. Kept from the earlier review: a retry after a concurrent revision advance re-reads, replans and revalidates and never overwrites newer facts. None of this authorizes a merge or a production operation.
- **Safe initial defaults** (code constants, changed by code review, none measured against production volume, owner-reviewable): 5 attempts; backoff 60 s, 300 s, 1,800 s, 7,200 s (the last repeats); 2 min in-flight attempt window; abandonment of a receipt older than 7 days (operation state only); at most 50 receipts per reconcile pass; at most 5,000 baseline entities.
- **Not decided:** the durable retention and lifecycle policy of receipts; it returns as its own owner decision once growth and cost are measured.

## Alternatives considered

- **Digest equality as proof of applied:** rejected: two actors can reach identical content, and a later writer can overwrite it; only operation-specific evidence or the writer's own atomic batch proves a request's effect.
- **A replay that re-plans against the current revision unconditionally:** rejected: it would overwrite newer content; the writer must revalidate first.
- **A two-batch commit-then-mark as the general path:** rejected by the owner (decision 1); it survives only as an exception-gated legacy mechanism.
- **Fabricating receipts for history, or calling every pre-boundary revision a fault:** rejected (decision 2); a verified baseline and a boundary generation scope the contract.
- **Content replay only** (the P2a/P2b state): rejected by owner decision 5 and the Controller reviews; it cannot prove an operation's outcome nor detect a change that nobody recorded.
- **A receipt per writer, like `request_id` on `film_localization_source`:** one table per writer and no shared reconciliation; rejected for the cross-domain case. That column stays as it is.
- **A new event store or queue:** excluded by owner decision 5 (no new event platform).
- **A scheduled reconciler:** excluded; no new cron or Scheduled Task without a separate GO. The pass is a function a later, separately authorized caller may run.

## Consequences

- One more table. A new cross-domain write costs two extra batches (the pending insert and the applied mark; the mark is skipped when the writer appends `appliedStatements()` to its own batch) and eight reads (one availability check, five marker reads, two receipt reads), pinned by the offline test; an already applied request id costs no batch. The table grows by one row per operation; **pruning terminal rows is not decided here** (rows are never deleted) and needs its own decision before volume matters.
- A receipt left `pending` while the marker is `held` is frozen, not guessed; it settles after `held` returns to `open`. The forward-fix drill for `held` to `open` ([ADR 0117](0117-film-person-d1-handoff-owner-decisions.md) decision 3) must include a reconcile pass.
- The in-flight window means a crashed attempt blocks its request id for at most two minutes.
- Taking the activation baseline is a second, later step after the apply; until it is taken no receipt can be written, so P3 stays blocked on both.
- `scripts/film-person-capture.mjs` still expects schema 18; `SCHEMA_EXPECTED` must be updated in the apply operation.

## Recovery and migration boundary

The migration is introduced in code only. **Applying it to production D1 is NOT authorized by this ADR, this PR, a merge or a deploy: it needs a separate, explicit owner GO with its own read-only preflight and readback** (`SELECT version FROM schema_contract` is 19, zero rows in `canonical_write_receipt`, `canonical_receipt_watermark` and `canonical_receipt_baseline`, the marker unchanged), and the same operation updates `SCHEMA_EXPECTED` in `scripts/film-person-capture.mjs` (18 today); nothing in the repository or a deploy applies it, and applying it writes no row. Until it is applied no producer may be wired (P3 is blocked on it). A code rollback does not remove the table; because the table only records, an empty or ignored table changes no canonical state. No flag, schedule, marker move or production access is part of this decision.
