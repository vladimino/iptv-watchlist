# ADR 0122: Prediction batch runner v2 runs beside the v5 runner on one queue, one lease and one persistence path

## Context

Production predictions run through the v5 runner: `prediction_start`, then for every film `prediction_next` (one film), `prediction_validate`, `prediction_submit` (one film), then `prediction_complete` ([contract](../reference/api/prediction-runner.md)). The [AIR-438 evidence](../evidence/prediction/air-438-step-latency-and-batch-sizing-2026-11-11.md) established, from code and an offline profile, that:

- one film costs one `next`, one `validate` and one `submit` whatever the selection batch is (12 while capacity is unknown, at most 20);
- a `next` makes 31 fixed calls plus 2 per selected film, and a one-item `submit` is about half fixed cost, so sharing a `next` and a `submit` among several films is the throughput lever and raising the selection batch alone is not;
- observed cycles on 11 November 2026 were 70–130 s per film (28–49 films per active hour); the model's best case for 10 films per `next` and 10 per `submit` is 57–112 films per active hour, assumptions named, not an SLA;
- the model quality of a multi-film answer, production D1 costs per step and Cloudflare limits above a selection of 20 were not measured.

[AIR-441](https://trello.com/c/fiOKmCHJ) and [AIR-442](https://trello.com/c/j564oeLD) lower the cost of the legacy `next` and `submit`. They do not replace the one-film protocol, which also sends the whole taste profile (about 12.5 KB of text) with every `next`, requires a separate MCP `prediction_validate` call per film, and re-reads the run state per film.

The owner's constraints for the replacement, recorded on the card: one `batch_start` returns a compact manifest of up to **100** eligible films with everything needed to generate them; one scheduled execution handles at most **100** films; generation starts at **10** films, `batch_submit` takes up to **10**; the best generation size (1–10) is chosen by an A/B run; the next hourly execution starts from a clean context; queue, lease, heartbeat and D1/R2 persistence stay shared; the legacy protocol and Task keep working in parallel; no new feature flag.

## Decision

Introduce a **batch runner v2** protocol as an additive second client of the existing prediction machinery. Nothing below is built, deployed or authorized by this ADR.

1. **Two protocols, one machine.** v2 adds `batch_start` and `batch_submit` (HTTP `POST /api/enrichment/batch/start` and `/batch/submit`; MCP `prediction_batch_start` and `prediction_batch_submit`). `heartbeat` and `complete` are shared. The v5 routes and tools are unchanged. A run records `protocol: "v5"` (absent on old records) or `"batch_v2"`; `next`/`submit` refuse a v2 run and `batch_submit` refuses a v5 run with `409 {code: "wrong_protocol"}`, writing nothing. The queue, the runner lease (one 15-minute lease, one holder), `already_running`, retry records, backoff, the fingerprint and prediction storage, the immutable bodies and the D1/R2 write order are the existing ones. A v2 run is a run: it appears in status, run diagnostics and Events like any other.
2. **Manifest.** `batch_start` takes the lease, selects once, and returns one compact manifest of at most **100** films (`maxManifestFilms`) and at most `maxManifestBytes` of compact JSON, whichever binds first (the byte budget is decided in D1 below; a manifest shorter than 100 films is complete, not an error, and carries `truncated: {reason, eligibleRemaining}`). It holds: `run` identity and lease (`runId`, `leaseExpiresAt`, `leaseTtlMs`, `fence`); the **Taste Profile** body, `version`, `hash` and `lineage`; the **contract** (fingerprint schema and its version, prompt versions, registry digest, validation contract version and the schema the Worker validates with); and per film: the full `modelMetadata`, `lane` (`hot` or `cold`, decided when the manifest is formed), and a `plan` of `fingerprint_and_prediction` or `prediction_only` (for the latter the stored valid fingerprint object and its hash). The caller needs no `next`, no further metadata call and no cache in ChatGPT between executions or within one.
3. **Selection at manifest time.** Order and lane follow the existing rule (hot first; cold only while no hot film is outstanding, minus films held by a future `retryAt`), evaluated once at `batch_start`. A hot film that arrives during the execution waits for the next hourly execution (at most one hour); `batch_submit` reports `hotArrived` as information only.
4. **Execution shape.** At most 100 films per scheduled execution (the run's `delivered` count, also enforced by the Worker: a second `batch_start` for a running run is `already_running`; it never re-delivers a manifest). The caller generates in groups of `generationSize` (initial 10, A/B-selectable 1–10) and submits each group with one `batch_submit` of **1–10** items (`submitMaxItems`), then repeats, then `complete`. Generation and submit sizes are client choices inside Worker caps and are echoed in the manifest as `limits`; the Worker has no server-side generation size.
5. **Server-side per-film validation.** `batch_submit` validates every item with the same validators and issue codes as `prediction_submit`, with no MCP preflight. `prediction_validate` stays available and optional. A result is one of `created`, `recalculated`, `already_current`, `validation_error` (the retryable item failure with `validation {stage, reportedBy, issues[{path, code}]}`), `stale_profile`, `not_in_manifest`, `deferred_budget` and `conflict` (see the reference). The call is **partial success by design**: HTTP 200 with per-item results, and a non-200 only for a whole-call fence (`lease_lost`, `contract_changed`, `wrong_protocol`, unknown run, `prediction_catalog_held`, storage failure, `413`).
6. **Idempotent replay.** An item is identified by `(runId, filmId, contentSha256)` where the hash is over its canonical submitted objects. A replay of an identical item answers its recorded outcome (`already_current` with `replayed: true`) and writes nothing; a different payload for a film this run already settled answers `conflict` and writes nothing. A whole `batch_submit` can be repeated after a lost response.
7. **Lease fencing.** Every `batch_submit` carries `runId` and the `fence` returned by the last call; the Worker checks the lease holder, expiry and fence before the first film and renews the lease with each call, and every film write is conditional on the same lease (the existing `beforeWrite` renewal). An expired or replaced owner gets `409 lease_lost` and writes nothing. `fence` is the existing D1 lease row token (or object etag in `r2` mode), not a new store.
8. **Bounded failure.** A `batch_submit` has a per-call wall budget (`callBudgetMs`, initial 25 s, D1 below): items are processed in order and, if the budget is spent, the unprocessed remainder is returned as `deferred_budget` with no write; the caller resubmits them. A call is limited to 10 items and to the MCP inbound limit of **64 KiB**; a larger body is rejected `413` by the transport before any processing, and the caller halves the group. The queue is advanced **once per call** (one `batch_progress` conditional write for every settled film), not once per film. The existing retry policy (1-hour exponential backoff, maximum 6 hours) and `format_error_storm` (five consecutive distinct format failures) are unchanged and count items, not calls.
9. **Profile change.** `batch_submit` never answers a bare profile mismatch as a validation error. When the current profile differs from the run's, the call is evaluated by the **existing impact evaluator** ([profile impact](../reference/domain/prediction-compatibility.md), [ADR 0031](0031-selective-prediction-profile-compatibility.md), [ADR 0044](0044-retire-profile-compatibility-switch.md)): the response carries `profile {changed, from, to, scope: "global"|"selective"}` and each item `compatibility: "compatible"|"impacted"|"unknown"`. `compatible` items are written (their stored identity is the profile they were generated with, and freshness is decided by the existing selective rule, so nothing unaffected is recalculated); `impacted` and `unknown` items are returned `stale_profile` and written nowhere, with no retry record and no count towards `format_error_storm`. With `scope: "global"` the response says `action: "complete"`; with `selective` the caller may continue with the manifest films the response lists as `compatible`. Films never recalculated because they are `compatible` are not regenerated by the next execution either.
10. **Dry run.** `batch_start` and `batch_submit` take `dryRun: true`. A dry run runs the same selection and validation read-only: no lease, no run record, no run Event or diagnostics row, no queue, prediction, fingerprint, view-index or `sources` write, no D1/R2 writer. `batch_start` accepts `pin {filmIds}` so the same films can be replayed at generation sizes 1 to 10; a pinned film that is no longer eligible is reported `not_eligible` and not replaced. `batch_submit` returns what it would have answered, plus the validation issues, and stores nothing. A dry run may coexist with a live run (it takes nothing). Where the comparison inputs and outputs of an A/B are kept is **not decided** (D2); the Worker writes none.
11. **Dual protocol and Task selection, no new flag.** The Worker exposes v2 additively; `enrichment_runner` publishes a `batchRunner {version: 2, ...}` capability block and leaves `pipelineVersion: 5` and `modelBatching` as they are for v5 callers. Which hourly Task is active is an owner action on the Task registry: exactly one hourly Predictions Task is enabled at a time (legacy v5 or Task v2). Overlap of two executions, in either protocol, is `already_running` with a stop and no adoption. There is no feature flag and no shadow mode switch; an unused route is inert and writes only when an authorized caller invokes it.
12. **Observation.** `batch_start` and `batch_submit` write the existing log-only `prediction_step_timing` line with `step` of `batch_start` or `batch_submit` and the same whitelisted counters (`items`, `created`, `recalculated`, `alreadyCurrent`, `failures`, `deferredBudget`, `staleProfile`, `manifestFilms`, `manifestBytes`). Monitoring, run diagnostics and the Events footer are unchanged and show a v2 run as a run.
13. **Authority.** No data migration: records, queue, immutable bodies, leases and D1 authority markers keep their shape; a v2 run adds only the `protocol` field and the counts above to the run record, which readers that do not know it ignore. D1 stays the owner of mutable prediction state and R2 of the immutable bodies.

**Not decided here** (open, listed under Open decisions): the manifest byte budget, the `callBudgetMs`, the optimal generation size, the place of A/B results, whether one repair resubmit per film is allowed, and every production operation.

## Alternatives considered

- **Keep v5 and expose larger `next` and `submit` batches** (`next.batchSize` up to 20, `submit` up to 10 items, as the HTTP routes already allow and as the [AIR-438 recommendation](../evidence/prediction/air-438-step-latency-and-batch-sizing-2026-11-11.md#7-recommendation) 4(b) names). Rejected as the target because every `next` still re-reads the whole profile and re-selects, selection above 20 is refused and each selected film adds two reads to every `next`, `submit` still advances the queue once per call and per film item, a separate validate call per film stays, and a change to a shared v5 contract would alter the live Task prompt for the one protocol that must stay unchanged. It remains the fallback if v2 is rejected.
- **One manifest page per `next`-style call (paginated manifest).** Not recorded as discussed by the owner. Rejected: the card asks for one `batch_start`, and pagination returns `next`-like round trips and a profile or contract refetch.
- **ChatGPT-side cache of metadata or profile between executions.** Rejected by the card (no persistent cache in ChatGPT; the next execution starts clean).
- **A feature flag to select the protocol.** Rejected by the card (no new feature flag); Task selection replaces it. A flag would also add a registered binding with its own contract.
- **The Worker generates predictions (a model call from the Worker).** Not discussed on the card; rejected here because it changes the trust boundary and the model credential location that [ADR 0005](0005-external-chatgpt-tasks.md) and the MCP boundary ([ADR 0004](0004-mcp-access-boundary.md)) keep outside the Worker.
- **Raise the MCP 64 KiB inbound body limit.** Not recommended here: the limit is a transport safety boundary ([MCP reference](../reference/api/mcp.md#transport)); the contract bounds the item count and tells the caller to split. Raising it needs its own security decision.
- **A server-side validation-only batch call (preflight in bulk).** Rejected: `batch_submit` validates per film anyway and a second call per group reintroduces the handshake the card removes.

## Consequences

- **Fewer, larger calls.** Per execution of 100 films: one start, ten generate-and-submit pairs, one complete (12 Worker calls instead of about 300 per execution on v5). The profile and contract cross the wire once instead of once per film. Throughput is not promised: the [AIR-438 model](../evidence/prediction/air-438-step-latency-and-batch-sizing-2026-11-11.md#5-throughput-model-assumptions-named-not-measured) gives 57–112 films per active hour for 10/10 under named assumptions, and model quality at 10 films per answer is unknown (D6).
- **Larger responses and a heavier start.** The manifest of up to 100 films is the largest answer the runner has produced (estimate 100–450 KiB, [analysis](../evidence/prediction/air-446-batch-runner-limits-2026-11-12.md)). It reads 100 films' state in one invocation (about 200 reads plus the by-id catalog read in chunks of 80), within the documented 10,000 subrequest default and the 30 s CPU default, but production wall and CPU are unmeasured. If D1 is not resolved by measurement, the manifest count shrinks, not the contract.
- **Context-window risk.** 100 manifest films plus generation outputs may not fit one model context; the byte cap (D1) and the 10-film generation groups bound it. A caller that loses its context loses only unsubmitted work, which stays in the queue.
- **A coarser checkpoint.** A crash loses at most the films generated since the last `batch_submit`, at most `generationSize` films, and nothing the Worker already settled.
- **More states in a response** (`stale_profile`, `deferred_budget`, `conflict`) and a second protocol to document, test and retire. The v5 code stays until a separate cleanup card.
- **Cross-protocol guard.** A run belongs to one protocol; a client that mixes calls gets `wrong_protocol`, never a half-applied step.
- **Compatibility.** Records, the retry policy, hot-first selection and the validation contract do not change; old run records without `protocol` are v5.

## Recovery and migration boundary

- **Reversible.** Rollback is: disable the v2 Task and re-enable the v5 Task (owner action on the Task registry), and revert the v2 routes by an ordinary code rollback. A v2 run that stopped mid-way expires by lease like any run; its unsubmitted films never left the queue; its settled films stay settled and valid. There is no data migration, so none is reversed. Rolling the code back does not roll back D1, R2, flags, Access or Task schedules.
- **Owner approval is separate for** each production operation: deploying the v2 code, any dry run that spends model quota or reads production, enabling or editing a Scheduled Task prompt, the first natural v2 run, the A/B, and the switch of the active Task. The Product Owner decision on this ADR is a gate for Accepted, not production GO. This ADR authorizes no operation.
- **Plan (separate cards, no data migration):** manifest builder; `batch_submit` with validation, fencing, replay and profile handling; Task v2 prompt (proposed text only until the owner enables it); dry-run A/B; cutover (owner-approved holdpoints and the v5 Task disabled); cleanup of the v5 code after stabilization. Each step stays offline and tested before any production use.
