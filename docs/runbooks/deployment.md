## Proportionate post-deploy acceptance

For a documentation-only PR with no runtime or configuration changes, **every** required GitHub Actions job succeeding and one safe MCP `probe_read` are sufficient operational acceptance unless the card explicitly changes a contract that needs a targeted read. Do not trigger EPG, discovery, predictions, TMDB, imports or full storage parity as a deployment smoke test. A release touching a runtime API or persisted projection gets the **smallest matching safe readback** for that scope, rather than a blanket bucket snapshot, manual replay or speculative incident checklist. Keep all post-merge jobs and report their actual conclusions: they are delivery guarantees, not permission to operate production data writers. [Risk-proportional policy](../process/agent-workflow.md#risk-proportional-operational-safeguards).

## EPG commit memory

The daily commit reads the active discovery ledger as bytes when the stored object provides a body or text, folds one candidate at a time, and puts one generation document. The document is pulled one chunk at a time. The put is a fixed-length stream of the UTF-8 length counted on the decision walk. A length mismatch stops before the published pin moves. The copy onto the stable keys uses each stored object's size and does not buffer the body as text. It does not raise the isolate limit, and it does not delete candidates. When the published EPG authority already names a programme run, the commit stops if that run's ledger cannot be read, or if the copy it would use names a different run. The latest scan is not published over that gap. The published pin and the archive pointer stay where they are. A commit that the platform kills for memory leaves the published generation and the D1 pin unchanged when the kill happens before those writes. Retry that same sync run after the discovery lease expires. The lease TTL is 90 seconds. Starting a new sync replaces the run record. Resetting the lease or removing ledger objects is not a memory remedy.

Node measurements of this path are not the isolate limit. The dated synthetic reading and its limits are in [the 3 November memory evidence](../evidence/epg-commit-memory-2026-11-03.md). A separate workerd reading of the fixed-length put is in [the 3 November R2 length evidence](../evidence/epg-r2-known-length-2026-11-03.md). Neither applies an isolate memory cap, and a green deploy does not by itself show that a live commit will stay under the limit.

## Moving a pipeline to a Cloudflare executor

This is the operator sequence of the shared reliability contract ([ADR 0089](../adr/0089-shared-orchestration-reliability-contract.md), Accepted; [reference](../reference/orchestration-reliability.md#rollout-and-rollback)). It applies to EPG publication, Discovery and Ratings one domain at a time; Predictions stay on the hourly ChatGPT task. No step is part of deployment. This is a **high-impact L3** producer ownership transition: the Product Owner approves an explicit bounded domain-specific plan with its holdpoints. One plan can include preflight, readbacks and staged commands; it does not remove the required verified drain and fencing or authorize unrelated task changes.

1. **Inert code.** The executor, its `ensure`, the read model and the tests are merged and deployed with the domain mode `external`. `Test and build`, `Test shard 2 of 3`, `Test shard 3 of 3` and `Deploy to Cloudflare` completed with success on the exact merge SHA. Verify with the domain's read-only status route that `orchestration.mode` is `external` and no Cloudflare owner is live. Nothing else is called.
2. **Close admission, drain, complete.** Each is a separate **verified state transition** for this domain, executed only within the approved L3 plan and its stated holdpoints. First close admission (`mode: switching`, new `epoch`); read it back. Then wait for the read model's `drain` to report `verified` (old lease absent or expired with margin over the longest step, old Workflow instance finished or absent, domain lease released). Only then complete the switch to `cloudflare` and read it back. Until completion both paths answer `switch_in_progress`; afterwards the external tool path answers `external_writer_fenced`. Do not test either with a write. An unverifiable drain is not completed.
3. **Acceptance.** Observe at least one complete run through the read model: `health` `healthy` or `idle`, `lastDurableProgressAt` advancing, no `quarantine`. Do not trigger a run to speed this up unless that run has its own GO.
4. **Retire the task path.** When the approved L3 plan authorizes the task-registry step and its holdpoint is satisfied, change the ChatGPT task registry so the task no longer drives this domain, and read the registry back. The hourly task keeps Predictions.

**Rollback.** The same three state transitions in the other direction, within an expressly approved rollback plan and its holdpoints: close admission (the epoch increases and the running instance's D1 commits are refused), verified drain, complete the switch back to `external`. Only then, when separately included in the approved rollback plan and after the required holdpoint, re-enable the ChatGPT task path. A code rollback alone leaves the mode, the data, the cron trigger and the task registry as they were.

**Quarantine.** `quarantined` with reason `budget_exhausted` ends only the current run key; the next run key retries by itself. Any other quarantine reason is `unsafe` and stays until an explicitly approved, reason-specific recovery action; L0 diagnosis alone is not permission to clear. Read the `failure` fingerprint and the domain's checkpoint first; clearing never resets a lease or forces a step.

## EPG diagnostic canary foundation (AIR-453, inert)

`src/epg-diagnostic.js` is bundled (so the Worker deploys with it) and referenced by nothing at runtime; `wrangler.jsonc` has no diagnostic binding, resource or migration directory, so a deploy needs, creates and applies nothing for it. Production routes are unaffected whether or not the diagnostic resources exist. Provisioning (a separate R2 bucket, a separate D1 with the production chain plus `diagnostic-migrations/0001`, the identity via `EpgDiagnostic.provision`, the Workflow binding) is the operation of AIR-456 and needs its own owner GO; so does every diagnostic invocation. Code rollback is a revert and removes nothing from a provisioned diagnostic bucket or database.

**AIR-455 (the Workflow).** `wrangler.jsonc` now declares the Workflow `iptv-epg-diagnostic` (`EPG_DIAGNOSTIC_WORKFLOW`, class `EpgDiagnosticWorkflow`): a deploy creates the Workflow definition and no instance, and the diagnostic D1, bucket and resource id are still not bound, so the routes `/api/epg/diagnostic/*` answer `diagnostic_bindings_absent`. Check after a deploy that `GET /api/epg/diagnostic/preflight` (a read) says `diagnostic_bindings_absent` and that the EPG, Discovery, Ratings and Predictions behave as before. Rollback is a revert of the code; it does not stop a running diagnostic instance or delete a provisioned diagnostic resource ([runbook](epg-diagnostic-canary.md#rollback)).

## Ratings executor switch (AIR-347)

The Ratings owner switch is a high-impact L3 operation requiring an owner-approved scoped plan and all explicit holdpoints. The state transitions remain separate, but safe preflight/readback inside the plan do not require repeated owner prompts: (1) `close_admission` with target `cloudflare` (epoch+1, both writers refused); (2) verify the drain, then `complete`; (3) disable the external Ratings Task. Rollback is the same protocol with target `external`. The switch needs D1 ratings authority open; with a held or non-`d1` marker it is refused and writes nothing. `ratings_storage_migrate apply` is refused while the mode is not `external`. Code deploy and Workflow resource creation start nothing. `clear_quarantine` runs no step.

## A Discovery Workflow instance that errors (AIR-360)

Read-only: `epg_pipeline_status` (`discoveryExecutor`), the instance steps in Cloudflare (`owner`, `plan` and `chunk` step outputs and attempts) and the Worker log line `discovery_workflow_step_failed`, which carries the bounded cause and the statement count of the instance. A step failure that the instance recognises as transient (`discovery_unavailable` or a transient class) is recovered by the instance itself at `recovery.dueAt` ([ADR 0098](../adr/0098-discovery-workflow-step-failure-recovery.md)); its record reads `stopped` with reason `step_failure` while the instance sleeps. An instance that errors for any other reason, is killed by the platform, or fails to arm is replaced by the hourly cron through `recovery.dueAt`; do not start, terminate or reset anything by hand without an owner decision. An instance that ends near 6,000 statements is the planned handover ([ADR 0094](../adr/0094-discovery-workflow-invocation-budget.md)), not an error.
