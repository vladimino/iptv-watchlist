# Letterboxd ratings — retired refresh, EPG ratings and the separate pipeline

[AIR-64](https://trello.com/c/WTnyO8bX) added an owner-triggered ratings-only refresh behind `RATINGS_REFRESH`. [AIR-92](https://trello.com/c/yP6I0sjp) retired it ([ADR 0040](../../adr/0040-retire-ratings-only-refresh.md)) after the [AIR-85](https://trello.com/c/NVS7Ywdq) preflight found the public films list answering HTTP 403 with an anti-bot page on page 2. This path never tried to get past that challenge, and no replacement scraper exists.

## What answers now

`POST /api/enrichment/ratings/refresh` answers `410 Gone` with `{"error":"gone","detail":"…"}` for every method, body and value of `RATINGS_REFRESH`. The Worker returns before it parses the body: no Letterboxd request, no lease, no bucket read, list or write. Nothing in the Worker reads `RATINGS_REFRESH` any more; the `feature_flags` readout lists it as retired so a stale binding stays visible ([feature flags](../feature-flags.md)).

`GET /api/enrichment/ratings/status` still only reads. It returns the stored `enrichment/ratings/status.json` (or an `idle` placeholder when none exists) with `generationId` and `pendingGenerationId` resolved from `enrichment/ratings/published.json` and `enrichment/ratings/pending.json`, and always `enabled: false`. The fields keep their AIR-64 meaning: `state` is `idle`, `healthy`, `degraded` or `blocked`; `lastSuccessAt` is the last complete films list the retired refresh read; `attempt` is its last call. No code path writes these objects any more, so the values are the last ones the refresh wrote.

The integration footer does not use this document for current ratings health; that comes from the EPG commit fields in `sync.json` ([enrichment API](../api/enrichment.md)). The footer only reports the document as the `retiredRefresh` history of the `letterboxd_ratings` source, labelled in the UI as the retired separate refresh with its last attempt time and outcome. `manualRefreshEnabled` on that source is always `false`.

## Where ratings come from

- **Ratings run, Diary page 1** ([ADR 0054](../../adr/0054-diary-first-epg-ratings.md), [ADR 0067](../../adr/0067-diary-recent-window.md), [ADR 0074](../../adr/0074-retire-ratings-pipeline-switch.md), [ADR 0075](../../adr/0075-retire-letterboxd-diary-history-switch.md)).
  - On supported [storage](#storage-schema-guard), the [diary history stage](letterboxd-diary-history.md#rating-facts) runs on the ratings run and turns each film on page 1 into a watched fact. Where the diary proves one, it also writes a rating fact, observed at the watched date. `LETTERBOXD_DIARY_HISTORY` is retired and does not select this.
  - The EPG commit does not read Diary. The public films list is not requested after a commit.
  - A blocked or failed diary ends the ratings run `error` and leaves every stored rating in place.
  - Attempts written while Diary still ran inside the commit are described under [Ratings attempt](#ratings-attempt). That marker is not written by the current commit.
- The per-film lookup and the owner `PUT /api/enrichment/actual-ratings` write single ratings through the fact records ([user facts contract](letterboxd-user-facts.md)); no switch selects a legacy writer ([ADR 0055](../../adr/0055-retire-letterboxd-facts-switch.md)).
- A watchlist removal event still receives a half-star rating when the per-film lookup records one.
- A historical removal event receives an already stored half-star when a ratings removal step links a rated legacy entry of that exact film id ([ADR 0071](../../adr/0071-legacy-removal-event-link.md)). The removal is not itself a viewing, and a missing rating is not invented.
- The Worker does not scan the public films list and has no diary or baseline repair path; the EPG commit requests nothing from Letterboxd. A stored films-list summary remains the floor of later observations.

## Ratings attempt

[AIR-270](https://trello.com/c/DJ6Jvg4F). The ratings work after an EPG commit carries a durable marker, `sync.json` `ratingAttempt`, also returned by the sync status:

| Field | Meaning |
| --- | --- |
| `id`, `startedAt` | One attempt per commit that still has `ratingPending` |
| `phase`, `at` | The phase entered last and when, on attempts this commit used to write: `post_commit` (saved with `stage: complete`, covers the prediction queue refresh), `diary`, `removal_lookup`. Attempts written before ADR 0054 may name `films_list` or `repair`. The current commit does not open this marker |
| `state` | `started` (work in progress), `finished`, `error` or `unknown`. Historical `finished` with `source: letterboxd_diary` means the diary page was read (`recent_window`). Historical `finished` with `source: none` and `cause: diary_off` means the old gate was off. `error`: the diary ended `blocked`, `rate_limited` or `failed`. `unknown`: closed after an interruption. The current ratings run records its own outcome on `letterboxd/ratings/run.json`, not here |
| `source` | Historical: `letterboxd_diary`, or `none` when the old diary gate was off |
| `finishedAt`, `closedAt`, `cause`, `interruptedPhase` | End of a finished or failed attempt; for `unknown`, when it was closed and the phase it died in |

Each phase is saved before its work starts and logged as `{"event":"epg_ratings_phase","runId",…,"phase"}`, so Workers Observability shows the last phase before an `exceededMemory` or time-limit end of the request.

**Recovery.** A later `/api/sync/epg` step on the completed run, before the discovery continuation, closes an attempt that is still `started` and whose last phase is older than five minutes (or, for a run written before this marker, `ratingPending` on a run updated more than five minutes ago): `state: unknown`, `cause: interrupted`, `interruptedPhase`, `ratingError` "Ratings step interrupted during <phase>; no outcome recorded" and `ratingPending` removed. It never reads the diary again, writes no programme, generation or event, and leaves a finished or failed attempt alone; further steps change nothing. The EPG commit does not read Diary ([ADR 0074](../../adr/0074-retire-ratings-pipeline-switch.md)). A later ratings run reads page 1; its history and facts writes are idempotent. An interruption is reported as a failure, never as a success.

## Removed films

**Shared upstream cooldown (AIR-604, dormant at `off`).** Before each removal lookup claim the phase reads the shared `letterboxd` cooldown ([contract](upstream-cooldown.md)). An enforced active cooldown claims nothing and charges no attempt: the queue pause becomes `max(pausedUntil, until_at)` (`pausedBy: upstream_cooldown`) and `lookup.stoppedBy` is `upstream_cooldown`; the run outcome comes from the Diary part, so this is neither a failure nor a quarantine charge. A 403, 429 or challenge of a sent lookup writes the cooldown. The Diary page reads the same cooldown and reports its existing non-charging `rate_limited` outcome.

`REMOVAL_RATING_LOOKUP` is retired ([ADR 0077](../../adr/0077-retire-removal-rating-lookup-switch.md), [ADR 0043](../../adr/0043-removal-rating-lookup-queue.md), [AIR-268](https://trello.com/c/7ePpEYev)). A removal event no longer waits for a complete films list. On supported storage the ratings run looks up removed films the Diary did not rate. A confirmed stored rating for a film the current Diary page did not list is not requested, including when a new reference reopens the entry. A film that page lists without a rating is still looked up. A null or absent rating is not watched. The binding does not select that lookup. The EPG commit does not ([ADR 0074](../../adr/0074-retire-ratings-pipeline-switch.md)): it only enqueues references on supported storage. Films the Diary rated get that rating on the removal event during the ratings run. A blocked Diary leaves those films to the lookup, and the run still ends `error` with the Diary cause:

- **Queue.** `enrichment/removal-rating-lookups.json` keeps one entry per film id: `url`, `state` (`pending`, `rated`, `not_rated`, `not_found`, `conflict`, `gave_up`), `attempts`, `enqueuedAt`, `nextAttemptAt`, `lastAttemptAt`, `lastResult`, `lastError`, and `rating` once found. A film already in the queue is not added again. A pending film is not dropped by the cap: after 14 days it becomes `expired` (no more requests). An `expired` entry is deleted 28 days after `enqueuedAt`, other finished entries after 14 days, and at most 100 non-pending entries, `expired` ones included, are kept; the cap never removes a pending film. A film removed again while its entry is still stored gains no new entry, so the second removal event is not queued. Every write is a compare-and-swap. These are the version 1 rules; on supported storage the queue follows [version 2](#removal-queue-version-2), keyed by removal event, and the ratings run is the only writer.
- **Bounded requests.** One call requests the member page `/<user>/film/<slug>/` of at most five due films, oldest first; the others stay pending for the next call. The attempt is recorded before the request, so a request killed mid-lookup counts the attempt and retries no sooner than an hour later. A film gets at most three attempts in all.
- **Outcomes.** A rating found goes through the existing per-film path (fact record, `actual.json`, `ratings_view` projection, removal event with `ratingObservedAt`); the first confirmed rating on an event is never replaced. A page without the owner's rating is retried after 24 hours and becomes final `not_rated` after the third attempt; it never marks the film watched. A 404 is final `not_found`.
- **Upstream blocks.** A 403 or 429 stops the batch at once, no request is repeated, and the whole queue waits six hours (`pausedUntil`, `pausedBy`) because the block is about the source, not the film. A network or 5xx error retries that film after an hour.
- **Independence.** The lookup runs inside the ratings step, not the EPG commit. An error stays on that step. A film left pending is retried on a later ratings step. A summary stored on an older `sync.json` as `removalRatingLookup` is not written by the commit.
- **Recovery.** A hand-over left on `sync.json` (`removalRefs` or `removalLookups`) stays there while storage is unsupported. Once storage is supported, the next `/api/sync/epg` step on that run, or the next `beginSync`, enqueues it and requests nothing from Letterboxd. There is no lookup replay on the commit.

## Separate ratings pipeline

[ADR 0060](../../adr/0060-independent-letterboxd-ratings-pipeline.md) and [ADR 0074](../../adr/0074-retire-ratings-pipeline-switch.md). Code: [`src/letterboxd-ratings.js`](../../../src/letterboxd-ratings.js). `RATINGS_PIPELINE` is retired and unread ([feature flags](../feature-flags.md)). Tools and routes: [MCP reference](../api/mcp.md#ratings-tools). Operation: [runbook](../../runbooks/letterboxd-diary-history.md#separate-ratings-pipeline).

**When it acts.** On supported [storage](#storage-schema-guard), for every value of the retired binding, including absence. Otherwise:

- the EPG commit publishes and fails closed: no Diary read, no member-page lookup, no enqueue, no conversion. It still writes the removal event and stores `removalRefs` on `sync.json`. A later blocked commit keeps the earlier references and appends its own. `ratings_sync_status` is unchanged by that, and `sync.json` and the reply carry `ratingsPipeline: blocked` and `ratingsStorage: unsupported`;
- no ratings run can start: the Ratings phase of the Letterboxd Sync reports `storage_unsupported` and writes nothing;
- `ratings_sync_status` still reads, with `switch: separate` and `pipeline: blocked`.

`switch: separate` is the permanent mode. It does not prove the binding is absent. `feature_flags` does.

### The EPG commit under the separate pipeline

- **No ratings work.** The commit makes no Diary or member-page request, writes no `ratingPending`, `ratingAttempt`, `diaryHistory` or `removalRatingLookup`, and its reply and `sync.json` carry `ratingsPipeline: separate`.
- **Stored ratings at publication.** Before the watchlist event is written, the removed films that have no rating yet are probed (at most 25 films) for a confirmed rating **already stored** in the fact store, through `LetterboxdFacts.confirmedFilmRating` (the fact-precedence winner of ADR 0077, one read of the link index and the films-list floor and one record read per film). A rating found is put on the film in the event at its first display. This reads stored facts only: no Diary, no member-page or other Letterboxd request, no wait, and the publication never depends on it. A film with no fact, a null rating, a film beyond the 25 or a failed read stays unrated and the event is written as it was (`removalPublication` on `sync.json` records `probed`, `rated`, `ms`, the wall time of these reads alone, and `failed`). A rating already on a stored event is never replaced by this probe. A rating that is not stored yet arrives later through the queue and `settleRemovalRefs` on the same event key and time, as before.
- **Durable enqueue.** The films the watchlist diff removed are remembered on the run at scan time and, when the run completes, saved as `removalRefs {ref, films}`: `ref` names the removal event (`eventKey`, `sourceRunId`, `at`) at the completion time, which is the event's key ([AIR-513](https://trello.com/c/Ktfi8lRR)). Once the run is complete **and** the journal object exists they are added to the queue as references and `removalRefs` is cleared. A failed event put leaves the hand-over on the run. The retired binding is not read, and the enqueue never requests anything.
- **Recovery.** If the request dies between saving `sync.json` and the queue write, the next `/api/sync/epg` step on that run, or the next `beginSync`, adds the saved references. A replay of the same event adds nothing. While storage is unsupported the same `removalRefs` value stays on `sync.json` and is not enqueued; one value is `{ref, films}`, and consecutive blocked commits store a list of those. The next start or step on supported storage enqueues every one. A version 1 hand-over still in `sync.json` (`removalLookups`) is enqueued the same way: films the saved watchlist event removed get that event as their reference, others become legacy entries.

### Run record — `letterboxd/ratings/run.json`

One record holds the running or the last run, written only by compare-and-swap.

| Field | Meaning |
| --- | --- |
| `runId`, `trigger`, `startedAt`, `lastStartAt` | The run and how it started (`scheduled` or `manual`). `lastStartAt` is the same instant as `startedAt` on this record and is not a gate between starts |
| `state` | `running`, `finished`, `error` (the Diary ended `blocked`, `rate_limited` or `failed`; `cause` names it) or `unknown` (closed after an interruption) |
| `phase` | `diary`, `removal`, then `done` |
| `lease` | `{step, expiresAt}`: the id of the step that owns the record and its expiry, three minutes after the step began |
| `checkpoint` | `diaryPagesRead`, `diaryNextPage`, `diaryMode`, `removalChecked`, `legacyPagesLinked`: this run's counters. The Diary cursor and the queue are the authority; the checkpoint never plans another run's read. `legacyPagesLinked` counts event-list pages saved for a rated legacy entry ([ADR 0071](../../adr/0071-legacy-removal-event-link.md)). An absent value compares as 0, so a run stored before the field still matches a new run that linked no page; 0 does not match 1. Other checkpoint fields still treat absence as null |
| `pinned` | At start: the published `programmeRunId` and the number of pending queue entries |
| `diary`, `removal` | Summaries: outcome, stop reason, pages, counts (including `overflowSuspected`), `historicalCoverage` (`incomplete` after a page-1 write), facts and queue entries resolved by the Diary; references settled (`written`, `resolved`, `waiting` for a missing event, `mismatched`, `left`) and lookups (`checked`, `rated`, `notRated`, `failed`, `refused`, `stoppedBy`, `pausedUntil`) |
| `outcome`, `cause`, `interruptedPhase`, `finishedAt`, `closedAt` | End of the run. A recent window has `cause: null`. A blocked, rate-limited or failed Diary is the `cause`. The retired binding does not end a run as `diary_off` |
| `isolation`, `isolationClearedAt` | See [isolation](#stale-runs-and-isolation) |
| `lastStepError` | The last exception a step threw, with its phase, the lease released |
| `recent` | The ten most recent runs as summaries, newest first |

### Start and step

- **Start** (`trigger`, optional `clearIsolation`). Answers `started` with a new `runId`, or one of:
  - `busy`: a run is active; its id is not handed out;
  - `isolated`, with `isolation`;
  - `storage_unsupported` (with `storage`) when the stored removal queue or Diary cursor is not version 2. There is no `disabled` answer.

  Neither `scheduled` nor `manual` is refused for following the previous start ([ADR 0069](../../adr/0069-no-scheduled-ratings-start-gap.md)). A stale `running` record is first closed as `unknown`. A start makes no Letterboxd request.
- **Step** (`runId`). Takes the lease by compare-and-swap, does one bounded piece of work, writes the record only while its lease holds, then releases it. Answers:
  - `continue` / `more_work`;
  - `wait` / `busy` while another step's lease is live, not before `nextCatchUpAt`;
  - `stop` with `finished`, `error`, `unknown` (a stale run closed by this call), `run_mismatch`, `not_running`, `lease_lost` or `storage_unsupported`.
- **Diary phase.** One GET of `https://letterboxd.com/<user>/diary/` per run ([ADR 0067](../../adr/0067-diary-recent-window.md), [ADR 0075](../../adr/0075-retire-letterboxd-diary-history-switch.md)). The retired `LETTERBOXD_DIARY_HISTORY` binding is not read. A checkpoint with `diaryPagesRead >= 1` does not fetch. No request is started once less than 45 seconds of the lease remain (`step_budget`); the step answers `continue` so the same run retries that page. After the page: the history merge, that page's facts, the queue entries the Diary rated (`rated`, `lastResult: diary`), the cursor join, then the checkpoint. A successful page is `recent_window` / `recent_window_only` and does not fetch another page. A blocked, rate-limited or failed Diary ends the run `error`; stored facts and history stay. `resumePage` is not a URL.
- **Removal phase.**
  1. While a legacy entry is `rated` with a confirmed half-star and its event scan is not done, list one page of `events/items/` (20 keys) and attach a reference for each stored watchlist event that removed that exact film id ([ADR 0071](../../adr/0071-legacy-removal-event-link.md)). The cursor is `legacyLink` on the queue. The entry is not reopened and no Letterboxd request is made. A step with nothing left to link does not list. A late step deletes an obsolete cursor only when the queue still has the ids and cursor that step read and those ids are still not candidates; it does not erase a newer scan, and the checkpoint counts a page only for a queue write that step committed. While the scan is unfinished the step answers `continue` (`stoppedBy: legacy_link`, unless settle still has a backlog). Retention does not run until the scan is done.
  2. Rated entries with unresolved references get their rating written to each referenced removal event, at most 100 references per step, least recently checked first. A run visits each reference once: references checked since the run started are skipped, and while unvisited ones are left the step answers `continue` (`stoppedBy: settling`). A reference is resolved only once the stored event lists the film as removed with a confirmed rating. Otherwise it stays unresolved with `checkedAt` and `issue`: `event_missing` (the event is not stored, for example a commit that never wrote it), `film_not_in_event` or `event_unrated`. So references that never resolve neither keep a run going nor hide later ones, and the next run starts with those it has not checked for longest. A confirmed rating already on the event is left in place.
  3. The [retention rules](#removal-queue-version-2).
  4. At most five member-page lookups per step, oldest due entry first, for a film the Diary did not already rate, with the claim, attempt, pause and outcome rules of [removed films](#removed-films) ([ADR 0077](../../adr/0077-retire-removal-rating-lookup-switch.md)). A confirmed stored rating for a film the current Diary page did not list resolves the entry first (`rated`, `lastResult: fact`) with no claim and no member-page GET, including an entry a new reference just reopened. The rating on the event is the fact-precedence winner, not a stale rating left on the queue. A film that page lists without a rating is still looked up. A null or absent rating does not resolve the entry. A step probes at most five films, reads the films-list floor once, and does not request a film it has not probed. Entries left pending stay pending and the step answers `continue`. Inside the lease margin it probes nothing further and requests nothing further. The retired `REMOVAL_RATING_LOOKUP` binding is not read. While due entries remain the step answers `continue`; each claim moves the entry's next attempt at least an hour ahead, so a run ends once none is due. A paused queue ends the lookups with the pause. There is no `lookup_off` stop.
- **Lease lost.** A step whose lease ran out, or whose record another writer took, writes nothing more to the record and answers `lease_lost`. What it already merged into the cursor, history, facts, queue and events stays: those merges only move forward.

### Stale runs and isolation

- **Stale.** A `running` record is `interrupted` when an active step's lease has expired, and `abandoned` when no step has begun or ended for 30 minutes. Only a start or a step closes it: `state: unknown`, `cause`, `interruptedPhase`, `closedAt`. It is never resumed. `ratings_sync_status` reports `stale` and never closes anything.
- **Isolation.** Two consecutive runs closed as `interrupted` in the same phase at the same checkpoint set `isolation {since, phase, checkpoint, runIds}`. Starts then answer `isolated` until a start with `trigger: manual` and `clearIsolation: true` clears it (`isolationClearedAt`). `clearIsolation` with a scheduled trigger is a `400`.

### Removal queue version 2

The same object, `enrichment/removal-rating-lookups.json`, with `schemaVersion: 2`, `droppedRefs` and, on a queue that earlier code converted from version 1, `migratedAt`. `films[id]` stays the unit of lookup.

- **References.** `refs` lists every removal event that removed the film: `{eventKey, sourceRunId, at, resolved}`, plus `checkedAt` and `issue` once a settle has tried it. A replay of the same event adds nothing. A new reference on a finished entry reopens it: `pending`, no attempts, fresh `enqueuedAt`, no claim. Past 20 references the oldest resolved one is dropped, or the oldest unresolved one when none is resolved, and counted in `droppedRefs`.
- **Legacy entries.** Entries that earlier code converted from version 1, and films without an event to name, are `legacy: true` with `refs: []`. An entry that is not `rated` with a confirmed half-star still promises nothing for an event and is pruned by the version 1 rules. A rated one is linked, once, to existing removal events of the same film id by the ratings removal step ([ADR 0071](../../adr/0071-legacy-removal-event-link.md)): one page of 20 keys per step, exact id only, no new lookup. When that scan finishes, a match drops `legacy` and leaves the new references unresolved until settle; no match keeps `legacy` and sets `legacyLink.done` so later steps do not list. The EPG commit does not do this scan. Merging the code does not run it.
- **Claims.** A claim stores a random token; only the outcome carrying it is accepted, and only while the entry is still pending. A reopened entry has no claim, so a late outcome of the earlier lookup is refused (its attempt counted).
- **Retention.** An entry with an unresolved reference is never deleted, by age or by the cap. A pending entry still becomes `expired` after 14 days. Entries whose references are all resolved, legacy ones included, follow the version 1 rules. Those rules wait while a rated legacy scan is unfinished, so an unmatched `refs: []` entry is not deleted between pages.
- **Writers.** Every write is the read-apply-compare-and-swap of the queue and branches on the version read in that attempt, so a writer that read version 1 follows version 2 when another writer has stored it first.
- **EPG commit.** On supported storage the commit stores the removal event as the reference and does not look the film up. On any other stored state the commit does not enqueue. The ratings run's member-page lookup does not read `REMOVAL_RATING_LOOKUP`.

### Storage schema guard

The ratings pipeline works only on version 2 storage ([ADR 0161](../../adr/0161-retire-ratings-storage-migration.md)): the removal queue at `schemaVersion: 2` and the Diary cursor in its [merge form](letterboxd-diary-history.md#run-state--letterboxddiarystatejson). The guard first reads the Ratings D1 authority marker: a held or unreadable marker refuses the pipeline whatever the R2 copies of the two keys look like, because those copies are stale and the writers would fall through to them. Only an open marker, or a store with no Ratings D1 tables (local development and the test harness), has a readable authoritative copy. `ratings_sync_status` reports the result as `storage: {supported, authority, queueV2, cursorV2}` (`authority` is `open`, `held` or `unavailable`), derived on every read, and writes nothing. `supported` is true only when the authority is open and both shapes hold. When the authority is not open the EPG commit reports `ratingsStorage: authority_held` or `authority_unavailable`, keeps its `removalRefs` and never writes the removal queue key.

- On any other stored state (an absent object, a version 1 object or any other shape), a run start or step answers `storage_unsupported` with the same `storage` object and writes nothing, the status reports `pipeline: blocked`, and the EPG commit fails closed as described above. Nothing falls back to an inline Diary stage and nothing reads another store.
- Nothing in the Worker converts storage: there is no tool, route or automatic step that rewrites a version 1 queue or cursor. The earlier witness document `letterboxd/ratings/migration.json` is neither read nor written; D1 still holds it as a historical record and it is not part of the guard.
- A restore of the D1 database to a point at which the queue or the cursor was still version 1 therefore leaves the pipeline refused until the stored objects are version 2 again, which needs its own owner-approved operation. See [D1 authority and recovery](../../runbooks/recovery/d1-authority-and-time-travel.md).

### Footer under the separate pipeline

On supported storage, the `letterboxd_ratings` source of the integration footer comes from the run record, with `pipeline: separate`:

- `ok`, with freshness from the last finished run;
- `running`;
- `degraded` (`ratings_pending`) for an isolated, stale or `unknown` run;
- `degraded` or `failed` for a Diary that ended `blocked`, `rate_limited` or `failed`;
- `unknown` (`no_data`) before the first run.

`lastSuccessAt` and `lastFailureAt` come from the run and the ten recent runs. On unsupported storage the source is `degraded` / `ratings_storage_unsupported` with `pipeline: blocked`, and old `sync.json` rating fields are not used.

## Rated-only Diary ids: bounded same-run Film bridge (AIR-489, [ADR 0166](../../adr/0166-diary-rated-only-identity-bridge.md))

The Diary phase stores `watched` and the rating first (unchanged, `lb-<lid>`, never waiting for anything below). Then, in the same step and only for ids whose record has no TMDB link, `LetterboxdDiaryIdentity.resolve` runs (`src/letterboxd-diary-identity.js`):

1. A trusted D1 bridge (`catalogFilmIdentityBridge`) is consumed when it is `ok`; `conflict` and `retired` are recorded as pending and never overridden. The check runs only while the Film/Person marker is `d1`/`open`.
2. Otherwise, for at most three ids per step, started only while 40 s of lease remain (every request is cut at the time left minus a 15 s write reserve, and no write starts without that reserve), `boxd.it/<lid>` must land on `/film/<slug>/` of the same Diary row; the page must carry one movie `data-tmdb-id`, an agreeing canonical path and shortlink and one year; the TMDB movie document must agree on title and year. A title, a year, a slug or an owner statement alone is never proof; the inferred identity of ADR 0104 stays export-only.
3. A unanimous result, with the writer's positive answer (`complete` and an applied/already/noop `film_admission` unit; `skipped` or any failed/unknown/refused/deferred count fails closed), writes the receipt entry (`identity: "diary_page"`) in `letterboxd/admissions/verified-films.json`, admits the Film through the existing `applyRatedAdmissionRetention`, and links `tmdb:<n>` to the record that already holds the id through `LetterboxdFacts.linkFilm` (history kept; a movie id already linked elsewhere or a code already admitted for another id is a conflict, never a merge). The planned film of the page and so the run event get the title, year and TMDB id.
4. Anything else stays in `letterboxd/facts/scans/diary-identity.json` (D1-owned prefix, at most 200 entries) with `reason`, `class`, `attempts`, `streak`, `queuedAt`, `lastAttemptAt`, `nextAttemptAt`, the same-row `slug`, the caller's `route` and, after a charged check, a `checkId`. Since AIR-599 the outcome follows [one retry contract for both callers](#one-retry-contract-for-both-callers-air-599-adr-0207-decision-4b): a transport stop (403, challenge, 429, timeout, network error, 5xx of Letterboxd or TMDB, no TMDB token) stops requests for the rest of the step but consumes no attempt; a 404 or 410 consumes one; at most six charged attempts per id, then the id stays visible for the owner and no run requests it again. An id deferred by the step cap, the budget or a temporarily unavailable Film authority (marker not `d1`/`open`, held, unreadable, generation moved, canonical read error; no outbound check is made meanwhile) is kept (`reason: deferred`, due at once, no attempt). Due entries that have left Diary page 1 are served by later ordinary steps in queue order. Before the first non-atomic effect (receipt, admission, alias, record link) the step writes a bounded link intent (`reason: linking`, the verified movie id, due at once, no attempt); if it cannot be written, nothing is written. On D1 the record compare-and-swap writes `ratings_view` in the same batch, so the remaining gap is between the alias index and that record batch. A `linking` or `link_failed` entry is served first and off-page, whatever its source-attempt count: `link_failed` (written only after a confirmed admission, with the movie id) is completed locally with no request and no admission; a `linking` intent whose alias never committed is an ordinary source retry and becomes `link_interrupted` at the six-attempt cap. A pending entry on an id that is already linked (a bridge that failed after the alias and the record link were committed) is repaired by a later ordinary step: the committed record is projected again (no request, no admission, no new fact) and the entry is cleared only when that succeeded. A usable same-row slug seen later on an existing pending entry (for example after `slug_missing`) is saved on it first, with attempts and backoff unchanged, so the entry stays retryable off-page. A Diary page the history parser does not accept runs no check. The run never fails because of this step; the run summary carries `diary.identity` counts (`considered`, `bridged`, `verified`, `repaired`, `pending`, `deferred`, `skipped`, the per-class `checked`, `transport`, `notNow`, `gone`, `definite`, `atCap`, `capRefused`, `backlogFull`, and `persistFailed` when the document could not be written, which never fails the run).


### One retry contract for both callers (AIR-599, ADR 0207 decision 4b)

The same check (`LetterboxdDiaryIdentity.resolve`) has two automatic callers, and both share the document above: the Ratings Diary phase of the Letterboxd Sync (`route: ratings_diary`) and the Sync's Watchlist admission step (`route: watchlist_admission`, ledger `watchlist_admission_pending`). Since AIR-599 they follow one policy ([ADR 0207 decision 4b](../../adr/0207-letterboxd-admissions-coordinated-in-d1-only.md#4b-both-callers-of-the-diary-check-one-retry-policy-fences-and-visibility-0207-u3--b)):

| Class | Reasons (today's paths) | Attempt | Next check |
| --- | --- | --- | --- |
| `transport` | `forbidden`, `challenge`, `rate_limited`, `timeout`, `network_error`, `upstream_5xx`, `tmdb_unavailable` | none; `streak + 1` | 15 min · 2^min(streak − 1, 5), at most 8 h; the step stops requesting after the first one |
| `not_now` | `deferred`, `unavailable`, `admission_skipped`, `admission_held`, `admission_unavailable`, `in_flight`, `epoch_fenced`, `diary_cap`, `persist_failed`, `owner_requeued` | none | the next run; the place is kept |
| `gone` | `not_found` (404 or 410 of `boxd.it/<lid>`, the film page or the TMDB movie) | +1, streak 0 | 12 h · 2^(n − 1), at most 48 h |
| `definite` | every other answer (`slug_mismatch`, `tmdb_*`, `detail_*`, `slug_missing`, `bridge_conflict`, `admission_conflict`, `link_conflict`, `check_failed`, …) | +1, streak 0 | as `gone`; owner review at the cap |
| `settled` | verified and admitted, already linked, or `owner_dismissed` | — | never |

- **Explicit outcome.** `resolve` returns `{checked, class, reason, retryAt, attempts, streak, terminal}` for every id it was asked about. The Watchlist step charges nothing itself: it **copies** the entry's `attempts` and next retry time into its ledger row, so a restart between the check and the settle, or a stale entry, is never charged again, and the cap applies to the one shared count. A new entry created for a ledger row starts from that row's count.
- **The cap is 6 and counts only `gone` and `definite`.** At the cap an entry or row is terminal and visible (`needs_owner_review`). Transport and not-now outcomes have no cap; a long transport `streak` is visible instead. Age no longer ends a ledger row: `age_exceeded` is not written any more, and a row pending longer than 14 days is reported (`overdue`; a legacy row whose first-seen snapshot was already pruned has an unknown age and is reported as `overdueUnknown`). Snapshot retention keeps the header (version and commit time) of the first-seen snapshot of every open ledger row and prunes only its members, changes and effects, so the age survives the eight-snapshot bound.
- **Exclusive ownership of an effect.** Before a step does anything with an EFFECT for an id (a source check, a link made from a trusted bridge, the completion of a confirmed admission's link) it reserves the id with one compare-and-swap: the entry (created from the backlog record or from nothing when needed, with the backlog record removed in the same write) gets a `reservation {checkId, until, route}` that expires after five minutes. Another step skips an id with a live reservation (`in_flight`, not now, no attempt, no request), so one reservation is at most one real check or effect holder, whichever caller runs it; a step that was cut off leaves a reservation that simply expires (a link intent it left is served after that); the check id of the charge is the reservation's. The reservation stays on the entry through the link intent (`linking`) and is released by the holder's final write. **An owner `requeue` or `dismiss` of an id with a live reservation is refused whole** (`check_in_flight`, nothing written, readback by the owner after the step finishes or the reservation expires): the owner action therefore cannot be reported as committed while an admission or link can still land. **An effect is fenced at commit by its reservation TOKEN, not by the clock.** The env an effect commits through carries `effectGuard {sql, params}` (built once by `LetterboxdFacts.reservationGuard`): a boolean over the logically reconstructed check document that holds only while it still contains the holder's `"reservation":{"checkId":…`. The document is stored in parts of 60,000 bytes cut with no regard to JSON tokens, so the SQL looks at each part and at the tail of each part joined to the head of the next (a needle spans at most two); the Ratings batches (`ratings-d1` epoch fence) and the canonical batches (`canonical-mutations` head, bound by the Letterboxd admission writers) assert that same text in their own batch (no schema, no second authority). A reservation that was released, taken over by another caller or voided by an owner `requeue`/`dismiss` (also after it expired, when an owner action is no longer refused) therefore refuses the link, the canonical admission and the projection at commit. The wall clock is used only to decide when an owner action stops being refused and to keep a step from STARTING a local effect (a trusted-bridge link, a `link_failed` completion) or a source check once the window is spent (the source-check budget is capped by the window, less the write reserve and a 15 s margin, whatever deadline the caller passed); an effect already running past expiry is stopped by the token, not by time. **Receipt limit:** `letterboxd/admissions/verified-films.json` is not a Ratings-D1 document (no batch fence), so a receipt written by a holder that stalled past expiry stays durable evidence. It is not permission to replay an owner-voided admission: the receipt is applied only by the canonical admission, and every Letterboxd identity admission made through the step's env asserts the live reservation, so an owner-voided id is refused there. A later reconciliation of that receipt outside the step has no reservation and is governed by the receipt rules (ADR 0105), not by this fence. **Every write that applies a ledger row's budget carries that row's token guard in its batch**, including the backlog record of an id with no free place (`backlogAdd`) and the expected absence of an entry; if a combined final write is refused, each id is written alone with its own guard, so one stale id (`entry_changed`) never rolls back another id's answered check. A writer that does not honour reservations (a foreign write that changes the entry in flight) still cannot win: the holder's writes, including the link intent that precedes every non-atomic effect, are bound to the entry it reserved and fail closed (`entry_changed`, no admission).
- **The cap applies to the effective count before any check:** the larger of the entry's attempts, the caller's row budget and the backlog record's. At the cap nothing is requested; the count is held on the entry (created for an id without one), so no store ever holds more than the cap or disagrees about it.
- **Writes are bound to what the step read.** `resolve` reads an entry before slow source I/O, so every write of the step (the final outcomes, the link intent, the claim step) is installed in the document's compare-and-swap only while the stored entry still equals the one it read (`expect`); an id that moved meanwhile (an owner `requeue` or `dismiss`, another caller's check) is left as it is and reported as `entry_changed` (not now, no attempt, counted `entryChanged`). Two overlapping checks of one id therefore charge once, an owner decision is never undone by an in-flight 404, and no admission starts over an entry the owner dismissed during the check.
- **The budget survives the backlog and the caller.** A backlog record keeps the attempts the refused id's Watchlist row held; an id entering from the backlog, or an existing entry with fewer attempts than the row, starts from the larger count, so a real check never lowers a row that already holds attempts (the Watchlist step copies `max(entry, row)`). A row's budget is applied only under its token: every write of the shared document that applies a row's seed (the reservation, the hold at the cap, an outcome that is not a source answer) carries a guard statement of the row's token (`attempts`, `updated_at`, `state = pending`) in the SAME D1 batch, so a seed read before an owner `requeue` or `dismiss` can never be installed after it (the write is refused whole, `entry_changed`, nothing charged; without a D1-owned store such a write is refused). Every ledger settle carries the same token as read with the due list and is fenced by it: a row an owner requeued or dismissed since cannot be overwritten by the outcome of a check that started before (`rowChanged`). An owner `requeue` resets the entry, the backlog record and the ledger row in one commit, so it is not undone.
- **The slug.** The Watchlist step takes the film slug from the first-seen snapshot, else from the same id's member of the CURRENT snapshot, else the shared entry's stored slug; only an answered read with no slug anywhere records `slug_missing`. A failed read (unavailable evidence) leaves the row due and unchanged for the step: no attempt.
- **Queue order.** Link repairs and pending claims first, then by queue position: the entry's `queuedAt` (legacy entries: their last attempt) or the ledger row's first-seen snapshot. A transport retry keeps its position, so new page ids cannot overtake an older retained id.
- **The 200-entry document evicts only settled entries** (`owner_dismissed`), oldest first, never a link intent, a pending claim, a reserved, retained, not-now, below-cap or at-cap entry. When no place is left the step starts no check for an id without an entry: the id waits in the `backlog` of the SAME document (`letterboxd/facts/scans/diary-identity.json`: `films` plus `backlog`, at most 2,000 ids, each `{slug, queuedAt, attempts}`; an id is in exactly one of the two and moves between them only inside one compare-and-swap), counted as `cap_refused`; backlog ids enter first, oldest first, when places return. A full backlog is counted as `backlog_full`. The cap is also enforced by the compare-and-swap itself, so a document that fills between a step's read and its write refuses the id instead of overflowing. The Watchlist caller at a full document gets `diary_cap` (not now; its row keeps its place). (Recorded by [ADR 0221](../../adr/0221-shared-letterboxd-check-state-in-one-document.md), which supersedes in part [ADR 0207](../../adr/0207-letterboxd-admissions-coordinated-in-d1-only.md) decision 4b, only the second-document layout of «Refused ids stay recoverable»: one document makes entry, backlog, reservation and owner transitions one atomic write; the backlog was never in production. Worst case, at the 200 / 2,000 bounds with every field at its maximum length and the owner audit bounded to 100 characters of `by` and 200 of `why` (backlog records keep only `by` and `at`): about 1.0 to 1.3 MB serialized, at most 30 parts of 60 KB in one batch, far below the D1 row limit; a typical full document is about 0.25 MB. Every write rewrites the document, so an ordinary step costs one reservation write per checked id plus one final write.)
- **Producer fence.** Called through the Letterboxd Sync's fenced env, the admission batch (`admitRatedFilm`) and its receipt transitions assert the Sync epoch (`producerFence` kind `letterboxd`), so a stale epoch cannot admit (`letterboxd_epoch_fence`, not now).
- **Visibility.** Run records: the Diary summary above and the Watchlist slot record (`watchlist_summary.admission`: resolved, pending, terminal and the per-class counts, plus `overdue`). Admin: the `watchlist_admission` lane shows each row's class, streak and next retry; the `diary_identity` lane lists the entries and the backlog ([identity work inventory](../domain/identity-work-inventory.md)). Monitor: [three conditions](../../architecture/observability-and-failures.md) on the Letterboxd stream.
- **Owner actions.** `POST /api/admin/identity-work/owner-action` ([admin API](../api/admin.md#owner-requeue-and-dismiss-of-the-shared-letterboxd-check-post-apiadminidentity-workowner-action)): `requeue` resets `attempts` and `streak` to 0, keeps `queuedAt` and records who, when and why; `dismiss` settles an entry as `owner_dismissed` (evictable) or makes a ledger row terminal `owner_dismissed`. Compare-and-swap on the token the owner saw; nothing is reset automatically.
- **Legacy entries.** Entries and rows the old rules exhausted (transport charged as attempts) or aged out keep their state. A read-only report (`scripts/letterboxd-check-legacy-report.mjs` over two read-only exports) lists them as counts by last reason; recovery is a bounded owner `requeue` of listed ids under an L2 contract (card DR), never a blind reset.
### Typed TMDB states of the identity check (AIR-670, [ADR 0217](../../adr/0217-source-independent-film-admission.md) decision 3; dormant)

The check names the TMDB state of each answer, so a later lid-only path (ADR 0217, a separate card) can tell "TMDB has no such movie" from "the answer was unusable". **Nothing live reads these states yet:** `movieDetail` returns exactly the `review`, `status` and `stop` it returned before and adds a `state`, so the Diary check and the Watchlist admission step behave unchanged. Pure code in `src/domain/letterboxd-rated-admission.js`: `TMDB_STATES`, `pageTmdbObservation` and the one composition `tmdbCheckState({fetched, evidence, detail})` (it takes no `title` or `year` argument: the title and the single year come from the page evidence only, see the preconditions below).

**The established retry contract wins.** ADR 0217's "any other non-200" does not supersede [ADR 0207 decision 4b](#one-retry-contract-for-both-callers-air-599-adr-0207-decision-4b): a TMDB or film-page 5xx stays the transport reason `upstream_5xx` (no attempt, queue place kept), a network failure stays `network_error`, an enforced cooldown stays `upstream_cooldown`, and `network` and `until` ride along with the typed state. Each outcome is chosen so that the existing classifier (`LetterboxdDiaryIdentity.classify`) gives the class below; a test runs the chain real fetch answer → real `pageEvidence` → typed state → classifier for every row. A TMDB 404 is still `not_found` (`gone`) in the live Diary check; `tmdb_contradiction` is what the lid-only path will use once it consumes the state, and `definite` has the same charge and backoff as `gone`.

| State | Observed | Outcome | Retry class |
| --- | --- | --- | --- |
| `page_movie` (intermediate, **not admitting**) | the page names exactly one movie id; the TMDB document is not fetched yet | none | — |
| `page_refused` (outside decision 3's table) | the page names one movie id but lacks the movie path's mandatory page evidence: no title (`title_missing`), no page year (`page_year_missing`) or several (`page_year_inconsistent`); refused before TMDB is asked | the existing `verifyPage` reason | `definite` |
| `tmdb_movie` | `page_movie` that passed the page evidence, **and** an agreeing TMDB document, reached only by `tmdbCheckState` | none: the existing path | — |
| `tmdb_disagrees` | the TMDB document disagrees | the existing `detail_*` reason | `definite` |
| `tmdb_tv` | one id with a `tv` marker, or a TV document | `tmdb_not_movie` | `definite` |
| `tmdb_missing` | TMDB answers `404` for the movie id | `tmdb_contradiction` | `definite` (owner review at the cap) |
| `tmdb_unavailable` | any transport answer: 403, 429, challenge, 5xx of the film page or TMDB, network failure, timeout, cooldown, missing token | the established reason (`upstream_5xx`, `rate_limited`, `network_error`, `upstream_cooldown`, …) | `transport`: no attempt |
| `tmdb_failed` | any other non-200 below 500, an unparseable or oversized TMDB document | `tmdb_fetch_failed` | `definite` |
| `tmdb_unreadable` | oversized or truncated page (no closing `html` tag), unparsable page, no id block, several ids, or any malformed, doubled or unknown `data-tmdb-id` or `data-tmdb-type` value in the raw markup | `page_unreadable` | `definite` |
| `page_not_read` (outside decision 3's table) | the film page itself answered 404 or 410, or with another review reason (`fetch_failed`, `blocked_redirect`, `not_film_page`, `too_many_hops`) | the established reason, e.g. `not_found` | `gone` or `definite`, as today |

**Preconditions of `tmdb_movie`.** The movie path keeps its page evidence exactly as `LetterboxdDiaryIdentity.verifyPage` demands it: a non-empty title and exactly one page year, taken from the page only. `tmdbCheckState` takes no caller fallback for either, so a missing or contradictory year (for example OG and JSON-LD disagreeing) can never become admitting through an agreeing TMDB document; only a lid-only admission may omit the year ([ADR 0217](../../adr/0217-source-independent-film-admission.md) decision 2), and that is a later card. A test compares the refusal with the live check's reason on the same page.

The page's id and type values are read from the raw HTML, not only from `pageEvidence`, whose arrays keep just well-formed numeric ids and lowercase alphabetic types: a malformed value next to a valid one would otherwise disappear. `pageEvidence` and the live acceptance are unchanged. No state is downgraded to `tmdb_none`: that state (H1) does not exist in this code, and a page without any id is `tmdb_unreadable` until a later card proves a parseable absence marker. No state mints a Film or writes canonical data. Rollback is a code revert; no schema or data is involved.

### The lid-only page proof and the `lid_only` coordinator kind (AIR-672, [ADR 0217](../../adr/0217-source-independent-film-admission.md) decisions 2 to 7, delivery step 3; dormant)

**Nothing live calls any of this.** H1 stays disabled, `film_lid_admission` (migration `0048`) is not applied, and the TMDB-proved path is unchanged.

- **The H1 page proof** (`src/domain/letterboxd-lid-only-proof.js`, pure): `lidOnlyPageProof({lid, redirect, fetched, evidence, rules, checkedAt})` returns the admitting state `tmdb_none` only for a complete, validated film page with a positively absent TMDB relation: the `boxd.it` redirect is a `3xx`, the page answered `200` completely and is no challenge, its shortlink equals the lid and its canonical path equals the redirect target, its type marker is readable and in the enumerated eligible list, the title is not empty, and the external-id block is present (matched exactly once) and holds no TMDB id of any type. A page that names a movie id stays `page_movie`, one that names a TV id `tmdb_tv`; a truncated page, an unreadable marker or block, or a stray TMDB reference is `tmdb_unreadable`, never "no TMDB"; a readable but ineligible type is `page_type_ineligible` (`definite`, reviewed). The year is optional here only (none or exactly one; several disagreeing years refuse). **`H1_RULES` ships empty** (no eligible type, no block marker), so nothing passes until the real markup is shown on permitted existing captures (ADR 0217 step 8, a hard pre-activation holdpoint); the tests pass synthetic rules and prove the code, not the upstream.
- **The proof digest** (`src/domain/letterboxd-lid-only-digest.js`): `sha256` over `[proofVersion, lid, finalUrl, slug, canonicalPath, shortlink, typeMarker, idBlockOutcome, completenessOutcome, title, year|null]`, each input in its own column of `film_lid_admission`, so it recomputes from the row. The route, the check time and the HTTP statuses are observation metadata outside the root. No HTML is stored.
- **The writer** (`admitLidOnlyFilm`, `src/film-admission.js`): re-verifies the proof (recomputes the digest, never trusts a column) and writes **one** fenced batch (13 statements with the `links.json` fence; measured by test 16): the Film `film:lb:<lid>` (`canonical_identity` NULL), the trusted `letterboxd` claim (provenance `{source: route, adr: 0217, evidence: digest}`), the immutable `film_lid_admission` row and the applied receipt tail. No evidence row (K2), no `film_rated_admission` row, no alias. It refuses before its first effect unless the admission marker is `d1` and the table exists, and asserts inside the batch: the marker generation, the Film revision, no `film` row or redirect for the id, no `letterboxd` claim of the lid of **any** trust, no `film_lid_admission` or `film_rated_admission` row for the lid, **and, both mandatory**, the exact `letterboxd/facts/links.json` parts the caller read (`ratingsDocumentFence`: part count and the one etag; an absent document is `parts: 0`; any other key is refused) and the **exact owned receipt of the common lid key** (pending, this request id, this attempt; the applied tail then settles exactly that receipt). A call without a receipt mark, without the links fence, with another document key, or whose receipt is missing, of another key, abandoned or of another attempt, mints nothing.
- **The coordinator kind** (`admitVerifiedLidOnly`, `src/letterboxd-admission-d1.js`): the same key `admission:lid:<lid>` as every lid-knowing attempt, origin `rated_admission_retention`. Before reserving it reconciles the **older keys** `admission:short_code:<lid>` and `admission:inferred_import:<lid>` (a live attempt waits, any other unresolved receipt is abandoned, never reserved again), and an unknown reverse mapping is held (`deferred`, `older_key_unknown`). `planLidOnlyD1` decides from durable state without a fetch: `present_lid_only` (replay, lost response), `present` (the lid is trusted on a TMDB Film or held by a rated admission), `conflict` (any other claim of the lid, the id taken, incomplete ownership, a redirect loop), `redirect` (the owning Film is a redirect source: non-terminal, never a success), `held` / `ownership_incomplete` (a rated admission holds the code but no trusted `letterboxd` claim of the lid exists yet: fail closed and retried), else `admit`. `present_lid_only` and `present` are reported only for **complete, non-conflicting ownership** (the TMDB-proved kinds classify an existing lid-only row with the same validation, so a moved, duplicated, untrusted or removed claim is a `conflict` / `lid_only_ownership_incomplete` and a redirect source is a non-terminal `redirect`, never a settlement): exactly one trusted claim of the lid, on the Film the proof row names (or the TMDB Film), that Film exists and no redirect leaves it. The coordinator requires a **positive observation of the Ratings link document** from the caller (`links: {fence, tmdbAlias}`, with `tmdbAlias: null` for none; a missing observation is refused `links_observation_missing` before any reservation), and an actual TMDB alias on the lid's fact key stops at `held` / `ratings_tmdb_link`. The outcomes are `admitted_lid_only`, `present_lid_only`, `present`, `conflict`, `lid_unverified`, `source_unavailable` and the non-terminal `wait`, `held`, `redirect`, `deferred`, `failed`, `unknown`.
- **The TMDB-proved kinds meet a lid-only Film** (decision 5b): the planner answers before any link, `present_lid_only` for Diary and Watchlist (`lid`), `needs_review` for the rated step (`short_code`), `conflict` for the inferred import, always with reason `lid_only_present`; natural sync never attaches. The TMDB batch also asserts, inside the batch, that no `film_lid_admission` row exists for the lid (or, while the table does not exist, that it still does not).
- **Owned-attempt assertion** (`ownedAttemptCondition`, `src/receipt-operation-key.js`): one boolean statement for a batch that is not the canonical batch: the receipt of the key is still `pending` with exactly this request id and attempt and inside its window, so an expired or abandoned attempt cannot land a late effect. The deadline is enforced **at the effect, in the batch's own SQL**: the assertion compares the receipt's `next_attempt_at` with the time the **database executes** the statement at (SQLite's UTC clock in the receipts' ISO convention), so a batch that was built in time but is delayed past the deadline before it runs (a queued write, a slow link) fails, and so does every later batch of the attempt; no Worker clock and no new retry policy enter it, and the window itself is unchanged. (`ownedAttemptCondition` also accepts a bound `now` for deterministic unit tests; the Ratings carrier does not accept that variant.) It is carried by the existing Ratings `admissionGuards` carrier (accepted there only in this exact shape) and is wired into the inferred import: see [the baseline commit](letterboxd-user-facts.md) (the reservation precedes the inferred mark and the link, which run inside the owned attempt, AIR-672 decision 5b).
- **Step 4, settlement (AIR-673, dormant).**

A linked TMDB alias always wins (`identity:<n>`), and an ordinary label stays `identity:verified`. Pending keeps the row due and terminal keeps its reason; a lid-only success is never invented from an unresolved id, and no receipt is written by the ledger.
  - **Ratings Diary.** The coordinator outcomes `admitted_lid_only` and `present_lid_only` clear the Diary entry (the intent) with the outcome `lid_only`, keep the record on its existing `lb-<lid>` fact key and invent no `tmdb:` alias (nothing is bridged or linked); the success is fenced on the current ownership (see the Diary and Watchlist bullet below).
  - **Rated archive candidate (dormant).** In `identityStep` at `d1`, a page that names no accepted movie is tried as an H1 lid-only page (`LetterboxdLidOnlyProof.lidOnlyPageProof`; its rules ship empty, so until the owner's step 8 no page proves `tmdb_none` and the delivered review is unchanged; `lidOnlyRules` is an injection point for tests and step 8 only). A proved page claims the row from `pending` to `admitting` by exact compare-and-swap with the durable intent `kind: 'lid_only'`, `intendedTmdb: null`, the page path (`filmPath`) **and the proof digest** of the page. The coordinator's `lid_only` kind then admits. The links observation (`LetterboxdFacts.linksObservation`, `RatingsD1.observeOwned`: exact parts and etag of `links.json`, and whether the lid's record already carries a movie) is read fresh inside the coordinator and fenced in the canonical batch.
  - **State contract.** The terminal state is the existing `verified` (`REGISTRY_STATES` and every progress reader know `pending`, `admitting`, `needs_review`, `verified` and `removed`; there is no `admitted` state). ADR 0217's "`admitted`, `tmdb: null`" names that terminal outcome, so the row becomes `verified` with `kind: 'lid_only'`, `tmdb: null`, `filmId` (the coordinator's resolved Film, not a spelling), `proofDigest` and `enrichment: 'done'` (enrichment is retired at `d1` and a lid-only Film is outside the ADR 0211 scope). No `film_rated_admission` row and no evidence row are written.
  - **Settlement and its fence.** One settlement path serves a newly applied attempt, an already-present Film and the recovery from an applied receipt. The assertions are built **before the first effect** and ride in **each effect's own D1 batch**, not only in the terminal write: the complete current ownership of the lid by the resolved Film (`lidOnlySettlementGuard`) and the exact version of the candidate document the settlement read (`lidOnlyDocumentFence`: the row content, so a row replaced, removed or changed is refused). They reach the link (`linkLidOnly`), the watched and rating record (`recordObservations`, whose D1 batch already carries the view projection) and the projection (`projectRecords`) through the `extra` of the existing D1 compare-and-swap. An effect whose guard is false commits nothing; effects that already committed while the guard was true are kept, never rolled back. The lid-only contract holds at the effect: the link lands on exactly `lb-<lid>` and is refused if any movie alias points at that key (also the same key), and the record is refused if it carries a movie id or was redirected (never followed). A movie alias that appears meanwhile reviews the row `ratings_tmdb_link`. The terminal `verified` write is the document compare-and-swap itself and carries the ownership assertion. A refused effect or terminal write leaves the row `admitting` (`ownership_changed`). The candidate value and its version come from **one snapshot** (`RatingsD1.observeOwned`: value and `{key, parts, etag}` of the same read); the facts are derived from that row, never from an earlier read; and the intent is **exact**: besides kind, path and proof digest, the row's rating and observation time must equal the observation the attempt writes (a row replaced with the same proof and path but another rating is another row, not claimed, not settled, not reviewed by the stale attempt). A change of another candidate moves only the document version: the attempt re-reads and retries (at most three snapshots) while this exact row still stands. After the lid-only link, the positive links observation (the same `links.json` fence of ADR 0217 5b) is taken again and rides in the record and projection batches, so a movie alias onto the same key before those batches refuses them; the next step reviews the row.
  - **Replay or present.** The coordinator distinguishes the caller's own replay from an independently proved Film. A caller with a **durable intent** (a persisted proof digest: the `admitting` row, or the `lid_only_intent` Diary entry) first compares its **freshly reacquired check** with that intent: a different digest (or a TMDB check against a LID-only intent, or the reverse) is `source_changed`, finalized by the caller (the row is reviewed behind the history guard, the Diary entry is written through the fenced finalization). A check that still matches the intent is the unchanged source. It then passes the intent to the coordinator (`intent: {proofDigest}`), where an applied receipt is its own replay (`ownReplay`, no fetch) only when its content digest names that proof. A Film proved by **another route** (another proof digest) is an independently proved Film, whatever the persisted intent: it settles as `present_lid_only` on current ownership alone, and an interrupted attempt that meets it again (the source unchanged) settles the same way, with no receipt of its own created or invented. The settlement then asserts, for a replay, that the proof row is the caller's proof and that its own applied receipt of the common key (content digest and, when the coordinator named it, the request id) still stands; the receipt is bound by key, digest and request, not by the survivor's id (a merge moves the proof row, not the receipt). For an independently proved Film it asserts ownership alone. Every terminal disposition of the rated row (the coordinator's conflict, `lid_on_tmdb_film`, the alias review) carries the exact candidate this attempt owns, so a replaced row is neither reviewed nor reported reviewed by a stale attempt; a replaced row (the same proof and path, another observation) is `claim_changed`, not a mismatched intent. The post-link observation also validates that the positively observed link maps the lid to the very key just linked, not only that no movie alias exists.
  - **Recovery and conflicts.** A row left `admitting` with a lid-only intent is reconciled through the same common key: an applied attempt finishes it without a fetch (idempotent: no second Film, receipt, proof row or rating event); otherwise the page is proved again. A row holding a different intent (a TMDB intent, another path or another proof digest) is reviewed `source_changed`; a lid trusted on a TMDB Film is reviewed `lid_on_tmdb_film` and never attached by this path; a lid whose Ratings link already names a movie is held (`ratings_tmdb_link`, counted by the existing six-attempt retry) and never admitted lid-only. The delivered TMDB path is unchanged.
  - **Diary and Watchlist (dormant H1 caller).** `LetterboxdDiaryIdentity.resolve` accepts the injected `lidOnlyRules` (tests and step 8; omitted, no page can prove lid-only). A page with no movie id that passes them writes the durable entry `lid_only_intent` (`kind: 'lid_only'`, no movie, the proof digest; repair-class: served first, never charged) and the coordinator's `lid_only` kind admits under the common key; the entry is cleared and the label `{title: null, year: null, tmdb: null, lidOnly: true}` is returned only while the current ownership holds: `lidOnlySettlementGuard` rides in the Diary entry write's own D1 batch and `lidOnlyOwnershipHolds` is evaluated again before the success is reported, so a competing claim after the coordinator returned leaves the entry in place with the outcome `ownership_changed` (not settled, no label). The outcome hands the same assertion on (`ownerGuard`) and the Watchlist ledger settles its row `identity:lid_only` with it in the ledger batch; a lid-only label without it is not trusted and the row stays due. A TMDB page meeting an already admitted lid-only Film (ADR 0217 case 5a) settles only (`present_lid_only`): never an automatic attach. A persisted LID-only intent is recovered through the same coordinator before any source request (a lost response settles from the intent's own receipt with no fetch; a live attempt waits and the entry is kept), it is preserved across waits and transport stops (`lidIntent`, like the TMDB intent), and a new check is compared to it before anything changes: a LID-only intent meeting a page that names a movie, a TMDB intent meeting a lid-only page, or another proof digest is `source_changed` and never overwrites the intent. A mismatch is written through the same fenced finalization as the TMDB path (the history guard rides in that batch, one attempt is charged); an explicit `source_changed` is never collapsed into an uncharged deferral. A trusted bridge never overwrites a persisted LID-only intent (the bridge shortcut is skipped while one exists, like for a TMDB intent). An interrupted settlement whose Film was proved by another route (another digest) is not turned into this caller's replay and no receipt is fabricated.
- **Not here:** `mergeFilms` moving the row (step 5), the owner re-check and attach (step 6), the activation (step 9).

### The admission under the marker `letterboxd_admission_authority` (AIR-602, [ADR 0207](../../adr/0207-letterboxd-admissions-coordinated-in-d1-only.md) decisions 1 to 4, card A1; dormant)

Both callers admit through the same function, so one marker ([schema 46](../data/d1-schema.md#letterboxd-admission-authority-schema-v46-adr-0207-decision-1-accepted-air-602-in-the-repository-not-applied), in the repository, **not applied**) governs both. At **`r2`**, and while the migration is absent, this section changes nothing (the receipt entry of step 3 above, the legacy `film_admission` unit). At **`closed`** `resolve` reads the marker first and every id of the step is *not now* with reason `admission_closed`: no source request, no reservation, no entry, no backlog record, no write; an unreadable marker is `admission_unavailable` (also not-now, never the legacy path). At **`d1`** the admission goes through the D1 coordinator instead of the R2 receipt entry: one key `admission:lid:<lid>` for both callers, keep-first admission, the evidence row of **this** page check (route `ratings_diary` or `watchlist_admission` according to the caller whose step performed the check, method `page_check`, source root the digest of what the page proved) in the same batch, and nothing written to `letterboxd/admissions/verified-films.json`. The typed outcome maps onto the table above: `admitted` and `present` proceed to the link; `other_code`, `admission_conflict` (a code held by another Film) and `source_changed` (the page now names another movie than the `linking` intent) are `definite`; `in_flight`, `admission_held` and `deferred` are `not_now`. The coordinator runs first: it reconciles the key (a live attempt waits with the intent untouched, an applied attempt that matches the `linking` intent finishes the id with no fetch and no fresh evidence) and only then asks for the real source check; the `linking` intent is never replaced by the movie of a new check (`source_changed`), and a transport stop or a wait keeps it in the entry's `intent`. The evidence of a genuine check is proven recorded before the id is linked (`evidence_unrecorded` keeps the repair intent with the evidence to record), and the terminal entry is written in the same batch as the history assertion. A second caller that finds the id already linked, or a pair already admitted, writes nothing and requests nothing. Details: [Film/Person reference](../domain/film-person.md).

UX before a bridge exists: the event shows «Название недоступно» for that film. `GET /api/events` presents a stored ratings event whose film has no title with the title of the TMDB movie its id has since been bridged to; the stored event is never rewritten. A watched, bridged movie is projected under `tmdb_<n>` in the view, so Finds excludes it by TMDB id.

**Ratings marker.** Migration `0010` is applied on production `iptv` as of 2026-11-04 06:48 UTC ([apply record](../../evidence/d1-migration/air-318-ratings-apply-2026-11-04.md); [ADR 0084](../../adr/0084-d1-authoritative-ratings.md), Accepted). A manual MCP run at 08:28 UTC left generation 12 ([manual run](../../evidence/d1-migration/air-318-ratings-manual-run-2026-11-04.md)). The 17:30 Europe/Madrid Ratings Task was not changed. Readers and writers use D1 and do not fall back to R2. A code deploy does not by itself change the marker. Only `d1` / `open` is served ([ADR 0162](../../adr/0162-d1-only-authority-retire-rollback-toolchain.md)): a marker in mode `r2` or a held cutover is refused for readers and writers, including the `ratings_view` overlays of the view index and the catalog film page (a `503`, never the R2 view index facts), and with `RATINGS_DB_REQUIRED=on` (production) a missing binding, schema or set of ratings tables is refused too; only without that variable (local development and tests) do the facts, the diary cursor and history, the run and the removal queue stay in R2. A code rollback does not drop the tables and does not change the marker. The load, activate, release, seal and revert commands are retired, so there is no way back to `r2`: recovery is a forward-fix through the fenced writers or an owner-approved Time Travel of the whole database. While `mode` is `d1`, the run lease is read from D1.

**Separate pipeline.** The retired `RATINGS_PIPELINE` binding cannot put Diary back inside the EPG commit. Disabling the Ratings Task stops the scheduled run; it does not change the commit. Setting that binding to `inline`, or deleting it, does not restore a Diary stage on the commit. A code revert to a version without these rules is not a rollback: that code ignores the references, so its pruning can delete entries with unresolved ones, and it writes the cursor back as version 1 (the storage guard then reports `storage.supported: false`). Code from before ADR 0074 treats a missing `RATINGS_PIPELINE` binding as `inline`. After the leftover binding is deleted, that code must not be deployed until `RATINGS_PIPELINE=separate` is restored and read back. Undoing the migration needs a separate owner decision on the stored objects.

**Diary gate.** `LETTERBOXD_DIARY_HISTORY` is retired ([ADR 0075](../../adr/0075-retire-letterboxd-diary-history-switch.md)). Setting it to `off` or deleting it does not stop Diary page 1. After that binding is deleted, code from before ADR 0075 must not be deployed until `LETTERBOXD_DIARY_HISTORY=on` is restored and read back: that older code skips Diary when the binding is absent. A revert does not roll back Diary history, the cursor, facts or the removal queue.

**Removal lookup.** `REMOVAL_RATING_LOOKUP` is retired ([ADR 0077](../../adr/0077-retire-removal-rating-lookup-switch.md)). Setting it to `off` or deleting it does not stop the member-page lookup. After that binding is deleted, code from before ADR 0077 must not be deployed until `REMOVAL_RATING_LOOKUP=on` is restored and read back: that older code skips the lookup when the binding is absent. A revert does not roll back rating facts, the queue or removal events. After the deletion the lookup cannot be turned off by a flag.

**Retired refresh.** Reverting the code restores the AIR-64 route behind `RATINGS_REFRESH`, which is unset in production (read 2026-10-29 05:16 UTC). Bringing the refresh back for real is a new decision under a new ADR, not a flag change. Deleting `enrichment/ratings/` is a separate owner-approved storage operation; the view index keeps the ratings already projected.

## Run result in the Events Log (AIR-361)

Every run that reaches a terminal state writes one compact `ratings` event (see the [events reference](../domain/events.md#ratings-run-result-ratings)). ### Root mirror reconcile (AIR-571 M1, dormant)

The Letterboxd `ensure` tick calls a bounded reconcile of the standalone root `watchlist.json` BEFORE it returns on a finished or running slot (`ports.mirror.reconcile`, reported as `delivery.mirror`), only while the Letterboxd mode is `cloudflare`. One target is owed: the current pointer, so a backlog of several slots collapses to one write. The owed token is `<snapshot_id>|<last_success_at>` (`watchlist_current.mirror_delivered_snapshot_id`), so a no_change scan that only moves freshness is delivered too. The writer reads the Watchlist marker (`d1`/`open` at the generation read), the Letterboxd mode (`cloudflare` at the epoch) and the current pointer (the exact target being delivered) in ONE read before any object I/O and again after the object read (a pass that finds the target moved writes nothing), puts conditionally on the etag read with a fresh representation token (no ABA), and then READS THE OBJECT BACK: a put reply is never proof, so a lost reply that stored the object is acknowledged by the readback and a reply that stored nothing is a failed attempt. The acknowledgement is a compare-and-swap that holds only while the pinned snapshot and freshness, the marker generation and the epoch still hold. Failures record `mirror_attempts` and `mirror_next_retry_at` (backoff 1, 5, 15, then 60 minutes) and never gate a scan, the causal effects, the Events, Discovery or the EPG. `readModel().mirror` reports `delivered`, `owed` or `stale` (`mirror_stale`: owed for more than 2 hours, or three failed attempts in a row) independently of the slot health. The bookkeeping applies only while the target is still owed (a duplicate acknowledgement is a no-op, a late failure records nothing). A scan promotion that loses its pointer compare-and-swap is replayed once by the repository adapter only when the pointer proves bookkeeping-only contention, with the original pin carried into the replay; a superseded scan or a freshness-only change is never replayed. An unproven outcome is `write_uncertain` with `retry: false`, never a stale pin. Exact order, refusals and recovery: [Letterboxd Sync runbook, holdpoint (e)](../../runbooks/letterboxd-sync.md).

## Runs started by a Letterboxd Sync slot

A ratings-pipeline run started by a slot of the Letterboxd Sync carries `slotKey` on its record. Such a run (a) writes no `ratings` Event through the pipeline: the slot's own outbox is the single Event source, so no Event is duplicated; (b) records no EPG generation pin and reads no EPG state at start; (c) is split between two phases of the slot, the Diary part (phase 1) and the removal lookups (phase 3), with the Watchlist scan between them; (d) commits every write in a batch that carries the Letterboxd mode-epoch guard (`env.ratingsFence.guard`, tripping a `CHECK` that the pipeline reports as `ratings_domain_fence`). ## The Letterboxd Sync run (implemented and active since 22 and 23 November 2026; [ADR 0186](../../adr/0186-letterboxd-sync-and-independent-watchlist-authority.md), Accepted)

The contract below describes the implemented Letterboxd Sync run, activated by the owner-approved cutover of 22 and 23 November 2026 ([activation evidence](../../evidence/d1-migration/air-571-letterboxd-sync-activation-2026-11-22-23.md)). The Ratings pipeline above is its engine; the Ratings executor that used to drive that pipeline is retired.

- **Slots and trigger.** One run per Madrid slot, 04:30, 10:30, 16:30 and 22:30 Europe/Madrid, keyed by Madrid date and wall time; a separate cron `30 * * * *` UTC calls only the Letterboxd `ensure`. A slot missed entirely is recorded and not run late.
- **Order of phases.** Diary and Ratings, then a complete Watchlist scan, then removal reconciliation (at most five member-page lookups per step). Each phase is bounded and checkpointed; no retry crosses the next slot's due instant.
- **Independent outcomes.** `ratings`, `watchlist` and `reconciliation` each have their own result; `ratings` and `watchlist` each keep their own `lastSuccessAt`. A Diary failure does not stop the scan and a Watchlist failure does not unconfirm Ratings.
- **Incomplete scans.** A scan is complete only when every page was read, the stated total equals the number of distinct ids, no page is empty while the total is positive, the pagination path matches the account and a repeat read of page 1 agrees. An incomplete scan commits nothing, removes nothing and produces no removal.
- **Handover from the former pipeline (historical, performed).** Activation first closed and drained the old Ratings writer and proved its mode and epoch fence, then admitted the Letterboxd writer; the legacy start and step gate had to answer fenced (the `external` mode alone would still have admitted them). The 17:00 contract and the obsolete implementation are retired (the Ratings Workflow, its binding and the external entry points are gone), and the shared hourly cron stays.
- **Complete scans publish.** Every complete and validated scan is published whatever share of members it removes; there is no mass-change guard.
- **Events.** One `ratings` and one `watchlist` Event per scheduled run, including no-op and error, created by create-only puts under slot-derived keys; reconciliation has no Event of its own and patches the removal Event of the run that observed the removal.
