# Catalog of available films outside the watchlist

`GET /api/catalog/available` is a read-only query over the published EPG generation. It returns the verified catalog films that are **not** on the watchlist and that the owner has neither watched nor rated (and, through the [display-only title exclusion](#display-only-title-exclusion), that do not match a private list of watched films without a proven identity), are available now, in the 72-hour catch-up or within the next 24 hours, and carry a prediction that is current for the current taste profile. It is the shared source for discovery surfaces such as a "finds" section or similar-film suggestions; those consumers rank and present, this route only decides eligibility and returns a minimal display record.

The route does not change `GET /api/programme` or `GET /api/watchlist`, which keep serving the watchlist catalogue. `GET /api/programme` still returns the published report (`updatedAt` is the scan clock used for archive/future windows) and overlays `publishedAt` when a valid EPG completion clock exists: complete `sync.json` `completedAt`/`updatedAt` for that run, otherwise `lastEpgPublishedAt` from a later in-flight record. Missing or invalid values omit the field. The header and footer use `publishedAt`, not `updatedAt`. Both routes read the Film/Person marker first ([AIR-374](https://trello.com/c/ha7ais3w) P4b): at `open` their cached titles come from D1 (the frozen `titles.json` is not read), `held` or an unreadable marker answers `503 {error:"storage_unavailable",reason}`, and before `open` the response is unchanged. The route performs no R2 write, no model call, no TMDB call and no sync; the [GET side-effect test](../../../tests/get-side-effects.mjs) covers it like every other read.

**Accepted target, not live:** [ADR 0217](../../adr/0217-source-independent-film-admission.md) (architecture only) plans an owner-only re-check route and an `eligibility` field of the unified Film read for lid-only Films. No such route or field exists, and this catalog route is unchanged.

## What it reads

| Object | Use |
| --- | --- |
| `epg/published-generation.json` | The generation pin. When the pointer names a published generation, the programme and the catalog are read **only** from that generation's copies (`epg/generations/<runId>/…`); an absent copy fails closed with `409` instead of falling back to the shared public keys, even when those keys already carry the new run id |
| `programme.json` | The watchlist films of that generation (exclusion by id and TMDB identity) and the run id the response is pinned to |
| `epg/discovered-films.json` | The catalog records: identity, display fields, credits, `aliases` and `movieTitles` (the titles TMDB gave the movie; absent on a record that no detail read has rewritten, see [ADR 0158](../../adr/0158-epg-title-alias-provenance.md)), the shows of the generation that last confirmed them |
| `watchlist.json` | Further watchlist ids and TMDB identities to exclude, including films without a programme show |
| The D1-derived view index ([contract](../domain/view-index-read-model.md); no stored object) | The current prediction and fingerprint facet, the owner's `watched` and `actualRating` per id (see [Watched and rated films](#watched-and-rated-films)), and a `watchlist` boolean when a fact recorded one (see [Watchlist facts](#watchlist-facts)) |
| `enrichment/profile/current.json` | The profile version and hash a prediction must match to be current |
| `letterboxd/display-exclusion.json` | On every request: the private list of normalized names and years for the [display-only title exclusion](#display-only-title-exclusion) |
| `metadata.json` | The frozen Letterboxd metadata cache of films that are or were on the watchlist, read for the stored TMDB id of a Letterboxd id (see [Watched and rated films](#watched-and-rated-films)) and for a poster fallback: a catalog record without its own TMDB poster takes the cached `https://` poster of the record with the same stored id (whose cached TMDB id is the same or absent), or of the same TMDB id. Every cached record for that stored id, and every cached record for that TMDB id, must carry the same poster: once two disagree the key stays conflicted regardless of further records or their order, and a conflicted TMDB identity yields no poster even through the stored-id match. Production never reads it: only at Film/Person `open` are the same fields served, from bounded D1 (`catalogMetadataFromD1`: `film_metadata` poster/year/url, localization title, and a TMDB id only when every `film_external_id` claim of that value is the one owner's trusted non-conflicting row). The Film/Person marker is captured once for the request and re-read after `predictionFreshness`, immediately before a successful answer. `held`, an installed `r2` or `prepared` marker, an unreadable marker and a generation move are `503` with no R2 fallback; only the explicit local stand-in reads the object. No other field is taken and nothing is fetched |

When `published_epg_authority.mode` is `d1`, the pin is that D1 generation ([ADR 0079](../../adr/0079-d1-authoritative-published-epg.md)). `programme.json` and `watchlist.json` are not a fallback, and a stale `epg/published-generation.json` is not the pin. The catalog copy is still `epg/generations/<run>/discovered-films.json` for that same run. A missing copy fails closed and is not replaced by another run. Until the marker is activated, the table above is the live read. Production has not applied migration `0008`.

The ratings seed compiled into the Worker is applied to an in-memory copy of the derived view index. `GET /api/enrichment/view` uses the same layer and nothing persists it. `started/` markers are not consulted: they belong to the watchlist UI and are not a watched signal for catalog films.

## Eligibility

A catalog record is returned only when every rule holds:

1. **Verified identity.** The record has a `tmdbId` and `canonicalIdentity` equal to `tmdb:<tmdbId>`. An observation key or a record without a verified identity is not a film here.
2. **Outside the watchlist.** Neither its id nor its TMDB identity appears among the programme's films or the watchlist's films. A watchlist film without a scheduled show is still a watchlist film. A view-index entry whose `watchlist` field is a boolean, either value, also excludes that catalog id. See [Watchlist facts](#watchlist-facts).
3. **Not watched and not rated.** Neither the record's own id nor any other id of the same TMDB film is watched or rated in the view index, after the compiled ratings seed. See [Watched and rated films](#watched-and-rated-films).
4. **Current prediction.** The stored prediction matches the current profile version and hash, the stored fingerprint hash, fingerprint schema version 1 and prediction prompt version 1; a prediction the shared evaluator keeps across profile versions also counts ([prediction compatibility](../domain/prediction-compatibility.md#one-rule-for-every-consumer)). Without a profile nothing is current and the list is empty.
5. **Real shows of the pinned generation.** The record's `shows` were written by the pinned generation (`showsProgrammeRunId` equals the response's `programmeRunId`). Shows carried over from an earlier generation are not availability in the new one. `epgLastAiring` alone is not a show.
6. **Inside the window.** (The catalog keeps its 24-hour hot future bound; the 168-hour retention of [EPG horizons](../domain/epg-horizons.md) applies to watchlist shows only.) At least one show starts strictly after `now − 72h` and strictly before `now + 24h`. A start exactly 72 hours ago has expired; a start exactly 24 hours ahead is outside the horizon. Only shows inside the window are returned.
7. **Not hidden by the display-only title exclusion**, when its list is valid. See [Display-only title exclusion](#display-only-title-exclusion).
8. **Not a proven Documentary or concert recording.** The same ADR 0150 `admissionPolicy` as `GET /api/programme`: stored genres/genre ids, title/aliases and synopsis-as-overview. No TMDB lookup. Ambiguous Music-only Live tokens stay.

### Watched and rated films

A view-index entry is **consumed** when it has `watched: true` or a non-null `actualRating`. `watched: false` alone, or `actualRating: null` alone (a watchlist film the films list shows without a rating, or an explicitly cleared rating), is not. A rated film is never returned, so a prediction never stands in for an actual rating, and the response carries no `watched` or `actualRating` field.

A catalog record is excluded when its own entry is consumed, or when any consumed entry belongs to the same TMDB film:

- an entry keyed `tmdb_<n>` belongs to TMDB id `n`;
- an entry keyed by a Letterboxd id belongs to the TMDB id stored for that Letterboxd id in `metadata.json`, in `watchlist.json`, in the programme or on a verified catalog record with that id, and only while every one of those stored values is the same. A Letterboxd id with two different stored TMDB ids, or with none, excludes only a catalog record with that very id.

Titles, years and aliases are never compared, so a remake or a namesake of a watched film is still offered. A watched export film without an accepted identity is therefore not excluded by this rule; the separate [display-only title exclusion](#display-only-title-exclusion) covers part of those films and never counts as identity. The [fact projection](../integrations/letterboxd-user-facts.md#projections), the only writer since the retired `LETTERBOXD_FACTS` switch ([ADR 0055](../../adr/0055-retire-letterboxd-facts-switch.md)), writes `watched` and `actualRating` under every trusted alias of a film (its Letterboxd id and `tmdb_<n>`), and the stored TMDB id covers a record that has only its Letterboxd id; index entries written before the facts model hold ratings under the Letterboxd id, and the stored TMDB id carries them to the `tmdb_<n>` record. The route reads neither the fact records nor the link index, so it stays a bounded read of fixed keys. Watchlist exclusions are unchanged and independent of these facts: a watched film that is on the watchlist again (a rewatch) stays on the watchlist and is excluded as a watchlist film.

### Watchlist facts

A view-index entry excludes its catalog id when `watchlist` is `true` or `false` ([ADR 0086](../../adr/0086-durable-watchlist-film-retention.md), Accepted). The same boolean on a Letterboxd lid also excludes a catalog row `tmdb_<n>` when that lid bridges to `n` by the same stored-id rule as [watched and rated films](#watched-and-rated-films): one agreed id from the metadata cache, the watchlist, the programme or a verified catalog record. Two stored ids, or none, leave the lid unbridged. Titles are never compared. `false` is a recorded removal. It is not a watched mark, it does not delete the Film, and it does not put the film on the watchlist grid. A missing `watchlist` field leaves this rule unused. The route still does not read the fact records.

One entry per canonical identity: when two records share a TMDB identity, the one whose availability ends later is kept, then the smaller id. The list is ordered by the end of the 72-hour window of the latest returned start (an internal key, no longer a response field), then id, so the same stored state always produces the same order.

### Display-only title exclusion

A separate, weaker rule hides a catalog film that matches a watched or rated Letterboxd export film which has no accepted identity ([ADR-0028](../../adr/0028-finds-display-only-watched-exclusion.md); namesake guards relaxed for the `strict_original_exact_year_v2` tag by [ADR-0033](../../adr/0033-finds-exclusion-namesake-relaxation.md)). It only removes the film from this response: it writes nothing, links no Letterboxd id to a TMDB id, records no fact or rating, and no other route reads it. The watchlist, the programme, predictions and the taste profile are unaffected.

**No switch.** The rule runs on every request ([ADR 0041](../../adr/0041-retire-finds-title-exclusion-switch.md)). The former `FINDS_TITLE_EXCLUSION` variable is retired and inert whatever it holds (see the [flag register](../feature-flags.md)). Whether films are hidden depends only on the list object: without a valid list nothing is hidden.

**The list.** One private R2 object, replaced only as a whole, built offline by `scripts/letterboxd-display-exclusion.mjs` and placed by a separately approved operation ([runbook](../../runbooks/finds-display-exclusion.md)); the Worker has no writer for it.

The builder writes the `strict_original_exact_year_v2` tag. It lists a watched or rated export film that has no accepted identity, a year and a non-empty normalized name. When other export films (in any list, identified or not) share that name, it lists the film only if every one of them has a year, the watched or rated ones have pairwise different years, and every watchlist-only one is at least two years from every watched or rated one; otherwise the name is dropped as a whole (`droppedExportNamesake`). `keptExportNamesake` counts the entries whose name the export carries more than once. A list with the legacy `strict_original_exact_year` tag, built when every repeated name was dropped, is still read with the legacy catalog guard below.

```json
{"schemaVersion": 1, "kind": "letterboxd_display_exclusion", "rule": "strict_original_exact_year_v2", "normalization": "normTitle_v1",
 "source": {"type": "letterboxd_export", "archiveSha256": "<64 hex>", "exportedAt": "<ISO time>", "baselinePlanSha256": "<64 hex>"},
 "builtAt": "<ISO time>", "counts": {"exportFilms": 0, "withIdentity": 0, "droppedNoYear": 0, "droppedNoName": 0, "droppedExportNamesake": 0, "keptExportNamesake": 0, "entries": 0},
 "entries": [{"title": "<normalized name>", "year": 2000}], "contentSha256": "<sha256 of JSON.stringify(entries)>"}
```

The list is used only when every check passes; otherwise the rule is `unavailable` for that request, every film is shown and the route still answers `200`:

- the R2 object size is at most 2 MiB, checked before the body is read or parsed, and the body is valid JSON;
- exactly the keys above at the top level and in `source`; `schemaVersion`, `kind` and `normalization` have exactly the values above, and `rule` is `strict_original_exact_year` (legacy) or `strict_original_exact_year_v2`; any other tag is invalid; `source.type` is `letterboxd_export` with lowercase 64-hex `archiveSha256` and `baselinePlanSha256`;
- `exportedAt` and `builtAt` are ISO dates, `exportedAt` is not after `builtAt`, and `builtAt` is not more than five minutes in the future;
- `counts` holds non-negative integers (any names) and `counts.entries` equals the number of entries; at most 20,000 entries;
- every entry has exactly `title` and `year`; `title` is a non-empty string of at most 300 characters that is already normalized; `year` is an integer from 1870 to 2100; entries are strictly ascending by `title`, then `year`, so a duplicate is invalid;
- `contentSha256` is the SHA-256 of `JSON.stringify(entries)`.

There is no age limit: a list older than the latest export only misses films watched since, which Finds would show anyway.

**Normalization.** `normTitle_v1`: NFKC, lower case, `ё` as `е`, every run of characters that are not letters or digits as one space, trimmed. It is `normTitle` of `src/letterboxd-match.js`; the Worker carries an identical copy, and a test keeps them equal.

**The rule.** Evaluated on every request against the pinned generation's catalog copy, after rules 1–6, so only films the response would otherwise offer are counted. A verified record is hidden when all hold:

1. it has an integer `year`, and its normalized **original** title and that year equal an entry exactly; the localized title and aliases never match;
2. catalog uniqueness, which depends on the list's `rule` tag:
   - `strict_original_exact_year`: no verified record of another TMDB film in the same catalog copy has that normalized key as its original title, localized title or alias, in any year;
   - `strict_original_exact_year_v2`: no verified record of another TMDB film has the key as its original or localized title, in any year; and every other TMDB film that carries the key only as an alias (no record of it has the key as its original or localized title) has, on every verified record, an integer `year` at least two years from the record's year. An alias-only namesake without a year or within one year blocks, because the export name may be that film's English title;
3. its TMDB id has no stored Letterboxd id in `metadata.json`, `watchlist.json`, the programme or a verified catalog record keyed by a Letterboxd id; such a film is decided by identity alone.

Nothing is stored: a new generation is evaluated afresh, so a film can be hidden in one generation and shown in the next when a namesake enters or leaves the catalog. Entries are unique by title and year, and a record has one original title and year, so at most one entry matches a record.

The three add up to `total`. It lets a plain read show how many available films still have no stored asset; it is not a per-film field, and `films[]` is unchanged |
| `watchedMarkEnabled` | Always `true`, so the client knows the [owner watched mark](#owner-watched-mark) can be offered. The mark has no switch: the former `FINDS_WATCHED_MARK` ([ADR 0042](../../adr/0042-retire-finds-watched-mark-switch.md)) and `LETTERBOXD_FACTS` ([ADR 0055](../../adr/0055-retire-letterboxd-facts-switch.md)) are retired and inert |
| `displayExclusion` | The [display-only title exclusion](#display-only-title-exclusion): `state` is `applied` (valid list used) or `unavailable` (list missing, unreadable or invalid; nothing hidden). The former `off` state is gone with the switch ([ADR 0041](../../adr/0041-retire-finds-title-exclusion-switch.md)); `excluded` counts the canonical identities hidden from `films` by it. It never carries a title, id, code or any hash of the list or its source |
| `programmeRunId`, `pinned` | The generation the response is derived from. `pinned: false` means no published pointer existed and the programme's own run id was used |
| `generatedAt`, `window` | The clock the statuses were derived with and the availability envelope `(now − 72h, now + 24h)` |
| `profile` | The profile version predictions were checked against, or `null` |
| `films[].poster` | The record's own TMDB poster URL when the discovery writer stored one, else the cached Letterboxd poster of the same stored id or TMDB identity, else `null`; always a stored `https://` URL, never constructed |
| `films[].shows[].status` | The per-show phase of the [lifecycle](../domain/film-availability.md): `future` (not started), `on_air` (started, before its effective end), `archive` (ended, still inside the 72-hour catch-up counted from its start), `expired` (ended, past the catch-up; only the film page can return one, the list window excludes them), `unknown` (started and no valid end can be determined). A show whose end cannot be determined is `unknown`, never `archive` |
| `films[].shows[].end`, `effectiveEnd` | `end` is the EPG end or `null`. `effectiveEnd` is the end every rule uses: the EPG `end`, else start + the film `runtime` in minutes, else `null` (never invented). Schedule-based, not a provider probe |
| `films[].availableNow` | `availability.state === 'available'`: a ready recording exists. A show on air does not count |
| `films[].nextStart` | The earliest returned show that has not started, or `null` |
| `films[].availableUntil` | `availability.archiveUntil` as an ISO time (the latest ready show's start + 72 hours) when the film is `available`, otherwise `null`. A future repeat never extends it |
| `films[].availability` | The [film availability lifecycle](../domain/film-availability.md) ([ADR 0114](../../adr/0114-film-availability-lifecycle.md)): `state` (`available` / `soon` / `unavailable`), `label` («Доступно» / «Скоро» / «Недоступно»), `appearsAt` (`soon`: the earliest known effective END of the show that will become the archive, milliseconds, else `null`; a schedule-based calculation, not verified availability at the provider), `appearsAtKnown` (`false`: do not promise an hour), `appearsAtEstimated` (`true`: that end was derived from the film runtime, `false`: the EPG gave it), `archiveUntil` (`available`: latest ready start + 72 h, milliseconds) and `onAir`. An archive outranks a repeat or a show on air; a show on air is not an archive until its effective end; a show whose end cannot be determined is never a ready recording. Both catalog endpoints take `availability`, `availableNow`, `availableUntil` and every `shows[].status` from this one helper, with `film.runtime` as the fallback for a missing or invalid EPG end |
| `films[].prediction` | The stored current prediction: rating, probability of 4+, the model's `confidence`, match signals, main risk and the canonical mood ids. When the snapshot has the `confidenceAssessment` key, that value is copied even if it is `null`, and `fingerprintHash` is copied with it. A snapshot without the key omits both. The route does not recompute the assessment |
| `films[].fingerprint` | The fingerprint facet (plot mechanics, mood ids, the general execution dimensions without `unknown` / `not_applicable`) when the stored fingerprint is the one the prediction was made from, otherwise `null` |
| `channels` | One row per channel id with the number of returned films that have a show on it, for channel and period filters on the client |

Not included on purpose: synopsis, aliases, the raw prediction and fingerprint objects, the mood vocabulary and `moodGroups` (served by `GET /api/enrichment/view`), and any ranking. Thresholds, ordering for display and franchise de-duplication are consumer decisions. Catalog `moodIds` stay the full derived set used to match a Finds filter. The watchlist grid's one-to-three chips, including a hidden generic theme, are the [taxonomy contract](../domain/taxonomy.md) and use the view, not this route. A Finds card still shows at most two mechanic or mood labels from this payload.

## Consumers

### `letterboxdUrl`

`url` is the TMDB page and is never a Letterboxd link. `letterboxdUrl` is an **optional, read-only** field of a returned film (AIR-382); it is absent, not `null`, when it is not proven. It is built by `catalogLetterboxdUrls` in `src/worker.js` from stored records only, with no lookup and no slug guessing: a record of the metadata cache, the watchlist or the programme that carries a Letterboxd id (not a `tmdb_<n>` id), the film's TMDB id and a canonical `https://letterboxd.com/film/<slug>/` URL, while that Letterboxd id bridges to exactly this one TMDB id across every stored record (`catalogLidTmdb`) and every proving record of the TMDB id gives the same URL. Two Letterboxd ids with different URLs, an ambiguous id, a malformed or non-canonical URL, or only a title/year match yield no field. The client validates the value again with the same pattern before it draws the icon (new tab, `rel="noopener noreferrer"`), so an unknown or unsafe value is ignored and consumers must treat the field as absent-compatible.

**Coverage and the TMDB redirect (AIR-384).** Only a film that stored records already tie to a Letterboxd page carries `letterboxdUrl` (typically one that was once on the watchlist and is still in the metadata cache); the endpoint is unchanged and no field is added. For every other catalog film the page shows a **navigation aid, not an identity**: when `canonicalIdentity` is exactly `tmdb:<n>` and agrees with a positive-integer `tmdbId` (at most 12 digits), the icon links to Letterboxd's own documented redirect `https://letterboxd.com/tmdb/<n>`, labelled «Открыть в Letterboxd по TMDB id». It is computed in the browser from fields the response already has, never stored, never written back to `letterboxdUrl` or an identity record, and nothing is fetched to check it; Letterboxd resolves it (or shows its own error page) when the viewer clicks, and a click on a film Letterboxd has not imported may start that import on their side. A stored canonical `letterboxdUrl` always wins over the redirect; the film's `url` (TMDB) never does, even when it happens to look like a Letterboxd film URL. TV identities (`tmdb_tv:`), a missing, mismatched or malformed id or identity, and a title/year-only match get no icon. Consumers must not treat the redirect address as proof that the film exists on Letterboxd.

The watchlist page's **«Находки»** section (`public/app.js`, `#finds`) is the first consumer. It reads this route on page load and with the other live refreshes, after the programme and the view and before the footer, never at the same time as another of those large reads (AIR-586: together they exceeded the Worker memory limit), and never adds a show or a prediction of its own. A cached answer is shown only while the loaded programme's run id equals the answer's `programmeRunId`: when the programme moves to a new generation the section is hidden until this route answers for that generation (a `409` during publication keeps it hidden), and an answer for a generation the programme has not reached yet waits for the programme; a failed refresh on the same generation keeps the last answer. On every render it re-checks each returned film against the loaded programme and view index (a film that has since entered the watchlist or received an actual rating disappears), re-derives the shows inside `(now − 72h, now + 24h)` with the browser clock (an expired catch-up hides the film without a new request), and keeps only a current prediction with `predictedRating ≥ 4.0`, `probability4Plus ≥ 0.70` and an effective confidence other than `low`. Effective confidence is the model's `confidence` when `confidenceAssessment` is absent. When the key is present it is the assessment `level` only if that object is a bound version-1 assessment of this snapshot's `fingerprintHash`; otherwise it is `low`, including a `legacy` or `insufficient` status. The rating and probability thresholds are unchanged. The remaining films are ordered by `predictedRating`, then `probability4Plus`, then the nearest end of availability; one entry per canonical identity; an adjacent franchise part (same title stem after a trailing sequel number or «часть N») with identical rating and probability is skipped; at most five are shown and the list is never padded with weaker films. The section is hidden entirely when nothing qualifies. Each card carries the `NEW` badge at the top left of the poster, meaning a film outside the watchlist, not a new release; the usual title, year, poster and prediction; up to two mechanic or mood labels from `fingerprint` and `prediction.moodIds`; and the relevant airing (on air now, the next start, or the catch-up deadline). The title opens the internal film page `/film/tmdb_<n>` ([below](#permanent-catalog-film-api-catalog-film-tmdbid)) when the identity is verified, and is plain text otherwise; it never links to TMDB. A Letterboxd icon (the shared `letterboxdLink`) is shown for a valid `letterboxdUrl`, or, when there is none and the film has a verified `tmdb:<n>` identity, for Letterboxd's `/tmdb/<n>` redirect ([below](#letterboxdurl)); a catalog film's own `url` is its TMDB page and is never read as a Letterboxd link. A catalog-only title in the similar-films list is plain text as well, with the same icon rule. Filters narrow and re-rank the section on the client ([Filter context](#filter-context)); they do not change this route.

**«Смотрел».** While `watchedMarkEnabled` is `true`, each card has a «Смотрел» button.
- **Mark.** It posts the card's TMDB id to [`POST /api/catalog/watched`](#owner-watched-mark). While the request runs, the button is disabled and reads «Сохраняю…».
- **Success.** The card leaves the section at once, before the next catalog answer. A notice above the cards says the film is marked and offers «Отменить», which posts `watched: false` and brings the card back.
- **Failure.** The card stays with an inline alert, and the button can be pressed again. A `film_not_in_catalog` answer also reloads the section.
- **Disabled.** Without `watchedMarkEnabled` no button is shown.

**Archive first and the «Скоро» mark.** The section reads the film's [availability lifecycle](../domain/film-availability.md) with the same shared module the Worker uses (`/film-availability.js`), over the film's shows inside `(now − 72h, now + 24h)` on the selected channels, the film `runtime` as the fallback for a show without a valid end, and the browser clock, so a card and the entry's `availability` never disagree (the client and the Worker are compared in the catalog tests). A film with a ready archive is always `available`: the airing line names the archive («Архив · канал · до …») even when a repeat is nearer, and no hourglass is shown. A film with no ready archive that is on air, or starts inside the next 24 hours, is `soon`: the line names the show whose effective end is the expected archive time (with overlapping shows, the one that ends first, so the channel and the time always belong together; with no promised hour, the show on air or else the nearest start) and stays short: «Сейчас в эфире · канал» for a show on air, «дата, время · канал» for a show ahead. It never repeats the expected archive time or promises one: the hourglass beside it already says «Скоро», and its label (`aria-label` and `title`) carries the expected time from that effective end (the EPG end, else start + runtime, marked «по длительности фильма»), or «время появления архива неизвестно» when no end can be determined and no hour is promised. The same short line is used on the similar-film cards. A started show with no determinable end is neither. The expected time is a schedule-based calculation, not a provider check. On equal predictions a ready archive is ranked before a `soon` film.

**Poster mark.** A `soon` film carries one small hourglass in the top right corner of its poster (`.soon-badge`, `role="img"`, the text in `aria-label` and `title`), opposite the NEW mark and separate from «Последний шанс». It is written by one function (`soonBadge` in `public/app.js`) and applied to the list cards, the Finds cards, the similar-film cards and the film page poster, with no mark on a film with a ready archive, including one with a future repeat. A poster container is positioned (`.poster-frame`, `.finds-poster`, `.film-similar-poster`, `#film-poster`); a film without a poster keeps the mark on the placeholder. The mark is computed at render time and a live page re-renders at the moment the archive is expected, so it disappears when the archive appears without a new request or a new programme. The timer is armed after every surface, the film page included, has rendered, so a film page opened on its own is covered.

**Channel and period scope.** While the page's channel filter is active, the watchlist grid and the finds become two sections of the same channel and period scope. The grid gets the heading «Из watchlist» and the section is titled «Находки на выбранном канале» (or «…на выбранных каналах»). Only shows on a selected channel count, several channels combine with OR, and the selected period tab is a hard constraint on the lifecycle state over those shows: `archive` keeps films with a ready archive, `future` («Скоро») keeps films with no ready archive that are on air or ahead, so a film with an archive and a repeat is not returned there, `all` keeps both, and the black zone has no finds. A film whose only shows in that scope are on another channel or in another state is not a find. The same thresholds, ordering (with the end of availability taken from the scoped shows), de-duplication and limit apply, and the airing line names a show on the selected channel. An empty section is not shown; the shared «Таких фильмов не найдено» state appears only when both sections are empty. Clearing the channel filter restores the plain section. A period tab other than «Все показы» without a channel scopes the shows the same way (the title stays «Находки» and the caption names the period). The URL keeps its existing `channel` and `period` parameters; nothing new is requested from this route.

<a id="filter-context"></a>**Filter context.** The section answers the page's other filters from the fields this route returns, on the catalog answer already loaded: a filter change, a restored URL or Back/Forward re-ranks it without a request. Every selected filter is a hard constraint, with the same rules as the watchlist grid: AND across filters, OR within a multi-select.

**«Похожие фильмы»** on the film page (`#film-similar` in `public/app.js`) is the other consumer. It is not the Finds section and it does not follow the page's filters, channel scope, period or selected person. It reads the answer this route already cached for Finds, and only while that answer's `programmeRunId` is the loaded programme's run id; a new generation or a `409` hides those candidates instead of showing the previous generation. A failed refresh on the same generation keeps the last answer, as Finds does. On every render it re-checks each returned film the same way: gone once it is on the loaded programme, gone once the enrichment view already loaded confirms that film is watched or rated, and gone once none of its shows still starts inside `(now − 72h, now + 24h)`. The confirmation is that film's own view entry, the `tmdb_<n>` entry of its verified `tmdb:<id>` identity, or a Letterboxd id that the loaded programme rows and the verified catalog rows agree maps to that TMDB id. A Letterboxd id with two stored TMDB ids, or with none, does not bridge, and a shared title does not either. `watched: false` without a rating does not remove the film. A stored rating does, including when that same entry says `watched: false`. This check uses only those loaded objects. It does not call this route again, and a film this route already omitted stays omitted.

The second source is the watchlist films already loaded with the programme, not this route (this route has excluded them). A loaded film marked catalog-only is not that watchlist source. Each candidate needs a real show in the same window. The open film is excluded by its id and, when both sides carry a verified `canonicalIdentity` of `tmdb:<id>`, by that identity. A catalog row whose verified identity is the open film's stored `tmdbId` is the same exclusion Finds already uses; a shared title or year is not. Credits match only when the id string is the same. A Letterboxd id and a TMDB id are not joined, and a shared name is not a match. There is no person-identity request.

A catalog candidate is eligible only when its own prediction already passes the Finds floor, and that check happens before either source is ranked: `predictedRating` is a finite number of at least 4.0, `probability4Plus` is a finite number of at least 0.70, the effective confidence defined above is a non-empty string other than `low`, and the prediction is not stale. The fallback prediction copies `confidenceAssessment` and `fingerprintHash` when the view already has them, so a reduced rating object does not drop the key and fall back to the model field. A missing or non-finite number fails the floor. A shared mechanic, director, actor or execution value does not waive it. A film under the floor is not ranked and is not used to fill a later slot, so one qualifying catalog film stays one card. A watchlist film is not held to that floor. A stored actual rating plus a substantive overlap stays on the watchlist path, including when that film's forecast is weak, stale or missing.

The two sources are ranked separately, using only stored fields, and only after that catalog floor. Shared plot mechanics come first, and a shared mood counts only together with a shared mechanic. A shared director id, then shared actor ids, then a concrete execution value (not `unknown` or `not_applicable`) follow. A shared genre does not rank and does not qualify a film on its own. Inside one source the current stored `predictedRating` and `probability4Plus` break ties, then the nearest end of availability, then the canonical id. A stale or missing prediction is not a number and is not shown. When both sources have a candidate, the page keeps that order and shows up to four watchlist films first, then catalog films in the slots that remain, eight in total. A source with no candidate lets the other source use all eight. A short list is not padded, and a watchlist film past the first four is not brought back after the catalog films.

The reason on a card is one real overlap: at most two shared mechanic labels, with one shared mood after them when a mood is shared, otherwise a shared director, shared actors, one concrete execution value, or, when nothing substantive is shared, «Подходит по прогнозу». The same reason signature is used at most twice across the whole slate. Diversity applies only among films that are already eligible, and only inside the strongest reason that film can still show. While a shared mechanic, a shared director or actor, or a shared plot engine is still under that cap, a generic execution value such as payoff, competence or adversarial goals is not chosen instead, and an unused signature is preferred only inside that strongest tier. A second copy of a mechanic label is kept before the card switches to a person. A generic execution value does not rescue a film whose stronger reason is already capped. A film whose only overlap is that generic value can still appear, after the stronger matches, when it is a watchlist film or a catalog film that passed the floor. A further film with only a signature already used twice is left out. A second film of the same franchise (the Finds title stem) is kept only when the reason it shows does not repeat a mechanic already shown for that franchise, including the same mechanic with a mood, and that reason is a mechanic, a person or a plot engine. A generic execution value and the prediction-only label are not a second franchise entry. Nothing is added to fill the eight. No strong match hides the whole section.

Every Similar card, like every Finds card, shows «МОЯ ОЦЕНКА» and «ПРОГНОЗ» independently (AIR-517): each badge exists only when its fact does, so a Finds card, whose film is by eligibility neither watched nor rated, normally has the forecast badge alone. `GET /api/catalog/available` and its DTO are unchanged, and the own rating comes only from the already loaded enrichment view entry for the card's id.

A watchlist film is «Пересмотр» when its loaded view entry has `watched: true` or a stored `actualRating`, and it still needs a substantive match. `watched: true` with no shared mechanic, person or execution is omitted, so it is never labeled «Подходит по прогнозу». A stored rating is enough when the same entry says `watched: false`. `watched: null`, a missing `watched` and a non-boolean are unknown: the film stays «В watchlist», which does not claim a first viewing, and a strong forecast may use the prediction-only label. `started` is not watched. `NEW` is only the catalog source. A watchlist card uses the neutral film-card surface. A catalog card uses the Finds green surface and the `NEW` badge. Both follow the Finds card: the poster already stored on the loaded film, or the same year placeholder Finds uses when that film has no poster, the original title, year and runtime when they are present, the show line, the reason, and the usual corner badges. The corner shows only the badges that exist: «МОЯ ОЦЕНКА» (a stored half-star rating 0.5 to 5.0) and «ПРОГНОЗ» (a fresh stored prediction), in that order. One fact is one badge, two facts are two, and with neither the card has no `film-score-badges` at all. A missing, stale or invalid value renders no badge: no placeholder, no «—», no reserved space, never 0.0 and never the other number. The rating is found under the card's own id and under the other spelling of the same Film only where the loaded data verifies it (a Letterboxd id and a TMDB id that the loaded programme and verified catalog rows agree on); a conflicted, ambiguous or disagreeing mapping renders no own-rating badge, and a title, year or slug is never matched. The page does not request a poster. A watchlist film opens with the usual film route. A catalog film that is not in the loaded programme and has a verified TMDB identity opens the internal film page `tmdb_<n>`; without one its title stays plain text. A card never jumps to TMDB. On the film page the synopsis, credits, history, comparison and availability stay in a 760px column. This grid uses the rest of the page, which is at most 1280px wide, so the cards sit in more than one column on a desktop viewport and fill the column they are in. Below 760px the grid is one column.

## Owner watched mark

`POST /api/catalog/watched` records the owner's statement that they have watched, or have not watched, one verified catalog film ([ADR-0032](../../adr/0032-owner-watched-mark-by-tmdb-identity.md)). It writes only the owner's `watched` fact through the [user facts](../integrations/letterboxd-user-facts.md#owner-watched-mark) and its projection. It never writes a rating, the watchlist, a prediction, the catalog or a Film/Person record. It does not link a Letterboxd id and never reads a title or year.

```json
{"tmdbId": "603", "watched": true}
```

**Guards**, checked in this order. A refused request writes nothing:

| Check | Refusal |
| --- | --- |
| Method is `POST` | `405` |
| `Origin` header present and equal to the Worker's origin (stricter than the shared check, which lets a request without `Origin` through) | `403` |
| `Content-Type` is `application/json` | `415` |
| Body is at most 512 characters of JSON, an object with exactly `tmdbId` (a string of digits) and `watched` (a boolean) | `400`, `code: invalid_request` for a wrong shape |
| A catalog is readable for the published generation, by the same pinned, authority-aware read as `GET /api/catalog/available`: Discovery on D1 reads the D1-owned catalog (no R2 copy exists), Discovery on R2 reads the generation's own R2 copy. There is never a fallback to another source. It holds a record with that `tmdbId` and `canonicalIdentity` exactly `tmdb:<tmdbId>` (an observation key, a pending or superseded admission or a conflicting identity does not) | `409`, `code: film_not_in_catalog` |
| The catalog could be read at all. Technical unavailability is never reported as a missing film | `503` with `code`: `catalog_not_published` (no published generation), `catalog_generation_unavailable` (no catalog for the published generation, including a D1 authority on another generation), `discovery_fence` (cutover held), `discovery_incomplete`, `discovery_unavailable`, `discovery_not_authoritative`, `catalog_read_failed` |
| The publication and the Discovery authority are unchanged between that read and the write: same publication run, phase and fence, and the Discovery authority read again immediately before the write has the same mode, cutover, generation, programme run and transfer state as when the catalog was read, is not held and (on D1) not loading. A switch between D1 and R2 counts as a change. The R2-owned path stays R2-owned and does not require D1 | `503`, `code: catalog_generation_changed`, `discovery_fence` (held) or `discovery_incomplete` (loading); nothing is written |

**Response** `200`: `{"outcome": "saved" | "unchanged" | "older", "watched": <current value>}`, and nothing else from the record.
- `unchanged`: the value already was the current effective value, and nothing was written.
- `older`: a concurrent, later observation is current.

A write that keeps losing compare-and-swap answers `409` with the facts error code. The route is behind the Worker's owner-only Access application, is not an MCP tool and is not called by any Scheduled Task.

## Permanent catalog film (`/api/catalog/film/<tmdbId>`)

`GET /api/catalog/film/<tmdbId>` (AIR-387) returns **one** verified catalog film for the permanent film page `/film/tmdb_<n>`, whatever its shows, prediction or watchlist state say. It is a bounded read-only lookup: one indexed row (`media_kind`, `tmdb_id`) of the Discovery admission, not a scan of the catalog and not `GET /api/catalog/available`, which is limited to the hot window and to eligibility. It performs no R2 or D1 write, no model call, no TMDB or Letterboxd call and no sync, and is covered by the [GET side-effect test](../../../tests/get-side-effects.mjs). `<tmdbId>` is a positive integer without a leading zero, at most 12 digits; anything else is `400`.

**HTML document status (AIR-531).** A direct `GET` or `HEAD` of `/film/<id>` serves the same SPA shell with the HTTP status the page will show; the status of the internal `/api/catalog/film/<tmdbId>` is not the status of the document, so the Worker decides it in the order of the SPA (`resolveFilm`, `filmDocumentStatus` in `src/worker.js`). (1) An id that is a programme or watchlist member of the pinned published generation (one indexed `published_epg_member` read, `kind IN ('programme','watchlist')`, following the `(programme_run_id, kind, film_id)` index) is `200` whatever the catalog says, a `tmdb_<n>` id included. (2) A `tmdb_<n>` id then asks which published films own that TMDB id through their trusted `tmdbLink` (`tmdbId` and a `resolved` movie link to that id, the page's rule), **before** the catalog, as the page does: one owner is `200` (the page shows that film), several owners are `409` even when the catalog holds the Film. (3) The bounded catalog identity decision (`catalogFilmIdentity`: Discovery admission, canonical fallback, retirement and conflict rules; no programme, watchlist, metadata, prediction or ratings read, no write, no outbound request) gives `404` absent or a malformed TMDB id, `410` retired, `409` conflict, `200` found. (4) Any other id that is no member is `404`. No published generation at all (no D1 binding or pointer) has no members, so the catalog answer stands for a TMDB id and any other id is `200`.

**Owner map and its cost.** `published_epg_member` has no TMDB column ([ADR 0142](../../adr/0142-epg-owned-generation-addressed-discovery-slots.md) decision 4), so `PublishedEpg.memberTmdbOwners(env, run, generation)` builds the map tmdbId -> member film ids from the sealed programme and watchlist documents. Those documents are **not** fixed for a run: `saveWatchlist` and `patchProgramme` replace one of them in place and advance the publication generation. The map is therefore keyed by `(database, run, generation)` (the last key only) and the build is fenced: the generation must be unchanged after both documents are read, otherwise it throws `published_epg_fence`. Cost (read-only measurement of production D1 on 2026-11-18: programme 37 rows, 1.95 MB; watchlist 23 rows, 1.19 MB; 62 rows read in total): a cold build reads those rows once per isolate and generation and parses about 3.1 MB (about 6 ms of CPU for documents of that size, measured locally); a warm request reads no document row. D1 transfer latency and Worker memory of a cold build were not measured. It is not an indexed point query: a D1 column or table of member TMDB ids would remove the cold build and is a separate migration decision (schema 25, ADR, owner GO), not part of AIR-531.

**Unknown is never absence.** Only a definite answer sets a non-`200` status. When the generation, the member read, the owner map (including a fence failure) or the catalog cannot answer, nothing is proven absent and the shell is `200`; the page then decides and shows its own temporary error. A catalog `404`, `410` or `409` is used only when the published side was read completely. Non-`200` documents carry `Cache-Control: no-store`. Client-side navigation cannot change an issued status, so a film opened from the SPA keeps its document status and shows the same error page.

**Source.** With `discovery_authority` on `d1` / `open` the row of `discovery_admission` for the movie id is read (a ledger seal in progress is readable, a catalog or decision load in progress is not); while Discovery is still on R2 the one shared `epg/discovered-films.json` is filtered by the same identity; a **missing or malformed** catalog object there is an unreadable source and answers `503 unavailable`, never `absent` (an existing empty catalog is a real absence). The generation is read through `epgPublicationReadOnly`: `currentGeneration` and the fenced `readDocumentAt` use SELECTs only, so, unlike `GET /api/catalog/available`, this route does **not** run the R2 mirror repair that `epgPublication` performs for a D1 generation; a missing or stale compatibility mirror is neither written nor consulted. A record counts only when it is verified: row identity and payload agree on exactly `tmdb:<n>`, `tmdbId` equals the route, and the payload `id` is the row id.

**Canonical fallback (AIR-409, AIR-475).** When Discovery answers `absent` **or cannot answer** (`discovery_fence`, `discovery_incomplete`, `discovery_unavailable`, `discovery_not_authoritative`: Discovery is an independent domain), the route falls back to the canonical Film. A Discovery refusal is overridden only while the Film/Person marker is `open` and D1 finds the Film (or a verified `409` conflict or `410` retirement); a canonical absence or any other marker state keeps the Discovery `503` and its `reason`, so an unreadable catalog is never reported as `absent`. The fallback is **gated by the live Film/Person authority marker** ([ADR 0099](../../adr/0099-canonical-film-person-d1-authority.md)):

- Explicit local stand-in only (a Film/Person domain that is not installed; `FILM_PERSON_DB_OPTIONAL=standin`, never in the deployed configuration): R2 is the authority, so the verified rated-archive admissions object `letterboxd/admissions/verified-films.json` is the existence and identity decision (unchanged by AIR-475). One key `tmdb_<n>` is read and must verify as the admission rules require (`tmdb` equal to the key, short code, sha256 digest, verification time, no `watchlist` field). A Film whose D1 projection is still pending is found: the receipt is written before projection (ADR 0105), and projection is not required. The receipt is then bounded by what can contradict it: the owner's R2 `identity/tmdb-retirements.json` (a retired movie id is `410 retired`; an unreadable object is `503`) and, where a marker table exists, the D1 projection (all claims of the typed TMDB id are read, as the admission writer does: any claim that is not the one owner's own trusted, non-conflicting row, whether untrusted or conflicting, on this or another Film, even beside a trusted owner, is `409 conflict`; a trusted Film that is a redirect source is `410 retired`; a failed guard read is `503`). D1 can contradict a receipt but never has to confirm it.
- `open` (D1 is authoritative; AIR-374 P4, [owner decision 4](https://trello.com/c/ha7ais3w)): the R2 receipt and the R2 retirements object are **never read**. The route answers from D1 only, through `catalogCanonicalFilmFromD1` (`src/canonical-catalog-reader.js`): the retirement ledger `tmdb_retirement_decision` (an unsuperseded `retire` of the movie id is `410 retired`), every `film_external_id` claim of the typed id (the same conflict rule as above, `409 conflict`), `film_redirect` (`410 retired`), and then the **canonical Film itself**: a retained Film is a Film because D1 holds its one trusted, non-conflicting TMDB claim, **independent of Discovery, of a rated-archive admission (`film_rated_admission`), of the programme and of the watchlist** (an absent typed claim is `404 absent`). A Film that records another `canonical_identity` than the claim it was found by is `409 conflict`; a claim without its `film` row, an admission row whose `tmdb` differs from the typed id, unreadable stored genres, more than 200 credits, a failed read or a marker generation that moved during the read is `503`. The page carries the Film's stored data: localized title (reviewed over provisional `film_dimension` localization, then an admission title if one exists, then `film.original_title`), `original`, `year`, `runtime`, `genres`, `poster` and `url` from `film_metadata` (an admission row only fills a missing title or year), and `directors` / `actors` from `film_person_credit` in stored order with the resolved Person name (a credit without a resolved name is omitted; `id` is the Person `role_id`). `shows` come only from the pinned current EPG generation, so a Film with no current showing has `shows: []` and `availability.state: unavailable`, which is normal, not absence. The read never adds the Film to the watchlist, the programme or Finds. `held`, a missing or malformed marker, a missing companion table and a failed marker read answer `503` (`film_person_held` or `film_person_unavailable`); the new D1 read failures answer `503` with `canonical_read_unavailable`, `admission_unavailable` or `film_person_generation_moved`. None of them ever falls back to R2. Discovery-found films are unchanged. The optional context reads of the route (`metadata.json`, view index, programme, watchlist) are separate and are listed as follow-up in the AIR-374 P4 evidence.
- **Credits of the canonical page (AIR-656).** A credit shows the Person's localized/effective name (reviewed over provisional) and, when there is none, the deterministic `person_alias` of kind `name` (lowest value) of the **same** Person; no name matching, no merge, no stored write. A Person with neither is omitted. The read is one ordered statement, bounded at 200 credits (directors first, then `role`, `ordinal`): a larger cast is **never** a whole-film `503`; the reader marks the page `creditsPartial: true` and the route's response shape and the client's top-ten display are unchanged.

Before `open` the page is built from the receipt's stored title, year, runtime, genres and people, with `shows: []`, no prediction and no invented fields. A missing object admits nobody (`404 absent`); an unreadable or malformed one is `503 unavailable`. Discovery `found`, `conflict`, `retired` and `unavailable` are never overridden. The fallback performs no write, no scan and no outbound request.

**Retention.** The catalog seal merges the incoming catalog with every record the catalog already holds (`mergeCatalogIdentity` in `src/sources.js`): a film that stops airing is carried over with `shows: []`, not dropped, and an admission becomes `superseded` only when a seal finds a film id missing from that merged catalog (`supersedeAdmissions`). The permanent page therefore exists for as long as the admission is `current`, independent of airings, the hot window or Finds eligibility. A superseded record answers `retired` and a film that was never admitted answers `absent`; the route does not promise that a removed film can come back, and it never reads older generations. This is the code's guarantee, not a measured production retention figure; no production read was made for this card.

**Answer.** `200 {"status":"found","programmeRunId","generatedAt","film",...}` where `film` has the same shape as an entry of `GET /api/catalog/available` (so the client's ranking reads it unchanged), with these differences: no eligibility rule applies; the owner's facts and the stored forecast are read through the **verified alias** (below), and the forecast is judged by the shared compatibility evaluator ([ADR 0031](../../adr/0031-selective-prediction-profile-compatibility.md)), never by comparing version numbers: `prediction` is `null` when no forecast is stored for the Film (or no profile is readable); a forecast the evaluator calls `current` or `compatible` is returned with `compatibility` and its `tasteProfileVersion` as provenance (a v1 forecast under profile v2 is shown as v1); a forecast the evaluator calls `stale` is returned with `stale: true` and `staleReason`, the evaluator's own reason (for example `profile_impacted`, `fingerprint_not_current`); `fingerprint` is returned whenever the stored fingerprint is the one the index entry holds, whatever the forecast's freshness; `actualRating` (a number, or `null` when unknown) and `watched` (`true` only on a stored mark) are the owner's facts and are returned whether or not the Film is on the watchlist (a rating is never turned into a watched mark, a mark never into a rating; a rating known twice and different is unknown); `shows` are only those written by the pinned generation (`showsProgrammeRunId` equals `programmeRunId`), and `[]`, `availableNow: false`, `nextStart: null`, `availableUntil: null` (and `availability.state` `unavailable`) when there are none; `letterboxdUrl` is present only when [stored records prove it](#letterboxdurl). **Verified alias.** While the Film/Person marker is `open`, the Letterboxd id under which the index holds the forecast and the owner's facts is the one trusted, non-conflicting `letterboxd` claim of the Film (`catalogFilmIdentityBridge`: the typed TMDB claim, no redirect, one trusted value per scheme, no untrusted claim of either value on any Film); the TMDB entry and the lid entry are merged field by field. **Where the facts come from.** For exactly those two keys the route projects the forecast and fingerprint from the prediction domain (`PredictionD1.projectItems`: `prediction_pointer` and `prediction_fingerprint`, two indexed statements) and the watched mark and rating from the ratings domain (`RatingsD1.viewItems`: `ratings_view`, one indexed statement) while that domain is d1 and open, **whether or not the R2 view index holds the keys** (a missing or stale index is only the seed and never decides whether D1 data exist; D1 overrides its display data), and the active taste profile is the prediction domain's D1 profile. A domain that is not d1 leaves the R2 index entry as the source. An unreadable domain is `503 {"status":"unavailable","reason":"prediction_…"|"ratings_…"}`, never a stale mirror. A contested identity adds `identity` to `degraded` and reads nothing under a guessed id; a title, year or slug is never matched. Below `open` no alias is resolved. `degraded` lists optional context that could not be read (`publication`, `programme`, `watchlist`, `index`, `profile`, `metadata`, `freshness`, `identity`): the film is still returned, with nothing claimed from the missing part.

| Status | `status` | When |
| --- | --- | --- |
| `200` | `found` | One current verified record |
| `400` | `invalid` | The id is not a positive integer of at most 12 digits |
| `404` | `absent` | No Discovery admission for this movie id and, below `open`, no verified archive admission (AIR-409); at `open`, no trusted canonical TMDB claim in D1 (AIR-475) |
| `409` | `conflict` | Two Films trust this TMDB id or an external id conflicts (archive fallback), a record of this number does not verify its identity, two current records exist, or its payload disagrees with its row |
| `410` | `retired` | Only superseded records exist, the owner retired the movie id, or the Film was merged away (archive fallback) |
| `503` | `unavailable` | Held cutover, a held, open or unreadable Film/Person authority for the archive fallback, a catalog or decision load in progress, an admission still pending, an unreadable or inconsistent authority, or a missing shared catalog object in R2 mode (`reason` names it); never reported as `absent` |
| `500` | `error` | Any other failure |

**Consumer.** The film page (`public/app.js`, `resolveFilm`) asks only for a TMDB route that no loaded source holds, caches the answer per session and refreshes it once per loaded generation; see [UI and read models](../../architecture/ui-and-read-models.md#one-permanent-film-url-air-387).

## Errors

| Status | Body | When |
| --- | --- | --- |
| `503` | `{"error":"No published programme"}` | No programme has been published yet |
| `503` | `{"error":"The catalog is not readable right now","code":"discovery_fence"\|"discovery_incomplete"\|"discovery_unavailable"\|"discovery_not_authoritative"\|"discovery_bounded"}` plus `Retry-After: 1` | D1 Discovery is held, loading (and not a ledger seal), bounded, unreadable, or the published programme pin moved during the catalog snapshot. The client may retry once. This is not an empty Finds list and not HTTP 502. Unrelated Discovery continuation or status writes do not produce this answer: the catalog snapshot is one admission `SELECT` fenced on authority, programme, transfer and `discovery_transfer.batches`, not on the global Discovery generation ([ADR 0147](../../adr/0147-discovery-user-read-snapshot-fence.md)) |
| `409` | `{"error":"Programme generation is not in place"}` | The pointer names a generation whose programme copy is absent or carries another run id (publication still copying); call again later rather than serving the previous generation or the shared public key |
| `409` | `{"error":"Catalog generation copy is not in place"}` | The pointer names a generation whose catalog copy is absent; the shared public catalog is not used as a substitute |

Without a published pointer the shared public keys are read and `pinned` is `false`. A missing view index or profile is not an error: the list is empty; a missing catalog is empty only when unpinned.

## Size and freshness

The response holds every eligible film of the pinned generation, so its size is bounded by the hot part of the catalog. Statuses and `availableUntil` are computed at request time; a client that caches the response must re-derive them from `shows[].start`/`end` with its own clock or request again. A new profile version empties the list until predictions are refreshed, which is the intended fail-closed behaviour: a stale prediction is never offered as current.

## Poster hydration

Catalog records keep the poster the discovery writer stored when it inserted them from TMDB movie detail (`https://image.tmdb.org/t/p/w342…`). Records written before that field existed, or by an older resolver, carry `poster: null`; every later catalog write preserves the field, so such a record stays without a poster, and the `metadata.json` fallback above only covers films that were on the watchlist. `POST /api/enrichment/catalog/posters` fills that field and records a terminal TMDB refusal in the negative index below. It writes no other catalog field. It is a permanent, owner-only maintenance write route for restoring posters after a mass TMDB discovery failure, with no switch of its own ([ADR 0048](../../adr/0048-permanent-catalog-poster-maintenance-route.md)); `GET /api/catalog/available` stays read-only. Access is the Worker's owner-only Cloudflare Access application, the same for every `/api` route, plus the same-origin check of the sibling POST routes; there is no separate permission check, token or role. The lease, generation and compare-and-swap checks, the batch limit and the identity rule protect the data, not access. The decision and its boundaries are [ADR 0020](../../adr/0020-owner-triggered-catalog-poster-hydration.md), [ADR 0048](../../adr/0048-permanent-catalog-poster-maintenance-route.md) and [ADR 0063](../../adr/0063-catalog-poster-negative-index.md). Terminal TMDB answers are remembered in `epg/catalog-poster-negatives.json`, one object keyed by the verified numeric TMDB id, and the ordinary queue skips them. The owner page `/admin/posters` is the browser client of this contract ([admin reference](admin.md#poster-coverage)): its preview is a read-only `GET /api/admin/posters` that counts the same objects with the same rule and shows the batch the next call would process, its confirmation guards against an accidental start, not an authorization, and it sends at most 30 sequential calls of at most 10 records, each with the previous `nextCursor` and the confirmed generation as `expectedProgrammeRunId`.

| Request | Effect |
| --- | --- |
| `{}` or `{"dryRun": true}` | Read-only: counts over the live catalog, the published generation's copy and the negative index (`catalogRecords`, `missingPoster`, `verifiedMissing`, `unverifiedMissing`, `actionable`, `noPosterHeld`, `identityReview`), the published `programmeRunId`, `enabled` (always `true`, kept for compatibility), and the first 50 actionable ids in `ids`. No TMDB request and no write. A value that is not an `https://` URL counts as missing. An absent index is empty. An unreadable index is `503` `{error: "Poster negatives unreadable", negativesReadable: false}` before any lease or TMDB request, and the body has no `done` |
| `{"dryRun": false, "limit": n, "cursor": "<id>", "expectedProgrammeRunId": "<run>"}` | Execution of the actionable queue; no variable gates it (the former `CATALOG_POSTER_HYDRATION` is retired and inert). `limit` is 1–20 (default 10); `cursor` continues after the given record id in id order of that queue; an absent or empty cursor starts at the first actionable record; `expectedProgrammeRunId` is the optional generation fence below |
| `{"dryRun": false, "recheck": ["<tmdbId>"], "limit": n, "expectedProgrammeRunId": "<run>"}` | One explicit recheck. `recheck` is an array of one to `limit` distinct numeric TMDB ids (`/^[1-9]\d{0,11}$/`). It requires `dryRun: false` and no `cursor`; anything else is `400 Invalid recheck` before any read. The call ignores the index and the sweep cursor, asks TMDB only for ids that are still verified records without a poster, and returns `not_eligible` for the rest. `recheck` in the answer is `true`, `nextCursor` is `null` and `remainingAfterCursor` is `0` |

**Generation fence.** `expectedProgrammeRunId` (optional, a non-empty string of at most 200 characters, otherwise `400 Invalid expectedProgrammeRunId`) binds the call to the published generation the caller saw. It is checked right after the generation pointer is read, before any catalog read, lease, TMDB request or write, and checked again once the lease is held, before the first TMDB request. If the published generation is another one, or none, the call answers `409 {error: "Programme generation changed", generationChanged: true, leaseLost: false, expectedProgrammeRunId, programmeRunId}` (the generation now published, or `null`) and has made no TMDB request and no write; when the mismatch is seen under the lease, only the lease was taken and released. A dry run honours the same fence. Without the field the call works on whatever generation is published, as before. The fence is in addition to the generation check before every write below, which still applies, so a generation published after the second check still stops all writes. `/admin/posters` sends it on every call of a run, the first included.

Execution takes the resolver lease (`409` while a discovery chunk or an EPG publication holds it, nothing fetched) and handles at most `limit` records in id order. Only a record whose `canonicalIdentity` is exactly `tmdb:<tmdbId>` is requested; an unverified record is never touched. For each one it requests `movie/<tmdbId>?language=ru-RU` through the resolver's TMDB client and pacing, with one retry on a failure and none on a `429`, which stops the batch.

**Outcomes.** Terminal: `hydrated` (the poster is now in every copy in scope; `poster` is returned), `already_present` (another writer stored one first), `no_poster_on_tmdb` (TMDB has no `poster_path`; record untouched), `tmdb_id_mismatch`, `not_eligible` (a recheck named an id that is not a verified record without a poster; TMDB was not called). Retryable: `tmdb_failed` (with the error), `rate_limited` and `not_attempted` (after a `429`, with `retryAt`), `skipped_changed` (the record disappeared or is no longer the same verified id), `generation_changed`, `lease_lost`, `catalog_changed` (two lost compare-and-swaps). A retryable outcome after a partial write carries `writtenTo` with the copies that already hold the poster. A `no_poster_on_tmdb` or `tmdb_id_mismatch` outcome also carries `negativeSaved` (`true` only when that id was actually stored). `tmdb_id_mismatch` is only a different valid positive numeric `movie.id`: a safe integer, or a string matching `/^[1-9]\d{0,11}$/`. An HTTP 200 whose `id` is missing, `null`, zero or not that form is retryable `tmdb_failed` with error `TMDB detail has no movie id` and is not stored.

**Remembered answers.** After the catalog writes, the call merges this batch's `no_poster_on_tmdb` and `tmdb_id_mismatch` into `epg/catalog-poster-negatives.json` and drops ids that are no longer a verified record without a poster. `no_poster_on_tmdb` stores `checkedAt` and `nextCheckAt` (`checkedAt` plus 90 days). `tmdb_id_mismatch` stores `checkedAt` only. Nothing else is stored: not `tmdb_failed`, `rate_limited`, `not_attempted`, a lost lease or a changed generation. The write uses the same generation and lease guard as the catalog copies, then one compare-and-swap (create when the object is absent, match when it exists) and one retry. The answer's `negatives` is `{persisted, reason, written}`. `persisted` is `true` only when the write is durable and every negative outcome of this call has `negativeSaved: true`. `reason` is `generation_changed`, `lease_lost`, `cas_conflict`, `unreadable` or `index_full` when that is why it is not. At 2,000 entries a new id is left unsaved, the stored entries stay, and the next ordinary call asks for that id again. An unreadable index never reaches this write.

**Display fields.** Every outcome also carries `title` (the record's title, at most 200 characters, `null` when it is not a non-empty string) and `year` (an integer or `null`), taken from the catalog record the call already read for its batch. They are for display only: no extra read, no TMDB request, and no effect on the outcome, the cursor or the writes. `/admin/posters` uses them to name every record of every batch in its receipt.

**Cursor and completion.** The queue is the actionable part only: verified records without a poster that have no remembered answer, plus a `no_poster_on_tmdb` whose `nextCheckAt` has passed. An unexpired `no_poster_on_tmdb` and every `tmdb_id_mismatch` are outside it. A changed verified id is not blocked by the old key. `nextCursor` moves only past records whose outcome is terminal; it stops before the first retryable one, so the next call retries it first. `done` is `true`, and `nextCursor` is `null`, only when the batch reached the end of that queue and every outcome in it is terminal. An empty actionable queue is `done` even when `missingPoster` is still above zero; `noPosterHeld` and `identityReview` say what remains. A recheck is not a sweep: its `nextCursor` stays `null`. A sweep that has to start again at the first record gets the empty cursor `""`, never `null`. `retryable` lists the ids that are still open, and `remainingAfterCursor` counts the actionable records after `nextCursor` (`0` for a recheck). Following `nextCursor` from no cursor until `done` settles the actionable queue, not every verified record without a poster. A record that keeps failing keeps the sweep open, and the [runbook](../../runbooks/catalog-poster-hydration.md) bounds the attempts.

**D1 authority (AIR-515).** While the Discovery marker is `d1`/`open`, the catalog the route reads and writes is the current `discovery_admission` rows, the same rows `GET /api/catalog/available`, the film detail and «Находки» read; there is no generation copy and no R2 catalog object is read or written. `DiscoveryAuthority.applyPosters` is the one writer: a single D1 batch that sets `$.poster` inside the admission `payload_json` and nothing else, behind the Discovery fence (mode `d1`, cutover `open`, the authority generation, the live lease of this run, a transfer that is not `loading`, and the published programme the call started from). A row is updated only while it is still `current`, a movie, the same positive TMDB id and canonical identity `tmdb:<id>`, and without an `https` poster; otherwise the record is `already_present` (a poster is stored) or `skipped_changed`. A stored `https` poster of the same identity survives every later `upsertAdmissions` and `replaceCatalog` (an explicit new `https` poster of the same identity still replaces it; another identity never receives it). `writes` keeps its shape with one entry, `key: "discovery_admission"`, and `outcomes[].writtenTo` is `["discovery_admission"]`. An authority that is held, not installed (no D1 binding, no or old `schema_contract`) or not `d1`/`open`, a `loading` transfer or an unreadable catalog is `503` with `storageUnavailable: true` (dry run and execution alike, before any TMDB call, lease or write), never "no poster", and there is no R2 fallback. A fence or compare refusal inside the write batch rolls it back whole and is the retryable outcome `catalog_changed` (or `generationChanged`/`leaseLost`). Any other failure of that batch may or may not have committed: the call answers `503` with `writeUncertain: true` and `retryable` ids, saves no remembered answer, and must not be retried blindly; re-read `GET /api/admin/posters` first (a duplicate apply is harmless: `already_present`). The R2 copies described next exist only in offline stand-ins that have no Discovery authority module; the built Worker never uses them. The negative index stays in R2 (ADR 0063).

**Writes (legacy R2 form, offline stand-ins only).** The built Worker does not do this: with Discovery on D1 the single write is the D1 batch described above and the R2 catalog objects are frozen history (ADR 0162). The older R2 form, kept for offline stand-ins without the Discovery authority module: after all requests the call writes the published generation's copy, then the live catalog. They are two separate R2 objects and are not atomic together. Each copy is re-read; the poster is set only where the record is still the same verified TMDB id and still has no poster; immediately before every write attempt, including the retry after a lost compare-and-swap, the call checks that the published generation is still the one it started from and renews the lease, and then writes with a compare-and-swap on the ETag. A lost compare-and-swap re-reads and retries once; a second loss leaves that copy unwritten. A failed generation or lease check stops every later write: before the first write nothing is written; between the two writes the generation copy keeps the poster and the live catalog does not, and `writes` and the per-record `writtenTo` say so. That poster is a correct TMDB asset of the verified id and harmless in the copy that holds it; the next call re-reads both copies and completes the missing one or reports it again. `generationChanged` and `leaseLost` summarise the stop; a lost lease answers `409`. Identity, aliases, shows, decisions, the generation pointer and every other key are not written. The negative index is the one extra object this route writes, and only as described above. The [poster hydration runbook](../../runbooks/catalog-poster-hydration.md) is the approved procedure; the route does not run on a schedule, and every production execution call is a separate owner-approved operation.

## Catalog Films in `GET /api/programme`

`GET /api/programme` keeps `films` as the watchlist members of the completed read, then withholds any member whose stored metadata proves ADR 0150 `documentary` or `concert` (`admissionPolicy`; no TMDB lookup). `GET /api/watchlist` is unchanged. It adds, only when the completed programme read holds catalog Films of the run, two additive fields. `catalogFilms` lists each catalog Film that has a current catalog record of the same TMDB id (the generation `discovered-films.json`, D1-owned under the Discovery authority) and is not that excluded type: the record's Film data without its availability fields (`shows`, `availableUntil`, `showsProgrammeRunId`, `epgLastAiring`, `hotEnteredAt`), plus `shows` and `availableUntil` taken from the completed read and `onWatchlist: false`. `catalogPart` states the outcome: `{state:'ok', entries, presented, unpresented}` where an entry without a current record, or a proven Documentary or concert, is not presented as a Film and is counted in `unpresented`; or `{state:'unavailable', entries}` with `catalogFilms: []` when the catalog reader cannot answer (a Discovery fence, a ledger seal in progress, a missing copy). The member part is never failed or emptied by the catalog part; a withheld watchlist Documentary is a presentation filter, not a catalog-part failure. With no catalog Films neither field is present and the catalog reader is not called. The read is a pure read (no write, no TMDB call). The programme screen (`public/app.js`) keeps the main grid on `films` (watchlist members and their completed-read showings). Presented `catalogFilms` stay on the payload for Finds, the film page and other completed-read consumers; they are not concatenated into the grid. A catalog-only card that does appear (Finds, similar films) keeps `onWatchlist: false` / `catalogOnly`, omits the started-watch action (the Worker answers `POST /api/started` from the canonical D1 Film and still returns `404` for an id with no canonical Film; see [Started and unstarted marks](../domain/events.md)), and does not count as a watchlist identity. The NEW badge is only for an unwatched, unrated catalog Film. With a scoped filter the grid heading stays «Из watchlist» when the visible cards are members. Filters and sort apply to the loaded members. The catalog Film titles are the catalog record's own and do not pass through the localization or owner-review overlay that `films` get. The catalog reader materializes the current admission records for each request that has catalog entries; monitor its latency, and a bounded identity-targeted reader is the follow-up if it matters.

## Showings of Finds and the film page

Under an authoritative D1 published run (`published_epg_authority.mode = d1`) with a pinned completed programme read, `GET /api/catalog/available` and the film page take the showings of a Film **only** from that completed read: the member `films` and the non-member `catalogFilms`, matched by TMDB id. The same overlay applies to prediction coverage (`canonicalCoverageSummary` on the footer, Event snapshots and MCP queue diagnostics): a catalog record that still looks hot is not in the coverage window unless the completed programme lists a showing. A Film absent from it has zero showings, also after an owner correction or rejection removed its assigned row; the `shows` of the admission payload are never a second source, even when its `showsProgrammeRunId` is the pinned run. Identity, title, credits, poster and the non-availability filters are unchanged. If the completed programme cannot be read or pinned, Finds fails closed (the existing 409 or error response), and the film page keeps its optional-context degradation: `degraded` names `programme`, the Film is still answered (200) with no showings. Outside D1 (R2 authority) both routes keep reading the record's own `shows` until that path is retired.

A catalog Film that the scan itself confirmed has no sealed row: its showings appear when the Discovery replay (the batched slot replay that opens each paged chunk, `known_epg_alias` decision, `assignObservationSlots`) reaches its observation (ADR 0142 decision 5, owner decision R2). Until then it has zero showings in Finds and on its page; that delay is accepted and is measured on natural runs, not hidden with the legacy fields. Under a live D1 pin, `replaceCatalogAvailability` does not rewrite availability. `touchCanonicalFilm` drops `shows`, `availableUntil`, `showsProgrammeRunId`, `epgLastAiring` and `hotEnteredAt` on the Film it writes. `mergeCatalogIdentity` does the same only for a staged identity change or a staged-only Film; an unchanged live row is left as-is so the seal does not upsert the whole catalog. Leftover bytes stay unused by D1 readers. R2 still stamps those availability fields. Both routes remain pure reads.

### Automatic weekly retry

Two automatic paths use the rules above without the owner route ([ADR 0179](../../adr/0179-weekly-automatic-catalog-poster-retry.md); procedure in the [runbook](../../runbooks/catalog-poster-hydration.md#weekly-automatic-retry)). Both are D1 only (no R2 catalog writer) and are implemented offline; neither runs in production until the cron is activated by a separate owner decision.

- **Seed at admission.** When Discovery admits a **new** film from a complete TMDB movie detail whose `id` equals the verified id, whose title is present and whose `poster_path` is explicitly `null`, it writes `no_poster_on_tmdb` (`checkedAt`, `nextCheckAt` 90 days later) into the negative index through the usual compare-and-swap, with no second TMDB request. The seed runs **after** the candidate and its Film are committed (and, on the second admission path, after the generation check), so a refused, late, skipped or fenced candidate leaves no marker. A missing key, a malformed path, a missing id or title, a network error, a `429`, a `5xx` or an id mismatch is never recorded as "no poster". An id the index already knows is left alone. An index that is unreadable, full or conflicting never blocks the admission; the film is left for the weekly catch-up.
- **Weekly sweep.** The daily Worker cron `24 3 * * *` UTC runs `catalogPosterRun`, the one core that the owner `POST /api/enrichment/catalog/posters` also wraps. It does not call the Access-protected route. Candidates are the verified Films without an HTTPS poster that have no index entry or an expired `no_poster_on_tmdb`; `tmdb_id_mismatch` is never rechecked automatically. A firing runs at most five batches of ten records. When nothing is due (an empty queue after the cursor) the weekly call returns `done` before the TMDB credential check and before the resolver lease: it takes no lease, writes no lease row, asks TMDB nothing and still produces its honest weekly report, even while Discovery holds the lease. The owner route keeps its semantics and still takes the lease. A `429` honours `Retry-After`; a busy resolver lease or EPG priority, a `5xx`, a network error or a stuck cursor leaves the run `pending` with a retry time (30 minutes by default) and no 90-day penalty. After six unfinished attempts the run is `failed`.

The manual route keeps its owner gate, dry run, `recheck`, cursor and receipts. One rule of the shared core now applies to it too: only an explicit `poster_path: null` in a 200 detail whose id matches is `no_poster_on_tmdb`; a missing key, an empty value or a malformed path is a retryable `tmdb_failed` and is never remembered. The weekly state, its outbox and the event ids are described in the [events reference](../domain/events.md#catalog-poster-weekly-report-catalog_posters).
