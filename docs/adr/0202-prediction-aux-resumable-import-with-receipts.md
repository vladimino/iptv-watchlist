# ADR 0202: The auxiliary import and its verification run as ordered, resumable chunks that leave receipts, and the flip checks the receipts instead of re-sending the dataset

**Superseded by:** None

## Context

The cutover contract so far is one atomic D1 batch for the import and one atomic batch for the flip that **contains the canonical row-level verification** (so it cannot be skipped and a differing byte aborts it before the marker moves). The first real export of the legacy state ([evidence](../evidence/prediction/air-554-aux-real-export-sizing-2026-11-22.md), 22 Nov 2026, consistent cut of the auxiliary scope of [ADR 0200](0200-prediction-aux-scoped-export-proof.md)) measured 1,947 objects and 34.8 MB: 738 run sources and 468 persisted manifests carry 33.7 MB of it. The derived import is **3,998 statements and 36.2 MB** and the verification **5,948 statements and 36.7 MB**, against the measured D1 batch limits of 2,000 statements and 8 MiB. Neither the import nor the flip fits one batch. The largest single run is 0.62 MB and the largest statement 55 KiB (the 100 KiB statement limit is respected), so the data can be split by run. The synthetic tests that shaped the original contract were one run of 16 KB.

## What `0034` guarantees today (and what it does not)

Read from `migrations/0034_prediction_aux_authority.sql`: `prediction_run_source_revision`, `prediction_run_source_piece`, `prediction_run_manifest` and `prediction_run_manifest_piece` refuse every `UPDATE` and `DELETE` (insert-only). **The rest is mutable:** `prediction_batch_stage` has no trigger at all and `prediction_batch_stage_head` no trigger; `prediction_run_source_head` may be updated forward (a higher revision, the same run); `prediction_event_outbox` may be updated (state, attempts, `last_attempt_at`, `settled_at`, compaction) with its identity columns fixed and may not be deleted; the outbox counters and state counts are maintained by triggers and are plain rows. While the marker is `closed` the Worker never writes these tables (its D1 aux branch is off), so the only writers are the owner-only operator and manual SQL. That protection is the Worker's code, not the database's. A receipt proving "these bytes were verified" is therefore sound **only** for rows the database itself forbids to change; for the mutable tables it would go stale.

## Decision (accepted)

1. **Chunked import under the closed marker.** The plan is split into ordered chunks of whole runs (a source revision with its pieces and head, a manifest with its pieces), then the event outbox, then the held stage, each chunk at most 1,500 statements and 6 MiB (margin under the limits; 6 chunks for the measured data, one run at most 0.62 MB). Every chunk is one atomic batch.
2. **Receipts and the serialization rule.** Each chunk's batch ends with one insert into `prediction_aux_import_chunk (generation, chunk_no, chunk_sha256, plan_sha256, statements, bytes)`, primary key `(generation, chunk_no)`. The batch begins with a guard, evaluated **inside the same transaction as the writes**, that aborts it unless: the marker is `closed` at exactly that generation, **no seal exists** for it, `chunk_no` is one more than the highest receipt (and 1 when there is none), and `plan_sha256` equals the plan digest of the existing receipts (or no receipt exists yet, for chunk 1). D1 serializes write transactions, so two competing attempts of one chunk cannot both commit (the second sees the receipt, or fails the primary key), an attempt of chunk k+1 cannot commit before chunk k, a batch of another plan or of an older closure generation cannot commit at all, and the read of a receipt gives a definite answer only for an attempt that has already finished. **A missing receipt at one readback does not prove that an earlier timed-out batch cannot commit later**, and this design does not rely on it: because the guard makes a chunk exactly-once, a retry of the **same** chunk (same bytes, same digest) is always permitted. A retry that finds its receipt with the same `chunk_sha256` was applied earlier by the old attempt and counts as done; any other guard failure stops the run. The operator never sends chunk k+1 until the receipt of chunk k is read, and a chunk whose result is unknown is never replaced by different bytes.
3. **Seal.** After the last chunk the operator inserts one row into `prediction_aux_seal (generation, chunk_count, plan_sha256)`, guarded by: marker `closed` at the generation, receipts exactly 1 to `chunk_count` of one plan digest, and the table totals equal to the plan's. A database trigger on **every** auxiliary data table (stage, stage head, source head, source revision and piece, manifest and piece, outbox, outbox counters and state counts) refuses `INSERT`, `UPDATE` and `DELETE` while a seal exists for the marker's generation **and the marker is not `d1`**. From the seal to the flip nothing in the cohort can change, whoever the writer is, including a late chunk of an old attempt; this is the database-enforced invariant that makes verification receipts sound for the mutable tables too. After the flip (marker `d1`) the trigger does not block and the Worker writes normally; it costs one primary-key read of the marker per write, a cost to measure.
4. **Chunked canonical verification after the seal.** The canonical per-row verification of the whole dataset (the assertions of `planVerifySql`, byte-level for source and manifest pieces) is split the same way. Each slice asserts its rows and, in the same batch and only if all assertions pass, inserts `prediction_aux_verify_slice (generation, slice_no, slice_sha256, plan_sha256)` under the same kind of guard (marker `closed`, seal present, next slice number, same plan digest). A differing byte aborts that batch before its receipt exists. Because the data is sealed, a receipt cannot go stale.
5. **A small flip.** One batch asserts: the marker is `closed` at the generation; the seal exists with the plan digest and chunk count the owner's release names; the verification receipts are exactly slices 1 to M of the same plan digest and cover the plan; the family totals and outbox states equal the report; then the marker moves to `d1`. The release binds the plan digest, K, M and the final capture identity. The flip batch is a few statements.
6. **Reads and recovery.** While the marker is `closed`, auxiliary **reads are still served from R2** (ADR 0196: `closed` is not an authority and not unavailable); the Worker's D1 aux branch is off, so partially imported or sealed D1 rows are **not authoritative and not read** until the marker is `d1`. `closed` to `r2` stays refused once any row exists. An interrupted import is resumed from its receipts. If verification fails after the seal the cohort cannot be edited (the seal forbids it) and the marker stays `closed` with the Tasks off: the cure is an owner decision (a restore or a new closure), which is not designed here.
7. **Schema.** Implement the two receipt tables, the seal table and the seal triggers in a **separate additive migration after `0034`**. Keep the reviewed `0034` byte-for-byte unchanged. Assign the new migration's number from the actual available sequence on current `main` when implementing it; do not reserve or assume `0035`. Neither migration may be applied to production without the separate owner GO.

## Alternatives considered and not selected

- **Verify the mutable tables inside the flip batch instead of sealing.** Measured on the real export: the canonical verification of the mutable tables (stage, source heads, outbox) is **1,480 statements and 1.76 MB**, which fits the flip batch today, with the immutable tables verified by receipts (their immutability is enforced by `0034`). It needs no seal triggers, but it grows with every run (about two statements per run, 70 to 80 runs a day), so it reaches 2,000 statements in a few days and would break the flip; it also leaves the mutable rows unprotected between the import and the flip. Not selected; it would be the cheapest short-lived option only if the cutover happened within days.
- **No receipts, progress read from the data.** No schema change, but the flip can no longer prove in the database that the whole verification passed; the proof moves to the operator's process, which the review of PR 897 rejected. Not selected.
- **Pre-import of immutable history before the freeze.** Terminal runs' sources and manifests are immutable; importing them while the legacy path is authoritative would leave only recent runs, the outbox (1.08 MB) and the stage for the window and would remove most of the window risk. It changes the rule that an import runs only under the closed marker and on empty tables, needs its own guard and proof and a decision on runs that change after a first import; it would require a separate architectural decision.
- **Keep old runs in R2.** Import only live and recent runs inline and leave terminal history in R2. It changes the accepted retention decision of ADR 0194 (all history inline) and was not selected.

## Consequences

- The import and the flip fit the measured limits: 6 import batches, one seal, 6 verification batches and one small flip for the measured dataset, each well under 8 MiB.
- The window budget (run sheet P3) needs the duration of one chunk on production D1, which is unmeasured; it is read from the first chunk (the first chunk makes the tables non-empty, so the abort path after it is "resume or hold", not `--reopen`; after the seal the cohort is frozen) or from a scratch D1, which the owner has not authorized. The implementation must update the budget rule and import gate of the run sheet around measured chunks before any cutover GO.
- More code (the chunker, the receipts, the seal, the flip check), a schema addition with triggers on every auxiliary table, new operator step states and tests, including concurrent and late-commit tests of an ambiguous chunk; nothing here is applied, imported or flipped by merging this ADR.
- The D1 cost of about 12 large batches is a measurement to take, not a threshold (Paid baseline); the current D1 load analysis is [AIR-579](https://trello.com/c/OlcWhyM7).

## Implementation and operational gates not authorized

The Product Owner has accepted the `seal` architecture and the separate additive migration after `0034`. The starting chunk limits of 1,500 statements and 6 MiB require implementation tests and real-size validation; revisions within D1 limits must be justified and independently reviewed. Implementation of the operator and SQL guards requires independent code review and evidence, including concurrent and late-commit cases. ADR acceptance does **not** approve applying `0034` or the new migration to production, a scratch-D1 rehearsal, Tasks freeze, R2/D1 writes, `closed`, imports, flip or any manual Workflow. Each remains under the existing AIR-554 owner gates. The residual risk of ADR 0196 and the drain bound are unchanged. AIR-554's D1 readiness gate is verified for that cutover independently of completion of AIR-579.
