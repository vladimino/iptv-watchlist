# Letterboxd Sync runbook

The Letterboxd Sync Workflow runs one slot at 04:30, 10:30, 16:30 and 22:30 Europe/Madrid: Diary and Ratings, a complete Watchlist scan, then removal reconciliation, and writes exactly two Events per slot (`ratings`, `watchlist`). Design: [ADR 0186](../adr/0186-letterboxd-sync-and-independent-watchlist-authority.md); control plane: [scheduling and orchestration](../architecture/scheduling-and-orchestration.md); tables: [D1 schema](../reference/data/d1-schema.md).

## State today

The code is LIVE since the staged activation of 22 and 23 Nov 2026 (the Watchlist authority `d1`/`open`, the Ratings executor `external`, the Letterboxd mode `cloudflare` at epoch 1 with the cron `30 * * * *` and the `iptv-letterboxd` Workflow, the schedule open; receipts in the [activation evidence](../evidence/d1-migration/air-571-letterboxd-sync-activation-2026-11-22-23.md)). Before that it was dormant: with the mode table empty or `external` nothing is created, and the legacy Ratings writer and the EPG Watchlist fetch are unchanged; that is also the state a rollback returns to. **Nothing on this page is authorized by a deploy or a green test run.** Every production step below is a separate owner-approved operation (L3).

## Observing (read-only)

- `status().letterboxdSync` of the Ratings status and the `letterboxd` monitor stream (the read model: mode, epoch, current and next slot, overdue slots, per-source `lastSuccessAt`, health, pending Events). Both are absent while no mode row exists. They write nothing.
- A slot row's `status` and its three outcomes; a pending `letterboxd_slot_event` row means an Event is owed, not that the scan failed.
- `late`: a due slot was never claimed (the `:30` tick did not run or `ensure` is refusing). `stalled`: an earlier slot is still unclosed after its own window ended. `missed`: a slot was recorded `skipped_missed`. `failed`: the last closed slot errored in both sources. `watchlist_stale`: no complete scan for 24 hours; `watchlist_never_succeeded`: none at all since the executor started 24 hours ago.

## Holdpoint (c): the bootstrap import (performed on 22 November 2026)

The operator `scripts/watchlist-bootstrap-production.mjs` imports the current published watchlist into snapshot version 1 while the Watchlist marker is still `epg` ([ADR 0186](../adr/0186-letterboxd-sync-and-independent-watchlist-authority.md) decision 8.2(c)). It is an import, not a scan: one atomic D1 batch writes the staging row, the ordered member rows, the snapshot row and the pointer, and nothing else (no change, effect or pending-admission row, no fact, no marker move). It needs its own owner GO and the prerequisite O4 (the EPG checkpoint cutover verified by a natural EPG run).

- **Read-only first:** `node scripts/watchlist-bootstrap-production.mjs --target iptv` (`status`, the default) prints the decision (`ready` or the refusal), the marker, the pointer, the published generation and its certificate, and the source count with **two** digests: `membersSha256` (ids in order) and `sha256` (the raw stored list, titles included), bound to the printed `epgGeneration`. It writes nothing.
- **Two separate pins, because the API presents localized titles.** `GET /api/watchlist` applies the owner-reviewed and cached titles at read time (`presentLocalized`), which can change a title without a new generation. Membership and order are not affected, so they are pinned apart from the raw payload:
  1. *Membership and order (`--expect-members-sha256`)*: the owner saves the authoritative, non-degraded `GET /api/watchlist` response to a file and runs `node scripts/watchlist-bootstrap-production.mjs --digest --file <response.json>` (local, no network, no target). It prints the count and the SHA-256 of the lines `ordinal<TAB>id<NEWLINE>`; titles are never hashed. A same-count change of membership or order differs. The saved response is evidence only when it is **bracketed**: read the published run id and generation with `status` before the request and again after it, require both reads equal and equal to `--expect-run` and `--expect-epg-generation`, and reject any degraded or fallback-labelled response operationally (a response that carries a degraded or stale label, an error body, or a non-200 status is not evidence). No new API is needed.
  2. *Raw payload (`--expect-sha256`)*: the digest `status` printed for the stored published document at the generation named by `--expect-epg-generation`. It is the digest the import writes, so a title presented differently by the route never refuses a valid current list.
  The two must describe the same generation: the operator refuses unless the run id, the generation, the count and both digests equal the stored source (`pin_mismatch`, with the list of failed pins).
- **The write:** `node scripts/watchlist-bootstrap-production.mjs --bootstrap --target iptv --confirm bootstrap --expect-run <programmeRunId> --expect-epg-generation <n> --expect-count <n> --expect-members-sha256 <digest> --expect-sha256 <digest>`. Every pin is required.
- **Preflight (fail closed):** the marker is `epg`, writes `open`; the pointer is version 0 with no snapshot; every watchlist table is empty; the published generation is `d1`/`open` and certified complete (`finalized_run_id` equals `programme_run_id`) and equals the pin; the source normalizes (unique ids, shape, order) and its member rows agree with the document; no executing EPG step, and both liveness records valid: a missing record is idle, a PRESENT record that does not satisfy the contract of `src/epg-orchestration.js` is unknown (`liveness_unknown`), never idle. The contract: `control` is an object with `schemaVersion` 1, a `budget` with integer `consecutive` and `total` and a known `phase` (`idle`, `starting`, `running`, `waiting`, `done`, `stopped`); `lease` is an object with a `holder`, a normalized-UTC parseable `expiresAt` and a boolean `released`. Busy means a `starting`, `running` or `waiting` phase, or an unreleased lease whose expiry plus the 15 s boundary margin is still ahead.
- **Guards inside the one batch:** the same marker, pointer, empty-table and certified-generation checks, **and** the EPG liveness proof, written in SQL with the same contract (NULL counts as invalid): the `control` and `lease` records are pinned by revision (absence included), a present record must satisfy its contract, and neither may show an active phase or a live lease. A writer that appears after the preflight, a record that changes revision, and a valid-JSON record of the wrong shape all trip the batch and nothing is imported. This is the only liveness check: there is no wider global drain check.
- **Readback (independent):** pointer version 1 with the snapshot id, digest, count and `effects_drained_version` 1; one staging and one snapshot row, the pinned number of members, zero change, effect and admission rows; the member rows in order reproduce the digest; the marker is unchanged; the published generation did not move; the stable fields (mode, cutover, writes) of the other domains are unchanged (live counters are never compared). A Time Travel bookmark is read before and after.
- **Stop conditions:** any refusal changes nothing. A transport or unproven outcome is `write_uncertain` (writeState `unknown`, `retry:false`) even when the readback looks untouched; only a proven rejected statement with an untouched readback is `statement_failed`. Nothing is retried or repaired without a separate GO.
- **Running it again (`already_applied`).** An existing import is verified read-only, never trusted from the pointer: the snapshot, staging and every member row (count, order, digest), the absence of change, effect and admission rows, the pointer, and then the **current** published source against the pins. `already_applied` with `receipt: verified_equal` means the stored import is complete and equals the current source at the pinned generation. A missing or altered member is `snapshot_inconsistent`; a newer publication, another generation or changed source content is `source_moved`; pins of another import are `already_bootstrapped`. The receipt is a statement of equality at that moment and **never an authorization for the next holdpoint**.
- **Holdpoint (d) revalidates.** Between the import and the marker switch the EPG may publish a newer generation. The hold/switch step must re-read the published generation and compare it with the snapshot's run (and re-import, with a new owner decision, if they differ) instead of assuming it cannot advance.
- **Rollback:** none by code. The snapshot is inert while the marker is `epg`; there is no delete path (immutability triggers). A wrong import is handled by the owner-approved data procedure, not by this operator.

- **Facts verified before and re-asserted in the batch.** The marker is exactly the expected mode, writes and generation. For `hold` and `activate` the pointer is the bootstrap import (version 1, effects drained, the pinned revision, every member present) and the published generation is still the source of the import: the same run and EPG generation, certified complete, the same member count; the full read-only proof of the bootstrap operator is repeated. For `release` the full import proof of the bootstrap operator is repeated without requiring the old EPG source to remain current (the snapshot, the staging receipt, every member, the pins), and the import-only row invariants are asserted inside the batch for `hold`, `activate` and `release`: one staging receipt of the import, one snapshot, exactly the pinned members and no change, effect or pending-admission row; a scan journal row that appeared, or a missing receipt, means it is no longer the bootstrap import. For `hold-rollback`, `export-rollback` and `revert-authority` the pointer and its snapshot are the pinned current ones (version and revision), validated separately, **and their durable causal effects are all done**: `effects_drained_version` equals the version and no `watchlist_effect` row is pending (`effects_pending`). Once the Letterboxd mode is `external` and the authority is `epg`, nothing could drain that journal, so an undrained rollback would lose unapplied facts, retention or removal work even though the membership was exported. Mirror delivery, Events and pending identity admission are not part of this check. The drain happens before the Letterboxd writer is closed (the handover step implements that orchestration); recovering an already closed, undrained journal is an explicit owner decision, never a silent discard. The EPG liveness proof (the contract of the bootstrap section: control and lease valid, no active phase, no live lease, revisions pinned) is part of `hold`, `activate` and `hold-rollback`. The EPG checkpoint authority must already be **`d1` and `open`** for `hold`, `activate` and `release` (ADR 0186 decision 8.3 and O4: the checkpoint cutover comes first); `r2` is refused (`checkpoint_not_d1`), a held marker is refused (`checkpoint_not_settled`), and the same condition is asserted inside the batch, so a change after the read aborts it. The natural-run acceptance of O4 is confirmed by the owner; the operator checks only the marker. The Letterboxd mode row is absent or `external`, pinned by revision, so there is no new writer. `release-abort` needs only the marker, so backing out is never blocked by an unreadable EPG record.
- **The root mirror fence (C3).** The root `watchlist.json` mirror is written, on the EPG side, only by `PublishedEpg.putWatchlistRoot`. Inventory of the root writers: the part replacement (`replacePart`, after `saveWatchlist`), the mirror writer `writeMirrors` (the cron repair `reconcileMirrors` and `repairMirrors` call it), and the three Worker fallback tails (`persistWatchlist`, the seal mirror unit and the commit tail), which reach it through `saveJSON` and `saveWatchlistRoot`; no other file writes the key (a test pins the inventory). The generation-addressed copies `epg/generations/<run>/watchlist.json` and the programme mirrors do not depend on the marker and are written as before, also when the root fails; nothing is paused.
  - **Who may write.** Only a marker that is POSITIVELY `epg` and `open` (a verified singleton row with a valid mode, writes, generation and its fence row), or the legacy case of the maintained Watchlist authority contract (`WatchlistD1.readAuthority`): a stored schema version BELOW 31 with none of the Watchlist tables (a test pins the version and the table set to that module). `d1`, `held`, a missing singleton row, a missing fence row, an unexpected value, a partial table set, a schema at or above 31 without the tables (a contradiction, not a legacy database) and an unreadable answer all block (fail closed). A state known not to be writable is refused BEFORE the object is touched, so a root error in a state the EPG does not own cannot stop the generation copy, the programme mirrors or the repair; in `epg`/`open` a failing root is a failed mirror, never a false success.
  - **The write path.** Read the object and its etag, read the marker AGAIN after that read, put only if the etag is still the one read. A plain re-check of the mode is not enough because the PUT is not conditional on the marker, and a content etag is not enough either: identical bytes give the same etag again (an ABA). So every root write, on every side, carries a **token no JSON reader sees**: a trailing whitespace suffix after the document (`\n`, an optional run of tabs naming the held generation of a fence, `\n`, then a 64-symbol space/tab nonce), with a FRESH nonce for each write. A write is skipped only when the stored list is semantically equal (the parsed document, the suffix ignored), so a steady state does not churn, and no representation is ever restored: an etag read before a fence can never match again, however many fences, flips, rollbacks and equal-content writes follow. The future Letterboxd-side root writer must follow the same contract (read, check the marker, conditional put with a fresh nonce), and the return to `epg` repeats the fence from that side.
  - **The fence (`fence-root`).** After `hold`, the operator rewrites the SAME list (the parsed content is checked equal before and after) with a new suffix that names the held generation, by a conditional put on the etag it read, so every in-flight conditional put loses and a writer that reads after it finds the marker `held`. It needs the R2 read credential and the R2 install credential (it may write only the key `watchlist.json`); a lost compare-and-swap is `root_moved` and wrote nothing; an unproven put is `write_uncertain` with `retry:false`.
  - **`activate` requires the proof of THIS generation.** It reads the root and requires a fence suffix whose generation equals the held generation (`root_not_fenced` otherwise: no fence at all, or the proof of an earlier hold after an abort and a new hold) and the etag the fence produced (`root_fence_mismatch` if the root changed again, which means a writer got through: the fence is repeated, never assumed). Order: `hold`, `fence-root`, `activate`.
- **Order and windows.** `hold` to `activate` is a short window: between them the EPG may start a daily run, and `activate` then refuses under the liveness proof; back out with `release-abort` and retry. In `d1`/`held` the EPG start fails closed and the snapshot is refused, never read as the EPG generation. `activate` re-reads the published generation, so a publication after the bootstrap is refused (`source_moved`) and needs a new owner decision (a new import), never a silent switch.
- **Readback.** The marker equals the target; the pointer (except that `activate` and `revert-authority` clear the mirror delivery receipt, which raises the pointer revision by at most one and is verified cleared), the row counts of every watchlist table, the checkpoint authority, the Letterboxd mode and the stable fields (mode, cutover) of the other domains are unchanged; live counters are never compared. A Time Travel bookmark is read before and after.
- **Stop conditions.** Any refusal changes nothing (`state_mismatch`, `pin_mismatch`, `snapshot_inconsistent`, `source_moved`, `checkpoint_not_settled`, `letterboxd_not_closed`, `writer_active`, `liveness_unknown`). A transport or unproven outcome, or a marker moved by another writer, is `write_uncertain` (writeState `unknown`, `retry:false`); only a proven rejected statement with the marker untouched is `predicate_refused`. Nothing is retried or repaired without a separate GO.
- **The data rollback (ADR 0186 decision 8.5).** Order: drain the causal effects and close the Letterboxd mode (it must be `external` or absent, else every step refuses `letterboxd_not_closed`), `hold-rollback`, `export-rollback`, `fence-root-rollback`, `revert-authority`, `release-rolled-back`, then re-open the Ratings daily mode (its own step). The export is the **EPG writer path** (`PublishedEpg.saveWatchlist`: a staged commit that replaces the watchlist part and moves the EPG generation by exactly one, compare-and-swapped on the generation read). Its own preconditions are asserted **inside the final replacement batch** through the writer's optional commit guard (`guards`, at most eight statements, absent for every other caller): the marker is `d1`/`held` at the generation read, the pointer and snapshot are the pinned ones with their effects done, the Letterboxd mode row is closed and pinned by revision, the EPG liveness proof holds and the publication is the pinned run, certified, at the pinned generation. A lease, a pointer move, a marker move, a mode change or an uncertified publication during the multi-batch staging aborts the replacement and nothing authoritative is written: the stored films keep every other field they already had, the snapshot owns id, title, year and url, the programme document and the shows are not touched, and the R2 mirrors are not written here (the EPG owns the root mirror again only after the revert, and its named writer reconciles it). **`fence-root-rollback` (AIR-571 M2, the reverse root fence)** runs next, in `d1`/`held`, with the generation, the run, the EPG generation the export PRODUCED and the root etag read before (`--expect-root-etag`, or `absent`): it rebuilds the root as the LEGACY document of the confirmed publication (the stored watchlist part exactly as stored, proven equal to the pinned snapshot in digest, membership and order; never a standalone mirror document, so a programme can never be paired with it), writes it with a fence token of THIS held generation and a fresh nonce by a conditional put on the etag read, and proves it by readback. A D1-side mirror writer that read the object earlier holds an etag that no longer exists, and a later one finds the marker held. **`revert-authority` additionally requires `--expect-root-etag` (the etag the reverse fence produced) and re-proves, before anything is written, that the root carries this generation's fence, has that etag and is semantically the confirmed publication's document** (`root_not_fenced`, `root_fence_mismatch`, `root_not_restored`). In the same batch that returns the marker, `revert-authority` (and `activate`) INVALIDATE the mirror delivery receipt in `watchlist_current` (`mirror_delivered_snapshot_id`, `mirror_attempts`, `mirror_next_retry_at`): the token is history, not proof of the object, because the EPG can legitimately replace the root while the token stays; the readback verifies the receipt is cleared and the pointer revision rose by at most one. It needs the list to differ and a certified, current published run; an equal list at the pinned generation answers `already_exported` and writes nothing. Its readback is digest, membership and order parity of the stored document and the member rows, the marker, the pointer, the row counts and the stable fields of other domains unchanged. **Two different facts are reported.** `authoritative` says whether the published list was replaced (`unchanged`, `replaced`, `moved_by_another_writer`, `unknown`), read from the generation and the stored list. `writeState` says whether any database write was made: a staged commit writes its claim, chunks and validation in earlier batches, so an unchanged generation does NOT prove `none`; `none` only when no batch completed and the failure is a proven rejection (or nothing was sent), otherwise `unknown` with no retry, the batches counted and the surviving staging rows reported (`stage`). A lost compare-and-swap writes nothing over the other writer and is never retried. `revert-authority` proves the stored document, not only the ids: the operator reads the published list and requires the normalized digest (title, year and url included) and the member order to equal the snapshot, the run to be certified (`published_not_certified`) and the generation to be the pinned one, and the batch binds that proof: the certified run at the exact generation, the stored payload digest of the generation (any later replacement changes it), the member rows joining the snapshot on ordinal and id, the pinned pointer with its effects done, the liveness proof and the Letterboxd mode. The same ids and order with another title, year or url (`parity_mismatch`), an uncertified publication, or a replacement after the read refuse; if the EPG published its own list in between, the export is repeated with a new owner decision. A list that already equals the snapshot needs no export. Snapshots stay as inert history; a code revert does not undo a marker.

## Holdpoint (e): the Ratings and Letterboxd writer handover (performed on 22 November 2026)

The owner's Letterboxd Sync mode control is a route of the Worker under the same Access protection as the Ratings executor route (`/api/letterboxd/ratings/executor`): `GET /api/letterboxd/sync/mode` is read-only, `POST /api/letterboxd/sync/mode` takes ONE command. It reuses the three-step switch of the control plane (`close_admission`, `complete`, `clear_quarantine`) and adds `abort`; there is no second control plane. Every command needs `confirm` equal to the action name and, except `clear_quarantine`, the **pins** of the row the owner read: `expectEpoch` and `expectRevision` (revision 0 = no row yet). A command with a stale pin is refused (`pin_mismatch`, naming the pin) and writes nothing; it is never retried, and a competing owner's write between the read and the write is a stale pin, not a blind retry. Nothing on this page is authorized by a deploy: each command is a separate owner GO, after O4, the bootstrap import (c) and the marker switch (d).

- **Read first (`GET`).** The mode row (`mode`, `target`, `epoch`, `revision`, `drain`, quarantine), the drain of the executor's instances (`verified`, `instance_live`, `unreadable`), the five-part handover proof read from live state, the causal effects of the current snapshot (`drained`, `pending`, `version`, `drainedVersion`), whether the legacy entry is fenced and how many Letterboxd writers are admitted. It writes nothing.
- **The handover proof and its protection.** `complete` toward `cloudflare` requires the proof: the Ratings executor closed (`external`), its step lease and instance drained, the legacy Ratings start and step gate answering fenced (an `external` marker alone is not the fence), the Watchlist authority an open `d1`, and every phase present. The proof is read OUTSIDE the commit and **pinned AT the commit**, from the evidence the proof itself captured (never from a second read): the facts are read before and after the proof and must be identical, otherwise the whole proof reads false. The same batch that writes the mode row asserts the Watchlist marker (`d1`/`open` at the generation read), the Ratings domain authority (`d1`/`open` at the generation read, which every authoritative Ratings commit bumps) and the stored etags of the Ratings mode, control and run records (absence included). A fact that changed after the proof aborts the completion (`handover_changed`) and nothing is written; a proof that cannot be pinned (`handover_unprotected`) does not complete a handover.
- **An already admitted legacy request.** The legacy Ratings start and step admission (and the old Cloudflare executor's step admission) decides the fence and records the Letterboxd mode revision from ONE read of the row (a second read could pick up a newer owner's revision), and every authoritative Ratings commit of that request asserts both that revision and `mode = external` (an absent row only for the initial default) in its own batch. A close, completion or abort of the Letterboxd mode after the admission therefore rejects the request's commit and writes nothing, not only the next admission. (Known window: if the Letterboxd schema is applied between a legacy admission and its commit, that one request carries no pin; the mode row is empty then and a switch needs the whole proof.)
- **Forward order.** (1) Close the Ratings Cloudflare executor to `external` through its own route (its three-step switch) and wait for its drain. (2) `close_admission` with target `cloudflare` and the pins: the epoch moves, so an in-flight old writer is fenced at its own commit, and while `switching` the legacy Ratings entry is fenced. (3) `complete` with the pins once `GET` shows the whole proof: exactly one admitted writer from that batch on.
- **Drain mode (D2).** `drain` and `resume` are owner commands on a running writer (mode `cloudflare`). Each needs `confirm` equal to the action name and FRESH `expectEpoch` and `expectRevision` pins read from `GET` just before (a `drain` changes the revision, so every later command needs pins read again). They write the marker `drain = scan_stopped` into the existing free-text column of the mode row, at the SAME epoch: no schema, no second control plane, and the running writer is not fenced. While the marker is set: no new Watchlist scan starts (the phase applies the pending effects and then reports `disabled` / `draining`; nothing is fetched, no attempt is recorded) and no promotion commits: the promotion batch, staged and final, carries a stricter guard (mode `cloudflare`, this epoch, marker not set), so a worker that began its scan BEFORE the marker cannot publish after it. The causal effects of the current snapshot, the Diary and Ratings phase, Events and the removal queue continue under the unchanged epoch guard: there is no global pause, and the owner does not force a slot; the effects finish on the next natural slot or tick. `GET` shows `scanning` (`open` or `stopped`). `resume` clears the marker. An abort back to `cloudflare` also clears it.
- **Drain outcomes.** Refusals change nothing: `not_running` (the mode is not `cloudflare`), `already_draining`, `not_draining`, `pin_mismatch` (a competing owner or a stale read: read `GET` again), `drain_not_started` (a reverse close without the marker). `write_uncertain` (`retry: false`) means the storage failed or the reply was lost: the row may or may not have changed, so read `GET` and decide with new pins; never repeat the command blindly. Recovery from a started drain is `resume`.
- **Partial schema and the legacy Ratings entry.** Once an epoch above 0 is recorded, a missing Watchlist authority table is a partial schema and fences the legacy Ratings entry (`watchlist_schema_absent`); only epoch 0 without the table is the dormant default. The legacy step admission uses the same single admission read and pin.
- **Canary hold (AIR-571 E).** The hold lets `ensure` claim ONLY the named Madrid slot (`canary_hold` for every other, nothing recorded) until `open_schedule` (confirm, pins), the owner's explicit gate before the full schedule. It is written by `complete` toward `cloudflare` WITH a `slot` (the owner route requires it: `canary_required`) or by `canary` (confirm, pins, `slot`), which also RETARGETS a settled hold (never claimed and expired, closed, or `canary:none`) in one pinned write, or moves a hold that is still before its own due instant and has no slot row to a strictly earlier valid unused slot (the earlier retarget, same single write); an in-progress canary is preserved (`canary_active` with `canary_pending`, `canary_in_progress` or `canary_instance_live`). Same epoch, same column (`canary:<slot>`, `canary:none` for the closed hold, `scan_stopped+canary:<slot>` while draining); `drain`, `resume` and an abort keep it, and an abort through the owner route without one ends in `canary:none`. `open_schedule` is refused on `canary:none` (`canary_not_set`). Refusals: `not_running`, `invalid_slot`, `canary_active`, `same_slot`, `slot_used`, `slot_in_past`, `no_canary`, `canary_not_set`, `canary_required`. See [the activation runbook](letterboxd-activation.md) for the order.
- **Reverse order.** *(Historical for the legacy writer: the Ratings Cloudflare executor is retired and its route answers `legacy_executor_retired`, so no step below hands the writer back to it or re-opens it and it is not executable. The steps remain the contract of the Letterboxd drain, the effects check and the Watchlist data rollback only; see "Recovery: forward only".)* (0) `drain`, then watch `GET` until `effects.drained` is true on a natural slot. Because no promotion can commit any more, the pending effects can only decrease. (1) The durable causal effects of the current snapshot are done BEFORE the running writer is closed: `close_admission` toward `external` refuses `drain_not_started` without the marker and `effects_pending` (with the versions and the pending count), `effects_unreadable` or `effects_unproven` otherwise, because once the epoch is closed the writer is fenced and nothing could drain them; there is no silent discard. The check is also asserted AT the commit: the batch that closes the epoch re-asserts the version read and that no effect row is undone, so a promotion that commits between the read and the write aborts the close (`effects_changed`, nothing written); a port that cannot pin it leaves the close refused (`effects_unprotected`). Mirror delivery, Events and pending identity admission are not part of this gate. (2) `close_admission` toward `external` (the writer is fenced), wait for the drain, then `complete` with the pins: the mode is `external`, which is the precondition of every Watchlist rollback operator (`letterboxd_not_closed` otherwise). (3) The Watchlist data rollback operators (holdpoint d: `hold-rollback`, `export-rollback`, `fence-root-rollback`, `revert-authority`, `release-rolled-back`) run in that order; `revert-authority` refuses without the root etag that `fence-root-rollback` produced. Through all of them the legacy Ratings entry (since retired, see "Recovery: forward only") stays FENCED: once the Letterboxd mode has been switched (epoch above 0), an `external` mode fences the entry (`watchlist_rollback_pending`) until the Watchlist marker is `epg`/`open` again, because the legacy writer rewrites the root mirror. The fence is the admission itself AND the commit of every authoritative Ratings write of an admitted request (the batch asserts the Letterboxd revision, `mode = external` and the `epg`/`open` marker), not a boolean read before a final CAS. Only then is the Ratings Cloudflare executor re-opened through its own route. Before the first switch (epoch 0, the dormant default) the Watchlist marker is not consulted, so today's pre-cutover behavior is unchanged. An integrated offline regression runs this exact order with the real rollback operator (`tests/watchlist-cutover.mjs`, section 10).
- **`abort`.** Recovery from an open `switching` back to the mode it started from (`external` or `cloudflare`), with the pins. The epoch was already raised by the close, so a writer of the old epoch stays fenced; an abort toward `external` admits no writer and the legacy entry stays fenced while the Watchlist is not `epg`/`open` (after a failed forward attempt the owner either retries the forward handover or rolls the Watchlist back; the Ratings executor cannot be re-opened before that, by design). An abort toward `cloudflare` (back out of a reverse close) re-admits the Letterboxd writer, so it needs the same five-part proof, pinned at the commit, as a forward completion: after a partial Watchlist rollback (the marker no longer an open `d1`) it is refused (`handover_not_proven`, `handover_unprotected` or `handover_changed`). An abort back to `external` after a forward close leaves the Ratings executor closed, and it stays closed: that executor is retired, so the former "re-open it through its own route" step is historical and not executable (the route answers `legacy_executor_retired`), and after such an abort no ratings writer is admitted until the Letterboxd writer is admitted again. The writer count is read from `GET` after every command (one admitted writer is the goal, zero is a visible state and two is never reached by these commands).
- **Stop conditions.** Any refusal changes nothing: `pin_mismatch`, `switch_open`, `already_in_mode`, `not_switching`, `handover_not_proven` (with the missing parts), `handover_unprotected`, `handover_changed`, `drain_not_verified`, `effects_pending`, `effects_changed`, `effects_unprotected`, `effects_unreadable`, `effects_unproven`, `drain_not_started`, `not_running`, `already_draining`, `not_draining`, `evidence_unreadable`. The one answer that is NOT a proven non-write is `write_uncertain` (`retry: false`): the storage failed or the reply was lost, so the command may or may not have committed; read `GET` again and decide with new pins, never repeat the command. A lost compare-and-swap is a proven rejection (the batch ends with a fence on the changed-row count) and reads as a stale pin. Nothing is retried or repaired without a separate GO. A Time Travel bookmark before and after each command is the operator's receipt.
- **Not here.** The Workflow binding, the cron `:30`, the flags, the Tasks and the first slot (the activation plan), and the root mirror reconciliation writer.

## Root mirror reconcile (AIR-571 M1, prepared, not performed)

The standalone root `watchlist.json` is delivery, not state, and it is written by exactly one function while the Watchlist is its own authority: `PublishedEpg.putStandaloneWatchlistRoot`, called by the Letterboxd mirror reconcile (`src/watchlist-mirror.js`) from the `ensure` tick (`ports.mirror.reconcile`; the activation wiring of the tick is the activation slice). The EPG-side writer (`putWatchlistRoot`) refuses a `d1` marker, this one refuses everything else, so the two never write the same state.

- **What is read (nothing is repaired by a read).** `GET` of the mode route is unchanged; the Letterboxd read model carries `mirror` (`state`: `delivered`, `owed`, `stale`; `attempts`; `nextRetryAt`; `warning`: `mirror_stale`). It is an independent signal: a stale mirror never changes the slot health and never stops a scan.
- **Order of one pass.** (1) ONE read of the marker (`d1`/`open` at generation G), the Letterboxd mode (`cloudflare` at the epoch) and the CURRENT pointer (snapshot id and success time equal to the target this pass delivers), before any I/O; (2) read the object and its etag; (3) the same single read again AFTER the etag read, so a pass that stalled while a newer target was delivered finds it moved (`moved`) and writes nothing: it can never overwrite a newer root with an older list that D1 would then claim delivered; (4) a stored list that is semantically equal is delivered without a write; (5) conditional put on that etag with a fresh token; (6) a readback that must be semantically the wanted document; (7) the acknowledgement, in-batch guards pinned to the generation, the epoch and the current snapshot id and freshness. The bookkeeping applies only while the target is still owed: an already delivered token is an idempotent no-op (no row change, no revision bump) and a late failure after a successful acknowledgement of the same target records nothing. Any step that cannot be proven is a failed attempt: `mirror_attempts` + 1 and `mirror_next_retry_at` (1, 5, 15, then 60 minutes).
- **Stop conditions.** Nothing to do: `not_owner` (the marker is not an open `d1`, or the mode is not `cloudflare`), `blocked` (the guard moved), `moved` (a newer target appeared while the pass ran), `unreadable`. The bookkeeping revision rises like any pointer write; a scan that loses its pointer compare-and-swap to it is replayed ONCE, only when the pointer proves bookkeeping-only contention (same version, snapshot id, success time and generation, higher revision), with that original pin carried into the replay batch. A superseded scan, a freshness-only change, an unrelated rejection and `indeterminate` are never replayed. A pass never writes while the mode is `switching` or `external`.
- **The reverse fence closes the in-flight window.** A D1-side writer that passed both guards and then stalls cannot complete a put after `hold-rollback` and `fence-root-rollback`: the fence changes the root's etag. The rollback sequence is `hold-rollback`, `export-rollback`, `fence-root-rollback`, `revert-authority`, `release-rolled-back` (see the data rollback above).
- **Receipt after a return of ownership (delivered in M2).** The delivery token in `watchlist_current` is a historical receipt, not proof of the object: the EPG can legitimately replace the root after a rollback while the token stays unchanged. `revert-authority` and `activate` therefore clear it (with the attempts and the retry time) in the same batch as the marker move, so the first reconcile after a return of ownership owes the current target again.
- **Not here.** The activation of the tick, the binding, the cron `:30`, the flags and the Tasks: the mirror reconcile and the reverse root fence are delivered dormant, and none of them is authorized to run in production.

## Activation

## Interrupted Ratings event (AIR-694)

A slot whose Ratings run was interrupted (lost step lease, a stale run closed as `unknown`) closes with Ratings `interrupted` and a `ratings` Event with badge «Прервано»; counters appear only for what the run confirmed, the rest is unknown. Already saved facts stay. It needs no manual retry, lease reset or forced run, and this runbook does not promise that the next slot starts a new run: an existing isolation can still refuse it (read `ratings_sync_status`). The step that loses its lease writes one bounded Worker log line `ratings_step_lease_lost` (`phase`, `how` = `expired` (the clock ran out) / `record_taken` (another writer took the record) / `cas_retries` (the record compare-and-swap kept failing), preserved from the site that raised it, also through the Diary page callbacks, `elapsedMs`, `leaseMs`, `diaryPages`, `lookups` and `marks`: milliseconds since the step start of `pageRead`, `planned`, `factsApplied`, `identityDone`, `pageSaving`, `removalStart`) with no URL, row, title or personal data; read it with the `cloudflare-observability-read` skill to tell a slow Letterboxd read from slow facts, identity or settlement work, and an expired clock from a taken record. RCA: [AIR-694](../evidence/letterboxd/air-694-ratings-interrupted-event-2026-11-27.md).

## Recovery: forward only

There is no rollback to a legacy writer. The Ratings Cloudflare executor (the Workflow, its class and the binding) is retired and the external ratings entry points no longer exist: the MCP tools `ratings_sync_start` and `ratings_sync_step` are unknown tools, `POST /api/letterboxd/ratings/start` and `/step` answer 404, the hourly tick does not call the Ratings executor, and the owner route `POST /api/letterboxd/ratings/executor` refuses to enter `cloudflare` (`legacy_executor_retired`). A Letterboxd mode `external` therefore closes the only ratings writer and nothing takes over; it is not a recovery target. After a failure of the Letterboxd Sync, recover forward with the controls above:

1. **Stop new Watchlist scans and promotions.** `drain` with fresh pins, then watch `GET` until `effects.drained` is true. `drain` deliberately does not stop the Diary and Ratings phase, the causal effects or the Events: they continue under the unchanged epoch guard and finish on the next natural slot or tick. `resume` only after the cause is fixed.
2. **Read the cause, read-only.** The slot rows and their outcomes (`late`, `stalled`, `missed`, `failed`, `watchlist_stale`), the Events, the mirror state, the mode row's quarantine and the read model. A read repairs nothing.
3. **Fix the cause** by a reviewed code or configuration change, deployed through the normal four jobs. Never edit a slot or outbox row to "retry".
4. **Re-establish through a natural slot.** A canary hold on one named Madrid slot, observed read-only, and `open_schedule` only by the owner's explicit gate, as in the activation record. Never force a slot.
5. **Fences stay.** A stale epoch, a held authority or an unreadable mode refuses the write; none of them is bypassed to recover.

The Watchlist rollback operators of holdpoint (d) still exist in code. They are not a recovery path: they move the Watchlist authority back to the EPG side and restore no Ratings writer, so any use needs its own owner decision and plan. Restoring a legacy writer would need a new reviewed implementation and an owner decision; it is not part of this runbook. A code rollback (`git revert`) restores code only: it restores no D1 or R2 mode or data, no Cloudflare resource and authorizes no writer. Any change of data, authority or mode needs its own owner GO. Do not start a Workflow by hand, re-enable a Scheduled Task or change a mode to test a recovery.

## Do not

Do not delete or edit a slot or outbox row to "retry" it; do not start a slot manually; do not set the Ratings mode to `external` and call that a fence. A pending Event is delivered by `ensure` and by the next run.

The dated read-only preflight, the gap analysis and the proposed holdpoints of the production cutover are in the [cutover GO/no-GO package](../evidence/d1-migration/air-571-go-no-go-package-2026-11-21.md). It authorizes nothing: every holdpoint needs its own owner GO.
