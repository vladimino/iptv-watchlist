# Read-only prediction diagnostics — MCP contract

[AIR-98](https://trello.com/c/JQEa1aK7) adds three owner-only MCP tools so a client can inspect the existing prediction queue without a one-off storage read. [AIR-82](https://trello.com/c/Oa33pTQK) can use that view for the queue investigation. [AIR-88](run-diagnostics.md) adds the run step log and caller-reported fault. These three tools stay read-only. This change does not add stored diagnostics, a D1 table, or a Scheduled Task, and it does not change how the queue, retries, coverage, or scoring are written.

## Tools

| Tool | What it returns |
| --- | --- |
| `prediction_queue_overview` | Published-generation and queue identity, snapshot time, hot/cold/total pending, `eligibleNow`, `deferredByRetry`, `retryExhausted`, `nextRetryAt` in UTC, coverage, and `snapshot.fingerprint`: the fingerprint rule in force, the Worker's target versions and registry digest, and the stored queue's classes and migration counts. `state` is `drained` only when nothing is outstanding and no retry-exhausted record remains. `temporarily_ineligible` means work remains and none of it is eligible, including retry backoff or only exhausted films. `retryExhausted` is not counted as predicted. |
| `prediction_film_diagnostics` | One film id: fingerprint presence, schema and prompt version, provenance (`produced`, `previous`), whether it is exact (`current`) and usable under the rule in force (`usable`, with `reason` and `migration`); `fingerprint.evidence` (`legacy` when the stored fingerprint has no evidence map, `unknown` when the fingerprint itself is missing, or `recorded` with a bounded `claims` list of dimension, value, basis, refs and confidence); prediction presence, whether it matches the current profile, its `reason` and `requiredWork` from the shared verdict; hot/cold membership, retry kind/scope/attempts/`failedAt`/`retryAt`/`lastRunId`, the retry's `validation` summary when the last rejection recorded one (see [the submit validation contract](enrichment.md#submit-validation-contract)), and whether the view index agrees with the film objects. A film whose stored `attempts` is at least 10 has `cause: prediction_retry_exhausted` and `eligibleNow: false`. A missing fact is `unknown` or `not_recorded`. |
| `prediction_pending` | A page of at most 20 film ids. `filter` is `all`, `eligible`, `deferred`, or `exhausted`. `all` / `eligible` / `deferred` omit exhausted identities. `exhausted` lists films whose stored retry `attempts` reached 10 (review candidates, not a catalog exclusion). The cursor belongs to one queue snapshot; after the queue changes it returns `snapshot_changed` and no ids. |

Eligibility is the same comparison the runner already uses (`queueReadyIds`): a numeric `retryAt` in the future is deferred, and `attempts >= 10` is excluded from automatic selection. The response prints that instant as UTC. The tools do not refresh the queue or rewrite a retry.

Each response has `atomic: false`. The queue, profile, programme, and view index are separate objects. When their run id, profile, or index disagree, `snapshot.partial` is true and `snapshot.reasons` names the disagreement. Coverage is `unknown` when the programme, profile, or view index cannot be read. An empty confirmed set has `percent: null`. Under a live D1 pin the window counts overlay completed programme showings by TMDB id; catalog `shows` are not a second source.

The overview reads the prediction queue, taste profile, view index, programme, discovered films, and published generation. A film diagnostic also reads that film's fingerprint and prediction. Whether a prediction is current, the index agreement and `index_ahead_of_queue` follow the same rule and profile snapshot as the queue and the readers ([prediction compatibility](../domain/prediction-compatibility.md#one-rule-for-every-consumer)). The film's `prediction` block carries `mode` (the profile rule) and `fingerprintMode` (the fingerprint rule, [fingerprint compatibility](../domain/fingerprint-compatibility.md#readers-and-diagnostics)); `cause: compatible` marks a prediction kept under another profile version by the selective rule, and `cause: fingerprint_not_current` means the fingerprint is not usable under the rule in force; `reason` and `requiredWork` are the shared verdict's, the same the queue records for the film. The `fingerprint` block separates `current` (exact schema and no invalidation) from `usable` (exact, or compatible through declared transitions), with the verdict's `reason` and `migration`. A queue built under other fingerprint schema, prompt versions or transition registry than the Worker's is reported in `snapshot.reasons` as `fingerprint_schema_differs`, `fingerprint_prompt_differs`, `prediction_prompt_differs` or `fingerprint_registry_differs`. A pending page reads the overview set and does not read one object per film. None of the tools lists the bucket or writes.

A saved failure is returned only as a short classification (`validation_error`, `parse_error`, `storage_error`, `quota`, and the existing safe stop reasons). The tools do not return profile text, fingerprint bodies, prediction text, prompts, tokens, or stack traces. `fingerprint.evidence.note` is the fixed text `declared_source_not_verified`: a `model_knowledge` token or a URL in `claims` is a declared source, not an independent check, and a legacy or unknown fingerprint adds no invented claims. A failure that was not stored is `not_recorded`. Historical retry records without a validation summary, and retries recorded for a system failure, return `retry.validation: null`; otherwise it is `{stage, reportedBy, issues}` re-checked against the closed vocabulary: a `stage` outside `caller_reported`, `fingerprint_schema`, `fingerprint_missing`, `prediction_schema` becomes `unknown`, a `reportedBy` other than `caller` or `worker` becomes `null`, and an issue whose `path` is not `fingerprint` / `prediction` with up to three field segments or whose `code` is not a contract issue code is dropped. The third segment is what keeps an evidence claim path such as `fingerprint.evidence.execution.payoff`. A `caller_reported` record from a caller that sent a failure claim (AIR-472) adds `claimed: {provenance: 'caller_claim', reason, preflightIssues}` re-checked against the same closed vocabulary (reason of the four allowed values or `null`, issues whose path is an allowed validator path and whose code is a contract code). It is shown only on a `caller_reported` record from `caller`, never on a Worker-verified one, and it is a client claim: an absent `claimed` does not mean no preflight ran, and a present one does not mean the Worker observed it.

## Hot queue parity

`prediction_hot_parity` is a fourth read-only owner tool. It answers one question: does the persisted hot lane of the Prediction queue hold the hot outstanding work that exists now? It takes no arguments.

**Method.** One cutoff (the call's own clock) and one pinned published D1 generation. The expected side is `buildPredictionQueue` run in memory on a fresh read of the pinned programme, the catalog admissions, the prediction facts and the recovery intents, with the stored queue passed as its `previous` (its retry records are the single retry authority). The window `[cutoff − 72 h, cutoff + 24 h)`, completed shows, eligibility, freshness and compatibility are therefore the queue's own rules, not a copy. The tool persists, settles, refreshes and retries nothing and calls no model. It reads the whole catalog once, so it is an occasional owner check and is never part of `prediction_batch_start`.

**Verdicts.**

| `verdict` | Meaning |
| --- | --- |
| `match` | The hot outstanding ids equal the queue's hot lane (retry-exhausted ids are outside both). |
| `degraded` | The only differences are clock-only window edges inside the 15-minute rate cap (`window_transition_deferred`), or the queue still ranks an earlier generation and waits for its own natural refresh (`generation_rollover_pending`). It is a stated deferral, not a verified count. |
| `mismatch` | A real difference. `reasons` lists the causes by size: `absent_from_queue`, `reclassified_hot`, `shows_signature_changed` (assigned shows moved after the build), `no_longer_outstanding` (the id is predicted, no longer admitted or no longer eligible), `reclassified_cold`, and `window_transition` beyond the rate cap. |
| `unknown` | The comparison cannot be made, and nothing is claimed: `queue_not_recorded`, `queue_unreadable`, `queue_shape_invalid`, `profile_not_recorded`, `programme_not_recorded`, `programme_generation_mismatch`, `epg_authority_not_d1`, `generation_unreadable`, `source_unreadable`, `snapshot_incomplete`, `catalog_not_recorded`, `shows_signature_unreadable`, `shows_signature_not_applicable`, `queue_not_comparable_<gate>` (profile, contract, registry or recovery revision differs from the Worker's), `queue_basis_carried` / `queue_basis_neutral`, and the fences `generation_changed_during_read`, `queue_changed_during_read`, `shows_changed_during_read`, `fence_unverifiable`. A source that cannot be read is never treated as empty and 0 is never reported for it. `errorCode` is a closed code, never error text.

**Answer.** `cutoff`, `generation` (authority, `programmeRunId`, generation, fence, phase), `queue` identity (revision, `programmeRunId`, basis, `refreshedAt`, age, `nextChangeAt`), `showsSignature` (stored, current, `matches`), `rateCap`, `expected` and `queueCounts` (`hotOutstanding`, `coldOutstanding`, `hotDeferredByRetry`, `actionableNow`; the queue side also `retryExhausted` and `staged`), `diff` (counts and cause histogram), `examples` (at most 10 film ids per side with `total` and `truncated`), `evaluated.films` and `elapsedMs`. These are separate quantities: actual outstanding, the queue's lane, immediately actionable (`queueReadyIds`) and excluded or deferred are never subtracted from one another. `atomic` is `false`: the generation, the queue revision and the assigned-shows signature are re-read after the evaluation, and any change is `unknown`, so a verdict is always about one snapshot.

## Recovery assessment of one film

The owner page uses the same per-film diagnostic through `GET /api/admin/prediction-recovery?film=<id>` ([route contract](admin.md#prediction-recovery-get-apiadminprediction-recovery)). The route reads the objects listed above for one film plus `enrichment/runner-lease.json` and `enrichment/latest-run.json`, runs `predictionFilmDiagnostic` and passes it to the pure assessment in `src/domain/prediction-recovery.js`. The assessment adds a status (`no_action`, `wait`, `investigate`, `blocked`, `unknown`), one cause, the next expected step with its time when known, missing prerequisites, the evidence it could not read and whether the latest run has the film in flight. It never offers a targeted action: `targetedAction.available` is always `false`, with the reason the ordinary mechanism handles the film ([why](admin-actions.md#prediction-recovery)). The queue-wide `index_ahead_of_queue` reason does not block one film's verdict; every other disagreement reason makes it `blocked` / `snapshot_partial`. Like the MCP tools it returns no profile text, fingerprint body, prediction text or raw error text.

## Production impact and rollback

The tools are read-only and stay behind the existing `IPTV MCP` Access application. Deploying the Worker does not start sync, prediction, a retry, or a Scheduled Task, and it does not change a feature flag or the queue.

Rollback is reverting this change. The previous tool list comes back. There is no stored migration to undo.

## Check after deploy

This repository change does not call production. After the Worker deploy, an owner-only MCP client can read:
