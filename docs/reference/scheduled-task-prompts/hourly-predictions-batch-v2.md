**Relation to the live prompt.** Every quality rule is carried over from [`hourly-predictions-only.md`](hourly-predictions-only.md) (Taste Profile use, `fingerprint.evidence` map, scale and reference films, `unknown` instead of invention, no `confidenceAssessment`, no version changes). What changes is the protocol: one `prediction_batch_start` replaces `prediction_start` plus `prediction_next` and the profile/schema/metadata reads, groups of up to 10 films go through `prediction_batch_submit`, and the separate `prediction_validate` call is removed because the Worker validates each film once at submit. The Task makes no `prediction_validate`, `prediction_next`, `prediction_submit` or `prediction_start` call.

## Execution playbook

One execution, from a clean context:

1. `enrichment_runner`: require the `batchRunner` block and `requires.predictionAuthority: "d1"`; otherwise stop as `batch_runner_unavailable`.
2. `prediction_batch_start({trigger:'scheduled'})` once. Outcome table:

| Answer | Task action |
| --- | --- |
| `running` | keep `runId`, `lease.epoch`, `profile`, `contract`, `films[]`, `manifestHash`; generate |
| `already_running` | success; do not adopt the `runId`; end, no `prediction_complete` |
| `noop`, `blocked` (`quota`, `retry_backoff`) | no run exists; end, report the reason |
| `manifest_too_large` | nothing created or shortened; report `bytes`, `limit`, `largestFilmBytes`; end |
| `batch_runner_requires_d1`, `prediction_catalog_held`, `prediction_retry_heal_pending` | nothing created; report the `code`; end |

3. Loop over the manifest in order, at most 100 films, groups of at most `generationSize` (10): generate, `prediction_batch_submit({runId, epoch, items})`, read every `results[].status`, keep the newest `epoch`. `prediction_heartbeat` before a long generation and at least every 10 minutes (lease TTL 15 minutes).
4. Handle `results[]` and errors as the prompt's step 8 says: `validation_failure` is not resubmitted in the run and its issue paths steer later films; `needs_regeneration` regenerates under the new profile; `deferred_budget` is resubmitted; a lost answer, timeout or `502 recoverable` replays the **same body**; `submit_in_flight` waits `retryAfterMs` then replays; `epoch_mismatch` takes the epoch from the last answer.
5. Profile change: `profile.changed` carries the new profile and `regenerate[]`; `action: "complete"` (global) ends with `prediction_complete` reason `profile_changed`.
6. End: `prediction_complete` only for an owned run: no reason when the queue is empty; reason `time_budget` when the 100-film manifest is spent and ready films remain, because the Worker refuses a reasonless complete then. **That stop is not a normal completion today:** the Worker records the run as `status: partial` with `stopReason: time_budget` and an Events Log entry titled «Прогнозы приостановлены», even when every selected film was written (`tests/scheduled-task-prompt-v2.mjs` asserts it). See [owner activation gate: bounded-run signal](#owner-activation-gate-bounded-run-signal). No completion after `already_running`, `manifest_too_large`, `wrong_protocol`, `prediction_catalog_held` or `lease_lost`. Re-read `enrichment_status` and `enrichment_queue` and compare.

### Dry run and A/B (separate procedure, not this Task)

The dry run is an owner-approved manual experiment (AIR-450), never the schedule. It follows [ADR 0122](../../adr/0122-prediction-batch-runner-v2-dual-protocol.md) decision 10: **one** read-only `prediction_batch_start(dryRun)` takes the manifest, and the ten size passes replay that one frozen manifest and **never call start again**. The start is a separate owner-run freeze step; each pass is the second prompt below, `DRY RUN PROMPT`, which takes the whole frozen manifest as an explicit input and has `prediction_batch_submit(dryRun)` as its only tool. Generation steps 4, 5 and 6 are byte-identical to the scheduled prompt's (a test compares them), so a size-A/B changes grouping only. The freeze, the private handoff and retention, the result contract and the comparison criteria are in the [dry-run A/B runbook](../../runbooks/prediction-batch-v2-dry-run-ab.md) and the machine-readable [sample and result schema](batch-v2-ab.schema.json).

The exact MCP calls (the frozen dry-run manifest has `runId: null`, and the MCP schema and the Worker still require a non-empty `runId` and a positive integer `epoch` on a dry-run submit; the dry-run branch never dereferences a run, so the fixed synthetic pair `runId: "dry-run"`, `epoch: 1` is used):

```
prediction_batch_start({trigger:"manual", dryRun:true, pin:{filmIds:[...]}})   // ONCE, by the owner's freeze step; never inside a pass
prediction_batch_submit({runId:"dry-run", epoch:1, dryRun:true, manifestHash:"<from start>", items:[{filmId, fingerprint?, prediction, inputHash:"<from start>"}, ...]})
```

Nothing is written (no lease, run, queue, fingerprint, prediction, version object or view-index entry); `tests/scheduled-task-prompt-v2.mjs` hands one serialized manifest to ten independent passes, counts a single start in total and checks zero D1 and R2 change.

### Owner activation gate: bounded-run signal

A run that stops at the 100-film manifest cap with ready films left can only end with `prediction_complete` and a non-normal `reason` (`time_budget` is the closest existing one). Today the Worker records that as a **partial stop**: run `status: partial`, `stopReason: time_budget`, an Events Log entry «Прогнозы приостановлены» and the footer's stop line, for every successful bounded cycle. AIR-449 changes no Worker code. Before AIR-451 the owner decides one of: (a) accept that signal for the v2 Task and its monitoring, or (b) scope a separate Worker delivery with a distinct normal completion (for example `manifest_spent`, no stop Event). Until decided, do not describe a 100-film cycle as an ordinary success in reports or Trello.

### Installation, activation and rollback (owner gates)

- **Install (disabled):** creating the Task, setting its schedule and every prompt edit need the owner's operation-specific approval. Create it disabled; paste the text below; compare the registry readback (length and SHA-256) with this header.
- **Activation (AIR-451):** exactly one Predictions Task is enabled. The owner disables the legacy hourly Task and enables this one in the approved order, then reads the registry back. There is no feature flag, and the Worker does not read the registry.
- **Rollback:** disable this Task and re-enable the legacy hourly Task. No data migration; runs, retries and predictions already written stay valid under the same contract.

ОБЯЗАТЕЛЬНАЯ КАРТА fingerprint.evidence для нового fingerprint по правилам manifest.contract.schema.contract.fingerprint.evidence: ТОЛЬКО plotMechanics и execution; на КАЖДЫЙ заявленный id в fingerprint.plotMechanics 1–4 обоснованных items в evidence.plotMechanics[id]; для КАЖДОГО general execution dimension с конкретным значением (не unknown/not_applicable) 1–4 items. Жанровые dimensions опциональны; конкретный genre dimension с items следует тем же правилам и не может быть только metadata. Каждый item содержит РОВНО {basis,refs,confidence}; basis = metadata, model_knowledge или web_research; confidence = low/medium/high; refs = 1–4 уникальных строк; без дублей и extra keys. metadata подтверждает механику лишь по факту, реально присутствующему в modelMetadata этого фильма (metadata:synopsis, metadata:genres, metadata:runtime, metadata:credits), и НЕ доказывает качество исполнения: все items одной execution-quality претензии не могут быть только metadata. model_knowledge имеет только ref "model_knowledge". web_research допустим только с реально использованными HTTPS-адресами; без фактического внешнего исследования не используй его, никогда не придумывай URL.
