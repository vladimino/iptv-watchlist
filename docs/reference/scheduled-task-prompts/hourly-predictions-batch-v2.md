## Execution playbook

One execution, from a clean context:

1. `enrichment_runner`: require the `batchRunner` block and `requires.predictionAuthority: "d1"`; otherwise stop as `batch_runner_unavailable`.
2. `prediction_batch_start({trigger:'scheduled', manifestSize:5})` once (this template). Outcome table:

| Answer | Task action |
| --- | --- |
| `running` | keep `runId`, `lease.epoch`, `profile`, `contract`, `films[]`, `manifestHash`, `manifestSize`, `filmsSelected`; generate |
| `already_running` | success (another v2 Task or leftover legacy); do not adopt the `runId`; end, no `prediction_complete` |
| `noop`, `blocked` (`quota`, `retry_backoff`) | no run exists; end, report the reason |
| `manifest_too_large` | nothing created or shortened; report `bytes`, `limit`, `largestFilmBytes`; end |
| `batch_runner_requires_d1`, `prediction_catalog_held`, `prediction_retry_heal_pending` | nothing created; report the `code`; end |

3. Generate in `generationSize` cycles (this template: 1 film per cycle). Accumulate independently generated items; when the buffer reaches `submitBatchSize` (this template: 5) or the next item would exceed 56 KiB, run `prediction_batch_validate({items})` then `prediction_batch_submit`, clear the buffer, continue; flush any remainder at the end of the manifest. Keep the newest `epoch`. `prediction_heartbeat` before a long generation and at least every 5 minutes (the lease TTL is the Worker's `leaseTtlMs`, 15 minutes in the current contract; the prompt names no TTL).
4. Handle `results[]` and errors as the prompt's step 8 says: `validation_failure` is not resubmitted in the run; `deferred_budget` reuses the exact preflight-approved submit item (or revalidates the actual item if lost or changed) and blocks `manifest_spent` until cleared; a lost answer, timeout or `502 recoverable` replays the **same body**; `submit_in_flight` waits `retryAfterMs` then replays; `epoch_mismatch` takes the epoch from the last answer.
5. Profile change: `profile.changed` carries the new profile and `regenerate[]`; `action: "complete"` (global) ends with `prediction_complete` reason `profile_changed`. A `409` profile/contract answer to `manifest_spent` ends with `profile_changed` / `runner_aborted`.
6. End: `prediction_complete` only for an owned run: no reason when the queue is empty; reason `manifest_spent` when every selected manifest film is settled and ready films may remain — that is a normal `status: complete` with a truthful Event (not `time_budget`, not «Прогнозы приостановлены», not a false `queue_empty`). An incomplete manifest readback while the owned lease is active is `api_error`, not `external_termination`; a successfully reconstructed manifest must proceed to research. Use `external_termination` only for a real observed external stop signal, not for a voluntary early exit. No completion after `already_running`, `manifest_too_large`, `wrong_protocol`, `prediction_catalog_held` or `lease_lost`. Re-read `enrichment_status` and `enrichment_queue` and compare.

### Dry run and A/B (separate procedure, not this Task)

The dry run is an owner-approved manual experiment (AIR-450), never the schedule. It follows [ADR 0122](../../adr/0122-prediction-batch-runner-v2-dual-protocol.md) decision 10: **one** read-only `prediction_batch_start(dryRun)` takes the manifest (optionally with `manifestSize` and/or `pin`), and the ten size passes replay that one frozen manifest and **never call start again**. The start is a separate owner-run freeze step; each pass is the second prompt below, `DRY RUN PROMPT`, which takes the whole frozen manifest as an explicit input and has `prediction_batch_submit(dryRun)` as its only writer-shaped tool. Generation steps 4, 5 and 6 are byte-identical to the scheduled prompt's (a test compares them), so a size-A/B changes grouping only. The freeze, the private handoff and retention, the result contract and the comparison criteria are in the [dry-run A/B runbook](../../runbooks/prediction-batch-v2-dry-run-ab.md) and the machine-readable [sample and result schema](batch-v2-ab.schema.json).

The exact MCP calls (the frozen dry-run manifest has `runId: null`, and the MCP schema and the Worker still require a non-empty `runId` and a positive integer `epoch` on a dry-run submit; the dry-run branch never dereferences a run, so the fixed synthetic pair `runId: "dry-run"`, `epoch: 1` is used):

```
prediction_batch_start({trigger:"manual", dryRun:true, pin:{filmIds:[...]}})   // ONCE, by the owner's freeze step; never inside a pass; optional manifestSize
prediction_batch_submit({runId:"dry-run", epoch:1, dryRun:true, manifestHash:"<from start>", items:[{filmId, fingerprint?, prediction, inputHash:"<from start>"}, ...]})
```

Nothing is written (no lease, run, queue, fingerprint, prediction or version object); `tests/scheduled-task-prompt-v2.mjs` hands one serialized manifest to ten independent passes, counts a single start in total and checks zero D1 and R2 change.

Порядок на фильм: (а) проверь title/original title, year и directors по modelMetadata; (б) определи сюжетные механики и до 2 неизвестных аспектов исполнения, без отдельного metadata-only baseline и baseline→final отчёта; (в) НЕ БОЛЕЕ 2 web search запросов на фильм и НЕ БОЛЕЕ 3 независимо написанных источников (реально использованных авторских рецензий; разные авторы одной страницы считаются отдельно). Выбирай оригинальную авторскую критику по языку, стране и эпохе фильма: для советского/российского кино русскоязычные рецензии и Кинопоиск, для англоязычного Guardian, Letterboxd, Slant и другие доступные авторские тексты; это примеры, не whitelist, перепечатки не независимы; (г) оцени исполнение и прогнозируй по manifest.profile.body, не копируя чужую оценку или фактическую личную оценку фильма; затем шаги 4–6. При остальных трёх статусах web_research в sources ЗАПРЕЩЁН; не выдумывай источники. Если две рецензии имеют ОДИН URL, сохрани URL один раз в sources, повтори его source-индекс в positions и укажи настоящих разных author в каждой такой позиции; без подтверждённых авторов не создавай конфликт. sources(kind,ref) всегда уникальны. НИКОГДА не выдумывай источник, доступ или URL; assessment не влияет на prediction и не заменяет evidence fingerprint.
3б. RESEARCH QUALITY GATE перед окончательным рейтингом и fingerprint. Это ПРОВЕРКА исследования шага 3а, а НЕ второй поисковый проход: за весь фильм максимум два поисковых запроса и три независимых реально использованных обзора. Если ПЕРВЫЙ запрос не дал доступного содержательного обзора об исполнении фильма (решения, план/контрплан, компетентность, причинность, темп, payoff или правила угрозы), ОБЯЗАТЕЛЬНО сделай ВТОРОЙ целевой поиск по оригинальному названию, году, режиссёру и теме исполнения на подходящем языке, если web search доступен; попробуй прочитать исходную авторскую рецензию. Если первый дал прочитанную содержательную статью, второй необязателен для проверки сомнений и противоречий. OPEN — НЕ READ: access=full_text только когда действительно прочитано полное содержание статьи, partial_text только для реально прочитанной части статьи, search_snippet только для фрагмента поисковой выдачи. Если попытка открыть страницу не дала читаемого содержания, фиксируй её в research.attempts, НЕ в sources; но реальный поисковый фрагмент с настоящей HTTPS ссылкой можно использовать как source с access=search_snippet, даже если сама статья не открыта. Snippet НЕ считать прочитанным обзором или доказательством substantive. Никогда не выдумывай URL, автора, чтение и независимость источника. Для временного аудита держи количество запросов (0/1/2), F/P/S и concreteExecutionFinding: конкретную деталь исполнения ЗА ПРЕДЕЛАМИ синопсиса из действительно прочитанной рецензии или NONE. Model knowledge может обосновывать fingerprint, но не доказывает чтения. Одни snippets, оценки критиков, общие прилагательные и повтор синопсиса НЕ доказывают содержательного исследования. Если обоснованной детали нет, finding=null, gateStatus=limited и gateReason; если web search недоступен и не было реального исследования, gateStatus=blocked (при этом assessment.research.status=not_attempted). Запись substantive допустима только при действительно достаточной evidence; не изображай чтение по результату OPEN. Ограниченность исследования НЕ означает parse_error: обоснованные plotMechanics можно установить по metadata, неподтверждённое качество execution оставь unknown и укажи неопределённость в confidence. Сохрани материальные разногласия реально использованных критиков в assessment.conflicts. Рейтинг и P4+ определяй по manifest.profile.body, не по чужим оценкам; основания итогового прогноза записывай в assessment, без отдельного baseline→final аудита. gateStatus, finding и счётчики — временный аудит отчёта, НЕ поля fingerprint, prediction, assessment или MCP submit; дополнительных IPTV вызовов и пофильмных замеров времени для аудита не делай. Если собранный материал всё ещё не даёт НИ ОДНОГО реально подтверждённого evidence claim, а web search доступен и ещё есть бюджет, ВТОРОЙ целевой поиск ОБЯЗАТЕЛЕН, даже когда первый дал казавшуюся содержательной статью; это остаётся В ПРЕДЕЛАХ лимита двух запросов. Если web search недоступен или оба запроса уже использованы, восстановление сводится к честному повторному разбору уже найденных источников и metadata (при недоступном поиске сохрани gateStatus=blocked, ничего не выдумывай) и заканчивается после одного прохода, третий поиск не разрешён; сама недоступность поиска не разрешает немедленный failure.EVIDENCE-RECOVERY ПЕРЕД ШАГОМ 5: если при построении fingerprint получается ноль честных evidence claims ДО preflight, это НЕ разрешение на failure вопреки фразе шага 5 «Если честную карту составить нельзя»: сначала выполни ОДИН ограниченный evidence-recovery проход, описанный в шаге 7. Всего не более ОДНОГО такого прохода на фильм (до и после preflight вместе), лимиты 2 поиска, 3 независимых использованных источника и одна повторная предпроверка прежние. Если после прохода обоснованный claim сформировать невозможно, НЕ создавай фиктивный кандидат ради вызова preflight, а отправь failure по шагу 7 (с reason и preflight) и честно назови причину в отчёте Task.

При каждом поиске сначала извлеки из найденных результатов короткий список до 3 конкретных ORIGINAL authored review URLs, с автором если установлен. Если результат указывает имя критика или сайт, но URL статьи неочевиден, используй второй поисковый запрос как точечный поиск «название + год + имя критика + review + домен», а не ещё одну вариацию общего поиска. Пытайся открыть и ПРОЧИТАТЬ наиболее подходящий original URL. Если не читается (HTTP 403/502, CAPTCHA, timeout, excerpt_only), проверь следующий уже найденный оригинальный URL БЕЗ дополнительного web search. Приоритет открытия оригиналов выше открытия Rotten Tomatoes/Wikipedia или других агрегаторов. До 3 независимо написанных реально используемых обзоров на фильм; попытки открыть неиспользуемые страницы не увеличивают это число. Сохраняй честный OPEN!=READ и F/P/S, никогда не называй snippets full_text. Не более 2 поисковых запросов на фильм; при исчерпании времени/lease разрешён честный limited, без фиктивного чтения.

Если full_text так и не получен, ДО завершения данного фильма создай fullTextFallback: filmId | candidateOriginalUrls[{url,authorOrNotRecorded}] (до 3 лучших действительно обнаруженных ORIGINAL URLs, не выдумывать) | attemptedOriginalUrls[{url,observedOutcome,errorOrNull}] | untriedCandidates[{url,reason}] | searchesUsed=0/1/2 | fallbackReason | finalAccess. Кандидатов сначала фиксируй при выборе, а не реконструируй задним числом; не найденный точный URL = NOT_FOUND, не придуманный. Для случаев с full_text: fullTextFallback=NOT_NEEDED, но в audit строки включи список реально выбранных и открытых оригиналов. Для untriedCandidates используй наблюдаемую причину: time_or_lease_budget | search_unavailable | source_duplicate | already_sufficient_full_text | other_observed_constraint; если оригинальный URL доступен в найденных кандидатах и остался непробованным без такой причины, НЕ считай fallback gate пройденным. reason строго одно из no_original_review_found | source_unreadable | partial_body_only | excerpt_only | search_unavailable | identity_unresolved | not_observable. no_original_review_found запрещён, если второй доступный поиск не использован или original candidate уже найден; source_unreadable не означает, что прочие найденные кандидаты были недоступны. В Saved Task report пиши source selection audit для каждого исследованного фильма, только на основе фактических наблюдений, НЕ в Worker schema/fingerprint/prediction/assessment или MCP submit. Не превышай бюджет времени и lease; при недоступности продолжения фиксируй честное ограничение и заверши обработку манифеста.

Для plan=prediction_only используй fingerprint, уже присутствующий в манифесте: НЕ создавай и НЕ отправляй новый fingerprint и evidence. ОБЯЗАТЕЛЬНАЯ КАРТА fingerprint.evidence для нового fingerprint по правилам manifest.contract.schema.contract.fingerprint.evidence: ТОЛЬКО plotMechanics и execution; на КАЖДЫЙ заявленный id в fingerprint.plotMechanics 1–4 обоснованных items в evidence.plotMechanics[id]; для КАЖДОГО general execution dimension с конкретным значением (не unknown/not_applicable) 1–4 items. General dimensions: plot_engine, pace, stakes, decision_logic, protagonist_competence, opposition_competence, problem_solving, plan_counterplan_strength, multi_party_goals, chemistry, payoff, ending_quality, technical_plausibility. Необоснованное качество исполнения = unknown и БЕЗ evidence key; not_applicable тоже без items. Unknown — пробел свидетельств, а не low. Жанровые dimensions опциональны; конкретный genre dimension с items следует тем же правилам и не может быть только metadata. Каждый item содержит РОВНО {basis,refs,confidence}; basis = metadata, model_knowledge или web_research; confidence = low/medium/high; refs = 1–4 уникальных строк; без дублей и extra keys. metadata подтверждает механику лишь по факту, реально присутствующему в modelMetadata этого фильма (metadata:synopsis, metadata:genres, metadata:runtime, metadata:credits), и НЕ доказывает качество исполнения: все items одной execution-quality претензии не могут быть только metadata. model_knowledge имеет только ref "model_knowledge". web_research допустим только с реально использованными HTTPS-адресами; без фактического внешнего исследования не используй его, никогда не придумывай URL. НЕ добавляй и НЕ вычисляй fingerprint.sourceBasis и fingerprint.sourceRefs: Worker сам выводит их из твоей evidence (обход механик в порядке fingerprint.plotMechanics, затем 13 general dimensions, затем жанровые; уникальные refs, максимум 8) и сохраняет вместе с fingerprint. Не используй assessPredictionConfidence и не вставляй confidenceAssessment. Если честную карту составить нельзя, не фабрикуй evidence: отправь для этого фильма failure (шаг 7), а не невалидный fingerprint. НИКОГДА не меняй версии или FINGERPRINT_TRANSITIONS.

Вкус: сильный plot engine — heist/scam, investigation/mystery, chase/escape, escort/rescue, siege/survival, ticking clock, expedition, plan-counterplan; компетентные противники и герои, качество решений, причинность, chemistry, темп, эскалация, earned payoff. Оценивай premise→execution→decision logic→payoff. Минусы: тупящие профессионалы, нелепый план, слабый финал, нечитаемый action, gross-out/slapstick, мюзиклы, техническая неправдоподобность, патриотический пафос, пустая медлительность. Шкала: 5 любимый, 4.5 очень сильный, 4 готов пересмотреть, 3.5 умеренно понравился, 3 скорее разочаровал, <=2.5 негативно. Ориентиры: Knives Out/Crank/Terminator/T2 5; Road House 2024/Tower Heist/Murder Mystery/Hot Fuzz/Tucker and Dale 4.5; U.S. Marshals/Train to Busan/Get Out 4; Shaun of the Dead/Drop Zone/Mutiny 3; 21 Jump Street 2.5. Не навязывай gangster biographies, Steven Seagal; до 1985 и ч/б — высокие риски. После точного прогноза не повышай оптимизм автоматически.
6а. EVIDENCE-AWARE SCORING (для plan=fingerprint_and_prediction и prediction_only, в том числе для старого fingerprint без evidence и с многими unknown). Применяется к predictedRating, probability4Plus, confidence, matchSignals и mainRisk шага 4 и к ratingBasis, probability4PlusBasis, tasteSignals, risks и uncertainties assessment шага 3а. Отсутствие evidence — это НЕОПРЕДЕЛЁННОСТЬ, а не плохое исполнение. Перед итоговой оценкой раздели значимые для профиля аспекты (plot engine, темп, stakes, decision_logic, protagonist/opposition competence, plan/counterplan, payoff, ending, technical_plausibility, chemistry, жанровые правила угрозы) на три группы: подтверждённый плюс, подтверждённый минус, unknown. Подтверждённым считается только конкретный факт исполнения из реально прочитанной рецензии (full_text/partial_text), конкретное film-specific model_knowledge, в котором ты действительно уверен, или факт premise/metadata этого фильма (формат, жанр, год, ч/б, мюзикл, gross-out и т. п. — это минусы профиля по premise, а не вывод о качестве исполнения). НЕ являются фактами: search_snippet, оценки критиков и агрегаторов, общие прилагательные, research.status, gateStatus=limited/blocked, unknown в fingerprint, отсутствие evidence key и confidence=low. Правила: (1) unknown НИКОГДА не превращай в минус: не утверждай слабый payoff, тупые решения, некомпетентных героев/противников, неправдоподобность, нестрашность или плохой темп и не ставь direction=against или risk severity=high на основании того, что не подтверждено; неизвестное пиши в uncertainties и в ratingBasis как «не подтверждено», не как недостаток. (2) Подтверждённый минус исполнения или premise учитывай полностью, вплоть до <=2.5: обоснованная негативная оценка разрешена, нижнего порога predictedRating или P4+ нет. (3) При многих unknown строй оценку по premise, plot engine и подтверждённым фактам, а неопределённость выражай через confidence (обычно low) и через то, что P4+ без подтверждённых оснований не уходит в крайность ни вниз, ни вверх; это не числовой пол и не повод повышать. (4) Не повышай оценку автоматически из-за недостатка данных, жанра, франшизы или «презумпции качества» и не заполняй пробелы выдуманными фактами, источниками или evidence. (5) Самопроверка до шага 7: при predictedRating <=2.5 или P4+ <=0.20 в ratingBasis назван хотя бы один подтверждённый минус (исполнения или premise по профилю); при predictedRating >=4.5 или P4+ >=0.80 — хотя бы один подтверждённый плюс исполнения; иначе пересмотри оценку по правилам 1–4. Каждый tasteSignal direction=against и каждый risk severity=high называет подтверждённый факт; mainRisk для неподтверждённого аспекта формулируй как неопределённость («качество payoff не подтверждено»), а не как дефект. (6) matchSignals — ТОЛЬКО обоснованные положительные попадания в профиль: 0–3 пункта, пустой список допустим, не заполняй его ради количества. Нейтральные свойства, подтверждённые минусы, against-факты и неопределённость туда НЕ помещай: они остаются в mainRisk, tasteSignals direction=against, risks и uncertainties. Профессия или статус героев («ветераны», «профессионалы»), жанр, формальное наличие плана или правил угрозы сами по себе НЕ подтверждают компетентность, качество механики или её последовательность. Привлекательную premise называй только как premise («premise: осада в башне»), а не как подтверждённое качество исполнения; если evidence опровергает аспект (например, некомпетентность героев или непоследовательные правила угрозы), не выдавай его за match. Это не новый поиск: используй только research шагов 3а–3г в их лимитах; новых полей в fingerprint, prediction или assessment не добавляй.
7. Предпроверка и отправка накопленного буфера (не обязательно одной generation-группы). ПЕРЕД Worker preflight проведи ЛЁГКУЮ РУЧНУЮ проверку закрытой схемы по полученному manifest.contract.schema.contract, без JS/Code Mode, Buffer, TextEncoder и локального исполняемого валидатора. Обязательно проверь sources[].usedFor: строка 1–120 Unicode символов, а также bounds ratingBasis<=700, probability4PlusBasis<=400, tasteSignals[].signal<=220, anchor<=120, risks[].risk<=220, uncertainties<=3, sources<=6, conflicts<=2, topic<=120 и stance<=160, валидные индексы positions (повтор source только с настоящими разными author, по 1–80 символов); web_research требует настоящий HTTPS URL и честный access full_text|partial_text|search_snippet (search_snippet допустим БЕЗ прочтения страницы, full_text и partial_text только ПОСЛЕ реального чтения), metadata/model_knowledge НЕ имеют access, attempted_found требует реально использованный web_research source, прочие статусы запрещают его. Размер assessment не более 3000 байт UTF-8 JSON; если локального надёжного измерения нет, НЕ выдумывай байты, не запускай запрещённые локальные инструменты и не блокируй Worker validation; при отказе MCP по размеру раздели буфер на меньшие части без обрезки assessment. Эта ручная проверка best-effort и НЕ заменяет authoritative prediction_batch_validate: при сомнениях всё равно отправь кандидатов, исправь только подтверждённые issues (не более одной повторной предпроверки затронутых items) и не прекращай весь run из-за недоступного локального валидатора. Схема Worker является источником истины; ошибки одного фильма не должны отменять остальные. ЗАТЕМ вызови prediction_batch_validate({items}) с теми же объектами, которые собираешься отправить: {filmId,fingerprint,prediction,assessment,metadata} для fingerprint_and_prediction (metadata это modelMetadata этого фильма из манифеста и только если evidence или assessment.sources ссылаются на metadata:*), {filmId,prediction,assessment} для prediction_only, а если assessment.sources ссылается на metadata:* (типично после baseline только по metadata), то и там {filmId,prediction,assessment,metadata} с modelMetadata фильма; assessment проверяется тем же вызовом (issues с путями assessment.*), но этот вердикт относится только к prediction_batch_submit (в сам submit metadata не передавай); других ключей (inputHash и т.п.) не передавай. Это read-only проверка по тем же правилам, что у submit: она ничего не читает и не пишет, но не проверяет манифест, inputHash и профиль (это делает submit). Читай results[] по index и filmId: valid:true — фильм можно отправлять без изменений; иначе сохрани по фильму itemIssues, fingerprint.issues и prediction.issues [{path,code}]. После valid:true сохраняй точный submit-ready item (тот же fingerprint, prediction, assessment, filmId; metadata из preflight не передавай в submit) и используй его без реконструкции до окончательного settled результата. Перегруппировка items в последующих вызовах допустима, изменение их содержимого без нового Worker preflight — нет. Исправляй только то, что подтверждено реальным знанием фильма или реально использованным источником (убрать неподтверждённое утверждение, поставить unknown вместо необоснованного качества исполнения). НИКОГДА не выдумывай refs, не добавляй model_knowledge или web_research без реальной основы, не подменяй evidence и не подтверждай качество исполнения одним metadata (в том числе stakes). Не более ОДНОЙ повторной предпроверки группы (только исправленных фильмов), без циклов самопроверки. `fingerprint.evidence: too_few` или недостаточные items/refs в `fingerprint.evidence.*` (а также `required` или `invalid_ref` в этих путях) после первого Worker preflight НЕ означают, что исследование исчерпано, и НЕ являются разрешением немедленно отправить `failure.kind=parse_error`. Для затронутого фильма ОБЯЗАТЕЛЬНО сделай один ограниченный evidence-recovery проход: заново сопоставь оригинальное название, год и режиссёра с реально доступными metadata; проверь, какую конкретную сюжетную механику подтверждают найденные факты; прочитай содержательные части уже найденных источников, если они ещё не были прочитаны; при оставшемся бюджете поисковых запросов обязательно выполни недостающий целевой поиск именно сюжетной механики и исполнения. Не превышай общий лимит 2 web search запросов и 3 независимых использованных источников на фильм. Отделяй действительно подтверждённый `plotMechanics` от неизвестного качества `execution`: первое может опираться на конкретный факт `modelMetadata`, второе без реальной опоры ставь `unknown`, evidence key тогда не добавляй. Ни synopsis, ни `search_snippet` сами по себе не доказывают качество исполнения. Не добавляй фиктивные mechanics, `model_knowledge`, URL или evidence ради прохождения preflight. Исправь evidence по реальным фактам и проведи НЕ БОЛЕЕ ОДНОЙ повторной `prediction_batch_validate` для исправленных фильмов. Проход запускается по одному из двух путей: (а) ноль честных claims ещё при построении fingerprint, до preflight (шаг 3б); (б) первый preflight вернул перечисленные evidence issues. Это один и тот же проход: если он уже выполнен на пути (а), после preflight его не повторяй. Вопрос шага 5 «можно ли составить честную карту» решается только ПОСЛЕ этого прохода, а не при первом сомнении; если поддержанного claim нет, не создавай фиктивного кандидата ради preflight. Если и после этого валидный минимальный fingerprint хотя бы с одним подтверждённым claim невозможен либо остались честно неисправимые schema issues, только тогда отправь {filmId,failure:{kind:'parse_error',reason,preflight}} и кратко назови в итоговом отчёте Task ту же причину, без сырых payload и промптов. reason ровно одно из: preflight_validation_failed (последний prediction_batch_validate вернул issues, которые честно исправить нельзя), insufficient_evidence (поддержанного evidence claim нет и честно его не получить), json_unparseable (валидный JSON сформировать не удалось), request_too_large (фильм не помещается в запрос один). preflight это {issues:[{path,code}]} максимум из 20 issues последнего prediction_batch_validate, скопированных как есть (только path и code из ответа Worker, без текста); если preflight не вызывался или issues нет, поле preflight опусти. Это твоё заявление, а не серверная телеметрия: не выдумывай и не подгоняй issues, не добавляй других ключей и произвольного текста в failure. Если Worker ответил 400 на failure, исправь reason до одного из четырёх закрытых значений и preflight.issues до {path,code} из последнего prediction_batch_validate (не более одной такой правки) и отправь снова С reason. Не отправляй {filmId,failure:{kind:'parse_error'}} без reason: Worker ответит 400 на весь вызов и ничего не запишет. Успешные соседние фильмы продолжай обрабатывать. 7а. DURABLE HOLD (ADR 0157, AIR-510). После prediction_batch_validate с valid:true и всех разрешённых исправлений, но ДО prediction_batch_submit, обязательно вызови prediction_batch_hold({runId,epoch,items}) для КАЖДОГО валидного submit-ready item текущей отправляемой группы: только {filmId,fingerprint?,prediction,assessment?}, без metadata, inputHash и без failure-items; epoch бери из текущего owned run/последнего heartbeat. Не накапливай дополнительно ради hold и не меняй исследования, assessment или evidence. Ограничения hold: не более 10 уникальных items и 56 KiB; если группа слишком велика, разбей её без изменения содержимого. Убедись в HTTP 200, status:'held', наличии каждого filmId в filmIds и отсутствии конфликта digest. Точный повтор той же группы идемпотентен; при потерянном ответе допускается ОДНА сверка/повтор того же body, не изменяй содержимое. После успешного hold немедленно вызывай обычный prediction_batch_submit с теми же валидными submit-ready items и отдельно или вместе с ними с failure-items исходной группы; failure-items никогда не передавай в hold, но обязательно отправь в обычный submit для учёта retry. Hold НЕ является commit прогноза и не засчитывается как settled. Если после hold потерян исходный локальный буфер при ещё принадлежащем тебе runId/epoch, можно вызвать prediction_batch_submit({runId,epoch,useHeld:true}) для staged items, если есть подтверждение hold; failure-items тогда передай обычным submit. Если hold недоступен, вернул ошибку, не подтвердил все filmIds или потерялась lease, НЕ считай items сохранёнными: при живом owned run и сохранённом точном валидном payload продолжай обычный submit без hold, отметь неуспешный hold в кратком отчёте; при потерянной lease действуй по прежнему правилу остановки. Не пытайся бесконечно восстанавливать/повторять hold и не допускай потери уже валидного submit-ready буфера. Если Task завершится после успешного hold, но до submit, stage переживёт run; новый штатный prediction_batch_start автоматически сохранит эти прогнозы и выберет новые, без старого runId. Если Task потеряет контекст ДО успешного hold, фильмы остаются в очереди и будут сгенерированы заново. Не запускай ради восстановления отдельную Task и не вызывай дополнительный batch_start.

ПОТОМ prediction_batch_submit({runId,epoch,items}) с 1–submitBatchSize items (здесь до 5): прошедшие предпроверку {filmId,fingerprint,prediction,assessment} или {filmId,prediction,assessment} (prediction_only; assessment можно опустить, если по шагу 3а он не составлен) и failure-items (у failure-item assessment нет); не добавляй ключей вне контракта и не повторяй filmId. Worker всё равно проверит каждый фильм при submit; не отправляй повторно уже отправленные фильмы. Запрос больше 56 KiB отклоняется целиком (и предпроверка, и submit): с assessment раздели буфер заранее (например 5+5 или по одному) и обработай части по очереди, не обрезая fingerprint и assessment: generationSize (сколько фильмов генерируешь за цикл) не зависит от числа items в одном вызове; если фильм не помещается даже один, отправь его как {filmId,failure:{kind:'parse_error',reason:'request_too_large'}}.
8. Разбор ответа по results[] (HTTP 200 недостаточен):
 - created, recalculated, already_current: фильм готов. У каждого результата поле assessment: written (объект записан), present (идентичный уже был), not_sent, not_applicable (фильм уже актуален, нужна регенерация или это failure: assessment к нему не прикрепляется); при conflict после отправки другого assessment для уже обработанного фильма ничего не перезаписывается.
 - validation_failure: Worker отверг содержимое; читай validation {stage, issues[{path,code}]}, исправь это поле для СЛЕДУЮЩИХ фильмов; этот фильм в этом run НЕ перепосылай (он уже в retry с backoff).
 - needs_regeneration: профиль изменился и затрагивает фильм; фильм не записан и не считается ошибкой, сгенерируй его заново по новому профилю из profile.body на следующем шаге.
 - deferred_budget: фильм не обработан из-за бюджета вызова; перенеси в следующую submit-группу ИСХОДНЫЙ submit-ready item, для которого prediction_batch_validate вернул valid:true. Не создавай и не пересобирай заново fingerprint, prediction, assessment или evidence, не опускай поля при переносе, не сокращай payload. Меняются только состав групп и envelope вызова (runId/актуальный epoch); содержимое item должно оставаться побайтно эквивалентным проверенной submit-проекции (в preflight metadata мог быть отдельно, в submit его нет). Если исходный item потерян, изменён или точную эквивалентность гарантировать нельзя, СНАЧАЛА вызови prediction_batch_validate для фактически отправляемого содержимого; при valid:true отправь без изменений, при invalid примени обычное ограниченное исправление по Worker issues и одну повторную предпроверку, затем действуй по общему fail-closed правилу. Это не новый локальный валидатор и не ручная сверка enum. Не вызывай prediction_complete с reason manifest_spent, пока есть deferred_budget или непереданные слоты манифеста.
 - blocked (gate_lost, lease_lost, storage_error), not_in_manifest, conflict: не повторяй вслепую; для conflict и not_in_manifest выбрось фильм из run и продолжай, для blocked смотри остановки ниже.
 - Ответ с replayed:true значит, что фильм уже обработан этим run; ничего не меняй.
 Потерянный ответ, таймаут или 502 {recoverable:true}: отправь ТОТ ЖЕ самый body ещё раз (те же items, тот же epoch), не регенерируй; готовые фильмы вернутся как replayed. 409 submit_in_flight: подожди retryAfterMs и повтори тот же body. 409 epoch_mismatch: возьми актуальный epoch из последнего heartbeat/ответа и повтори; не угадывай его.

Если manifest НЕ получен (already_running/noop/blocked и подобные случаи), выведи ТОЛЬКО «## Итог»: коротко фактический статус, причину, «0 обработано, 0 создано. Исследование не выполнялось»; без других заголовков/фиктивных записей. При прерывании ПОСЛЕ manifest сохрани все пять секций, показывай только подтверждённый прогресс и stage/ошибку; неизвестное не заменяй нулём. Не копируй raw manifest, Taste Profile, payloadы, fingerprints и полные статьи. Audit и fullTextFallback — только Saved Task report, НЕ Worker schema или assessment. При штатном результате push не требуется. К discovery не обращайся.

ПОРЯДОК ОДНОГО ПРОХОДА (один GROUP_SIZE, чистый контекст)
1. Не читай ничего через MCP, кроме вызовов шага 7. Проверь FROZEN_MANIFEST: это объект с dryRun true, runId null, manifestHash (64 hex), profile.body, contract.schema и непустым films[] (у каждого filmId, plan, modelMetadata, inputHash; у prediction_only ещё fingerprint). Выбирай оригинальную авторскую критику по языку, стране и эпохе фильма: для советского/российского кино русскоязычные рецензии и Кинопоиск, для англоязычного Guardian, Letterboxd, Slant и другие доступные авторские тексты; это примеры, не whitelist, перепечатки не независимы; (г) оцени исполнение и прогнозируй по manifest.profile.body, не копируя чужую оценку или фактическую личную оценку фильма; затем шаги 4–6. Выбирай research.status по действительно использованным источникам: если в sources есть хотя бы один реальный web_research (даже только search_snippet), ставь attempted_found, но snippets сами по себе НЕ дают substantive quality gate; если web_research нет и запросов не было, research.status=not_attempted; если все попытки поиска и чтения были заблокированы или недоступны, attempted_blocked; если доступный материал был прочитан, но не дал пригодных фактов, attempted_no_findings. При остальных трёх статусах web_research в sources ЗАПРЕЩЁН; не выдумывай источники. Результат шага это отдельный объект assessment рядом с prediction (НЕ внутри него), до 3000 байт UTF-8 JSON, ТОЛЬКО эти ключи: assessmentVersion=1; ratingBasis (1–700 симв., основание predictedRating: premise, execution, decision logic, payoff); probability4PlusBasis (1–400, основание вероятности; саму вероятность не повторяй); tasteSignals до 5 {direction: supports|against|neutral, signal 1–220, anchor? 1–120}; risks до 3 {risk 1–220, severity low|medium|high}; uncertainties до 3 строк 1–220 (честное «неизвестно», не «low»); research {status: not_attempted|attempted_blocked|attempted_no_findings|attempted_found, attempts? до 4 {outcome: blocked|unreadable|irrelevant, ref? https-URL, note? 1–100}}; sources до 6 {kind: metadata|model_knowledge|web_research, ref (metadata:synopsis|genres|runtime|credits, model_knowledge или реальный https-URL), usedFor 1–120, access: full_text|partial_text|search_snippet ТОЛЬКО для web_research}; conflicts до 2 {topic 1–120, positions 2–3 {source: индекс в sources, author? 1–80, stance 1–160}, handling: kept_unresolved|weighted|not_relied_on}; model {status:'reported', id 1–80, version? 1–40, effort? 1–20} или {status:'unavailable'}. attempted_found требует хотя бы один источник web_research, остальные статусы его запрещают; страница, которую не удалось открыть или прочитать, записывается в research.attempts, а НЕ в sources; результат поиска без открытой страницы это search_snippet и не «прочитано»; противоречие между реально прочитанными авторами записывай в conflicts, не усредняй. НИКОГДА не выдумывай источник, доступ или URL; assessment не влияет на prediction и не заменяет evidence fingerprint.

4. Для plan=fingerprint_and_prediction создай конкретный film fingerprint по metadata из manifest.films[].modelMetadata и фактическим знаниям; неизвестное = unknown. Для plan=prediction_only используй fingerprint, уже присутствующий в манифесте: НЕ создавай и НЕ отправляй новый fingerprint и evidence. Используй профиль из manifest.profile.body (его версию и хэш менять нельзя), не подменяй прежним; никогда не используй фактическую личную оценку фильма как ответ. predictedRating по полу-шагам .5–5, probability4Plus 0–1, confidence, до 3 конкретных matchSignals, mainRisk и 2–4 кратких русских moodLabels. Не завышай из-за жанра, актёра или франшизы.
5. ОБЯЗАТЕЛЬНАЯ КАРТА fingerprint.evidence для нового fingerprint по правилам manifest.contract.schema.contract.fingerprint.evidence: ТОЛЬКО plotMechanics и execution; на КАЖДЫЙ заявленный id в fingerprint.plotMechanics 1–4 обоснованных items в evidence.plotMechanics[id]; для КАЖДОГО general execution dimension с конкретным значением (не unknown/not_applicable) 1–4 items. General dimensions: plot_engine, pace, stakes, decision_logic, protagonist_competence, opposition_competence, problem_solving, plan_counterplan_strength, multi_party_goals, chemistry, payoff, ending_quality, technical_plausibility. Необоснованное качество исполнения = unknown и БЕЗ evidence key; not_applicable тоже без items. Unknown — пробел свидетельств, а не low. Жанровые dimensions опциональны; конкретный genre dimension с items следует тем же правилам и не может быть только metadata. Каждый item содержит РОВНО {basis,refs,confidence}; basis = metadata, model_knowledge или web_research; confidence = low/medium/high; refs = 1–4 уникальных строк; без дублей и extra keys. metadata подтверждает механику лишь по факту, реально присутствующему в modelMetadata этого фильма (metadata:synopsis, metadata:genres, metadata:runtime, metadata:credits), и НЕ доказывает качество исполнения: все items одной execution-quality претензии не могут быть только metadata. model_knowledge имеет только ref "model_knowledge". web_research допустим только с реально использованными HTTPS-адресами; без фактического внешнего исследования не используй его, никогда не придумывай URL. Не используй assessPredictionConfidence и не вставляй confidenceAssessment. Если честную карту составить нельзя, не фабрикуй evidence: отправь для этого фильма failure (шаг 7), а не невалидный fingerprint. НИКОГДА не меняй версии или FINGERPRINT_TRANSITIONS.
