# ADR 0194: The batch_v2 auxiliary state (held stage, run sources, persisted manifest, event outbox) moves to D1 as one fenced cohort, built dormant behind its own authority marker

## Context

Confirmed from `main` at `bfbc373` (21 Nov 2026), by reading `src/enrichment.js` and `src/prediction-d1.js`:

- The prediction profile, queue, runs, `latest-run` and the runner and writer leases are D1-owned (`prediction_*` tables, marker `prediction_domain_authority`, every write one fenced batch). Six families of the same batch_v2 flow are still R2 objects written by unconditional `saveJSON` or by an ETag compare-and-swap (`mergeStoredJSON`), and none of them is claimed by `PredictionD1.saveMutable` (`predictionMutableKey` knows only queue, profile, leases, run, latest, fingerprint and predictions):
  - `enrichment/batch-stage.json`: the transferable held results of earlier runs (read by the start, the drain, hold, submit and resume paths; changed by a merge-with-retry).
  - `enrichment/sources/<runId>.json`: the model input of each manifest film (`modelMetadata`), written at the start and rewritten by the hold and resume paths; read to rebuild a stop Event and to validate a submit.
  - `enrichment/batch-manifest/<runId>.json`: the exact start answer, written once at the end of `batchPersistRun`, served in parts to the live holder; for a deferred start it is the readiness boundary (ADR 0193 decision 7: not served before the owner-fenced `startReady` edit).
  - `enrichment/start-events/*`, `enrichment/stop-events/*` (including `skipped-<requestId>.json`) and `enrichment/event-outbox.json`: the delivery records of the Events journal and the index of failed deliveries.
- The AIR-546 ledger found that the manifest PUT is **not** create-only and not byte-checked, that the stage and the outbox index are split from the D1 lease that fences them, and that the outbox is mutable delivery state, not an immutable Event. Disposition accepted by the owner: migrate these to D1; large immutable content may stay in R2 behind a D1-owned reference.
- Bounds in the code today: manifest at most 100 films and 256 KiB (`BATCH_RUNNER.maxManifestBytes`; the 21 Nov `:30` manifest was 39,372 bytes, [evidence](../evidence/prediction/air-573-deferred-start-offline-2026-11-21.md)); stage and one submit at most 10 items and 56 KiB; outbox drain 20 entries per authorized start, 3 journal attempts, quarantine after 8; one D1 statement is held to 100 KiB and 100 binds by `assertStatements`; the queue document already uses 40,000-character chunks. **Not measured yet:** the byte size of a `sources` object for 100 films and of a stage with 10 held items; the acceptance criteria require a synthetic measurement (Evidence).
- `batch-start/<runId>.json` (terminal outcome) and `batch-start/attempt/<runId>.json` (the "instance exists" marker) are written only through `writeCreateOnly` (`onlyIf: etagDoesNotMatch '*'`); a replayed instance never overwrites either.
- The run diagnostics projection (`run-diagnostics/*`, `run-diagnostics-settle.json`), the Events journal (`events/items/*`), immutable prediction, fingerprint and profile version bodies are classified **retain** in AIR-546 and are out of scope.

Constraint carried from [AGENTS.md](../../AGENTS.md): the production default stays the current R2 path until a separate owner-approved activation (AIR-554); deploying code must need no new schema, create no second writer and enable no D1 live path.

## Decision (proposed)

1. **One cohort, one new authority marker.** A new migration (number taken from the chain at implementation time; `0034` if nothing else claims it first) adds `prediction_aux_authority` (one row, `mode` `r2`/`d1`, generation, inserted as `r2`) and its fence table, in the pattern of `0028`/`0029`. The marker is **its own**, not a column of `prediction_domain_authority`, so the dormant schema can be applied and rolled forward without touching the live prediction domain. While the marker is `r2` (default, and also when the tables are absent) the Worker runs today's R2 code unchanged. When it is `d1`, stage, sources, manifest and outbox are served **only** from D1: a missing binding, missing tables or an unanswering database is `prediction_aux_unavailable` (the existing `storage_error` mapping), never a read of the R2 object (ADR 0162). One cohort means the four families flip together by one marker value; there is no per-family switch and no dual writer.
2. **Every aux write is one D1 batch fenced three ways:** the aux marker (`d1`, generation read), and, for run-owned writes, the same runner-lease guard (`COMMIT_GUARD`: runId, epoch, unexpired, protocol) that `batch_submit` commits already carry. A stale epoch, a takeover or a marker move fails the batch closed; no write is blind.
3. **Held stage (`prediction_batch_stage`).** Transferable, not run-scoped: one row per held film, `film_id` primary key, with `origin` provenance, `batch_item_digest`, `film_input_hash`, `held_by_run_id`, `held_at` and the item body (single statement, at most the 56 KiB item cap; the document cap of 10 items is enforced by a count check inside the same batch). Duplicate is a no-op on an identical digest and `hold_conflict` on a different one, exactly as today; stale and profile drift drops use a conditional delete; the drain under a new run's lease deletes a row only with `held_by_run_id`/digest match in the commit of the same film. No model work is repeated: the drain commits the stored item through the existing submit path.
4. **Sources (`prediction_run_source`).** One row per `(run_id, revision)` with `source_hash` and the body in chunks of at most 40,000 characters (the queue's chunk size); revision starts at 1 and every rewrite is `UPDATE … WHERE run_id=? AND revision=?` (explicit CAS). The original model input is preserved: a rewrite may only add film entries or equal ones; a changed entry for an existing film is `source_conflict`. The run document carries `sourceHash` so a reader verifies hash binding.
5. **Manifest (`prediction_run_manifest`).** Create-only: `run_id` primary key, `manifest_hash`, `selected_ids` (JSON, ≤100), `drained` metadata, chunked body, `bytes`, `part_digests`. A second write for the run id with equal bytes is a no-op; with different bytes it is `manifest_conflict` (never an overwrite). Bounded part readback (envelope, profile, contract, one film, hold list) reads the row and verifies `manifest_hash` before serving; a missing or mismatching row is `manifest_unavailable` (fail closed, as ADR 0193 decision 6). For a deferred start the manifest rows and the `startReady` edit are **one** batch, so "ready" can never be declared before a durable, readable manifest (ADR 0193 decision 7 keeps its order, now atomic). A stale Workflow instance fails the lease guard and can neither publish the manifest nor release another lease.
6. **Event outbox (`prediction_event_outbox`).** One row per delivery record, key `kind:identity` (`stop:<runId>`, `start:<runId>`, `skipped:<requestId>`), holding the event JSON, the deterministic event id, the original `at` (which fixes the journal key), `state` (`pending`, `delivered`, `superseded`, `quarantined`), `attempts`, `since`, `last_attempt_at`. It replaces the three R2 shapes (record, index entry, parked skipped record) with one row, so the "index entry before parked record" ordering of ADR 0180 disappears. Delivery is unchanged in meaning: the Events journal stays R2 (`events/items/*`, keyed by event id and `at`, idempotent rewrite), `delivered` is set only after the journal write is proven (write returned, or a `head` of the journal key), an unknown outcome keeps the row `pending`, replay is safe, and `superseded` is set by a recovering run exactly as the R2 flag is today. Drain keeps its contract: the latest run's rows first, then `WHERE state='pending'` oldest-first by an index on `(state, since, event_key)`, at most 20 per authorized start, 3 journal attempts per delivery, quarantine at 8 attempts, quarantined rows are counted and shown in status but never take a slot, no history listing, GET/status/manifest stay pure reads.
7. **Skipped events from a request without the lease.** A request that the runner lease turns away (`already_running`) or that the catalog gate refuses (`catalog_held`, ADR 0190) does **not** own the lease and must not touch it. Its registration is one statement `INSERT … ON CONFLICT(event_key) DO NOTHING`, guarded only by the aux marker generation (the `prediction_domain_cas`-style check), with a bounded backlog: a trigger refuses a new `skipped:` row while 64 undelivered skipped rows exist (best effort by design; the refusal is logged and counted, never changes the refusal response, as ADR 0180). It changes no lease, run, queue or film. Same request id replayed is a no-op that returns the first row's `at` (same journal key); a distinct request id is a distinct row; a concurrent pair resolves in the database, not by an R2 read-then-put race. A journal or D1 failure never changes the original `already_running`/`catalog_held` answer.
8. **Terminal and run-bound events keep their contracts.** batch_v2 still produces exactly one terminal Event per run (ADR 0146), the stop row is created inside the same fenced batch that finalizes the run (or reconstructed by the existing drain step as an insert-or-ignore), a recovered run supersedes its predecessor's pending row, and no new start Event is created (v2 writes none; legacy `start:` rows are import-only).
9. **Deferred-start receipts stay in R2.** `batch-start/<runId>.json` and `batch-start/attempt/<runId>.json` are one-shot, create-only, never overwritten, and answer only "was this key refused/failed, does its instance exist". They are immutable receipts, not mutable coordination state, so they stay R2 per the accepted disposition. The authority that decides *readiness* (lease preparation mark, gate, manifest) is entirely D1 after this ADR; the receipt cannot make a run ready or unready. Workflow instance state is not migrated. (Decision requested, point 3 below.)
10. **Dormant means observable only.** The deployed code carries the D1 adapters and the Worker/Workflow branches behind the marker; with marker `r2` or no tables they are unreachable. A bounded offline importer and dry-run (reads R2 families, builds the rows and a digest/count report, writes nothing unless run with an explicit owner-only apply; the apply is **not** performed by AIR-553) feeds the cutover plan of AIR-554: quiesce (no live run lease, no deferred instance preparing, outbox drained or preserved), import with per-family counts and digests, verify, flip the marker, retire the R2 writers in a later change. Rollback of code is not rollback of state: after the flip the R2 objects are a frozen pre-flip copy, not a fallback (ADR 0162).

## Alternatives considered

- **A. All four families inline in D1 (recommended).** Stage, sources, manifest and outbox rows as above. For: one store, so the lease/epoch fence, the marker and the readiness edit commit **atomically**; no unknown-PUT outcome, no orphan, no pointer/body disagreement; the crash matrix collapses to "the batch happened or it did not". The data is operational recovery state with a short life (a manifest is served only to the live holder; sources are read until the stop Event is delivered), so it can be pruned by the same writer. Against: D1 row growth (a manifest is about 40 KB typical and at most 256 KiB, four Tasks per hour; bounded by retention, see Consequences); a 256 KiB body needs up to 7 chunk rows per write (each statement stays under the 100 KiB budget); D1 write rows scale with chunks, not bytes.
- **B. D1 pointer plus immutable content-addressed R2 body for sources and manifest, D1 payload for stage and outbox.** For: no D1 growth for the large bodies; matches "large immutable content may stay in R2". Against: reintroduces the cross-store window the task has to test for (payload then pointer, unknown PUT outcome, orphan blobs needing a sweep, a body that is unreadable while the pointer is committed), and the readiness boundary stops being atomic (R2 PUT, then one D1 batch). `sources` is rewritten by hold/resume, so it is not immutable and would need a new blob per revision. It also keeps R2 on the critical path of the 180 s deferred-start preparation. Reasonable if measurement shows the bodies are much larger than estimated.
- **C. Leave the manifest and sources in R2 and make the PUT create-only with a digest check; move only stage and outbox.** For: smallest change. Against: contradicts the accepted AIR-546 disposition (`migrate`) and leaves a split authority for the run (D1 run hash, R2 manifest); rejected as it does not satisfy AIR-275 without a new owner exception.
- **D. Put the aux tables inside the existing `prediction_domain_authority` marker.** For: one marker. Against: the dormant schema could not be applied before activation without touching the live prediction fence and its triggers, and a separate cutover (AIR-554) needs its own revert-free readback; rejected.
- **E. Per-family markers.** Rejected by the card: the four families share the lease fence and the event identity; splitting them recreates split authority.

## Consequences

- No behaviour change for the Tasks, the API/MCP contract, sizes, scores, retry counters, queue settlement, Events/status UX or the scheduler. The model, prompt, batch sizes, heartbeat and TTL are untouched.
- New tables are bounded: stage ≤ 10 rows, outbox bounded by drain/quarantine plus retention of delivered rows (proposed: delete delivered/superseded rows older than 14 days inside the drain, at most 20 per pass), run sources/manifest rows pruned when the run's terminal Event is delivered or superseded and the run is older than the newest 48 (proposed; values for the owner to confirm). Pruning never touches a live run.
- A start's D1 work grows by the stage, manifest and source batches that were R2 puts (offline budget to be measured and asserted in a test, no unbounded scan, every statement under the 100 KiB budget).
- Deploying the dormant code requires no schema, creates no second writer and no new binding. Applying the migration is a separate owner GO (like 0024 → AIR-478) and the cutover is AIR-554.
- Reads that need the aux state (manifest part readback, status, skipped events view) remain pure reads and are added to the [read side-effect baseline](../reference/api/read-side-effects.md) check.

## Recovery and migration boundary

Reversible: the whole change until the migration is applied and the marker is flipped (code revert). Irreversible without a new owner-approved operation: the marker flip and the retirement of the R2 writers. This ADR authorizes no migration apply, import, flag, binding, Task change, manual batch, lease reset, workflow run or deletion. In-flight state at cutover (a live runner lease, a deferred Workflow instance in `preparing`, pending outbox rows, a held stage) is a precondition list of the AIR-554 plan, not handled here. A marker restored to `r2` after the flip is refused, not read as the old objects.

## Decisions requested

1. **Storage shape:** A (recommended) or B (R2 body behind a D1 pointer for sources and manifest).
2. **Retention values** for delivered outbox rows (14 days) and run sources/manifests (newest 48 runs after the terminal Event is settled).
3. **Deferred-start receipts:** confirm they stay in R2 as immutable create-only receipts (recommended), or migrate them too.
4. **Skipped-event backlog cap** of 64 undelivered `skipped:` rows (best effort, never changes the refusal answer).
