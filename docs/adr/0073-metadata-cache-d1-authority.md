# ADR 0073: The metadata cache is owned by D1 only after its own marker is switched

**Status:** Proposed  
**Original decision date:** 2026-11-01  
**Recorded at:** 2026-11-01  
**Approval source:** Owner approval to continue the metadata-cache move as a real reader and writer, recorded on [AIR-313](https://trello.com/c/jjjp0FhK). Acceptance of this record is architectural. Applying migration `0006`, importing rows, and switching the marker are separate approvals.  
**Related work:** [AIR-313](https://trello.com/c/jjjp0FhK), [ADR 0072](0072-owner-reviewed-localization-overlay.md), [ADR 0070](0070-metadatasync-freshness-clocks.md), [ADR 0056](0056-d1-enrichment-write-through.md), [ADR 0051](0051-d1-domain-r2-blobs.md)
**Supersedes:** [ADR 0070](0070-metadatasync-freshness-clocks.md) decision 6 in part, and only once this record is accepted and `metadata_cache_authority.mode` is `d1`: `beginSync` and `metadataSync` may use D1 as the working set. The four clocks and `film_sync_state` stay. [ADR 0056](0056-d1-enrichment-write-through.md) decision 1 in part, for metadata records only, in that same mode: the projector reads those records from D1 and still does not write R2. [ADR 0051](0051-d1-domain-r2-blobs.md) names this kind of per-domain flip; this record is that flip for the metadata cache alone. The rest of each record stands.  
**Superseded by:** None

## Context

`beginSync` decides which watchlist films to fetch by merging each film with the `metadata.json` record stored under that film's Letterboxd id. A film is pending when `metadataAt` is missing, `peopleVersion` is not 1, `peopleNamesVersion` is not 2, `synopsisFetchedAt` is missing, or `metadataAt` is older than 30 days. `metadataSync` then updates that same object and writes it back whole. It does not delete a key when a film leaves the watchlist. The merge keeps the cache record's `aliases`.

[ADR 0070](0070-metadatasync-freshness-clocks.md) stores four clocks on `film_sync_state` for a Film row that already exists. That table cannot be the working set. A cache key with no Film row has nowhere to go, and the columns do not hold the synopsis, names, aliases, credits or the rest of the record `metadataSync` writes. A production read on 2026-10-31 found 421 keys in `metadata.json`, 396 of them matching a Film row and 25 matching none. Those counts are a sample from that read, not a contract.

Owner-confirmed titles and names live in `admin/owner-reviews.json` ([ADR 0072](0072-owner-reviewed-localization-overlay.md)). Projected reviewed values also live on `film_dimension` and `person_dimension`. D1-only TMDB credits live on `film_person_credit`. None of those is a field of `metadata.json`. `tmdb` and `tmdb_tv` are different identities and both can appear on a cache record.

Production schema is v5. `D1_ENRICHMENT_WRITE=on`. The cron is `37 * * * *`. A code deploy must not start a new writer, and it must not add a Worker flag. There is no transaction that covers D1 and R2 together.

## Decision

1. **The whole cache record, keyed as `metadata.json` keys it.** Migration `0006_metadata_cache.sql` adds `metadata_cache`. `cache_key` is the original key. There is no foreign key to `film` and no new Film is minted for a key that has none. `payload_json` is the whole record, so a missing field and a null field stay different, and `tmdb` and `tmdb_tv` both survive. Typed columns repeat `metadata_at`, `synopsis_fetched_at`, `people_names_version`, `people_localized_at` and `people_version` for the sync decision. A non-integer `peopleNamesVersion` is stored as NULL in the column and unchanged in the payload. The 30-day window is not a column. It stays `METADATA_FRESH_MS`.
2. **One marker, default `r2`.** `metadata_cache_authority` is a single row. `mode` is `r2` or `d1`. The migration inserts `r2`. `metadata_cache_cas` is the fence that makes a batch fail when the compare-and-swap matches nothing. It is not a switch and not a Worker flag. Applying `0006` does not by itself move `beginSync`, `metadataSync` or the projector off `metadata.json`, and it does not insert cache rows. Schema v4 and v5 do not query these tables. A missing D1 binding is not version 6.
3. **The working set follows the marker.** `beginSync` and `metadataSync` call one repository. On a contract that is not version 6, including a missing D1 binding, they read and write `metadata.json` with the same unconditional put. On version 6 while `mode` is `r2`, a save first advances `cache_generation` only when `mode` is still `r2` and the generation is the one just read, and only then puts the object. If that compare-and-swap matches nothing, the put does not run. If `mode` is already `d1`, the save fails and does not put. A version 6 database whose cache tables are missing, or whose marker row is missing or has a mode other than `r2` or `d1`, fails the step and does not read `metadata.json`. In `d1` they read every `metadata_cache` row and do not consult `metadata.json` to decide. An empty table is an empty cache. A failed read or a payload that is not JSON fails the step. The pending predicate and the watchlist merge are the same functions in both modes.
4. **Writes are one fenced D1 batch, then a mirror.** The batch advances `cache_generation` only when `mode` is `d1` and the generation is the one the step read. The same batch upserts every key of the in-memory map. Each statement stays within D1's limit of 100 bound parameters. A complete map then deletes rows whose `generation` is not that commit, which removes keys the map no longer contains, including when the map is empty. That delete binds one parameter. A map that was not a complete read does not delete. `metadataSync` still saves the whole map, so a film leaving the watchlist does not by itself delete a key. If the fence matches nothing, the batch rolls back and R2 is not written. The mirror put of `metadata.json` runs after the batch and only while this commit is still the cache generation. Before it replaces a different object, it reads the marker again. A newer generation that already owns the marker is not overwritten, whether the publisher is the commit itself or a later read repairing a lagging mirror. On success, `mirror_generation` and `mirror_etag` advance only while `cache_generation` is still that commit. A crash between the two leaves the mirror behind. The next `d1` read repairs the mirror from D1 under the same rule. That read returns records and a cache generation observed together. If the repair finds a newer generation, it reads that generation's records again and does not hand the older records the newer generation as a compare-and-swap token. The projector never writes the cache and never writes R2.
5. **The projector must not copy a stale mirror back.** When `mode` is `d1`, the projector builds its view from `metadata_cache` instead of from the `metadata.json` it read for the cut. A failed cache read stops the run before any write. Version 6 without the cache tables, or without a valid marker row, fails the same way and does not project from that object. When `mode` is `r2` on a complete version 6 database, or the contract is not version 6, the projector's inputs are unchanged, including `film_sync_state` from R2. Version 6 still writes those clocks when `film_sync_state` exists and the cache marker can be read. The cron stays `37 * * * *`. No new cron and no Scheduled Task.
6. **Activation is explicit and checked.** `scripts/metadata-cache-authority.mjs` prints status unless asked to write. `--load` with `--confirm load` copies a local `metadata.json` into the table behind an etag fence, proves every key round-trips, and leaves `mode` at `r2`. `--activate` with `--confirm activate` sets `d1` only when the generations match, the etag still matches, and every payload matches the file. An `r2` save that has already claimed a newer generation makes that check fail, so the in-flight put is the one that lands and the mode stays `r2`. `--revert` with `--confirm r2` and `--metadata` sets `r2` again only when that file matches the latest cache generation. If the mirror lags, the command publishes that generation once. If the publication fails, or the file still does not match the rows and the stored etag, the mode stays `d1`. A successful revert does not delete rows. The script refuses a database path that names production and does not call the network. Running it against production is not authorized by this record.

Not decided here: applying `0006` to production, importing the live object, setting the marker to `d1`, reverting it, and any change to `finishSync`, discovery, ratings, EPG programme or generation objects, or predictions.

## Alternatives considered

- **Keep using `film_sync_state` as the working set.** Rejected. The foreign key drops the keys that have no Film, and the four columns drop the rest of the record.
- **A new Worker flag.** Rejected. The owner asked for one durable marker. A flag would be a second switch with its own lifecycle.
- **Fall back to `metadata.json` when D1 is unavailable in `d1` mode.** Rejected. The mirror can be the stale copy the failure just created. The step fails instead.
- **Make the projector keep reading R2 in `d1` mode.** Rejected. It would write the stale mirror back onto `film_sync_state` and `film_metadata`.

## Consequences

- Until `0006` is applied, production behavior is the schema v5 projector and R2-backed `metadataSync`. After it is applied, and while the marker stays `r2`, `beginSync` and `metadataSync` still decide from `metadata.json`. A save on that database advances `cache_generation` before the put and does not write `metadata_cache` rows. `/api/d1/status` reports `schemaVersion` 6 with `cacheMode` `r2` once the new tables are present. Version 5's success object does not gain those fields. The status query reports version 6 without the new tables as `schema: false`. A projection run on version 6 without the cache tables, or without a valid marker row, fails before a write. Version 5 without those tables keeps the R2 path, and Film and Person writes continue there.
- A cache commit does not write `film`, `film_person_credit`, `film_dimension`, `person_dimension` or `admin/owner-reviews.json`. The owner-review overlay, projected reviewed localization and D1-only credits are untouched by that commit.
- Pages that still read `metadata.json`, including the poster fallback and the started-mark lookup, read the mirror. In `d1` mode that mirror follows D1 and can lag by one failed put.
- The backfill executor still requires schema version 4. A database at version 5 or 6 stops before a reload write.
- `beginSync` and `metadataSync` read `schema_contract` before using `metadata.json`. If that read fails, they do not guess the marker. On schema v5 the read returns version 5 and the R2 path continues. A missing binding is not version 6 and keeps the unconditional put. Version 6 with a missing cache table or a missing or invalid marker fails the step and does not read the object.

## Recovery and migration boundary

Code rollback does not drop the tables, does not return the contract version, and does not change the marker. A Worker that only reads `metadata.json`, running while the marker is `d1`, would decide from a mirror that may lag. Returning the marker to `r2` is `--revert` with `--confirm r2` and a metadata file that matches the latest generation, or the equivalent fenced update, and is its own approval. A revert whose mirror cannot be verified leaves the mode at `d1`. Unsetting `D1_ENRICHMENT_WRITE` stops the projector, not `metadataSync`. Restoring the database is a Time Travel of the whole database and is its own approval. This record does not authorize applying `0006`, importing, activating, reverting, a flag change, a cron change, or any production R2 or D1 write.
