The RCA window of 22 Nov held 422 in three hours and 120 in seven minutes. The amplification is a **burst** phenomenon, not a steady rate.

## What it does not explain

The offline census ([the committed one](air-579-catalog-read-attribution-2026-11-22.md), and an uncommitted probe of the same real Worker over a D1 stand-in at the real schema, extended with a ledger, 800 decisions, a published D1 EPG generation and admissions of 30 and 3,000 films) gives **one whole-catalog read per call** for `enrichment/view`, `catalog/available`, `footer/status` and `pipeline/status`, none for `programme`, `events`, `started`, the status routes and the fast cron tick, and none for the Predictions tools after a submit (the queue is rewritten from stored data). The counts do not change with the catalog size. Production shows **about 39 reads for one page load (three catalog-reading routes) and 21 for a lone cron tick**. The offline model therefore **does not reproduce production** and the cause of the difference is **unattributed**: a state the stand-in lacks (a real ledger and queue size, the live authority state, a retry or a loop that the small world short-circuits), not a route count. No hypothesis is claimed.

## The change this justifies: one log line per whole-catalog read

Analytics names the statement but not the caller, and a request is not a statement. Workers Logs attach a log line to the invocation that wrote it, so a line written **inside `readCatalog`** is attributed to its route, cron tick, MCP call or Workflow step by `$metadata.trigger`, with no payload and no per-request counter (the same mechanism as `mcp_tool_call`). `readCatalog` now writes `{"event":"discovery_catalog_read","rows":<n>,"ms":<n>,"projected":<bool>}`, one per whole-catalog read and nothing for the bounded reads by id. It never carries a film id, a title, a payload or a key, never throws into the read and changes no result (`tests/discovery-catalog-read-log.mjs`: exact keys, a canary in the data never logged, projected flag, bounded reads silent, a failing read writes none, a throwing console changes nothing). The aggregate recipe is in [the monitoring runbook](../../runbooks/monitoring.md).
