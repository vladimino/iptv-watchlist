# EPG diagnostic canary: owner-only Workflow, receipts and reporting, offline evidence (AIR-455, 12 November 2026)

Scope: [ADR 0121](../../adr/0121-epg-diagnostic-rehearsal-design.md) and [ADR 0123](../../adr/0123-epg-diagnostic-canary-run-contract.md), offline code only. No Cloudflare resource, no live Workflow instance, no production read or write. All results come from `tests/epg-diagnostic-run.mjs` (about 8 s): sqlite stand-ins of the diagnostic and the production-like D1, in-memory buckets and a scripted Workflow binding; the real `stageSealedGeneration` and what it calls, the real step lease and the real replay module run.

| Claim | Result |
|---|---|
| Inert | Without the diagnostic bindings (and without a resource id) every route answers `503 diagnostic_bindings_absent`, no instance is created and neither the production-like nor the diagnostic resources change (byte-for-byte fingerprints); a cross-origin POST is refused by the existing origin rule |
| Reads never write | `preflight`, `status` and `result` leave the diagnostic database and bucket byte for byte unchanged; the guard's write counter is 0 |
| Launch gates | 12 invalid configurations and a missing or wrong confirmation reserve nothing; the owner is verified in the Worker on every route with real signed assertions (no assertion, garbage, another key, the MCP audience, another e-mail, no e-mail, a service token, expired, wrong issuer: `403` on all six routes with nothing read or written; unconfigured audience, e-mail or team domain: `503`; unreachable keys: `503`); a missing or tampered dataset, an underivable plan, a live production step lease, an open mode switch, a running control phase, a seal or fresh sync in `sync.json` each refuse before any reservation |
| Idempotency and slot | The same key and parameters resolve to the same run and create nothing; other parameters are `idempotency_conflict`; a second key while one is active is `canary_active`; the instance id is deterministic and the Workflow gets the key only |
| Unknown outcomes | A create that throws with an unreachable status leaves the receipt `reserved` (`202`); a repeat with the status still unknown creates nothing; once the instance is seen it is attached and recorded without a second create; `already exists` is attached to |
| The run | `begin`, `seal`, `finish` (no step throws); the real seal archived exactly the planned departures into exactly the planned segments; the report is `canary-measured`, with measured `published:false` and `productionWrites:0` and an `outcome` (`ok`, `violations`), with plan, seal-stage phase markers (fences, skipped fences, fenceMs, readMs, putMs), per-resource reads and writes, lease renewals, CPU and memory as null with the reason, and the invariants (no denied access, no refused write, identity verified); no ledger payload in the report |
| Faults | A lost lease, an expired lease (`step_lease_expired`), a pointer conflict (the other writer's pointer stays), a domain not prepared, a dirty domain and a consumed baseline each end in a `failed` receipt with a typed reason and a free slot; a deadline already past stops the real step guard before the next write (`budget_exceeded`); a run measured over its budget, or with any violated postcondition, is `failed` with `postcondition_failed:…` and its full report; production busy at `begin` or at the start of `seal` fails the run before any baseline write |
| Stop and cleanup | `stop` marks the receipt `stopping`, releases the lease and terminates the instance, answers `202` and keeps the slot (no launch, no cleanup) until the instance ended and the lease was quiet for 60 s, then `stopped`; a woken instance ends at `begin` and materializes nothing; `cleanup` is refused while active and, when allowed, removes only the baseline and keeps identity, datasets and receipts; a new run is possible after it |
| Isolation | The production-like database and bucket of the same process are byte for byte what they were after a whole run, a stop and a cleanup |
| Mutation checks | 26 mutants of the run module (confirmation, owner verification, owner e-mail, production gate at launch, at `begin` and at `seal`, deadline enforcement, `complete` ignoring the outcome, stop without quiescence, Workflow binding, dataset verification, idempotency conflict, active slot, unknown create and unknown status retried, a repeat that creates again, stop without terminate, a stopped receipt that runs on, cleanup while active, the published generation not compared, a dirty domain overwritten, a consumed baseline reused, a report that claims a publication or the wrong label, a status that writes) are each caught by the checks they concern |

Limits (honest): the Workflow engine, Cloudflare D1 and R2 latency, CPU and memory and shared account-level limits are not exercised offline; the diagnostic domain must be prepared by the provisioning procedure (published generation and Discovery markers) which this card does not do; the Mermaid diagram was parsed with Mermaid 11.4.1, its GitHub rendering needs the independent reviewer's visual check; isolation is application-enforced, not platform-enforced. This is offline mechanics evidence, not `canary-measured` and not AIR-444 acceptance.
