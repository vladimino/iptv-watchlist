# Production ChatGPT Scheduled Tasks — operational contract

This is the maintained **expected behavior** of the ChatGPT Scheduled Tasks for IPTV Watchlist. Since the Cloudflare EPG cutover ([AIR-348](https://trello.com/c/PUrlzMuH), accepted 8 November 2026), the Discovery Workflow ([AIR-324](https://trello.com/c/kNtaEbm8), accepted 7 November 2026) and the Ratings Workflow ([AIR-347](https://trello.com/c/j2Ua76yv)), **only the personal Predictions depend on a ChatGPT Scheduled Task**: the [hourly Predictions Task](#hourly-predictions). The [read-only drift monitor](#read-only-drift-monitor) in the same registry is not a producer. The legacy [Daily EPG Task](#daily-programme-update-retired-task) and the legacy [Ratings Task](#ratings-task) are retired and disabled. Registry baseline read on 10 November 2026 ([AIR-406](https://trello.com/c/PPe2fFcu)): 16 Tasks, 2 enabled (the hourly Predictions Task and the drift monitor) and 14 disabled. `RATINGS_PIPELINE` is retired ([ADR 0074](../adr/0074-retire-ratings-pipeline-switch.md)): the Worker does not read it. The authoritative status, schedule, timezone and executable prompts for ChatGPT Tasks are in the **live ChatGPT Scheduled Tasks registry**, outside GitHub; the state of the Cloudflare executors is in Worker D1 and its read-only status. GitHub Actions deployment does not run, edit or enable these tasks. An enabled task is not proof of successful execution. For runner and MCP details see [prediction runner](api/prediction-runner.md), [MCP tools](api/mcp.md), [prediction operations](../runbooks/prediction-operations.md) and [scheduling architecture](../architecture/scheduling-and-orchestration.md).

EPG, Discovery and Ratings are Cloudflare-owned. EPG: the Cloudflare EPG Workflow ([ADR 0100](../adr/0100-epg-cloudflare-workflow-executor.md), Accepted; `epg_status` read `mode=cloudflare`, epoch 1 on 8 November 2026). Discovery: the Cloudflare Discovery Workflow (permanent since AIR-325; the `DISCOVERY_EXECUTOR` selector is retired and ignored). Ratings: the Cloudflare Workflow under [ADR 0090](../adr/0090-ratings-cloudflare-workflow-executor.md) and the shared [ADR 0089](../adr/0089-shared-orchestration-reliability-contract.md) contract ([reliability reference](orchestration-reliability.md)). The Worker refuses the write paths of the retired Tasks with `external_writer_fenced`. Changes to any Task or domain mode remain separately gated.

### Legacy contract (rollback only)

The bullets below are the contract of the retired Task as it ran before the cutover. They are kept for a separately approved reverse cutover and for reading the dated evidence; they do not describe the live system.

- **Authority:** connected owner-only IPTV Watchlist MCP to Cloudflare Worker `iptv`, authoritative R2 `iptv`. Never use legacy Sites, direct HTTP, Cloudflare Cron, a browser or local CSV as a production substitute.
- **Preflight:** `probe_read`, `epg_status`, `epg_pipeline_status`; stop safely if unavailable, unauthorized or inconsistent.
- **Execution:** exactly one `epg_sync_start({})` for this invocation, using only its returned `runId`; sequential `epg_sync_step({runId})` through metadata and programme publication; stop on ownership/lease conflicts, terminal errors or unsafe retries. Do not adopt another run.
- **After programme publication:** follow `discovery.nextAction`: `continue` means one further explicit `epg_sync_step` (at most one discovery chunk per call), `wait` means honor `nextCatchUpAt`/backoff, `stop` ends that sequence. Persisted outstanding chunks may be continued by the hourly task. EPG completion does not imply discovery completion. Since [ADR 0030](../adr/0030-discovery-queued-at-publication.md) the discovery series of the published generation is opened before the commit's tail, so a commit interrupted after publication shows outstanding chunks while `epg_status.stage` is still `epg`; a step in that state retries the commit on its resume path (no EPG download, no TMDB). That retry belongs to this daily task, never to the hourly task.
- **Completion:** read `epg_status`, `epg_pipeline_status` and `enrichment_queue`; distinguish published programme, pending discovery and `ratingsPending`. Ratings/Letterboxd HTTP 403 are not reasons to restart EPG. Do **not** run predictions or modify the Taste Profile in this task.
- **Ratings ownership:** the task calls no ratings tool of its own. Production runs ratings through the [Cloudflare executor](#ratings-task-and-the-cloudflare-executor-air-347). Once the storage migration is complete, this task's `epg_sync_step` does not read Diary. An incomplete migration still publishes and records `ratingsPipeline: blocked`; it does not read Diary. A Ratings Workflow failure is not an EPG publication failure when `epg_status.stage` is `complete`.

## Hourly predictions

**Live prompt: Stage B only.** The live `Почасовые прогнозы «В эфире»` prompt has been the Predictions-only text since the owner-approved [AIR-324](https://trello.com/c/kNtaEbm8) edit (11,372 characters; [the proposed text](scheduled-task-prompts/hourly-predictions-only.md)). It forbids `epg_sync_start`, `epg_sync_step` for any reason, discovery resolve, TMDB, the ratings tools and any lease reset. Its first natural run (scheduled 10:20 UTC on 6 November 2026) was recorded `completed` with no failure. Discovery catch-up is no longer a duty of this Task: the Cloudflare Discovery Workflow renews its series itself. This page does not edit a task prompt, an enabled flag or a schedule, and the live registry, not this page, holds the executable prompt.

**Workflow instance budget ([ADR 0094](../adr/0094-discovery-workflow-invocation-budget.md), Accepted).** An instance counts the D1 statements it issues and hands over to a successor at 6,000, besides the 20 chunk limit. A failing step logs one `discovery_workflow_step_failed` line (step, code, bounded cause, statement and batch counts) and the executor record carries `invocation.statements` and `invocation.batches`. The external executor in the legacy section below is not part of the live prompt.

- **Task:** `Почасовые прогнозы «В эфире»`. **Expected:** enabled; **hourly, nominally :20 Europe/Madrid**; `default_timezone: Europe/Madrid`. The scheduler may execute late; nominal time is not an SLA.
- **Stage B — full prediction queue:** read `enrichment_runner`, `enrichment_schema`, `enrichment_profile`, `enrichment_queue`, `enrichment_status`; ensure `prediction_validate` is exposed before a new prediction run. Run `prediction_start({trigger:'scheduled'})` once; for a fresh owned `runId`, call `prediction_next` immediately and process server-sized batches without an invented time or film cap. Respect `already_running`, leases and retry/backoff; a `blocked` start with `code: prediction_retry_heal_pending` selected nothing and is retried by the next scheduled trigger, never by resetting the lease. The same holds for `503 {status: "blocked", code: "prediction_catalog_held"}` on start: an EPG publication holds the catalog, the start kept no lease and selected nothing, and a later trigger tries again. The **expected** Worker contract for the same 503 on `prediction_next`, `prediction_submit` or `prediction_complete` of an owned run is a wait, not a stop: keep the `runId`, do not complete, retry that step for at most one 15-minute lease with heartbeat, then leave the run for ordinary lease expiry. The **live** hourly Task prompt (independent review read-only capture, 10 November 2026) does not name `prediction_catalog_held` and still tells the caller to `prediction_complete` on a systemic error; that prompt is not edited here. Proposed Russian patch is in [AIR-424 evidence](../evidence/prediction/air-424-next-discovery-fence-2026-11-10.md). An identical `prediction_submit` after that 503 is idempotent (`already_current`). Consider **hot, cold and deferred** coverage, not just `pendingCount`.
- **Required validation before every prediction submit:** generate the complete intended `prediction` and, only for `fingerprint_and_prediction`, the complete intended `fingerprint`. Invoke `prediction_validate` on those **exact** objects. Require `success===true`, `valid===true` and `contractVersion===enrichment_schema.contract.version`; the Worker sets `success` and `valid` to the same verdict, so a report with one of them `false` carries at least one issue to correct. For `fingerprint_and_prediction`, both `fingerprint.checked` and `prediction.checked` must be true. For `prediction_only`, `prediction.checked===true` and `fingerprint.checked===false`; reuse the Worker-supplied fingerprint. Revalidate after any change. Validation issues must be corrected and rechecked, with a bounded retry count; do not submit unvalidated payloads. An unavailable validator is a **fail-closed** condition (`prediction_validate_unavailable`), not permission to bypass preflight. The same fail-closed classification applies to a tool error (`isError: true`) and to a report that lacks `success` or `valid`: that is a tool or contract problem, not a schema violation of the generated objects, so it must not be recorded as a per-item `validation_error` and must not defer the film. A contract-permitted per-item validation failure may be submitted as a failure result; never fabricate a successful prediction.
- **Batch sizes in force:** one film per `prediction_next` (`batchSize: 1` is sent by the MCP tool), one per `prediction_submit`, one model generation per film (`modelBatching.enabled: false`), a run selection of at most 12 while capacity is unknown and at most 20. The measured cost of each ([AIR-438 evidence](../evidence/prediction/air-438-step-latency-and-batch-sizing-2026-11-11.md)) is the basis for any later change; none is authorized by this page.
- **Completion and evidence:** use `prediction_submit` only after successful preflight; inspect **each** item result (HTTP 200 alone is insufficient). Process `prediction_next` and `prediction_heartbeat` as required by the lease, then call `prediction_complete` only for an owned run and an allowed stop condition. Re-read `enrichment_status` and `enrichment_queue`; failures or deferred items must not be described as full coverage. Do not mutate profile, flags or other running tasks.

### Batch runner Task (Proposed)

**Accepted design, Task not live.** The Worker's tools `prediction_batch_start` and `prediction_batch_submit` are implemented, and no such Task exists. [ADR 0122](../adr/0122-prediction-batch-runner-v2-dual-protocol.md) (Accepted) describes a future second hourly Predictions Task that would use the [batch runner v2 contract](api/prediction-runner.md#batch-runner-v2-proposed-contract). No such Task exists, this page edits no prompt and a documentation merge never creates, enables or changes a Task.

- **One protocol at a time.** The legacy v5 Task above and any v2 Task never run together: the owner enables the legacy Task or the v2 Task(s), never both. Several independent v2 Tasks may be enabled at once under the AIR-451 plan; they share one lease and queue, and an overlapping `start`/`batch_start` answers `already_running` and stops without adopting the `runId`. Read the registry for which entries are enabled; this page states no live enabled state. There is no feature flag.
- **Shape of one execution (v2).** Read `enrichment_runner` (the `batchRunner` block) → `prediction_batch_start` once with optional `manifestSize` (1..100, default 100; the ready-to-install template uses 5 per [ADR 0136](../adr/0136-prediction-batch-manifest-size-and-spent-complete.md)) → repeat { generate up to `generationSize` films (template 1; range 1–10), `prediction_batch_validate` the group (accepted read-only architecture, [ADR 0131 (Accepted)](../adr/0131-batch-candidate-preflight-tool.md); correct only what real knowledge supports, at most one re-preflight, otherwise a `parse_error` failure item), `prediction_batch_submit` up to `submitBatchSize` items (template 5; max 10) } → `prediction_complete` with reason `manifest_spent` when every selected film is settled (normal complete even if ready films remain). Do not call `prediction_next`. Heartbeat before a model call that can last long and at least every 10 minutes; keep the `epoch` the heartbeat and each submit return. Each execution starts from a clean context and keeps nothing between executions.
- **Stops.** `already_running`, `manifest_too_large` (nothing was created), `lease_lost`, `wrong_protocol` and `prediction_catalog_held` end the execution without a lease reset. `profile.scope: "global"` is stopped with `prediction_complete` reason `profile_changed`, and `contract_changed` with reason `runner_aborted`. After a lost response or a `502` the Task replays the same `prediction_batch_submit` body instead of regenerating, and on `submit_in_flight` waits `retryAfterMs` before that replay. A `deferred_budget` or `stale_profile` item is not a failure of the run; a `validation_error` item is deferred by the existing retry policy and is not resubmitted.
- **Dry run.** A `dryRun: true` execution is a separate, owner-approved procedure that writes nothing to prediction state; it is not a scheduled Task. It keeps the one manifest it received and replays those same films at generation sizes 1 to 10 from that held copy, never re-reading the live queue between passes.
- **Prompt text.** The ready-to-install Russian prompt and its execution playbook are [`hourly-predictions-batch-v2.md`](scheduled-task-prompts/hourly-predictions-batch-v2.md) (AIR-449; `manifestSize` / `manifest_spent` under AIR-463 / ADR 0136; proposed text, not installed). A spent selected manifest with ready films left ends with `prediction_complete` reason `manifest_spent`: normal `status: complete` and a truthful Event, not `time_budget` and not «Прогнозы приостановлены». Enabling the Tasks remains [AIR-451](https://trello.com/c/NN3N6kRp). A ready dry-run prompt, the [A/B procedure](../runbooks/prediction-batch-v2-dry-run-ab.md) and the offline report aggregator (`scripts/prediction-ab-report.mjs`, AIR-450) exist; none is installed, approved or run against production. `tests/scheduled-task-prompt-v2.mjs` checks its length, hash, tool names and a simulated run.
- **Authorization.** Creating, editing, enabling or running a Task, a dry run, and the switch of the active Task each need the owner's explicit, operation-specific approval ([authorization](../process/authorization-and-escalation.md#chatgpt-scheduled-task-authorization)).

### Legacy Stage A: external Discovery executor (rollback only)

The bullets below are the Stage A text the hourly Task carried while Discovery was driven from ChatGPT (`DISCOVERY_EXECUTOR` absent, the external executor). They are **not** in the live prompt and are kept for a separately approved rollback of the Discovery executor. A spent series of 12 chunks waited for the next hour in that mode; the Workflow executor renews it without the hour wait ([ADR 0083](../adr/0083-inert-discovery-workflow.md), Accepted 2026-11-02; [ADR 0093](../adr/0093-discovery-workflow-cron-reconcile.md)). The real production switch was [AIR-324](https://trello.com/c/kNtaEbm8).

- **Stage A — safe existing-generation discovery catch-up:** call `probe_read`, `epg_status` and `epg_pipeline_status`. Never call `epg_sync_start`. **Make no `epg_sync_step` unless `epg_status.stage` is `complete`** ([ADR 0030](../adr/0030-discovery-queued-at-publication.md)). This gate applies to every stage A step, including the orphaned-`running` exception and the AIR-159 generation handoff of a stranded earlier-generation record. At `stage: epg` a step is a retry of the daily commit's tail, even when the published generation already shows outstanding chunks. Beyond the gate, continue discovery only when the published `programmeRunId` is unambiguous and the checkpoint authorizes either ordinary continuation with positive `remainingChunks` or the due exhausted-budget renewal described below. A zero budget is not by itself a completed backlog. No lease, backoff, retry or generation mismatch may block the step. Call `epg_sync_step({runId})` sequentially, one chunk per call, following `nextAction` and `nextCatchUpAt`. Do not manufacture run IDs, reset leases, force retries or start a separate TMDB/discovery job. If stage A cannot proceed, still attempt stage B **if safe**.
- **Due exhausted `chunk_budget` (AIR-299):** The hourly task must recognize a checkpoint with `continuation.stage=paused`, `reason=chunk_budget`, `remainingChunks=0`, and a valid `nextCatchUpAt` that is at or before the current time. This is a **new bounded series on the same published EPG generation**, not an orphan recovery, generation handoff, forced resolve, or a new EPG run. Require fresh read-only `epg_status.stage=complete`; a single nonempty `runId` identical in `epg_status`, `epg_pipeline_status.programmeRunId`, and `continuation.programmeRunId`; `continuationHealth.status=settled`; and no future `retryAt`, additional hard wait, terminal error, conflicting writer, or ambiguous ownership. Repeat **both** status reads and all guards immediately before the one ordinary `epg_sync_step({runId})` that reopens the budget. A `settled` health report with `lease=null` does not prove that no other writer owns a live resolver lease: the Worker must still enforce its lease and checkpoint CAS; stop on `busy`, wait, error, mismatch, conflict, or unknown outcome without retrying. After a confirmed response for the same published generation, follow only the fresh server `nextAction` and new budget, one chunk per request. Do not attempt a second budget renewal in the same task invocation. A persisted `discovery.nextAction=wait` for `chunk_budget` can remain `wait` after its stored time has passed, because the new budget is opened by the **next eligible step**, not by a background clock. This narrowly defined exception applies only to `paused/chunk_budget/0`, not `complete`, `interrupted`, `backoff`, or an old generation.
- **Interrupted series:** `continuation.reason: interrupted` stays `nextAction: stop`. Do not call `epg_sync_step` for it, and do not send a recovery flag: `epg_sync_step` has no such argument. The gated confirm is an owner resolve body outside this task ([ADR 0088](../adr/0088-guarded-interrupted-discovery-recovery.md), Proposed). After that confirm has stored an ordinary checkpoint for the same published generation (`reason` no longer `interrupted`, and the fresh contract says `continue` or a due `wait`), the next invocation of this task may take one ordinary chunk under the stage A rule above. Until that checkpoint is visible on a fresh status read, this task still stops. A `settled` health report on an interrupted record is not permission to step.
- **Seal `busy` (AIR-362):** a `stage: seal` answer with `discovery.state=busy`, `busyKind: lease_held` and a `nextCatchUpAt` no later than about 93 s away is a bounded wait for the writer whose step was cancelled: wait until `nextCatchUpAt`, then call `epg_sync_step` once more for the same `runId` and follow the fresh answer. Wait at most once per step; a second `busy`, `lost_race`, an error, mismatch or unknown result stops the invocation. No lease reset, no new run. The deployed contract does not edit the Task prompt; adopting the wait in a prompt needs a separate owner-approved change.
- **Projector window `busy` (ADR 0103, not active):** while the projector holds an exclusive window, an EPG step may answer `discovery.state=busy` with `busyKind: projector_window` and a `nextCatchUpAt` at the window's absolute deadline (up to about 300 s away), from the sync step or the seal step, without failing the run or persisting an error. The wait rule above covers only a `lease_held` seal busy within about 93 s, so a Task that follows this contract stops its invocation on a `projector_window` busy and reports it; the Cloudflare EPG executor sleeps until `nextCatchUpAt`. Waiting for the window in the Task needs a separate, owner-approved prompt or timeout change, which this document does not make; until then the feature flag stays off.
- **Orphaned `running` continuation — fail-closed exception:** A raw `continuation.stage=running` does **not** authorize a step. Only a fresh, read-only `epg_pipeline_status` from a compatible Worker can establish `continuationHealth.status=orphaned`, `lease=expired|none`, `generationConflict=false`, no live competing owner, and an exact match between the pinned `continuation.programmeRunId` and the published `programmeRunId` confirmed by `epg_status` and `epg_pipeline_status`. Require `remainingChunks` to be a positive integer and `resumeBudget` an integer from zero through `remainingChunks`. No hard wait or future `retryAt`/`nextCatchUpAt` may apply. With `epg_status.stage=complete`, only then may the hourly task call **one ordinary** `epg_sync_step({runId:publishedRunId})` for the same generation; the Worker is responsible for CAS, fencing and settle/resume. Missing health (including a pre-recovery Worker), `live`, `settled`, `unknown`, ambiguous owner, generation mismatch, invalid budget or a `busy` response means **do not call or retry**. Never infer recovery authority from an expired lease alone, change the task itself, reset a lease or create a new EPG generation. After any successful step, honor server `nextAction=continue|wait|stop`, current generation and budget; do not chain steps against a changing checkpoint. Worker behaviour, not a prompt rule: when the orphan's hop and the hop it was resumed from both ended before their checkpoint, the Worker answers this step with `stop` / `reason: interrupted` and runs no chunk (fail-closed, [discovery contract](api/enrichment.md#live-and-orphaned-running-records)); the task reads it as any other `stop`.

A separate registry readback around 10:28 confirmed: task enabled, hourly at :20 Europe/Madrid, updated prompt 19,454 characters, and no new evidence-free authority prefix. [Dated activation evidence](../evidence/prediction/air-335-hourly-prompt-activation-2026-11-03.md) distinguishes registry acceptance from the still-pending first production fingerprint. This document is a maintained contract, not the executable task registry.

**Active authority guidance.** Mutable prediction state, including queue, profile and fingerprint pointers, prediction current/history, runner files and leases, is D1-authoritative after AIR-317. Immutable fingerprint and prediction bodies remain in R2 bucket `iptv`. On 3 November 2026 Stage A remained unchanged (no `epg_sync_start`, and no `epg_sync_step` unless `epg_status.stage` was `complete`); AIR-324 later removed Stage A from the live prompt and forbids `epg_sync_step` for any reason.

**Active Stage B evidence rules.** Use the map only when the server requests `fingerprint_and_prediction`. On `prediction_only`, reuse the existing Worker fingerprint without writing or inventing its `evidence`:

- Include `evidence` with only `plotMechanics` and `execution`.
- Every asserted `plotMechanics` id has one to four items at `evidence.plotMechanics[id]`. No extra mechanic key. A mechanic may use `metadata` when that fact is on the film `modelMetadata` passed to `prediction_validate` (`metadata:synopsis`, `metadata:genres`, `metadata:runtime`, `metadata:credits`). It may use `model_knowledge` with the single ref `model_knowledge`, or `web_research` with `https` URLs that were actually used. Do not invent a URL. The Worker does not fetch one.
- Every general execution value other than `unknown` or `not_applicable` has one to four items. Metadata does not support an execution-quality claim: items that are all `metadata` are invalid. A metadata item beside `model_knowledge` or `web_research` is valid. The general dimensions are `plot_engine`, `pace`, `stakes`, `decision_logic`, `protagonist_competence`, `opposition_competence`, `problem_solving`, `plan_counterplan_strength`, `multi_party_goals`, `chemistry`, `payoff`, `ending_quality` and `technical_plausibility`.
- If an execution value cannot be supported without metadata alone, set the dimension to `unknown` and omit its evidence key. `unknown` is a gap, not `low`. `not_applicable` has no evidence key. Do not put items on `unknown` or `not_applicable`.
- Genre dimensions stay optional. Omit the key when the fingerprint has no such dimension. A concrete genre value may omit evidence. If it has items, they follow the same shape and are not metadata-only.
- Each item is exactly `basis`, `refs` and `confidence`. `basis` is `metadata`, `model_knowledge` or `web_research`. `confidence` is `low`, `medium` or `high`. `refs` holds one to four unique strings. No duplicate item. No extra key.
- **Since [ADR 0129](../adr/0129-fingerprint-source-fields-derived-from-evidence.md) the Worker derives `sourceBasis` and `sourceRefs` when both are omitted** (the proposed batch v2 prompts omit them; the live v5 prompt text below still computes them and stays valid because a supplied aggregate must only equal the derived one). Historical rule of the live v5 prompt: set `sourceBasis` and `sourceRefs` from the aggregate, not from a guess. Walk asserted mechanics in list order, then the general dimensions in the order above, then genre dimensions in schema order, and within a claim the submitted item order. One basis keeps its name; more than one is `mixed`. `mixed` is never an item basis. `sourceRefs` is the first-seen unique refs, capped at eight.
- Before `prediction_submit`, call `prediction_validate` on the exact objects. Only when an item cites a metadata token, pass that film's exact `modelMetadata` from `prediction_next` as the optional `metadata` parameter to `prediction_validate`; otherwise omit `metadata`. Require `success` and `valid`. Do not submit a rejected fingerprint. Do not call `assessPredictionConfidence` and do not add `confidenceAssessment`. ## Timing: nominal trigger versus server gate

The Worker cannot read the task registry. It states the expected hourly recurrence once, as `HOURLY_TASK_SCHEDULE` (`Europe/Madrid`, minute `20`) in `src/enrichment.js`, and derives every displayed or reported "next run" from it. Two times are kept apart:

- **Nominal hourly trigger** (`nextScheduledRunAt` in prediction and discovery `wait` responses, `predictions.nextScheduledRun` in the footer status, shown as `Следующий запуск по расписанию: около HH:MM` Europe/Madrid): the first instant whose Europe/Madrid wall-clock minute is `:20`. Europe/Madrid offsets are whole hours, so this is every UTC hour at `:20`, also across the March and October DST changes (on the October change the local time `02:20` occurs twice). It is an estimate of the trigger, not of the actual start and not evidence that the task will reach the Worker: the scheduler can run late and has no SLA. It is `null` when the time zone or the recurrence is unusable; nothing guesses a time then. In prediction responses `nextCatchUpAt` is a compatibility name for the same nominal value.
- **Discovery gate** (`discovery.nextCatchUpAt` when `nextAction` is `wait`): the Worker's own earliest permitted step. For `chunk_budget`, an error and a pending generation it is the next whole UTC hour; for `backoff` the stored retry time; for a live writer its lease expiry. It throttles a new chunk series and fences concurrent writers, does not depend on the schedule, and is not a run time. A `wait` also carries `discovery.nextScheduledRunAt`, the first nominal trigger at or after the gate, which is when the hourly task was expected to catch up while the external executor drove Discovery. The hourly Task no longer carries Discovery catch-up: the Cloudflare Discovery Workflow renews its series itself. A `continue` or `stop` carries `null`.

A caller honors the gate; it reports the nominal trigger as the next scheduled run. A change of the live recurrence (owner-approved, see below) needs the same delivery to update `HOURLY_TASK_SCHEDULE`, this section and `tests/scheduled-task-timing.mjs`, which checks that the constant and this contract agree.

### What the footer can tell about a missed hourly run

The footer classifies stored Worker records only. It does not read the task registry, and it does not call a usage or billing API. The ChatGPT product limit that can stop a Scheduled Task before any MCP call is a different meter from OpenAI API-key usage, and this service has no credential, route or stored owner-entered value for that product limit. Nothing in the footer invents one.

A prediction run that actually stored `stopReason` `quota` is the one case the footer names as a usage limit, with the run's finish time as the confirmation. A task that ends before it contacts the Worker leaves no such record. Recognition then uses the schedule grace in the [enrichment footer contract](api/enrichment.md#failure-behavior): after two nominal triggers past a due exhausted `chunk_budget`, plus 45 minutes, with ready discovery work, a parseable checkpoint time and a same-generation discovery batch whose `finishedAt` parses and is not later than the gate, the recognition line says there is no confirmed execution and that an external block is possible. A missing status, a missing or unparseable checkpoint or batch time, or a batch from another generation is unknown evidence, not that sentence. That sentence is not a quota finding. The prediction line keeps the last stored run, including a drained queue. The next-run line stays the nominal schedule.

## Operational controls and drift

Only authorized, action-specific owner approval permits **changing the prompt, schedule or enabled state of any automation on this page, or triggering a production writer**. Updating this reference or merging a PR is **not** such approval. Changes to the live task must be followed by a semantic comparison against this contract and same-delivery updates to affected reference, diagrams and runbooks. The external registry wins on what is currently configured; this document defines what is expected.

When auditing the live registry, compare the hourly Predictions Task entry with its expected enabled state, recurrence, timezone, prompt permission boundaries and recorded execution outcomes. A read-only drift review must not call production writers or edit a task.
