# MCP connection, safe probes and recovery

> **Operator procedure — not production authorization.** Never invoke writable MCP tools, change Access, secrets or Scheduled Tasks without an action-specific owner approval. Protocol, tool schemas and trust boundaries: [MCP reference](../reference/api/mcp.md).

## Connecting ChatGPT

The connector is connected. The 19–20 October 2026 `probe_read` and `probe_echo` calls confirmed only interactive Managed OAuth, not unattended refresh or successful production work. [AIR-62](https://trello.com/c/CU71gW4c) subsequently accepted scheduled EPG and prediction operations on 21 October. On 24 October both external recurring tasks were observed enabled with recent execution timestamps. These dated observations do not guarantee today's authorization or job success.

After a new MCP tool deployment, refresh the connected ChatGPT tools if their cached schema is stale. The list must be exactly `probe_read`, `probe_echo`, `epg_status`, `epg_pipeline_status`, `enrichment_schema`, `enrichment_profile`, `enrichment_runner`, `enrichment_queue`, `enrichment_status`, `prediction_queue_overview`, `prediction_film_diagnostics`, `prediction_pending`, `epg_sync_start`, `epg_sync_step`, `prediction_start`, `prediction_next`, `prediction_submit`, `prediction_heartbeat`, and `prediction_complete`, plus the read-only `prediction_validate`. Do not call writer tools against production without action-specific owner approval, even though AIR-62 has been completed. The three prediction diagnostic tools are read-only; the production check for them is the procedure in [AIR-98](../reference/api/prediction-diagnostics.md), after this deploy.

To connect a replacement server, use the same URL and OAuth with an empty client ID and secret, and sign in as the owner. The current allow-list already permits a ChatGPT connector callback under `https://chatgpt.com/connector/oauth/*` (requirement 2).

## Connecting Claude

Claude Code cloud sessions reach `/mcp` through a claude.ai custom connector, not through a local MCP configuration. Settings → Connectors → Add custom connector: name `IPTV MCP`, URL `https://iptv.vladimino.workers.dev/mcp` exactly (the client sends it as the RFC 8707 `resource`), empty client ID and secret (DCR). The connector's callback, `https://claude.ai/api/mcp/auth_callback`, must be on the `IPTV MCP` allowed-redirect list (requirement 2). The claude.ai account email plays no part: the identity in the Access JWT is the one used at the Cloudflare Access login, so the owner signs in there with an identity the owner-only policy admits. Connectors are read when a session starts; an already running session can pick a new connector up after reconnecting. On 25 October 2026 the connected Claude client listed the 19 tools exposed to that client at the time, `probe_read` returned `authorization: cloudflare-access-jwt-verified`, `storage: not_accessed`, protocol `2025-11-25`, and `probe_echo` returned its marker. The same boundaries apply to Claude as to ChatGPT: writer tools and `enrichment_status` only with an action-specific owner approval.

The repository's `.claude/settings.json` pre-approves only `probe_read` and `probe_echo` from this server for cloud sessions; every other tool call still prompts the owner. The same file pre-approves read-only tools of the official Cloudflare MCP servers (`https://mcp.cloudflare.com/mcp` and `https://observability.mcp.cloudflare.com/mcp`) used to verify live Worker, Access and log state; the Cloudflare API `execute` tool, which can write, is deliberately not on that list.

## Safe verification procedure

These checks contact production only through Cloudflare Access and the two probes. None of them reaches R2. Run them only with the owner's approval. Never paste tokens, JWTs, or cookies into logs, issues, or chats.

0. Local: `npm ci`, `npm test`, `npm run build`.
1. Unauthenticated discovery. Access answers these requests; they never reach Worker code.

   ```bash
   curl -sS -o /dev/null -D - -X POST https://iptv.vladimino.workers.dev/mcp \
     -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
     --data '{"jsonrpc":"2.0","id":1,"method":"ping"}'
   ```

   Expect `401` with `WWW-Authenticate: Bearer … resource_metadata="…"`. Fetch that `resource_metadata` URL with `curl -sS`: expect JSON whose `resource` is exactly `https://iptv.vladimino.workers.dev/mcp` and which lists `authorization_servers`. Fetch `<issuer>/.well-known/oauth-authorization-server` for that issuer and check requirement 5. Record whether `authorization_response_iss_parameter_supported` is `true`. Any HTML, `302`, or `403` here means discovery is blocked (requirement 4). Stop.
2. Use the connected ChatGPT server described above.
3. In a chat, ask ChatGPT to call `probe_read` from this server. Expect `status: ok`, `storage: not_accessed`, `sideEffects: none`.
4. Ask it to call `probe_echo` with a marker such as `mcp-probe-2026-10-19`. Expect the identical text back.
5. Repeat step 1. The unauthenticated request must still get `401` from Access.

Leave Scheduled Tasks and writer MCP tools out of this connectivity smoke test. `epg_sync_start`, `epg_sync_step`, `prediction_start`, `prediction_next`, `prediction_submit`, `prediction_heartbeat`, and `prediction_complete` may write R2 or advance a run; AIR-62 completion is not permission for extra production calls. In contrast, `prediction_queue_overview`, `prediction_film_diagnostics`, and `prediction_pending` are read-only tools, suitable for separately authorized diagnostic checks. Do not use `/api/*`, the dashboard or synchronization as connectivity probes; some `GET` routes have side effects (see [README](../../README.md)).


## Reading the deployed feature flags

`feature_flags` answers one question: which value does each registered flag have on the Worker version that answered, and what does the code make of it. It reads no storage and changes nothing, so it is a safe read under the existing MCP authorization; it is not an approval for any flag change.

1. Call `feature_flags` with no arguments. Check `summary`: `invalid` and `redacted` should be 0.
2. For each flag you rely on, read `state`, `effective` and, where present, `effectiveWithRequirements`. A flag whose `effective` differs from `effectiveWithRequirements` is set but blocked by an unmet requirement.
3. `redacted: true` means the binding holds something other than the flag's tokens; only its length is shown. Fix it in the dashboard (Workers & Pages → `iptv` → Settings → Variables and Secrets) under the owner's approval; never ask for the value in chat.
4. `issue: retired_tokens` on `LIFECYCLE_LOCALIZATION` or a `set` `SCORED_RESOLUTION` is a leftover binding: inert, and its removal is a separate owner-approved settings change.
5. Record the read time (`readAt`) next to any ledger update in the [feature flag reference](../reference/feature-flags.md#production-configuration-evidence-ledger).

The field list is in the [feature flag reference](../reference/feature-flags.md#reading-the-deployed-values).

## Diagnosing a stalled EPG continuation

Use this when the continuation stays `paused / epg_committed` with `remainingChunks: 12` after a published generation, as in [AIR-69](https://trello.com/c/FlcWZX7W). Everything below is a read; none of it starts a chunk, a sync or a task.

1. Read the Worker log first: with the Cloudflare Observability connector (or the dashboard's Workers Logs), filter the `iptv` Worker for messages containing `"event":"epg_continuation"` in the window around the scheduled call. Each step produces lines with the same `id`: `phase: entered`, `checkpointed` when its discovery hop stored a checkpoint, then `completed` or `failed`. This is the arrival evidence; the ring below is a convenience view of the same entries. The `$metadata.requestId` of those lines identifies the Worker invocation; the invocation's own event (same request id) carries `$workers.outcome` (`ok`, `exceededMemory`, `canceled`, `exception`), `wallTimeMs` and `cpuTimeMs`. When an MCP client reports a generic `Internal error`, this join is how the platform outcome is established; query outcome and timing fields only, never request headers.
2. Call `epg_pipeline_status` (or `GET /api/enrichment/pipeline/status`) and read `continuation` and `continuationDiagnostics.recent` (newest first, at most 20 entries; `recorded.entered: false` in a log line means the ring never got that entry, and 20 later steps evict an entry).
3. Find the entries around the time the external Scheduled Task should have called `epg_sync_step` after the EPG commit. The commit itself is the entry with `branch: epg_commit` and `discovery.reason: epg_committed`.
4. Read the table:

| What the log and the ring show after the commit entry | Meaning | Next safe step |
| --- | --- | --- |
| No `entered` log line with `caller: mcp` and `route: /api/sync/epg` in the retention window, and no ring entry | No request reached the Worker handler. This does not say where it stopped: a call rejected by Cloudflare Access (`401`/`403`), dropped by the client or never sent leaves the same absence | Check the Scheduled Task's own execution history and prompt, then the Access logs for `/mcp` in that window |
| No ring entry but an `entered` log line exists | The call arrived; the ring write failed or the entry was evicted | Read the log pair for that `id`; `recorded` on the outcome line says which write failed |
| `branch: run_mismatch`, `httpStatus: 409` | The call arrived with a `runId` that is not the current `sync.json` run; `runIdShape: invalid` means it was not even a server-generated id | Compare the task's `runId` with `epg_status` |
| `checkpointed` without a `completed`/`failed` line of the same `id`, or a ring entry `phase: interrupted` with `interruption.committed: true` | The step's chunk and checkpoint committed (`checkpoint.hopId`, `checkpoint.remainingChunks`), then the invocation ended in its trailing writes or before the response; the caller saw an error or a timeout for a committed step | Nothing to recover and nothing to repeat: the next ordinary step continues the series (after the lease expires when its release was lost too). Record the platform outcome from the invocation event; a repeated `exceededMemory` here is a memory defect of the chunk, not a continuation defect |
| `phase: interrupted` with `interruption.committed: null` (closed from `entered`) | The invocation ended before its hop stored a checkpoint, or before it reached the discovery branch at all. `cause: unknown` is literal: the entry is not evidence of an error by itself | Read the continuation: an `orphaned` record is the orphan row below; a settled record with a later checkpoint means another step committed. Join the invocation outcome for the cause |
| `continuation.reason: interrupted` (`discovery.nextAction: stop`, `diagnostic.branch: interrupted`) | Two hops of the series in a row ended before their checkpoint; the series failed closed and every scheduled step answers `stop` without running a chunk | Find the platform outcome of both interrupted entries. Do not reset the lease or edit the record. The next EPG commit of a new generation opens a new series; running the chunk earlier is an owner-approved forced `POST /api/enrichment/discovery/resolve`, normally only after the cause (for example memory) is fixed |
| `entered` log line without a `completed`/`failed` line of the same `id` (or a ring entry stuck at `phase: entered`) | The call arrived and the invocation ended before a response was formed. Read the continuation next to the entry: a checkpoint written after the entry (`continuation.at` later than the entry's `at`, `lastBatch.hopId` equal to `continuation.hopId`, `continuationHealth.status: settled`) means the chunk and its checkpoint committed and only the trailing writes or the response were lost, a transport failure the client may show as an MCP error or a timeout; a record still `running` means the invocation ended between the status write and the checkpoint write (the orphan row) or before the chunk finished | Transport failure: nothing to recover, the next ordinary step continues (after the lease expires when its release was lost too, `busy` / `wait` until then). Otherwise look at the Worker invocation in the same window (exception, memory, cancellation) and follow the orphan row |
| `phase: failed` | The handler threw; `error.code` classifies the cause (`storage`, `upstream`, `timeout`, `publish_conflict`, `resolver_busy`, `invalid_input`, `unknown`) | Fix the cause before any retry; the message itself is only in the Worker exception, never in the entry |
| `branch: continuation`, `diagnostic.branch: lease_live` | Another chunk held the resolver lease; the contract answered `busy / wait` and nothing was overwritten | Wait for `nextCatchUpAt`; a lease that never expires is a separate defect |
| `diagnostic.branch: contract` with `decision.nextAction: wait` or `stop` | The stored continuation already said wait or stop; `decision.hardWait` tells whether `force` would have been ignored too | Read `entry.reason` and `entry.nextCatchUpAt` |
| `diagnostic.branch: missing_secret` | `TMDB_API_READ_ACCESS_TOKEN` was unset in that invocation | Verify the Worker variable; a deploy with `keep_vars` does not remove it |
| `diagnostic.branch: chunk` with `chunk.stage: error` | The chunk ran and failed; `chunk.error` classifies the cause; the continuation is `error` with a catch-up time | Fix the cause; the next call after `nextCatchUpAt` resumes |
| `diagnostic.branch: chunk` with `saved.owned: false` | The chunk ran but another hop had replaced the continuation meanwhile; this call's result was not stored | Read the owner hop's entry (`saved.hopId`) |
| `continuation.stage: running` in pipeline status with `continuationHealth.status: live` (`diagnostic.health.status: live`, `branch: lease_live`) | A writer holds the resolver lease; `leaseHop` says whether it is the record's own hop or another one | Wait until `continuationHealth.leaseExpiresAt`; the record is not an orphan yet |
| `continuation.stage: running` with `continuationHealth.status: orphaned` | The writer's lease expired without a checkpoint and the hop has been silent for a whole lease TTL. The likely cause is an invocation that ended between the status write and the checkpoint write (the very next write), or a checkpoint write that failed; the lease release, the diagnostics ring and the response come after the checkpoint and cannot produce an orphan: record the cause as an inference. `chunkCompleted` says whether a status marked with this hop's id was saved; `resumeBudget` is what the next step resumes with | One ordinary explicit `epg_sync_step` recovers it; no lease reset, R2 edit or forced call is needed or allowed. A caller that reads only the raw `continuation.stage` will not make that call by itself; teaching the external scheduled caller to read `continuationHealth` is a separate owner-approved change |
| `diagnostic.branch: chunk` or `orphan_settled` with `recovery.action: settled` | The orphan was settled from the hop-marked chunk status under the dead hop's id (`recovery.orphanHopId`), then the step continued as usual (`chunk`) or reported the settled contract (`orphan_settled`, for example `chunk_budget` / `wait`) | Nothing; the series continues from the correct remaining budget |
| `recovery.action: resumed` | No status marked with the orphan's hop id was found (the chunk had not finished, another hop wrote the last status, or the status predates hop markers); the step ran the chunk again with the hop's full budget | Nothing; decisions already saved for that chunk were reused, at most one extra chunk was spent |
| `diagnostic.branch: chunk` with `saved.write: write_conflict` | The chunk ran, but both conditional writes of its checkpoint were rejected while the record still named the hop; the checkpoint is reported as not stored and the record stays `running` | The next explicit step settles it from the hop-marked status; nothing is repeated |
| `chunk.stage: error` with `chunk.error: resolver_busy` and `saved.write: other_hop` | A hop that stalled past the lease TTL tried to write after a replacement had taken the lease; the renewal before the write failed and the chunk aborted without touching storage | Nothing; the replacement's checkpoint stands |
| `diagnostic.branch: chunk` with `recovery.action: generation_recovered` | The checkpoint belonged to an earlier generation (an orphan with `generationConflict: true`, a finished or paused series, a `programme_changed` stop) or was a `programme_changed` record of the published generation written mid-publication; the step superseded it with a fresh `epg_committed` series for the published generation (`recovery.superseded` names the earlier one) and ran the first chunk. The earlier hop's decisions and statuses were not touched | Nothing; the series continues on the published generation. This is also the repair for a commit that ended after publication but before its discovery checkpoint |
| `continuation` is `paused / epg_committed` for the published generation while `epg_status.stage` is `epg`, and the commit's ring entry has no outcome | Since [ADR 0030](../adr/0030-discovery-queued-at-publication.md) the commit opens the series right after publication; the invocation then ended in the commit tail (watchlist and events, prediction queue, ratings) | The hourly task makes no step here (stage A requires `epg_status.stage=complete`). The run's own daily task, or a separately owner-approved manual `epg_sync_step` with the run's id, retries the commit on its resume path and keeps the series as it is. Read the Worker invocation (memory, exception) for the cause |
| `diagnostic.branch: generation_pending` | The checkpoint belongs to an earlier generation, but the published generation is not in place yet (the pointer names it while the shared `programme.json` still carries the earlier one); nothing was written | Wait for `nextCatchUpAt`; if the shared programme never follows the pointer, the publication itself failed mid-copy and needs its own investigation |
| `diagnostic.branch: record_changed` | The continuation moved between this call's read and its write (a concurrent step settled or opened it); the call released its lease and wrote nothing | Read the entry of the hop named in `saved.hopId`; call again after `nextCatchUpAt` |
| `diagnostic.branch: chunk` with `saved.owned: true` and `remainingChunks` decremented | The step worked as designed | Nothing; the next call continues the series |
| `diagnostic.leaseReleased: false` on a completed step | The checkpoint is stored, but the release of the hop's lease failed; the lease expires on its own within one TTL | Nothing; a call before the expiry answers `busy` / `wait` and writes nothing |
| `diagnostic.trailingError` set on a completed step | A write after the checkpoint failed (`storage` for the score preview or the variant plan); the chunk result and the checkpoint stand | Nothing for the series; the failed artefact is rewritten by the next chunk |

5. Record the finding on the card with the entry `id`, `at`, `branch` and `diagnostic.branch`. The entry holds codes, UUIDs, timestamps and counts only, never tokens, titles, messages or payloads.

Deleting or editing `epg/resolver-continuation-diagnostics.json` is a production write and needs approval; it is never needed, the ring overwrites itself. The same holds for `epg/resolver-continuation.json` and `epg/resolver-lease.json`: an orphaned `running` record is recovered by the next ordinary `epg_sync_step`, not by editing or deleting either object. Running that step on production is a writer call and needs its own approval like any other discovery step.

## Rollback

Revert the change on `main` and let GitHub Actions deploy it; `/mcp` then returns the generic `404`. Removing the two variables makes `/mcp` return `503` immediately, which also requires approval because it publishes a version. Disabling `IPTV MCP` is an Access change and needs approval. It leaves `/mcp` closed (see Authorization). None of these steps touches R2 or Scheduled Tasks.
