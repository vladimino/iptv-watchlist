# Events log

The activity list reads objects under `events/items/`. The key is `events/items/<reverse-timestamp>-<id>.json`, so a page is newest first. `GET /api/events` returns one page and may also recover an undelivered prediction stop event. That route is not a safe production read. Clients ignore an event type they do not render. A rendered event shows its `at` in Europe/Madrid and does not show storage keys, hashes, prompts or profile text.

| `type` | When it is written | What the list shows |
| --- | --- | --- |
| `epg` | The successful end of an EPG run (its completion time) | Counts of films and broadcasts |
| `watchlist` | A watchlist commit | Added and removed films |
| `discovery` | One logical Discovery tick: a chain of Workflow instances that settled, or a scheduled firing that confirmed an empty queue | One compact result: new films, observations resolved, what is left in the queue, honest stop |
| `ratings` | A Ratings run that ended (finished, error or closed as unknown) | One compact result: Diary rows checked, new facts, removals handled, honest error or interruption |
| `started`, `unstarted` | An owner mark on one film | The film title |
| `enrichment` | A prediction run's start, progress, stop or completion | Queue progress, separate from profile publication |
| `taste_profile` | One committed move of the taste-profile current pointer | Version transition, a short category and selective or global scope |

## Taste-profile publication

`PUT /api/enrichment/profile` writes this event only after compare-and-swap has made the version current ([publication contract](../api/enrichment.md#taste-profile-publication)). A dry run, a refusal, a lost compare-and-swap and a version record that is not current write none. The current pointer may be the R2 object or the D1 profile row. The event is always the R2 object above. The two writes are not one transaction.

```json
{"id":"taste-profile-3","type":"taste_profile","at":"2026-11-02T20:15:00.000Z","fromVersion":2,"toVersion":3,"changedFields":["horrorPreferences"],"scope":"selective"}
```

`id` and `at` come from the committed version (`taste-profile-<toVersion>` and that record's `updatedAt`), so a replay stores the same object and does not append another. `fromVersion` is the previous lineage link, or `null` when this version has no stored predecessor. `changedFields` are the field names the publisher already accepted, not the field text. `scope` is `selective`, `global`, `identity`, or `null` for the first version. The profile body, `profileHash`, approval and declaration hash are not copied.

The list turns one known field into a short category, several known fields into one summary line, and `identity` with no known field into a line that the content did not change. `selective` and `global` become «Влияние: выборочное» and «Влияние: глобальное». Any other scope adds no impact line. An unknown field name is not printed. Nothing in this event is a count of recalculated predictions.

If the event put fails, the publication response stays HTTP 200 and adds `publicationEvent: {recorded: false}`. Current stays where it is. The identical request then answers HTTP 409 `version_not_increasing`, does not move current, and records the missing event only when the committed version body has `tasteProfileEventExpected: true`. That field is server-written on the immutable version record. A version without it, including one that was already current before this writer, stays without an event; a caller-supplied field does not create one. A different body for that same version does not. The procedure is in the [publication runbook](../../runbooks/taste-profile-publication.md).

## EPG and watchlist events: publication, retry and idempotency

Contract of [AIR-359](https://trello.com/c/0IV9qKWR).

- **One `epg` event per published generation.** Its id is `<runId>-epg`, and `films`, `archive`, `future` and `broadcasts` are counted from the published report. Since [AIR-390](https://trello.com/c/apwh5ERU) its `at` is the **successful end of the run**: `run.completedAt`, the very value that becomes `sync.json` `updatedAt` when the run is `complete`, and so the footer's EPG time (`integrationHealth` `lastSuccessAt`). It is no longer the scan time (`report.updatedAt`), which still defines the archive and future windows the counts use. The event is written only **after the run record is durably `complete`**: by `finishSync`, or at the end of the staged seal `queue` phase, never in `finalize`. A run that has not published or whose complete record could not be saved leaves no event, so there is no false «Обновлён EPG».
- **Order and recovery.** The completion step fixes `run.completedAt`, parks the finished event in `run.epgEventPending` and saves the complete run record (`stage: complete`, `updatedAt = completedAt`, the mark) in one write. Only then is the event put and the mark cleared. If the record save fails, nothing was exposed and the retry completes the run. If the event put or the clearing save fails, the persisted complete run keeps the mark and the next step on it (the complete-run continuation) writes the same event again and clears it: the event is then late, never false, and never duplicated. The key `events/items/<reverse-timestamp>-<runId>-epg.json` is derived from the parked `at`, so every retry hits the same key, and `sync.json` `updatedAt` carries the same time. Only the `epg` timestamp changed: the watchlist event, its removal-reference key rules and the other event types are untouched, and events already written are never rewritten, moved or deleted (the 8 November 17:01 entry keeps its scan time).
- **Run in flight across the deploy.** A staged run whose `epg` event was already written under the scan time by earlier code (its `finalize` ran before the deploy) keeps that event and gets no second one; its `completedAt` stays unset.
- **Rescan inside a run.** If an earlier attempt of the same run failed before the pointer moved, the next scan builds the events again for the scan it is about to publish (`epgSync` rebuilds them when the saved `epg` event does not carry the new `updatedAt`). A run saved by earlier code that still carries an `epg` event of a superseded scan has that event rebuilt from the published report when the run completes (its `at` is then the completion time).
- **Watchlist event.** Its diff (`added`, `removed`, `total`, `baseline`) is computed from the watchlist before the run and the run's watchlist, so a rescan yields the same delta. An event with no removal is rebuilt for the new scan and carries the published time. An event that reports removals keeps its key, and with it the time of the first scan of the run: the removal hand-over references the event by key (`events/items/<reverse-timestamp>-<id>.json`, derived from `at`), the commit hands the references to the removal queue **before** it publishes, and a queue entry cannot be re-pointed afterwards, so a rebuilt key would leave that reference dangling. For such an event `at` therefore denotes the watchlist observation (the first scan of the run that saw the removal), not the EPG publication. This is a contract decision that needs the owner's approval ([AIR-359](https://trello.com/c/0IV9qKWR) records the request); the alternative is to hand the references over only after the publication, which changes the commit order and needs its own card.
- **Ratings at the first display (AIR-379).** The watchlist event is written with the confirmed ratings the fact store already holds for its removed films (at most 25 probed; stored facts only, no Diary, no Letterboxd request, no wait; see the [ratings reference](../integrations/letterboxd-ratings.md#the-epg-commit-under-the-separate-pipeline)). A film rated before the publication is shown with its rating at once (the half-star value is kept); a film with no stored fact, a null rating or no probe stays unrated and is listed as «Остальные удаления», never as viewed on the strength of a missing rating. A rating that arrives later enriches the **same** event (same key, same `at`, one event, other confirmed ratings kept) through `settleRemovalRefs`. Listing events (`GET /api/events`) looks nothing up. On the daily schedule the Ratings run (17:00 Madrid, seconds long) normally finishes before the EPG commit, so a rating that Diary shows that day is already stored; a rating that Diary does not show yet waits for the next daily Ratings run, which settles it on the same event.
- **Idempotency.** A repeated `finishSync`, a resumed committed run and an events refresh write the same keys; no second event is created. Events written by earlier code are not rewritten, and ordering and pagination by key are unchanged.
- **Not covered.** A one-off correction of an event that was already written with a stale time (the 5 November 17:03 entry and the 8 November 17:01 entry) is a separate owner-approved action: exact key, idempotency and readback. This contract changes code only.

## Ratings run result (`ratings`)

Contract of [AIR-361](https://trello.com/c/pKYwrxcZ). One immutable event per Ratings run that reached a terminal state in the run record (`finished`, `error`, or `unknown` when a stale or interrupted run is closed). Never one per film, per step or per heartbeat, and none for a run that never started or whose terminal state was not persisted.

| Field | Meaning |
| --- | --- |
| `id`, `runId` | `<runId>-ratings` and the run id. The Workflow instance id, the hour and the generation time play no part |
| `at` | The run's real end (`finishedAt`, or `closedAt` for an unknown close); the key is `events/items/<reverse-timestamp>-<id>.json` as for every event |
| `state`, `cause` | `finished` / `error` / `unknown`; `cause` is one of `failed`, `blocked`, `rate_limited`, `interrupted`, `abandoned`, `diary_off` or null |
| `trigger` | `scheduled` or `manual` |
| `coverage` | `recent_window` while only Diary page one was read; never «whole history checked» |
| `diary` | Counts only: `pages`, `rows` (checked), `added` and `updated` (Diary entries), `written` (facts written), `unchanged`, `skipped` (already recorded), `conflicts` |
| `removal` | `pending` at the start, `checked` lookups, `rated` (removed films whose rating was found in this run, by Diary or by a lookup) and `resolved` (removal references of the Events Log settled with a rating, including films rated earlier). The two count different things and do not overlap; a rating whose reference could not be settled counts as `rated` only |
| `details` | Optional, [AIR-393](https://trello.com/c/45smSEfH). Only for the films this run **changed**, absent when it changed none and on every event written before the field (those render as the short summary, with no backfill). Groups, each a list of `{id, title, year, tmdb, rating}`: `added` (a new watched fact; `rating` null for a view without a rating), `updated` (a different rating, with `from` only when the earlier one was a stored number), `rated` (removed films whose rating this run found, by Diary or by a lookup: the `removal.rated` measure) and `resolved` (films whose removal reference this run settled: the `removal.resolved` measure). A film appears once per group, so a film with two references is listed once while `removal.resolved` counts both. At most 25 films per group; `more: {<group>: n}` counts the rest, so nothing is cut silently. `incomplete: true` states that some change could not be captured or named. `id` is the Letterboxd film id (never shown as a title); `title`/`year` are null when no stored source knew them; `tmdb` is set only where every stored id agrees |

Written, read and unchanged are different numbers: 50 rows checked with one new fact reads «записей проверено 50, новых фактов 1». The aggregates carry only numbers. The optional `details` carry titles, years and ratings of the changed films only, never Diary rows, URLs, the unchanged 50 or raw Letterboxd content.

**Delivery.** The D1 run record is the source and R2 is a projection, and the two are not atomic. An event is built from a **committed** terminal record only and put with a create-only precondition, so a repeat finds the key and writes nothing; a close that a start has not committed (a compare-and-swap that is lost) publishes nothing. It is delivered right after the terminal commit and again at the next look: a start (after its own commit), a terminal read by the Cloudflare executor, the closing of a stale run, or the hourly executor tick, so a missed event is repaired without starting Ratings again. The run is marked `ratingsEventAt` once delivered. If the record is replaced before delivery, the owed event moves to the new record (`pendingEvents`) with a retry time (15 minutes, doubling to a day), so the attempt rate is bounded but the outcome is never given up on. Only when more than 60 outcomes are owed at once (about two months of daily runs with the Events Log unreachable) is the oldest discarded, and `eventsDropped` on the run record counts it. The owner accepted this bounded policy on 2026-11-06 (AIR-361 review); keeping overflow without loss would need another store and a new decision. A failed put never fails the run, never reads Diary again and never repeats a step; the status reads and writes nothing. Events for runs that ended before this change are not created.

**How the details are taken (AIR-393).** They are recorded on the run record while the run works and are never rebuilt afterwards. A plan is an intent and a receipt is a fact, and only receipts reach the event. For the Diary page, the films it will change (a new watched fact, a different rating, a removed film whose queue entry the Diary will resolve) are **planned from the view index before any fact is written** and saved on the record under the page's own key, `diary.pageChanges[<page>]`, in state `planned`, so a kill after the facts are written cannot lose them. The page checkpoint then saves the contribution in state `applied`: on the first attempt narrowed to the writes that really happened (`applyDiaryEvidence` outcomes and the queue entries the Diary resolved); on a replay of the page (a plan already stored) narrowed to what the stored view and queue show now (a film that is watched, a rating equal to the planned one, a queue entry resolved by the Diary), so a write another writer won, or one the page lost as older, is not claimed. This is a check of the stored **state**, not of who wrote it: a replay cannot tell this page's own earlier write from another writer's identical value stored after the plan, so for a replayed page `details` state what the stored data shows changed during the run, not a proof of which writer changed it. A first attempt is stricter: it claims only the writes its own `applyDiaryEvidence` reported. A contribution that stays `planned` (the page never completed: a failed, blocked or abandoned run) is ignored by the event. The plan and the confirmed contribution keep **every** candidate of the page (a page holds about 50 rows; the hard ceiling is 100 per group), so the confirmation covers the whole page, not only the films an event can show; the event is built from the confirmed lists and only then shows the first 25 and counts the rest, so the remainder is exact. A replay replaces its page's contribution instead of adding to it, so a remainder is never counted twice. Past the ceiling the count is a lower bound and the event carries `details.incomplete`. If the planning, reading or saving of a page's details fails, the facts are still written and the contribution is saved as `incomplete`: the event then carries `details.incomplete: true` and the screens say the list is incomplete, never a complete-looking list. The removal steps work the same way. Before a step settles a reference or looks a film up, it saves an **intent** (`removal.intents`: the film, and the reference's event key for a settlement) on the run record; after the effects it confirms each intent against the stored queue (a `rated` film is a queue entry in state `rated` with a half-star rating; a `resolved` film is a reference that is marked resolved) and moves the confirmed films into `removal.changes`, clearing the intents. A kill after a lookup or a settlement, before that confirmation, leaves the intents on the record, and the **next step confirms them before it starts**, so the film is neither lost nor claimed twice. An intent whose effect did not happen (a film that was not rated, a reference whose event is missing) is dropped, not claimed. As for a replayed Diary page, this confirms the stored state, not which writer produced it. `rated` (rating discovery) and `resolved` (reference settled) stay separate groups, a film with several references appears once in `resolved`, and the counters keep their meaning. `removal.changeSteps` keeps the recent confirmation tags, so a repeated merge of one confirmation is ignored. The event merges the applied page contributions and the removal contribution. The counters of the Diary page are still saved with the step summary, as before this change, so a step killed after its page checkpoint loses that step's counters (the event can then show `0` written next to a list of films), never its films; the list is the receipt, the counter is the older, coarser number. The names come from what is already stored: the removal event that listed a removed film, otherwise the metadata cache and the title dictionary. No Letterboxd or TMDB request is made for a name, and `GET /api/events` reads nothing extra. Because the event is built from the committed record, a retry, a checkpoint between steps, a lost create-only put and the carried delivery all produce the same `details`; a repeated delivery changes no stored event. `rated` and `resolved` are different measures: the same film may be in both, and neither list is added to the other's count. The details are bounded by construction (4 groups, 25 films per contribution and in the event), also in the carried `pendingEvents` list.

The events screen and the compact feed draw each non-empty group as an expandable list like the watchlist event. A film is a local link to `/film/tmdb_<id>` only when `tmdb` is present; without a stored title it reads «Название недоступно», never its id; a rating is shown only when it is a half-star between 0.5 and 5.

## Discovery tick result (`discovery`)

**Boundary of a tick (AIR-410).** A *logical tick* is one orchestration run, not one chunk, step or Workflow instance. It is either (a) the chain of Workflow instances of one published generation, from the start of its first instance to the terminal stop of the last one (a rollover to a successor instance and the recovery after a failed step stay inside the same tick), or (b) one **scheduled hourly firing** that starts no chain because the queue of the published generation is confirmed empty. A chain that runs longer than an hour is still one tick and one event, written when it settles; no event is written for the hours in between. A firing that starts a chain, finds one running, or cannot start the pipeline (authority held or loading, handoff pending, executor not `workflow`, lease busy, anything unconfirmed) writes no event.

**Fields.** `id` is `discovery-<tick id>` (the tick id is the generation and the start time of the tick; an empty tick is `discovery-empty-<generation prefix>-<hour>`). `at` is the settlement of the tick (for an empty tick, the start of its hour, so the same hour always has the same key) and `startedAt` its start. `kind` is `run` or `empty`. `status` is `finished`, `superseded` (a newer generation replaced the run), `failed` (recovery exhausted) or `stopped`; `reason` is the terminal reason of the executor (`complete`, `backlog_empty`, `stale_generation`, `recovery_exhausted`, `executor_not_workflow`, or `queue_empty` for an empty tick). `chunks` counts the chunks whose checkpoint was saved. The counters are `checked` (observations processed: resolved, reused and screened), `added` (new catalog films), `reused` (observations that reused an already known identity), `screenedOut` (observations screened as not films), `touched` (known catalog films whose showing was refreshed) and `tmdbCalls` (TMDB requests of the chunks). `remaining` is the last known queue size (`null` when unknown) and `queueEmpty` is `true` only when the queue is a confirmed zero; `error` is a code from a fixed list or `null`. No film, title, key or free text is stored.

**What the numbers are.** Each counter is the sum of the per-chunk summaries that the owner checkpoint saved during the tick. Every summary describes one chunk and none is a cumulative total, so a repeat, a resume, a Workflow replay after a sleep and an older observation are not counted again. The sums live in the executor record (`tick`), are carried by every successor instance and are settled in the same compare-and-swap as the terminal stop. A chunk whose checkpoint was not saved loses its numbers, so the counters are a lower bound; `remaining` is the value of the last saved chunk, not a fresh count. No full scan is made for the event.

**Empty and unknown.** A queue is empty only when **both** the remaining count and the cheap-pass remainder are proven numeric zeros, with no error. A part that is missing, `null`, negative, fractional or not a number is unknown and is never read as zero: a chunk that does not report its cheap-pass remainder confirms nothing, so its tick is not claimed empty (`queueEmpty: false`). An unknown remainder is shown as unknown, never as zero. «0 checked, queue not empty» (`checked: 0`, `queueEmpty: false`) and «queue empty» are different events. An empty tick is written only by a scheduled firing, only while the stored continuation says complete and the last saved status of the published generation carries `remaining` `0` and `cheapRemaining` `0` as numbers, at most once per hour.

**Delivery and idempotency.** The event is immutable and is written create-only under its id: a second put finds the key and keeps the first. A settled tick not yet marked delivered is delivered by the next caller that sees it (the owner that settled it, or the next scheduled reconcile), which writes the event and then marks the record, so a lost event write never repeats a Discovery chunk or a TMDB request. When a newer generation replaces the executor record, the tick it replaces is written first as `superseded`. If that put is not confirmed, the settled tick is **not dropped**: it moves to the `outbox` of the new record, every later write of the record keeps it, and the next scheduled reconcile delivers it (an entry leaves the outbox only after its put is confirmed). The outbox never drops an entry. It holds at most 64 (about 350 bytes each); a failed put alone never blocks the new generation, but when the entries still undelivered would exceed 64 the replacement **fails closed**: `createWorkflowInstance` answers `events_outbox_full` and leaves the record as it is. The hourly reconcile delivers the outbox before it looks at the generation, so the replacement goes through at a later firing once the event puts succeed again, and every replaced tick still becomes exactly one event. `GET /api/events` returns the stored event unchanged and writes nothing for it.

**Display.** The events screen and the compact feed draw one compact card from fixed sentences chosen by `kind` and `status` («Найдено новых фильмов: N», «Новых фильмов не найдено», «Новых изменений нет», «Очередь Discovery пуста», «Прогон Discovery прерван: вышла новая программа», «Прогон Discovery остановлен после повторных ошибок»), the three numbers (new films, observations resolved, left in the queue; zeros are shown) and one line with the reused, screened and TMDB counts. A count that is not a non-negative integer is drawn as `0`, an unknown remainder as «неизвестен», and nothing stored reaches the page as markup.

## Type filter on the events screen

The events screen (`/events`) shows the one feed of `GET /api/events` in its main column; its sidebar holds a single-select group of seven buttons, «Тип событий». The filter is applied in the browser to the events already loaded, never on the server, and it never changes the loaded set or the cursor. The compact feed of the programme and film pages is not filtered.

| Button | Stored `type` values it shows |
| --- | --- |
| «Все события» (default) | Every loaded event, including a type the page does not know |
| «Watchlist и просмотр» | `watchlist`, `started`, `unstarted` |
| «Программа» | `epg` |
| «Находки» | `discovery` (one Discovery tick result, separate from the prediction runs of «Прогнозы») |
| «Оценки» | `ratings` |
| «Прогнозы» | `enrichment` (start, progress, stop and completion of a prediction run) |
| «Модель вкуса» | `taste_profile` (a profile publication, not a prediction run) |

The choice is the `type` query parameter of the events URL, next to the `return` target of the programme page; the default needs no parameter, an unknown value means «Все события», and a deep link, a reload and Back or Forward restore the pressed button. Changing the choice replaces the current history entry.

**Automatic pagination.** Choosing a type (and opening `/events` with one) loads the following pages by itself, in cursor order and one request at a time, until 10 loaded events match or the cursor is exhausted. A page with no match neither stops the search nor needs a click, and events that are already loaded are reused, so nothing is read twice. While it searches the page says «Ищем более давние события…» with the number of matches found among the loaded events, and the matches found so far are listed. When 10 are loaded the search stops and «Более давние события» stays for manual paging. «Все события» never searches: it shows the first page and the manual button.

The search stops at once, and its request is aborted, when the type or the screen changes. It stops on an API error (the reason is shown with «Повторить»; there is no automatic retry, and the retry resumes from the cursor that failed) and on a cursor that repeats or does not advance (a visible message and the same «Повторить»). An empty result is reported only when the whole archive has been read: «Во всём доступном архиве событий этого типа нет.» Before that, a type with no loaded match says «Среди загруженных событий этого типа пока нет.» A count is always a count of the loaded events, not a total. Events are keyed by `id`, so a page that repeats an event does not list it twice. Each page is a normal read of `GET /api/events`, which may also recover an undelivered prediction stop event (see above): this is not a safe production probe.
