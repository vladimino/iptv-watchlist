# ADR 0078: Mutable prediction state is owned by D1 only after its own marker is switched

**Status:** Proposed  
**Original decision date:** 2026-11-01  
**Recorded at:** 2026-11-01  
**Approval source:** Owner GO to implement the domain ([AIR-317](https://trello.com/c/jj45y0JW)). Acceptance of this record, and visual approval of the changed diagrams, are still owner gates. Applying migration `0007`, importing rows, switching the marker, and any other production write are not authorized by that GO.  
**Related work:** [AIR-317](https://trello.com/c/jj45y0JW), [ADR 0073](0073-metadata-cache-d1-authority.md), [ADR 0064](0064-prediction-queue-conditional-writes.md), [ADR 0051](0051-d1-domain-r2-blobs.md), [ADR 0015](0015-queued-prediction-recovery.md)  
**Supersedes:** [ADR 0064](0064-prediction-queue-conditional-writes.md) for the queue fence only while `prediction_domain_authority.mode` is `d1`: the compare-and-swap is the D1 generation, and the object etag is the mirror. [ADR 0002](0002-cloudflare-worker-r2-authority.md) for mutable prediction state only, in that same mode. Immutable fingerprint bodies, prediction version objects and profile version objects stay in R2. The rest of each record stands.  
**Superseded by:** None

## Context

The prediction runner reads and writes a set of R2 objects: the active taste profile, each film's current fingerprint and prediction bundle, the queue (hot and cold work, retries), the runner lease and the writer lease, and the run checkpoint. Immutable bodies already live beside them: `fingerprints/<hash>.json`, `predictions/versions/<sha256>.json` and `profile/versions/<n>.json`. The Worker is the only writer. The hourly ChatGPT Scheduled Task calls the same start, next, submit, heartbeat and complete protocol. That schedule and prompt are not part of this decision.

Schema v1 already has `profile_version`, `fingerprint_payload`, `prediction_current` and `prediction_history`. Those tables are the offline import. Their film id is `film:<lid>`, they have no queue, lease or run, and a foreign key would drop an off-watchlist id and a redirect id that the runner still stores. They are not a runtime marker.

Production schema is v6. The metadata cache marker is `d1`. `D1_ENRICHMENT_WRITE=on`. The cron is `37 * * * *`. A code deploy must not apply a migration, start a prediction run, or add a Worker flag. There is no transaction that covers D1 and R2 together.

## Decision

1. **One domain, keyed as the R2 objects key it.** Migration `0007_prediction_authority.sql` adds the marker, a fence row, an in-flight intent row, and tables for the active profile, the fingerprint pointer, the current prediction, its lineage, the queue chunks, the runner and writer leases, and run checkpoints. `film_id` is the id in the R2 key. It is not a foreign key and the write does not insert a `film` row. An off-watchlist id and a redirect id stay as stored. The queue, the leases and the run checkpoint are the mutable documents. The profile, fingerprint and prediction rows are pointers. The immutable bodies stay in R2. The queue is ordered chunks in `prediction_queue`, one replace in one transaction, each rendered statement under D1's 100 KB limit. Stale film and run ids are deleted in pages of at most 80 keys. `prediction_domain_intent` records one `r2` put that has claimed a generation and has not finished, including the SHA-256 of the exact object text that put was about to write. The current fingerprint row keeps `produced` and, when the writer stored them, `fields`. The immutable fingerprint body does not carry that provenance.
2. **One marker, default `r2`, and it stays forward-compatible.** `prediction_domain_authority` is a single row. `mode` is `r2` or `d1`. `writes` is `open` or `held`. The migration inserts `r2`, generations at 0, and `writes` `open`. `prediction_domain_cas` makes a batch fail when the compare-and-swap matches nothing. It is not a switch and not a Worker flag. Applying `0007` does not copy a profile, a fingerprint, a prediction, a queue, a lease or a run, and it does not set `d1`. It refuses a contract below version 6 before it creates tables. On version 6 it sets the contract to 7. On a higher version that has not installed this domain it creates the tables and leaves that higher version in place. A contract older than version 7 does not query these tables and keeps the objects. A missing `schema_contract` table keeps the objects only when `PREDICTION_DB_REQUIRED` is unset. A caller that omits the binding and does not set `PREDICTION_DB_REQUIRED` stays on the objects: that is the local API. The deployed Worker sets `PREDICTION_DB_REQUIRED` to `on` in `wrangler.jsonc`. With that variable, a missing `DB` binding, or a bound database with no `schema_contract` row, fails the prediction read or write and does not use the object. The variable is a deploy-time binding invariant, not a runtime flag. A binding that is present and does not answer fails the step. Version 7 or newer with none of the ten prediction tables means this domain is not installed. A later migration may have advanced the contract, and prediction stays on the objects. Some but not all of those tables, or all of them without a marker whose mode is `r2` or `d1` and whose `writes` is `open` or `held`, fails closed.
3. **`r2` on version 7 or newer claims the generation before the object put.** A mutable save advances `generation` only when `mode` is still `r2`, `writes` is `open`, and the generation is the one just read. The same batch inserts `prediction_domain_intent` for that object key and stores the SHA-256 of the exact bytes the put will write. The fence observes the generation update, so a failed insert rolls the generation back with the intent. The object put runs after that batch. `completePredictionWrite` deletes the intent only after the put returns, including a put that returns null. A put that throws leaves the intent. A crash before the delete leaves it too. `--reconcile` with `--confirm reconcile` deletes an intent only when the object now stored under that key hashes to the recorded bytes. It does not delete an intent whose object is absent or different. `--release` still refuses while any intent remains. If the compare-and-swap matches nothing, the put does not run. The queue, the leases, the profile publication and the other mutable saves take that claim. A queue or lease write reads the marker again immediately before the put. A head captured while these tables were absent does not put once the marker is `d1`; that attempt returns without a request, and the caller opens the head again. While the marker is still `r2` and the tables are now present, that head claims the live generation before the put. A head that already saw the tables still claims the generation it captured, so a stale generation does not put. A run-file checkpoint writes that run and does not elect `latest`. Only the latest-run write clears the previous `latest` and elects its run. A late stop of an older run therefore cannot displace the current run. The immutable body write is unchanged and stays create-only.
4. **`d1` reads and writes the tables, and does not fall back.** A read of a mutable key returns the row. A read of the current fingerprint overlays `produced`, `fields` and the other mutable provenance from the row onto the immutable body. `fields` is the list stored for a partial fingerprint. A restored fingerprint may omit it. The read fails closed rather than dropping that list. An empty table is an empty value. A failed read, a payload that is not JSON, or an immutable body that is missing or whose canonical SHA-256 does not match the pointer fails the read. The mirror object is not the fallback. The view index keeps ratings and the other fields it already holds, and the overlay reads only films already in that index, in chunks of 80, and fails above 5000 films. It replaces prediction, fingerprint, fingerprint hash, impact and the stored mood facet from the tables. The mood function is an argument of the overlay. The view recomputes the mood from the overlaid fingerprint and does not read a global. It does not add a film that was not in the index. A film with no row does not keep those fields from the object. `GET /api/enrichment/view` overlays the index it returns. Writes are one fenced batch. The batch advances `generation`, and the queue or profile generation when that document is the one being saved, only when `mode` is `d1` and the generation is the one the step read. The queue replace deletes the chunks and inserts the new ones in that same batch. The immutable body is written and verified before the pointer moves. If the fence matches nothing, the batch rolls back and the pointer does not move. The mirror put runs after the batch. A crash between them leaves the mirror behind. The next read still uses D1.
5. **The same runner protocol.** Hot before cold, retry growth, the 15-minute runner lease, the writer lease, heartbeat, lost response and `prediction_retry_heal_pending` stay. In `d1` the lease compare-and-swap is the row token. A queue conflict is still five attempts and then `prediction_queue_conflict`. The queue document is at most 900000 characters. One film keeps at most 80 history rows. A larger write fails and changes nothing. A statement that cannot fit 100 bound parameters or 100 KB fails the same way. The hourly task, its prompt and its schedule do not change. There is no new operational flag and no new cron.
6. **The projector keeps its job.** On schema version 7 or newer it still writes Films, Persons and sync clocks, and it still reads the metadata cache when that marker is `d1`. It does not write the prediction domain. Version 7 or newer with some but not all of the prediction tables, or with all of them and no valid marker, fails that run before a write. None of those tables means this domain is not installed: the run still writes Films, Persons and sync clocks, and prediction stays on the objects. Version 6 stays valid when those tables are absent, and its status object does not gain the prediction fields. A later additive version reports the prediction mode and `writes` only when the ten tables are present. A later version with none of them stays `schema: true` and does not report those fields.
7. **Activation is a separate, bounded procedure.** `scripts/prediction-domain-authority.mjs` prints status unless asked to write. `--load` with `--confirm load` copies a local snapshot in one fenced batch per unit and leaves `mode` at `r2`. The fence is the generation just read. The load does not advance it, and a finished claim whose generation is already above 0 does not block the load. An active lease refuses the load before a write. Load and activate then set `writes` to `held`. A new claim requires `writes` `open`, so it fails while the gate is held. If an intent row remains, the command throws `prediction_domain_busy` and does not copy or flip. The load reads the snapshot again after that hold and copies that snapshot. Activate reads the snapshot again after the hold and requires parity with that read. The flip requires `writes` `held`, the same generations, and no intent row. `--activate` with `--confirm activate` is that flip. `--revert` with `--confirm r2` rewrites the mutable mirrors that the rows still have, deletes a mutable mirror the rows no longer have, checks each write and each delete, and sets `r2` with `writes` `open` only when no intent remains. A missing immutable body, a delete that does not stick, or a listing that cannot be bounded leaves `mode` at `d1`. Immutable bodies are not deleted. `--release` with `--confirm release` sets `writes` back to `open` only while `mode` is `r2` and no intent remains. `--reconcile` with `--confirm reconcile` is the only other way to clear an intent, and only when the stored object matches the hash recorded before the put. The offline script refuses a database path that names production and does not call the network. `scripts/prediction-domain-production.mjs` is the production entry and is not authorized by this record. It names the database `iptv`. Each of `--apply`, `--load`, `--activate`, `--revert`, `--release` and `--reconcile` needs its own `--confirm`. `--apply` accepts version 6, and a higher version whose prediction tables are absent. It does not lower a higher contract version. It also requires `--producers-drained`. That flag is the operator's statement that this Worker build is the one serving, that no prediction request is in flight, and that no request which read prediction state on the previous build is still between that read and its put. Deploying this code is not that drain. The command reads the runner and writer leases and sends no migration statement if either lease is active or those two objects cannot be read. `--revert` writes and deletes only when the install credential names the production account, the bucket `iptv`, and that account's `r2.cloudflarestorage.com` endpoint. Any other bucket or endpoint refuses before a request and does not change D1. A revert that has already put or deleted a mirror and then fails reports `writeState` `partial`, or `unknown` when that later request's outcome is not known, and leaves the marker at `d1`. Each unit is one HTTP body `{sql}`, the same shape as the backfill unit in [ADR 0076](0076-backfill-single-database-batch.md). This entry does not use the REST `{batch}` body. A lost write response is `write_uncertain`, `writeState` `unknown`, and it is not retried. A failure after a committed unit, including the hold, reports `writeState` `partial` and does not say that nothing was written. A busy lease before the hold still reports `writes` false. The load retries a compare-and-swap that committed nothing. It refuses a queue above 900000 characters, a film history above 80 rows, or a unit that cannot fit the statement limits. A revert that cannot verify an immutable body, or cannot prove a stale mutable mirror is gone, does not flip the marker. The schema v1 prediction tables are not this load.

Not decided here: applying `0007` to production, importing the live objects, setting the marker to `d1`, reverting it, and any change to the hourly task, the projector flag, or the cron.

## Alternatives considered

- **Reuse `prediction_current` and the other schema v1 tables.** Rejected. They are the offline import, the film id is a different shape, and they cannot hold the queue, the leases or the run.
- **A new Worker flag.** Rejected. The owner asked for one durable marker. A flag would be a second switch.
- **Fall back to the R2 object when D1 fails in `d1` mode.** Rejected. The mirror can be the stale copy the failure just created. The step fails instead.
- **Move only the queue.** Rejected. The profile, the pointers, the leases and the run would still be a second owner of the same domain.
- **One queue row, or one `NOT IN` of every kept id.** Rejected. D1 allows 100 bound parameters and a 100 KB statement. A legal queue and a legal film set do not fit either shape.
- **The REST `{batch}` body for this domain.** Rejected for the prediction operator. [ADR 0076](0076-backfill-single-database-batch.md) keeps that body for the metadata-cache operator and does not treat its rollback as established. This domain uses the measured `{sql}` unit.
- **A global mood function.** Rejected. The bundle does not make that assignment visible to the overlay. The caller passes the function.
- **Clear an intent when the put throws.** Rejected. A timed-out put can still commit after the client has seen the error. The intent stays until a reconcile reads those same bytes.
- **Treat every schema version of 7 or newer as this domain.** Rejected. An open later migration can advance `schema_contract` without these tables. Readiness is the ten tables and the marker. The contract version only moves forward.
- **Leave a stale mutable mirror in place on revert.** Rejected. After the marker returns to `r2` that object would be current again. Revert deletes it, or refuses to flip.
- **Treat a code deploy as producer quiescence.** Rejected. An isolate that read the queue on the previous build can still put after `0007`. `--apply` refuses without `--producers-drained` and without idle, readable leases. A queue or lease write on this build re-reads the marker before the put.
- **Report a partial revert as no writes.** Rejected. Mirrors already put or deleted stay changed when a later mirror fails.
- **Accept any bucket named by the install credential.** Rejected. `--revert` deletes. The account, the bucket and the endpoint must be the production target.

## Consequences

- Until `0007` is applied, production behavior is the schema v6 runner on R2. After it is applied, and while the marker stays `r2`, readers and writers still use the objects. A mutable save on that database advances `generation`, records an intent, and deletes that intent only after the put returns. A put that throws leaves the intent. A load or activation holds `writes` until activate, revert or `--release`, and refuses while the intent remains. `/api/d1/status` reports `predictionMode` and `predictionWrites` once the ten tables are present, and it still reports the cache fields. Version 6's success object does not gain the prediction fields. A later version with none of the prediction tables stays `schema: true` and does not report those fields. A partial set of them is `schema: false`, and a projection run on that database fails before a write. A later additive version with the ten tables and a `d1` marker keeps D1 as the owner and does not resume R2 writes.
- A queue or lease head captured before these tables existed does not put after the marker is `d1`. A prediction commit does not write `film`, `film_person_credit` or `film_dimension`. An id with no Film row stays an id.
- Pages that still read the mirror can lag by one failed put. Freshness, the queue and the diagnostics that go through the Worker read the tables in `d1` mode.
- The backfill executor still requires schema version 4. A database at version 5, 6 or 7 stops before a reload write.
- The local API omits `PREDICTION_DB_REQUIRED` and keeps the object put, including when the bound database has no `schema_contract` table. The deployed Worker sets that variable to `on`, so a missing `DB` binding or a bound database without that table fails the prediction step and does not read the object. A binding that does not answer, a partial prediction domain, and a complete domain with a missing or invalid marker fail the step and do not read the object. A later contract with none of the prediction tables stays on the objects.

## Recovery and migration boundary

Code rollback does not drop the tables, does not return the contract version, and does not change the marker. A Worker that only reads the objects, running while the marker is `d1`, would decide from a mirror that may lag. Returning the marker to `r2` is `--revert` with `--confirm r2` on the production entry, or the equivalent fenced update, and is its own approval. That revert repairs the mutable mirrors the rows still have and deletes a mutable mirror the rows no longer have, and only in the production bucket on the account endpoint. If an immutable body is missing or does not match, or a stale mirror cannot be removed, the marker stays `d1`. A revert that already changed a mirror and then fails reports that write as partial or unknown. Applying `0007` also requires the producers to be drained and the runner and writer leases to be idle and readable. A deploy is not that drain. A revert does not delete rows or immutable bodies. Clearing an intent whose put threw is `--reconcile` with `--confirm reconcile`, and only when the object bytes match the hash recorded before the put. It is its own approval. Unsetting `D1_ENRICHMENT_WRITE` stops the projector, not the runner. Restoring the database is a Time Travel of the whole database and is its own approval. This record does not authorize applying `0007`, importing, activating, reverting, reconciling, releasing writers, a flag change, a cron change, a task change, or any production R2 or D1 write.

## Follow-ups

Applying migration `0007`, the fenced import, and the marker activation are separate owner approvals. None is implied by accepting this record. After a later activation, the next natural scheduled run is the observation that the live queue, profile and pointers follow D1. That observation is not this record.
