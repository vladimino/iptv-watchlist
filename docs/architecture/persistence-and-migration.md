## Authority per domain

Authority is per domain, not per database. A domain is D1-authoritative only while its own marker says so; an installed table, imported rows or an R2 mirror alone prove nothing. Read the markers live before acting.

| Domain | Marker | Authoritative store | R2 still holds |
| --- | --- | --- | --- |
| Canonical Film/Person | `film_person_authority` `d1`/`open` | D1, fenced adapters (the projector is compare-only) | Immutable sources, frozen `titles.json` / `people.json` mirrors (not a fallback) |
| Metadata cache | `metadata_cache_authority` `d1` | D1 working set | `metadata.json` mirror |
| Mutable predictions | `prediction_domain_authority` `d1` | D1 queue, lease, profile and current/history pointers | Immutable fingerprint, prediction and profile version bodies |
| Published EPG and watchlist | `published_epg_authority` `d1`/`open` | D1 generation | Compatibility mirrors, raw XMLTV inputs, seal payloads and receipts |
| Discovery | discovery marker `d1`/`open` | D1 ledger, decisions, admission, continuation and lease | Immutable observation segments, archive and R2 ledger copies |
| Ratings documents | `ratings_domain_authority` `d1`/`open` | D1 documents | Ratings and removal events, raw Letterboxd inputs |
| Owner reviews | `owner_review_authority` `d1` | D1 rows | `admin/owner-reviews.json` mirror |

What a domain does when its marker is not open is per domain, not universal. Canonical Film/Person `held` or unreadable fails closed: reads answer `503` or unavailable and never reach R2. The published EPG is served only at `d1`/`open`: a marker in mode `r2`, a held cutover or a partly installed set of tables is refused with `published_epg_unavailable` ([ADR 0162](../adr/0162-d1-only-authority-retire-rollback-toolchain.md)), mirror repair does not run and a publisher fails closed instead of writing R2; only the explicit local stand-in (`PUBLISHED_EPG_DB_OPTIONAL`) serves the R2 generation, and only when the tables are not installed. Ratings and predictions fail closed when their marker or tables are missing (`RATINGS_DB_REQUIRED` and `PREDICTION_DB_REQUIRED` are `on` in `wrangler.jsonc`); ratings also refuse a marker in mode `r2` or a held cutover for readers and writers, and predictions refuse a marker in mode `r2`, a contract below 7 and a database without the domain tables in production (`writes` `held` is the normal state after activation and is served) ([ADR 0162](../adr/0162-d1-only-authority-retire-rollback-toolchain.md)). Owner reviews and the metadata cache fail closed when the binding, schema, tables or marker are missing or invalid, or the marker is not `d1` (a local-only `standin` mode exists for development and tests), and Discovery is served only at `d1`/`open`: an installed marker in mode `r2` or a held cutover, and an unreadable authority, are refused with `discovery_unavailable` instead of reading the R2 ledger (a missing binding, schema or set of tables is refused too unless the explicit local stand-in `DISCOVERY_DB_OPTIONAL` is set, and then only for a domain that is not installed at all). The `standin` and `OPTIONAL` modes exist only for local runs and tests. The R2 branches that remain in code for these domains are the cutover and revert toolchain, local and test stand-ins, and the held-reader contract; the [retirement audit](../evidence/d1-migration/air-79-legacy-r2-runtime-audit-2026-11-17.md) classifies each one. Two findings were recorded there: one mutable R2 writer path (catalog poster hydration of the discovered-films catalog, still open) and one stale R2 metadata reader (the started-film event lookup, closed by AIR-516: `POST /api/started` now reads the canonical D1 Film and fails closed). Only the first is an R2 write authority; the second was a reader of a frozen mirror and never evidence that R2 owns canonical Film/Person metadata. GET of programme and watchlist does not write the R2 compatibility mirrors; the hourly EPG `ensure` and the publication tail do. The Finds person filter above is a reader of one GET, not a cutover. Recovery boundaries are in the [D1 authority and recovery runbook](../runbooks/recovery/d1-authority-and-time-travel.md); a code rollback reverts none of this.

## Projector window (schema 18)

Migration `0018` ([migration index](../../migrations/README.md)) adds `projector_window`, one seeded `idle` row (`state` `idle`, `requested` or `held`, an `owner`, and one absolute `expires_at`). It follows a complete version 17, writes nothing else, and was applied to production on 2026-11-08 ([apply record](../evidence/d1-migration/air-383-0018-apply-2026-11-08.md)); the code treats an absent table as no window ([ADR 0103](../adr/0103-projector-exclusive-window.md)), and the flag that requests a window is off. The row is a mutual-exclusion flag with an expiry and is never compared to data. The projector writes it (request, grant and release) and moves the existing `discovery_lease` row with it in one batch; no Film, Person or Discovery document changes owner. Applying it and switching `D1_ENRICHMENT_WINDOW` are separate owner decisions.

## Projector write path (ADR 0106, flag off)

The enrichment projector has one canonical write path per entity and, behind `D1_ENRICHMENT_BULK` (off by default), a grouped path onto the same repository ([ADR 0106](../adr/0106-bulk-projector-write-path.md), [schema reference](../reference/data/d1-schema.md)). Both write the same rows and the same change keys through the same lease or window fence; the grouped path adds nothing to the authority table above: no new writer, store, marker or schedule. A group is one read batch (the repository's traced reads with a digest of each and the Film/Person marker) and one atomic write batch that re-proves the lease or window, the marker generation and every traced read before it writes. The two batches are not one snapshot, so a failed proof rolls the batch back whole and the group is written by the per-entity path. The diagrams on this page are unchanged: the grouped path moves no data between the stores they show.

## Reads during a loading ledger seal

The D1 discovery ledger is published by a multi-batch handoff. While it is `loading`, discovery reads fail closed, except the catalog (`discovery_admission`), the status and the continuation: the handoff writes only the active ledger, the transfer row, the lease and the generation, so those three are exactly what they were before it began. They are served with a `transfer: loading` marker only when the loading transfer is a ledger seal and no admission is pending; a half-replaced catalog stays closed. The active ledger, the observation index, decisions, the score preview and every write stay closed, and nothing falls back to R2 ([ADR 0091](../adr/0091-selective-reads-during-a-loading-ledger-seal.md)). The diagrams above are unchanged: no component, store or arrow is added.

## Resumable ledger seal

Schema 12 adds `discovery_seal`, the durable cursor of the ledger seal job. A seal reads the immutable generation ledger in R2 by byte offset and writes observation rows and the cursor in one D1 batch; R2 keeps the document and a staging payload of the publication, and D1 owns the rows, the cursor and the transfer ([ADR 0092](../adr/0092-resumable-bounded-ledger-seal.md)). Without the table the Worker keeps its previous behaviour. No new store and no new arrow is added to the diagrams above.

The publication after the catalog is three bounded steps (`publish`, `finalize`, `queue`, [ADR 0096](../adr/0096-bounded-seal-publication-steps.md)) so that no step exceeds the shortest MCP client wait; the stores and arrows above are unchanged.
