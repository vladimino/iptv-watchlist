# AIR-696: RCA of the repeated Wikidata HTTP 403 in the Catalog Enrichment producer, 28 November 2026

[AIR-696](https://trello.com/c/SWGZNQQC) · [AIR-607 evidence](air-607-rated-scope-activation-2026-11-28.md) · [ADR 0211](../../adr/0211-catalog-enrichment-producer.md) · [ADR 0219](../../adr/0219-discovery-film-enrichment-and-refresh.md) decision 7 · [runbook](../../runbooks/catalog-enrichment-producer.md).

A dated, sanitized RCA from the code on `main` and already stored telemetry (read-only). No upstream request, producer run, retry, lease reset, flag, Task or D1/R2 write was made for it.

## Result in one line

The producer's Wikidata request (`fetchWikidata` in `src/catalog-enrichment-sources.js`) carried **no `User-Agent`** (only `accept`), while the three other Wikidata readers in `src/sources.js` send `WatchlistAirtime/1.0 …`. Wikimedia's User-Agent policy asks every client to identify itself. A missing `User-Agent` is a verified local deviation and a plausible cause of the `403`; **causality is not proven** (no response body or headers are stored).

## What is proven

- Request path: `query.wikidata.org/sparql?format=json&query=<SELECT DISTINCT ?label … wdt:P4947 "<tmdb id>" … LANG="ru" LIMIT 5>`, GET, headers `accept: application/sparql-results+json` only, through the shared cooldown coordinator, scope `wikidata`.
- Telemetry, 09:41:58-10:06:04 UTC: 23 `upstream_cooldown` events for `caller=catalog_enrichment`, `scope=wikidata`, `reason=forbidden`: 12 `written` (900 s each) and 11 `would_skip`. Within the 7-day log window these are the only Wikidata cooldown events of any caller.
- Classification is as ADR 0219 decision 7 requires: `failureOf(403)` is `transport/forbidden`, which costs no attempt, is not absence or identity mismatch, and sets the shared cooldown; pinned by `tests/catalog-enrichment-sources.mjs`.

## What is not proven

- The response body, `cf-mitigated`, `Retry-After` and any `Server`/`X-Analytics` headers are not logged, so a policy block, a challenge, an IP-level block and a Worker egress mechanism cannot be told apart from stored data.
- No successful Wikidata response by any caller is logged, so the other readers cannot be compared on outcome, and the other readers' header (no contact address) is not shown to be accepted.
- Reproduction needs one upstream diagnostic fetch, which requires a separate exact owner GO (endpoint, purpose, request count). None was made.

## Disposition

Minimal offline fix: send the same `user-agent` as the other Wikidata readers (`WIKIDATA_USER_AGENT`). No change to the cooldown contract, provenance or identity guards, scope or cutoff, priority, or the 72 h fallback. No IP change, browser imitation or retries added.

Regression coverage: header present, accept preserved, `403` stays `transport/forbidden` with no fabricated title (existing cases cover success, absent, ambiguous, malformed, cooldown).

Open for the owner: Wikimedia recommends a contact in the `User-Agent`; this repository is public, so none is added without an owner decision.

## Acceptance (pending)

Natural acceptance on the next ordinary Wikidata access after the cooldown: a `200` outcome with durable progress, or an honest `transport` status with no failure charge or unwarranted write. Provider recovery is not promised; if `403` persists with the header, the cause is external and goes back to the owner with options.
