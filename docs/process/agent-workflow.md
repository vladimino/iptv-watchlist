# Agent delivery workflow

This document is the durable collaboration policy for the IPTV Watchlist project. It does **not** track today's active Trello card, latest PR, deployment version, or production feature flags. Those must be checked live. For code-agent Git preflight and repository safety, also follow [AGENTS.md](../../AGENTS.md); for Trello formatting follow [trello-card-conventions.md](trello-card-conventions.md).

## ADR pre-merge decision gate

An ADR must not be merged with `Status: Proposed`. Before the ADR PR is merged, the owner explicitly decides `Accepted` or `Declined`; the ADR file and register must reflect that decision in the same PR, with an identifiable approval source. Independent technical review or the merge of a design proposal does **not** constitute owner acceptance. A `Declined` ADR is recorded as a rejected decision and does not authorize implementation. Accepting an ADR approves its documented architecture only; it does not authorize production flags, data writes, migration, task edits, or cutover. This gate applies even when the code/documentation changes are otherwise green. Who applies the decision on the branch after a positive review is set out in [Owner gates after a positive review](#owner-gates-after-a-positive-review-executor-hands-off-chatgpt-closes). An administrative correction to a previously merged Proposed ADR is separate from ongoing authorized implementation and must not block unrelated or owner-authorized successor work.

## Owner gates after a positive review: executor hands off, ChatGPT closes

This rule applies to a PR whose only remaining pre-merge gates are owner decisions on documentation artifacts: a `Proposed` ADR (the decision gate above) and/or a changed Mermaid diagram (rendered visual approval). It ends the back-and-forth of edits from two sides on the same branch.

1. **The executor's work is done at a positive review.** Once the independent review of the executor's head finds no blocking issue and PR CI on that head is green, the implementation is accepted as correct. The executor states the open owner gates in its Trello handoff (and in the PR body) and then **stops following the PR**: it unsubscribes from PR activity, cancels its check-ins and pushes nothing more to the branch. The general rule that an agent watches its PR until merge or close does not apply from that point.
2. **ChatGPT resolves the owner gates on the branch.** The owner gives the ADR decision and the visual verdict to ChatGPT. ChatGPT then commits directly to the PR branch:
   - **ADR decision:** flips `Status` to `Accepted` or `Declined`, fills the approval source (owner decision and date), updates the [ADR register](../adr/README.md) row and any supersession pointer in the affected older ADR, all in the same PR.
   - **Mermaid and Markdown:** fixes layout, labels, arrow semantics or formatting the owner asks for after looking at the rendered diagram on GitHub, and re-checks the actual GitHub rendering.
   These are documentation-only edits by the coordinator; they need no new executor round and no new independent review, only green PR CI on the final head before ChatGPT merges as in the delivery pipeline below.
3. **Substance goes back through the card, not the branch.** If the owner declines the ADR in a way that invalidates the implemented code, or asks for a change to behavior, contracts or tests, ChatGPT does not edit code on the branch. It writes a consolidated fix handoff in the Trello card and the executor resumes the PR (subscribing again) or a new card is opened.
4. **Nothing else is waived.** An ADR still never merges as `Proposed`, and a changed diagram still needs the owner's explicit visual approval; this rule only changes who applies those decisions. Blocking review findings, red CI, conflicts and production-risk gates still go back to the executor as before.

## Interactive owner acceptance for ADR and Mermaid

Use this owner-facing presentation for a PR whose approved delivery requires an ADR decision and/or visual Mermaid gate, **after** independent review of the latest PR HEAD has no blocking findings and CI for that HEAD passes. If the executor pushes fixes, re-review the new HEAD before presenting the owner gate; never reuse an outdated review or request acceptance while fixes are still pending.

1. **Explain the actual decision.** Verify live Trello, GitHub, the PR diff, tests, ADR, source contracts and relevant diagrams. Describe the proposal, rejected alternatives, effects and rollback implications in Russian, and recommend `Accepted` only if technically justified. Do not confuse the owner's earlier flag disposition with ADR acceptance.
2. **Show original changed Mermaid, not a reconstruction.** Copy the full exact Mermaid fenced source from each modified diagram in the PR head into an interactive ChatGPT Mermaid preview (native `CodeBlock`, `language="mermaid"`, `model_previewable`) and link the corresponding GitHub file/preview. The owner must see the **rendered** diagram. If the chat preview cannot render, ask for inspection of GitHub's actual rendered Preview; source inspection is not visual acceptance. Do not require a diagram when none changed.
3. **Offer a compact owner decision control.** When both gates apply, use two independent native radio groups: ADR `Accepted` / `Declined`, and Mermaid `Визуально одобряю` / `Нужны изменения`; one `Зафиксировать решения` button submits both explicit choices back into the current conversation via `GenUI.issueNewTurn` with PR, AIR and ADR IDs. For a single applicable gate, collect only that decision. No Trello/GitHub action may be triggered merely by rendering the selector or choosing a radio option: owner approval occurs only when the button is pressed and the response is received. If native controls are unavailable, request an explicit written decision instead of pretending Markdown controls are interactive.
4. **Complete the pipeline after consent.** For accepted ADR and visually approved Mermaid, ChatGPT commits `Accepted`, dated approval source, register and predecessor links to the **same PR branch**, validates the final HEAD and CI, merges once all remaining gates pass, verifies both post-merge GitHub Actions jobs, performs only authorized safe production checks, writes Trello evidence, moves to `Готово` **and** invokes `Отметить как выполненная`, reading both states back. For `Declined` or requested Mermaid changes, do not merge; document the decision and route substantive fixes through the existing task/review process.

This is a **user-experience standard**, not an additional approval or a replacement for positive independent review, real rendering, action-specific production authorization or the existing owner gate workflow.

## Roles and sources of truth

- **Owner:** approves goals, non-routine scope and production-risk actions; may have several ChatGPT conversations working on independent streams.
- **Cursor / coding agent:** implements a bounded card, writes tests/docs, creates a PR and reports evidence. Do not assume the coding agent's summary replaces review.
- **ChatGPT delivery coordinator / reviewer:** checks Trello and GitHub firsthand, maintains the board, reviews changes, provides ready-to-send Cursor instructions, merges approved work, watches deployment, verifies acceptance, documents completion and advances the approved queue.
- **Trello:** current card status, approved ordering, native prerequisites, scoped acceptance criteria and operational discussion. Inspect the *actual* linked cards, not IDs inferred from memory; IDs can collide across independent streams.
- **GitHub:** the latest source, code diff, review threads, CI/CD runs and technical documentation. GitHub main is canonical code, but a successful commit is not proof of an enabled production feature.
- **Production evidence:** safe, authorized status and diagnostic reads; source-of-truth, flag and schedule state must be verified for the relevant decision. Historical snapshots are not live evidence.

At the start of work, read the relevant current card and latest comments, its native checklist and linked upstream/downstream cards, the current PR/commits and CI, plus affected runbooks. Do not reuse a previous-session handoff as a current board snapshot. Separate parallel delivery streams, and do not take over another stream's cards unless authorized.

## Language and public-repository boundary

- **Trello:** Russian for cards, comments, dependencies, delivery reports, and instructions intended for Cursor.
- **GitHub:** English for PR descriptions, review summaries, inline review comments, code discussions, and repository documentation.
- **Technical names:** preserve function/class names, API paths, field names, error/reason codes, commit SHAs, and other identifiers exactly.
- **ChatGPT conversation:** Russian by default, unless the owner asks otherwise.
- This repository is public. Never post secrets, authorization tokens, private production payloads, raw model responses/prompts, personally identifying data or confidential operational records to GitHub. Use sanitized aggregate evidence where appropriate.

## Work item scope, acceptance and dependencies

- Each Trello card must deliver one independently reviewable and closeable outcome. Avoid numbered implementation epics hidden in one card. Split separate shadow/cutover/stabilization or live-migration outcomes into independent cards before work starts.
- Follow the detailed [Trello card conventions](trello-card-conventions.md) for Russian descriptions, '[AIR-N]' names, a current plan-context introduction, relevant functional labels, scope, objectively verifiable Done, tests/evidence and rollback.
- Real prerequisites belong in a **native Trello checklist**. **Read existing checklists first; reuse an existing prerequisites checklist instead of creating a duplicate**, and deduplicate prerequisite items across legacy checklists. Each item must be **only the bare Trello card URL**, never a Markdown link or an AIR/title-prefixed label; this is required for Trello to display the actual linked card title and status. Do not create false blockers or empty checklists. Reconcile checkmarks with *actual* Done status after closing upstream cards.
- Give direct Trello links to relevant prerequisites and successor work in PR descriptions and final delivery reports. Do not assign the next AIR number without checking whether it is already used.
- **Ambiguous Trello write results are not permission to retry.** After a timeout, tool error or missing/unclear write response, read or search live Trello to determine whether the mutation actually succeeded before repeating it. Especially never retry `create` blindly: check the intended card's name, AIR number, board/list, and existing matches first. If a duplicate is found, preserve the canonical card and its activity, then archive only the confirmed duplicate. Apply the same verify-before-retry rule to moves, comments, checklist edits and other non-idempotent mutations.
- Code ready, PR merged, successful deployment, read-only production smoke test, shadow verification and cutover are different claims. Record precisely which of them is proven.

## Newly discovered risks: explicit owner triage, not automatic scope expansion

**A task must not become a gate for risks outside its explicitly approved acceptance boundary.** Newly discovered risks are tracked separately unless they demonstrably invalidate that boundary. Define the smallest safe, independently useful outcome and its acceptance boundary before work begins; do not silently grow Done criteria into a migration-wide or cutover-wide gate. A prerequisite must block only the capability that truly depends on it, not unrelated successors.

**The coordinator's responsibility is two-sided:** actively surface meaningful risks **and** prevent unrelated work from being blocked by them. Do not treat every discovered risk as an instruction to stop and broaden the current card. For each material new risk, tell the owner what was found, the evidence and uncertainty, what concrete operation or acceptance criterion it threatens, the consequences of proceeding, and the recommended disposition. Ask the owner to select one of three explicit outcomes:

1. **Accept (принять).** Record the identified risk, consequences, owner decision and date in the current Trello card's comments for traceability; continue the originally approved work and retain the original Done criteria. Acceptance is informed risk ownership, not a claim that the risk was fixed.
2. **Address now (адресовать).** Pause only the affected delivery or production action, define the corrective work and verification, and obtain any needed scope/approval change. Expand the current card only if the risk demonstrably invalidates its accepted result; otherwise use a separate atomic blocking card for the affected capability.
3. **Defer (отложить).** Create or reuse a separate atomic, **non-blocking** Trello card describing the risk, evidence, impact, follow-up trigger and owner; link it from the current card and continue. Do not add it to native prerequisites unless a later, explicitly justified dependency requires it.

**Never silently choose “address now” as the default.** If the owner has not decided, present the options, pause only the operation actually exposed to the unresolved risk, and continue unrelated already-approved safe work; do not silently expand the acceptance boundary. An existing hard safety requirement, an actual invalidation of the agreed acceptance, an explicit legal/security obligation or a production owner gate cannot be waived by merely calling it accepted or deferred: stop the unsafe operation and request an authorized resolution. Record any revised scope and dependencies explicitly before implementation; do not retroactively declare an unmet criterion satisfied or remove an agreed gate without owner approval. Historical comments explain decisions, while live Trello scope and native prerequisites remain the operative contract.

## Delivery pipeline for already approved work

1. **Mandatory next-card readiness preflight.** Before declaring the next already-approved task ready, moving it to `В процессе`, or sending `Приступай к AIR-N`, inspect the **live** card, latest comments, existing native checklists, current `main`, related PRs and relevant safe production evidence. Fix the card first and check all four conditions:
   - **Current card conventions:** the title, atomic deliverable, functional labels, scope, acceptance, dependencies, rollback/safety, documentation/ADR/visual gates and delivery expectations match the latest [Trello conventions](trello-card-conventions.md). Do not quietly change an owner-approved scope or gate.
   - **Current facts:** reconcile stale dates, old phase statuses and historic snapshots with live evidence; label historical observations with their dates instead of presenting them as current truth. Distinguish code merged, deployed, activated and accepted, and do not infer production state from a prior comment or memory.
   - **Native prerequisites:** first read **all existing checklists**, including alternate names, reuse the existing prerequisites checklist rather than creating another, deduplicate entries, and represent each upstream card with **only its bare Trello URL**. Verify each prerequisite against its *live acceptance status*, mark confirmed Done items checked, and keep unfinished genuine blockers unchecked. A checked item or completed upstream card is not sufficient unless its actual required scope is accepted.
   - **Self-contained handoff:** the card's description and clearly identified latest handoff comment contain enough actionable requirements, contract, tests, boundaries and PR/report expectations for an executor who reads only Trello plus current repository instructions. No cross-chat explanation, private memory or ad hoc Cursor prompt is necessary; the owner's entire instruction can be **«Приступай к AIR-N»**.
   If any condition fails, repair and recheck the card **before** announcing readiness. If a genuine prerequisite remains open, leave the task blocked and select only another independently approved, unblocked task; never fabricate a cleared gate.
2. **Card-first implementation handoff.** Before moving an approved, unblocked card to `В процессе` or handing it to Cursor, make its live Trello description and/or a clearly named handoff comment **self-sufficient**: exact scope, inputs/contract, dependencies, tests, safety limits, documentation impact, visual QA and PR/report expectations. The owner's entire executable instruction must be simply **«Приступай к AIR-N»**. Cursor reads the card, latest comments, native checklist, current `main` and repository workflow; no separate instruction text in ChatGPT is needed or expected. Correct missing or stale Trello detail **before** task handoff. For rework, write actionable review findings in GitHub and put a linked, consolidated fix handoff in the same Trello card before asking Cursor to continue. Chat may briefly report status and the card link, but must not be the only place that contains execution requirements.
3. **Independent review.** Open the actual PR diff and relevant changed files, confirm the base/head and current card scope, inspect CI/test evidence and documentation changes, check risk/security/read-only claims, consider missing negative tests and rollback, and resolve review threads. Do not accept a summary alone.
4. **Review feedback.** Leave specific technical comments in English on GitHub. Report practical findings and Cursor instructions in Russian to the owner. If reviewing one's own PR via the owner's GitHub identity, GitHub may reject formal APPROVE; use an explicit positive COMMENT review, not a false claim of approval.
5. **Merge without a redundant owner prompt.** Owner approval of a card's scope and its ordinary PR delivery path **pre-authorizes merge** after a positive independent code/documentation review, resolved blocking threads, successful PR CI on the exact reviewed head, and confirmation that prerequisites and the agreed scope still hold. ChatGPT then checks the latest main/head for conflicts and merges without force or destructive operations, **without asking the owner to say “merge” again**. This is not permission to self-approve an authored PR: independent review remains mandatory. Do not merge if the card or changed artifact has an **explicit pre-merge owner gate** (notably actual rendered Mermaid visual approval), a new architectural/security decision or material scope change, failed/pending CI, unresolved blocking review findings, or meaningful new risk; first obtain the particular missing approval or fix. Normal UI visual acceptance on real production data is **post-deploy** and does not by itself block an otherwise eligible merge, but it does block premature Trello Done. A standard code deploy triggered by merging approved work does **not** authorize any distinct production writer, migration/cutover, flag, Access or Scheduled Task operation; those require separate action-specific owner authorization.
6. **Post-merge tracking is mandatory.** Read the new main merge commit and corresponding GitHub Actions workflow. Stay with the workflow through terminal results for **both Test and build and Deploy to Cloudflare**. A running/queued deployment is not a finished report. On failure, do not claim success or close the card; report the blocker and concrete corrective steps.
7. **Production acceptance.** After successful deploy, use only the safe, authorized checks required by the card. If acceptance calls for a new MCP tool, actually invoke that tool; a successful probe/CI alone is not enough. A cached connector tool list is a real blocker, not proof of a successful smoke test.
8. **Close with evidence.** Add a Russian Trello report linking the PR, review, merge SHA, terminal CI/CD run, smoke test or other evidence, unresolved known limitations and exact outcome. When all defined acceptance criteria are met, move the card to 'Готово' **and explicitly invoke Trello's «Отметить как выполненная» / mark_done action**. These are separate operations; moving a card does not mark it complete. Read back both the list and card-complete state, and correct either mismatch before reporting Done. Update any successor prerequisite checklists.
9. **Continue the conveyor.** If the next card is unambiguous, already approved and unblocked, first ensure its Trello card is self-sufficient for «Приступай к AIR-N», then move it to 'В процессе' without writing a separate Cursor prompt in the chat. Do not ask for re-approval of an agreed sequence. Stop and ask the owner only at a genuine ambiguity, new scope/approval gate, safety decision or unavailable external action.

The reviewer must not return an unfinished routine handoff just because a merge happened while post-merge deployment is still running. If tooling fails or access prevents verification, explicitly distinguish blocked from Done rather than guessing.

## Feature flag lifecycle: plan, test, switch, remove

Every temporary feature flag must have an explicit end-to-end lifecycle **at the time it is first planned**:

1. **Create and plan.** Specify its owner, exact permitted values and defaults, consumers, data effects, rollback boundaries and the reason the flag is temporary. Create a separate, atomic Trello **flag-removal card immediately**, before implementation, link it from the introduction/rollout card, and include the specific cutover, stabilization and acceptance criteria that will unblock deletion. Do not defer creation of the removal card until after rollout.
2. **Implement and test.** Ship the gated change with tests for old/new modes, compatibility and failure paths; register the flag in [the maintained feature-flag contract](../reference/feature-flags.md). No assumption that a deployed flag is enabled.
3. **Switch and stabilize.** Execute shadow/rollout/cutover only under explicit, action-specific owner authorization. Verify the actual production binding from authoritative Cloudflare settings or an MCP diagnostic that **explicitly exposes that exact effective setting**, then verify the relevant production behavior and complete the defined stabilization period. A code default, previous Trello comment, generic MCP probe, or successful deployment alone does not establish a live binding.
4. **Close the rollout with an explicit flag disposition.** Before marking the rollout card Done, record in its Trello comments one owner-approved decision for **each introduced temporary flag**: `retire now`, `retire after stabilization`, or `retain as permanent operational gate`. State the evidence, reason, rollback/operational consequences, and exact successor card. For either retirement outcome, the pre-created removal card **must contain the actual rollout/acceptance/stabilization card as a native Trello prerequisite** (one bare canonical Trello URL per item), not merely a descriptive sentence or a chat note. Verify live card IDs and status, reuse the existing prerequisite checklist, and mark the item checked only after that prerequisite's defined acceptance is truly Done. For `retire after stabilization`, link an existing stabilization acceptance card **only if one genuinely exists and its outcome is required**. Stabilization can instead be a bounded, evidenced check inside the removal card's readiness/acceptance, using already available routine production observations; do not invent a separate card, waiting period, or rollback exercise merely to populate a checklist. If a distinct unsafe operation or material independent delivery is actually required, obtain its owner gate and create a separate atomic task. Do not confuse a readiness card (which may only prepare activation) with proof that activation occurred. For `retire now`, the completed rollout card remains a linked, checked prerequisite and the removal card can proceed only after readiness preflight. A permanent gate requires an explicit safety/operational rationale, owner-approved disposition, and a clear follow-up/review trigger; do not silently omit an existing disposal ticket. **The cleanup card's own scope and prerequisites are live Trello data, never chat-only knowledge.**
5. **Remove and deconfigure.** When the new mode is accepted and the old mode is no longer needed, use the removal card to delete the selector, legacy branch and obsolete tests and update references/runbooks. After approved merge, both CI/CD jobs and safe runtime verification, the **final required acceptance step** for a retired Cloudflare Worker environment variable is to remove that exact production binding under explicit action-specific owner authorization, then independently read back its absence (authorized settings or an MCP diagnostic reporting the exact flag). Never silently remove bindings or assume deployment clears them (`keep_vars: true`). Record both the code retirement and verified binding removal; only then mark the cleanup card Done and Trello `mark_done`. If permission or access is unavailable, leave the cleanup card open with the precise remaining step. Retaining a permanent operational gate requires a separate explicit disposition, not deletion. Restore the old binding according to the documented rollback procedure if reverting to code that reads it. Preserve data, security gates and supported operational capabilities.

Distinguish a **transitional switch** from a **permanent owner-only safety gate**: an endpoint permitting sensitive one-off writes may need a durable gate rather than automatic removal. In that case the initial card must state the rationale and the removal/disposition ticket must explicitly decide whether to retire the endpoint, retain its gate, or replace it with a supported operational control. Never remove protections merely to satisfy a cleanup metric.

Before creating any cleanup card, search live Trello for an existing removal/disposition card using the flag's literal identifier and relevant migration terms; avoid duplicate tickets and duplicate prerequisite checklists. If the required rollback or migration remains incomplete, do not prematurely remove the flag. Review the register after each rollout and verify the cleanup card's existence and prerequisites.

## Documentation acceptance

Before implementation, record the documentation impact in the Trello card and implementation handoff using the [documentation governance matrix](documentation-governance.md). At independent review, compare the actual diff with that matrix; require the matching source, contract, evidence, ADR and diagram changes in the same delivery. A claimed `Documentation impact: none` needs a reason that survives review. Missing required documentation is a blocking finding even when tests are green. Do not defer it to a future cleanup card.

Every material architectural change requires a new ADR that records alternatives, rationale, trade-offs, and supersession where applicable, plus corresponding Mermaid diagrams and technical contracts. Pure refactoring that preserves architectural decisions does not require a new ADR. Mermaid modifications retain the existing owner visual review gate.

## Visual QA

A substantial UI change requires visual QA in a local browser at a desktop width around 1280 px and a mobile width around 390 px. Check representative full and partial states, visual hierarchy, spacing, overflow, whether the controls can be reached, and the main interactions. The PR needs a short written report of what was checked and which problems were found or fixed. Creating, saving, downloading, or attaching screenshots is not required. The owner does the final visual acceptance on real production data after a successful merge and CI/CD. Until that acceptance, the UI card stays open. Green tests or CI are not visual QA. Do not commit screenshots anywhere in the repository.

## Safety and production boundaries

- Never run production sync, discovery/TMDB, model predictions, retry resets, lease overrides, destructive cleanup, R2/D1 migration/backfill, authoritative read/write cutovers, or enable/disable scheduled jobs/feature flags without **separate explicit authorization** for that action.
- Deploying main code is not permission to exercise writable endpoints. A route named GET or 'status' may still have recovery side effects: follow [deployment.md](../runbooks/deployment.md), [mcp.md](../reference/api/mcp.md), README and side-effect tests for safe verification.
- Check the live authoritative storage and configuration; do not assume that a historical Site, R2 snapshot or D1 dry-run has become current production. Treat snapshot integrity/parity and source/target identity reconciliation as evidence gates, not as permission for migration.
- Keep production and historical data private. Do not reproduce raw record dumps in public issues, PR comments, docs, CI logs or chat summaries if those contain sensitive information.
- Verify current Scheduled Task and Access state from authorized live sources before operational claims. Neither an older runbook nor a successful Worker deployment proves tasks are enabled, disabled, connected or executed.

## Conversation handoffs and shared state

- Cross-session handoffs should describe the present blocked acceptance, exact links and the next safe action, **with a date**. New sessions immediately recheck GitHub, Trello and connected tool availability.
- Stable operating rules belong here and in the Trello conventions; live status belongs in Trello, GitHub and current operational evidence. Avoid baking temporary AIR statuses, counts or next-ticket numbers into evergreen instructions.
- The ChatGPT Movies project may include both film-taste modeling and the IPTV website. These workflow rules apply only to IPTV/code/operations tasks, not to general film recommendations or Letterboxd analysis.
- If the owner's requested project change is only documentation, direct-to-main is allowed **only when explicitly approved**; even then, verify the resulting commit and the automatic post-merge/deploy pipeline, because every main push can publish the Worker.
