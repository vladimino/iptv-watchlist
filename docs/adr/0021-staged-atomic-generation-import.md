# ADR 0021: A large programme generation is staged in bounded chunks and published by one fixed-size commit

**Status:** Accepted conceptually, conditional on the scratch G4 gate below (design decision only; it authorizes no migration, scratch or production D1 write, export, token, flag or Task change)  
**Original decision date:** 2026-10-26 (owner architecture review of the design PR)  
**Recorded at:** 2026-10-26  
**Approval source:** [owner review on PR #123](https://github.com/vladimino/iptv-watchlist/pull/123#pullrequestreview-5655427816) ("the design is accepted conceptually, conditional on a subsequent real-scratch G4 performance and atomicity gate"; no D1 or R2 operation or migration authorized)  
**Related work:** [AIR-167](https://trello.com/c/6ZaRfXWL), [AIR-74](https://trello.com/c/5AdAmKPe), [AIR-165 executor](https://trello.com/c/cNTnYS1b), [ADR-0019](0019-live-d1-backfill-boundaries.md), [ADR-0017](0017-staged-d1-migration.md), [ADR-0001](0001-d1-schema-v1.md)

**Superseded by:** [ADR 0075](0075-backfill-single-database-batch.md) in part: a later backfill run does not open a scratch database and does not repeat the G4 harness. The staged generation design and the historical gate results stay. The decision text below is the 26 October 2026 record and is not rewritten.

## Context

The backfill executor (`scripts/d1-backfill.mjs`) writes each unit as one D1 query request and refuses a unit larger than the batch size the scratch probe proved atomic (`batch_too_large`); it never splits a unit, because a split unit is not atomic. The owner proved atomicity on an isolated scratch D1 at one size: a request of 1,000 statements and 954,893 bytes applied every statement, and a request of 1,000 statements and 953,986 bytes whose last statement failed returned `SQLITE_ERROR` and left `COUNT(*) = 0` (recorded on [AIR-167](https://trello.com/c/6ZaRfXWL)). That proves only that size.

Every unit is small except one. `publishGeneration` in `src/epg-repository.js` writes a whole programme generation as one buffered statement list: the pointer guard, the generation row, the pointer, one statement per film membership, film show, last airing, candidate upsert, candidate snapshot and candidate show, and a final statement that marks every candidate absent from the new generation. `scripts/d1-generation-size.mjs` runs that real repository code against a recording adapter on a synthetic generation and counts what it emits; the count equals `3 + F + F·sf + F + 2C + C·sc + 1` for `F` films with `sf` shows each and `C` candidates with `sc` shows each. At the production order of magnitude in the [readiness assessment](../evidence/d1-migration/air-74-backfill-readiness-2026-10-26.md) (22,199 candidates in the latest generation; 2,300 films, the current prediction count, used as an upper bound for films in one generation):

| Shows per film / per candidate | Statements | Bytes | Largest statement |
| --- | --- | --- | --- |
| 1 / 1 | 73,501 | 63.1 MiB | 710,511 bytes (the absent-candidate `UPDATE`) |
| 2 / 2 | 98,000 | 69.0 MiB | 710,511 bytes |
| 3 / 3 | 122,499 | 74.9 MiB | 710,511 bytes |

The candidate upserts alone are about 44 MiB. The [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) as documented on 26 October 2026 apply to each statement inside a batch: at most 100,000 bytes per SQL statement, a 2 MB row, 30 seconds per query, and for a request through the Cloudflare API the 30 seconds bound the whole batch call. The documentation also advises splitting writes that touch hundreds of thousands of rows. So today's generation unit is not merely larger than the proven batch; its absent-candidate statement alone is seven times the documented per-statement limit, and the unit cannot run on D1 at production size in any batch configuration.

Two schema facts shape every alternative. `candidate` is shared mutable state across generations (`activity`, `last_seen_*`, `seen_in_latest`, `attempts`, `retry_at`, `terminal_reason`, `evidence_key`), read directly by discovery and decisions, and `candidate_generation` and `candidate_show` reference it by foreign key. Readers of shows go through `published_film_show`, which joins the `published_generation` pointer with `phase = 'published'`.

## Decision

Alternative (b), accepted conceptually by the owner and conditional on the scratch GO/NO-GO gate below. A programme generation is imported in four steps, and only the last one is visible to readers.

1. **Open a stage.** One small request inserts a `generation_stage` row keyed by `programme_run_id`, carrying the baseline identity (the manifest's aggregate SHA-256), the phase, `published_at`, the expected published run, an owner token, the planned chunk count and the expected row count of each staged table. The primary key refuses a second stage for the same run.
2. **Load chunks.** The staged rows (`stage_film_generation`, `stage_film_show`, `stage_candidate`, `stage_candidate_show`) are produced by the same pure projection that `publishGeneration` uses today (`observationJson`, `candidateParams`, `withheldParams`, refactored to be shared, never duplicated), ordered deterministically (films, their shows, candidates, their shows) and cut into chunks of at most the probe-proven statement count and bytes (today 1,000 statements and 1 MiB; the implementation keeps a margin, about 950 statements). Each chunk is one request: a guard statement, a state statement, the rows, and a write-once receipt `(programme_run_id, chunk_index, row_count, content_sha256)`. The guard aborts the whole request unless the stage exists for this owner and baseline and is `new` or `loading`. The receipt's primary key aborts a second request for the same chunk. Stage foreign keys make chunks load in order: a child row whose parent chunk never landed aborts its chunk.
3. **Validate.** One statement moves the stage to `validated` only when every receipt from 0 to `chunk_count - 1` exists and every staged table holds exactly its declared count. The executor then reads the staged rows back in bounded pages and compares them, field by field, with the source projection; any extra, missing or different row fails the stage. Only a validated stage whose read-back matches may be committed.
4. **Commit.** One request of twelve set-based statements, about 4.4 KB whatever the generation size. Only the SQL text is constant: the rows the commit reads and writes grow with the generation (about 100,000 rows at production size), so its duration grows too and is a measured gate, not a property of the design. Its first statement aborts the request unless the stage is `validated` for this owner and the published pointer still names the expected run (the same CHECK-violation guard `publishGeneration` uses). Then, in order: the `programme_generation` row, the pointer upsert, `INSERT … SELECT` into `film_generation` and `film_show`, the last-airing upsert as `MAX(start_ms) … GROUP BY film_id`, the candidate upsert with the same evidence-key-conditioned resets as today, `candidate_generation`, `candidate_show`, the absent-candidate update written as `NOT EXISTS (SELECT 1 FROM stage_candidate …)` instead of a 710 KB key list, and the stage's state change. A withheld generation uses its own commit with the same guard minus the pointer, `ON CONFLICT DO NOTHING` for candidates and no absent marking.

The design was first proven as an executable SQL prototype on local SQLite ([PR #123](https://github.com/vladimino/iptv-watchlist/pull/123)). [AIR-168](https://trello.com/c/984pXiL6) implemented it: `migrations/0002_generation_stage.sql` (the staging tables, schema version 2), `src/generation-stage.js` (the plan, the stage statements and the orchestration), `generationProjection` in `src/epg-repository.js` (the projection both writers share) and the executor's opt-in `--staged-generation` path in `scripts/d1-backfill.mjs`. `tests/generation-stage.mjs` proves at 1.25× the production order of magnitude (27,749 candidates, 2,300 films, two shows each) that the final tables after staging and committing are identical, row for row, to the final tables after `publishGeneration`, for a published generation over a prior one (with seeded attempts, retry times and terminal reasons and changed evidence keys) and for a withheld one.

**Lifecycle.** `new` (opened, nothing loaded) → `loading` (at least one chunk landed) → `validated` (counts and receipts complete; read-back is the executor's gate before commit) → `published` (committed; for a withheld stage it means recorded without moving the pointer) → `superseded` (a later stage was committed; its staged rows may be discarded). From `new`, `loading` or `validated` an executor may move a stage to `failed` with a reason. Only `failed` and `superseded` stages can be discarded; discard deletes staging rows only, at most a bounded number per table per request, children before parents, and a failed stage loses its stage row so the same run can be staged again.

**Commit point and read invariants.** The commit request is the only write that changes a final table. Before it, every final table, including the shared `candidate` rows, is exactly as the previous commit left it, so the old generation stays unchanged and readable. The commit is one atomic request, so the new generation appears whole or not at all: the pointer moves in the same request that inserts the generation's rows and updates the candidate projection. `published_film_show` joins on the pointer, so a reader sees either the old pointer with the old rows or the new pointer with the new rows, never a mix. Decisions (`recordDecision`) remain separate small units after the commit; they are fenced on the pointer and generation membership exactly as today.

**Ownership, concurrency, resume and uncertain writes.** The owner token and baseline fence every chunk, so an executor working from another baseline, or holding another token, cannot write into a stage. The implementation derives the token from the target database id and the baseline checksum, so a resumed run of the same baseline continues its stage. Because two executors of the same baseline therefore share the token, the token is not a writer lock; the owner accepted the derived token on the condition that an exclusive claim makes one execution the only writer. Each execution draws a random nonce. It opens the stage with that nonce as the claim (`claim_nonce`, `claim_generation` 1, `claim_expires_at`), or takes over a claim that was released or has expired, which raises `claim_generation` in the same statement. It then reads the stage back and continues only if the claim carries its nonce (otherwise `stage_claimed_elsewhere`, nothing else written). Every later write (chunk guard and state, validate, commit, fail) requires the execution's nonce and claim generation in the same request, so once another execution has taken the claim over, the previous one is refused at its next write and stops as `stage_claim_lost`. Chunk and validate requests renew the expiry, 15 minutes by default and bounded to between 1 and 60 minutes. Safety rests on the fence, not on clocks: an expired claim that nobody took over still lets its holder write, and clock skew between executors can only make a takeover early or late. A takeover resumes at the first chunk without a receipt, and the write-once receipt with its checksum stays the check on every chunk. Two stages of different runs that expect the same pointer can both load; the first commit wins and the second aborts on the pointer guard with nothing written (`pointer_moved`); the executor then marks it failed, and it is discarded under the cleanup approval. Following the AIR-165 rule, a write is sent once: a lost response or a `429`/`5xx` on a chunk, validate or commit request stops the run as `write_uncertain`. The next run reads the stage and its receipts. A chunk whose receipt exists with the same `content_sha256` landed whole; a receipt with a different checksum is `chunk_conflict` and stops; a chunk without a receipt did not land (the request is atomic) and is sent once. The executor resumes at the first chunk without a receipt. An uncertain commit is resolved on the next run by reading the final tables: an equal committed generation is a replay; otherwise the stage is still `validated` and is committed then. An uncertain validate is resolved by reading the state. An uncertain claim is not retried either: if it landed, the claim belongs to the stopped execution, and the next run takes it over only after it expired. A changed manifest is a changed baseline: the executor refuses to resume (`stage_baseline_changed`), the stage is abandoned (marked failed) and discarded under the cleanup approval, and the run is staged again from the new baseline. Deletion in the source is not a stage concern: a generation is immutable once committed, and a later generation's commit marks candidates absent.

**Rows and limits.** A staged row is one statement and is never split. A row whose statement would exceed a cap below the per-statement limit (90,000 bytes) stops the unit as `stage_row_too_large` before any write; at the synthetic production size the largest staged statement is 873 bytes. A chunk is cut at whichever limit (statements or bytes) is reached first.

**Schema, code and migration order.** The implementation is a separate atomic card after this design is accepted:

1. `migrations/0002_generation_stage.sql` adds the six staging tables exactly as prototyped. It changes no table of `0001` and no read path. The frozen `0001` stays frozen; the owner applies `0002` to `iptv` and the scratch database under the same approval that creates them (G4), or under a separate approval if they already exist.
2. `src/epg-repository.js` exports the shared projection and adds `openStage`, `stageChunk`, `validateStage`, `commitStage`, `failStage`, `discardStage`, each one buffered request. `publishGeneration` stays as the reference implementation and for small generations; the equality test above keeps them aligned.
3. The executor (`scripts/d1-backfill.mjs`) treats the `generation` unit specially: it stages, validates, reads back and commits it, and records chunk and commit receipts in its run report; the unit's ordinary receipt `(programme.json, sha, programme_generation, run)` is written only after the commit reads back equal, as for every other unit. `batch_too_large` remains for every other unit.
4. The offline importer's parity read-back is unchanged: it reads the final tables, which are identical to what `publishGeneration` writes. The parity report counts staged-but-uncommitted stages as `pending` for the generation unit, never as applied.
5. The D1 contract and the backfill runbook name the staging tables, the stage report fields and the new stop reasons.

**What is not decided here.** Whether the commit fits the D1 duration limit at production size is measured, not assumed (see the GO/NO-GO criteria below); the chunk size is bound to whatever the scratch probe proves; the retention of superseded stages beyond the backfill is decided with shadow writes ([AIR-75](https://trello.com/c/AXPYIVCa)), where the runtime writer may or may not adopt staging.

## Alternatives considered

- **(a) A larger single D1 batch.** Rejected. The unit is 73,500 to 122,500 statements and 63 to 75 MiB against a proven 1,000 statements and 0.95 MB, and its absent-candidate statement (710,511 bytes) exceeds the documented 100,000-byte per-statement limit, so no batch configuration can carry it. Even rewritten with a staged key set, a 100-fold larger request is unproven against the 30-second batch bound and would have to be re-proven on scratch for every growth of the generation.
- **(b) Staging rows in chunks and one atomic set-based commit.** Chosen. Every request stays within the proven size; nothing a reader can see changes before the commit; the commit's statement count and text are fixed; the equality with `publishGeneration` is tested.
- **(c) Shadow generation id in the final tables, activated by moving the pointer.** Rejected. Generation-scoped rows (`film_generation`, `film_show`, `candidate_generation`, `candidate_show`) could be loaded under a not-yet-published run id, but `candidate_generation` and `candidate_show` need their `candidate` parent first, so new candidates would become visible to discovery and decisions before the pointer moved, and the shared projection (`seen_in_latest`, `activity`, evidence-key resets) would still have to change in one request. `programme_generation.phase` admits only `published` or `withheld`, so a loading generation would need a new phase that every reader must learn to exclude, and a failed load would leave partial rows in final tables whose cleanup is a delete on authoritative tables. It also changes the read path, which the backfill must not do.
- **(d) D1 file import (`wrangler d1 execute --file`).** Not adopted. The documented import path is built for whole-database loads; its atomicity for a partial load into a populated database is unproven here, it bypasses the executor's identity fence and receipts, and it would still need the guard and absent-candidate logic.

## Consequences

The generation unit becomes importable at any realistic size within the proven request size, with the same atomicity guarantee as every other unit and an exact, tested equality with the reference writer. The cost is a second schema migration, about 90 to 125 chunk requests for one production generation (at 1.25× today's candidates and two shows each: 90,147 staged statements, 40.6 MB, 95 chunks of at most 445 KB at 950 statements), a read-back of the staged rows before commit, and storage for one extra copy of a generation's rows until the stage is superseded and discarded (at the measured scale roughly the size of one generation, well below the 10 GB database limit). On local SQLite the staging took 3.1 s and the commit 0.7 s at that scale; D1 durably replicates every write and will be slower, so these numbers are a lower bound, not evidence.

The new risks are bounded: a commit that exceeds the D1 duration limit fails atomically and writes nothing, and a stage that is never committed is invisible and removable by a staging-only cleanup.

## Recovery and migration boundary

Nothing in this design writes R2. Before the commit, recovery is staging-only: fail and discard the stage; the final tables never changed. After the commit, the generation is an ordinary committed generation and the ADR-0019 rollback applies (backup, identity fence, drop, re-import from the same verified baseline). Migration `0002` adds tables only; dropping them is reversible as long as no stage is in flight. Applying `0002`, running anything against the scratch database and any production write are each separate, action-specific owner approvals; this ADR authorizes none of them.

### Scratch verification plan (execution only under a separate owner approval)

On the existing isolated scratch D1 only, never `iptv`, with synthetic data generated locally (no production payload):

1. Apply `0001` and `0002` to scratch; seed films and a prior generation of 22,199 candidates through the staged path itself.
2. Stage a second synthetic generation at 1.25× (27,749 candidates, 2 shows each, 2,300 films) in chunks at the proven size; record requests, bytes, durations and any `429`/`5xx`.
3. Interrupt deliberately after an arbitrary chunk; resume; confirm receipts, no duplicate rows and a matching read-back.
4. Commit; record the commit duration reported by D1; read back the final tables and compare with the locally computed expected rows.
5. Repeat the commit request: it must abort and change nothing. Commit a stage with a stale pointer: it must abort and change nothing.
6. Fail and discard a stage in bounded batches; confirm final tables unchanged.

The owner accepted this design on that condition: the 10-second bound at 1.25× is a GO/NO-GO criterion, not a proven capability. GO for the production backfill of the generation unit (part of G4/G5) requires: every chunk request succeeds at the configured size; resume after interruption yields an equal read-back; the commit succeeds at 1.25× in at most 10 seconds (one third of the documented 30-second bound); repeat and stale commits change nothing; discard touches staging only. NO-GO if the commit exceeds 10 seconds or fails on a limit: no production write, and a follow-up design splits the generation-scoped inserts out of the commit before it is retried.
