# Batch runner v2 dry-run A/B procedure (AIR-450 input, proposed)

**Status: proposed procedure, nothing authorized.** This page is the repeatable procedure for the dry-run A/B experiment of [AIR-450](https://trello.com/c/VPd21Y9d)'s scope. Delivered by AIR-449 as documentation. Running it needs the owner's explicit, operation-specific approval. Creating, editing, enabling or running a Scheduled Task, any production `prediction_batch_start` or `prediction_batch_submit` (dry run included), flags and authority changes stay unauthorized until then ([authorization](../process/authorization-and-escalation.md#chatgpt-scheduled-task-authorization)). The dry run writes nothing to prediction state: no lease, run, queue, fingerprint, prediction, version object or view-index entry ([contract](../reference/api/prediction-runner.md#batch-runner-v2-proposed-contract)).

## Frozen manifest (one start, ten passes)

[ADR 0122](../adr/0122-prediction-batch-runner-v2-dual-protocol.md) decision 10: the caller keeps the **one** dry-run manifest it received and replays the same complete film metadata, plans, stored fingerprints, profile and contract at generation sizes 1 to 10, and does not call `batch_start` between passes, because live input moves. So the experiment has two kinds of step:

1. **Freeze (once, owner-run).** The owner, under the AIR-450 approval, runs `prediction_batch_start({trigger:"manual", dryRun:true, pin:{filmIds:[...]}})` once with the frozen sample's ids. The whole answer is the **frozen manifest**: `manifestHash`, `profile` (with its body), `contract` (with the schema), and every film with `plan`, `modelMetadata`, the stored `fingerprint` of a `prediction_only` film and its `inputHash`. Record the sample as `$defs.sample` of [`batch-v2-ab.schema.json`](../reference/scheduled-task-prompts/batch-v2-ab.schema.json) (ids, `frozenAt`, `source`, `approvedBy`, and the `manifestHash` once known). **Size preflight (gate).** The manifest is not shortened: it carries the full `modelMetadata` and every stored fingerprint of a `prediction_only` film, and its whole serialized answer is bounded by `maxManifestBytes` (initial 160 KiB). 100 films do **not** always fit: [AIR-447's measurement](../evidence/prediction/air-447-batch-start-manifest-2026-11-12.md) found 100 metadata-only films within the limit and 100 `prediction_only` films with stored fingerprints over it. If the freeze start answers `409 manifest_too_large`, nothing was created and the experiment stops: report `bytes`, `limit` and `largestFilmBytes` to the owner and wait for an owner-scoped decision on the sample or the limit (the D1 gate on the limit stays open). Do not shorten the manifest, drop or replace films, or retry with another pin to get under the limit. A sample the owner fixes at 100 films is run only if its freeze start fits.
2. **Ten passes (no start).** Each pass is a clean-context run of the `DRY RUN PROMPT` with `SAMPLE_ID`, `GROUP_SIZE` (1 to 10) and `FROZEN_MANIFEST` (the full manifest text, byte for byte the same in all ten) filled in. A pass calls only `prediction_batch_submit(dryRun:true)`: it never calls `prediction_batch_start`, reads nothing, and takes profile, rules, metadata and fingerprints only from the manifest. Run the order 1, 10, 5, then the rest, so a context or quota limit shows early.

**Private handoff and retention.** The manifest carries the Taste Profile body and film metadata, which is private user context. It never goes into this repository, a PR, `docs/evidence/`, a Trello card or comment, a screenshot, a log or an issue. The owner decides how it reaches the ten passes (a private chat or a private note the owner controls) and deletes every copy when the AIR-450 report is accepted. A pass whose manifest fails the check of its step 1 (`manifest_invalid`) is discarded. **Report boundary.** The per-pass `$defs.result` records carry the raw model outputs (`films[].fingerprint` and `films[].prediction`), which are private user taste context like the manifest. The full result records and any raw output stay in the owner-controlled private trial channel or storage the AIR-450 approval names, under the same retention and deletion rule as the manifest. Public `docs/evidence/` may hold only sanitized aggregates: safe sample and film identifiers, `manifestHash`, profile and contract identity, group sizes, the comparison statistics and timings, quota figures and counts per `submitStatus`, and redacted representative examples after a privacy review. No manifest, profile body, film metadata, fingerprint or prediction object is published. AIR-449 stores no real record.

## Calls (exact)

```
prediction_batch_start({trigger:"manual", dryRun:true, pin:{filmIds:[...]}})   // once in total, by the freeze step; never inside a pass
prediction_batch_submit({runId:"dry-run", epoch:1, dryRun:true, manifestHash, items:[{filmId, fingerprint?, prediction, inputHash}, ...]})   // in a pass: 1..GROUP_SIZE items
```

`runId` and `epoch` are required by the MCP schema and by the Worker even in a dry run, and the frozen manifest has no run, so the fixed synthetic pair `"dry-run"` and `1` is used. The Worker's dry-run branch never dereferences a run. `manifestHash` and each item's `inputHash` come from the frozen manifest, so the Worker reports per film whether the live input is still the manifest's (`liveInput`). A group over 56 KiB is refused by the MCP tool with nothing submitted: that is itself a result (record it, resubmit one film at a time).

## Output contract

Each pass ends with one JSON object shaped as `$defs.result` of the schema: identity (`sampleId`, `groupSize`, `manifestHash`, profile and contract identity), per-film records (`plan`, `groupIndex`, the generated `fingerprint` and `prediction`, `submitStatus`, `liveInput`, sanitized `validation`, `generationMs`), per-call records (`itemCount`, `bodyBytes`, `toolMs`, `ok`) and `telemetry` (model, tokens, quota before and after, wall time). A value the platform does not show is `null` and its name goes into `telemetry.unavailable`; nothing is estimated. The pass returns it in the chat and the pass itself saves nothing; the owner copies it to the approved private location above, never to the repository and never as a screenshot.

## Comparison criteria

1. **Same input.** All ten results carry the same `sampleId`, `manifestHash`, profile and contract identity, and every film `liveInput` is `same`. Because no pass starts anew, a different `manifestHash` means the wrong manifest was pasted: discard and rerun that pass. A `liveInput` of `changed` means the live queue or catalog moved after the freeze; report it, it does not alter the frozen replay.
2. **Reliability per size.** Share of films per `submitStatus` (`would_write` against `validation_failure`), the issue paths and codes that recur, and groups refused for size.
3. **Quality against the size-1 pass.** For each film present in both: the absolute difference of `predictedRating` and `probability4Plus`, agreement of `confidence`, and whether the fingerprint evidence map validates. Report the distribution (median, p90, maximum), not one average. Only a stable result across sizes supports a larger `generationSize`; a drift that grows with the size is a finding against it.
4. **Model cost against tool latency.** Model generation (`generationMs`, or `wallMs` minus the sum of `toolMs`) is reported separately from MCP and Worker latency (`toolMs`) so a slow model is not read as a slow Worker. Where only `wallMs` is visible, say so.
5. **Quota.** Quota before and after each pass, and tokens where shown, per film and per pass. Unavailable stays unavailable.
6. **Decision output.** A table of the ten sizes against 2–5 and a recommended `generationSize` with the evidence. The owner decides the value; the Worker's range stays 1–10.

## Not part of this procedure

Any non-dry-run call, a Scheduled Task, an installed prompt, a production write, flags and the cutover (AIR-451). The [bounded-run signal](../reference/scheduled-task-prompts/hourly-predictions-batch-v2.md#owner-activation-gate-bounded-run-signal) is a separate owner decision before activation.
