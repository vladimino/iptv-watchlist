## Decision: what the in-batch applied update checks (12 Nov 2026)

The first version matched the pending row on `request_id`, `state` and `attempts` only and used the target solely to read the revision, so a valid mark for entity B could carry the request id and attempt of entity A's pending receipt and falsely mark A `applied` at B's revision. The update now also requires, on the STORED row:

- `target_kind = ? AND target_id = ?` (the entity the writer bumps; the immutable-target trigger fixes these columns, so the stored value is the authority, not the mark);
- `planned_revision + 1 = revision of that entity after the writer's bump`. The writer's own `REVISION` assertion has already proven the revision before the bump equals the writer's `expectedRevision`, and the bump adds one, so the predicate says `planned_revision = expectedRevision`: the receipt is applied only at the revision it was planned against plus one, the same rule `validEvidence` uses for readback (`appliedRevision = plannedRevision + 1`). On a retry the receipt module first moves `planned_revision` to the current revision (after `revalidate` says `proceed`) and hands that same value to `run` as `currentRevision`, so the writer's expected revision and the stored plan stay equal and the rule needs no retry special case; a retry that skipped re-planning is refused;
- `marker_generation = live marker generation`. The batch's `FENCE` statement already asserts the live generation equals the generation the writer read, so the check is a SQL comparison with the live row and needs no new parameter. This is a conservative rule: a receipt planned under an older generation (a hold and re-open since planning) is not applied by a writer fenced to the newer one. A retry re-plans it under the live generation first (trigger `canonical_write_receipt_generation`). I enforce it because the insert and retry triggers already treat a plan under an older generation as stale; a producer that sees `film_person_precondition` re-reads and retries.

Every mismatch updates no row, so the `changes()>=1` assertion fails and the whole batch rolls back (entity rows, revision and receipt). The failure surfaces as `film_person_precondition` (revision and fence are unchanged when it is read back). The rule is in the shared tail, so all nine writers carry it; no statement was added (the tail is still 2, outside `MUTATION_STATEMENT_CAP`) and behaviour without a mark is unchanged. This tightens the existing ADR 0119 decision 4 ("the applied mark is inside the writer's batch and fails closed") without a new decision, so no new ADR; ADR 0119 states the rule in one added sentence.
