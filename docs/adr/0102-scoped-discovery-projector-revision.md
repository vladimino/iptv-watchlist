# ADR 0102: The D1 enrichment projector takes a coherent cut of the Discovery inputs under a scoped revision and applies each entity only if its sources and target are still current

## Context

The projector pins the global Discovery authority generation before it reads and requires the same value right before its first write. The whole diff phase sits between the two points (21.2 s on the 2026-11-08 08:37 UTC run, 10.6 s of it reading). Discovery bumps that generation about 17 times a minute, so the pin almost never holds: the projector has written nothing since 2026-11-08 02:38 UTC and no Film since 2026-11-05 ([evidence](../evidence/d1-migration/air-373-baseline-inventory-2026-11-08.md)).

Three measured facts shape the decision ([audit](../evidence/d1-migration/air-385-projector-scope-audit-2026-11-08.md)):

1. A bounded retry of the whole phase cannot help: with 17 bumps a minute the chance that a 10.6 s window is stable is 5 %, and 0.25 % for the 21 s phase (AIR-383).
2. A scoped revision that still has to be **unchanged** across the phase is not enough either. About 10 of the 17 bumps a minute are real writes to `discovery_decision` or `discovery_admission`, the only two Discovery tables the projector reads. Removing the other 7 leaves a stable-window probability of about 3 % for 21 s.
3. The reader is not key-local. The catalog loop links every record against the Films already built, in id order (`src/domain/film-person-reader.js`), so "which Discovery rows can change Film F" cannot be assumed; it has to be derived and proven.

The projector's write batches today reference no Discovery state at all. The only post-diff check is one handoff guard before the first batch, and the write phase may last 60 s.

## Decision

The projector keeps a strict guarantee, and changes where it is enforced. It no longer demands that the world stays unchanged for the whole phase. It demands (a) a coherent cut of the Discovery inputs, proven by a short revision bracket around the read alone, and (b) for every entity it writes, a predicate check, inside that entity's own fenced batch, that the exact sources it was derived from and the target it replaces are still the ones it saw. An entity that fails (b) is skipped and retried on the next natural tick; it is never written from a stale plan. Everything the projector cannot prove fresh fails closed.

1. **Scope identity and a scoped revision.** The scope of the projector's Discovery inputs is `(programme_run_id, projection_revision)` on the single `discovery_authority` row. Proposed DDL, not a migration file and not applied: additive columns `projection_revision INTEGER NOT NULL DEFAULT 0` on `discovery_authority` and `written_revision INTEGER NOT NULL DEFAULT 0` on `discovery_admission` and `discovery_decision`, with a `schema_contract` bump and the precondition style of migrations `0013` and `0017`. The revision rises **in the same `UPDATE` that bumps `generation`**, in the same `db.batch`, behind the same lease and CAS, and only in batches that write projector-relevant data (below). Because the bump statement precedes the data statements and `FENCE_SQL` aborts the batch when it changed no row, a relevant write cannot commit without its bump. **Every relevant data statement in that batch also stamps the row's `written_revision` from `(SELECT projection_revision FROM discovery_authority WHERE id=1)`, evaluated after the bump in the same batch**, so the stamp is the exact post-bump revision of that batch, unique per batch and never stale. This is the durable, monotonic per-row mutation token the projector validates; the content `decision_hash`, the existing `generation` stamp (taken from a gate that a multi-flush load reads once and later flushes overtake) and the `discovery_decision_history` revision are **not** version tokens and are never used as one. Rows written before the migration carry `0`.
   - **Relevant:** any insert, update or delete of `discovery_admission` or `discovery_decision` rows, any move of `programme_run_id` or `published_programme_run_id` (a handoff or publish), and any activation or hold transition of the marker. The full path-by-path table is in the [audit](../evidence/d1-migration/air-385-projector-scope-audit-2026-11-08.md#3-writers-of-the-projectors-discovery-inputs): rows 3 to 8 and the programme move of rows 13 and 16, plus offline imports and resets (S3, S4, S5), which today change the data without any bump and must stamp the revision.
   - **Irrelevant:** status, checkpoint, score, continuation, workflow, lease, intent, observation-ledger and segment writes. They keep bumping the global generation and leave the revision alone.
   - **Coverage is enforced by construction, not by reading.** `fence()` and `loadingFence()` take a required descriptor (`relevant` or `irrelevant`) with no default; a call without it throws. A structural test scans every SQL string in `src/` and `scripts/` and fails when a statement that writes `discovery_admission`, `discovery_decision`, or the programme ids is reachable from a batch built without the `relevant` descriptor. A writer missed by this test is the one residual risk; decision 3(b) is the second line of defence against it.
   - **No runtime deletion.** No runtime path deletes a `discovery_admission` or `discovery_decision` row today (supersession is an update). A structural test keeps it that way; the only deleting code is the offline `--reset-import` (S5), which runs only in mode `r2` and must bump the revision. A row that is ever deleted and re-inserted is stamped with a later revision than any value a cut can hold, so a delete/reinsert is detected as a change, never as the original row.
   - **Arming and the zero default.** `written_revision` and `projection_revision` start at `0`, and a `0` stamp can never exceed a cut revision, so a writer that does not stamp would be invisible. The dormant stage therefore adds `projection_armed INTEGER NOT NULL DEFAULT 0` to the marker row. The projector refuses to take a cut (`scope_unarmed`, fail closed, `deferred`) until the marker is armed. Arming is a separate fenced owner-GO step that may run only after (i) the stamping code is live in every writer (the Discovery Workflow, the paged and document resolvers, the owner routes, the seal and publish paths) and the structural coverage test is green on that exact code, and (ii) the migration is applied. A cut taken after arming reads every row as it then stands, so rows changed before arming are part of the cut, and every later write is stamped above any `R0` taken after arming. Offline writers S3, S4 and S5 stamp and bump too.
2. **A coherent cut.** The projector reads the Discovery inputs in one bracket:
   `M1 = read marker` → read catalog and decisions (paged and bounded, see AIR-386) → `M2 = read marker`.
   The cut is accepted only if `M1` and `M2` agree on `mode`, `cutover`, `programme_run_id` and `projection_revision`, the marker is not `held`, and `transfer` is not `loading` at either end. The cut does **not** rely on a D1 `batch` being a snapshot: the batch is documented as a transaction, but nothing in this repository proves that for reads, so the revision bracket is the proof and a snapshot property, if later verified, is only an optimization. On a failed bracket the projector retries **the cut only**, at most three attempts with bounded jittered backoff and no busy loop, each attempt re-reading marker, catalog and decisions from scratch; exhausting them ends the run as `deferred` with reason `cut_unstable`, never as success. The unchanged-revision requirement therefore covers the Discovery read alone (seconds), not the 21 s phase. The model in the audit gives 72 % per attempt for 2 s and 44 % for 5 s at 10 relevant writes a minute, 98 % and 82 % with three attempts. The read duration is **not measured**; the implementation card measures it in `dry` before any `on` run. **Abort gate:** if the measured p95 duration of the cut (with AIR-386's bounded reads) exceeds 5 seconds, or more than 20 % of `dry` ticks end `cut_unstable`, stage (b) does not proceed to `on`; the fallbacks are the materialized snapshot of the alternatives below or the owner-approved Discovery pause. These thresholds are proposals for the implementation card to confirm.
   The other inputs keep their own brackets (published-EPG generation, owner-review marker generation), and the D1 metadata cache read, which has none, gains a `cache_generation` bracket. **R2 sources are fenced only by an enrolled writer protocol; polling is not a fence.** A D1 batch cannot read an R2 etag atomically with its own statements, and re-checking etags every few seconds leaves an R2 write landing between the last check and a batch commit, so a bounded re-check window is **rejected as a safety fence** and may remain only as defence in depth. The normative protocol is a verified seqlock in D1: a `source_epoch` row per R2 source group (`metadata`, `titles`, `people`, `view_index`, `verified_films`, `tmdb_retirements`, `diary_history`, `owner_review_mirror`, and every other R2 object `d1EnrichmentStore` reads), with `epoch`, `state` (`idle` or `writing`), a writer lease with expiry and the recorded R2 version after the last completed write. Every R2 writer of a source group is **enrolled** and runs **begin** (one D1 CAS: `idle` to `writing`, lease taken, `epoch` odd) → **mutate** the R2 object → **finalize** (one D1 CAS: record the new R2 etag and version, `writing` to `idle`, `epoch` even and increased). The projector reads the epochs and requires `idle` before reading any R2 source (`writing` defers, fail closed), reads the R2 sources, re-reads the epochs and compares the R2 versions with the recorded ones after completion, and every write batch asserts in D1 that each epoch is still `idle` and equal to the value pinned at the cut. An epoch bumped only after an R2 put would leave the same race, which is why `begin` precedes the put. The `begin` row records the pre-put R2 etag. The projector records, for each source group, the pinned `(epoch, recorded R2 version)` pair and the R2 version it read, and the run summary reports that set (no payloads) as the end-to-end source versions. In D1 cache mode the metadata cache already fences its own writes on `metadata_cache_authority.cache_generation`; that single D1 CAS is the `metadata` group's epoch while the marker is `d1` (there is no R2 mutation to bracket), the pinned `cache_generation` is asserted in every batch, and the R2 `metadata.json` group applies only while the marker is not `d1`. A writer that dies between `begin` and `finalize` leaves the source `writing`; the projector treats an expired `writing` as fail closed (`source_epoch_stale`), never as idle, and recovery is an owner repair procedure, and it is **permitted only after the original writer is verified quiescent**. An expired D1 lease, a timeout or an unknown outcome is **never** evidence that the writer has stopped: a paused or stalled former writer can still execute its R2 put after a repair has set `idle` and raised the epoch, and a D1 compare-and-swap cannot fence an out-of-band R2 put by a live former writer (a conditional put on the `begin` etag does not help when the object is unchanged since `begin`, and no storage-level fencing of late puts is established by this ADR). Quiescence is therefore verified, not inferred: the owner confirms from an independent source that the writer's invocation or Workflow instance has ended (for example Worker observability and the Workflow instance list) before any repair. Only then does the repair take a repair lease, read the current R2 etag, compare it with the one recorded at `begin`, and run `finalize` with the etag it found (changed or not), which always increases the epoch so every cut taken before is invalid. A crash during `finalize` is a failed single CAS and leaves `writing`, handled the same way. **Without verified quiescence the source stays `writing` (held), the projector keeps failing closed, and stage (b) stays off.** That cost is accepted. **Normative fail-closed rule:** if any R2 writer of a read source is not enrolled, or the protocol has not been demonstrated by deterministic tests including a crash between `begin` and `finalize`, stage (b) stays `off`; a 2-second window is never an acceptable default. The cross-source assumption that no single writer step changes both a relevant Discovery row and an R2 or cache source is re-verified by the implementation card.
3. **Two guards in every write batch.** Each batch keeps the lease fence as its first statement and adds:
   - **(a) A global guard.** The batch asserts that the `discovery_authority` row still has `mode='d1'`, `cutover='open'` and the pinned `programme_run_id`, that `discovery_transfer.state` is not `loading`, that the published-EPG generation (and, in D1 mode, the metadata cache and owner-review generations) still equal the pinned values. Failure stops the run. The projector then re-reads the lease and the marker to classify the cause (lease lost, authority moved, handoff) and ends `deferred` or `lease_lost`; it never keeps writing and never reports success. Classification is by re-read, not by parsing the CHECK-failure message, which today sets `leaseLost` for any CHECK failure.
   - **(b) A per-entity guard.** Before the entity's rows, the batch asserts the **predicate** of that entity (decision 4) and its **target** (decision 5). A failed predicate rolls the whole batch back (nothing written, the change key not advanced) and the projector records `skippedStale` and goes on with the next entity. An unchanged revision is not required; a changed source of this entity is fatal for this entity only.
   - **Releases are revalidated in a fresh, short cut; ordering alone is not a safeguard.** A release (`releaseFilm`, membership removal) is a negative claim, so it never relies on the diff's cut, which is about 21 s old. For the release candidates of a run (at most 25, by the existing `absent_guard`) the projector takes a **fresh release cut after the diff and before the first release batch**: it re-reads the marker (`M1'`), reads in one batched, indexed `SELECT` the `discovery_admission` rows by `film_id` and `(media_kind, tmdb_id)` and the `discovery_decision` rows by `film_id`, `tmdb_id` and `observation_key` for every candidate's closure keys, re-reads the marker (`M2'`), re-verifies the R2 etags and the published-EPG generation, and confirms that no source lists the candidate. The release batch then asserts the global guard and that no row in the candidate's closure keys has `written_revision` above the revision `R1` of the fresh cut. The window between `R1` and the commit is one batch read plus one batch, about a second, so the model gives 85 % per attempt at 1 s before the key scoping, and close to 100 % once the check is limited to the candidate's own keys, which an unrelated Discovery write never touches. A candidate whose keys a relevant write did touch is skipped (`skippedStale`, kind release) and decided afresh next tick. If the closure of a class of Film cannot be shown complete (S1), its release is **not performed**: it is reported as `release_unprovable` with the age of the oldest pending release, and the owner's fallbacks apply (a reload, as ADR 0056 prescribes for an intended mass removal, or the Discovery pause). **No-perpetual-starvation check:** a deterministic seeded simulation of 1,000 ticks with 17 global and 10 relevant writes a minute, none touching the candidates' keys, must apply at least 99 % of release batches in their first tick, and a candidate whose keys are touched must apply within a bounded number of ticks once they stop being touched. The existing `absent_guard` and `membership_guard` stay as they are.
   - **Unprovable classes fail closed or compare against the original cut.** An entity whose dependencies cannot be established, or exceed the cap (64 keys, to be tuned), is **never** validated against a fresh cut, because a fresh marker read cannot refresh a plan that was computed from `R0`. It is written only if `projection_revision` still equals the original `R0` at commit (no relevant write at all since the diff's cut) and is otherwise skipped and reported as `strict_stale`; its starvation is visible as a count and an age, and the owner's fallbacks apply. The only item revalidated against a fresh cut is a release candidate, whose fresh read explicitly re-evaluates the negative claim and is contingent on closure completeness (above). A deterministic test requires that a relevant source mutation between the original diff cut and any later fresh cut never lets a stale entity apply.
4. **Per-entity predicates are derived and tested, not assumed.** For each planned entity the plan carries a dependency set made of the lookups its derivation performed on the Discovery inputs, split into two kinds. **Identity hits** are every row the derivation was *returned*, whichever way it was looked up: the projector records the stable primary key (a `discovery_admission` row by `film_id`, a `discovery_decision` row by `observation_key`) and the `written_revision` of **each returned row, including rows returned by a secondary or membership lookup that never queried the primary key**. This is a normative invariant, not a reading of the lookup: a row matched by `tmdb_id=X` at the cut and later updated to `tmdb_id=Y` is still asserted by its primary key, so the guard fails although the current membership of `X` is empty. **Membership lookups** are, in addition, the questions asked by a non-primary key, hits and misses alike, recorded to catch **new arrivals**: an admission by `(media_kind, tmdb_id)`, a decision by `film_id` or `tmdb_id`. With `R0` the revision of the cut, the guard asserts (a) that **every identity-hit row has `written_revision` not above `R0`** (so a row that was updated to move away from the key it was found under is still caught by its primary key), and (b) that **no row currently matching any membership key has `written_revision` above `R0`** (so a row that appears, or moves into a key, after the cut is caught, and a miss stays a miss). A row cannot disappear because no runtime path deletes these rows (decision 1). Because `written_revision` is the post-bump revision of the writing batch, it exceeds `R0` for every write after the cut and cannot return to an earlier value: a decision that changes A to B and back to A, a row that is deleted and re-inserted, a row inserted after the cut, and a rewrite of identical content all fail the guard (the last conservatively). The content hash of a decision is still verified for payload integrity on read, but it is not the version. Each statement stays below `BIND_CAP` (100 parameters) and each batch below `STATEMENT_CAP` (40 statements). The projector's soundness rests on two conditions the implementation card must establish with deterministic tests before the switch can leave `off`; they are **tests, not proofs**, because the reader's catalog loop is order-dependent and not key-local:
   - **S1, completeness of the read set:** an instrumented (test-only) store records every Discovery lookup the reader and projection make for each entity; the plan's dependency set must equal it, including misses. It runs over **every** entity of the offline snapshot, not a sample, and over fixtures for ordering, linking, archive-stub replacement and redirects.
   - **S2, perturbation:** over a seeded sample of entities and of mutations to Discovery rows, a mutation whose keys are disjoint from an entity's dependency set never changes that entity's change key, and a mutation that touches the set always changes the key or fails the guard. Because it samples, it can falsify the claim but not prove it; it is complemented by the exhaustive S1 and by the strict fallback below. Required cases include key-change fixtures (a decision whose `film_id` or `tmdb_id` is changed away from, and into, an entity's keys), a decision changing A to B to A, a delete and re-insert of the same payload, a row inserted after the cut under a looked-up key, and a catalog record that arrives with the same TMDB id as an existing Film.
   Any class of entity that fails S1 or S2 is marked strict until the reader is fixed: it is written only if `projection_revision` still equals the **original** cut revision `R0` at commit, or it fails closed (decision 3). A fallback never refreshes only the marker. Persons derive from credits on catalog records, so their set is the ids of the catalog records that carry them; a failed 25-Person batch falls back to single Persons, which isolates the stale ones.
5. **Target compare-and-swap.** The batch also asserts that the entity it replaces is what the plan was computed against: the `projection_state` change key read at the cut (absent for a new entity) and, once rows exist, the entity's `canonical_revision` ([ADR 0099](0099-canonical-film-person-d1-authority.md), schema `0013`). A changed Film is never overwritten, new credits or aliases are never dropped by a stale plan, and a redirect or link batch asserts both Films plus the union of their predicates. The D1-only credit renumbering stays inside the same batch as today. **Normative fail-closed rule (a blocker for stage (b)):** every non-projector writer of Film, Person, credit, alias, localization or link rows must be enumerated in a machine-checked writer registry, and each must either bump the entity's `canonical_revision` atomically in its own batch or be demonstrably mutually excluded from running while a projector lease is live (by the lease or the marker). The enumeration starts with the AIR-286 credit script, the offline importer and the AIR-373 baseline tooling, owner-review localization, `projectLink` callers and any `d1-backfill` script; this ADR does not trace them and leaves the enumeration to the implementation card **only because this rule is normative**: with any writer outside the registry, or any registered writer neither bumping nor excluded, the projector must refuse the switch and stay on the strict protocol.
6. **Unknown outcomes are not retried.** A batch error that is a definite rollback (a CHECK or constraint failure) is classified as above. Any other error, a timeout or a lost response, has an unknown outcome: the projector stops writing for the run, reports it, and does not retry in the run. The next tick's diff is the readback, because every change key is written in the same batch as its rows.
7. **Observability.** The run summary gains bounded, payload-free fields: `cut` (attempts, milliseconds, `programmeRunId`, `scopeRevision`), `applied` and `skippedStale` by kind (Film, Person, release, strict), `unknownOutcome`, `revisionAtStart`, `revisionAtEnd`, and the new deferred reasons `cut_unstable` and `authority_moved`. Durable progress and the age of the last write remain derivable from `projection_state.projected_at` and `remaining`. A perpetual `deferred`, `skippedStale` or `cut_unstable` is a non-success outcome and stays visible; nothing masks it. [The enrichment API reference](../reference/api/enrichment.md) is updated by the implementation cards, not by this record.
8. **Staged delivery, each stage its own card and approval.** (a) Dormant: schema proposal, `projection_revision`, the required descriptor on every writer, the structural coverage test, the `written_revision` stamping and the `projection_armed` marker, the stamping of S3, S4 and S5, the `source_epoch` table and the enrolment of every R2 writer of a read source in the begin/mutate/finalize protocol, and the machine-checked registry of non-projector canonical writers; the revision is written, and read by nothing but the structural tests. (b) Projector switch: the coherent cut, the two guards, the observability, the S1 and S2 tests and the deterministic fixtures below, behind a new flag that defaults off (registered in the [flag contract](../reference/feature-flags.md)); `off` keeps today's strict protocol. (c) Explicit production schema apply and flag activation, each with an owner GO. (d) Post-deploy read-only natural acceptance under active Discovery: several consecutive ticks with Film and Person writes, a falling or explained `remaining`, no `leaseLost`, no unexplained `skippedStale`. [AIR-386](https://trello.com/c/z4tQryUa) (bounded, keyset-paged reads of the decisions, merged on `main`) is the prerequisite of (b) that makes the cut readable. Nothing here starts any of them.
9. **Required deterministic tests** (named so a reviewer can check the implementation cards against this list): 17 global and 10 relevant writes a minute with a productive projector; a relevant change to the entity being written stops that entity and no other; an unrelated entity changing mid-run does not block; a release whose keys a relevant write touched is skipped and one whose keys were untouched applies in its first tick (the seeded 1,000-tick starvation check); a decision changing A to B to A and a delete/reinsert of the same payload both fail the guard; a row inserted after the cut under a looked-up key fails it; the structural no-runtime-delete check; a relevant source mutation between the diff cut and a later fresh cut never applies a stale unprovable entity; an R2 write between begin and finalize, a crashed writer left `writing`, a paused writer whose D1 lease expired, followed by a repair and then a late R2 put by that former writer (which must fail closed: the source stays held until quiescence is verified, and no test may infer quiescence from lease expiry or an unknown outcome), an unenrolled R2 writer and a source epoch that moved between the cut and a batch each fail closed; an update that moves a row away from a lookup key is caught through its primary key, including a row that was returned by a secondary lookup only and never read by primary key; an unarmed marker refuses the cut; redirects and links; a changed R2 etag; changed owner review and metadata; a new published programme or handoff mid-run; a held or unreadable marker; transfer `loading`; a lost lease; a CAS conflict on the target; an unknown write outcome (no retry); convergence over several ticks; a failed cut and an exhausted cut budget write nothing and advance no key; the structural writer-coverage test; independence of the monitor, Ratings and Discovery cron from the projector; regression of the AIR-375 D1-owned catalog and decisions read.

**Not decided here:** any schema apply, migration number, flag name, threshold (attempts, backoff, dependency cap), the exact stamping SQL of `written_revision`, the `source_epoch` schema and the list of enrolled writers, the handling of non-projector Film writers (decision 5), or a change to the discovery authority contract of ADR 0085. Nothing in this record is implemented, deployed, activated or verified in production.

## Alternatives considered

- **Bounded retry of the whole read phase (AIR-383).** Rejected: 0.25 % to 5 % per attempt at the measured rate, so it spends CPU and wall time for no liveness.
- **Scoped revision that must stay unchanged until the first write.** Rejected by measurement: about 10 relevant writes a minute leave a stable-window probability of about 3 % for the 21 s phase. It is also what A would give without this ADR's per-entity guards.
- **Write the old plan once the revision has not regressed.** Rejected by the owner: an unconditional stale overwrite of a Film, a lost credit or a destructive release by stale membership is exactly what the strict fence exists to prevent.
- **Content hash or etag of the routed reads instead of a revision.** Rejected: it gives no mutual consistency of catalog and decisions and permits an ABA between the two reads, and it still needs the unchanged window.
- **A materialized snapshot (table or R2 object) of catalog and decisions.** Not rejected on principle. Costlier (extra writes, retention, a second source of truth, proof of consistency with the R2 inputs); kept as the fallback for the cut if the measured read duration makes the cut bracket too long.
- **A bounded re-check of R2 etags every few seconds as the fence.** Rejected as a safety fence: it leaves a write between the last check and a batch commit and so contradicts the rule that a stale plan never overwrites newer data; kept only as defence in depth.
- **Pause Discovery for the projector** ([runbook](../runbooks/d1-projector-discovery-freeze.md)). Kept as the owner-approved fallback only if the S1 and S2 proofs fail for entity classes that matter; it relieves the symptom for a window and leaves the cause. It is never activated automatically.

## Consequences

- Progress under active Discovery is expected to be near-complete per tick, with the stale fraction small: a 60 s write phase sees about ten relevant writes, each touching a handful of entities, so on the order of 1 % of the guards should fail and retry next tick. This is an estimate, to be measured in stage (d).
- New complexity: a required descriptor on every Discovery writer, a read-set instrument and two property tests, a longer write batch (guard statements), a new revision column, a new flag, new summary fields, and cut retries.
- The fence is no longer "nothing changed"; it is "this entity's sources and target did not change, and the authority state is the pinned one". The safety argument moves from a global equality to S1, S2 and the coverage test, so those tests are the contract, not a nicety.
- The projector stays the only canonical writer in `r2` and `prepared` ([ADR 0099](0099-canonical-film-person-d1-authority.md) invariant 11).
- Cost: extra D1 reads per batch for the predicate rows and a few extra statements per entity; the query budget (800) and wall budget (60 s) are re-measured in stage (b).
- A release is revalidated by a fresh short cut over the candidate's own keys, so under continuous Discovery it applies in its first tick unless a relevant write touched exactly those keys. A candidate that cannot be proven (`release_unprovable`) is not released and stays visible with the age of the oldest pending release; the fallbacks are a reload or the Discovery pause. Membership drift is bounded by the existing `absent_guard` and `membership_guard`.
- R2 sources need every writer enrolled in a begin/mutate/finalize epoch protocol, which touches the metadata sync, the view-index, diary and other writers, and adds a fail-closed `writing` state with an owner repair path after a crashed writer. This is the price of a real fence; until it is demonstrated, stage (b) stays off.

## Recovery and migration boundary

Stage (a) is additive and inert: the column is unread, and a code rollback leaves it in place. Stage (b) is gated by a flag that defaults off; unsetting it restores today's strict protocol, which is safe and starves under active Discovery. The projector's own rows written under the new protocol are real writes and a code or flag rollback does not undo them (ADR 0056: Time Travel to a bookmark taken before activation is the only restore). Schema apply and flag activation are separate owner GOs per stage. This ADR never authorizes any of them, and no step here changes a Scheduled Task, cron, lease or Discovery run.
