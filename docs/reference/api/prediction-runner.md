# Continuous prediction runner v5

The same start/next/submit/complete protocol serves manual and scheduled triggers. Read GET /api/enrichment/runner before every launch. Its contract supersedes the obsolete v3 single-batch/deadline instructions. ChatGPT reaches this protocol through the MCP tools in [docs/mcp.md](mcp.md): `enrichment_runner`, `prediction_start`, `prediction_next`, `prediction_submit`, `prediction_heartbeat`, and `prediction_complete`. Those tools fix the scope to `watchlist_all`, the mode to `queued`, and each next/submit step to one film. The HTTP routes remain the contract. The external ChatGPT Scheduled Task was restored by AIR-62, independently of deploying this Worker contract; always verify the live task state, and do not change it without owner approval.

1. POST start with scope watchlist_all, mode queued and trigger scheduled/manual. Supply real known capacity only. Do not impose a total-film or time cap.
2. already_running is a successful no-op: never adopt another trigger's runId. busy is transient contention; retry with bounded backoff, without starting concurrent generation.
3. Read next, generate only requested work using the unchanged schema/profile/scoring rules, and submit each film immediately. Repeat next/submit across batches continuously.
4. Before model calls renew POST heartbeat; renew concurrently every 10 minutes if an individual call can last that long. Checkpoints also renew automatically. A 15-minute persistent R2 CAS lease stores owner/runId, heartbeatAt and expiresAt. Expired owners cannot submit. Crash checkpoints survive takeover.
5. next re-evaluates hot urgency before every selection. Cold may run only while hot has no outstanding work. Model call batching remains disabled. Valid fingerprints/predictions are reused; timeslot changes never invalidate them.
6. Before submit, check the generated fingerprint and prediction against `contract` from GET /api/enrichment/schema (`enrichment_schema`): every required `execution` dimension present, every enum value from its list, `moodLabels` 2–4 labels. An isolated malformed/invalid film output is reported through submit items[].failure.kind (parse_error or validation_error), is persisted as a retryable item failure and must not end the run. A Worker schema rejection is the same retryable item failure and additionally returns `results[].validation` with `stage` and `issues[{path, code}]` naming the field (for example `fingerprint.execution.payoff invalid_enum`, `fingerprint.moodLabels required`); fix that field for the following films and do not resubmit the deferred one in the same run. See [the submit validation contract](enrichment.md#submit-validation-contract). Failed items are skipped within that run and deferred by a 1-hour exponential retry (maximum 6 hours). Five consecutive distinct format failures trigger format_error_storm. mustComplete means call complete with stopReason. At actual quota/model/API/storage error, complete with a short safe reason and retain all saved predictions. No credentials in outputs, URLs, Events or persisted error reasons. A killed process recovers through lease expiry.
7. Progress Events aggregate the run every 50 successful predictions or 30 minutes, whichever comes first; the final event is separate. Check heartbeat/next/submit to emit time-based progress during active work. Successful empty checks don't spam Events. Eligible queue exhaustion with deferred item retries is a normal completion, not a run interruption.
8. A formed response does not prove the client received it. Send or read `X-Request-Id`; the same id is returned as `requestId`. On an external or systemic stop, `complete` may include `fault` (`origin`, `failedStep`, `providerErrorCode`, `httpStatus`, `receivedRequestId`). Omit `fault` when the cause is unknown. A fault on `queue_empty` or another normal completion is rejected. `receivedRequestId` acknowledges only the matching step. `firstNextAt` is not a successful `next`. See [AIR-88](run-diagnostics.md).

Run counters and film outcomes persist after each submission. Current-batch film reads stay bounded; completed batches are counted from saved outcomes rather than loading every completed film on every next request.

Tests: node tests/continuous-drain.mjs; node tests/throughput.mjs; node tests/enrichment.mjs. The multi-batch integration test uses an isolated R2 implementation and deterministic validated model outputs; it is not a production LLM throughput benchmark.
