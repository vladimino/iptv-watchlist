# Catalog poster hydration: maintenance procedure (owner approval required)

Catalog-only films offered in the «Находки» section show the year placeholder when their catalog record has `poster: null` and the `metadata.json` fallback has nothing for them. The decisions are [ADR 0020](../adr/0020-owner-triggered-catalog-poster-hydration.md) and [ADR 0048](../adr/0048-permanent-catalog-poster-maintenance-route.md); the route, outcomes and write rules are in the [catalog reference](../reference/api/catalog.md#poster-hydration). This page is the procedure. The route is a permanent owner-only maintenance tool for restoring posters, for example after a mass TMDB discovery failure; it has no switch of its own (the former `CATALOG_POSTER_HYDRATION` is retired and inert). Access is the Worker's owner-only Cloudflare Access. Every execution call in production is a separate operation needing explicit owner approval; a code deploy approves none. It is a bounded manual operation, never a schedule. The owner page `/admin/posters` runs the same steps through the same route, with its own preview, confirmation and receipt ([below](#through-the-admin-page)); the direct calls of the plan stay valid.

## Plan

1. **Read-only count.** `POST /api/enrichment/catalog/posters` with `{}` through the Access-protected site, from the same origin. Record `programmeRunId`, `catalogRecords`, `missingPoster`, `verifiedMissing`, `unverifiedMissing` and the sampled `ids`. No TMDB request and no write happen. `unverifiedMissing` records are out of scope for this procedure.
2. **Bounded calls until `done`.** Under the execution approval, call `{"dryRun": false, "limit": 10}`, then repeat with `"cursor"` set to the returned `nextCursor` (an empty string means "start again at the first record"). Stop with success when a response has `done: true` (`nextCursor` is then `null`). Keep the per-film `outcomes` and `writes` of every call as the receipt.
   - A `409` with `Resolver is writing the catalog`: wait for the discovery chunk to finish and repeat the same call; never override the lease.
   - `rate_limited` with `retryAt`: wait until `retryAt`, then repeat the same call.
   - `generationChanged: true` or `leaseLost: true`: repeat the same call later. Look at `writes`: a copy written before the stop already holds correct posters; the next call re-reads both copies and completes the other one.
   - To keep a sequence of calls on the generation recorded in step 1, add `"expectedProgrammeRunId": "<programmeRunId>"` to every call. Once another generation is published the route answers `409` `Programme generation changed` before any TMDB request and any write; start again from step 1 for the new generation.
   - **Attempt bound:** stop after at most 5 consecutive calls that hydrate nothing and return the same `nextCursor`, or after 30 calls in total. Report the `retryable` ids of the last response with their outcomes (`tmdb_failed` errors, `catalog_changed`, …) to the owner. Do not skip a retryable record by editing the cursor without a separate decision; `done` is only meaningful for a cursor chain that started without a cursor.
   - `no_poster_on_tmdb` and `tmdb_id_mismatch` are terminal: those films keep the placeholder by design and are listed in the receipt.
3. **Read-only verification.** `GET /api/catalog/available`: `posterCoverage.catalog` grows by the hydrated films that are currently available and `missing` shrinks; for the films the owner reported, `films[].poster` is a URL. A repeated step 1 shows the new `verifiedMissing`. Then the owner's visual smoke on desktop and mobile: at least some «Находки» cards show an image instead of the year.

## Through the admin page

`/admin/posters` ([reference](../reference/api/admin.md#poster-coverage)) is the same plan with the bounds built in. It is behind the same Cloudflare Access; it never configures the TMDB token, never touches the discovery lease itself and has no flag. Every confirmed run in production is still a separate owner-approved operation.

1. **Read-only count.** Opening the page, changing an option or «Проверить заново» is one `GET /api/admin/posters`: the counts of step 1, the restorable records and the ones without a verified TMDB id, and the first batch the next call would process. Nothing is written and TMDB is not called. A warning appears when 20 or more records are restorable. When the generation pointer, the live catalog or the generation copy is missing or unreadable the page says «Покрытие неизвестно: данные неполные», names what is missing and offers no run; the page does not create or repair those objects, and restoring them is a separate approved operation, not part of this procedure.
2. **Bounded calls.** Choose the batch size (at most 10), the call budget (at most 30) and the start (the position the last run in this browser saved for this generation, or the start of the queue), tick the confirmation of that exact scope and press «Запустить». The page re-reads the queue first and refuses, with nothing sent, when the generation or the first batch changed. It then sends the calls of step 2 one after another, each bound to the confirmed generation with `expectedProgrammeRunId` (a generation published meanwhile is refused by the route before TMDB and before any write), and stops by itself on `done`, the budget, five idle calls, `retryAt` (the next preview waits until then), a generation change, a busy or lost resolver lease, `TMDB is not configured`, a rejected request, or any answer it cannot read. «Остановить после текущего пакета» stops between calls.
3. **Receipt and verification.** Each film name in the preview and the receipt opens its TMDB page in a new tab, which is how a `no_poster_on_tmdb` or `tmdb_id_mismatch` verdict is checked by hand; records without a verified TMDB id have no link. The receipt lists the stop reason, the totals, every record's latest outcome and, under «Технические подробности», every call with its writes per copy; a partial write between the two copies is named. The page re-reads the coverage and shows before → after. Keep the receipt text as the operation record, then do the read-only verification of step 3 above.

After an unknown result (a network failure or an unreadable answer) the page keeps the previous saved position and asks for a re-check: the call may or may not have written, and a repeated call is harmless (`already_present`). The page's run history is kept only in that browser.

## Failure recovery

The two catalog copies are separate R2 objects and are not written atomically together. A call that stops between them leaves the published generation's copy with the poster and the live catalog without it; the response reports it per copy (`writes`) and per record (`writtenTo`). Nothing has to be undone: the poster is the TMDB asset of the record's verified id. The next call re-reads both copies, writes the missing one or reports the record again. A call that stops before the first write wrote nothing.

## Rollback

To stop, make no further execution call; nothing runs by itself. Posters already written stay: each is the TMDB asset of the record's verified id, in the same form the discovery writer stores, and nothing else in the record changed. Removing them would be a separate approved write that sets `poster` back to `null` for the listed ids from the receipts; no deletion step is part of this procedure. The route never writes the generation pointer, identity, shows or decisions, so there is nothing else to restore.

A code revert to a release that reads the former switch needs `CATALOG_POSTER_HYDRATION=on` restored on Worker `iptv` (owner authorization) before any execution call there; without it that code answers `409 Catalog poster hydration is off`. The dry run works either way.

## When to use

When the read-only count shows verified records without a poster that matter to the owner, typically after a mass TMDB discovery failure. Each run needs the owner's approval of the execution calls, then the owner's visual smoke with at least some posters visible. Films without a stored asset keep the placeholder until a run fills them. A recurring or scheduled hydration is not part of this procedure.
