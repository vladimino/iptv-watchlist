# ADR 0208: Where the durable evidence of a Canonical Producer outcome lives until its Events Log entry is delivered

**Status:** Accepted (option B)  
**Original decision date:** 2026-11-24  
**Recorded at:** 2026-11-24  
**Approval source:** [Product Owner decision of 2026-11-24, recorded by the coordinator](https://github.com/vladimino/iptv-watchlist/pull/976#issuecomment-7128839612) (the owner approved the revised ADR at `658590ab` as presented, «в таком виде утверждаю»: option B, indefinite retention, the fenced `held` outcome, the scoped read-only Monitor fact)  
**Related work:** [AIR-594](https://trello.com/c/iPaLDfzP), [PR #976](https://github.com/vladimino/iptv-watchlist/pull/976), [independent review of `d1ca719c`](https://github.com/vladimino/iptv-watchlist/pull/976#pullrequestreview-6037146819)  
**Supersedes:** None

## Context

AIR-594 adds the Events Log type `canonical_producer` («Обогащение каталога»): one report per logical Producer outcome. An outcome is a completed pass `P:g` (chain `complete`, written in the same batch as the run's `passed` claim), a recorded stop `(P, owner epoch)` (chain `stopped`), or an in-flight chain (`pending`, `active`, `released`) superseded by a newer publication. The event identities, fields, run-versus-chain semantics and display are in the [events reference](../reference/domain/events.md#canonical-producer-outcome-report-canonical_producer) and are not what this ADR decides.

The difficulty is the evidence. The chain row (`canonical_producer_chain`, [ADR 0141](0141-producer-workflow-chain-protocol.md)) holds an outcome only until the next transition: the hourly reconcile recovers a stopped chain into a new epoch (`stopped_by` cleared), reopens a completed one for a new generation, and supersedes every chain of an older programme run. The Events Log is R2 (`events/items/`), D1 is the Producer's store, and the two are never written atomically.

The first implementation at `d1ca719c` (PR #976) read the chain in the hourly reconcile, put the event create-only into the journal before moving the chain, queued a refused put in a new mutable R2 ledger `events/canonical-producer-outbox.json` (etag compare-and-swap, `baselineAt`, bounded `pending` and `settled`, a `lost` counter), and reported a superseded chain after the supersede commit. The independent review found, and this ADR accepts as facts:

1. **Supersede window.** The supersede is committed before the event is offered. A Worker that dies between the two, or a commit whose response or readback fails, leaves a superseded chain that no later tick lists (`listNonterminalChains` excludes it), and its in-flight state is gone. The outcome is lost permanently.
2. **Ledger read window.** An unreadable ledger (a transient R2 GET failure) makes the tick skip reporting while it still recovers, reopens or supersedes the chain, so the only durable evidence is erased. An invalid existing ledger was treated as absent: a new baseline replaced it and its queued events.
3. **Recovery promise clock.** The frozen `recovery: automatic` was computed at the stop time; `recoverChain` applies its 24-hour streak window at the reconcile time, so a stop just before the window ends is described as resuming while the reconcile holds it for the owner.

These are not corner cases of one implementation: any design that keeps the outcome only on a mutable row and copies it out afterwards has a window between the transition and the copy. Paid Workers is the cost baseline (AGENTS.md); write counts here are a few rows a day and are not a decision driver.

## Decision (Accepted: option B)

**Option B — a D1 outcome outbox written in the same batch as the transition.** Selected by the Product Owner on 2026-11-24 ([decision record](https://github.com/vladimino/iptv-watchlist/pull/976#issuecomment-7128839612)), with indefinite retention, the distinct `held` outcome and the scoped read-only Monitor fact, and no alert or Telegram policy change. The [design review of `05304216`](https://github.com/vladimino/iptv-watchlist/pull/976#issuecomment-7128375975) recommends B with a distinct `held` outcome; its [revision](https://github.com/vladimino/iptv-watchlist/pull/976#issuecomment-7128509290), after the owner challenged the 30-day cleanup, replaces that retention with keeping every row. Both were reviewer recommendations; the owner's decision is the record above.

1. **One additive table** (migration `0038`, the number provisional until checked against live `main` at implementation; the file is inert until applied, and applying it is a separate owner GO): `canonical_producer_outcome`, primary key the event id (`canonical_producer-<P>-g<g>-passed`, `-e<epoch>-stopped`, `-e<epoch>-superseded`, `-e<epoch>-held`), with the outcome, `at`, the programme run id and generation, the counters snapshot and the chain counts as typed, nullable columns (no free text), and delivery columns `state` (`pending`, `delivered`), `attempts`, `next_attempt_at`, `delivered_at`. Writable only while the Film/Person marker is `d1`/`open` (the trigger pattern of 0020 and 0023). Rows are inserted and moved `pending` → `delivered`; they are **never deleted** (6). The trigger pattern forbids deletion and any change of the identity and payload columns: only the delivery columns move.
2. **Atomic payload and ordering inside the batch.** The outcome row is a plain `INSERT … SELECT` (never `INSERT OR IGNORE`) placed **last** in the batch that makes the outcome, after the run and chain updates and their compare-and-swap assertions, followed by a `changes()=1` assertion, so it reads the state those updates just wrote and a missing or conflicting row fails the whole batch instead of committing the transition without its outcome. A transition happens once by its own compare-and-swap, so an identical replay of the batch is already refused by that CAS before the insert; a primary-key conflict is therefore an invariant failure, never a silent no-op.
   - `commitPassComplete` (today `producerExtras(…complete:true)` precedes the run update that sets `pass_state='passed'`, `open_at_completion` and `completed_at`; the insert goes after both) and `completeChain` (the `already_complete` path): `passed`, counters and `completed_at` from the run row as just written.
   - every `stopChain` (Workflow and reconcile-side stops): `stopped`; the run row is joined with a `LEFT JOIN` from a one-row select, so a stop before the run row exists keeps a row with **null** counters, never zeros.
   - `supersedeChain` from the hourly reconcile: the caller holds the row it read and the batch already guards the update by that row's `revision`; the insert is included only when that read state is `pending`, `active` or `released`, and it selects the pre-state values from the caller's guarded parameters (the same revision), not from the updated row. A complete or stopped chain that is superseded adds no row and no event (its outcome row already exists, or it ended before activation); the owner path `producer_chain_operator` adds none.
3. **`held` is a fenced current decision, not an inference.** A stop row states *eligibility* at the stop (`recovery: eligible` when its class and counters then allowed an automatic restart, else `owner`); its card says the stop qualified for automatic retry and never promises a resumption. The hourly reconcile writes one `held` row for `(P, epoch)` only when, in the same tick, `recoverChain` or `reopenChain` answers `held` for that stopped chain, the `stopped` row of the same `(P, epoch)` exists with `eligible`, and the insert is guarded in one batch by the chain's current `owner_epoch`, `owner_state='stopped'` and `revision`. A repeated tick finds the `held` row and writes nothing (the identity is stable). A stop that ended before activation has no `stopped` row and therefore never gets a `held` report. An eligible stop whose chain is then **superseded** by a newer publication gets no further event: it is not resumed, its card never claimed it would be, and the newer chain's outcomes report the work.
4. **Activation and failure contract.**
   - *Schema probe.* The writers learn whether the table exists from one read per Workflow invocation and one per reconcile tick (`schema_contract.version` plus the table's presence), charged to the existing entry and tick costs. Only a **proven absent** pre-migration schema (version below the migration and no table) means "write no outcome": that is today's behaviour. An unreadable probe, a version at or above the migration without the table, or a malformed table is a storage fault: it fails closed through the existing classification (`producer_transport` / `producer_store_missing`, the existing fenced stop and recovery paths), never a silent fallback to writing no outcome.
   - *A failed outcome insert* rolls back the terminal batch it belongs to; the transition is then not recorded and the Producer follows its existing fenced recovery path (a stop not written leaves a lapsing lease and a takeover; a completion not written is redone by the next instance). This is the same failure class as any other failed terminal batch.
   - *R2 delivery never blocks or fails the Producer:* a refused journal put only leaves the row `pending`.
   - *No absolute zero-loss claim across inactive periods:* outcomes made by code that does not write the table (before activation, by old instances still running while the migration is applied, after a code rollback) have no row and are never reported; there is no backfill.
5. **Delivery** belongs to the hourly reconcile only: each tick takes at most 8 rows with `state='pending'` and `next_attempt_at` due, ordered by `next_attempt_at` then `at` then id (indexed), so a row that keeps failing moves behind the others and cannot starve them. Each is put create-only to `events/items/<reverse-timestamp>-<id>.json`, the key derived from the row's frozen `id` and `at`; a put that finds the key counts as delivered. The row is then marked `delivered` by a compare-and-swap on `attempts`; a failed put increments `attempts` and sets `next_attempt_at` one hour later, with no give-up and **no eviction of a pending row**. Because ids are unique by construction and the row keeps its frozen `id`, `at` and payload, a replay of the drain never writes a second item. `GET /api/events` stays read-only.
6. **Retention: every row is kept indefinitely**, pending and delivered alike: no TTL, pruning, retention delete, cleanup job or setting. There is no demonstrated storage, performance, cost or privacy reason to delete: at ten outcomes a day that is about 36,500 small rows of aggregate counters and delivery metadata over ten years, with no film payload. The permanent row keeps the event identity for deduplication and the delivery evidence (`attempts`, `delivered_at`). The pending drain stays bounded and indexed on `state` and `next_attempt_at`, so the delivered history never enters its work. Retention is revisited only by a new decision on measured evidence.
7. **Visibility, scoped.** The Monitor stream `canonical_producer` gains one read-only fact, `outcomeDelivery: {pending, oldestPendingAt, readable}`, shown in the Monitor status and the runbook. It is not a Producer health input: a healthy Producer with pending deliveries stays healthy, and no new alert, reminder or Telegram policy is added by this ADR.
8. **Budget and ordering.** Inside a Workflow instance each terminal batch gains the insert and its assertion (two statements) and each invocation the probe; both are charged to the existing ceilings (`CHAIN_COST.entry`, `CHAIN_COST.complete`, `CHAIN_COST.end`) and `tests/canonical-producer-budget*.mjs` must keep proving every admitted operation within its ceiling on the measured ADR 0141 budget. The reconcile's reads and writes are outside the instance budget. Order: (1) the implementation is merged and deployed, inert because the probe proves the table absent; (2) a separate owner GO applies the migration, with its own evidence; (3) the next invocation and tick find the table and start writing. The R2 ledger of `d1ca719c` is not shipped. The Mermaid flow on the observability page, the events and driver references, the D1 schema reference and the runbook are updated with the implementation, with rendered Mermaid QA.

**Option A — keep the R2 ledger and close the windows inside it** (not selected): write a supersede **intent** to the ledger before the supersede and confirm it from the chain revision afterwards; distinguish absent, invalid and unreadable ledgers (an invalid one is preserved under a quarantine key and stops reporting, visible in the Monitor, never replaced); when the ledger is unreadable, still put the event create-only and accept the residual loss when both the journal and the ledger are unreachable at the moment of a transition; compute the recovery wording at the reconcile tick that decides.

**Not decided here:** the event fields and display (events reference), any change to the Producer protocol of ADR 0141 beyond the extra statement in the terminal batches, any production apply, activation, backfill or manual run.

## Alternatives considered

| Criterion | A: R2 ledger (PR #976, fixed) | B: D1 outcome outbox (recommended) |
| --- | --- | --- |
| Atomicity with the outcome | None: the copy follows the transition; windows closed by intents and ordering, not by a transaction | The row commits in the same D1 batch as the transition, last and asserted: no window while the table is active |
| Residual loss | A tick with the journal **and** the ledger unreachable while it moves a chain; a Worker death between an intent and its confirmation needs a later reconciliation | None while active; a journal outage delays delivery only. Outcomes of inactive periods (before activation, old instances during the apply, after a rollback) are not reported |
| Supersede in flight | Intent before, confirmation after (two extra R2 writes per supersede) | Same statement as the supersede |
| Recovery promise (finding 3) | Wording computed at the deciding tick | Eligibility at the stop plus a durable `held` report |
| Instance budget (ADR 0141 D5) | Untouched (reconcile only) | +2 statements per terminal batch and one probe per invocation, inside existing ceilings, proven by the budget tests |
| Store consistency | A second mutable R2 ledger with its own CAS, baseline and validity rules | Same store and fences as the chain and run rows; follows ADR 0194 (the prediction event outbox moved from R2 to D1 for the same reasons) |
| Retention | 32 pending, 64 settled ids, overflow counted lost | Every row kept indefinitely (a few a day, small aggregates); the pending drain is indexed and bounded, so the history adds no per-tick work |
| Loss visibility | `lost` counter and log line | Pending count, oldest age and readability as a Monitor fact (no alert policy); nothing evicted |
| No backfill | Needs `baselineAt` and its own validity rules | Structural: no row before the code and schema exist |
| Rollout | Code deploy only | Code deploy (inert, the probe proves the table absent), then the migration apply by a separate owner GO; activation follows the schema |
| Rollback | Code revert; the ledger object stays | Code revert; the additive table and its rows stay; events already in the journal stay |

A third option, writing the event from inside the Workflow straight to R2 after each commit, was rejected without further work: it spends unmetered subrequests inside the instance and still has the window between the D1 commit and the put.

## Consequences

- **B:** while the table is active no outcome can be lost between the transition and the report; the Producer never waits for or fails on the journal, while a failed outcome insert fails its terminal batch like any other storage fault. New: one migration, an asserted insert in five batch builders, a schema probe, a drain in the reconcile, a fenced `held` insert and a Monitor fact. No cleanup: the table grows by a few small rows a day, kept as permanent delivery evidence. The schema checks of `tests/canonical-producer-schema.mjs` and the budget proofs grow accordingly. Activation is two steps with an owner gate in between.
- **A:** no migration, but a second mutable store with its own validity, CAS and quarantine rules, a documented residual loss, and more R2 operations per transition.
- Either way the user-visible contract of the events reference holds, and a code rollback leaves every delivered event in place; old clients ignore the unknown type.

## Recovery and migration boundary

This ADR authorizes nothing in production. Under B, applying `0038` is a separate owner-approved L2/L3 operation with its own evidence; the code that writes the table is inert before it. Neither option backfills an outcome that ended before its code ran (P518 included). Reverting the code stops new rows and new events; the table, every pending and delivered row and the journal entries remain and are harmless (a pending row left by a reverted drain is delivered once the drain returns). No rollback, code or data, deletes outcome rows. Dropping the table would itself need a migration and a decision.
