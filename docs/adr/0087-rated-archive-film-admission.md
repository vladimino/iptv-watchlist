# ADR 0087: A confirmed rated archive registers the short code, and only a verified movie admits the Film

## Context

The ZIP preview compares only films the matcher marks `accepted`, then a confirmed apply writes those films through the existing baseline commit. A rated film that is absent from the watchlist and from the canonical catalog is not `accepted`. The previous preview counted it and the commit dropped it. ADR 0086 keeps a Film by a watchlist boolean on the view index. A rated-only film has no such fact. Inferring `watchlist: false` or `watchlist: true` would invent membership.

Authoritative ratings already follow the ratings marker. While that marker is `d1` and cutover is `open`, readers and writers use D1 and do not fall back to R2. The archive comparison was still reading `letterboxd/facts/links.json`, the scan summaries and the fact records with `env.BUCKET.get`, so an older R2 fact could win over the D1 fact.

The 27 October 2026 export reconciliation reported 561 candidates, 1 ambiguous and 1,478 unmatched (2,040). That figure is a snapshot of one private ledger. It is not the queue of a new ZIP. Unverified titles, old provisionals and a halted network checkpoint are not accepted identities. Watched rows with no rating are not a Film source.

## Decision

1. **Fact comparison uses the ratings read contract.** A mutable ratings key is read through `RatingsD1.readOwned` when the marker is open. A missing D1 document is `object_missing` and is not filled from R2. A marker that is not open, including `d1` with cutover `held`, stays on R2. An unreadable marker, including partial tables, is unavailable (`ratings_domain_unavailable`) and is not filled from R2. The open generation is part of the consistency fence (`ratings_domain_generation`). Newer-wins, the receipt and rollback stay on the existing fact writer. Import receipts, the ZIP and the candidate document stay in R2.
2. **A confirmed rated row that is not accepted is a candidate, not a Film.** After the owner confirms that chunk, the short `boxd.it` code and the archive SHA-256 are stored on `letterboxd/imports/<sha256>/rated-candidates.json`. The code is the candidate key. It is not a Letterboxd lid and it is not written as `links.letterboxd`. No `watchlist` field is written. Pending and needs-review rows are chunks of 50 after the fact chunks. Their pin is `archive-` plus the archive SHA-256. The commit creates `letterboxd/imports/<sha256>/chunks/<n>.candidates.json` and does not call the baseline fact commit. The action receipt reports `fact: "candidate"` with outcome `registered` or `kept`. It does not report a rating write. A replay of the same hash does not register the code again. A newer stored `observedAt` is kept. Rollback of that receipt removes codes that are still pending or needs-review. A code that is `admitting` or `verified` stays.
3. **Identity is one explicit request, after the candidate is stored.** `POST /api/admin/letterboxd-archive/identity-step` with `{archiveSha256, accepted: true}` does one thing. It selects an `admitting` code first, then any still-pending code. The checkpoint cursor is a progress mark and does not hide a pending code that sorts before it. A stored stop returns no next code until `resume: true`. The page fetch and the TMDB movie document are bounded: 25 s and 3,000,000 bytes for the page, 12 s and 1,000,000 bytes for the movie document. A timeout, an abort or an oversized body is a stop and the code stays pending. HTTP 403, 429, a challenge and a failed fetch are the same kind of stop. Two unfetched codes that share a title and year stop as needs-review before any fetch. The decision reuses `letterboxd-identity.js` and sees movie ids already owned by another admission, another candidate, or the ratings link index. A second short code for that movie is needs-review and does not replace the first source code. A TV id, a title or year alone, an ambiguous alias, and a stored historical TMDB id that disagrees with the page stay needs-review and write no Film. A missing TMDB read token stops as `tmdb_unavailable` and writes no admission. A clean movie is fenced as `admitting` with the intended movie id and film path. The stored row is read back before any admission or rating. A row that is removed, in review, or already claiming a different movie is not admitted and is not marked verified. A short code already bound to another movie id, in this archive or another, is not given a second movie. An admission conflict writes no rating. Resuming the same `admitting` claim skips the page and does not write the rating twice. When no identity work remains, the same route continues one verified film: first the stored Letterboxd film path for synopsis and credits, then one localization pass. That page is kept only when its short code, canonical path, movie type and movie id still match the admitted film. A mismatch writes no metadata. That continuation is this POST, not cron, and verification itself does not store metadata. `POST …/identity-status` reads the stored queue and writes nothing. Preview does not fetch and does not call either route. Nothing in the Worker cron calls them.
4. **A verified movie enters the existing Film read through one admissions object.** The object is `letterboxd/admissions/verified-films.json`, schema version 1, films keyed `tmdb_<n>`, with no `watchlist` field. The existing lifecycle reader and the existing enrichment projector read it. A missing object admits nobody. The same verified movie id already on a programme film stays one Film. A thin archive stub yields to a richer discovered film of that movie id. Synopsis and credits stored later on the admission are part of that read and do not mint a second Film. The rating is written by the existing `linkTmdbOnly` path: watched and rating only, no Letterboxd link and no watchlist fact. A real EPG airing of that same movie id joins the show to that Film. This delivery writes no synthetic showing.
5. **Historical ledgers are evidence, not the queue.** A remembered count, including 2,040, is ignored. Eligibility is the confirmed archive plus the current Film match and the authoritative rating. A conflicting historical alias stays needs-review.

What this decision does **not** do: it does not authorize a production ZIP commit, a live Letterboxd or TMDB call, an R2 or D1 write, a scheduler, a flag, Access, or a migration. It does not add a second Film authority. It does not pull watched-only rows into the catalog. It does not resume the rejected AIR-185 resolver. It does not change Finds eligibility. Accepting this record would still not authorize those operations.

## Alternatives considered

Treating the October ledger as the current queue was rejected because a new ZIP has its own rows and the stored facts may be newer. Inferring a watchlist boolean for a rated-only film was rejected because membership and a rating are different facts. A separate network mass resolver was rejected with AIR-185. The discovery detail gate was not reused: it requires a programme pin and a duration, and this identity check is a movie document plus title and year.

## Consequences

Preview stays read-only. The page names three groups before any write: films already matched, new candidates, and errors or ambiguity. It does not call an unverified network identity confirmed. After a candidate commit, one button checks one identity and stays while pending work, an admitting fence, unfinished metadata or a stop remains. A stop is continued only with an explicit resume. «Прочитать сохранённое состояние» reads the queue already written and fetches nothing. The tab does not keep that queue. A verified film can appear in the lifecycle view once the admissions object exists. Until that object exists, the projector admits nobody from this path, so deploying this code does not upsert a rated-only Film.

`D1_ENRICHMENT_WRITE` is already `on`. The cron still runs only the existing enrichment projector. After a later identity step has written the admissions object, that same cron would upsert the verified movie. Metadata and localization of that film are further explicit posts of the identity route, not that cron and not `metadataSync`. Neither the upsert nor those posts are authorized by this delivery or by a merge. Each needs a separate explicit owner approval before anyone treats the identity step as allowed to run in production.

An open ratings marker makes the archive comparison ignore an R2 fact. A held marker still reads R2. A broken marker refuses the comparison instead of trusting R2.

## Recovery and migration boundary

This record authorizes no production write. Code rollback stops later identity steps from running and stops later projector reads of the admissions object. It does not delete a Film row, a fact, a candidate document or an admissions object already written. Candidate rollback removes only codes that are still pending or needs-review. An admitting fence and a verified movie stay until their own rollback. A newer rating is not overwritten by an older archive.
