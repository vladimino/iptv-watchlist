# Deployment and rollback: Cloudflare production and legacy Sites reserve

## Production topology (19 October 2026)

GitHub `main` is the canonical code source. Cloudflare is the production runtime:

- Production: https://iptv.vladimino.workers.dev/. Worker `iptv`, deployed by GitHub Actions, private behind Cloudflare Access. R2 bucket `iptv` (binding `BUCKET`) stores immutable bodies, ratings and removal events, raw inputs, archive segments and compatibility mirrors; it is not the authority for canonical Film/Person (see [authority per domain](../architecture/persistence-and-migration.md#authority-per-domain)). Migration `0011` is applied ([apply record](../evidence/d1-migration/air-320-discovery-apply-2026-11-04.md)). The ratings marker is `d1` / `open` at generation 12 ([manual run](../evidence/d1-migration/air-318-ratings-manual-run-2026-11-04.md)). The discovery marker is `d1` / `open` at generation 1 ([activation record](../evidence/d1-migration/air-320-discovery-activate-2026-11-04.md)). D1 `iptv` (binding `DB`) is authoritative for metadata cache, mutable predictions, the published EPG/watchlist generation ([AIR-319 evidence](../evidence/d1-migration/air-319-production-cutover-2026-11-03.md)), owner reviews (`owner_review_authority.mode=d1`, generation 1, [activation record](../evidence/d1-migration/air-314-owner-review-activate-2026-11-03.md)), the mutable ratings documents, and the discovery ledger, decisions and admission. The owner-review object is the mirror.
- Experimental MCP: `https://iptv.vladimino.workers.dev/mcp`, served by the same Worker. A separate Access application, `IPTV MCP`, protects this path with Managed OAuth and an owner-only policy. Application `All Workers` keeps protecting every other path. The Worker verifies the Access JWT using the runtime variables `MCP_ACCESS_TEAM_DOMAIN` and `MCP_ACCESS_AUD`, which are set in the Cloudflare dashboard and not committed. The probe tools do not use R2. The EPG and prediction tools call the existing sync and runner functions and can read or write R2 when invoked; deploying the Worker does not invoke them, and it neither configures nor triggers external ChatGPT Scheduled Tasks. [AIR-62](https://trello.com/c/CU71gW4c) separately restored scheduled operations on 21 October 2026. See [docs/mcp.md](../reference/api/mcp.md).
- Resolver continuation: Discovery chunks run only in the Cloudflare Discovery Workflow (`DISCOVERY_WORKFLOW` binding, permanent since AIR-325; the `DISCOVERY_EXECUTOR` selector is retired and ignored). No HTTP request runs a chunk: the EPG commit and `/api/enrichment/discovery/resolve` only delegate. Without the Workflow binding or D1 admission everything fails closed and nothing falls back to an external executor. No second Worker or Access exception is configured. The internal `DiscoveryContinuation` entrypoint stays unreachable from public HTTP and carries no credential. The Sites-era `EPG_SITE_SERVICE_TOKEN` is no longer read. If it still exists as a Worker secret, removing it is a separately approved environment change. A leftover `DISCOVERY_EXECUTOR` Cloudflare variable is harmless (`keep_vars: true` keeps it across deploys); removing it is an owner-controlled settings action, after which `feature_flags` reads `absent` and `retired`. Code older than AIR-325 selects `external` when the variable is absent, so do not roll back to it after removal without a separate approval. See [ENRICHMENT_API.md](../reference/api/enrichment.md#epg-resolver--hotcold-pipeline-v2).
- Legacy reserve: https://iptv.vladimino.chatgpt.site/, Site `appgprj_6abfed826e148191903dec4175166ff7`. Its separate R2 store is a temporary reserve and the source of the historical snapshot. It is not the destination for current writes. Do not run sync, prediction, or other mutating processes there. Do not use it for ordinary browsing or diagnosis without separate approval: opening the UI is not guaranteed read-only, because `GET /api/events` can recover events. `GET /api/enrichment/view` overlays the compiled ratings seed in memory and does not persist it, but other GET routes on that Site can still write. GitHub/Cloudflare deployment does not update this Site.

**Scheduled operations (historical, 24 October 2026; current ownership: [scheduled tasks](../reference/scheduled-tasks.md)):** [AIR-62](https://trello.com/c/CU71gW4c) restored unattended ChatGPT Scheduled Tasks using owner-only IPTV MCP: daily EPG/watchlist at 17:00 Europe/Madrid and hourly predictions. Both tasks were enabled with recent executions in the ChatGPT automation registry on 24 October. These are **external ChatGPT Tasks, not Cloudflare Worker Cron triggers**: Worker `schedules=0`, observed during [AIR-69](https://trello.com/c/FlcWZX7W), did not mean the external tasks were off. Since [ADR 0056](../adr/0056-d1-enrichment-write-through.md) the Worker has had a cron trigger (`0 * * * *` since AIR-348; the D1 enrichment projector was retired from it by [ADR 0155](../adr/0155-retire-enrichment-projector-cron.md), and since AIR-534 / [ADR 0174](../adr/0174-discovery-only-fast-recovery-cron.md) a second, Discovery-only trigger `1-59/2 * * * *` exists) whose hourly tick runs the ratings `ensure`, the EPG `ensure`, the monitor and `reconcileDiscoveryWorkflow` ([ADR 0093](../adr/0093-discovery-workflow-cron-reconcile.md), Accepted). With `D1_ENRICHMENT_WRITE` unset the projector returns at once. The Discovery reconcile creates nothing without the Workflow binding and D1 admission; the retired `DISCOVERY_EXECUTOR` variable is ignored. The cron never runs an EPG download, a discovery chunk, TMDB, predictions or a ratings step. An enabled task or recorded invocation is not proof of a successful EPG or prediction cycle; correlate the specific run with MCP/EPG/runner state. GitHub deploys do not change tasks, OAuth grants or their schedule. Always recheck the live registry and runtime before operational claims. Any schedule change, new writer invocation, lease override or Access policy change needs separate owner approval. Keep Cloudflare Access enabled.

The GitHub environment `Cloudflare Prod` identifies deployment credentials. It does not authorize a data restore or a schedule change.

## Cloudflare: automatic GitHub Actions CI/CD

Source: `.github/workflows/ci.yml`. The former independent Cloudflare Workers Builds integration has been disconnected.

1. Pull requests into `main` run `test-and-build`, `test-shard-2` and `test-shard-3`. Each `Run tests` step is `npm test -- --shard N/3 --suite core`. A GitHub ruleset must be configured separately if CI is required to block merging.
2. Pushes to `main` run the same three jobs: `npm ci --ignore-scripts`, the core suite and `npm run build` on Node.js 20 in `test-and-build`. That job then runs `node scripts/check-discovery-workflow-bundle.mjs` on Node.js 22. The Node.js 20 build is the artifact the deploy job downloads, kept for one day. The dry-run does not replace that artifact. Wall time of each core shard's `Run tests` step is a health metric in the job summary, with a 180-second quality threshold (see [test-speed policy](../process/agent-workflow.md#test-suite-performance-quality-gate)). Exceedances warrant investigation, not a blocked deploy. A failed file, the per-file timeout and the job timeout still fail the job.
3. The `deploy` job requires successful `test-and-build`, `test-shard-2` and `test-shard-3` and downloads that exact verified artifact. Deployment runs only on pushes to `main`. The daily workflow `.github/workflows/nonfunctional-tests.yml` is not a `needs` of deploy. It runs at 04:17 UTC (05:17 Europe/Madrid while the offset is UTC+1, 06:17 while it is UTC+2) and on `workflow_dispatch`, with no secrets and no Cloudflare environment. A failure there is a regression signal. It does not deploy and it does not block deploy.
4. Deployment credentials belong to GitHub environment `Cloudflare Prod`:
   - Secret: `CLOUDFLARE_API_TOKEN`
   - Variable: `CLOUDFLARE_ACCOUNT_ID`
5. Deployment concurrency group: `cloudflare-iptv-production`, with `cancel-in-progress: false`. Before publishing, the job verifies that `GITHUB_SHA` still equals the remote `main` HEAD. This prevents common stale deployments, but the freshness check is not atomic with publication.
6. Before Wrangler starts, the job verifies the account token and the settings of Worker `iptv`. It prints the HTTP status and a short classification, not response bodies. A non-200 response or a network error stops the job before deploy.
7. `cloudflare/wrangler-action@v4` uses Wrangler 4.151.1 and `deploy --message`. Cloudflare release descriptions are:
   - Normal commit: commit subject
   - Merge commit: `PR #N: <PR title>`
8. `wrangler.jsonc` configures:
   - Worker: `iptv`
   - Entrypoint: `dist/server/workflow-entry.js` (the Worker fetch handler plus the `DiscoveryWorkflow` class). `dist/server/index.js` stays the script local dev imports and does not import `cloudflare:workers`
   - Compatibility date `2026-10-18`, which enables `ctx.exports` for the resolver continuation. Do not add `disable_ctx_exports` or move the date before 2025-11-17.
   - R2 binding: `BUCKET` -> `iptv`
   - `keep_vars: true`, so dashboard variables such as `MCP_ACCESS_TEAM_DOMAIN`, `MCP_ACCESS_AUD`, `ADMIN_ACCESS_AUD` and `ADMIN_OWNER_EMAIL` survive deploys. `ADMIN_ACCESS_AUD` (the AUD tag of the Access application `All Workers`) and `ADMIN_OWNER_EMAIL` open the owner route [`POST /api/admin/identity-work/owner-action`](../reference/api/admin.md#owner-requeue-and-dismiss-of-the-shared-letterboxd-check-post-apiadminidentity-workowner-action) (AIR-599); until the owner sets both, the route answers 503 and nothing else changes
   - `preview_urls: false`

## Owner person-name confirmation

As of 2026-11-03 23:13 UTC, `owner_review_authority.mode` is `d1` at generation 1 ([activation record](../evidence/d1-migration/air-314-owner-review-activate-2026-11-03.md)). The same two buttons send the same POST. The Worker commits both maps as `owner_review_entry` rows and then puts `admin/owner-reviews.json` as the mirror. `reviewsVersion` is `d1:<generation>`. A marker in any other mode, a missing binding or missing tables is refused ([ADR 0162](../adr/0162-d1-only-authority-retire-rollback-toolchain.md)). The paragraphs below describe the local stand-in store (`OWNER_REVIEW_DB_OPTIONAL=standin`), which production never sets.

With the local stand-in, `POST /api/admin/people/<id>/name-review` is the only writer of a reviewed Russian Person name and of an owner-added name alias. The owner presses **Добавить вариант** or **Сделать предпочтительным** on that person's card in `/admin`. «Добавить вариант» adds one alias and leaves the preferred name. «Сделать предпочтительным» reviews a new preferred name. The Worker puts `admin/owner-reviews.json` once, replacing `people` entries for that command and copying `films`. It does not rewrite `programme.json`, `people.json`, `titles.json`, the published generation, or D1, and it does not call TMDB, Letterboxd or a model. Deploying the route does not create the object and does not change a name. A missing object stays missing until one of those buttons succeeds and the reread proves the command. The film card uses the same two buttons for the film title command. Choosing another stored Russian radio arms «Сделать предпочтительным», and that save reviews the chosen title as preferred. «Добавить вариант» on that radio does not put. A typed title on «Добавить вариант» adds one film alias and leaves the preferred title. A typed title on «Сделать предпочтительным» reviews a new preferred title. An answer that changes nothing stays on the card and does not reload it. A 200 by itself is not the confirmed sentence. Either way it replaces one `films` entry and copies `people`. A failed readback is unknown until the stored audit for that request is present; an added alias also has to be in the slice. The page accepts that alias only when the reloaded record shows it with owner-added provenance, not because the text is already an option. Do not send a new command for that answer.

Programme and watchlist reads stamp the saved name after the dictionary and the name cache. The EPG commit does not read or write the object. A dictionary or automatic name does not replace an owner review. The route reports the card saved only after it has read the object back and found the request's audit entry on the person and on every linked role. `readback_failed` (503 `storage_unavailable`) means that read did not prove the write. The object may already contain it. Repeat the same request from the card; do not treat that answer as a failed write that needs a new command, and do not delete the object to clear it. Rollback is a Worker redeploy of the previous commit ([procedure](recovery/cloudflare-worker-rollback.md)). That redeploy does not delete the object and does not downgrade the stored review. A later EPG commit on a build without the overlay can publish the dictionary name again; the object remains for the build that reads it. Do not delete the object as part of a code rollback.

**Derived taxonomy.** The former `POST /api/enrichment/moods/backfill` route no longer exists and answers an ordinary 404; deploying mapping version 2 does not rewrite fingerprints, predictions or hashes. `GET /api/enrichment/view` recomputes ids and chip groups from the stored raw labels. `enrichment/diagnostics/moods.json` may stay on mapping version 1; the page does not read it for chips or filters. The per-film `mood-facet.json` sidecar is no longer written and nothing reads it; objects written earlier are inert. A diagnostics refresh is a separate approved write. See the [taxonomy contract](../reference/domain/taxonomy.md).

**Code-only paths and leftover variables.** Deploying the Worker does not create or write `admin/owner-reviews.json`. That object appears only when the owner confirms one title or one name in `/admin`. A code rollback does not delete it; the previous Worker ignores it until a forward deploy reads it again. The EPG resolver and the localization of the programme and watchlist reads and of the EPG commit have no runtime switch: rolling either back is a redeploy of the previous verified commit through the [Worker rollback procedure](recovery/cloudflare-worker-rollback.md), never a dashboard variable. `keep_vars: true` also preserves variables the code no longer reads (`SCORED_RESOLUTION`; the `epg`, `programme` and `watchlist` tokens of `LIFECYCLE_LOCALIZATION`, which gates the metadata sync alone). They are inert; removing them is a separate owner-approved settings change followed by a read-only check, not part of a deploy. The [flag register](../reference/feature-flags.md) lists what each variable still does.
**Rollback of the Film localization reconciler ([AIR-663](https://trello.com/c/UP10l6Js), ADR 0218 stage 4).** The reconciler is dormant code: deploying it runs nothing, adds no route, flag, Scheduled Task or migration, and a code rollback removes only the unused module. Rows it wrote and its applied receipts are valid under the previous code. A `film_localization_reconcile` receipt that is still `pending`, `failed` or `unknown` has no operation in the previous registry (`operation_unregistered`, left `waiting`): roll the code back only when this read-only count is 0, `SELECT COUNT(*) FROM canonical_write_receipt WHERE operation='film_localization_reconcile' AND state NOT IN ('applied','abandoned')`. A rollback never repairs or restores a row; a restore needs the token the production operation ([AIR-664](https://trello.com/c/Og9XxXfy)) recorded. See the [reconciliation runbook](film-localization-reconciliation.md).

**Rollback of the Film localization projection write ([AIR-662](https://trello.com/c/P8cCPv1V), ADR 0218 stage 3).** Rows it wrote (source rows, the effective `localization` row, a created `identity` row) and its applied receipts are valid under the previous code. A `film_localization_projection` receipt that is still `pending`, `failed` or `unknown` has no operation in the previous code's registry, so that code leaves it `waiting` as `operation_unregistered`: it neither settles nor abandons it. Roll the code back only when this read-only count is 0, otherwise let the new code settle the receipts first or accept that they stay open (reported as unreceipted) until it returns: `SELECT COUNT(*) FROM canonical_write_receipt WHERE operation='film_localization_projection' AND state NOT IN ('applied','abandoned')`. The previous code's readers treat every reviewed/owner localization row as independent owner authority, so a marked owner projection (`provenance_json.projection='owner_review'`) whose owner decision was revoked keeps displaying its value after a rollback until the new code or AIR-663 corrects it. A rollback never repairs a projection and never removes a row; see the [receipt kind](../reference/data/d1-schema.md#automatic-localization-sources-schema-v14).


## Published-EPG compatibility mirrors

GET `/api/programme`, `/api/watchlist`, `/api/catalog/available` and Admin reads of the published generation are query-only. They do not fall back to R2 when D1 is held or unreadable. The existing hourly cron `EpgOrchestration.ensure` copies the published D1 documents onto the R2 compatibility keys when they drift, even when the daily publication is not due; aligned mirrors, a held cutover and a live EPG step lease write nothing. A deploy of that path starts the light reconcile on the next tick; it does not start a daily EPG download, TMDB or discovery. Rolling the Worker back does not undo mirrors already rewritten. See [ADR 0108](../adr/0108-epg-mirror-reconciliation-writer.md) and [read side effects](../reference/api/read-side-effects.md).

GET `/api/events` is query-only as well ([AIR-416](https://trello.com/c/f7FX4Elk)): it never delivers a prediction run event. A start or stop event that did not reach the Events Log is delivered by the next `prediction_batch_start` under the Predictions writer lease; `eventOutbox` in `GET /api/enrichment/status` shows what is pending or quarantined ([events](../reference/domain/events.md#delivery-of-prediction-run-events)). A deploy does not deliver, replay or remove anything; a code rollback keeps journal items, event records and the outbox index. Replaying a quarantined or pre-existing undelivered event is a separate owner-approved operation.

## Proportionate post-deploy acceptance

For a documentation-only PR with no runtime or configuration changes, **every** required GitHub Actions job succeeding and one safe MCP `probe_read` are sufficient operational acceptance unless the card explicitly changes a contract that needs a targeted read. Do not trigger EPG, discovery, predictions, TMDB, imports or full storage parity as a deployment smoke test. A release touching a runtime API or persisted projection gets the **smallest matching safe readback** for that scope, rather than a blanket bucket snapshot, manual replay or speculative incident checklist. Keep all post-merge jobs and report their actual conclusions: they are delivery guarantees, not permission to operate production data writers. ## EPG commit memory

The daily commit reads the active discovery ledger as bytes when the stored object provides a body or text, folds one candidate at a time, and puts one generation document. The document is pulled one chunk at a time. The put is a fixed-length stream of the UTF-8 length counted on the decision walk. A length mismatch stops before the published pin moves. The copy onto the stable keys uses each stored object's size and does not buffer the body as text. It does not raise the isolate limit, and it does not delete candidates. When the published EPG authority already names a programme run, the commit stops if that run's ledger cannot be read, or if the copy it would use names a different run. The latest scan is not published over that gap. The published pin and the archive pointer stay where they are. A commit that the platform kills for memory leaves the published generation and the D1 pin unchanged when the kill happens before those writes. Retry that same sync run after the discovery lease expires. The lease TTL is 90 seconds. Starting a new sync replaces the run record. Resetting the lease or removing ledger objects is not a memory remedy.

Node measurements of this path are not the isolate limit. The dated synthetic reading and its limits are in [the 3 November memory evidence](../evidence/epg-commit-memory-2026-11-03.md). A separate workerd reading of the fixed-length put is in [the 3 November R2 length evidence](../evidence/epg-r2-known-length-2026-11-03.md). Neither applies an isolate memory cap, and a green deploy does not by itself show that a live commit will stay under the limit.

## Moving a pipeline to a Cloudflare executor

This is the operator sequence of the shared reliability contract ([ADR 0089](../adr/0089-shared-orchestration-reliability-contract.md), Accepted; [reference](../reference/orchestration-reliability.md#rollout-and-rollback)). It applies to EPG publication, Discovery and Ratings one domain at a time; Predictions stay on the hourly ChatGPT task. No step is part of deployment. This is a **high-impact L3** producer ownership transition: the Product Owner approves an explicit bounded domain-specific plan with its holdpoints. One plan can include preflight, readbacks and staged commands; it does not remove the required verified drain and fencing or authorize unrelated task changes.

1. **Inert code.** The executor, its `ensure`, the read model and the tests are merged and deployed with the domain mode `external`. `Test and build`, `Test shard 2 of 3`, `Test shard 3 of 3` and `Deploy to Cloudflare` completed with success on the exact merge SHA. Verify with the domain's read-only status route that `orchestration.mode` is `external` and no Cloudflare owner is live. Nothing else is called.
2. **Close admission, drain, complete.** Each is a separate **verified state transition** for this domain, executed only within the approved L3 plan and its stated holdpoints. First close admission (`mode: switching`, new `epoch`); read it back. Then wait for the read model's `drain` to report `verified` (old lease absent or expired with margin over the longest step, old Workflow instance finished or absent, domain lease released). Only then complete the switch to `cloudflare` and read it back. Until completion both paths answer `switch_in_progress`; afterwards the external tool path answers `external_writer_fenced`. Do not test either with a write. An unverifiable drain is not completed.
3. **Acceptance.** Observe at least one complete run through the read model: `health` `healthy` or `idle`, `lastDurableProgressAt` advancing, no `quarantine`. Do not trigger a run to speed this up unless that run has its own GO.
4. **Retire the task path.** When the approved L3 plan authorizes the task-registry step and its holdpoint is satisfied, change the ChatGPT task registry so the task no longer drives this domain, and read the registry back. The hourly task keeps Predictions.

**Rollback.** The same three state transitions in the other direction, within an expressly approved rollback plan and its holdpoints: close admission (the epoch increases and the running instance's D1 commits are refused), verified drain, complete the switch back to `external`. Only then, when separately included in the approved rollback plan and after the required holdpoint, re-enable the ChatGPT task path. A code rollback alone leaves the mode, the data, the cron trigger and the task registry as they were.

**Quarantine.** `quarantined` with reason `budget_exhausted` ends only the current run key; the next run key retries by itself. Any other quarantine reason is `unsafe` and stays until an explicitly approved, reason-specific recovery action; L0 diagnosis alone is not permission to clear. Read the `failure` fingerprint and the domain's checkpoint first; clearing never resets a lease or forces a step.

## Scoped Worker bundle: the build checks imports (AIR-532)

`build.mjs` turns several modules into named scopes with `scopedImports`: it strips every ES import and prepends a hand-written preamble that destructures the already-scoped bindings. A used import that the preamble does not name is undefined in the Worker, and an ES-module test cannot see it (there the import resolves). Since 19 Nov 2026 the build fails with "imports and uses X but the scope preamble does not provide it" for such a name, and `tests/canonical-rated-admission-bundle.mjs` runs the generated bundle. When you add an import to a scoped module, add it to its preamble in `build.mjs`; a green `npm run build` is then the proof. Background: [the 19 Nov regression](../evidence/orchestration/air-532-bundle-binding-regression-2026-11-19.md). A fix is a normal deploy only when the deploy and rollback holdpoints above (no unfinished seal claim, no live Workflow owner) are clear; otherwise it needs its own owner-approved recovery plan.

## A Discovery Workflow instance that errors (AIR-360)

Read-only: `epg_pipeline_status` (`discoveryExecutor`), the instance steps in Cloudflare (`owner`, `plan` and `chunk` step outputs and attempts) and the Worker log line `discovery_workflow_step_failed`, which carries the bounded cause and the statement count of the instance. A step failure that the instance recognises as transient (`discovery_unavailable` or a transient class) is recovered by the instance itself at `recovery.dueAt` ([ADR 0098](../adr/0098-discovery-workflow-step-failure-recovery.md)); its record reads `stopped` with reason `step_failure` while the instance sleeps. An instance that errors for any other reason, is killed by the platform, or fails to arm is replaced by the hourly cron through `recovery.dueAt`; do not start, terminate or reset anything by hand without an owner decision. An instance that ends near 6,000 statements is the planned handover ([ADR 0094](../adr/0094-discovery-workflow-invocation-budget.md)), not an error.

## EPG run certificate: deploy and rollback holdpoint (AIR-539, [ADR 0175](../adr/0175-epg-priority-holds-until-run-complete.md))

- **Order.** (1) Deploy the code; it is dormant while `published_epg_authority.finalized_run_id` is absent. (2) A separate owner GO applies `0026` ([runbook](epg-run-certificate-0026-apply.md)). (3) Read-only preflight that the deployed version is the certificate code and no older instance is live. A deploy never applies the migration.

An unreadable inventory is the existing `discovery_unavailable` failure of the gate read: nothing is admitted for any role, the EPG role included, until it reads again (owner-accepted on 2026-11-19; the EPG lease already needed the same inventory).
