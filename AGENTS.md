## Collaboration and delivery

- Roles are capability-based, not ChatGPT/Cursor-specific: Product Owner decides intent, material trade-offs and final product acceptance; Planner chooses approved ready work; Executor implements; Independent Reviewer checks; Delivery Controller handles approved merge, CI/CD, evidence and Trello. See [authorization](docs/process/authorization-and-escalation.md).
- Follow the **actual Trello card scope** and native prerequisite checklist. **Before creating a `Prerequisites` checklist, inspect and reuse any existing prerequisites checklist** (including differently named equivalents); never create a duplicate checklist or duplicate items. **Each prerequisite item is exactly one bare Trello card URL** (`https://trello.com/c/...`), with no Markdown `[AIR-N](url)`, AIR-ID prefix, label or extra prose, so Trello shows the live card title and status. See [Trello conventions](docs/process/trello-card-conventions.md). Keep cards atomic; separate offline implementation, tests, shadow, production cutover and stabilization. Do not pick a next task merely from a remembered AIR number.
- Trello cards/comments and messages to Cursor are **Russian**; GitHub PR/reviews, repository docs and technical code discussions **English**. Preserve code identifiers.
- No direct main commits without explicit approval. An approved routine PR includes Controller merge after independent review, resolved blocking threads and green CI on exact HEAD. Routine Mermaid changes require actual rendered independent QA, **not** routine owner sign-off; new material architecture/product/security decisions and explicit exceptional gates stay owner-controlled.
- Before changing a local checkout, run `git fetch origin main` and inspect remotes, HEAD, branch, tracked/untracked changes, and divergence from `origin/main`. Preserve other work; no force push, destructive reset or silent overwrite. When working solely through GitHub APIs, read current `main` and use expected-head checks on ref updates.
- Validate changes with `npm ci`, `npm test`, `npm run build` when running locally, then check GitHub Actions. A PR run tests/build only; after merge or owner-approved direct main commit, confirm that `Test and build`, `Test shard 2 of 2` (the suite runs as two shards; the deploy needs both) and `Deploy to Cloudflare` reached success before marking Done. Report exact commit, PR, evidence and limitations in Trello.
- [Documentation routing and acceptance](docs/process/documentation-governance.md) is mandatory for every technical task. Each card, implementation handoff and review must state affected documentation paths, or `Documentation impact: none` with a concrete reason. Missing required documentation blocks acceptance.
- Documentation is part of Definition of Done. Changes to runtime topology, persistent data flow, security/trust boundaries, integrations, deployment or operations must update the affected [architecture diagrams](docs/architecture/README.md), [reference](docs/reference/README.md) and [runbooks](docs/runbooks/README.md) in the same PR. Record material durable decisions as [new ADRs](docs/adr/README.md); supersede rather than silently rewrite accepted decisions. Dated test results belong in [evidence](docs/evidence/README.md). Check whether this guide, `CONTRIBUTING.md` and root `README.md` also need changes.
- For UI work, follow [Visual QA](docs/process/agent-workflow.md): check a local browser at desktop and mobile widths and put a short written report in the PR. Do not create, save, download, attach, or commit screenshots. For Mermaid work, syntax or CI alone is not visual QA: inspect actual GitHub rendering, legibility and arrow semantics.

## Ways of work with the owner

- Address the owner informally in Russian («ты», never «вы»/«ваш»). Chat with the owner and Trello comments are Russian; GitHub PRs, review replies, commit messages and repository docs are English.
- Times in chat with the owner and in Trello comments are Europe/Madrid (state the zone, e.g. «09:52 Madrid»), with UTC added in parentheses only where it matters for logs, CI runs or snapshot identities. Repository docs and evidence stay in UTC. Schedule windows (Scheduled Tasks, quiet windows) are reasoned about in Madrid time as well, DST included.
- Role names are independent of tool providers. An authorized Controller maintains Trello evidence/completion; the Executor records fix/review handoffs. Product acceptance stays with owner unless scoped technical acceptance was delegated.
- Independent review is mandatory: assess actual diff, tests, docs, safety and accepted criteria against exact PR HEAD; resolve blockers, rerun CI after fixes and never self-approve.
- When a real PR event subscription is available, the Executor/Controller follows it to terminal status. Otherwise persist handoff in GitHub/Trello; a chat session is not a continuous event listener. No special ChatGPT branch handoff for routine ADR/Mermaid documentation fixes.
- **Never create, enable, disable, reschedule, edit, or manually run a ChatGPT Scheduled Task without the owner's explicit, operation-specific authorization.** This includes one-time reminders, CI/deployment polling, follow-up checks and other allegedly helpful background work, even when the underlying work item or routine delivery is approved. Do not infer consent from a request to finish a PR, monitor CI, wait for deployment, or avoid handing control back. Use available in-session checks; if continued observation is impossible, persist the blocker/handoff in GitHub/Trello. See [authorization](docs/process/authorization-and-escalation.md#chatgpt-scheduled-task-authorization).
- Authorization follows [L0–L3](docs/process/authorization-and-escalation.md): verified safe observation and approved routine delivery need no per-step prompts; L2 writes require an operation-specific standing contract; L3 needs an owner-approved plan and holdpoints. This docs-only change authorizes no new production writer.
- Report outcomes plainly with commit, PR, CI run and test evidence; say what was skipped or could not be verified rather than rounding up.

## Production and security boundaries

- GitHub `main` is authoritative code. Production runs on Cloudflare Worker `iptv` with R2 bucket `iptv` and D1 database `iptv`. **Storage authority is per domain, not per database:** the production D1 `iptv` (its schema version and every authority marker are read live; the projector run summary of 10 Nov 2026 reported `schemaVersion` 18) owns the metadata cache, mutable prediction state, published EPG/programme/watchlist generation (`published_epg_authority.mode=d1`, `cutover=open`), Admin owner reviews (`owner_review_authority.mode=d1`, generation 1) and the mutable ratings documents (`ratings_domain_authority.mode=d1`, `cutover=open`, generation 12); the discovery authority marker is `d1` / `open` (activated 2026-11-04 UTC, [activation record](docs/evidence/d1-migration/air-320-discovery-activate-2026-11-04.md)), so the Discovery ledger, decisions, catalog admission, continuation and lease are D1-owned and the Cloudflare Discovery Workflow is the executor (accepted under [AIR-324](https://trello.com/c/kNtaEbm8)); R2 still owns Film/Person sources outside the D1-owned cache and the immutable Discovery observation segments. R2 also retains ratings events, immutable prediction bodies, raw inputs/archives, published compatibility mirrors and the owner-review mirror. Migration `0009` is applied, the object is imported, and the marker was set to `d1` at 2026-11-03 23:13 UTC ([activation record](docs/evidence/d1-migration/air-314-owner-review-activate-2026-11-03.md)). The historical ChatGPT Site is **reserve**, not a parallel writer. Verify the current authority markers and run state before acting: an installed D1 schema, imported rows or R2 mirror alone does not prove a live cutover. See [deployment](docs/runbooks/deployment.md), [persistence diagram](docs/architecture/persistence-and-migration.md) and [dated cutover evidence](docs/evidence/d1-migration/air-319-production-cutover-2026-11-03.md).
- `/mcp` uses owner-only `IPTV MCP` Cloudflare Access with Managed OAuth **and** signed JWT checks in the Worker (issuer, audience, expiry and identity). The broader Worker is also Access-protected. Never weaken Access, add bypasses, expose credentials or allow arbitrary MCP URL/R2 keys/routes. See [MCP reference](docs/reference/api/mcp.md).
- External ChatGPT Scheduled Tasks are **not** Worker Cron. Since the AIR-348, AIR-347 and AIR-324 cutovers only the personal Predictions depend on a ChatGPT Scheduled Task: the hourly Predictions Task (Stage B only); the Drift monitor is a registry-only check, and the Daily EPG and Ratings Tasks are retired and disabled ([scheduled-task contract](docs/reference/scheduled-tasks.md)). Deployment does not trigger EPG, discovery, TMDB, predictions, ratings refresh, scheduled Tasks or R2 migration. The Worker has one cron trigger (`0 * * * *`), and each tick calls the following independently. The D1 enrichment projector ([ADR 0056](docs/adr/0056-d1-enrichment-write-through.md)) reads R2, never writes it, and does nothing unless `D1_ENRICHMENT_WRITE` is `dry` or `on`; its exclusive window ([ADR 0103](docs/adr/0103-projector-exclusive-window.md)) and grouped write path ([ADR 0106](docs/adr/0106-bulk-projector-write-path.md)) sit behind `D1_ENRICHMENT_WINDOW` and `D1_ENRICHMENT_BULK`. The Ratings `ensure` ([ADR 0090](docs/adr/0090-ratings-cloudflare-workflow-executor.md), Accepted) makes the Cloudflare Ratings Workflow the routine ratings writer while the D1 mode document says `cloudflare`. `EpgOrchestration.ensure` ([ADR 0100](docs/adr/0100-epg-cloudflare-workflow-executor.md), Accepted; [ADR 0108](docs/adr/0108-epg-mirror-reconciliation-writer.md)) makes the Cloudflare EPG Workflow the daily publication while its mode document says `cloudflare`, and on every hourly tick reconciles R2 compatibility mirrors of the published D1 generation (idempotent; GET never does that). It creates no Workflow instance while the mode says `external`. `reconcileDiscoveryWorkflow` ([ADR 0093](docs/adr/0093-discovery-workflow-cron-reconcile.md), Accepted) creates Workflow instances only while `DISCOVERY_EXECUTOR` is exactly `workflow`. The monitor's `Monitor.run` ([ADR 0095](docs/adr/0095-cloudflare-native-production-monitor.md), Accepted) does nothing unless `MONITOR` is `on` (a permanent emergency gate that accepts only `on` and `off`). The `feature_flags` tool read `D1_ENRICHMENT_WRITE`, `D1_ENRICHMENT_WINDOW`, `D1_ENRICHMENT_BULK`, `DISCOVERY_EXECUTOR=workflow` and `MONITOR` as set on 10 Nov 2026; the EPG and Ratings modes live in D1 documents. Verify present task/flag/mode/run state from authorized live sources; never infer from historical docs.
- Do not run extra production sync, predictions, ratings, discovery, lease reset, flags, schedules, migrations, imports or cutovers outside an **existing authorized L2 operation contract** or **owner-approved L3 plan**. No new writer is authorized by AIR-358; deployment never grants permission for an unrelated data operation.
- The discovery pipeline executes **one chunk per explicit request**; internal `DiscoveryContinuation` is not a public API, independent Worker or self-fetch with forwarded cookies/tokens. No audited GET endpoint or MCP read tool writes or repairs stored state any more: repairs belong to named writers (the EPG hourly ensure for mirrors; `prediction_start` for expired runs and undelivered run events). What a read may still do (one registered outbound TMDB probe) is the baseline in [read side effects](docs/reference/api/read-side-effects.md) ([ADR 0107](docs/adr/0107-get-head-read-side-effect-boundary.md), Accepted), checked by `tests/get-write-audit.mjs`; a new read route or MCP tool must pass it and a new writing read needs an ADR change. Consult that baseline, the [older R2 test](tests/get-side-effects.mjs) and the [runbook](docs/runbooks/deployment.md) before treating a production read as safe; classify a potentially writing production probe as L2/L3 until its exact side effects and authority are verified and approved.
- Code rollback does **not** revert R2 or D1 data, D1 authority markers, Cloudflare Access configuration, secrets, or external Task schedules. An EPG authority revert and its compatibility-mirror checks need their own fenced, owner-approved procedure; do not assume a deploy undoes a storage cutover. Do not republish, browse or operate the legacy Site without separate approval; preserve confidential production payloads outside public docs, fixtures, GitHub and logs.
