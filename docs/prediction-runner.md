# Continuous prediction runner v5

The same start/next/submit/complete protocol serves manual and scheduled triggers. Read GET /api/enrichment/runner before every launch. Its contract supersedes the obsolete v3 single-batch/deadline instructions. ChatGPT reaches this protocol through the MCP tools in [docs/mcp.md](mcp.md): `enrichment_runner`, `prediction_start`, `prediction_next`, `prediction_submit`, `prediction_heartbeat`, and `prediction_complete`. Those tools fix the scope to `watchlist_all`, the mode to `queued`, and each next/submit step to one film. The HTTP routes remain the contract. Enabling the hourly Scheduled Task is a separate decision.

1. POST start with scope watchlist_all, mode queued and trigger scheduled/manual. Supply real known capacity only. Do not impose a total-film or time cap.
2. already_running is a successful no-op: never adopt another trigger's runId. busy is transient contention; retry with bounded backoff, without starting concurrent generation.
3. Read next, generate only requested work using the unchanged schema/profile/scoring rules, and submit each film immediately. Repeat next/submit across batches continuously.
4. Before model calls renew POST heartbeat; renew concurrently every 10 minutes if an individual call can last that long. Checkpoints also renew automatically. A 15-minute persistent R2 CAS lease stores owner/runId, heartbeatAt and expiresAt. Expired owners cannot submit. Crash checkpoints survive takeover.
5. next re-evaluates hot urgency before every selection. Cold may run only while hot has no outstanding work. Model call batching remains disabled. Valid fingerprints/predictions are reused; timeslot changes never invalidate them.
6. An isolated malformed/invalid film output is reported through submit items[].failure.kind (parse_error or validation_error), is persisted as a retryable item failure and must not end the run. Failed items are skipped within that run and deferred by a 1-hour exponential retry (maximum 6 hours). Five consecutive distinct format failures trigger format_error_storm. mustComplete means call complete with stopReason. At actual quota/model/API/storage error, complete with a short safe reason and retain all saved predictions. No credentials in outputs, URLs, Events or persisted error reasons. A killed process recovers through lease expiry.
7. Progress Events aggregate the run every 50 successful predictions or 30 minutes, whichever comes first; the final event is separate. Check heartbeat/next/submit to emit time-based progress during active work. Successful empty checks don't spam Events. Eligible queue exhaustion with deferred item retries is a normal completion, not a run interruption.
8. A formed response does not prove the client received it. Send or read `X-Request-Id`; the same id is returned as `requestId`. On an external stop, `complete` may include `fault` (`origin`, `failedStep`, `providerErrorCode`, `httpStatus`, `receivedRequestId`). Omit `fault` when the cause is unknown. `firstNextAt` is not a successful `next`. See [AIR-88](air-88-run-diagnostics.md).

Run counters and film outcomes persist after each submission. Current-batch film reads stay bounded; completed batches are counted from saved outcomes rather than loading every completed film on every next request.

Tests: node tests/continuous-drain.mjs; node tests/throughput.mjs; node tests/enrichment.mjs. The multi-batch integration test uses an isolated R2 implementation and deterministic validated model outputs; it is not a production LLM throughput benchmark.

## ChatGPT Scheduled Tasks: timing and troubleshooting

**The hourly schedule is a target, not an exact Worker execution time.** The ChatGPT Scheduled Task is external to Cloudflare Worker `iptv` (there is no hourly Cloudflare Cron driving predictions). A nominal `:00` trigger can begin around the hour rather than precisely at `:00`; delays can vary and there is **no documented guaranteed ±10-minute window**. The footer's `Следующий запуск: около HH:MM` is calculated from `nextScheduledRun` as an **estimate**, not a countdown, SLA, or evidence that a new run has started. Times shown in the app use Europe/Madrid.

**Do not infer scheduler accuracy from /events timestamps.** A `Прогнозы запущены` event records a server-side run start; `Прогнозы восстановлены` or `Прогнозы продолжены` describes a lease recovery/continuation, not necessarily a fresh scheduled trigger. Progress/completion events can appear much later. In the Events history captured on 15–21 October 2026, visible event times included minutes around `:50` through `:07`, plus a `:22` outlier; these mixed event types do **not** establish a reliable scheduler start-time distribution. For exact scheduler triggers, inspect the Scheduled Task execution history separately.

**An unchanged status is not a missed trigger.** The footer can retain a previous `storage_error` until a later run emits updated state, and an invocation with `already_running`, `busy`, or `noop` may not produce a new Events entry. Verify independently:

1. Check the ChatGPT Scheduled Task is enabled and review its last execution time/result; do not treat the next nominal clock hour as a deadline.
2. Via authorized IPTV Watchlist MCP, inspect `enrichment_runner`, `enrichment_status`, and `enrichment_queue`, including `runId`, `state`, `lastHeartbeatAt`, `hotRemaining`, `coldRemaining`, and retry/backoff.
3. `pendingCount=0` only means no immediate *hot/watchlist* work. It does **not** mean the full database is complete if `coldRemaining>0` (the queued runner can process off-watchlist cold films). Validate complete coverage using `confirmedFilmsTotal` versus `currentPredictionsTotal`, not the viewing-window counter. `localPercent` and `windowPercent` are tenths of a percent. The value `100` means the two counts are equal, or that the denominator was empty. An incomplete pair stays at or below `99.9`. A finished run and `queue_empty` are also separate from those counts: outstanding films can remain in retry backoff. See [AIR-82](air-82-prediction-rca.md).
4. Check /events for the corresponding run's start/resume, progress, and terminal event. If a run is stuck or `storage_error` recurs, inspect authorized Cloudflare logs and stored checkpoints rather than forcibly clearing leases or resetting the queue.

Keep existing Cloudflare Access protections; don't embed auth tokens in links, logs or documentation. Do not trigger extra production sync or prediction runs just to test timestamps. The legacy Sites-specific prompt in [prediction-scheduled-prompt.md](prediction-scheduled-prompt.md) is historical and must remain disabled.

The Scheduled Task itself is outside this repository. Until that task sends `fault` and echoes `receivedRequestId`, caller-reported metadata on a production run stays unconfirmed. The Worker records the attempt and the response it formed either way. The caller change is specified in [AIR-88](air-88-run-diagnostics.md).
