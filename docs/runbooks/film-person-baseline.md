# Film/Person baseline: parity ledger, bounded import and the `prepared` gate

**Role:** the procedure and the tooling of [AIR-373](https://trello.com/c/ugu3sQmp) stage A for the baseline of canonical Film/Person ([ADR 0099](../adr/0099-canonical-film-person-d1-authority.md), C6a): how D1 is proven equal to the state derived from R2, how a difference is repaired, and what must be true before the baseline row can be recorded as verified and before the marker may leave `r2`. The schema steps are in [the schema preflight runbook](film-person-schema-preflight.md). **This page authorizes nothing:** the R2 snapshot export, the bounded baseline import, recording the baseline and the `r2` to `prepared` move are each a separate, operation-specific owner decision with its own readback. The module is inactive: it is not bundled and no Worker route, job or cron calls it.

Tooling: [`src/film-person-baseline.js`](../../src/film-person-baseline.js), tested by `tests/film-person-baseline.mjs` on fixtures and the sqlite stand-in (no Worker, R2 or production access).

## What is built (stage A)

| Part | What it does |
| --- | --- |
| Parity ledger (`buildParityLedger`) | Compares an expected side with the actual D1 side per class (`film`, `person`, external ids with trust, aliases, credits, owner/reviewed localization, watchlist membership, redirects, TMDB retirements, rated admissions, retention, owner-review links, projector keys): counts, order-independent sha256 digests, differences `missing` / `extra` / `differs`. Lists name keys only (never a title, name or payload) and are bounded (200) with a truncated flag; the planner still gets every difference. Deterministic: one input, one ledger digest. |
| Explanations | A difference is **explained** only by a per-class, per-side rule (`DEFAULT_EXPLANATIONS`) or by an owner exception (class C) that carries a reason and the approving owner; an exception without both is ignored and counted. The rules: a D1-only TMDB credit in the role of its id on a watchlist Film; the rows of a Person explained by **verified AIR-286 provenance** or by an owner Person exception (see below); Films kept by retention or a rated admission. No default rule explains a missing or differing row, so a differing owner localization is never explained, and **a Person without a projector key is not explained by being unkeyed**. |
| Encoding contract (`VALUE_COLUMNS`, `encodeValue`) | One canonical encoding of every class value, used by both the expected side (`expectedFromInputs`, owner extras) and the D1 reader: a JSON array of the class's value columns in a fixed order, integers coerced (booleans to 0/1), absent text as `null`; a class with no value column (`filmAlias`, `personAlias`, `watchlist`) is `[]`. `encodeValue` throws `baseline_encoding` on a wrong shape. The test seeds the sqlite stand-in with the rows `expectedFromInputs` implies, reads them back and requires a ledger with zero differences and zero unexplained, then mutates one row per class and requires exactly that class to differ. |
| D1 reader (`readD1State`, `readStableCut`) | Keyset pages (default 500 rows, at most 400 queries per call) with a resumable state; an optional table that does not exist (for example a schema below 16) makes its class **unavailable**, never empty. `readStableCut` is the baseline read; see **The read cut**. |
| Delta plan (`planReconciliation`) | From the unexplained differences: one Film unit per missing or differing Film and People groups of 25 (the projector's own batch sizes). Extras and the classes the projector does not own (redirects, retirements, admissions, retention, owner links, projector keys) are listed for an owner decision and are **never applied by the importer**. Each unit carries the digest of the D1 rows it was planned against. |
| Importer driver (`runImport`) | Applies a unit through an **injected writer** (in production the projector's repository under the projector's lease and fence, as `scripts/d1-projection-seed.mjs` does with a seed lease; the fenced AIR-367..370 mutations are for the open state and are not used). A write-ahead checkpoint is saved before and after each unit; a unit whose D1 rows changed since the plan is skipped as stale; the marker and the lease are re-read before each unit; an unknown outcome is settled by readback and never retried blindly (one re-apply, only after a readback that says not applied); a lost lease stops the run with the unit still in flight; a crash at any save point resumes by readback without applying a unit twice. |
| Gate and recorder (`baselineGate`, `markBaselineLoading`, `recordBaselineVerified`) | The gate passes only when the ledger is complete, the read was consistent, the source identity is a verified sha256 digest, every class was compared, nothing is unexplained and the ledger digest still matches its content. Recording runs in **one batch** that proves the marker is `r2` / `open` at the expected generation, moves `film_person_baseline` empty or loading to verified with the ledger digest as the reference (through the triggers of migration 0013), and never moves the marker. |

`expectedFromInputs` turns the projector's own view (`enrichmentInputs`) into the expected classes, so the expected side is what the projector would write. The caller derives the classes the view does not carry (retirement, admission, retention, owner links, redirects, projector keys) from the same sources.

## The read cut (what "consistent" means here)

D1 offers no snapshot isolation across statements, so two reads of the marker are not a snapshot. `readStableCut` combines two things and is honest about the rest:

1. **The projector's lease.** It acquires the `enrichment` lease in `projection_run` with the projector's own SQL before reading, renews it at every page, checks at every page that the row still names it (holder and `started_at`), and releases it in a `finally`. A live foreign lease means nothing is read (`lease_unavailable`); a taken or lost lease aborts (`lease_lost`). While it is held the projector cannot write: in `r2` and `prepared` the enrichment projector is the only canonical Film/Person writer (the fenced AIR-367..370 writers are for the open state and dormant).
2. **A content witness.** Per table: row count and the maximum of `updated_at` / `projected_at` / `revision` and the like, taken at the start, again for the table just read at every page boundary and for every table at the end. Any difference refuses the read as `unstable_cut:<table>`. Marker and baseline row are compared at the start and the end (`marker_moved`, `baseline_changed`).

**What the cut does not cover.** A writer that does not take the projector lease is caught only by the witness, which is a fingerprint, not proof: it misses a write that leaves every witnessed aggregate unchanged, or a change reverted between two witnesses. One-off owner operations (the AIR-286 credits script, owner-review writes, Admin routes) do not take the lease. The measurement is therefore valid for the moment of the read only, and the baseline must be read with those operations quiet. Production liveness of this path against the real projector repository is unmeasured (tests inject the writer and use the stand-in).

**Person provenance.** A Person with no projector key is D1-only by construction only if it is an AIR-286 Person (`scripts/tmdb-watchlist-credits.mjs`). `verifyAir286` accepts one only when all hold: id `person:tmdb_director/<n>` or `person:tmdb_actor/<n>`; `role_id` equal to the id without `person:`; contract version 1; exactly one alias of kind `name` whose provenance is `{"source":"tmdb","task":"AIR-286"}`; no external ids and no dimensions; at least one credit, each in the role of the id on a watchlist Film (a Film with a Letterboxd id or a watchlist row). Anything else stays unexplained and the gate stays closed. The owner may instead list a Person id in an exception (id, reason, approving owner); it explains exactly that id (and only when the Person exists in D1 without a projector key), never another Person's child rows.

## What each production step still needs

Nothing below is done by this stage; each is a separate owner GO after the previous one is proven.

1. **Projector liveness.** A stalled projector makes any parity measurement stale at once. The read-only liveness evidence ([baseline inventory](../evidence/d1-migration/air-373-baseline-inventory-2026-11-08.md)) shows sustained starvation (no write since 02:38 UTC on 8 Nov; no Film since 5 Nov); its fix is a separate task and a dependency of the baseline, not of this tooling.
2. **R2 snapshot export (read-only).** The expected side needs a consistent fenced snapshot ([export procedure](r2-snapshot-export.md)); it is taken after the tooling and the read-consistency conditions are ready, so it is not stale on arrival.
3. **Measured ledger.** Build the expected side from the snapshot, read D1 consistently, build the ledger, review every unexplained difference and every owner exception with the owner.
4. **Bounded baseline import.** Only for the units of a ledger that cannot be left to the projector, through the projector's writer and lease, resumable, with a readback of every unit; a fresh ledger afterwards must show zero unexplained differences.
5. **Recording the baseline.** `markBaselineLoading` at the start and `recordBaselineVerified` with the passing ledger.
6. **`r2` to `prepared`.** `transitionAuthority` from the generation read, only against a verified baseline; the projector stays the only canonical writer in `prepared`. Recovery before activation is the reversible `prepared` to `r2` move.

## Boundaries

A passing gate is evidence, not a permission, and a ledger digest names one measurement: a later write by the projector or a producer makes it stale. Unmeasured by this stage: the real expected side (R2), per-entity hashes of production, the class-C exceptions and the real counts. The producer writes no fenced mutation covers yet ([AIR-371 evidence](../evidence/d1-migration/air-371-producer-routing-offline-2026-11-07.md)) block the cutover, not this baseline. A code rollback reverts neither the baseline row nor any D1 row.
