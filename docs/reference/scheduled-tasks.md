# Production ChatGPT Scheduled Tasks — operational contract

This is the maintained **expected behavior** of the ChatGPT Scheduled Tasks for IPTV Watchlist. Since the Cloudflare EPG cutover ([AIR-348](https://trello.com/c/PUrlzMuH), accepted 8 November 2026), the Discovery Workflow ([AIR-324](https://trello.com/c/kNtaEbm8), accepted 7 November 2026) and the Ratings Workflow ([AIR-347](https://trello.com/c/j2Ua76yv)), **only personal Predictions depend on ChatGPT Scheduled Tasks**: the [four hourly Predictions v2 Tasks](#predictions-v2-four-active-hourly-tasks-00153045). The [read-only drift monitor](#read-only-drift-monitor) in the same registry is not a producer. The legacy [Daily EPG Task](#daily-programme-update-retired-task) and the legacy [Ratings Task](#ratings-task) are retired and disabled. Registry baseline read on 10 November 2026 ([AIR-406](https://trello.com/c/PPe2fFcu)): 16 Tasks, 2 enabled (the hourly Predictions Task and the drift monitor) and 14 disabled. `RATINGS_PIPELINE` is retired ([ADR 0074](../adr/0074-retire-ratings-pipeline-switch.md)): the Worker does not read it. The authoritative status, schedule, timezone and executable prompts for ChatGPT Tasks are in the **live ChatGPT Scheduled Tasks registry**, outside GitHub; the state of the Cloudflare executors is in Worker D1 and its read-only status. GitHub Actions deployment does not run, edit or enable these tasks. An enabled task is not proof of successful execution. For runner and MCP details see [prediction runner](api/prediction-runner.md), [MCP tools](api/mcp.md), [prediction operations](../runbooks/prediction-operations.md) and [scheduling architecture](../architecture/scheduling-and-orchestration.md).

EPG, Discovery and Ratings are Cloudflare-owned. EPG: the Cloudflare EPG Workflow ([ADR 0100](../adr/0100-epg-cloudflare-workflow-executor.md), Accepted; `epg_status` read `mode=cloudflare`, epoch 1 on 8 November 2026). Discovery: the Cloudflare Discovery Workflow (permanent since AIR-325; the `DISCOVERY_EXECUTOR` selector is retired and ignored). Ratings: the Cloudflare Workflow under [ADR 0090](../adr/0090-ratings-cloudflare-workflow-executor.md) and the shared [ADR 0089](../adr/0089-shared-orchestration-reliability-contract.md) contract ([reliability reference](orchestration-reliability.md)). The Worker refuses the write paths of the retired Tasks with `external_writer_fenced`. Changes to any Task or domain mode remain separately gated.

### Legacy contract (rollback only)

The bullets below are the contract of the retired Task as it ran before the cutover. They are kept for a separately approved reverse cutover and for reading the dated evidence; they do not describe the live system.

- **Authority:** connected owner-only IPTV Watchlist MCP to Cloudflare Worker `iptv`; storage authority is per domain (D1 markers; R2 holds blobs, inputs and mirrors). Never use legacy Sites, direct HTTP, Cloudflare Cron, a browser or local CSV as a production substitute.
- **Preflight:** `probe_read`, `epg_status`, `epg_pipeline_status`; stop safely if unavailable, unauthorized or inconsistent.
- **Execution:** exactly one `epg_sync_start({})` for this invocation, using only its returned `runId`; sequential `epg_sync_step({runId})` through metadata and programme publication; stop on ownership/lease conflicts, terminal errors or unsafe retries. Do not adopt another run.
- **After programme publication:** follow `discovery.nextAction`: `continue` means one further explicit `epg_sync_step` (at most one discovery chunk per call), `wait` means honor `nextCatchUpAt`/backoff, `stop` ends that sequence. Persisted outstanding chunks may be continued by the hourly task. EPG completion does not imply discovery completion. Since [ADR 0030](../adr/0030-discovery-queued-at-publication.md) the discovery series of the published generation is opened before the commit's tail, so a commit interrupted after publication shows outstanding chunks while `epg_status.stage` is still `epg`; a step in that state retries the commit on its resume path (no EPG download, no TMDB). That retry belongs to this daily task, never to the hourly task.
- **Completion:** read `epg_status`, `epg_pipeline_status` and `enrichment_queue`; distinguish published programme, pending discovery and `ratingsPending`. Ratings/Letterboxd HTTP 403 are not reasons to restart EPG. Do **not** run predictions or modify the Taste Profile in this task.
- **Ratings ownership:** the task calls no ratings tool of its own. Production runs ratings through the [Cloudflare executor](#ratings-task-and-the-cloudflare-executor-air-347). On supported storage this task's `epg_sync_step` does not read Diary. On any other stored state it still publishes and records `ratingsPipeline: blocked`; it does not read Diary. A Ratings Workflow failure is not an EPG publication failure when `epg_status.stage` is `complete`.

## Hourly predictions

**Predictions producer contract.** The four enabled external hourly batch v2 Scheduled Tasks, scheduled at :00/:15/:30/:45 Europe/Madrid, each start an owned manifest through `prediction_batch_start`, process selected films individually (`generationSize=1`), validate and submit buffered results (`submitBatchSize=5`, `manifestSize=5`), and call `prediction_complete` under their shared lease and per-run budgets. The nominal recurrences are hourly at `:00`, `:15`, `:30` and `:45` Europe/Madrid (a fifth registry entry, `:48`, is disabled); verify the actual schedules, enabled state and executable text in the live registry rather than treating this page as live operational evidence. A source-reading audit and any `fullTextFallback` explanation belong in the Task's saved report, not in the Worker assessment schema. The Task distinguishes genuine `full_text`, `partial_text`, and `search_snippet`, uses source-selection/full-text fallback audit, observes the two-search-per-film limit and records actual access errors rather than imputing them. On `deferred_budget`, reuse the exact preflight-approved submit item or preflight the actual item again if its identity was lost; no separate client-side enum validator is required. See the [maintained batch prompt](scheduled-task-prompts/hourly-predictions-batch-v2.md) and [research diagnostics runbook](../runbooks/prediction-operations.md).

### Retired v5 Predictions procedure (historical only)

The v5 tools this procedure names no longer exist ([ADR 0167](../adr/0167-retire-prediction-runner-v5.md)); it records how the retired Task worked.

**Workflow instance budget ([ADR 0094](../adr/0094-discovery-workflow-invocation-budget.md), Accepted).** An instance counts the D1 statements it issues and hands over to a successor at 6,000, besides the 20 chunk limit. A failing step logs one `discovery_workflow_step_failed` line (step, code, bounded cause, statement and batch counts) and the executor record carries `invocation.statements` and `invocation.batches`. The external executor in the legacy section below is not part of the live prompt.

- **Historical Task:** `Почасовые прогнозы «В эфире»` (legacy v5). Before the v2 cutover it was enabled hourly, nominally `:20` Europe/Madrid, with `default_timezone: Europe/Madrid`. This is a historical description, not the current production state; the v2 Task A is listed above. A scheduled trigger was never an exact-time SLA.
- **Stage B — full prediction queue:** read `enrichment_runner`, `enrichment_schema`, `enrichment_profile`, `enrichment_queue`, `enrichment_status`; ensure `prediction_validate` is exposed before a new prediction run. Run `prediction_start({trigger:'scheduled'})` once; for a fresh owned `runId`, call `prediction_next` immediately and process server-sized batches without an invented time or film cap. Respect `already_running`, leases and retry/backoff; a `blocked` start with `code: prediction_retry_heal_pending` selected nothing and is retried by the next scheduled trigger, never by resetting the lease. The same holds for `503 {status: "blocked", code: "prediction_catalog_held"}` on start: an EPG publication holds the catalog, the start kept no lease and selected nothing, and a later trigger tries again. The **expected** Worker contract for the same 503 on `prediction_next`, `prediction_submit` or `prediction_complete` of an owned run is a wait, not a stop: keep the `runId`, do not complete, retry that step for at most one 15-minute lease with heartbeat, then leave the run for ordinary lease expiry. The **live** hourly Task prompt (independent review read-only capture, 10 November 2026) does not name `prediction_catalog_held` and still tells the caller to `prediction_complete` on a systemic error; that prompt is not edited here. Proposed Russian patch is in [AIR-424 evidence](../evidence/prediction/air-424-next-discovery-fence-2026-11-10.md). An identical `prediction_submit` after that 503 is idempotent (`already_current`). Consider **hot, cold and deferred** coverage, not just `pendingCount`.
- **Required validation before every prediction submit:** generate the complete intended `prediction` and, only for `fingerprint_and_prediction`, the complete intended `fingerprint`. Invoke `prediction_validate` on those **exact** objects. Require `success===true`, `valid===true` and `contractVersion===enrichment_schema.contract.version`; the Worker sets `success` and `valid` to the same verdict, so a report with one of them `false` carries at least one issue to correct. For `fingerprint_and_prediction`, both `fingerprint.checked` and `prediction.checked` must be true. For `prediction_only`, `prediction.checked===true` and `fingerprint.checked===false`; reuse the Worker-supplied fingerprint. Revalidate after any change. Validation issues must be corrected and rechecked, with a bounded retry count; do not submit unvalidated payloads. An unavailable validator is a **fail-closed** condition (`prediction_validate_unavailable`), not permission to bypass preflight. The same fail-closed classification applies to a tool error (`isError: true`) and to a report that lacks `success` or `valid`: that is a tool or contract problem, not a schema violation of the generated objects, so it must not be recorded as a per-item `validation_error` and must not defer the film. A contract-permitted per-item validation failure may be submitted as a failure result; never fabricate a successful prediction.
- **Batch sizes in force:** one film per `prediction_next` (`batchSize: 1` is sent by the MCP tool), one per `prediction_submit`, one model generation per film (`modelBatching.enabled: false`), a run selection of at most 12 while capacity is unknown and at most 20. The measured cost of each ([AIR-438 evidence](../evidence/prediction/air-438-step-latency-and-batch-sizing-2026-11-11.md)) is the basis for any later change; none is authorized by this page.
- **Completion and evidence:** use `prediction_submit` only after successful preflight; inspect **each** item result (HTTP 200 alone is insufficient). Process `prediction_next` and `prediction_heartbeat` as required by the lease, then call `prediction_complete` only for an owned run and an allowed stop condition. Re-read `enrichment_status` and `enrichment_queue`; failures or deferred items must not be described as full coverage. Do not mutate profile, flags or other running tasks.

### Batch runner Tasks (four active schedules)

**Current configuration.** The Worker's `prediction_batch_start` and `prediction_batch_submit` tools are implemented and four external batch v2 Tasks are enabled at the latest registry readback; a fifth entry is disabled. [ADR 0122](../adr/0122-prediction-batch-runner-v2-dual-protocol.md) and the [batch runner v2 contract](api/prediction-runner.md#batch-runner-v2) remain authoritative for the protocol. Merging documentation never creates, enables or changes a Task.

- **One protocol.** Batch v2 is the only prediction protocol; the v5 tools are retired ([ADR 0167](../adr/0167-retire-prediction-runner-v5.md)). Several independent v2 Tasks may be enabled at once; they share one lease and queue, and an overlapping `prediction_batch_start` answers `already_running` and stops without adopting the `runId`. Check the live registry before relying on the dated enabled-state readback above. There is no feature flag.
- **Shape of one execution (v2).** Read `enrichment_runner` (the `batchRunner` block) → `prediction_batch_start` once with optional `manifestSize` (1..100, default 100; the ready-to-install template uses 5 per [ADR 0136](../adr/0136-prediction-batch-manifest-size-and-spent-complete.md)) → repeat { generate up to `generationSize` films (template 1; range 1–10), `prediction_batch_validate` the group (accepted read-only architecture, [ADR 0131 (Accepted)](../adr/0131-batch-candidate-preflight-tool.md); correct only what real knowledge supports, at most one re-preflight, otherwise a `parse_error` failure item with a required closed `reason`), `prediction_batch_submit` up to `submitBatchSize` items (template 5; max 10) } → `prediction_complete` with reason `manifest_spent` when every selected film is settled (normal complete even if ready films remain). The retired v5 tools are not available. Heartbeat before a model call that can last long and at least every 5 minutes; keep the `epoch` the heartbeat and each submit return. Each execution starts from a clean context and keeps nothing between executions.
- **Deferred start (ADR 0193, the target protocol of the Tasks; dormant until the prompts use it).** Each Task execution calls `prediction_batch_key` once, keeps the issued key, sends `prediction_batch_start({trigger:'scheduled', manifestSize:5, deferred:true, invocationKey})`, polls `prediction_batch_manifest` with the returned `retryAfterMs` (5 s, at most 3 minutes) until the envelope is ready (`manifest_pending` means keep polling; `start_refused` and `start_failed` end the execution), heartbeats **before** the remaining part reads and checks that it succeeded (the preparation holds a 180 s lease until the first heartbeat; a heartbeat during the persist answers `busy` and is repeated), and continues as before. A transport error on the start is answered by the same keyed start again (the run id is derived from the key, so a retry never starts a second preparation); the answers `accepting`, `start_finished` and `deferred_start_ambiguous` are in [the delta note](scheduled-task-prompts/hourly-predictions-batch-v2-deferred-start-delta.md). The minimal prompt change is [the delta note](scheduled-task-prompts/hourly-predictions-batch-v2-deferred-start-delta.md); the Controller changes the prompts, the Executor does not.
- **Task label (ADR 0195, the target protocol of the four Tasks; not installed until the owner-approved cutover).** Every call of a run carries the Task's fixed `taskId`. A repeated `prediction_batch_start` of the **same** Task while its lease is live returns the same stored manifest, or `start_pending` (read it with `prediction_batch_manifest`) while the first start still prepares it, and is never `already_running`; `already_running` means another Task holds the slot. A foreign or missing label on a labelled run is `wrong_owner` (stop, no `prediction_complete`). The label replaces the per-invocation key of ADR 0188 and ADR 0193 for these Tasks; those protocols stay in code, unchanged and unused. Success is a real committed forecast, never `start = 200`, `already_running` or a green CI.
- **Keyed start (ADR 0188, the synchronous variant; its caller-composed key is superseded by the issued key of ADR 0193).** A Task invocation passes one deterministic `invocationKey` (per Task and slot, identical on every repeat and model re-issue, never a fresh model-generated value) to every `prediction_batch_start` of that invocation; on `start_pending` it reads the manifest with `prediction_batch_manifest` (`manifest_pending` means not stored yet) or repeats the same keyed start, and never starts under a different key. The key source must be validated before any prompt rollout (see the ADR gate).
- **Stops.** `already_running`, `manifest_too_large` (nothing was created), `lease_lost`, `wrong_protocol` and `prediction_catalog_held` end the execution without a lease reset. `profile.scope: "global"` is stopped with `prediction_complete` reason `profile_changed`, and `contract_changed` with reason `runner_aborted`. After a lost response or a `502` the Task replays the same `prediction_batch_submit` body instead of regenerating, and on `submit_in_flight` waits `retryAfterMs` before that replay. For `deferred_budget`, the next submit reuses the exact preflight-approved item or preflights the actually reconstructed item if the original was lost. A `deferred_budget` or `stale_profile` item is not a failure of the run; a `validation_error` item is deferred by the existing retry policy and is not resubmitted.
- **Dry run.** A `dryRun: true` execution is a separate, owner-approved procedure that writes nothing to prediction state; it is not a scheduled Task. It keeps the one manifest it received and replays those same films at generation sizes 1 to 10 from that held copy, never re-reading the live queue between passes.
- **Prompt text.** The ready-to-install Russian prompt and its execution playbook are [`hourly-predictions-batch-v2.md`](scheduled-task-prompts/hourly-predictions-batch-v2.md) (AIR-449; `manifestSize` / `manifest_spent` under AIR-463 / ADR 0136; current identical installed snapshots for all four minute-named Tasks). A spent selected manifest with ready films left ends with `prediction_complete` reason `manifest_spent`: normal `status: complete` and a truthful Event, not `time_budget` and not «Прогнозы приостановлены». The controlled scale-out and acceptance of the Tasks are tracked in [AIR-451](https://trello.com/c/NN3N6kRp). The frozen dry-run prompt, the [A/B procedure](../runbooks/prediction-batch-v2-dry-run-ab.md) and offline report aggregator (`scripts/prediction-ab-report.mjs`, AIR-450) are test-only artifacts, not installed in the four production Tasks. `tests/scheduled-task-prompt-v2.mjs` checks its length, hash, tool names and a simulated run.

### Legacy Stage A: external Discovery executor (rollback only)

The bullets below are the Stage A text the hourly Task carried while Discovery was driven from ChatGPT (`DISCOVERY_EXECUTOR` absent, the external executor). They are **not** in the live prompt and are kept for a separately approved rollback of the Discovery executor. A spent series of 12 chunks waited for the next hour in that mode; the Workflow executor renews it without the hour wait ([ADR 0083](../adr/0083-inert-discovery-workflow.md), Accepted 2026-11-02; [ADR 0093](../adr/0093-discovery-workflow-cron-reconcile.md)). The real production switch was [AIR-324](https://trello.com/c/kNtaEbm8).

- **Stage A — safe existing-generation discovery catch-up:** call `probe_read`, `epg_status` and `epg_pipeline_status`. Never call `epg_sync_start`. **Make no `epg_sync_step` unless `epg_status.stage` is `complete`** ([ADR 0030](../adr/0030-discovery-queued-at-publication.md)). This gate applies to every stage A step, including the orphaned-`running` exception and the AIR-159 generation handoff of a stranded earlier-generation record. At `stage: epg` a step is a retry of the daily commit's tail, even when the published generation already shows outstanding chunks. Beyond the gate, continue discovery only when the published `programmeRunId` is unambiguous and the checkpoint authorizes either ordinary continuation with positive `remainingChunks` or the due exhausted-budget renewal described below. A zero budget is not by itself a completed backlog. No lease, backoff, retry or generation mismatch may block the step. Call `epg_sync_step({runId})` sequentially, one chunk per call, following `nextAction` and `nextCatchUpAt`. Do not manufacture run IDs, reset leases, force retries or start a separate TMDB/discovery job. If stage A cannot proceed, still attempt stage B **if safe**.
- **Due exhausted `chunk_budget` (AIR-299):** The hourly task must recognize a checkpoint with `continuation.stage=paused`, `reason=chunk_budget`, `remainingChunks=0`, and a valid `nextCatchUpAt` that is at or before the current time. This is a **new bounded series on the same published EPG generation**, not an orphan recovery, generation handoff, forced resolve, or a new EPG run. Require fresh read-only `epg_status.stage=complete`; a single nonempty `runId` identical in `epg_status`, `epg_pipeline_status.programmeRunId`, and `continuation.programmeRunId`; `continuationHealth.status=settled`; and no future `retryAt`, additional hard wait, terminal error, conflicting writer, or ambiguous ownership. Repeat **both** status reads and all guards immediately before the one ordinary `epg_sync_step({runId})` that reopens the budget. A `settled` health report with `lease=null` does not prove that no other writer owns a live resolver lease: the Worker must still enforce its lease and checkpoint CAS; stop on `busy`, wait, error, mismatch, conflict, or unknown outcome without retrying. After a confirmed response for the same published generation, follow only the fresh server `nextAction` and new budget, one chunk per request. Do not attempt a second budget renewal in the same task invocation. A persisted `discovery.nextAction=wait` for `chunk_budget` can remain `wait` after its stored time has passed, because the new budget is opened by the **next eligible step**, not by a background clock. This narrowly defined exception applies only to `paused/chunk_budget/0`, not `complete`, `interrupted`, `backoff`, or an old generation.
- **Interrupted series:** `continuation.reason: interrupted` stays `nextAction: stop`. Do not call `epg_sync_step` for it, and do not send a recovery flag: `epg_sync_step` has no such argument. The gated confirm is an owner resolve body outside this task ([ADR 0088](../adr/0088-guarded-interrupted-discovery-recovery.md), Proposed). After that confirm has stored an ordinary checkpoint for the same published generation (`reason` no longer `interrupted`, and the fresh contract says `continue` or a due `wait`), the next invocation of this task may take one ordinary chunk under the stage A rule above. Until that checkpoint is visible on a fresh status read, this task still stops. A `settled` health report on an interrupted record is not permission to step.
- **Seal `busy` (AIR-362):** a `stage: seal` answer with `discovery.state=busy`, `busyKind: lease_held` and a `nextCatchUpAt` no later than about 93 s away is a bounded wait for the writer whose step was cancelled: wait until `nextCatchUpAt`, then call `epg_sync_step` once more for the same `runId` and follow the fresh answer. Wait at most once per step; a second `busy`, `lost_race`, an error, mismatch or unknown result stops the invocation. No lease reset, no new run. The deployed contract does not edit the Task prompt; adopting the wait in a prompt needs a separate owner-approved change.
- **Projector window `busy` (ADR 0103, not active):** while the projector holds an exclusive window, an EPG step may answer `discovery.state=busy` with `busyKind: projector_window` and a `nextCatchUpAt` at the window's absolute deadline (up to about 300 s away), from the sync step or the seal step, without failing the run or persisting an error. The wait rule above covers only a `lease_held` seal busy within about 93 s, so a Task that follows this contract stops its invocation on a `projector_window` busy and reports it; the Cloudflare EPG executor sleeps until `nextCatchUpAt`. Waiting for the window in the Task needs a separate, owner-approved prompt or timeout change, which this document does not make; until then the feature flag stays off.
- **Orphaned `running` continuation — fail-closed exception:** A raw `continuation.stage=running` does **not** authorize a step. Only a fresh, read-only `epg_pipeline_status` from a compatible Worker can establish `continuationHealth.status=orphaned`, `lease=expired|none`, `generationConflict=false`, no live competing owner, and an exact match between the pinned `continuation.programmeRunId` and the published `programmeRunId` confirmed by `epg_status` and `epg_pipeline_status`. Require `remainingChunks` to be a positive integer and `resumeBudget` an integer from zero through `remainingChunks`. No hard wait or future `retryAt`/`nextCatchUpAt` may apply. With `epg_status.stage=complete`, only then may the hourly task call **one ordinary** `epg_sync_step({runId:publishedRunId})` for the same generation; the Worker is responsible for CAS, fencing and settle/resume. Missing health (including a pre-recovery Worker), `live`, `settled`, `unknown`, ambiguous owner, generation mismatch, invalid budget or a `busy` response means **do not call or retry**. Never infer recovery authority from an expired lease alone, change the task itself, reset a lease or create a new EPG generation. After any successful step, honor server `nextAction=continue|wait|stop`, current generation and budget; do not chain steps against a changing checkpoint. Worker behaviour, not a prompt rule: when the orphan's hop and the hop it was resumed from both ended before their checkpoint, the Worker answers this step with `stop` / `reason: interrupted` and runs no chunk (fail-closed, [discovery contract](api/enrichment.md#live-and-orphaned-running-records)); the task reads it as any other `stop`.

## Timing: nominal trigger versus server gate

The Worker cannot read the ChatGPT Scheduled Tasks registry and **does not store or derive the ChatGPT Predictions Task recurrence**. Cadences of those Tasks belong only to that registry; this page does not snapshot them. Enabled state, minutes and Task IDs stay with the live registry and with [AIR-451](https://trello.com/c/NN3N6kRp) / Draft PR #661. A `prediction_batch_start` is accepted or refused by lease, epoch, queue, retry and backoff, never by the minute of the hour. Three clocks stay distinct:

- **Scheduled Task registry.** Recurrence, timezone and enabled state of each Predictions Task. Owner-approved registry operations change them; a Worker deploy does not. Jitter means an invocation can start well after the nominal minute.
- **Worker timestamps.** Actual run start, heartbeat, complete, Events `at`, lease expiry. Evidence of work that reached the Worker. Stored Events keep the fields they were written with; this contract does not rewrite history.
- **Discovery gate** (`discovery.nextCatchUpAt` when `nextAction` is `wait`): the Worker's own earliest permitted step. For `chunk_budget`, an error and a pending generation it is the next whole UTC hour; for `backoff` the stored retry time; for a live writer its lease expiry. It throttles a new chunk series and fences concurrent writers. It is not a ChatGPT Task time. The Cloudflare Discovery Workflow renews the series itself. A `continue` or `stop` carries `null`.

Prediction and discovery wire fields still include `nextScheduledRunAt`. The Worker always answers `null`. In prediction responses `nextCatchUpAt` is the same compatibility name and is also `null`; it is **not** the discovery gate. The footer prints `Следующий запуск по расписанию: —` and does not format a clock from those fields.

A caller honors `discovery.nextCatchUpAt`. Changing a live Task recurrence needs an owner-approved registry operation and a documentation update of the expected registry section; it does not change Worker code.

### What the footer can tell about a missed hourly run

The footer classifies stored Worker records only. It does not read the task registry, and it does not call a usage or billing API. The ChatGPT product limit that can stop a Scheduled Task before any MCP call is a different meter from OpenAI API-key usage, and this service has no credential, route or stored owner-entered value for that product limit. Nothing in the footer invents one.

A prediction run that actually stored `stopReason` `quota` is the one case the footer names as a usage limit, with the run's finish time as the confirmation. A task that ends before it contacts the Worker leaves no such record. Recognition uses a **time-based discovery grace** in the [enrichment footer contract](api/enrichment.md#failure-behavior): after two hours plus 45 minutes past a due exhausted `chunk_budget` gate, with ready discovery work, a parseable checkpoint time and a same-generation discovery batch whose `finishedAt` parses and is not later than the gate, the recognition line says there is no confirmed execution and that an external block is possible. That duration is independent of ChatGPT Task minutes and of DST wall-clock gaps. A missing status, a missing or unparseable checkpoint or batch time, or a batch from another generation is unknown evidence, not that sentence. That sentence is not a quota finding. The prediction line keeps the last stored run, including a drained queue. The next-run line does not claim a Task time.

Its retained prompt is legacy/rollback material, not the active producer contract. [Registry change evidence](../evidence/orchestration/ratings-task-disabled-2026-11-06.md).
- **Mode:** storage supported (version 2); the legacy Task is now server-fenced (`external_writer_fenced`) and must not invoke `ratings_sync_start`. Authorized Cloudflare Workflow execution runs the ratings pipeline ([ADR 0060](../adr/0060-independent-letterboxd-ratings-pipeline.md), [ADR 0074](../adr/0074-retire-ratings-pipeline-switch.md)). The Worker ignores `RATINGS_PIPELINE`. There is no `disabled` answer. On any storage that is not version 2, start and step answer `storage_unsupported`. The task must never use `epg_sync_start` or `epg_sync_step` to obtain ratings.
- **Legacy contract (rollback only, subject to a separately approved reverse cutover):** one `ratings_sync_start({trigger:'scheduled'})`, then sequential `ratings_sync_step({runId})` calls with only the returned `runId` while `nextAction` is `continue`, honoring `wait` and never retrying a `stop`, an `unknown` run or a call that ended without a response. `busy` and `isolated` end the invocation. A scheduled start has no minimum interval after the previous one ([ADR 0069](../adr/0069-no-scheduled-ratings-start-gap.md)). The task never sets `clearIsolation`. It never calls an EPG, discovery or prediction tool; the hourly task never calls a ratings tool. The Diary phase requests `https://letterboxd.com/<user>/diary/` once and no later page ([ADR 0067](../adr/0067-diary-recent-window.md), [ADR 0075](../adr/0075-retire-letterboxd-diary-history-switch.md)). The retired `LETTERBOXD_DIARY_HISTORY` binding does not skip that request. The removal phase then looks up at most five films the Diary did not rate. A confirmed stored rating for a film the current Diary page did not list is not requested, including after a new reference reopens the entry. A film that page lists without a rating is still looked up. A null or absent rating is not watched. The retired `REMOVAL_RATING_LOOKUP` binding does not skip that lookup ([ADR 0077](../adr/0077-retire-removal-rating-lookup-switch.md)). A finished run is a recent window, not a complete diary, and the task does not start an archive import.
- **A change** of the prompt, the schedule or the enabled state needs its own owner approval. The registry-only drift monitor does not audit the disabled Ratings Task; Cloudflare Ratings progress belongs to the independent Worker monitor ([monitor runbook](../runbooks/monitoring.md)).

## Ratings Task and the Cloudflare executor (AIR-347)

Ratings production is Cloudflare-owned: `orchestration.mode=cloudflare`, epoch `1`; the first natural Workflow `ratings_20261105_0` completed on 2026-11-05 with Diary page 1 (50 rows, one new fact) and no pending removals. The previous ChatGPT Ratings Task was separately disabled on 2026-11-06 and verified in the live registry. The existing Worker cron (`37 * * * *`) calls `RatingsOrchestration.ensure` after the logical daily due of 17:30 Europe/Madrid; it creates a deterministic Workflow instance, not an inline cron writer. The external Ratings start/step path is fenced. Rollback to external requires its own owner-approved drain/mode switch and a separately authorized Task re-enable. For runtime status read `ratings_sync_status`, not the Task's old run history. See [ADR 0090](../adr/0090-ratings-cloudflare-workflow-executor.md) and [dated evidence](../evidence/orchestration/ratings-task-disabled-2026-11-06.md).

## Worker monitor and the external drift Task (AIR-349)

The Worker's own monitor ([ADR 0095](../adr/0095-cloudflare-native-production-monitor.md)) checks the stored result of each stream independently of ChatGPT and is inert unless `MONITOR` is `on`. The external «IPTV Scheduled Task Drift» checks only the enabled state, schedule, prompt boundaries and recorded execution outcomes of the one producing ChatGPT Task, the hourly Predictions Task. It performs no Worker health check. See the [monitor API](api/monitor.md).

## Cloudflare cron and the Letterboxd Sync

No Cloudflare cron or ChatGPT Scheduled Task exists for the Letterboxd Sync. The control plane is in the repository and inert: the cron `30 * * * *` that would call only `LetterboxdOrchestration.ensure` is **not** in `wrangler.jsonc`, there is no Workflow binding, and the existing crons do not call it. Adding the trigger and binding is a separate owner-approved production cutover. The ChatGPT Task registry is unaffected.
