# D1 enrichment projector: checkpoint buckets on non-ASCII ids (SQL and JavaScript parity)

**Captured:** 2026-11-09, offline (the real projector code on the `sqlite3` CLI stand-in of the tests and, for timing, on an in-memory SQLite). No production read or write of any kind, no manual projector, Discovery or EPG run, no schema, flag, Task, cron, window, lease or budget change.
**Scope:** [AIR-398](https://trello.com/c/UaxgcH6l): the bucket mapping of the checkpoint reconciliation of [AIR-395](air-395-checkpoint-reconciliation-offline-2026-11-09.md), which cut the last four **characters** of an id with SQLite's `substr()`/`unicode()` in the database and with `charCodeAt()` in the Worker. It states what the first mapping did on non-ASCII ids, what replaces it, and what the tests prove. It does not measure D1.
**Verdict:** **FIXED AND PROVEN OFFLINE; NO SILENT MISS WAS EVER POSSIBLE BEYOND THE ACCEPTED CHECKSUM COLLISION, BUT TWO REAL DEFECTS EXISTED.** The first mapping (1) put an id ending in a non-BMP character, or holding a lone surrogate, in a different bucket in SQL and in JavaScript, which only made **extra buckets differ** (a cost, never a hidden change: both buckets of a misplaced id hold a count that does not match), and (2) gave a stored id **shorter than four characters a NULL bucket, which made the whole diff fail** (`outcome: failed`) on every run while such a row existed. The mapping is now the last four **UTF-8 bytes** of `'0000'` + the id on both sides, which is the same for every well-formed string and defined for every length; an ill-formed fresh id and any digest or row the Worker cannot place send the run to the whole-table read with a visible `skipped` reason. The bucket path gives exactly the plan, writes and D1 state of the whole-table read on every tested id class. The price is a heavier SQL expression (about 18 ms more per pass over 32,100 rows on this machine).
**Used by:** [AIR-395](air-395-checkpoint-reconciliation-offline-2026-11-09.md) (the mechanism), [ADR 0056](../../adr/0056-d1-enrichment-write-through.md) (the diff).

## What the first mapping did (reproduced on the code of `main` before the fix)

SQL (`b` of the digest statement) against JavaScript (`d1EnrichmentBucketOf`) for one stored row of each class:

| Id (suffix class) | SQL bucket | JavaScript bucket | Same |
| --- | --- | --- | --- |
| `film:w1`, `film:tmdb_5` (ASCII) | `person:3023`, `person:2350` | the same | yes |
| `person:actor/иван-петров` (Cyrillic, BMP) | `person:2554` | the same | yes |
| `person:actor/josé` and `person:actor/jose` + U+0301 (composed and decomposed accent) | `person:3207`, `person:2070` | the same | yes (two different strings, two different ids, each consistent) |
| `person:actor/日本語` (CJK, BMP) | `person:432` | the same | yes |
| `person:actor/😀`, `person:actor/a😀b`, `person:actor/x𝒳y` (non-BMP) | `person:3404`, `person:2508`, `person:2783` | `person:1068`, `person:1978`, `person:231` | **no** |
| `person:actor/` + a lone high surrogate | `person:3365` (the database stores U+FFFD) | `person:2149` | **no** |
| `x`, `ab` (a stored-only id shorter than four characters) | **NULL** | `NaN` | **no** |

The cause is two counting units: SQLite counts code points, JavaScript counts UTF-16 units, so the last four characters of a non-BMP id are not the same four on both sides, and `substr(id,-4,1)` of a short id is empty, so `unicode()` is NULL.

What that did to the diff, from the new test run against the old code: with 40 Films whose Persons carry ids of every class, the **steady state** (nothing changed) reported 10 differing buckets of 162 instead of 0 (extra rows read, no wrong plan: first import, change, new Film, deletion and restoration still gave exactly the plan, writes and D1 state of the whole-table read). A stored-only row with a one-character id made the buckets run end `failed` while the whole-table run completed: a NULL bucket reached `byKind[bucket.slice(0, at)]` and the diff threw, every hour, until the row was removed. A real id (`film:`, `person:` plus a role id or a slug, at least six characters) never has a NULL bucket, and the independent review of AIR-395 found no real TMDB or slug id that ends in a non-BMP character (this report did not scan production); the correctness had to be proven while the mechanism is in `main`.

**Why a mismatch cannot hide a change.** The digest of a bucket is its count and two sums of the stored keys. An entity placed in bucket X by the Worker and Y by the database leaves X with a fresh entity the table does not have there and Y with a stored row the view does not have there: both counts disagree, so both buckets differ and both are read, and the unchanged plan then sees the stored row and the fresh entity. A change could be missed only if some other entity's key made a bucket's count **and** both sums equal again, the checksum collision of about 2^-64 that the owner accepted on AIR-395; the mismatch adds no new risk class, only cost (and, with many mismatches, the 40 % fallback to the whole table).

## The fix

- **Mapping.** The bucket is `(b4*1664525 + b3*22695477 + b2*48271 + b1*69069) % 4096` over the last four bytes of the UTF-8 encoding of `'0000' + id` (`b4` the last). SQL: `hex(substr(CAST('0000'||id AS BLOB),-4))` split into bytes with `instr('0123456789ABCDEF', …)`; JavaScript: `TextEncoder`. For a well-formed string the two byte sequences are identical by definition, the padding makes every id at least four bytes (so no NULL), and for an id longer than four bytes the padding changes nothing. The arithmetic stays far below 2^53. Each side has one definition (`D1_ENRICHMENT_BUCKET_EXPR`, `d1EnrichmentBucketOf`); no id enters the SQL text.
- **Well-formedness.** A fresh id with a lone surrogate (which the database would store as U+FFFD, so the two sides could never agree) is not bucketed: `d1EnrichmentCheckpoints` reads the whole table before any query of the bucket path, `checkpointBuckets: {skipped: 'unsafe_id'}`.
- **Detection.** A digest row whose bucket name is missing or malformed, or a row read for a differing bucket whose JavaScript bucket is not a differing one, means the two sides disagree about the mapping: the whole table is read and `checkpointBuckets: {…, skipped: 'bucket_mismatch'}` says so, instead of throwing or trusting the sums. The existing `checkpointMode`, the summary fields and the whole-table path are unchanged, the bucket path still costs the same number of queries, and nothing is written or indexed differently.
- No schema, flag, Task, budget, writer or authority change; the `projection_state` format and the key slices are untouched.

## What the tests prove (`tests/d1-enrichment-bucket-unicode.mjs`; `d1-enrichment-buckets.mjs` of AIR-395 passes unchanged)

- **SQL and JavaScript agree** on 20 ids of every class (ASCII, Cyrillic, composed and decomposed accents, CJK, emoji, a ZWJ emoji sequence, non-BMP letters, and ids of 1, 2, 3 and 4 characters), one at a time and as a whole digest (the bucket sums equal), and no stored id has a NULL bucket.
- **Parity with the whole-table read on non-ASCII ids**: first import, steady state (**0 differing buckets**, where the old code gave 10), a roster change that removes one non-BMP Person and adds another, a new Film with non-BMP Persons, two Films deleted (their Persons become absent) and restored; then stored-only rows (a one-character id, a two-character non-BMP id, a Person ending in an emoji, a Film with a Cyrillic id), a live non-BMP Person stored as `absent`, and a corrupt key on a non-BMP Person. Each step compares the summary (changed and absent counts, writes, releases, members, errors) and the final D1 state (Films, Persons, credits, watchlist rows, checkpoints) with the whole-table run, and asserts the bucket path was used (`checkpointMode: buckets`).
- **Ill-formed id.** A fresh id with a lone surrogate reads the whole table, asks for no digest, and says `unsafe_id`; the same inputs with a well-formed id take the bucket path with 0 differing.
- **Injected disagreement.** With the database made to compute the old code-point mapping, or to answer NULL: the plan, writes and D1 state still equal the whole-table run and the change is not missed; the NULL case is detected (`bucket_mismatch`, mode `full`); the code-point case shows as extra differing buckets, and with every exotic id disagreeing at once as the 40 % fallback to the whole table.
- The test fails on the code of `main`: its first section (no NULL bucket, equal buckets) fails there, and with that section removed the steady-state case (10 differing buckets, 0 expected) and the stored-only one-character id (the run `failed`) fail as described above.

## Cost (offline, this machine; D1 is not measured)

The SQL expression is heavier: `hex()`, `CAST` and eight `instr()` per row instead of four `unicode()`. On 32,100 stored keys (the AIR-395 benchmark, `scripts/projector-checkpoint-bench.mjs`, an in-memory SQLite): the digest statement took **76 ms before and 122 ms after**; the grouping expression alone 21 to 24 ms before and 41 to 43 ms after (seven timed runs, medians). The rows statements evaluate the expression for every row of the table once per statement (as before, a full scan), and took 11, 24, 69 and 161 ms before against 38, 71, 207 and 488 ms after at 0.1, 0.5, 2 and 5 % of entities changed. Rows crossing the binding and queries are **identical** in all eight scenarios (the ASCII fixture lands in the same buckets), so the AIR-395 benchmark's transfer figures stand. A hybrid that uses the character expression for printable ASCII ids and the byte expression for the rest was measured at 28 to 29 ms for the grouping (about 8 ms cheaper than the byte expression alone) and gives the same buckets, but it keeps two code paths to prove; a variant that computes `hex()` once in a subquery was no faster (49 ms). The simplest single mapping was chosen. On D1 the added SQL time is expected to be of the same order (tens of milliseconds a pass); whether it matters inside the exclusive window is read from the `diff.checkpointDigest` and `diff.checkpointRows` timings and the D1 `meta` of the next natural runs.

## What this does not show

- **D1 itself.** The stand-in is SQLite 3.45 through the `sqlite3` CLI. `hex()`, `CAST(... AS BLOB)`, `substr()` on a blob and `instr()` are standard SQLite and D1 is SQLite, but D1 was not exercised here; the check that its digest agrees with the Worker is the runtime detection (`bucket_mismatch`) and the natural-run `checkpointMode` and `checkpointBuckets.differing`.
- **A lone surrogate stored by the database.** What the Workers runtime does with an ill-formed string it binds was not tested; the code does not depend on it (it never buckets such an id).
- **Unicode normalization** is not applied: a composed and a decomposed accent are two different ids, each consistently placed. The tests cover both; nothing in the repository normalizes ids.
- **Frequency.** No id in production is known to be non-ASCII beyond what the role-id and slug rules produce; the fix does not depend on how often such ids occur.
- **The AIR-395 evidence and the unchanged parts.** The AIR-395 report's description of the bucket as "the last four characters" is superseded by this one for the mapping; its measurements of rows crossing the binding stand.

## STOP and rollback

A natural run that reports `skipped: bucket_mismatch` is a STOP for the bucket path: it falls back by itself to the whole table, and the ids involved and the mapping must be checked before the next run is trusted. Rollback is an ordinary code revert; state, schema and the `projection_state` format are untouched. A revert returns the NULL-bucket failure for a stored short id and the extra differing buckets for non-BMP ids.
