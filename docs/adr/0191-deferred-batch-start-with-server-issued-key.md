# ADR 0191: A Scheduled Task starts a prediction run with a server-issued key and a fast receipt; the heavy preparation runs in a Cloudflare Workflow and is read back as an immutable manifest

**Status:** Proposed (the target direction is approved by the Product Owner in the AIR-573 handoff of 2026-11-21; the concrete choices below await review and acceptance)  
**Original decision date:** 2026-11-21 (direction); the concrete design is recorded with the implementation PR  
**Recorded at:** 2026-11-21  
**Approval source:** The Product Owner's handoff comment on [AIR-573](https://trello.com/c/4pD66DLd#comment-6b01d7b358e86c3c2baa6752), 2026-11-21 17:41 UTC: approved a fast asynchronous start with a server-side idempotency key and a later readback of the prepared manifest, replacing the long synchronous start for Scheduled Tasks, with all four existing Tasks moved together after delivery.  
**Related work:** [AIR-573](https://trello.com/c/4pD66DLd) (P0 incident); implemented on top of [PR #854](https://github.com/vladimino/iptv-watchlist/pull/854) ([ADR 0188](0188-idempotent-keyed-batch-start-and-early-start-claim.md)); the health contract of [AIR-556](https://trello.com/c/ZjqzW7EB) is extended, not duplicated; [AIR-574](https://trello.com/c/ZyUoLRki), [AIR-575](https://trello.com/c/4ncE69Ic), [AIR-560](https://trello.com/c/NZ70Dzom) and the recovery-priority work are not touched.  
**Supersedes:** In part [ADR 0188](0188-idempotent-keyed-batch-start-and-early-start-claim.md): its caller-composed key and the validation gate for its source (section 5), and the synchronous join with a bounded wait as the protocol of the Tasks. The claim, the fencing, the join eligibility (`clientSubmitAt`), the field-preserving lease writes, the commit guard and the no-foreign-adoption rule of ADR 0188 stay in force and are reused.

## Context

Confirmed from the AIR-573 traces of 21 Nov 2026 (Europe/Madrid), recorded on the card and in [the evidence note](../evidence/prediction/air-573-deferred-start-offline-2026-11-21.md):

- A synchronous `prediction_batch_start` took 75–90 s (S5 `:15`: 90.166 s; `:30`: 78.883 s, a 39,372 byte manifest, 325 D1 calls, 51 R2 operations, three preflights, a 20.758 s queue refresh and a 36.017 s persist). A second HTTP start arrived about 60.6 s after the first and was answered `already_running`; the Task treated that as a lost slot and ended, leaving its own run in a live lease.
- After [PR #854](https://github.com/vladimino/iptv-watchlist/pull/854) the keyed start is correct, but it stays dormant: a natural `:15` probe found the `invocationKey` schema present and **no** scheduler invocation id, `scheduled_for` or source available to the Task. ADR 0188's key (derived per Task and slot) therefore has no provable source, and its validation gate cannot be passed.
- At `:30` a different failure appeared: the Task received `runId` and `selected=5` and ended about 3 s after the Worker logged a successful start, with no heartbeat, submit or complete.

**Not established:** who issues the repeated request, and why the Task ends after a receipt. Neither a faster synchronous path nor a stricter "do not repeat" prompt rule addresses both, so this ADR does not depend on either answer.

## Decision

1. **The server issues the key before the start.** The MCP tool `prediction_batch_key` returns `{status:'issued', invocationKey}` with `dk1.<32 hex>` (128 random bits from the platform). It reads and writes **nothing**: no lease, no run, no storage. A lost answer leaves nothing behind, and a repeat only returns another unused key. A Task calls it once per execution, keeps the key and sends the **same** key on every repeat of that start. The key is not composed from the model, the clock, the Task name or the slot, and the Worker does not need the scheduler's invocation id.
2. **The start accepts and answers a compact receipt.** `prediction_batch_start({deferred:true, invocationKey})` requires an issued-shape key (`dk1.…`), is never a dry run or a pin, and does only what ADR 0188 already does cheaply: validate, take the runner claim (180 s, with the key hash and the canonical argument hash), create one Workflow instance whose id is the run id, and answer `{status:'accepted', runId, epoch, phase:'preparing', retryAfterMs, read:{tool:'prediction_batch_manifest', …}}`. It runs no preflight, no queue refresh and no manifest build in the request. If the Workflow binding is absent or `create` fails, the claim is released and the answer is the typed `503 deferred_start_unavailable`; an instance that was created although its answer was lost finds its claim released and ends before any side effect.
3. **The preparation is durable and independent of the MCP request.** A Cloudflare Workflow (`iptv-prediction-start`, class `PredictionStartWorkflow`, one instance per run id) runs one step `prepare` with **no retries** and a 4 minute timeout. The step runs exactly the keyed start of ADR 0188 (preflights, queue refresh when needed, revalidation under the claim, conversion under the same epoch, the fenced persist, the stored manifest) and then records one small terminal **outcome** at `enrichment/batch-start/<runId>.json`, written create-only so a replayed or stale instance never overwrites it: `ready`, `refused` (with the existing refusal code: `noop`, `quota`, `manifest_too_large`, `prediction_catalog_held`, …) or `failed` (`start_claim_lost`, `storage_error`). A refused or failed preparation releases its claim. The Workflow is an existing platform mechanism of this Worker (Discovery, Ratings, EPG, Producer); `waitUntil` is not used.
4. **Readback uses the existing manifest tool.** `prediction_batch_manifest` answers `manifest_pending` (HTTP 409, `retryAfterMs`) while the claim is live and nothing is stored, the usual envelope, profile, contract and film parts when the manifest is stored, and the typed final `start_refused` or `start_failed` (with `outcomeCode`) when the outcome says so; it never answers `unknown_run` for a run that is preparing or ended. A repeat of the same keyed deferred start with the same arguments returns the same receipt with `phase: 'preparing'` or `'ready'`: it starts no second preparation and never waits. Another key, other arguments (`reason: key_args_mismatch`), no key, an expired holder or a run with a client submit answer `already_running`, as in ADR 0188.
5. **A prepared run holds a short lease until its first heartbeat or submit.** The claim converts to the run lease with a 180 s expiry (not the ordinary 15 minutes), and the persist's own gate is cut back to the same short expiry when it is cleared. The first `prediction_heartbeat` or `batch_submit` renews it to the full TTL (every existing renewal already does). A caller that disappears after the receipt therefore blocks the runner for minutes, not 15; the next start recovers the abandoned run through the existing `recovered_stale_lease` path, with no reset by hand and no adoption.
6. **Isolation.** A join or receipt needs the same key hash **and** argument hash on a live holder before any client submit; four concurrent Tasks with four issued keys produce one accepted run and three `already_running` answers, as today. A key that was issued but never used writes nothing. **A full loss of the key or the Task context is not recoverable by this protocol**: the next start gets `already_running` until the live claim or short lease expires (at most about 3 minutes), then proceeds with a new key. No source of correlation beyond the issued key is claimed.
7. **Observability.** The start's step-timing line carries counters `deferredAccepted`, `deferredReplay`, `deferredUnavailable` next to the ADR 0188 ones; the Workflow step logs one sanitized `prediction_start_prepared` line (phase, code, `prepareMs`, preflights, refresh rounds, claim renewals; no key, no payload). **Repeated orphan starts become one more reason of the shared AIR-556 verdict** (`predictionStallAssessment`, used by the Footer and the Monitor, not a second monitor): with eligible work, at least three ownerless starts since the last confirmed progress (a start turned away with `already_running`, or a run abandoned without a film; a run still `running` is not counted) and at least 20 minutes without progress give `no_progress` with `reason: 'repeated_orphan_starts'`. The existing 60-minute rule is unchanged. A `start=200`, an `accepted` receipt or an `already_running` is never progress.
8. **Compatibility and rollback.** The synchronous start, the synchronous keyed start of ADR 0188, a keyless start and `dryRun` are unchanged and remain until the Tasks are moved. Rollback is a prompt change back to the synchronous start plus, if wanted, a code revert; the Workflow definition then stays inert. No schema change, no feature flag, no migration.

Not decided here: the Task prompt change and the rollout order (owner and Controller, after delivery; the minimal prompt delta is in [the delta note](../reference/scheduled-task-prompts/hourly-predictions-batch-v2-deferred-start-delta.md)), any manual run, lease reset, flag or schedule change, the manifest size, the recovery ranking, the S7 research and AIR-574/575.

## Alternatives considered

- **Only speed up the synchronous start.** Rejected as the fix: it is already optimised in AIR-471 and AIR-486 and still takes 75–90 s; it also leaves the Task exposed to any later slowness and does not explain the `:30` end after a receipt. It remains useful work, not the protocol.
- **A stricter prompt rule against repeating the start.** Rejected: the source of the second request is not proven, and the rule cannot be tested offline.
- **A key composed by the Task from its schedule** (ADR 0188 section 5). Rejected: the natural probe shows no scheduler invocation id or scheduled time reaches the Task, and a model-composed time or random value is not stable across a re-issue.
- **A signed or stored issued key.** Rejected: a signature needs a new secret, a stored key needs new state, and neither adds isolation over 128 random bits that are used only for correlation behind the owner-only Access boundary; a forged or reused key can only collide with itself.
- **`ctx.waitUntil` for the preparation.** Rejected: the platform grants a bounded time after the response (about 30 s), shorter than the measured preparation.
- **A Durable Object or a Queue.** Rejected: a new class with a migration or a new binding and delivery semantics for no gain over a Workflow, which this Worker already uses and which keeps one instance per run id.
- **Precomputing manifests on the hourly cron.** Rejected: manifests would be stale against the queue, and ADR 0122's revalidation would refuse many of them.
- **A long synchronous wait on the repeat (ADR 0188's `start_pending` bound).** Kept only for the synchronous keyed start; the deferred start never waits.

## Consequences

- The request path of a start is a claim and an instance creation (offline: 4 D1 round trips and one R2 operation); the measured 150 D1 round trips of the preparation move off the caller's critical path. The preparation is somewhat heavier than the unkeyed synchronous start (claim, gate and guard overhead; about 150 against 82 D1 round trips offline), which matters only for its own duration.
- Deploying creates the `iptv-prediction-start` Workflow definition (a Cloudflare resource, no data). It is inert until a Task sends a deferred start.
- A Task must poll with the returned `retryAfterMs`, then heartbeat soon after the manifest is ready (the short lease lasts 180 s); the delta note gives the minimal prompt change.
- Four Tasks that start within one preparation window still lose the slot to the first, as before; the loser is `already_running`, which is a lost slot, not an incident.
- One more verdict reason in the shared progress assessment can raise the alert earlier than 60 minutes; it can be wrong only for a run that is not abandoned yet, which the assessment excludes while the lease is live and young.

## Recovery and migration boundary

Code only: no schema, no flag, no data migration. The Workflow definition created by the deploy is inert and stays after a code rollback; removing it is a separate owner-gated operation. A prompt rollback restores the synchronous start. Terminal outcomes under `enrichment/batch-start/` are small immutable records and need no cleanup. This ADR authorizes no production operation: moving the four Tasks, any run, lease reset or Worker setting remains owner-gated.
