# Letterboxd baseline import: approved execution plan and receipts

`scripts/letterboxd-baseline-import.mjs` imports the owner's Letterboxd account export as fact observations under [ADR-0023](../adr/0023-letterboxd-user-facts.md). The storage rules, the merge order and the request contract are the [user facts contract](../reference/integrations/letterboxd-user-facts.md). This page is the procedure. The route is a permanent owner-only maintenance tool with no switch of its own ([ADR 0053](../adr/0053-permanent-letterboxd-baseline-import-route.md)). Nothing on this page is authorized by a merge or a deploy: issuing an Access credential, every `validate`, every `commit` and every `rollback` against production each need their own owner approval.

## Proportionality and existing tooling limits

This CLI currently **requires** a verified `consistent_fenced` snapshot for `plan`; a small archive, limited number of accepted Films or repeated import does not remove that input requirement. Do not invent a supported target-only import mode. The snapshot protects cross-source identity matching and freshness at planning time, while the Worker uses chunk receipts, create-only intents and fact precedence to avoid overwriting newer observations. Those are data-integrity requirements, not general availability ceremonies.

Once a plan is fixed to its archive SHA-256, chunking and accepted identities, **one owner authorization may name a bounded L3 execution plan** (for example validate plus explicitly enumerated commit chunks), including internal integrity reads and safe receipt-based resume. A new archive, changed plan, additional chunks, conflicting identity or a rollback outside the approved bounds requires a new decision. A failed or timed-out commit is handled through the existing idempotent intent/replay protocol, **not** a new full snapshot or a new plan for each retry. Do not require repeating a successful validate merely to reproduce an identical result; validate again when source facts or the accepted plan may have changed.

A future snapshot-free, target-scoped planner would require a separate implementation and contract review (identity alias completeness, freshness and competing writers), not a documentation-only promise. [Risk-proportional policy](../process/agent-workflow.md#risk-proportional-operational-safeguards).

## What the tool never does

- `plan` sends nothing and reads only the export ZIP (in memory) and a verified snapshot; its outputs stay in a private directory outside the repository.
- No film name, code, URI or rating reaches standard output, `report.json`, a commit message, a PR or a card; they exist only in `plan.jsonl` and the private `*.json` results of the remote steps.
- Only films the export matching marks `accepted` are planned; `candidate`, `ambiguous`, `conflict`, `provisional` and `unmatched` films are counted, never imported by this CLI.
- An export never sets `watched: false` or `watchlist: false`; absence is not an observation.
- The CLI Worker route writes fact records, the link index, the conflict list, the view-index projection and `letterboxd/imports/<archive sha256>/chunks/<n>.intent.json`, `<n>.receipt.json` and `<n>.rollback.json`. The browser candidate path, which this CLI does not call, also writes `letterboxd/imports/<archive sha256>/rated-candidates.json`, `chunks/<n>.candidates.json` and, only after an explicit identity step, `letterboxd/admissions/verified-films.json` plus one tmdb-only fact ([ADR 0087](../adr/0087-rated-archive-film-admission.md), Accepted).

## Inputs

| Input | Rule |
| --- | --- |
| `--zip` | The archive exactly as Letterboxd delivered it, named `letterboxd-<user>-YYYY-MM-DD-HH-MM-utc.zip`; that name is the export time. A renamed archive is refused unless `--generated-at <UTC>` is given, which `origin.json` records as `owner_declared` |
| `--snapshot` | A verified `consistent_fenced` production R2 snapshot ([snapshot export](r2-snapshot-export.md)); it gives the identity of the planned films |
| `--output` | A private absolute directory outside the repository, new and empty for every `plan`; it then holds that one plan for good: `origin.json`, `plan.jsonl`, `report.json`, then `validate.json`, `commit.json`, `rollback.json` |
| `--chunk-size` | `plan` only: films per chunk, an integer 1–100, default 50 (see [Chunk size](#chunk-size)). The remote steps take the size from `origin.json` and refuse the flag |
| `--endpoint` | The Worker origin over HTTPS (`http://localhost` for local development only) |
| `LETTERBOXD_IMPORT_ACCESS_CLIENT_ID`, `LETTERBOXD_IMPORT_ACCESS_CLIENT_SECRET` | A Cloudflare Access service token allowed to reach the Worker, in the environment only; sent as `CF-Access-Client-Id`/`CF-Access-Client-Secret`, never printed or written |

## Procedure

0. **Preview (optional, no write).** On `/admin/letterboxd` the owner can upload the same ZIP and see its export time, completeness, match counts and what an import would do per fact (`new`, `replaces`, `older`, `unchanged`, `tie`). The page leads with «добавится», «изменится» and «пропущено»; the SHA-256 stays in a closed disclosure. The page says separately that the ZIP was read, that the R2 comparison is partial (that gap alone does not ask for a new ZIP and is not a full check), and «Нужен свежий архив» only when the export is stale or a compared rating in R2 is newer. It also separates a changed value from a same-value observation update: both can be `replaces`, and only the second leaves the rating, watched flag or watchlist membership as stored while still writing a new observation time and source ([admin API](../reference/api/admin.md#letterboxd-archive-preview-post-apiadminletterboxd-archivepreview)). The preview stores nothing, needs no service token and is no substitute for `validate`: it reads live R2 instead of a fenced snapshot, compares at most 300 fact-record GETs (a redirect hop counts) and never imports. Recording a chunk is the [browser apply](#browser-apply), a later pair of requests, not this preview.
1. **Rehearse.** `node tests/letterboxd-baseline-import.mjs` runs the ZIP reader, the plan, the tamper checks and every route outcome against invented data and an in-memory bucket. `node tests/letterboxd-baseline-chunks.mjs` runs the chunk sizes and boundaries, legacy 200-film plans, network failures and resume from the intents the same way.
2. **Plan (offline).** `node scripts/letterboxd-baseline-import.mjs plan --zip <zip> --snapshot <snapshot> --output <dir> [--chunk-size <n>]`, into a new empty directory; `plan` never writes into a directory that already holds a plan or a result file, and the same inputs planned into two new directories give identical files. Check `report.json`: `chunkSize`, `planned` (films, chunks, watched, rated, not rated, watchlist), `matchStatus` and `unresolved` against the [reconciliation evidence](../evidence/letterboxd/README.md).
2a. **Inferred identities (optional, AIR-388, [ADR 0104](../adr/0104-inferred-letterboxd-identity.md)).** `plan … --include-inferred` also plans films whose export name equals the stored **original** title of exactly one TMDB movie in the snapshot, with the same year and no competing or contradicting link. They are recorded as `inferred` (never verified) with the archive SHA-256. The switch exists only on `plan`; it is recorded in `origin.json` (`identityPolicy`) and the report (`identityPolicy`, `inferred`, and `review`: counts per review reason, with no names). Everything else with a title match stays out as a review candidate: `year_drift`, `alias_title_only`, `tmdb_linked_elsewhere`, `tmdb_duplicate_in_export`, `tmdb_already_accepted`, `no_tmdb_id`, `missing_year`. Films with no stored title are not touched; creating a Film for them is a separate step (ADR 0104, not implemented). Two limits to read before a production plan: the snapshot's link index is an R2 copy and can be behind the D1 ratings domain, so the commit-time alias conflict stays the authority for a contradicting link; and a wrong link is corrected per film with `unlink --zip <zip> --output <dir> --endpoint https://<worker> --lid <code>` (an owner-approved production step like every remote one), which reverses that film's facts under the rollback rules, removes its Letterboxd link and `identity`, and leaves the rest of its chunk alone; the chunk `rollback` now unlinks every inferred film of its chunk as well. Without the switch the plan is exactly the verified-only plan.
2b. **Live catalog input and TMDB search (AIR-388 B2, [ADR 0105](../adr/0105-live-catalog-input-and-tmdb-search-admission.md)).** Each production read below is its own owner approval. (i) *Catalog directory, once, read-only:* check the markers first (`film_person_authority`, `ratings_domain_authority`, `published_epg_authority`, `discovery_authority`); read the catalog by `SELECT` of `discovery_admission` where `state='current'` and `media_kind='movie'` (fields id, tmdbId, canonicalIdentity, title, original, year, aliases) and the link document `letterboxd/facts/links.json` from `ratings_document` (the R2 copy is behind once the ratings marker is `d1/open`); read the R2 objects `metadata.json`, `watchlist.json`, `programme.json`, `enrichment/view-index.json` with the read-only exporter client (`GET`/`HEAD` only), never through a Worker route (some of those routes repair mirrors); write `catalog.json`, `links.json`, `provenance.json` (`source: live_catalog_read`, `readAt`) and the optional files into a private directory. (ii) *Search:* `node scripts/letterboxd-tmdb-search.mjs --export <dir> --catalog-dir <dir> --output <dir> --dry-run` prints the number of requests without a credential; the real run authenticates one of two ways (the tool creates no credential): `TMDB_READ_TOKEN` in the environment (a read-only TMDB API read access token, sent as a bearer header), or `--auth proxy` when the cloud environment holds the token as a network secret for `api.themoviedb.org` (Bearer type, header `Authorization`, prefix `Bearer`): the proxy then adds the header, the tool sends none and no variable exists, and it must run with `NODE_USE_ENV_PROXY=1` so Node's fetch uses the proxy; a 401 ends the run and the film it was asked for is not recorded, makes one attempt per film, ever, at most 1,500 requests in total over every resume (the count is kept in the file) at no more than 4 per second, records every attempt including a failed or blocked one (a resume never asks the same code again; retrying one is a separate decision), stops at the first 403 or 429, and resumes from `tmdb-results.json`, which is bound to the export and the catalog read and refused for another input. (ii-b) *Newer catalog read:* a results file is bound to one catalog read, so a newer read makes it unusable (`--tmdb-results was not made for this export and catalog read`). Never search again for that: run `node scripts/letterboxd-tmdb-search.mjs rebase --export <dir> --catalog-dir <new read> --previous <old tmdb-results.json> --output <new empty dir>`. It is offline (no request, no credential), requires the same export digest, keeps the cumulative request count and the original provenance in a `rebase` block, matches the whole export again against the new catalog and judges every recorded code again (unchanged: reused; now known to the catalog: superseded, the catalog decides; movie now linked elsewhere: `review`; ambiguous or conflict, a title or year disagreement, or a code not in the export: stop with nothing written); it prints aggregates, and films with no recorded attempt stay pending. Plan from its output with the new catalog directory. The catalog directory must hold all four optional files before any search or rebase: without them the stored codes behind `accepted` are lost and the unmatched count is inflated. (iii) *Plan:* `plan --zip <zip> --catalog-dir <dir> --include-inferred --tmdb-results <dir>/tmdb-results.json --output <new dir>`; the planner refuses a results file that is not bound to this export and catalog read, names a code it did not leave unmatched, or holds an entry whose original title or year differs from its export film; the report counts `filmsToCreate`, `inferred`, `search` (decided, review per reason, pending, errors, blocked) and `review`. Validate and commit then follow steps 4 to 6; an `admit` item writes the admissions entry before its facts. The catalog directory can be stale by the time of a commit: the alias and admission conflicts are counted, never written, and a plan is made again from a fresh directory when the read is old.
3. **Access (owner).** The route is a permanent owner-only maintenance route with no switch ([ADR 0053](../adr/0053-permanent-letterboxd-baseline-import-route.md), [ADR 0055](../adr/0055-retire-letterboxd-facts-switch.md)); the former `LETTERBOXD_BASELINE_IMPORT` and `LETTERBOXD_FACTS` are retired and inert. The routine writers always record facts, so the next sync cannot clear imported ratings by absence. Access is the Worker's owner-only Cloudflare Access: the CLI sends the service-token headers below when they are set, and the token used for the first import has been revoked. Issuing a credential for a remote step is a separate owner decision outside this procedure. The [browser apply](#browser-apply) reaches the same commit and rollback through the owner's existing Access session and never sends a service token. Every production `validate`, `commit` and `rollback` run is a separate owner-approved operation.
4. **Validate (no write).** `… validate --zip <zip> --output <dir> --endpoint https://<worker>`. Every chunk reports what a commit would do now: `new`, `replaces`, `older` (a newer stored or scanned observation wins), `unchanged`, `tie`, and `films.conflict`. Review before committing.
5. **Commit.** `… commit --zip <zip> --output <dir> --endpoint https://<worker>` sends the plan's chunks in order and stops at the first failure. Each chunk writes an intent (with the view before-image), the facts, the projection and a receipt. Re-running the same command is safe: committed chunks answer `replay`, an interrupted chunk is completed from its intent. `--from-chunk`/`--to-chunk` bound a run. `commit.json` (like `validate.json` and `rollback.json`) is rewritten after every chunk, so a run that stops still records the chunks it completed and the one that failed.
6. **Rollback (if needed).** `… rollback --zip <zip> --output <dir> --endpoint https://<worker>` walks the committed chunks in reverse. Per fact it restores the value the import replaced only if the import's observation is still current; a later observation (an owner edit, a newer scan) is reported `superseded` and kept. A fact the import created is removed and the view field it projected returns to its before-image. Each chunk's rollback first writes a rollback intent; an interrupted rollback is completed by running the same command again, which converges on the same result without touching values written after the import. A completed rollback is a replay.

Each remote step first re-reads the archive and refuses to continue if the archive, any CSV inside it or `plan.jsonl` differs from `origin.json`, or if a plan line is not in the chunk its position and the recorded chunk size give (exit code 3).

## Browser apply

On `/admin/letterboxd`, after a preview, the owner can record one compared chunk without a service token ([admin API](../reference/api/admin.md#letterboxd-archive-apply), [ADR 0068](../adr/0068-letterboxd-archive-confirmed-apply.md)). The preview fetches nothing. Rated films the matcher did not accept appear as a later chunk. That chunk stores the short code and the archive SHA-256, does not confirm a TMDB id, does not put the film on the watchlist and does not download a page. After that commit succeeds, «Проверить следующий в общей очереди» fetches one admitting or pending code, fences the movie, and only then writes a rating. The button stays while work or a stop remains, and a stop continues only as «Продолжить проверку». A `needs_review` answer that still wrote the candidate document says so; `writes` is not reserved for a verified Film. «Прочитать сохранённое состояние» reads the queue and fetches nothing. Codes stored as `needs_review` / `shortlink_missing` return to pending only after «Подтвердить повтор разметки» for the ticked codes, then «Вернуть в очередь»; that pair does not fetch and does not walk the other pending codes. A write to another candidate does not make that confirmation stale; a change to a chosen row refuses per code, re-reads the stored state and asks for a new confirmation. If the answer to «Подтвердить повтор разметки» or «Вернуть в очередь» is lost, or is any 5xx (including `storage_error`), stop: the outcome is unknown, the page keeps the key, and the same request recovers the stored confirmation even if a chosen row changed meanwhile. For «Вернуть в очередь», stop: use only «Узнать исход (тот же ключ)», which reads the stored receipt back, never a new confirmation. Each requeued code then has its own «Проверить <code>» button, which posts identity-step with that code and does not take the next pending code. Each later identity-step still needs its own owner approval. For a bounded production acceptance of named codes: read identity status first, read the old action receipt when one exists, confirm and run one retry, step each named code by itself, then read status again and the canonical Film for that code. On an unknown outcome, stop and read back; do not retry blindly. This page and the general [authorization policy](../process/authorization-and-escalation.md) do not independently authorize a production ZIP commit or Letterboxd/TMDB write; the concrete L3 plan and existing identity checks control them. A missing admissions object admits nobody, so deploying the page does not upsert a rated-only Film. An identity step that writes the object would let the existing enrichment cron upsert that Film, and a later explicit step may fetch metadata. Neither write is this deploy, and each needs its own approval. The page walks five steps one at a time: choose the ZIP, read freshness and completeness (an incomplete comparison is not a full check), read the exact difference, confirm one batch, then read the receipt. Only the current step is on screen. Back and Continue do not send a request, and the receipt appears only after a write or rollback attempt. The difference leads with «добавится», «изменится» and «пропущено». Hashes, the programme run id, the chunk id and the plan hash stay in a closed disclosure. Two clicks, never one. «Подтвердить партию» stores only the issued confirmation. «Записать партию» uploads the ZIP again and calls the same commit as step 5, for at most 50 films the preview compared. A `partial` or `unknown` receipt is not success. A lost response after the commit or rollback request has left the browser is `unknown`, and the page does not say the write never started. «Прервать ожидание» stays outside the file form, on the active step, and Escape does the same: both stop waiting only and do not cancel or roll back the Worker. The preview's own «Отменить» is a different control and drops that read. Choosing another ZIP, or another declared UTC time, marks that preview stale and disables confirm and commit until the selected file has its own check. That change does not discard an unresolved command. «Проверить архив» and «Очистить» refuse while the outcome is unknown. «Забыть команду в этой вкладке» drops it from the tab and is not a rollback. The same control is offered when a confirm or a rollback confirmation comes back unknown, even if the apply receipt is already on screen. A 409 `in_progress` answer is replayed with the same confirmation and is not shown as a batch that was not recorded. A refused rollback leaves that apply receipt in place. `unknown` does not retry by itself; «Повторить ту же запись» sends the same confirmation and the file from that check again, and does not mint a new key. «Подтвердить откат» then «Откатить» call the same rollback as step 6 and keep a later observation. The archive is not stored, so a new check asks for the file again. The UTC field is only for a renamed archive; the clock on screen is Europe/Madrid, and the page says whether the export time came from the file name or from that field. The page never sends `CF-Access-Client-Id` or `CF-Access-Client-Secret`. The CLI route is unchanged. A production confirm, commit or rollback must be covered by the applicable owner-approved L3 plan and any named holdpoint; do not require repetitive per-chunk owner messages when the plan explicitly includes those chunks. Merging or deploying the page does not run one. A code revert does not remove facts written this way. Use the rollback while the receipt exists.

## Chunk size

The Worker commits a chunk with several sequential R2 operations per film (link index, record read and CAS, floors, projection), on the order of a second per film. A 200-film chunk can exceed the 300 s a Node.js client waits for response headers; the client then drops the request while the Worker has written only part of the chunk. Plans therefore use chunks of **50 films by default and at most 100**, which keeps a commit chunk around a minute and well inside the client limit. Prefer a smaller size over a longer client timeout; there is no timeout flag.

- The chunk size is part of the plan. `origin.json` schema 2 records `chunkSize`; every remote step re-derives the chunks from it, so validate, commit and rollback of one plan always use the same chunks.
- An `origin.json` with schema 1 and no `chunkSize` is a plan made when the size was fixed at 200 films. It keeps that chunking: it still validates, replays its receipts and rolls back chunk by chunk. Do not re-plan it.
- Receipts and intents are keyed by archive SHA-256 and chunk number, and the plan in its directory is the only record of what each chunk holds. `plan` therefore refuses any output directory that already holds `origin.json`, `plan.jsonl`, `report.json` or a result file, even for the same archive and size: another snapshot or other matching can accept other films and would leave the receipts without their plan. A new plan of an already committed archive with another size, in a new directory, is refused by the Worker as `chunk_conflict` on its first chunk; roll the earlier plan back from its own directory first if the archive must be re-imported.
- A new export is a new archive with its own receipts, so a delta import plans with the current default regardless of the size an earlier import used.

## Outcomes

| Exit / answer | Meaning | Next step |
| --- | --- | --- |
| `plan` exit 0 | plan written | review `report.json` |
| exit 2 | usage, a path inside the repository, a missing `watched.csv`, a renamed archive without `--generated-at`, a future export time | fix the input |
| exit 2 `--chunk-size` | a size outside 1–100, the flag on a remote step, or `--output` already holding a plan or a result file | fix the flag, or plan into a new empty directory; keep the old directory for replay and rollback |
| exit 3 | archive or plan differs from `origin.json`, or its chunking differs from the recorded chunk size | re-plan from the original archive into a new directory |
| exit 1, `failed.error: network_error` (`cause` e.g. `UND_ERR_HEADERS_TIMEOUT`, `ECONNRESET`, `TimeoutError`) | the connection dropped or the client timed out; the chunk's outcome is unknown and part of it may be written | rerun the same command: a committed chunk replays, an opened one continues from its intent, so repeated reruns converge. Do not re-plan with another size once any chunk of the archive is opened; a smaller `--chunk-size` is for an archive with no intent yet |
| exit 1, `failed.error: response_unreadable` | an HTTP 2xx whose body was not JSON (a proxy page or a cut body) | rerun the same command; check the endpoint if it repeats |
| HTTP 400 `invalid_request` | a request outside the contract (bad checksum, future time, `watched: false`, a rating without watched, duplicate film, more than 200 films in one request) | do not retry; the plan is wrong |
| HTTP 409 `chunk_conflict` | the chunk number was opened or committed with other items | do not force; re-plan, or roll back the earlier commit first |
| HTTP 409 `not_committed` | rollback of a chunk without a receipt | nothing to roll back |
| HTTP 500 `readback_failed`, `write_contention` or a storage error | a fact did not read back, writers raced past the retries, or a write failed | rerun the same command; the commit or rollback intent completes the chunk |
| `films.conflict` / `conflicts` > 0 | ids that would join a record holding another id of the same kind | listed in `letterboxd/facts/conflicts.json` for the identity review; not written |

## Rollback of the tool

There is no switch to close the route; stop by making no further remote call, since nothing runs by itself. A code revert of [ADR 0055](../adr/0055-retire-letterboxd-facts-switch.md) brings the facts gate back: that code answers 409 `facts_disabled` unless `LETTERBOXD_FACTS=on`, and its legacy sync clears imported ratings by absence while the binding is off or absent. A revert of ADR 0053 as well also brings back the former import switch, and that code answers 409 `import_disabled` until `LETTERBOXD_BASELINE_IMPORT=on` is set under owner authorization. Code rollback does not remove imported facts; use the `rollback` step for that while the receipts exist.
