# AIR-374 P3a: dictionary-store producer for canonical Film title and identity facts, offline tests

**Captured:** 2026-11-12, local runs of `node tests/canonical-dictionary-producer.mjs`, `node tests/canonical-dictionary-producer-mutation.mjs`, then the full `npm test -- --jobs 3` and `npm run build`. **Method:** a sqlite file plays D1 (all migrations, schema 19), the same stand-in as the P3-0a, P3-0b and EPG-layer tests. No R2, D1, Cloudflare, connector or production call of any kind.

**Result:** the pure planning and apply layer for dictionary-sourced `film_facts` units exists and is DORMANT: nothing calls it, `build.mjs` is unchanged, `epgSync` is unchanged, no operation is registered, no marker moves and the projector stays the only canonical writer. `handoffReadiness` is unchanged: `producer_not_wired:epg_commit` stays a blocker (the layer is not wired and the Person kinds are not built). The dictionary reaches the canonical Film only through `writeFilmFacts` behind the receipt adapter; the module holds no SQL and no second write path.

**Equivalent mutants (not counted):** two first-draft mutants were equivalent and the redundant code was removed: an explicit higher-precedence title branch (the dictionary ranks below the owner only and the owner source is already named `owner_kept` just before) and the re-plan's `outcome==='proceed'` test (only `proceed` carries an input). Six first-draft mutants survived because a test did not look: cursor revisit, title fill clock, identity-only unit, the `already` count, a plan without an event, the re-plan's Film and the reconcile limit; each now has an assertion.

**Shared files:** the review-fix pass changes two shared writers: `writeFilmFacts` and `prePlanFilmFacts` gain the opt-in `requireExisting` (byte-identical SQL without it, the EPG producer tests and mutants stay green) and `filmFactsOperation` propagates typed read failures of a re-plan (ADR 0123 decision 5 (c) amended). Earlier, additive only: `src/canonical-producer-adapters.js` re-exports `digestOf` and `readFilmSnapshot` (one export line, no behaviour change; the 57 mutants of its mutation file are still killed); `tests/canonical-producer-adapters.mjs` allows the second importer of the adapter; `scripts/run-tests.mjs` adds one WEIGHTS entry (12; the file takes about 10 s of wall on a busy machine).

**Full run:** `npm test -- --jobs 3`: 371 of 371 files passed, wall 332.9 s (a local figure on a shared, busy machine, not the CI shard time); the new test file takes under 2 s and the new mutation file about 10 to 20 s (WEIGHTS entry 12). `npm run build`: see the delivery report.

**Limits and open questions:** the call site (where a snapshot is planned and the durable attempt marker), the resolution of a dictionary id to a canonical Film, the durable per-unit failure result and the durable cursor with a plan fingerprint (ADR 0125 consequences; the plan carries the event, the snapshot digest and a deterministic order so both can key on `(event, filmId)` later), the Person-name dictionary and the combined-producer per-run ceiling are NOT built or chosen; the first E6 production measurement of 12 Nov 2026 ([evidence](air-374-e6-production-measurement-2026-11-12.md)) sized Film-facts units only (about 397 per EPG run; 38 round trips for a changed `applyFilmFacts` unit, 14 unchanged, on the offline stand-in), while changedShare, Person/credits volume and the EPG-step budgets remain unmeasured. Owner questions: (1) a stored title that differs, or equals the entry, and has no `titleSource` is kept (`unranked_kept`; an equal one is not claimed) although the writer's own planner would overwrite it; is the conservative rule right, or should a dictionary entry overwrite an unranked title? (2) owner protection reads the identity and localization dimension rows (`authority` `owner`), not `owner_review_entry`; is a reviewed owner value always materialised on those rows before a dictionary unit can run? (3) a title is written only where the identity dimension row exists (it carries `titleSource`); should a Film without that row get one from this layer? The title-source exceptions of the differential registry are related to this layer (it writes `titleSource`) and are not accepted or edited here.
