# MCP endpoint — transport, tools and security contract

Worker `iptv` serves a remote MCP server at `https://iptv.vladimino.workers.dev/mcp`. Cloudflare Access application `IPTV MCP` authenticates every request with Managed OAuth, and the Worker verifies the signed Access JWT. The same endpoint exposes two connection probes and a narrow set of EPG and prediction tools. Those tools call the existing Worker functions. They do not accept a URL, an R2 key, or an API path, and they do not generate fingerprints or predictions: ChatGPT does that and submits the result.

Publishing this Worker does not start sync or prediction and does not enable Scheduled Tasks. A tool writes to R2 only when an authorized caller invokes it. [AIR-62](https://trello.com/c/CU71gW4c) separately restored the two external ChatGPT Scheduled Tasks on 21 October 2026. A deploy does not control their enablement, and additional writer runs or task changes require separate approval. See [deployment.md](../../runbooks/deployment.md) and check live task state. Any isolated production write/read/cleanup test would require separate explicit approval; `probe_echo` does not replace it.

The endpoint lives in the existing Worker. There is no second Worker, no new binding, no Durable Object, and no KV namespace.

## Architecture

```text
ChatGPT (custom MCP server, OAuth) or Claude (claude.ai custom connector, OAuth)
  -> Cloudflare Access application "IPTV MCP" (path /mcp, Managed OAuth, owner-only policy)
       answers unauthenticated requests itself: 401 challenge, OAuth discovery, DCR, /authorize, /token
  -> Worker "iptv": src/mcp.js
       1. verifies the signed Cf-Access-Jwt-Assertion (signature, issuer, audience, time, identity)
       2. validates the Streamable HTTP request
       3. answers JSON-RPC: initialize, notifications/initialized, ping, tools/list, tools/call
```

`src/worker.js` routes only the exact path `/mcp` to `mcpRoute`. Every other path, including `/mcp/`, keeps its existing behaviour, and `/api/*` is unchanged. Access application `All Workers` still protects all other paths.

### Transport

- Streamable HTTP, single endpoint, `POST` only. Every response is one JSON object (`Content-Type: application/json`). The server never opens an SSE stream.
- Stateless: no `Mcp-Session-Id`. `GET` and `DELETE` return `405` with `Allow: POST`. That is the documented response when a server offers no standalone SSE stream and no sessions.
- Protocol versions `2025-11-25` and `2025-06-18` (the `initialize`-based era). `initialize` echoes a supported requested version and otherwise answers `2025-11-25`. Every later message, including `notifications/initialized` and `ping`, must carry a supported `MCP-Protocol-Version` header. Without sessions, the header is the server's only record of the negotiated version. Under the 2025-11-25 transport rules a missing header means `2025-03-26`, which this server does not support, so it gets `400`. `probe_read` reports the version from that header.
- A `2026-07-28` request (stateless era) gets `400` with JSON-RPC code `-32600`, not the modern `-32022`. Under the MCP backward-compatibility rules, a dual-era client treats that as a legacy server and falls back to `initialize`. A client that supports only `2026-07-28` cannot connect.
- Batches, client-sent JSON-RPC responses, malformed JSON, invalid UTF-8, non-JSON `Content-Type` (`415`), an `Accept` header that excludes JSON (`406`), and bodies over 64 KiB (`413`) are rejected. Notifications get `202` with no body.
- A browser `Origin` header must be the Worker's own origin or `https://chatgpt.com`. Any other origin gets `403`. Server-to-server requests without `Origin` are accepted once the Access JWT is valid.

The protocol is implemented directly in `src/mcp.js` instead of through the MCP TypeScript SDK. The build in `build.mjs` concatenates source files without a bundler or runtime npm dependencies. The SDK would add a bundler, dependencies, and Node compatibility flags to the deploy artifact, all for four JSON-RPC methods. `tests/mcp.mjs` exercises the protocol over real HTTP requests through `worker.fetch`.

### Call log

Every authorized `tools/call` with a valid tool-name parameter attempts one structured Worker log line **after tool execution**, so a read of the logs can count calls by named MCP tool (the request log names only `POST /mcp`): `{"event":"mcp_tool_call","tool":"<name>","outcome":"ok|tool_error|rejected|failed","ms":<elapsed>}`. `outcome` is `ok` for a result, `tool_error` for a tool-level error answer, `rejected` for a protocol-level refusal (an unknown tool, an `arguments` value that is not an object) and `failed` when the call threw. The line carries the tool name, the outcome and the elapsed time and **nothing else**: never an argument, a result, an identity or a header. A name that is not a registered tool is logged as `unregistered`, never as the caller's string. Access is verified first, so an unauthenticated call, a malformed request and every method other than `tools/call` write no such line. The line is best-effort and changes no response. Calls rejected before dispatch, including a missing tool name, do not emit a line; an interrupted execution may end without a terminal line. The outcome is what the Worker observed, not proof the caller received the result. **This is a tool-level call counter, not a measurement of per-call SQL statements, D1 rows read, or R2 requests.** Compare aggregate counts with known tool code paths and D1 metrics before making a causal load claim ([AIR-579](https://trello.com/c/OlcWhyM7)).

### Tools

`probe_read`, `probe_echo`, `feature_flags` and `prediction_batch_validate` do not read or write R2; `feature_flags` reads the registered feature flag bindings by name and answers even without a bucket binding; `prediction_batch_validate` runs the submit validators on the caller's own candidate objects and answers even without a bucket binding. `prediction_queue_overview`, `prediction_film_diagnostics`, and `prediction_pending` read a fixed set of stored objects and return that diagnostic with `httpStatus: 200`. They do not call an HTTP route, list storage, or write. `prediction_batch_manifest` reads the stored start answer of one owned `batch_v2` run and writes nothing. Every other tool returns `structuredContent.httpStatus` plus the JSON body of the existing HTTP contract. `400`, `404`, `409`, `503`, and `5xx` set `isError`, and the body stays in `structuredContent` so the caller can still read `Run id mismatch`, `lease_lost`, `busy`, or `Queue not empty`. `already_running` is HTTP 200: stop and do not adopt that `runId`.

### Batch runner tools

**Task label `taskId` ([ADR 0195](../../adr/0195-scheduled-task-id-as-run-owner-label.md)).** Each of the four standing Prediction Tasks sends its fixed, non-secret label (`task00`, `task15`, `task30` or `task45`, a closed enum) on every call of a run. It is **required** by `prediction_batch_manifest`, `prediction_heartbeat`, `prediction_batch_hold`, `prediction_batch_submit` (a real submit; `dryRun: true` needs none) and `prediction_complete`, and by a real scheduled `prediction_batch_start` (`trigger: "scheduled"`, no `dryRun`, no `invocationKey`); without it the call is refused as an MCP tool error **before any storage access**. `prediction_batch_start` rejects `taskId` with `trigger: "manual"`; with `invocationKey` or `deferred` it is only a correlation; a dry run ignores it. `prediction_batch_validate` takes it as a parameter of the Task workflow but it is read-only and never confirms ownership; `enrichment_runner`, `enrichment_status` and `enrichment_queue` accept an optional `taskId` and ignore it. The label is not a secret and not an identity: Cloudflare Access and the JWT are unchanged. The Worker stores it on the run and its lease next to `runId` and `epoch` (which keep fencing every write) and answers a foreign or missing label of a labelled run, and any label on a label-free run, `409 wrong_owner` with no write and no payload (presence and value must match); see [the runner reference](prediction-runner.md#task-label-and-owner-scoped-run-calls-adr-0195).

`prediction_batch_start`, `prediction_batch_validate`, `prediction_batch_hold` and `prediction_batch_submit` are the only prediction runner protocol ([ADR 0122](../../adr/0122-prediction-batch-runner-v2-dual-protocol.md), [ADR 0167](../../adr/0167-retire-prediction-runner-v5.md)). The one-film v5 tools `prediction_start`, `prediction_next`, `prediction_submit` and the standalone `prediction_validate` are retired: they are not in the tool list, and a `tools/call` of one is the JSON-RPC error `-32602 Unknown tool`. A run, a dry run and a Scheduled Task change each still need the owner's explicit approval. Full contract: [batch runner v2](prediction-runner.md#batch-runner-v2). The batch tools accept the optional per-film `assessment` ([ADR 0132](../../adr/0132-prediction-assessment-artifact.md), [contract](prediction-assessment.md)). `prediction_batch_validate` and the submit path derive `fingerprint.sourceBasis` and `sourceRefs` from a valid `evidence` map when both are omitted ([ADR 0129](../../adr/0129-fingerprint-source-fields-derived-from-evidence.md)); a supplied value must still equal the aggregate. **Result size.** A `prediction_batch_start` answer is bounded by 256 KiB (262,144 bytes). Like every tool result, `mcpPayload` sends it twice, as the `text` content and as `structuredContent`, so the `tools/call` result is about 2.1 times larger (measured 524,712 bytes for a 250,622-byte answer). The 64 KiB limit is the *inbound request* limit and does not apply to a result; Cloudflare enforces no response body limit, and the client and model side is unmeasured ([evidence](../../evidence/prediction/air-450-manifest-limit-256kib-2026-11-12.md)).

A keyed real start claims the runner lease (short claim, same epoch, renewed per stage) before its preflights and releases it on every exit that creates no run; a repeat with the same key **and** the same arguments (`scope`, `mode`, `trigger`, resolved `manifestSize`, `capacity`) while the run is live and before any client `batch_submit` returns that run's stored manifest, or `{status: 'start_pending', runId, epoch, retryAfterMs}` after at most 10 s when it is not stored yet (then read it with `prediction_batch_manifest`, which answers `manifest_pending` until it is, or repeat the same keyed start). A different key, other arguments (`reason: key_args_mismatch`), no key, an expired lease or a run with a client submit answer `already_running` as before. The key is stored only as a hash; `dryRun` ignores it and stays write-free. Without a key the start is unchanged. **`deferred: true`** ([ADR 0193](../../adr/0193-deferred-batch-start-with-server-issued-key.md)) needs the key issued by `prediction_batch_key` and is never combined with `dryRun` or `pin`: the start answers a compact receipt `{status: "accepted", runId, epoch, phase, retryAfterMs}` within seconds and prepares the manifest in a Workflow instance; read it with `prediction_batch_manifest` (`manifest_pending`: poll again after `retryAfterMs`; `start_refused` / `start_failed` are final), and repeat the same keyed start for the same receipt. `503 deferred_start_unavailable` means nothing was accepted. **`answer: "envelope"`** (AIR-588, [ADR 0205](../../adr/0205-batch-start-compact-ready-envelope.md); `full` or omitted keeps the whole manifest) returns, for a real synchronous start only, the compact ready envelope of the stored manifest (`kind: envelope`, `status: running`, `runId`, `lease` with `epoch`, `manifestHash`, `limits`, the part list) instead of the whole manifest; the caller reads `profile`, `contract` and every `film` part with `prediction_batch_manifest`, checks them against `manifestHash` and submits under the same `runId` and `epoch`. With `dryRun` or `deferred` it is refused (`envelope_needs_stored_manifest`). The tool returns one text copy, as for a full start. |
| `prediction_batch_validate` | no (`readOnlyHint: true`) | **Accepted architecture (ADR 0131); implementation still subject to exact-HEAD review and CI.** Pure preflight, no HTTP route, no storage read or write, answers without a storage binding ([ADR 0131 (Accepted)](../../adr/0131-batch-candidate-preflight-tool.md)). Argument: `items`, 1 to 10 of `{filmId, fingerprint?, prediction?, assessment?, metadata?}` (closed keys; `prediction_only` sends only `prediction`; `metadata` is the film `modelMetadata`, only when the evidence cites `metadata:*` tokens; at least one of `fingerprint`/`prediction`). Refused whole (tool error, nothing checked): no or more than 10 items, an unknown top-level key, a repeated `filmId`, a request over 56 KiB (57,344 bytes; the MCP inbound limit is 64 KiB). Measured offline: ten realistic candidates are about 44 KB, the answer about 1.6 KB (sent twice as `text` and `structuredContent`), median 3.9 ms in process ([evidence](../../evidence/prediction/air-450-batch-preflight-2026-11-12.md)). |
| `prediction_batch_hold` | yes | `POST /api/enrichment/batch/hold` with `runId`, `epoch` and 1 to 10 already generated items of the owned manifest. Persists them for later `prediction_batch_submit({useHeld:true})`. Not a submit and not a substitute for `prediction_batch_validate` (ADR 0131, ADR 0157). |
| `prediction_batch_submit` | yes (no write with `dryRun: true`) | `POST /api/enrichment/batch/submit` with `runId`, `epoch` (the lease epoch every answer returns) and 1 to 10 items (or `useHeld: true` with no items, loading the hold), validated once per film on the Worker; a failure item must include `failure.reason` (closed vocabulary; omitting it is a 400 and writes nothing). `prediction_heartbeat` and `prediction_complete` are the shared runner tools; they also accept a stored legacy v5 run. A client that caches the tool list sees a change only after it refreshes or reconnects. The response of `prediction_batch_start` is large; the Worker caps it by bytes as well as by count.

All MCP tools require the [Cloudflare Access and Worker JWT validation](#authorization) described below. `epg_sync_step` follows the [discovery continuation contract](#discovery-contract-for-scheduled-tasks). External Scheduled Tasks orchestrate EPG and predictions independently of deployment; D1 is not the authoritative data source for these tools.

Write tools are annotated `readOnlyHint: false`. `enrichment_status` is annotated `readOnlyHint: true`: it shares the HTTP status body, projects an expired lease and does not persist a run or deliver a stop event ([AIR-415](https://trello.com/c/NHyIKM6z)). `tests/get-write-audit.mjs` fails on any read-only tool that has an effect. `epg_sync_start` and `epg_sync_step` are `openWorldHint: true` because they fetch Letterboxd, the configured EPG source, or TMDB. A wrong argument returns a tool result with `isError: true` and does not call the domain function. An unknown tool returns JSON-RPC error `-32602`. The response never contains the caller's identity.

The caller repeats `epg_sync_step` until `stage` is `complete`. It then reads `discovery.nextAction`: `wait` (the normal answer, `reason: delegated`) means the Workflow executes Discovery and no further step is needed to drive it; `stop` means discovery is finished until the next EPG commit; a stored `continue` is only a stored checkpoint of the engine and is never an instruction to call again. `ratingsPending` does not mean retry Letterboxd: no step repeats the films list. A ratings attempt killed before it recorded an outcome is closed as `unknown` by a later step on the completed run ([ratings attempt](../integrations/letterboxd-ratings.md#ratings-attempt)). One call is one metadata batch, the EPG commit, or a seal step; it is never a discovery chunk. A separate request does not guarantee a new isolate. The prediction caller follows the [batch runner v2 flow](prediction-runner.md#batch-runner-v2): one `prediction_batch_start`, then groups of generated films through `prediction_batch_validate` (or the `enrichment_schema` `contract` applied by the caller), `prediction_batch_hold` and `prediction_batch_submit`, then `prediction_complete`. The Worker validates every film again at submit and stores it. A rejected film is a `validation_failure` that names the field and the violation code; the caller fixes that field for the following films, and the rejected film stays deferred under the ordinary retry rules. The Worker is the enforcement point: the preflight tool is available to the client, but whether the external Scheduled Task calls it is decided by that task's prompt, outside this repository.

**Executor fence (AIR-348, [ADR 0100](../../adr/0100-epg-cloudflare-workflow-executor.md), inert).** Once the owner has closed admission of the Cloudflare EPG executor, `epg_sync_start`, `epg_sync_step` and the HTTP routes `/api/sync/start`, `/api/sync/metadata` and `/api/sync/epg` answer HTTP 409 with `reason` `switch_in_progress`, and after the switch to Cloudflare completed `external_writer_fenced` (`nextAction: stop`), and write nothing. `epg_status` (`GET /api/status`) is unaffected and carries the read-only `orchestration` object. Before the switch, and while the table of migration `0017` is not applied, nothing changes.

### Discovery contract for Scheduled Tasks

`epg_sync_step` returns this object once the programme commit has happened. `epg_sync_step` never runs a Discovery chunk (AIR-325): after the commit it answers `wait` / `delegated` while the Cloudflare Workflow has work. The external EPG caller should branch on `nextAction` and not infer it from `ratingsPending` or from `stage` alone.

| `discovery.nextAction` | When | What the caller does |
| --- | --- | --- |
| `continue` | EPG commit (`state: paused`, `reason: epg_committed`, `remainingChunks: 12`), a chunk finished with candidates and budget left, or an orphaned `running` record (`reason: orphaned`: its writer's lease expired without a checkpoint) | Stored engine state, not a caller action. The Workflow continues the series; on an orphan it settles and resumes the same generation, and on a checkpoint of an earlier generation it supersedes it with a new series for the published generation. A client sees `wait` / `delegated` |
| `wait` | `chunk_budget`, `backoff`, `busy`, or `error` before `nextCatchUpAt`; a live `running` record (`reason: busy`, `nextCatchUpAt` = the writer's lease expiry); a newer generation published but not yet in place (`generation_pending`) | Do not call before `discovery.nextCatchUpAt`; `discovery.nextScheduledRunAt` is unused and `null` ([timing](../scheduled-tasks.md#timing-nominal-trigger-versus-server-gate)) |
| `stop` | Backlog finished for the published generation, a programme change seen by the chunk, nothing to resolve, or a series that failed closed after repeated interruptions (`reason: interrupted`, below) | Do not call until the next EPG commit. A checkpoint left behind by an earlier generation (an orphan, a finished series or a programme-changed stop pinned to it) is not a `stop` once a newer generation is published and in place: the Workflow supersedes it (`continue` above). While the pointer already names the new generation but the shared programme has not followed yet, the call writes nothing and answers `wait` with a catch-up time (`diagnostic.branch: generation_pending`) |

**Current rule (AIR-325).** `epg_sync_step`, `POST /api/sync/epg` and `POST /api/enrichment/discovery/resolve` never run a Discovery chunk, settle an orphan, renew a chunk budget or recover an interrupted series: they delegate to the Cloudflare Discovery Workflow (`nextAction: wait`, `reason: delegated`, `delegated: true`) or refuse (`recovery.cause: executor_workflow`). The Workflow owns chunk execution, budget renewal, orphan settlement and interruption handling; the rows and paragraphs below that mention those actions describe the stored `discovery` contract and the engine's rules, not what a caller can trigger. A caller never repeats a step to drive chunks.

**Hourly catch-up after an exhausted chunk budget (AIR-299; renewal is done by the Workflow since AIR-325, a step no longer triggers it).** The published `discovery.nextAction=wait` is a snapshot of the stored checkpoint, not a dynamically recomputed permission to restart a series. The Workflow's plan (formerly the next ordinary `epg_sync_step({runId})`) permits the next series after `nextCatchUpAt` when `continuation.stage=paused`, `reason=chunk_budget`, `remainingChunks=0`, and the checkpoint belongs to the current published generation. `continuationDecision` then replenishes the per-series budget to `DISCOVERY_CHUNK_BUDGET` (currently 12), without an EPG refresh or a forced resolve. The retired external hourly task's authorization was narrower: it requires fresh `epg_status.stage=complete`, exact current-generation agreement in both read-only statuses and the checkpoint, `continuationHealth.status=settled`, no future retry or extra hard wait, no conflicting writer indication, and revalidation immediately before a **single** ordinary step. A `settled` status does not prove an absent live lease; the Worker enforces lease and checkpoint CAS independently. Any `busy`, wait, generation mismatch, error, or unknown result stops this attempt without retry. This is separate from orphaned-`running` recovery and old-generation handoff. See [Scheduled Task contract](../scheduled-tasks.md#hourly-discovery-catch-up-and-predictions).

**Interrupted steps.** When the platform ends a step invocation without a response (for example the Workers memory limit, outcome `exceededMemory`, HTTP 503 from the platform), the MCP client shows a generic error such as `Internal error`. The step's result is then unknown to the caller and the call must not be repeated: the Workflow's own plan reconciles it. Whether the step committed is read from `epg_pipeline_status` (the step's diagnostics entry and the continuation, see below). A series in which two hops in a row end before their checkpoint fails closed: the next step writes `paused` with `reason: interrupted` and answers `stop` without running a chunk, so a chunk that kills its invocation every time is not run again by the Workflow. A new EPG generation opens a new series. Since AIR-325 a forced `POST /api/enrichment/discovery/resolve` runs no chunk and the gated confirm (`recovery: "interrupted"`, same route) is refused with `executor_workflow`; `epg_sync_step` has no such argument. The retired rules are kept in [the enrichment contract](enrichment.md#live-and-orphaned-running-records) as history. `interrupted` stays `stop` until the next EPG commit opens a new series.

**Seal busy answer (AIR-362).** While the staged publication holds `stage: seal`, an `epg_sync_step` that finds the discovery lease held answers `discovery.state=busy`, `nextAction=wait`, `reason=busy` plus `busyKind` (`lease_held` or `lost_race`), `nextCatchUpAt` (ISO time) and `retryAfterSec`. For `lease_held` the time is the stored lease expiry plus a 3 s margin, capped at one lease TTL (90 s) plus the margin from now; for `lost_race` it is 5 s away; it is never less than one second away. The caller waits until `nextCatchUpAt`, then repeats one ordinary step for the same `runId`; the Worker still decides by lease CAS, so an early call is answered `busy` again and moves nothing. The answer is not an error, a reset or a new writer, and a generation mismatch is answered `state=error`, `nextAction=stop`, `reason=programme_changed`, `busyKind=generation_mismatch`, `nextCatchUpAt=null` (no retry time is promised), while `discovery_fence` or an error also stays a stop. A `lease_held` answer exists only with a finite, positive stored expiry; a holder without one is answered as `lost_race` (5 s). The Scheduled Task prompt is not changed by this contract.

**Projector window busy answer (ADR 0103, not active).** While the projector holds an exclusive window, an `epg_sync_step` whose step needs the discovery lease (the commit step before or inside the seal, or the seal step) answers with a normal 200 payload, not a tool error: `discovery.state=busy`, `nextAction=wait`, `reason=busy`, `busyKind=projector_window`, and a `nextCatchUpAt` at the window's absolute deadline plus a 3 s margin (up to about 300 s away, with no lease-TTL cap), and `retryAfterSec`. The run keeps its stage, no `run.error` is stored and no failure or retry is charged. The tool does not wait itself. The daily Task's documented wait covers only a `lease_held` seal busy within about 93 s ([contract](../scheduled-tasks.md)), so the answer is a stop that the Task reports until its prompt is changed by a separate owner decision. The answer exists only with migration `0018` applied and `D1_ENRICHMENT_WINDOW` on.

`discovery.state` is `paused`, `running`, `complete`, `error`, or `busy`. A finished response is not left `running`; a `running` record in `epg_pipeline_status` is read together with `continuationHealth` (`live`, `orphaned`, `settled`, `idle`), which is what distinguishes an active writer from an interrupted one. `remainingChunks` counts chunks still allowed in the current series. The field list, the lease rules and the orphan recovery are in [ENRICHMENT_API.md](enrichment.md#live-and-orphaned-running-records).

### Continuation diagnostics

Every `epg_sync_step` that reaches `POST /api/sync/epg`, and every discovery resolve request, is one **step entry** with two channels. The Worker log gets one structured line per phase (`{"event":"epg_continuation", …}`): `entered` before any storage access, `checkpointed` as soon as the step's discovery hop has stored its continuation checkpoint (before the hop's trailing writes and the response), then `completed` or `failed`, all with the same `id`. The ring `epg/resolver-continuation-diagnostics.json` (newest first, at most 20) gets the same entry written best effort with `phase: entered` before the step, replaced by `checkpointed` and then by the outcome. An entry that is still `entered` or `checkpointed` 15 minutes after its `at` belongs to an invocation that ended without its terminal phase; the next ring write closes it as `phase: interrupted` and logs one `interrupted` line with the same `id`. `epg_pipeline_status` returns the stored ring as `continuationDiagnostics`; reading it writes nothing. The log line is the arrival evidence; the ring is a convenience view that can miss an entry (write failure, eviction after 20 later steps), so an absent ring entry means *no persisted evidence*, not *no call*.

| `interruption` | Only on `interrupted`: `lastPhase` (`entered` or `checkpointed`), `committed` (`true`/`false` from a `checkpointed` entry, `null` (unknown) from an `entered` one), `cause: unknown`, `closedAt`. ## Authorization

Cloudflare Access is the OAuth authorization server and the gate. The Worker issues no OAuth tokens, publishes no protected-resource or authorization-server metadata, and sends no `WWW-Authenticate` header. Cloudflare documents that Managed OAuth replaces the application's `401` behaviour, so a competing challenge from the origin would only confuse clients.

With Managed OAuth, ChatGPT sends an opaque bearer token (`oauth:…`) to Access. Access resolves it to the owner's identity, re-checks the Access policy, and forwards the request with a signed RS256 JWT in `Cf-Access-Jwt-Assertion`. The Worker trusts only that header, after verifying:

- `alg` is `RS256`, and `kid` names a key from `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`. Keys are cached for up to an hour. An unknown `kid` triggers at most one refresh per 30 seconds.
- The RSASSA-PKCS1-v1_5 SHA-256 signature is valid.
- `iss` equals `MCP_ACCESS_TEAM_DOMAIN` exactly.
- `aud` contains `MCP_ACCESS_AUD`, the AUD tag of `IPTV MCP`. A token minted for `All Workers` has a different AUD and is rejected.
- `exp` is present and not past; `nbf` and `iat`, when present, are not in the future. The allowed clock skew is 60 seconds.
- `sub` is a non-empty user identity. Service-token assertions, whose `sub` is empty, are rejected.

The Worker ignores the `CF_Authorization` cookie, `Cf-Access-Authenticated-User-Email` and other identity headers, and the client's own `Authorization` header.

Failures are closed and generic:

| Condition | Response |
| --- | --- |
| `MCP_ACCESS_TEAM_DOMAIN` or `MCP_ACCESS_AUD` missing or malformed | `503`, JSON-RPC `-32603` "MCP authorization is not configured" |
| Signing keys unreachable or unusable | `503`, JSON-RPC `-32603` "Access signing keys are unavailable" |
| Any missing or invalid assertion | `403`, JSON-RPC `-32001` "Forbidden" |

Authorization runs before method, header, and body checks. A caller without a valid assertion learns nothing else about the endpoint. The Worker answers `403` instead of `401`: an assertion mismatch is a server-side configuration problem, and re-running OAuth cannot fix it.

If `IPTV MCP` is disabled or deleted, `/mcp` falls under `All Workers`. That application's JWT carries a different AUD, so the Worker keeps returning `403`.

## Configuration

| Variable | Value | Secret |
| --- | --- | --- |
| `MCP_ACCESS_TEAM_DOMAIN` | `https://<team>.cloudflareaccess.com`, the Zero Trust team domain | No |
| `MCP_ACCESS_AUD` | Application Audience (AUD) tag of Access application `IPTV MCP` (Zero Trust → Access controls → Applications → `IPTV MCP`) | No |

Set both as plain-text variables on Worker `iptv` (Workers & Pages → `iptv` → Settings → Variables and Secrets). They are not committed, following the repository rule that runtime values live in Cloudflare. `wrangler.jsonc` has `keep_vars: true`, so a GitHub deploy keeps dashboard variables. Until both are set, `/mcp` returns `503` behind Access.

Saving a variable publishes a new Worker version. That is a production environment change and needs the owner's explicit approval. No other configuration is involved: the R2 binding `BUCKET` is unchanged, and no secret is added. The probe tools ignore `BUCKET`. The EPG and prediction tools use it only when called.

## Cloudflare Access requirements

This repository change does not modify Cloudflare Access. Each item below must be confirmed by the owner, and any change needs separate approval. Do not add Bypass or Everyone policies, service-token shortcuts, or exceptions to `All Workers` to make discovery work.

1. **`IPTV MCP` application.** Destination `iptv.vladimino.workers.dev/mcp`, owner-only Allow policy, Managed OAuth on. Cloudflare recommends a short access-token lifetime (5–15 minutes) with a longer grant session (1–2 weeks) for agents.
2. **Redirect URI for dynamic client registration.** ChatGPT and Claude register themselves through DCR. Access accepts only redirect URIs on the Managed OAuth allow-list (Advanced settings → Allowed redirect URIs). The working `IPTV MCP` allow-list permits the connected ChatGPT server through the path wildcard `https://chatgpt.com/connector/oauth/*` and, since 25 October 2026, the claude.ai custom connector through `https://claude.ai/api/mcp/auth_callback`. No exact ChatGPT callback was recorded in the UI. An exact callback, `https://chatgpt.com/connector/oauth/<callback_id>` or `https://chatgpt.com/connector_platform_oauth_redirect` when the authorization server advertises RFC 9207 issuer identification (`authorization_response_iss_parameter_supported: true`), is preferable once ChatGPT shows one. Tightening the allow-list is a separate Access change and is not part of this repository change.
3. **RFC 8707 resource indicator.** Access Managed OAuth rejects `/authorize` without `resource` (`invalid_target`). ChatGPT sends the `resource` value from the protected-resource metadata on both the authorization and token requests. That value must be exactly `https://iptv.vladimino.workers.dev/mcp`, with no trailing slash, and the ChatGPT server URL must be the same string.
4. **Discovery reachability on a path-scoped application.** `IPTV MCP` covers only `/mcp`, while `All Workers` covers the rest of the hostname, including `/.well-known/*`. Cloudflare documents that Access serves the challenge and `/.well-known/oauth-authorization-server` for a Managed OAuth application. It does not document which application answers well-known URLs outside the protected path. The 401 challenge must point to metadata that Access serves without an `All Workers` login redirect. Verify this with step 1 of the procedure below. If any discovery URL returns an HTML login page or a `302`, discovery is blocked. Stop and choose a fix with the owner. Possible options, each needing approval and a check against current Cloudflare documentation: an additional `IPTV MCP` destination for the metadata path, or a dedicated hostname for the same Worker that `IPTV MCP` covers entirely.
5. **Authorization-server metadata.** It must include `registration_endpoint`, `code_challenge_methods_supported` with `S256`, and `token_endpoint_auth_methods_supported` with `none`. If it does not advertise `client_id_metadata_document_supported`, choose DCR in ChatGPT, not CIMD.


## Limitations


- Probe tools, `feature_flags` and `prediction_batch_validate` do not touch R2. `feature_flags` shows the bindings of the Worker version that answered; a changed variable publishes a new version, and a client sees it on its next call. The EPG and prediction tools can, and only when an authorized caller invokes them. A connected ChatGPT or Claude client may cache the tool list; a tool added by a deploy appears only after that client refreshes or reconnects the server. Exercising those tools on production, including an isolated write/read/cleanup, needs its own approval. The external Scheduled Tasks were enabled under their own owner approval; new invocations or modifications need separate approval.
- No SSE, sessions, server-to-client requests, `list_changed` notifications, resources, prompts, or batches. Clients that support only `2026-07-28` are not supported.
- The origin allow-list is fixed in code: the Worker's own origin and `https://chatgpt.com`.
- Initial October 19–20 interactive MCP probes did not establish unattended access. [AIR-62](https://trello.com/c/CU71gW4c) subsequently accepted scheduled EPG/prediction runs on October 21; on October 24 both external recurring tasks remained enabled with recent executions. These dated checks do not prove current OAuth health or unspecified security/revocation test results.
- The first request after a cold start fetches Access signing keys from the team domain. If they are unreachable, the endpoint returns `503`.



For approved operator procedures see [MCP connection and verification](../../runbooks/mcp-connectivity.md), and for the original unattended-authorization checklist see [the AIR-62 historical record](../../archive/superseded/mcp-air-62-checklist.md).

**Auxiliary-state backing (ADR 0194, D1 authority since 24 Nov 2026; ADR 0196 `closed` was the state during the cutover).** While the marker is `closed` the mutating batch tools answer the typed refusal `prediction_aux_closed` (HTTP 503 on the route they call) and `prediction_batch_manifest` still reads from the R2 object. `prediction_batch_manifest` reads its parts from D1 pieces, each verified against its digest, since the marker `prediction_aux_authority` became `d1` on 24 Nov 2026 (before that, from R2 objects); the argument and answer shapes are the same. It remains a pure read in both cases.
